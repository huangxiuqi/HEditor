## 光标唯一真源：`caret_` = {段, 段内流位置}（第五批现象，结构性收口）

用户报的第五批：**三层嵌套把控件内文字全删空、光标定位到最后一枚右括号之前再输入字符，

"为什么 caret_ 只数字符、不数括号，括号不是字符？"

**评估结论：模型对，光标存了两套坐标。** 模型里括号是流里的普通元素（每个边界各占一个流位置），
"一个字符一个字符地移动"本来就是在流位置上加减一；而引擎的光标存 (段, 码点偏移) 加一对
`caret_side_` / `caret_side_at_` —— 后两个字段与位置天然可能失配，才需要失效标记兜。

**修法（一个概念）**：`caret_para_` + `caret_rel_`（段内流位置，括号占位算在里面）是唯一真源；
`offset` 与 `side` 全是派生量（`caret()` / `caretSide()`），不可能不同步 ⇒ 失效标记消失。

## 参考：DCWriter 的光标位置模型（读本地源码 `D://Develop//DCWriterLite`）

用户指出本地有 DCWriter 源码（`Source/DCSoft.Writer.Core/`，410 个 .cs）。读了位置那一层，纠正了
此前"只从公开事件参数推断"的粗结论。

**位置表示**（`Dom/DCContent.cs`，3357 行；外层 `Dom/DCSelection.cs`，2444 行）：
`_StartIndex` / `_Length`（实际区域）+ `_NativeStartIndex` / `_NativeLength`（原始区域）+
**`_LineEndFlag`（bool，注释"光标在行尾标记"）**；`DCSelection` 再包 `StartIndex` / `AbsStartIndex` /
`AbsEndIndex` / `Ranges` / `_StartElement` / `_EndElement`（缓存）。

**下标数的是"展开后的扁平元素流"**：`DCContent : DomElementList`，`AppendViewContentElement`
（`Dom/DomContainerElement.cs:1461`）递归把容器子元素摊进这张表，而 **`DomCharElement`（单个字符）
与 `DomParagraphFlagElement`（段落标记）各是一个元素**。`DomElement.ContentIndex` 的注释写明它是
"元素在 Content 列表中的序号，用来加速 IndexOf"。
⇒ **每个字符、每个段落标记各占一位，容器边界天然在流里** —— 与 ProseMirror 的整数 pos 同构，
也正是我们改成 `rel` 之后的形态。此前把它的"扁平下标 + 标记"直接类比成我们的"(码点偏移 + 侧别)"
是错的：它的下标本身数边界，我们的偏移不数。

**`LineEndFlag` 只服务一件事**：同一格上"画在行尾标记之前 / 之后"。`MoveEnd` 里当 index 已是下一个
元素、`InnerFixIndex` 不再改动时置 true（`DCContent.cs:2706`）；`MoveHome` / `MoveStep`（垂直移动）
调 `ClearLineEndFlag()`。它不是"跨过几枚边界"。

**它怎么防位置飘**：`DCSelection.NeedRefresh(newStartIndex, newLength)`（`DCSelection.cs:533`）
同时比对 `_NativeStartIndex`、`_NativeLength`、`OwnerDocument.ContentVersion`、`Content.LineEndFlag`
—— 任一变了就重建整个选择状态。这与我们的 `caret_side_at_` 失效标记是同一个套路（两个独立字段
可能失配，所以需要版本号兜）；我们改成"全部派生"之后这个失效标记就消失了。

**它也把不可见元素从位置流里剔掉**：`if (element._RuntimeVisible == false) continue;`
（`DomContainerElement.cs:1553` / `1568`）⇒ 它的下标是**视图内容表**的下标，不是结构流的下标。
我们上一刀踩到的正是这个坑（`rel` 相对显示表会漂），差别是我们现在把"结构"与"显示"分成两张表、
`rel` 走结构那张。

**对外同样给"容器 + 下标"**：`GetCurrentPositionInfo(out DomContainerElement, out int elementIndex)`、
`GetElementIndexByContentIndex(...)` ⇒ 容器+偏移是**派生量**，与我们的 `caret()` 一致。

**一处真实分歧**：`InnerFixIndex(index, direction, ...)` 的注释是"根据表单视图状态修正插入点位置" ——
DCWriter 在表单视图下会**夹住插入点**；我们的硬决策是**光标位置不受控件约束，只编辑受**（用户报的
"字段点不进去"逼出来的）。这是设计选择差异，不是谁对谁错，但要知道。


## 决策：caret() / caretSide() 保留为派生访问器，不让 LineBox 吃 rel

问的是"既然 rel 是唯一真源，为什么还要派生 caret() 与 caretSide()"。结论：两处必须换算，
且换算点必须收口在这两个命名访问器上（engine.cpp 24 处、diag 4、paint 5、wasm 2 读 caret()；
caretSide() 6 处生产调用 + 一批断言）。

排版层按 cp 索引：LineBox 的簇表是 (cp, 第几枚) 两级（firstClusterAt + bracketCountAt），
offsetAtSide(cp, side) 就是这个签名；侧别是排版的接口语言。宿主算不出 rel ——
rel = cp + 这一处的边界枚数 + 侧别，而"这一处的边界枚数"是引擎内部随树变的结构，
宿主只认 (段, 偏移)。

**不继续收的原因**（以后别再来一遍）：让 LineBox 直接吃 rel 需要给每枚簇挂流位置，而排版只
知道显示出来的那些簇（bracketCountAt 数的是本行括号占位簇）；隐藏括号占位为 0，
"簇序号"与"流位置"不是一一对应 —— 等于把"夹侧别"的动作从 offsetAtSide 挪到建表处，
还得把结构表耦合进排版。收益不大。

**还留着的一条缝**（知道即可）：caretSide() 是结构口径（数全部边界），
LineBox::offsetAtSide 是显示口径（数本行括号占位簇并把侧别夹住）。All 档两者一致，
Focused 档靠夹。漏的是"画在哪一格"，不会漏到编辑归属与删除区间。


## 参考：DCWriter 也是"两套坐标"（四层），而且形状与我们的同构

问的是"这两套坐标别的编辑器也这么做吗"。读源码后：**是，DCWriter 有四层坐标，第 2 层同样是派生量。**

- 真源：`DCContent.Selection.StartIndex`（扁平元素流下标）+ `DCContent.LineEndFlag`（bool）
- 派生·对外：`(DomContainerElement container, int elementIndex)` + `lineEndFlag`，**正反两个显式函数**：
  `GetPositonInfo(contentIndex, out container, out elementIndex, lineEndFlag)` 正算；
  `GetPosition(container, elementIndex, lineEndFlag)` 反算；`GetCurrentPositionInfo(...)` 取光标的。
- 排版侧：`DomElement` 引用 + `DomLine` / `Line.LayoutElements`
- 几何：`MoveToPoint(float x, float y)` / `GetCaretPosition()`

**关键发现**：`GetPositonInfo` 里对 `DomFieldElementBase`（输入域）有**硬编码特判** —— 输入域的
起止各是一个元素，"位置在域之前 / 在域之内末尾"分不出来，于是按元素类型分支处理
（`startElement == element` → container 取 field.Parent；`endElement == element` → container 取 field）。
**这与我们"同一偏移上多枚括号要特判"是同一类问题**，差别是它按类型硬编码，我们是一个计数 + 夹。

**真正的差异（重要）**：`DomCharElement` 持有**单个 `char`**（`CharValue`）—— 它是一字一元素。
所以 DCWriter 的位置流**天然含文本**，模型层没有"文本坐标 vs 流坐标"的分岔。
我们的 `cp_text` 是字符串、边界另存 `objects` 侧表 —— **分岔发生在块模型里，不在光标里**。
要收成一套坐标，得动块模型（把文本也变成元素流），不是动光标。
代价对照：它为性能做了 `AddRangeRaw2` 批量添加、`ContentIndex` 缓存加速 `IndexOf`
（`DomElement.cs:486` 的注释自陈"文档元素多时 IndexOf 缓慢"）、`_InsertOrDeleteTextOnlyFlag`
快速路径 —— 一字一堆对象的模型更重；我们用字符串换掉了这份开销，代价就是两套坐标。


## 术语澄清：cp_text 不是 run（三个"run"概念不要混）

问的是"cp_text 就是那个 textRun 吗"。不是，项目里有三个不同的 run：

- `NodeKind::TextRun`（`src/core/doc/node.h:73`）—— 树里的文本节点，模型层的原子叶子，
  带字符属性（标记）。名字借自 Word 的 w:r。这才是"文本 run"。
- `cp_text`（`src/core/layout/layout.h:110`，`std::vector<uint32_t>`）—— **编译产物里"这一段
  所有 TextRun 的码点首尾相接拼成的那一个数组"**。`compile.cpp:131-133` 逐节点 append，
  同时给 `FormatRun` 记下 `[cp_begin, cp_end)`。**文本节点的边界在拼进去之后就不在 cp_text 里了。**
- `FormatRun`（`layout.h:58`）—— 编译产物里的字符格式 run：只有区间 + 格式，不存文本。
  它是"run 边界"在块流侧的唯一残留，而且相邻同格式的还会被并成一个。
- `FontRun` —— 排版期按字形覆盖再切一次（派生量，不落盘），与 FormatRun 是两把尺子求交。

所以 cp_text 数的是**合并之后的字**，没有节点边界可数 —— 这就是"文本进字符串、边界进侧表"
的具体机制，也是块流侧坐标只能是码点偏移的原因。DCWriter 相反：它一字一元素，节点边界全在。

顺手修了 `layout.h` 里 InlineObject 那段注释：它原文写着"与文本共用一个坐标，于是光标、
命中测试、断行、增量都不需要第二套坐标" —— **这句断言是错的**（共用轴不等于共用位置），
正是它让"同一 cp 上多项对象"这件事一直没被当成坐标问题。改成"共用轴、但位置另有一个分量"。
lint 0 违规、clang-format CLEAN。

2. **`setControls` 自己会重排，`setDocument` 只标脏**（已定位）。试迁移里 `loadControls` 不补
   `relayout()` 就会读到上一份排版（占位看起来没生效，4 项红）。
3. **相邻同标记的文本节点在树里会被合并**（模型层规范化的既定行为）⇒ "把一个 run 切成 N 个
   同属性小 run"这条 ECMA-376 性质**在树上不可表达**（2 项红：整形段数 1 → 1）。要留这条判据，
   得让它走块流层（直接调 `layoutDocument`），不能在树这条路上验。
4. **换控件丢掉了"只重排受影响段"**：旧 `setControls` 只标脏最靠前的控件所在段（判据
   "挂控件只重排第 120 段，其余 79 段原样复用"），树这条路是整份重建 + 全量重排（1 项红）。
   这是**能力损失**（性能，不是正确性），要留就得给树路径加"只重编译/重排受影响段"。
5. ★ **真缺陷（产品路径上一直存在，只是判据走了旧路径所以没暴露）**：在某个**零宽字段的位置上分段**，
   该字段会**整个消失**（`e.controls()` 里按 id 查不到，测试的 `at()` 退回默认区间 [0:0,0:0]）。
   推测：分段插入段落标记后，那个字段的起止边界分落两段 → 变成"跨段控件"，而树里表达不了 →
   被丢。旧路径用 `adjustControlsOnSplit` 的手工账把它推到新段，所以旧判据是绿的。
   **这条要修，不是改判据。**

**结论**：删除旧路径的前置条件不是"迁移 82 处"，是先把上面 3/4/5 三条定下来 ——
要么给树路径补能力，要么明确放弃那三条判据。等用户拍。


## 概念澄清：run 边界为何在 OOXML 里要保留 + 我们只有两条路径

问的三件事，查证后：

**一、ECMA-376 为什么不强制合并同属性相邻 run。** `w:r` 是 `rPr` 的载体，但**不只**：还承载
`w:rsidR`（哪次编辑会话写入）、书签/批注锚点、`w:lang`、`w:proofErr`、修订的 `w:ins/w:del`。
Word 保存时同格式文本碎成许多 run 正是 rsid 不同 —— 这是"相邻同 rPr 的 run"在真实文档里极常见的
原因。规范本身**不强制合并**（合并是可选优化）。关键区分：**渲染层合并无损，存储/往返层合并有损。**

**二、落到我们项目，这条约束的是"存储/往返层"，不是模型层。** 证据：
- `src/core/doc/char_format.h:23` 的 `CharFormat` 只有 6 个**纯格式**字段（bold/italic/underline/
  font_index/size/color），**没有任何 run 级元数据**；第 50 行的注释"逐字段相等就是'标记集合相同'。
  合并相邻文本节点的判据正是它，所以必须是全字段比较"。
- 修订刻意不挂进树：`src/core/doc/revision.h` 开篇"为什么走这条路而不是把修订标记写进文档树"——
  修订是**步骤叠加**（基线 + 未折叠步骤），树永远只表示当前内容。
⇒ 我们合并同属性相邻 run 是**无损**的，这条对我们**不成立**（我们的存储是自研 JSON，不承担
OOXML 的 w:r 级往返保真）。★ **将来会撞上的点**：一旦给 TextRun 挂任何 run 级元数据
（作者/时间、批注锚点、拼写标记、语言），`CharFormat::operator==` 就不再是合法的合并判据，
必须改成"格式相同**且**元数据相同"。

**三、路径只有两条，`layoutDocument` 不是第三条。** 分叉点唯一：**块流从哪来**。
- 树路径：`setDocument(tree)` → `compileDocument(tree, vis, sheet)`（`compile.cpp:307`，
  `engine.cpp:147` 是唯一调用点）→ `blocks_full_` → 排版。
- 旧路径：`setBlocks(vector<BlockSpec>)` → 调用方直接递入 → 排版。
- `layoutDocument(FontLibrary&, const vector<BlockSpec>&, const PageMetrics&)` 是**排版层的自由函数**
  （`src/core/layout/layout.cpp:371`），输入契约就是块流，**本来就在两条路的下游** ——
  所以"直调它"不是另开路径，是退回到它真正的测试对象。
- 直调排版层在项目里是**既有手法**：`tests/edit_test.cpp:4704` 的契约判据（注释原话"契约：排版层
  只吃块流 —— 直接调 layoutDocument（完全不经引擎）也能插出占位簇"）、
  `src/core/engine/engine_audit.cpp:221` 的增量审计拿它当全量对照。

⇒ 第一条的出路 (a)（把"同属性 run 切分"那两条判据改成直调 `layoutDocument`）**不是新发明**，
是把判据放回它本来测的层（排版读不读 runs），与树的规范化解耦。


## 第三条验完：字段没"消失"，是变成了跨段控件（模型未定义）

诊断脚本 `scripts/diag_split_empty_field.mjs`（variant 2 三连字段，先删空 part2/part3）。
cp 7 上压着 5 枚边界（part1 的 ]、part2 的 [ ]、part3 的 [ ]），所以侧别 1 = part2 外面、
侧别 2 = part2 里面。实测：

- 侧别 1（控件外）回车 → **被拒**（正确：落点不在可编辑控件内）。
- 侧别 2（空字段内容位置）回车 → 分段成功，但：
  - 光标 `1:0/0`（新段偏移 0 侧别 0）
  - part1 = `[0:5, 0:7)` 不变；**part2 = `[0:7, 1:0)` 跨段**；part3 = `[1:0, 1:0)` 被带进新段
  - 文本换行成 `患者主诉：反复`
- 所以"字段消失"的说法不准确：**字段没消失，是变成跨段控件**（开括号留旧段、闭括号进新段）。
  光标 rel = 新标记之后那一位，映射到新段 cp 0 侧别 0，而 cp 0 上压着 part2 的 `]` 与
  part3 的 `[ ]` —— 几何上光标贴着 part3 的括号，这就是用户看到的"光标跑到第三个控件里"。

**根因是模型未定义，不是实现的小错**：`Control` 的注释说"允许跨段，但编辑时的伸缩只处理同段
端点"，而 `DemoFieldSpec` 说"段落内置，一个字段不跨段" —— 两句话矛盾，"控件能不能跨段、
跨段怎么算"从没定过。

**旧路径（setBlocks）其实也允许跨段**，而且更宽：`src/core/doc/control.cpp:193`
`adjustControlsOnSplitPara` 把 `e.offset >= pos.offset` 的**两端**都推到新段 —— 于是紧邻断点的
**前一个控件的 end 端点**也被推走（part1 [5,7) 的 end 7 >= 7 → 变成 (0,5)-(1,0) 跨段）。
旧判据只查了 part2，没查 part1 是否跨段，所以绿着。**这说明"跨段控件"两条路都在产生，
只是没人定义过它的语义。**

⇒ 这一条要按模型定夺：**控件允不允许跨段**。两条路：
1. 允许（Word 的 content control 语义）：回车在控件内 → 控件扩张包含新段。则 `Control` 的
   "只处理同段端点"要扩、`DemoFieldSpec` 的"不跨段"要改、`innermostAt`/区间判定/渲染都要支持跨段。
2. 不允许（病历表单语义：一个字段 = 一段）：回车在控件内 → 段落标记插到该控件闭括号之后，
   控件整体留旧段，新段从控件之后开始。
倾向 2（项目定位是病历表单，字段=一段），但这是产品语义，要用户拍。


## 用户拍板：控件是容器，可跨段、可含任意块级内容

原话："肯定是允许啊，文本控件不止能跨段，里面什么都能放，文字、控件、甚至表格"。

**树模型已经支持**：`src/core/doc/node.cpp` 的 `isContainer` 把 `ContentControl` 与 `Table`
都列为容器 ⇒ 控件含段落标记（跨段）、含嵌套控件、含表格，在树里都能表达。缺的只是注释与
判定口径的一致性。

**跨段行为验证（`scripts/diag_split_empty_field.mjs`，三连字段先删空 part2/part3，回车前
cp 7 上压 5 枚边界）**：

| 落点 | 回车结果 | 判定 |
|---|---|---|
| 侧别 1（part2 的 `[` 之前 = part1 的 `]` 之后） | 被拒 | ✓ 正确：落点在两个控件之外 |
| 侧别 2（part2 的 `[` 之后 = 内容位置） | 分段成功 | ✓ 正确 |
| 侧别 3（part2 的 `]` 之后 = part3 的 `[` 之前） | 被拒 | ✓ 正确：同上 |

侧别 2 的详细数字：光标 `1:0/0`、面板 = part2；区间 part1 `[0:5,0:7)`（不变）、

⇒ **用户报的"光标跑到第三个控件里"是视觉误读**：位置与归属都正确，但 part2 的 `[` 留在
上一段行尾、`]` 在新段行首 —— 括号被劈成两半，**而控件没有外框/标签**，看不出"这是一个跨了
两段的控件"。真正缺的是**控件跨段的呈现**（appearance），那是新功能不是 bug。

**顺带发现旧路径的一个真 bug**：`src/core/doc/control.cpp:193` 的 `adjustControlsOnSplitPara`

**要改的注释（与"允许跨段"矛盾）**：
- `src/core/doc/control.h:38`："允许跨段（start.para != end.para），但编辑时的伸缩只处理同段端点"
- `demo/demo_documents.h:36`："段落内置，一个字段不跨段"（那只是演示数据的简化）

  ① 该段在旧产物里有来源身份；② 内容区间（上一枚段落标记之后 → 本段标记）里没有节边界、

## 流索引：两张哈希表换成按 id 下标的数组（那个"下一刀"已落地）

上面那条"下一步（未做）"做完了，而且比原计划更彻底 —— 不是把两张 map 并成一张，
是**两张 map 一起换掉**。

**为什么可以不用哈希**：`NodeId` 是 `NodeTree::next_id_` 递增出来的水位（`node.h` 的
`maxAllocatedId()` 就是它 - 1），所以 id 天然是下标：`first_` / `span_` 各开一个
`std::vector<int>`，大小 = 水位 + 1，构造时 `assign` 一遍就完事。原计划的两张 map
即使并成一张，每个节点仍要一次哈希插入 + 一次哈希查询；数组是顺序写 + 直接索引。

**改动只在 `flow.h` / `flow.cpp` 的私有实现**（公共接口一个字没改，全仓调用方零改动）：
- `inFlow(id)` 从 `first_.find(id) != end()` 变成"这一格不是 -1"（顺带把越界 id 也
  判成"不在流里"，与 map 版本同义）；`firstOf` / `spanOf` 从 `.at()` 变成下标。
- 不在流里的节点（摘下的子树、呈现态下被隐藏的子树）留 -1 —— 与原 map"没有条目"同义。
- 构造的 `reserve(nodeCount())` 两行删了（数组不需要），换成按水位开一次表。

**数字（3000 段 × 20 字，`scripts/diag_compile_cost.mjs`，编辑 5 次取最小）**：
编辑时流索引 **1.3 ~ 1.7ms → 0.000ms**（量程内已测不出）；装载时 0.1ms。

## 改写判据：这一轮把 4 条"假过"和 1 处"自己跟自己比"揪出来了

**一、`demoTree` 会把严格落在别的字段内部的零宽字段整个丢掉（真 bug，已修）。**
`emitFields` 的候选条件是 `f->so >= pos`，而 `pos` 会被前一个字段（`across`）推到它的
`eo`。一个零宽字段落在 `[4,8)` 内部的 5 处，等轮到它时 `pos` 已经是 8 ⇒ `so(5) < pos(8)`
⇒ 被跳过，字段静默消失（[12] 打印的是 `empty=[0:0,0:0]`，那是"找不到"的兜底值）。
修法：候选判据分两种 —— 零宽字段**严格**落在内部（`so > pick->so && eo < pick->eo`）时
跟着递归进去（与老路径 `rangeContainsForNesting` 同一口径），贴在边界上的照旧并列。
演示场景里一个零宽字段都没有，所以这个洞一直没暴露。

**二、`[11]` 那组策略判据原来是拿 `EditPolicy::canInsert/canErase` 直测的**，树路径下
必须改成用真实动作观察（`splitParagraph` / `backspaceAndRender`）。改完暴露三条期望本身
就是错的：
- "只读字段之内：不可以分段" —— 文档里只有一个只读字段时 `formDegraded()` 为真（安全阀：
  一个可编辑控件都没有 ⇒ 表单退化成文档模式），编辑一律放行。要测这一格，**另一段里必须
  再放一个可编辑字段**，否则断言会假过。已在注释里写明。
- "合并点落在可编辑字段末尾：可以合并" / "只读字段末尾：不可以合并" —— 合并判的是
  **前一段那枚段落标记自己那一位可不可编辑**，不是光标落在哪，也不是"字段末尾含端点"。
  字段整段落在某一段里时标记永远在字段之外 ⇒ 表单模式下必拒。反向那一半只能这样造：
  **先在可编辑字段里分段**（字段被拉成跨两段），那枚标记就落进字段内部了 ⇒ 放行。
  这一对（拒 / 放）才是完整的判据。

**三、`[12]` 的空字段往返判据原来是空话。** `const ControlSet& c1 = e.controls();` 之后
`c1` 是常引用、每次编辑就地重建，比较 `c1.at(i)` 与 `e.controls().at(i)` 等于自己跟自己比
（永远为真）。已改成"拆开之前先抄一份 `state_before`，合并回来与它逐 id 比对区间"。
顺带把空字段那一格的期望改对：光标落在 5 这个位置上时它是"最内层含端点"的那一个，
标记插在它那一对括号中间 ⇒ 它**跟着断到两段**（与 `across` 同一个形状），得到
`(0,5)-(1,0)`；老路径按区间算术给 `(1:0)-(1:0)`，那是"控件不是节点"时代的产物。

**四、`[29](a)(b)` 原来是自己跟自己比。** 我上一轮把 `loadBlocks` 实现成
`setDocument(demoTree(...))` 之后，`loadBlocks(a, blocks)` 与
`b.setDocument(demoTree(blocks, {}), ...)` 是**逐字相同的调用**，两帧当然一样。
重写成两件真事：
- (a) **往返**：源块流（末段手工挂 3 个 run）→ 树 → 编译回来的块流逐字段相同
  （文本 / 块级字段 / `effectiveRuns`），再加"装载之后增量上屏 == 从零上屏"（0 像素）。
  比 `effectiveRuns` 而不是 `runs`：源里"runs 为空"表示整段一个 run，编译回来一定显式产
  一条 —— 两者是同一形状，直接比 `runs` 会把三个演示段全判成不一致。
- (b) **绝对期望**：四条控件区间、嵌套深度 0/1/2/0、父子关系、业务类型，加
  "增量上屏 ≈ 从零上屏"（带控件的参照引擎，`list` 要传进去，空表会让参照物丢字段）。

**五、术语统一**：文件里的"两条路"统一成"两种建树"（48 处）。旧装载入口退役之后，
两个引擎比的是**两种建树方式**：块流 + 字段名单交给 `demoTree`（"块流路"）与逐节点手工建

## `tree_valid_` 怎么收敛（这条别让后来人重新推）

它的每一处分支都在区分"树有 / 没有"，处理办法是**树路径下两边同时跑一遍**：

- **编辑入口**一律只留树分支（旧分支整段删）。
- **审计入口**用 `loaded_` 保留"没装载过"这半边 —— `not-loaded` 时返回 `0` /
  `{"diff":0,"note":"not-loaded"}`，而不是拿一棵空树去编出 0 段来。
- ★ **只有一处例外**：`tabCaret` 末尾"退回 `focusControl`"那一支被**结构性删除** ——
  `focusControl` 给的目标与 `tabFrom` 的口径不同（前者按区间、后者按可编辑集合），
  不是"两边同时跑一遍"能覆盖的。

**`loaded_` 为什么必须有**（不是"树有效"的换名）：`g_engine` 是全局对象，`main()` 先于任何装载跑；
"没装载过"是一个真实状态。它的语义是"**装载过文档没有**"，编辑入口一律拒绝、审计入口报
"没有可比的东西"。

## 顺手量了"构建为什么这么慢"（用户问的）

结论：**不是每次全量**。分项实测（脚本 `out/_t_build.ps1` / `_t_build2.ps1`，机器 i7-8550U / 8 线程 / 16 GB）：

| 场景 | 实测 |
|---|---|
| `ninja` 无改动 | **0 个计划步骤，0.8 s** |
| 改一个 `.cpp` | **13 s**（含 6 个链接产物） |
| ★ 改 `src/core` 下**任意一个头文件** | **380 s（6 分 20 秒）** —— 12 个 core TU 全重编 |
| 改 HarfBuzz 自己的头 | **106 s** —— `harfbuzz.cc`（69 个 .cc 合成一个 TU）重编 |
| `cmake --build` 比直接 `ninja` 多花 | 约 **12 s**（`GLOB CONFIGURE_DEPENDS` 预检查） |
| `build_native.ps1 -Run` 稳态 | **54 s**（其中 `heditor_edit_tests` 一项 27 s） |

两个真因：
1. **`heditor_track_header_deps()` 的粒度是有意做粗的**（`OBJECT_DEPENDS` 把 `src/core` 全部头文件
   挂在每个 core TU 上）—— 代价是改一个头 = 重编 12 个 TU，换来的是**绝不会静默用旧对象**
   （本机 MSVC + Ninja + C++20 的头依赖追踪开箱就是坏的，坑见陷阱 18）。
2. **`HEDITOR_BUILD_STAMP` 每次配置都变** ⇒ `native_main.cpp` / `wasm_main.cpp` 每次构建都重编。

★ **另一个发现：并行跑两个后端会互相拖慢**。native 独占 54 s，与 `build_wasm.ps1` 同时跑时
实测 **6 分 34 秒**（4~7 倍）—— 两个构建都吃满这 8 个逻辑核。以后 `build_native` 与 `build_wasm`
**别同时跑**，看着省时间实则翻倍。这也解释了本任务早期那几次"6 分多钟"的记录：当时正是并行跑的
（日志里只有 2~3 个 TU 重编，时间却对不上 —— 对得上才怪）。

## 守卫为什么也慢（实测 ~8 分钟）

`verify_header_deps.ps1` 的时间几乎全在两处**故意制造的**重编上：
- 第 3 步推 `engine.h` 的 mtime ⇒ 12 个 core TU 全重编（~380 s）；
- 第 5 步推 HarfBuzz 头的 mtime ⇒ `harfbuzz.cc.obj` 重编（~106 s）。
它要证的就是这两条依赖边**真的存在**，所以**没有可省的地方**（删掉 `OBJECT_DEPENDS` 时它必须变红）。
它还会额外跑 3 次 no-op ninja（~3 s）与 6 个链接。

★ 顺带一个自己踩的坑：量 HarfBuzz TU 时第一次用 `Get-ChildItem -Recurse -Filter hb-version.h`
取"第一个"匹配 —— 拿到的是 `.toolchain/skia/.../harfbuzz/src/hb-version.h`（**不在构建图里**），
于是量出 2.6 s 的假数。守卫自己是从**产物 obj 的路径反推**源码根的，不写死、也不猜。

# 更正：头依赖"坏"不是工具坏了，是我把构建目录的代码页弄成两边不一致

触发是一句提醒：**"有些东西可能不是坏了，而是你的环境里不好使。"** 去量，量出来是我错了。

## 真机制

`cl.exe` 的 `/showIncludes` 前缀是本地化的「注意: 包含文件: 」，它的**字节编码跟随控制台输出
代码页**；CMake 用同一个代码页解释那句输出、**原样**写进 `rules.ninja` 的 `msvc_deps_prefix`；
ninja 再拿它去**逐字节**匹配 cl 的输出。同一条命令只改代码页，实测：

| 控制台输出代码页 | cl 吐出的前缀字节 | 是什么 |
| --- | --- | --- |
| 936 | `D7 A2 D2 E2 3A 20 B0 FC BA AC CE C4 BC FE 3A 20` | GBK 的「注意: 包含文件: 」 |
| 65001 | `E6 B3 A8 E6 84 8F 3A 20 E5 8C 85 …` | UTF-8 的同一串 |

判据因此只有一条：**configure 与 build 处在同一个代码页**。全新目录 + 两端同码页，`ninja -t deps`
实测 **`#deps 50`**（936 与 65001 各测一次，都是 50）；不一致则一条都不记，而且**不报错**。

白天那轮"MSVC + Ninja + C++20 的头依赖追踪开箱就是坏的"是**误判**：坏的是那一刻 `build/native`
里**残留的前缀字节**（`E5 A8 89…` = UTF-8 的「娉ㄦ剰」，即"UTF-8 被当 GBK 解码再编回 UTF-8"的
双层编码），它跟任何代码页下 cl 的输出都不相等。它由**某次会话的码页组合**写进去 ——
而来源就是**我自己**：每条命令开头都设 `[Console]::OutputEncoding = UTF8`（"防日志乱码"的旧习惯）。
普通会话默认就是 **936**（`chcp` 实测），所以"工具本来就坏"这个结论从一开始就站不住。

## 顺手排掉的岔路

- **VSLANG=1033 / 804 无效**：cl 的文案语言不跟它走（三种取值输出**逐字节相同**）⇒ 没有"让 cl 说
  英文、前缀变 ASCII、彻底免疫代码页"这条捷径（这是最想走的那条）。
- **CMake 缓存编译器探测结果**（`CMakeFiles/4.1.0/CMakeCXXCompiler.cmake`）：换了码页**只重配不会
  重新探测**，前缀一动一不动（实测：CP 报 936、前缀仍是旧的 UTF-8）⇒ 修的时候必须把
  `CMakeCache.txt` 与 `CMakeFiles/<版本>/` 挪开（我挪成了 `.bak`），让探测重跑。探测在
  `CMakeDetermineCompilerId.cmake:250` 的 `CMAKE_DETERMINE_MSVC_SHOWINCLUDES_PREFIX`。

  上屏 = `putImageData` 的源矩形切片（零拷贝），只贴 `dirtyPages` 报的页。
- 窗口 = 可见页 ∪ 光标页，封顶 3 页，**带滞回**；换文档前 `presetWindowForLoad()` 先摆锚点。
- 兼容层 `frameCanvasProxy`（老探针把帧当一张画布用）；`__heditor.blitBox` 退役 → `dirtyPages`。

**效果（实测，`scripts/diag_perf.mjs`）**：
- 合成那一笔 **16.6 ms → 0.0 ms**（画布可见 vs 不可见的对照；5 档 zoom 里 4 档为 0.0）。
- 装载 200 段：**447 ms → ~190 ms**；3000 段的帧 **73 Mpx → 3.4 Mpx**（wasm 两张位图 587 MB → ~4 MB）。
- 剩下的一半：单拍操作 17~23 ms，其中**字形光栅 10~14 ms**（整页约 1000 个字形每帧重画一遍）
  ⇒ 行级重光栅是下一刀。宿主收尾只 2.9 ms。

**判据**：native 803 / 706 / 55 全绿；`edit_probe.mjs` **202 项 0 失败**；`stress_probe.mjs` 69 次点击 0 不一致。

**这一刀踩到的四个坑**（详见 `TRAPS.md` 第 20 条）：
1. `EditStats::total_pages` 一度改成"帧里那几页"，宿主于是把整篇当成 1 页（帧恒 1 页、滚不动）。
2. 换文档时先重排、后设锚点 ⇒ 按上一篇文档的锚点栅格化，且"装载账"被后一次呈现覆盖（5 条断言红）。
3. 收尾顺序反了（先对窗口再滚光标）⇒ 光标在第 0 页、屏幕停在第 15 页时窗口被拉成整篇。
4. ★ **`putImageData(img, dx, dy, dirtyX, dirtyY, w, h)` 的目标位置是 `(dx+dirtyX, dy+dirtyY)`**，
   不是 `(dx,dy)` —— 实测确认（4×4 画布上贴源 y=4 那一块，`putImageData(img,0,0,0,4,4,4)` 什么都不发生）。
   写成 `(img, 0, 0, 0, srcY, w, ph)` 会把第 2 页起的内容画到画布外，症状是"只有第 1 页对、其余页停在旧内容"。
   正解：`putImageData(img, 0, -srcY, 0, srcY, w, ph)`。

## 补刀：多页时点第二页"乱滚"

**两处独立的错，都是"帧坐标 → 页号"漏了窗口首页的偏移**：
1. 宿主 `scrollCaretIntoView`：写成 `caretPage * step + caretY`，而 `caretY` 已经是
   "窗口帧内的 y"（含了 `(caretPage - 窗口首页) * step`）⇒ 页偏移算两遍，光标坐标落到下一页，
   屏幕往下冲。正解 `窗口首页 * step + caretY`。
2. 引擎 `hitTestPt`：`page = floor(y_pt_frame / stride)` 隐含"帧从第 0 页起"。
   窗口化之后帧坐标是窗口内的 ⇒ 点第二页被判成第一页，光标跳到别处、屏幕跟着滚。
   正解：`doc_y = y_pt_frame + base_first_page_ * stride`，再用它算 page 与 local_y
   —— 与 `caretRectPx` 的 `off_y` 对称。

**判据**（`edit_probe.mjs` 第 [9] 节新增两条，断言总数 202 → 204）：
"点第二页光标所在那一行：页不变、滚动量小于半页（不乱滚）" + "点第二页之后屏幕 == 引擎帧"。
取点选在"光标当前所在的那一行"——它一定看得见，所以根本不该把页面挪走。
修前实测 光标页 1 → 0、滚动 1331 → 469 px；修后 **1 → 1、1331 → 1331（一次都不滚）**。

★ 这条也说明：窗口化之后凡"坐标 → 页号"的地方都要复查一遍（已复查 `caretRectPx`、`hitTestPt`、
`controlAtPt`（走 hitTestPt）、`drawControlMarks`、`positionIme`、`framePointFromEvent`、`clickAt`）。

## 第二刀：行带重画（页粒度 → 行粒度）

**做法**：行指纹（与页指纹同一次遍历、同一把尺子，下标 = `LineBox::line`）+
`line_lo/hi_in_base_`（底图里每条行带的块轴范围）。增量分支里页指纹变了 →
按行指纹找连续差异段 `[d0,d1]` → 只重画这一条带，帧也只贴这条带。
带边界取**与相邻行盒的中线**（新旧两版取更靠外的），页边框每次补画。

**实测（`scripts/diag_perf.mjs`，200 段 / 16 页 / 1.5 倍）**：
- 单拍操作 **21.2 → 5.0 ms**；paint **12.2~17.0 → 0.8~1.2 ms**；字形 **9.6~14.2 → 0.7~0.8 ms**。
- 重画像素 1.14 M（整页）→ **147 k（4.3%）**。
- **帧间隔 33.3 → 16.7 ms，30 拍 0 慢帧**。

**判据**：native 803 / **707** / 55，浏览器 **204** + 压力 69，全绿；lint 110 文件 0 违规。
新增 `EditStats::band_y0/y1`（面板显示"重画行带"）。

★ 两条**过期判据**顺手改掉（"该页整页重画"、"每一次按键都整页重画"）：它们编码的是旧页粒度。
★ 两个坑：带边界不能用行盒自己的 block_lo/hi（会啃相邻行的抗锯齿边）；页边框要补画
（差 4308 = `2×(893+1263)-4`）。
