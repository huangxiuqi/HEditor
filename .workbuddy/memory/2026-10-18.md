# 2026-10-18 台账

## 1. 折行处的行首/行尾是两个位置（光标行别）

**报障**：光标定不到行首 —— 鼠标一点行首，光标就跑到上一行的行尾。

**根因**：一段排满折行时，上一行的末尾与下一行的开头是**同一个位置**（偏移一样、侧别一样）。
`findLineFor` 只按位置找行，取的是"先遇到的那一枚"口行盒 ⇒ 点下一行行首必然画到上一行行尾。
这不是命中测试算错，是**信息在落点上丢了**（Chromium 里同一个问题叫 `Affinity`：
upstream / downstream）。

**修法**：给光标加一个会话状态 `caret_line_aff_`（0 = 贴上一行行尾，1 = 贴下一行行首）。

- 命中测试算出它：`cp == best->first_cp && best->first_cp != 0` ⇒ 1（段首那一行不算，它前面没有上一行）。
- 一路带出去：`hitTest` 的 JSON 多一个 `line` 字段 → `setCaretAtSideLine` / `setFocusAtSideLine`
  → `projectCaret(..., line_aff)` → `setCaretRel(..., line_aff)`（唯一写入点）。
- 一路吃进去：`findLineFor(pos, aff)`（aff>0 取"最后一枚"含该位置的行）、`caretRectFor`、
  `caretInlineAxisPt`、`moveCaretVertical`、`moveCaretToLineStart/End`。
- **清回 0**：任何别的定位（打字、方向键、程序化摆位、setCaretAtSide）都把它清成 0 ——
  与上下键列位同一待遇。写完字光标本来就该贴在前一个字后面，而那在上一行末尾。

**顺带修掉的一族**：光标在行首按 ArrowDown 原来"原地不动"（当前行被取成上一行，Down 落到
下一行，位置与光标一模一样 ⇒ `moveCaretVertical` 判成"没动"）。行别修好之后这条自动消失。

**判据两条**：
- native `edit_test [41]`：同一偏移两次点击（下一行行首 / 上一行行尾）—— 偏移与侧别都相同、
  行别一个 0 一个 1、光标各自画在自己那一行；**再加一条反向的一半**：不带行别的老路径
  仍然画到上一行（把 bug 本身写成判据，证明这条判据对它敏感）。
- 浏览器 `out/_linehead.mjs`：真 `clickAt`（走宿主的坐标换算与 `placeAt`），判"光标 y 与
  被点那一行行首的距离 < 半个行距"。★ 别用"行带 ± 容差"判 —— 两条带紧挨着，容差一给就
  互相包含，画错行也能通过。

★ 记一笔：Chrome 在 `vertical-rl` 里做"上一个字"时，如果那个字正好在上一列末尾，
它也是把光标画在**上一列的列尾**（不是下一列列首）。所以"贴上一行"是通用默认，行别只在
用户明确点到下一行时才翻。

## 2. 竖排方向键：物理方向 = 移动方向（含蒙文左右相反）

**报障**：竖排时键盘左右变成上下、上下变成左右。

**先测参考行为**（`out/_vkeyref.mjs` + `out/_vkeyref.html`）：Chrome 原生 `vertical-rl` 的
contenteditable 里真按键，读 `anchorOffset` 与插入点矩形。

| 键 | vertical-rl（列自右向左） | vertical-lr（列自左向右） |
| --- | --- | --- |
| ArrowLeft | x -20（左一列）= 文本前进 | x -20（左一列）= **文本后退** |
| ArrowRight | x +20（右一列）= 文本后退 | x +20（右一列）= **文本前进** |
| ArrowUp | 列内，文本后退（-1） | 列内，文本后退（-1） |
| ArrowDown | 列内，文本前进（+1） | 列内，文本前进（+1） |

⇒ 通行约定是"**物理方向 = 视觉移动方向**"，不是"按逻辑轴分配键"。我们原来按逻辑轴
（左右 = 行内、上下 = 块轴）分配，于是竖排下全反。★ 而"往左是文本前进还是后退"随**列序**
翻转 —— 这就是用户问的"蒙文竖排的左右是反的，就是这样的吗"：**屏幕上不是反的**（左右键
永远往屏幕那一侧走），**文本前后是反的**（蒙文列自左向右，中日列自右向左）。

**修法**：`keyToOp`（两宿主各一份）按两条输入映射：`caretVertical` 与 `caretBlockReversed`。

- 横排：原样（左右走字、上下换行）。
- 竖排：上下走字；左右换列，方向由列序定 —— `dirLeft = blockReversed ? +1 : -1`。
- **蒙文是另一套**：`VerticalLR`（列自左向右、字形侧倒），所以同一个 ArrowLeft 在蒙文里是
  "上一列"（文本后退），在中日竖排里是"下一列"（文本前进）。**只给"是竖排吗"一定会把蒙文
  的左右按反** —— 这是本轮用户追问"蒙文竖排的左右是反的，就是这样的吗"的直接答案：
  按屏幕方向看不是反的（左右键永远往屏幕那一侧走），按文本前后看才是反的（列序相反）。

**判据** `out/_vkeys.mjs`（真按键，两个场景各一遍：2 = 中文竖排、1 = 蒙文竖排）：

- 同列内：Down 前进、Up 后退、**x 不动**，再按 Up 原路退回同一个字。
- 换列：偏移跳 > 10 个字；**ArrowLeft 一律往屏幕左、ArrowRight 一律往屏幕右**（两种竖排都必须成立）；
  另一半随列序翻转：中文往左是前进、蒙文往左是后退。
  ★ 只判前一半的话，把蒙文按反也能通过。
- 换列再换回来，回到出发那一列（两个方向的符号都对才成立）。

★ 写探针时的两个坑：① 起点不能紧贴列首（"退一个字"会落到上一列末尾，那是同一个位置）；
② 蒙文一个簇可能两个码点，落在簇内部的偏移会被吸附 ⇒ 起点用"设进去能原样读回来"来挑。

**引擎侧的判据** `edit_test [43]`：中日竖排 `moveCaretVertical(+1)` 的 x 变小、`-1` 走回来；
蒙文同一份文本只换列序，`+1` 的 x 变大。判的是**位置的 x**，不是标志位 —— 标志位对了、
算出来的位置反了照样是错的。

## 3. undo 之后光标落到被恢复字符的前面

**报障**：删除一个字符后按 undo，光标跑到这个字符前面。

**根因**：`eraseOnTree` 把 `selection_before` 一律记成**删除区间的起点**。撤销恢复的是
这一份快照，所以：

- 前删（Delete）：删除前光标在起点 —— 记起点是对的；
- 退格（Backspace）/ 反缩进：删除前光标在**终点** —— 记起点就落到被恢复的字前面。

**修法**：`eraseOnTree(a, b, label, caret_at_end)`；退格与反缩进传 true（`caret_before = to`），
前删用默认 false。

**判据** `edit_test [42]`：三条路径各自"撤销之后偏移回到编辑之前"。一条判据同时压住三处 ——
记错一端的那条会当场掉出来。另外补一条重做（回到编辑之后那一格），两条快照的方向不能混。

## 5. 控件边界上的删除（退格 / 前删）—— 用户报"删控件只把括号删掉了"

**规则**（用户给的，从左到右；参照 `D:/Develop/DCWriterLite` 的 `DocumentControler.Backspace`
/ `Delete`）：

| 光标位置 | 控件有内容 | 控件为空 |
| --- | --- | --- |
| 退格 · 闭括号右面 | 进控件，删左边那一项 | 删控件 |
| 退格 · 开括号右面 | 退到开括号左面，不删 | 删控件 |
| 前删 · 开括号左面 | 进控件，删右边那一项 | 删控件 |
| 前删 · 闭括号左面 | 跳到闭括号右面，删右边那一项 | 删控件 |

- "进控件"是递归的：内容里最后一项若是个非空控件就再往里进一层（删的始终只有一个东西）。
- 四条全落在**流位置**上判：这些格子两两共用同一个码点偏移。
- 旧行为（"退役控件、内容留成正文"= 拆壳）从键盘路径**撤掉**；`removeControl(keep_content)`
  这个 API 保留（宿主按钮、探针仍在用）。

**实现**：`engine.cpp` 新增 `controlFlowSpan` / `controlIsEmpty` / `controlEndingAt` /
`controlStartingAt` + `bracketBackspace` / `bracketDeleteForward`（返回
`BracketHit{None, MoveOnly, MoveThenErase, Handled}`）。`backspace()` / `deleteForward()` 先过它，
`MoveThenErase` 时把光标摆好再落回**原来的普通删除**那一段（不另写一套删字）。

**顺手挖出并修掉的两个模型层缺陷**（都不是本轮引入的）：

1. ★★ `InsertNode` / `RemoveNode` 还在按"孩子槽位下标"定位 —— TRAPS 39 那条只改了

   ★ 另外：`canApply` 里取"某个孩子自己的槽位"**不能用 `posAt`** —— 它对叶子孩子会把

## 6. 竖排列宽逐列算（阶段 1 的最后一条尾巴）

**先做的确认**（这一步的价值就在这里）：阶段 1 剩的两条尾巴里，
- **竖排逐列变宽**：真的差距，做了。
- **`line_factor` 与段后距按 run**：**不成立**。模型层把它们放在 `ParaFormat`（段落属性），
  OOXML 的 `w:spacing` 也在 `w:pPr`（段落属性），Word 的行距与段后距只在段落上设。
  ⇒ 引擎输入里它们留在 `BlockSpec` 的块级字段，**不进 `FormatRun`**。上一轮把它们列成"尾巴"是错的。
- **`LineBox` 的形状不用改**：`size_pt` / `block_lo_pt` / `block_hi_pt` 本来就能表达"这一列自己的
  范围"。⇒ **光标/命中测试与命令层的拆分不再被阶段 1 卡住，现在就能做**（原判断"先确认改不改
  `LineBox` 的字段"的答案：不改）。

**改法**（`layout.cpp` 的竖排分支）：列宽 = **该列**所有 run 的最大字号 × 行距；列位由**前缀和**
推进（中日从右边缘往左、蒙文从左边缘往右，各记一个 `next_edge`）；"本列放不下就换带"这一步
只能放在**这一列的内容定下来之后**（列宽是逐列算的），而**列长与列宽无关** ⇒ 换带之后同一段
内容仍装得下，不必重取。原以为的"要连列序与页内列数一起重算"没有循环依赖。
`col_w_max`（整段最大）只留作分页估计的上界与 `avail` 的安全阀。

**判据** `tests/shaping_test.cpp [7]`（+10 项，`heditor_tests` 94 → 104）：把内容高度压到装不下
两个字 ⇒ 一个字符一列，列的归属不依赖字号（判据因此不脆）。八列、字号 24/12 交替，逐列断言
"字号 = 本列最大字号"、"列宽 = 字号 × 行距"、"不越出内容框"、"同页两两不重叠"、"列号小的更靠右"，
加"大字列真的比小字列宽"这条对照，加反向一半（整段一个字号 ⇒ 所有列宽相等且 = 字号 × 行距）。
★ **注入旧行为（列宽取整段最大）当场两红**（大字列宽 38.40 与 38.40 相等），反向那一半照绿 ——
正是它该有的样子。

- **行盒几何与命中**：`findLineFor` / `caretRectFor` / `caretRectPt` / `caretPage` /

移动族的公开入口因此是 4~6 行：记计划 id → 调解析器 → 按需重排 →（行首行尾）按新簇表再投影。

**输入是一份只读视图** `PositionView`（9 个指针：两张块表、块起点与跨度、流索引、控件集合、
节点 id 表、id→下标表、排版结果）。解析器不持引擎指针。

★★ **两个真踩到的坑**（写进 TRAPS）：

1. **视图只存地址 ⇒ 摆的时机**：`setDocument` 会先落一次光标再重建，而那时视图还没摆 ⇒
   空指针崩溃。收口点改成 `init` / `setDocument` / `rebuildFromTree` / `relayout` 各摆一次。
2. **流索引要持 `std::optional` 的地址，不是它内容的地址**：`flow_` 是"重建时 emplace 进去"
   的，第一次重建之前它还没建 ⇒ 持内容地址会拿到空指针并**一直空下去**。症状是
   `flowPosAt` 全返回 -1（编辑被判越界、`edit_test [26]` 整节 15 条红）。

★ **机械搬迁的方法**（这次没手抄一行，全靠脚本 + 编译器兜底）：
用花括号配平从 engine.cpp 切出每个方法的 [注释 + 定义]，把 `EditorEngine::` 换成
`CaretResolver::`、把成员名按"占位符 + 长名优先"换成视图（**必须先占位再替换**，否则
`blocks_` 会吃掉 `blocks_full_` 的前缀）；引擎侧把公开方法的定义换成 1~8 行前向器、
私有助手的调用点统一加 `caret_.` 前缀。★ 切范围时 **一行的函数体**（`int caretSide() const
{ return ...; }`）会让"累计花括号到 0"的循环判不出结束 —— 必须按**逐字符**累计并记 started，
否则范围会一路吞到下一个多行函数（这次就是这么把 `projectCaret` 的头部吃掉的）。
★ 范围算完必须**查重叠**：重叠范围按"从后往前替换"会让行号错位，静默毁文件。

## 11. 用户报"第二个行距没了"：行高把行距吃掉了

**症状**：在场景 9 里敲一段长文本把它顶到折行，带原子那一行的下一行贴到了盒底上。

## 13. 表格（阶段 5）开工前的两个概念澄清（写进设计文档）

**一、"跨页"是三件事，不是一件。** 上一轮我把它们捆成"跨页拆行 + 表头重复"一刀，是错的：

| 行为 | 是什么 | 粒度 | 状态 |
| --- | --- | --- | --- |
| 行跨页断开 | 一行太高就在页边界切开，切点**没有横线**（左右边框在页底截断、下一页接着画） | 每段的开关，默认允许 | 待做（分页器只有"整行往前排"） |
| 重复标题行 | 表跨页时把开头几行在每页顶端再画一遍 | **逐行属性**（`TableSpec::header_rows`） | 待做，可以晚于上一条 |
| 纵向合并的格跨页 | 跨页的 rowspan 格在下一页重复显示内容 | 排版产物，不进模型 | **已定**，依赖第一条 |

未定一处：重复出来的表头在模型里只有一份、产物里每页一份 ⇒ 命中副本落到原件还是不可编辑。

**二、"扁平化 + 单元格标注"能支持格内任意内容（含嵌套表格、控件），但标注必须是路径。**
- 模型层本来就允许：`acceptsChild` 对 `TableCell` 是"什么都收"；`FlowIndex` 给表 / 行 / 格
  各算了一对边界位置 ⇒ **"格里的位置"本来就是流位置**（不需要新概念）。
- 输入扁平、过程分层：排版按"格 → 行 → 表"递归（格内块 = 路径以该格为前缀的连续块），
  行高 = 该行各格的大者，表高 = 各行之和；嵌套表在内层格宽度里递归同一个过程。
- 产物必须加一张**单元格表**（矩形 / 逻辑行列 / 原点格 / 所在页 / 页内片段号），`LineBox`
  只多带一个格下标 —— 一个格的矩形不由某一行决定，从 `LineBox` 推不出来。
- 真正的工作量在**行为**不在形状：格内上下走到头、Tab 到下一格 / 末格新建行、跨格选区的
  矩形按格裁剪、跨格删除的语义。
- 嵌套表会让 autoFit 变成递归约束（内层表宽贡献外层列宽）⇒ 第一刀只做固定 / 作者指定列宽。

文档：`docs/文档模型设计.md` 第九节新增"跨页要拆成三件事说"、十四节新增"表格是第三样新输入"；
行数不变量 2699 → **2744**（LF、四个禁用串仍为 0）。
