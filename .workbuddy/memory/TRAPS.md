# HEditor 会复发的陷阱（速查）

从 `MEMORY.md` 拆出（体量原因）。这里是"踩过、改好了、但会再犯"的清单，动手改这些区域前先扫一眼。

## 模型与语义
1. `NodeTree::find` 也能查到**已摘下的子树** ⇒ 判"还在文档里吗"用 `isAttached`（也可判它"被整块摘下"）。
2. 批量构建步骤时**每步的流位置会过期** ⇒ 用 `pushMappedStep` 推坐标。
3. **编译产物是只读输出**：`blocks_` / `blocks_full_` 上的 `cp_text`、`runs`、`objects` 三者是
   编译一次写定的，手工改其中一项就会让另两项的锚点失配（run 铺不满文本 ⇒ 排版在尾部取不到属性，
   表象是"尾部的字变了形"、不报错；`objects` 的 cp 锚点同理）。**编辑一律在树上落笔**（步骤 + 事务），
   产物每轮由新树重编 —— 旧装载路径退役之后，引擎里已经没有"就地改产物"这条路了，别把它加回来。
4. ★ **结构口径 ≠ 编辑口径**：`makeDeleteRange` 走 `normalizeRange`，端点落在不可半分单位（控件/表格/链接）
   **内部**时会**向外扩到单位边界** ⇒ "删控件里的一个字"被当成"覆盖控件节点本身"、步骤构造直接失败。
   编辑删的是**码点**，用 `makeDeleteTextSteps`（按文本节点切分、从后往前发步）。两个入口各管各的，不合并。
5. ★ **段落属性挂在结束标记上** ⇒ 段落格式归属会错位：① 回车在光标处插新标记 ⇒ 新标记结束的是**前半段**；
   ② 合并删的是前段结束标记、留下来的却是**后段**标记 ⇒ "保留前段格式"要显式搬到后段标记上。这类只改标记数据、
   不改流结构的修正走步骤 `SetParaMarkFormat`（位置映射恒等）。★ **末尾段没有结束标记**：合并进末段要补插一枚
   标记带上被删标记的格式，坐标按"删完之后"给（`mapPos(rm.step, end_before, Assoc::After)`）。

## 编译期静默陷阱
6. `WritingMode` 没有 `operator==` ⇒ `std::optional<WritingMode>` 的默认相等被隐式删除（MSVC 静默、clang 报
   warning）⇒ 需要比较就手写（如 `sameParaPatch` 逐字段比），别用 `= default`。
7. **`NodeTree` 没有拷贝构造**（`vector<unique_ptr<Node>>` 不可拷贝）⇒ "按值收一棵树"编译不过，报错落在
   MSVC 的 `xmemory/std::construct_at` 深处，看不出是它。接树用 `const NodeTree&` + 内部 `assignFrom`；
   `clone()` 是另一个显式入口。
8. **wasm 侧关了异常**：`try` 直接编译不过；nlohmann 的失败路径在无异常环境下是 `std::abort()`
   ⇒ 解析用 `parse(text, nullptr, false)` + `is_discarded()`，写出前自己校验 UTF-8。

## 写判据时
9. 判据要写它真正判的东西：`reported()` **精确比较规则名**（写前缀恒假）；构造反例别用 `children.pop_back()`
   （孤立节点会让别的规则先报，用 `eraseChild`）；断言别把"命中计数"写死总数。
10. **断言的"实际值"要先把被测动作算出来再拼消息**：先 `const bool ok = 动作(...);` 再
    `expectTrue(ok && ..., "实际 " + got)`。否则求值顺序未指定（MSVC 从右往左），消息拿到的是动作之前的旧值。
11. 造"字段被删空"的场景时，**被删的那个字段必须可编辑**（只读字段里的退格会被编辑策略拒掉，验成"删不动"）。
12. 拼接期望串别留**尾分隔符**（`s += 项 + " "` 会让 `got == want` 恒假，人眼却看着一样）。
13. **构造"控件包住一段内容"的测试时，段落标记要挂在控件之外**（标记落进控件内部 = 该控件跨段，闭边界落到
    下一段，按"一段"写的期望会整组红）。跨段控件本身是对的 —— 先想清标记位置再写期望。
14. 判长度别用 `cp_text.size()`（那是**字节**）⇒ 先 `utf8ToCodepoints().size()`。

## 引擎与宿主（第七刀：树上编辑 + 演示页切换）
19. ★ **两套句柄空间**：占位簇上的 `owner_control` 是**产生端句柄**（控件的节点 id），而
    `controls()` / 命中测试 / 宿主报的"归谁"一律是**下标**。两个方向分别是 `controlIndexOfOwner`
    （句柄→下标，**未命中返回 -1**，不再原样返回句柄）与 `slotOwnerOf`（下标→句柄）。拿下标直接去和
    占位簇比，一次都比不中 —— 表象是"括号排对了、共享边界上光标却画到另一侧"，只有像素级判据看得出来。
20. ★ **求流位置时要带侧别**：同一个偏移上可能压着好几枚括号，`flowPosAt` 拿不到侧别时只能猜 ——
    而"紧贴控件开括号"的那一侧是控件**外**，猜错就把"把字段最后一个字退掉"判成越出控件
    （"删到只剩一个字就删不动了"）。持树那条路一律走 `flowPosAtSide` + `sideForPos`。
21. ★ **宿主的底稿会过期**：树上编辑之后引擎里的文本已经变了，而宿主手里那份块流还是装载时那一份。
    紧接着"改控件再重建"会把用户改过的内容整个倒回装载时的样子（光标归零、字打不进任何字段）。
    修法两件套，缺一不可：① 重建走 `setFormControls(list)` —— **换名单与建树在同一次调用里**，
    宿主没有"重建前先 `g_blocks = g_engine.blocks()`"这种手工对账的机会，也就不会忘；
    ② `setFormControls` 自己第一句就是 `syncBlocksFromEngine()`（底稿取引擎里当前那一份）。
    旧写法（删 `setControls` 再逐个 `addControl`）要靠宿主自觉，是这条陷阱一直复发的原因。
22. ★ **空字段不参与嵌套**：零宽字段的开闭两枚落在同一列，引擎的括号次序把它那一对排在"到此为止"
    的闭括号之后、后一个字段的开括号之前（`][][]`）。建树时若把它当成"被包住"的子节点，画出来就
    成了 `[][]][` —— 区间一模一样，只有括号的排布不同。建树时让空字段与包住它的字段**并列**。
23. ★ **光标只有一个数：段内流位置 `rel`**（见 `MEMORY.md` 引擎现状）：文本字与边界括号各占一位，
    偏移与侧别都是派生量。四条要记住的：① 方向键 = `rel ± 1`，并在**字素簇边界**上停（`e` + 组合
    重音算一格，不是两格）；② 点击量到的是侧别，`hitTestPt` 的 `field` 只是它的投影（同一个偏移上
    好几枚括号时投影会抹平细节）；③ **写入口只有 `setCaretRel` 与 `setCaretAtFlow`** ——
    凡是"把 (偏移, 侧别) 变成 rel"的地方都走 `relAt`（它会把侧别夹到本偏移实际有的枚数）；
    ④ **`rel` 相对"边界表"而存在**，所以表在变的那一刻读它就会得到别的位置 —— 见第 28 条。

24. ★ **默认侧别 = "最内层含端点"**（`controls_.innermostAt(p, true)`，与编辑归属同源）：相邻空字段
    必须停在它自己那一对括号之间，否则"字打不进去"；而 `focusedControlIndex()` **必须保留这条回落** ——
    `bracketedControls()` 在聚焦档要问它，边界对象表又由 `bracketedControls()` 决定，少了回落会
    互相等成死结（首次排版前一个括号都排不出来，于是更推不出归属）。
    ★ 但它只是**从文本坐标投影到流位置的约定**，只该用在"宿主按 (段,偏移) 定位"那一处：
    编辑落点一律用 `setCaretAtFlow`（删除后 = 区间起点、插入后 = 区间终点、Tab / 撤销 = 目标）。
    拿它去算编辑落点，症状是"删一个字光标跳一格"（落到相邻括号的另一侧）。
    ★ **删除区间用 `textSpanAt`**（＝这段文本码点自己占的那一段，括号不进区间），
    判定与真删共用它；区间多含一枚括号的表现是"删完光标跑到括号另一侧"。
    ★ **`caretSide()` 不再需要"不拿边界枚数去卡"这条特例**：侧别是派生的（`rel` 与偏移之差），
    没有"存着的侧别"可以失配。反过来要注意的是**中间态**：控件被清空那一刻 `rel` 与偏移对不上，
    派生出来的侧别必然是 0 —— 见第 28 条。
    ★ **`relayout()` 开头不许吸附簇**：那一刻用的是上一轮的簇表，会把光标拉回旧段长
    （连打 60 个字符后停在 17 而不是 68）。源码注释写了原因，别顺手删。

## 探针与坐标（写浏览器判据时）
25. ★ **`window.__heditor.caret.x` 是帧像素**（乘过 zoom），而且是**光标矩形的左缘**而不是插入点 ——
    插入点还要加半个光标宽（`caret.w / zoom / 2`）。少算这半格，点选判据就会落在括号格的正中偏左，
    差 0.05pt 就翻到另一侧去（"点 [ 归后一个字段"整组红）。
26. ★ **"点某字段的开括号"不要用"两枚括号间距的一半"**：那落在括号格的正中，落在左半边就变成
    "括号之外"了。稳的取法是取内侧插入点再往左半磅（既在括号格右半边、又紧贴字段第一个字）。
27. ★ **判"方向键一次一格"要读 (偏移, 侧别) 两个数**：只读偏移看不出"同一偏移上退了一格"，
    那种一步在偏移上是不动的（`caret.side` 由 `editStatsJson` 给出）。
28. ★ **`rel` 相对"边界表"而存在 ⇒ 表在变的那一刻不能读它。** 两条实测教训（第三条已结构性消除）：
    ① **读 `rel` 的那张表必须是"不随显示档漂"的那一张**。`objectsFor` 读的是编译产物
    （`blocks_full_`，全部边界、不区分显示与否），所以 `rel` 的解释不受"显示哪些括号"影响；
    `syncInlineObjects` 只重写 `blocks_`（显示副本）这一份。**两张表不能对调** —— 旧 `setBlocks`
    路径只有显示表，`rel` 会随显示档漂，这也是退役那条路的理由之一。★ 由此旧写法里那条顺序约束
    （"清空对象表要排在问聚焦字段之后"，先清再问会把光标解释成另一个偏移、聚焦字段当场换人）
    **已结构性消失**：`syncInlineObjects` 现在只重写显示副本，而解释 `rel` 读的那一份引擎碰不着。
    ② **整批换控件期间表会整体换掉**，中间态里一枚括号都没有 —— 侧别那一刻没有对应物，引擎
    自己搬必然抹成 0（实测 7/2 → 7/0，接着打字进了左边那个字段）。修：重建走 `setFormControls`
    —— **换名单与建树在同一次调用里**，中间态不存在。旧写法（先 `clearControls` 再逐个 `addControl`）
    靠宿主自己存 `(偏移, 侧别)` 再摆回去，是这条陷阱一直复发的原因，别把它加回来。

## 构建与工具
15. **循环变量别叫 `r`**：不变量检查器里报告对象就叫 `r`，会把它遮住（闭包遮蔽也犯过）。
16. 崩溃时缓冲里的断言行会整块丢掉 ⇒ 测试 main 已加 `setvbuf(stdout, _IONBF, 0)`（MSVC 把 `_IOLBF` 当全缓冲）。
17. **重写"扫描并插入"的循环时，旧循环里隐含的兜底行为最容易被丢掉**：旧 `slotIndex` 对越界偏移是**夹到末尾**，
    换成归并循环后越界项会被静默丢掉（凭空少一枚括号）。改这类循环先把旧循环的**边界行为**逐条列出来。
18. ★ **改「被静态库构造的类」的布局时，先确认那个静态库会重编**。`demo_documents.cpp` 直接构造 `BlockSpec`，
    `heditor_demo` 曾**漏挂**头依赖 ⇒ 库的 .obj 用旧布局、测试的 .obj 用新布局混链 ⇒ **析构时随机段错误，
    而崩溃前所有断言都打印 PASS**。判据是构建图：`ninja -C build/native -t deps` 看它的依赖表，或改一下
    那个头再看首轮日志里有没有这个 .obj 的 `Building CXX object`。★ 排查手法（Release CRT 下
    `_CrtSetDbgFlag` 是空实现）：往 **stderr** 打点，能定位到"函数体走完了、崩在析构"这一级。
19. ★ **构建目录的代码页决定头依赖能不能记**。cl 的 `/showIncludes` 前缀字节跟随**控制台输出代码页**
    （936 → GBK，65001 → UTF-8），CMake 用同一码页解释它、原样写进 `rules.ninja` 的 `msvc_deps_prefix`，
    ninja 再**逐字节**匹配 ⇒ **configure 与 build 同码页才记**（936 / 65001 各自都正常）；不一致则
    `ninja -t deps` 全 `#deps 0`，而且是**静默**的：改头文件不重编译 → 旧布局 .obj 配新 .lib 混链段错误，
    断言照印「失败 0 项」。★ **本机默认就是 936，够用 —— 别去切码页"修"它**（那条"构建期钉 65001 +
    跑完还原"的补丁是拿项目文件给沙箱限制买单，2026-10-13 已撤）。
    · ★ **CMake 缓存编译器探测结果**：换码页只重配、**不重新探测**，前缀不动 ⇒ 换码页必须挪走
      `build\<预设>\CMakeCache.txt` 与 `CMakeFiles\<版本>\` 让探测重跑，否则白折腾（实测踩过）。
    · ★ **VSLANG=1033 / 804 实测无效**（输出逐字节相同）—— 没有"让 cl 说英文"这条捷径。
    · ★ **Emscripten 侧与码页无关**：clang 走 `-MD` depfile，wasm 的 `rules.ninja` 里没有 `msvc_deps_prefix`。
    · ★ 教训：这条曾被写成"本机 MSVC + Ninja 的头依赖追踪**开箱就是坏的**"，其实只是**我自己**每条命令
      都设 `[Console]::OutputEncoding = UTF8`（为了日志不乱码）、而构建脚本又没钉码页，于是 configure 与
      build 的码页不一致。**先怀疑环境（尤其是我自己造的），再怀疑工具。**

20. ★ **帧是视口窗口，不是整篇**（2026-10-13 起）。`repaint()` 只呈现
    `[vp_first, vp_first+vp_count)`，`vp_count <= 0` 才是整篇。踩过的四个坑：
    · ★ **`EditStats::total_pages` 是文档页数**，不是帧里那几页（那看 `window_pages`）。
      把两者合成一个数会让宿主算窗口时把整篇当成 1 页（帧恒 1 页、`#pages` 高 1 页、
      永远滚不动），而且"脏页 / 总页"恒等于 1。
    · ★ **换文档之前必须先设锚点**（`presetWindowForLoad`：锚点摆到开头 + 滚动回顶）。
      顺序反了会先按上一篇文档的锚点栅格化、再挪窗口重排一次，探针拿到的就是后一次的账
      （"重排 0/200 段"这种读不出装载成本的数字）。
    · ★ **收尾顺序：先滚光标入视口 → 再对窗口 → 再上屏**。先对窗口会按旧的滚动位置算，
      光标在第 0 页而屏幕还停在第 15 页时窗口被拉成整篇（封顶只是兜住，根子在这里）。
    · ★ **窗口要带滞回**：现有窗口还盖得住"光标页 + 可见页"就不动。没有它，光标一路往下打字、
      可见页一格一格地换，每换一格整帧重建一次（一页约 13 ms）⇒"每隔十几个字卡一下"。
    · ★ **凡"帧坐标 → 页号"的换算都要加回窗口首页的偏移**，一个都不能漏：
      `caretRectPx` 的 `off_y`、`hitTestPt` 的 `page = floor(doc_y / stride)`、
      宿主的 `scrollCaretIntoView`（`窗口首页*step + caretY`，写成 `caretPage*step + caretY`
      等于把页偏移算两遍 ⇒ 点第二页屏幕往下冲两页）。★ `hitTestPt` 这一处最阴：
      点第二页会被判成第一页，光标跳到别处、屏幕跟着滚 —— 看起来像"滚动坏了"，
      其实是命中算错了页。判据：`edit_probe` 的"点第二页光标所在那一行：页不变、一次都不滚"。
21. ★ **行带重画（页粒度 → 行粒度）的两个坑**（2026-10-13）：
    · ★ **带边界取"与相邻行盒的中线"**，不是行自己的 block_lo/block_hi。行盒给的是
      ascent/descent，个别字形（标点、带钩部件）的墨迹会探出去 —— 用行盒边界就会
      啃掉相邻行的抗锯齿边（增量帧 vs 从零重画差 339~3550 px、最大通道差 49）。
      取中线之后相邻带正好相接、互不重叠。★ 边界还要取**新旧两版里更靠外的那个**，
      否则行往下挪之后旧墨迹留在原地（幽灵字）。
    · ★ **页边框每次都要补画**：它在页矩形的边上，而带底色的填充会擦掉一条。
      漏掉的后果是"差 4308 像素" —— 正好 `2×(893+1263)-4`，页边框的长度。
    · ★ 竖排页整页重画（行盒的块轴在竖排下是横轴，行带会变成竖条，而擦除矩形与
      字形筛选都按纵轴写）。判据是 `edit_test` 的"增量帧 == 从零重画的帧（逐像素）"
      与 `edit_probe` 的"屏幕 == 引擎帧 / 增量重绘 == 重新排一遍"。
    · ★ **表格里行盒会纵向重叠，"相邻两组中线"就落进组的内部**（2026-10-26）：同一
      表格行里各格的行数可以不同 —— 图片格的行盒 97..131、邻格第二行 115..132，两者
      相交。按"top 相同"分组时，那条中线算出 122.8，落在行盒内部 ⇒ 这半截不属于
      任何带；擦除按带做，于是它被擦掉却不再重画。症状是格内折到第二行之后，后半截
      字变空白或与旧墨重叠，而 `auditPage` 只差几十个像素（一条 3 px 高的横条）——
      肉眼"字没出来"、数墨却要贴着边界才抓得到。⇒ 分组按**纵向重叠**合并，组内
      共用一条带（宁可多画几十像素，不能让某行落在所有带之外）。
      判据：`edit_test` 第 86 节"图在左格、字敲在右格并折行"（逐键对页位图）。
22. ★ **判"卡在哪一层"必须做画布可见性对照**。帧间隔（rAF 间隔）才是手感，它包含浏览器合成；
    引擎计时与 `putImageData` 都测不到合成 —— 后者**惰性**：73 Mpx 与 1.13 Mpx 的画布
    贴同样一小块都返回 0.000 ms，拿它判画布大小等于没测。做法：同一串敲字，把画布
    `visibility:hidden` 再跑一遍，差就是合成那一笔（实测 18.3 Mpx 差整整一个 vsync）。
23. ★ **字形画在底图上，账要读 `base_` 不读 `bitmap_`**（2026-10-14）。帧（`bitmap_`）那边
    只从底图搬像素过来，它自己的记账回答的是"上屏搬了多少"。新加"画了几个字形"时
    从 `bitmap_.paintedGlyphs()` 读，恒得 0 —— 面板照常渲染，不看就发现不了。
    两块的账要各自 `resetPaintedPixels()`。
24. ★ **窗口不能把光标页无条件并进来**（2026-10-14 改）。求并集再从 `min` 那一端起算，
    等于用户把屏幕滚到别处之后窗口仍被钉在光标页上（封顶正好取到光标那几页）：
    可见页没进窗口 ⇒ 没有画布（一片空白），且算出的锚点与上一轮相同 ⇒ `applyWindow`
    返回 false、连 present 都不做。症状是"滚动时下面的画布不生成，点一下才出来"。
    正解：以可见页为准，光标页只在挨着可见页（±1 页）时才并进来。
25. ★ **光标不在窗口里时，`caretY` 是个"帧外"的数**。`scrollCaretIntoView` 与 `positionIme`
    都要先判 `caretPage ∈ [windowFirstPage, +windowPages)`：否则前者会按帧外的 y 算绝对位置
    （滚到一个毫无关系的地方），后者会把输入框（连带输入法候选框）摆到屏幕角落。
26. ★ **画布"重建"的钱在重新分配 backing store，不在换内容**（2026-10-14 实测）：
    重建 4 张 6.7 ms vs 复用 4 张 2.0 ms（一页 893×1263 = 4.5 MB）。换窗口时用池子
    （卸下来的 canvas 元素留着，`appendChild` 回去，backing store 不重分配）。
    `canvas.width = w` 只在尺寸真变了才写 —— 这是同一个坑的另一半。
27. ★ **批量画字形：一段一次，顺序不能乱**（2026-10-14）。攒段按 (font, color, rotate) 分键，
    刷新时机是"键变了"，数组里的次序就是绘制次序（重叠字形靠它决定压盖）。
    侧倒竖排必须退回逐字形 —— 旋转是每个字形各绕自己的原点转，一次 `drawGlyphs` 只有
    一个画布变换，凑成矩阵会引入浮点差异（`T(x,y)R(θ) == R(θ)T(R⁻¹(x,y))` 只在线性代数上成立）。
28. ★ **别拿"编进二进制的构建戳"与"产物文件的 mtime"相减判旧副本**（2026-10-14）。
    两者的时刻种类不同：编进去的是**配置时刻**（这样没改源码的构建能停在第 0 步，
    不必重编那几个引用它的 TU 并重新链接），而产物 mtime 是**构建时刻**。
    相减得到的差值等于"构建比配置晚了多久"，于是只要晚过五分钟阈值就恒报旧副本，
    而页面跑的其实是最新的那份（纯误报，且会让人怀疑整套工具）。
    正解：让构建成功时写一份同源的旁证（`heditor_wasm` POST_BUILD 写 heditor.buildstamp），
    页面拿它与 wasm 自己报的戳对照 —— 一致 = 跑的就是磁盘上这一份。
    ★ 判据要含反向一半：把旁证改成别的值，红色警报必须出现。
29. ★ **std::optional<T> 里的 T 必须有 operator==**，否则外层那个
    `bool operator==(...) const = default` 会被**静默删除**（WritingMode 缺 operator==
    就是这样，ParaFormatPatch / StyleDef 的相等比较跟着一起没了）。症状是每条包含该头的
    TU 各报一遍、还拖着几十行无关候选；真去比较时才编不过。这类"声明了但被删除"的成员
    不能当噪音忽略 —— 它是"想比却比不了"的定时器。
30. ★ **段数变化也能走后缀复用之后，两个索引坑**（2026-10-14）：
    · ★ **段表的槽位搬移方向与顺序不能错**：往后挪（段数变多）要先扩容、再从尾到头搬，
      否则会盖住还没搬的项；往前挪（段数变少）要**先把项搬到新位置、最后才缩容** ——
      反过来会先丢掉末尾那几项，之后再读它们就是越界：搬过去的是垃圾，
      而排版看起来"成功了"（只有 auditLayout 会红，它比到段表那一层）。
    · ★ **行盒与字形的段号字段要跟着整体平移**：两个结构都把段号存成字段，
      而光标几何（按段号找行）与审计（逐字段比）都读它 —— 不跟着改，
      光标会落到别的段上，且在画面上只表现为"某个字串行了"。
31. ★ **段数变化几乎总落到"后缀整体平移"那一级，而不是"同状态"**（2026-10-14）。
    段落边界一变就多让（或少让）一次 space_after_pt，后缀必然整体下移 ——
    所以判"能不能复用"时别只盯"状态逐位相同"；那条路基本只有"在行首回车且段间距为 0"
    这一类才会命中。
32. ★ **读 editStats 必须走带 render 的入口**（`typeTextAndRender` / `splitParagraphAndRender`…），
    否则读到的是**上一次呈现时**抄下来的值。危险在于陈旧值常常"看起来是对的"：
    分段前后两次都是"重排 1 段 / 复用 99 段"，于是断言照过、而真正被测的那一步根本没被量到。

33. ★ **"标脏"必须写成"与底图那一版必然不同"的值，不能写成常量**（2026-10-14，我踩的）。
    页/行指纹的判据是"new != base"，而 present 之后 base 也会被刷成标脏值 ——
    下一次标脏若写回同一个常量，判据读出来就是"没变"，**那一页从此不再重画**。
    症状：**连续换行只有第一次把文档推下去，之后屏幕不动**（用户就是这么报的）。
    正解：高位恒置（真指纹一律清掉它 ⇒ 不可能等于真指纹）＋ 低位按底图那一版翻一下
    （`(v == base) ? (v ^ 1ull) : v`）—— 翻一下之后高位仍在，两个性质同时成立。
    ★ 判据必须落在**帧**上，`auditLayout` 抓不到它（它只比排版结果，底图漏画照样绿）：
    「第二次回车画面变了多少像素」（脆，>20000）＋「与从零重画差多少」（有界，<5000 且通道差 ≤4）。
    反向验证实测（把标脏退回常量）：画面变了 **84** 像素、与从零重画差 **750062**（通道差 **231**）；
    修复后：**750148** / **562** / **3**。两组差 4 个数量级，判据不含糊。
34. ★ **页指纹是 O(文档) 的一笔，必须能"标脏"而不能只靠哈希**（2026-10-14）。后缀整体平移那一级
    里，后缀在的**每一页**内容都跟着挪了 —— 答案早已确定，可原来还是把整条后缀的字形哈希了一遍
    （2000 段 21.1 ms、10000 段 33.9 ms，比排版本身贵一个数量级）。改成 `markPagesChangedFrom(fp_lo)`
    之后恒 0.0 ms，**且与文档规模无关**。判据：同一个回车操作里 pageFp 从 21.1 → 0.0，
    而"敲字"那几档仍是 0.1（那是真的在哈希 1 页）。
    ★ 另一半：续排路径（没有后缀可复用，例如在文档末尾敲字）原来 `fp_lo = -1` ⇒ 整篇重算，
    现在按"脏段新旧两版的第一页取更靠前的那一页"框出范围（3000 段从 7.5 ms → 0.1 ms）。
35. ★ **跨轮比绝对耗时不可信，要读"同一次操作内部的读数"**（2026-10-14）。同一个 build 连跑三次，
    场景 7 的**装载**分别 171 / 245 / 331 ms（装载路径一个字都没改），机器状态的影响能到 2 倍。
    判"这一刀省了多少"只能看同一操作内部的分项（pageFp 21.1 → 0.0）或同轮内的对照组。
    ★ 报账也要诚实：`EditStats::total_ms` 原来只算 layout + paint，**pageFp 不在里面** ——
    面板显示"合计 18 ms"而这一次操作实际 39 ms，看的人自然对不上手感。
36. ★ **段落标记落在控件内部时（在字段内容里回车 ⇒ 字段跨段），"只重编译被改的那一段"不能按
    标记的父容器取子节点区间**（2026-10-14）。那一段的内容可能**起自控件之外** —— 控件里的
    半截被当成整段编译：前半段的字与控件自己的边界一起丢掉，`block_src_` / `block_flow_` 被这
    半个产物覆盖、控件集合随之空掉。症状：**退格删一个字，前面九个字与三个控件一起消失**
    （三连可编辑字段里「天」后回车，再在「悸」后退格 ⇒ 只剩一行「三天」）。
    修法：`rebuildParagraphFromTree` 里加一条**形状判据** —— 段落起点（`block_src_[para].first`）
    的祖先链要经过 `container`，且它在 `container` 下的下标落在 `[begin, mark_idx]` 内；
    不满足就退回全量编译。表格单元格里的段落在同一个单元格内，不受影响（增量照走）。
    ★ 反向验证（实测）：去掉判据，新断言 [31] 的 `auditCompile` 立刻报 **4** 项差异、文本变成
    `[三天][，加重一天。]`、控件 **0** 个；加上之后是 **0** / `[患者主诉：反复心三天][，加重一天。]` / **3**。
    ★ 别"顺手"把跨段控件禁掉 —— 它本来就是正常形态（演示变体 1 演示的就是它，模型文档也写着
    "跨段控件会让中间那些块的 mark 落在控件内部"）。要修的是增量重编译的形状判据，不是那个形状。
37. ★ **可见性口径一旦能被设置，编辑坐标会立刻错位**（尚未发生，先记）。`flow_` / `blocks_` 走

38. ★ **判据不能依赖它正在校验的那份数据**（2026-10-14）。上一轮给增量重编译加的"形状判据"
    用的是 `block_src_[para].first`（段首第一个内容元素）的祖先链 —— 而 `first` 是编译层**记下来
    的**：`noteFirst` 只在文本与**开括号**处调用，**闭括号没记**。于是"段首第一枚内容是一枚闭括号"
    的段落（前一段的控件跨到这一段、它的结束边界落在段首），`first` 退化成这一段自己的结束标记
    —— 结束标记必然在容器内，判据当场失效，看起来还在、实际什么也没拦。
    症状：三连字段里「天」后回车、再「悸」后回车，然后把光标放到「天」后面退格 ⇒ 第二段段首的
    两枚边界（前一个字段的闭括号、后一个字段的开括号）成对消失，**控件从 3 个掉到 1 个**，而
    `auditCompile` 只报 **2** 项差异（`exportControlsFromBlocks` 对半截边界是整对丢弃）。
    两处修法：① `compile.cpp` 的闭括号也 `noteFirst` —— 契约（"第一个吃进内容的元素，含控件
    边界"）本来就是这么写的，是实现的漏记；② `rebuildParagraphFromTree` 的判据改成比**流位置**：
    段的流起点（上一枚标记之后那一位）必须与 `container.children[begin]` 的区间起点重合。
    ★ ②不依赖来源记法 —— 实测把 ① 停用，[32] / [33] 照样全绿（这道护栏才是本质的）。
    泛化：判"某段能不能用某区间表达"，**比流位置，不比节点归属**；归属是别人记的，可能记错。
    ★ 连带：**降级不许静默**。`auditCompile` 现在独立数一遍成对控件个数，并校验"段起点必须落在
    `intervalOf(sources[i].first)` 区间内"，把"控件整批消失"变回一条可读的差异。
    ★ 判据侧配套：`edit_test` [33] 把回车切点与随后的段内编辑**穷举**一遍（10 个切点、140 次编辑），
    不再靠人列举形态 —— 本文档第 36、38 两条都是"想漏了一种形态"。

60. ★ **取模取槽那个"上限"不是 8 —— `maxWindowPages` 会超过 8**（2026-10-16）。
    引擎的窗口页数是 `max(视口页数, min(kWindowMaxPages, 像素封顶, 视口页数 + 余量))`，
    外面那层 **`Math.max(视口页数, ...)`** 意味着：**视口比 8 页还高时窗口页数就超过 8**。
    于是"槽号 = 页号 mod 8"会让两页落进同一个槽 —— 症状是那几页**永远"缺画布"**
    （`pagesMissing()` 里 `s < count` 永远数不全），而且每一拍都在重贴。
    正解：N = `max(8, ceil(视口高 / 步距))`，**两侧从同一份几何现推**（同一份
    `viewH/pageH/gap`），不必额外通信、推出来也一致；N 变了就整体作废。
    ⇒ 凡"用常数当上限"的地方，先去读那个上限的真实推导式，别只看常量名。

64. **优化路径的兜底会把"为什么没走优化"的证据一起擦掉**（2026-10-17）。

67. ★ **给"看起来很对称"的逆运算之前，先确认两边的输入是谁产出的**（2026-10-17）。

    ★ 一般化：**渲染布局是私事，不该泄漏进输入换算**。命中测试问的是"文档里的哪个位置"，

68. ★ **"对区间里每一位做一次 O(扇出) 的查询" = 亿级**（2026-10-17）。
    `FlowIndex::posAt` 从根下降到最内层，**每一层线性扫孩子** —— 2000 段的文档里每次
    约 O(段数)。于是删除路径上两处"逐位问一遍"的循环各付 120393 位 x 1000 ≈ 1.2 亿次：
    `makeDeleteTextSteps` 逐位找"这一位属于哪个文本节点"、`eraseFlowSteps` 逐位找段落标记。
    表象：**2000 段全选后删除 7.4 秒**（用户报"耗时非常久"）。
    ⇒ 判据 `out/_selallcost.mjs`：`H.backspace()` 的墙钟，三轮取最小（本机抖动大，
      单次读数会差三倍）。改后 35.1 ms（worker）/ 46.8 ms（单线程）。
    ⇒ 修法三条都是"把逐位换成跳跃或查表"：文本节点**逐节点跳跃**（拿到节点直接跳到它的
      流末端，节点区间两两不重叠）；段落标记位置**由块表给出**（`block_flow_[k] - 1`，
      标记就夹在两段之间）；**整段并成一个 DeleteRange**（`Fragment` 本来就支持多 piece：
      文本与段落标记交错）—— 步骤数 4000 → 1。
    ★ 同族的第二类：**`applyStep` 每一步重建一次流索引**（O(节点数)），一批四千步就是
      几千次全树遍历。判据不是"某个函数慢"，而是"**每步都建**"这件事本身。
      修法是让调用方把已建好的索引传下去（`collectCovers` / `makeRemoveParaMark` /
      `canApply` 各加一个收 `const FlowIndex&` 的重载），判据与应用共用同一份。
    ★ 一般化：区间长度是文档量级、扇出也是文档量级，两者相乘就是亿级 —— 而它藏在一个
      "看起来只是遍历一遍"的 for 里，编译器与静态检查都不会提醒。
    ★ 另一条（不是性能）：**Ctrl+A 不该搬视口**。焦点端在文档末尾，把视口拽过去等于
      整篇跳一次，而换窗要重画一屏（冷字形 100 ms 以上）—— 画面因此分两拍出现
      （用户原话"先停在中间再往下选择"）。主流编辑器都保持当前视图。判据同样是
      `out/_selallcost.mjs` 的 F 段（真 Ctrl+A 逐拍采样 scrollTop）。


69. ★ **增量绘制的正确形态是"新旧差集"，不是"擦全部再画全部"**（2026-10-17）。
    帧是增量的：`refresh` 之外的像素本来就是对的。据此给选区绘制加过滤，**第一版一点
    没变快**（overlay 仍 6~10 ms）—— 因为"擦上一拍的选区"那一步把上一拍的**整窗**
    矩形无条件加进了 refresh，refresh 于是总是覆盖整窗选区，过滤等于没过滤。
    第二版加"新旧完全相同就整段跳过"：只覆盖"窗口完全没变"那一档，而
    `selectionRectsPxIn(first, count)` 只返回窗口内那几页 —— 窗口内平移一页时新旧各差
    一页，必然不等。实测重画 0 页的拍降到 0.1 ms，重画 1 页的拍仍是 8~10.5 ms。
    第三版（差集）：不再有的擦掉、新出现的铺底后画、交集不动 ⇒ 重画 1 页的拍 1.5~2.3 ms。
    ⇒ 一般化：**"擦旧的"与"画新的"两批都要按差集算**，交集才不会被无谓地碰。
      任何"按整批处理"的增量都会退化成全量 —— 而它看上去仍然"只做了必要的事"。
    ★ 判据要按**像素**给（改的是绘制，耗时对了不等于画对了）：`out/_selallcost.mjs` 的
      G 段数"画布上偏蓝的像素"，用"有选区 vs 无选区"的差做判据 —— 绝对阈值分不出，
      画面上本来就有偏蓝的像素（背景、字形）。第一版探针就栽在这上面（把 23697 个
      背景像素当成"选区残留"报了 8 条假红）。
    ★ 另记一条：worker 宿主的页画布已 `transferControlToOffscreen`，`getContext` 会抛
      `InvalidStateError` —— 这条像素判据只能在单线程宿主上跑，探针里 catch 成 -1 并跳过。


70. ★ **连页模式（一个视口画布）修了三处，都是"看着能跑、其实是错的"**（2026-10-18）。
    用户报的症状是整页停用（横幅"宿主处理引擎状态时抛异常"）。
    ① **漏转移列表**：`post({canvas: el.transferControlToOffscreen()})` 没带 `[off]`，
       抛 `DataCloneError`（OffscreenCanvas 不能按值克隆）。与 `sendPageCanvas` 那条
       同源，但那条写在注释里、这条没写 —— **凡"把画布交给 Worker"都必须带转移列表**，
       而且它抛在"状态到达"的路上，会被宿主当成致命错误整页停用。
    ② **改页间隙只重排、不重绘帧**：`setPageGap` 走 `applyConfig()`（重排），帧缓冲里
       还是上一套布局的像素。只作废槽表重贴的话贴出去的是"新步距 x 旧像素"，**从第二页
       起整体错位**（第一页恰好对，它的偏移是 0），而且槽表随即被记成"这一槽已装这一页"，
       后面整窗重贴也会跳过它 —— 错位永久留在画面上。修法：`syncFrameSlots()` +
       `relayoutAndPaint()` + 作废 + 重贴，四步。
       ⇒ 一般化：**凡"改了页的落点"的地方，必须重排 + 重绘帧，不能只重贴**。
    ③ **"窗口没变就只回 ack"在连页下不成立**：分页下浏览器会把画布搬走，所以窗口没变
       时引擎什么都不用做；连页下屏上那一张画布不动、页的落点是随滚动量算的，
       滚动量一变就必须重贴。不修的症状是"滚动后有的页还是旧内容"。
    ④ **提前量不能混进落点**：宿主报的位置沿滚动方向提前（`viewLeadPx`），它只该影响
       "先装哪几页"；连页下它直接决定内容画在哪儿 ⇒ 滚动时画面跑到实际位置前面、停稳
       再弹回来。已拆成 `scrollY`（真实）+ `leadPx`（只喂 `visibleRange`）。
       判据（`out/_continuous.mjs`）：真滚轮甩 6 拍后"引擎记的位置不许比 DOM 靠前"，
       停稳后两者必须相等。★ 必须真滚轮 —— 程序化写 scrollTop 不积累速度、提前量恒 0，
       这条判据会假绿。
    ⑤ 顺带修掉一处同类：宿主 `positionIme` 用 `gm.first * pageStep + caretY` 摆输入法框，
       而 `caretY` 含的是**槽偏移** ⇒ 窗口首页不是槽数整数倍时框摆到别的页上
       （与命中测试那次同一类：帧槽与窗口偏移混用）。判据 = 与按页号算出的位置一致
       （实测 538 vs 538）。
    ★ 判据本身的教训：**"配置层的事实全对"不等于画面对**。第一版连页探针只断言了模式、
      间隙、画布数、点击落点 —— 而那时画布压根没转移成功、屏上一个字都没有，探针照样
      "通过"。补上 `selfCheck` 的连页分支（视口画布 vs 帧逐字节）与 `compared > 0`
      之后才拦得住：**比过的像素数必须进判据**，否则 `missing = 页数 / diff = 0`
      也会被读成全绿。

71. ★ **"去掉分页"是排版层的事，不是把页间隙设成 0**（2026-10-18）。
    用户要的连页是"没有页的概念、内容一列连到底"；把间隙设成 0 只是让页首尾相接，
    内容照样在页底让位（实测分页 12 条带 → 真连页 7 条带）。
    ★ **核心设计**：连页下页号退化成"渲染条带号" = `floor(块轴位置 / 条带高)`，
      条带高 = 页高 + 页间隙。于是帧的槽、光标、选区、命中测试读的仍是
      "页号 + 页内坐标"，绝大部分下游代码一行不用改 —— 这是这个方案能小的原因。
    ★ 三处必须成对改的：
      ① 断页判据有三条（页底溢出 / 显式分页符 / 竖排"吃掉本页剩余高度"），**漏一条
         就留下"某一处还在翻页"的接缝**；竖排还要把"另起一页"改成"另起一条横带"。
      ② **所有写进 LineBox / PlacedGlyph 的 y 都要减条带偏移**（横排的 block_lo/hi、
         bracket_axis、字形 y；竖排的 inline_origin 与字形 y）。漏一处就是那一处按
         绝对坐标落进帧里 —— 跨条带时整体错位一条带。
      ③ 字形要按**自己的** y 取条带（不跟行盒走）：一行可以跨条带，跟行盒走的话
         跨过去的那几个字会被画到条带框外（那一行的尾字整段不见）。
    ★ 命中测试在连页下必须按**文档 y** 找最近的行：按页号筛会漏掉跨条带那一行的尾段
      （每跨一条带就有一条这样的窄带点不中）。
    ★ 绘制侧反而简单：连页下条带整幅填页面底色就是"一整条连续白底"，不画边框、不擦间隙。
    ★ 宿主：滚动高度取内容底边（`contentBottomPx`），不是"页数 x 步距" ——
      后者末尾会多出一整条空条带的空白。
    ★ 判据要**成对**（这次是分页/连页互为正反）：
      native `edit_test` [40]：分页跨页那两行的间距 ≥ 页间隙 + 2 倍边距、墨迹永远够不到
        条带底；连页最大一跳 = 段间距、墨迹跨过条带底、条带数变少。
      web `_continuous.mjs`（`inkRows` 读数）：条带里"非白底的行"连页必须为 0、分页必须 > 0；
        跨条带行距 vs 条带内行距 —— 连页同量级、分页差一个量级。
    ★ **判据自己写错过一次**：第一版断言"分页下文档 y 会回跳"，实测**不会** ——
      页号乘上条带高之后文档 y 是递增的，页底让位表现为"相邻两行的**间距**突然变大"。
      凡"某一处被让开了"这类判据，先想清楚它在那套坐标里到底表现成什么量。

72. ★ **叠加式的效果不能重复施加**（选区混色每重画一次深一层）（2026-10-18）。
    症状链：用户报"光标所在行的选区颜色会随着光标闪烁逐渐加深"，最后那条蓝条里的
    **字被叠成与底色同色**（看上去是一条空白的蓝条，而选区宽度是对的）—— 于是先被误读成
    "这一行的字没画出来"。
    根因：选区用 `blendRect`（叠加式混色：把当前像素按 alpha 再混一次）。而增量绘制里
    `refresh` 常常只有**光标那一小条**（光标每闪一次就把它自己那一格铺回底图），
    代码却把**整块**选区矩形再混一遍 ⇒ 整块矩形每闪一次深一层。
    ⇒ 一般化：**凡"叠加式"的绘制（混色、加色、羽化），重画前必须先把目标区域整块恢复成
      干净的源像素**；只恢复了其中一小条就重画整块，等于按重画次数累积。
      这一条对"擦旧的"那批矩形同样成立 —— 差集算的是"哪些矩形要重画"，而"重画"的粒度
      必须与"恢复"的粒度一致。
    ★ 判据不要写成"颜色深不深"（要定阈值），要写成**幂等**：
      同一份逻辑状态重画若干次，帧的指纹必须一字不变（相位开→呈现→指纹，相位关→呈现→
      指纹，反复几轮；所有"开"的指纹彼此相同、所有"关"的也相同、且开与关不同）。
      读数用 `frameDigest`（FNV-1a，只算 RGB）—— 整帧 8 MB 搬回去比太贵。
      判据在 `out/_repaint.mjs`，已进验收清单。

73. ★ **同一个"页步距"被算了两遍 ⇒ 误差按页号累积**（2026-10-18）。
    用户报"2000 段长文档最后几页鼠标点击光标定位偏下"。
    两套步距：宿主把页摆在**整数像素步距**上（`pagePxHeight + pageGapPx` = 1123 + 19 = 1142 px，
    canvas 只能摆整数像素），引擎按**磅步距**折页号（`height_pt + page_gap_pt` = 841.89 + 14
    = 855.89 磅）。1142 px / (4/3) = **856.5 磅 ≠ 855.89 磅** —— 每页差 0.61 磅 ≈ 0.8 px。
    到第 160 页累积 **98 磅 ≈ 130 px**（十几个行高），表象就是"最后几页点哪都偏下"。
    两套基准：worker 宿主原来按"被点中那张页画布的 rect.top + 页号 x 步距"算文档 y
    （一次乘法 + 一张画布的基准），而单线程宿主按"页容器 rect + 滚动量"算（一次乘法都没有）。
    ⇒ 修法三条：① 文档坐标只用一个算式（页容器的 rect + 滚动量），点选与拖选共用
      `framePointAt`；② 引擎反推页号用**像素步距**（`y_pt * zoom / step_px`），与宿主摆页的
      取整完全一致；③ 连页下按行搜索改在**文档像素**里比（页号 x 像素步距 + 页内磅 x zoom
      = 渲染位置），不再混磅步距。
    ★ 判据：`out/_hitfar.mjs` —— 在若干页（含最后几页）的同一相对位置点一下，
      落点的页内 y 与点击处的页内 y 之差必须在一个行高量级（实测各页一致 -23~-31 px）。
      "最后几页"必须进判据：只测前几页的话，累积误差还没长出来，判据是假绿的。

74. ★ **跟随光标的浮层要裁掉，否则它会把整页顶出滚动条**（2026-10-18）。
    用户报"滚动时页面还是会出现滚动条，点一下滚动条消失"。
    根因：输入法框被撑成"从光标到页右缘"那么宽、位置跟着光标走；光标滚出视口时它就落到
    视口外面，而它那一层（`#overlay`）不裁剪 ⇒ 顶出 body ⇒ 整页长出一条外层滚动条；
    点一下让光标回到视口内，滚动条又消失（这个"点一下就没了"正是它的指纹）。
    单线程宿主不存在这个问题：它的 `#ime` 挂在滚动容器里，天然被裁掉。
    ⇒ `#overlay { overflow: hidden }`。
    ★ 同类的另一条：工具条用 `height: calc(100% - 74px)` 这种魔数撑滚动区，工具条一换行
      （加了「视图」下拉）就失配 ⇒ 页面也长滚动条。改成纵向弹性布局（`body` flex column +
      `#wrap { flex: 1 1 auto; min-height: 0 }`）—— 魔数会随工具条长出来而失效，弹性布局不会。
    ★ 判据：`out/_repaint.mjs` 里滚动 4 拍读 `document.scrollingElement.scrollTop` 与
      `scrollHeight - clientHeight`，两者必须恒为 0。

75. ★ **折行处的"行首"与"行尾"是同一个位置，只按位置找行一定会画错一边**（2026-10-18）。
    用户报"光标定不到行首，一点行首就跳到上一行行尾"。根因不在命中测试：折行把段内第 k 个
    位置同时算作**上一行的末尾**与**下一行的开头**，偏移一样、侧别一样，`findLineFor` 取
    "先遇到的那一枚" ⇒ 点下一行行首必然落到上一行行尾。这是 Chromium 里叫 `Affinity`
    （upstream / downstream）的那个自由度，落点上必须多带一位。
    ⇒ 光标状态加 `caret_line_aff_`：命中测试算（`cp == best->first_cp && first_cp != 0`）、
      `hitTest` 的 JSON 带 `line`、落点走 `setCaretAtSideLine` / `setFocusAtSideLine`、
      `findLineFor(pos, aff)` 与五个读行盒的地方都要吃它；**别的定位一律清回 0**。
    ★ 它同时修掉"光标在行首按 ArrowDown 原地不动"（当前行被取成上一行，Down 落到的正是
      光标所在位置，于是判成"没动"）。
    ★ 判据必须成对：同一偏移点两次（行尾 / 下一行行首）偏移与侧别都必须相等，**再加一条**
      "不带行别的老路径仍然画到上一行" —— 只判"带行别画对了"的话，一个总是取下一行的实现
      也能通过。浏览器判据别用"行带 ± 容差"判（两条带紧挨着，容差一给就互相包含）。

76. ★ **方向键要按"物理方向 = 视觉移动方向"映射，不是按逻辑轴分配**（2026-10-18）。
    用户报"竖排时键盘左右变成上下、上下变成左右"。原来按逻辑轴分配（左右 = 行内、上下 = 块轴），
    横排下恰好与物理方向一致，竖排下全反。参考行为用 Chrome 实测（`out/_vkeyref.mjs`）：
    `vertical-rl` 里 ArrowLeft 换列往左（文本前进）、ArrowUp 只是行内后退。
    ★ **列序决定"往哪边换列"，不只是"竖不竖排"**：中日竖排 `vertical-rl` 往左换列、蒙文
      `vertical-lr` 往右换列。同一个 ArrowLeft 在两种竖排里文本前后相反。宿主键位表要两个
      输入：`caretVertical` + `caretBlockReversed`（后者取自**段自己的书写模式**，别拿行盒的
      `sideways` 代用 —— 那是"字形要不要转"，与列序是两件事）。
    ★ 判据 `out/_vkeys.mjs` 两半都要：**ArrowLeft 一律往屏幕左**（两种竖排都成立）+
      **往左是前进还是后退随列序翻转**。只判前一半，把蒙文按反也能通过。

77. ★ **撤销恢复的是事务里那一对快照，删除类操作必须记"删除之前光标在哪一端"**（2026-10-18）。
    用户报"删一个字符后 undo，光标跑到这个字符前面"。`eraseOnTree` 原来把 `selection_before`
    一律记成删除区间的**起点** —— 前删（Delete）恰好对（删除前光标就在起点），退格与反缩进
    则落在被恢复那个字的前面。⇒ `eraseOnTree(a, b, label, caret_at_end)`，退格/反缩进传 true。
    ★ 判据写成"**撤销之后偏移回到编辑之前那一格**"（不是"回到区间起点/终点"）：一条判据能
      同时压住三条路径，记错一端的那条当场掉出来；再补一条重做（回到编辑之后），
      确认两份快照的方向没被混着用。

78. ★ **控件边界上的删除只有两条出路：删内容里的那一项，或者（空了才）删控件本身**（2026-10-18）。
    四条规则（从左到右）：退格贴闭括号右面 ⇒ 进控件删左边那一项 / 空则删控件；退格贴开括号右面
    ⇒ 退到开括号左面不删 / 空则删控件；前删贴开括号左面 ⇒ 进控件删右边那一项 / 空则删控件；
    前删贴闭括号左面 ⇒ 跳到闭括号右面删右边那一项 / 空则删控件。
    ★ **"进控件"是递归的**：控件内容里最后一项若本身是个非空控件，就再往里进一层 —— 删的
      东西始终只有一个（参考实现 DCWriterLite 的 `DocumentControler.Backspace/Delete` 同此）。
    ★ 判定只能落在**流位置**上：这些格子两两共用同一个码点偏移（"内容末尾"与"闭括号之后"是
      同一个 `(段, 偏移)`），按偏移判必然把"删字"和"删控件"混成一件事。
    ★ 后果：**"内容全空但控件都还在"这个状态按键到不了** —— 删掉最后一个字之后光标正停在空
      控件内部，下一次按键就删控件。要构造这个状态只能显式建树（判据 [29](a) 就是这么改的）。
    ★ 表单模式：结构锁（`structureLock` 默认 true）只挡"删控件"那一下；挡不住时退化成"只把
      光标移出去"并记账，不吞掉按键、也不去删控件外那个字。删内容那一下照常生效。

79. ★★ **`InsertNode` / `RemoveNode` 也必须按流位置定位**（2026-10-18）。第 39 条已经写明
    "槽位下标活不过一次规范化"，`UnwrapNode` / `WrapNode` 当时改了，这两个原语漏了 —— 一直
    潜伏到"删一个空控件"这条路上才露头。症状：删控件之后**撤销永远失败**，而 `while
    (canUndo()) undo()` 那种写法把它变成**死循环**（`undo()` 失败会把事务塞回栈顶，
    `canUndo()` 恒真，`heditor_model_tests` 因此卡在第 1.5 节 9 分钟）。
    ★ 两处都要改：`canApply` 与 `applyStep`。`applyStep` 走 `slotAtFlow`（必要时切文本节点），
      `canApply` 走 `slotForFlow`（只读，不能切）。
    ★★ **`canApply` 里取"某个孩子自己的槽位"不能用 `posAt`**：`posAt` 对**叶子**孩子会把
      "流位置等于叶子起点"归给叶子自己（规范表示取最内层），于是容器找出来的是那个叶子，
      报"目标不是容器"。用 `slotForFlow` —— 它对叶子返回"叶子自己那一格"，对文本内部才返回
      "它之后那一格"。`UnwrapNode` 当年是靠"容器必须与记录相同"这条额外判据绕过去的。
    ★ 过期步骤的报错措辞要对齐既有判据：越界那条也要带"**对不上**"（`model_test` 1.2 直接
      `find("对不上")`）。

80. ★ **删控件的撤销快照记"按键之前光标在哪"，不是"选中整个控件"**（2026-10-18）。用户报
    "左括号左边按 del 删掉空控件，undo 后光标跑到右括号右边、还带着选区"。根因：
    `removeControl` 把 `selection_before` 写成 `Range{lo, hi}`（整段控件区间）—— 那是"显式
    删控件按钮"的叙事，键盘那一路照抄就错。⇒ 加 `FlowPos caret_before = -1` 参数，键盘四个
    调用点都传当时的 `selection_.focus`；不传时保持旧行为。
    ★ 判据要两条一起：**光标回到按键之前那一格** + **`hasSelection()` 为假**。只判前者的话，
      "把整段区间折叠成起点"也能通过。

81. ★★ **"只读视图"这一层只有两个失效点，两个都踩过**（2026-10-18）。拆 `CaretResolver` 时，
    位置解析不再持引擎指针，改成吃一份 `PositionView`（9 个指针，全指向引擎的成员容器）。
    ★ **摆的时机**：视图里只有地址，所以"什么时候摆"就是正确性的一部分。`setDocument` 会在
    重建之前先落一次光标，而那时视图还没摆 ⇒ 空指针崩溃（`heditor_tests` 段错误，
    `refreshCaretView` 一次都没被调到）。收口点是 `init` / `setDocument` / `rebuildFromTree` /
    `relayout` 各摆一次。
    ★★ **持 optional 的地址，不持它内容的地址**：`flow_` 是 `std::optional<FlowIndex>`，
    在重建里 `emplace` 进去。`v.flow = flow_.has_value() ? &*flow_ : nullptr;` 在**第一次重建
    之前**取，拿到的是 `nullptr`，而且 `emplace` 之后视图里那个指针**仍然是 nullptr**
    （它指向的是旧内容，不是 optional 本身）。症状：`flowPosAt` 全返回 -1 ⇒ 编辑一律被判
    越界、`edit_test [26]` 整节 15 条红。正解是 `v.flow = &flow_;` + `hasFlow()` 里判
    `flow->has_value()`。★ 判据侧的特征是"整节一起红且都是 -1"，那是"桥整个不存在"而不是
    "某一个位置算错"。
    ★ 其余容器（`blocks_` / `blocks_full_` / `block_flow_` / `layout_` / `controls_` …）都是
    **成员对象本身**，重建是 assign、重排是就地改，地址一直有效 —— 所以"摆一次就够"成立。
    谁要是把某个容器换成了另一个对象（move 走、重新 new 一个），这条就破了。

82. ★ **机械搬迁的两条脚本纪律**（2026-10-18，拆 `CaretResolver` 时全靠脚本搬 45 个方法）。
    其一，**逐字符累计花括号**：按行累计时，`int caretSide() const { return ...; }` 这种
    一行的函数体在同一行内 `{` 与 `}` 相抵，循环判不出结束，范围会一路吞到下一个多行函数 ——
    这次就这么把 `projectCaret` 的头部吃掉，留下半截函数体（编译能过到链接才炸）。
    要么逐字符累计并记一个 started 标志，要么断言"末行以 } 结尾"。
    其二，**范围算完必须查重叠**：重叠的两个范围按"从后往前替换"处理时，后替换的那个用的是
    已经错位的行号，会静默毁掉文件（这次的表现是 `caretPara` 的范围把 `caretRel` / `caret`
    一起圈了进去）。查重叠只要三行。
    ★ 成员名替换要**先占位再替换**、长的在前：`blocks_` 会吃掉 `blocks_full_` 的前缀
    （变成 `view_.view_.blocksfull`）。
    ★ 兜底是编译器：把要搬的方法声明删掉，调用点漏改的地方会一条条报出来。

83. ★★ **命令层的边界是"这次编辑发哪些步骤"，不是"文档怎么重建"**（2026-10-18，拆 `EditCommand`）。
    编辑入口搬进命令层之后，"事务交出去"与"编译产物重建"必须分开：命令只造事务（步骤、撤销
    快照、光标落点），重建归引擎 —— 出口是 `EditHost::commitEdit` 一次虚调用。踩到的三处：
    ★ **`ParaDelta` 原先嵌在 `EditorEngine` 里**，命令层要构造它就得先把它提到
    `edit_command.h`（命令层不该反过来 include 引擎头）。判据是编译期：搬的时候编译器一条条
    报"未声明的标识符"，比事后回忆边界可靠。
    ★ **`setControlProp` 的返回值必须变富**：引擎的 `setControlPropAndRender` 要问"值变了没有"

    实测（14 磅 / 行距 1.85 / 45 磅盒）：带原子那一行的行高 45，而它自己的行盒是

      （验过：`validateRef`、`italic`）。

100. ★ **往返判据用"哈希相同"比用"逐字段相等"更强，但必须配反向验证**（2026-10-19）。
     `rev` 的落盘只写形状与身份，哈希与段落数在重建时重算 —— 于是"读回来哈希相同"直接等价于
     "所有参与哈希的字段都写出去并读回来了"，不需要再维护第三份字段清单。
     但这条判据有个前提要亲口验：**它真的会红**。做法是临时删一行写出，重建，看断言失败，
     再恢复（本次两处都验过）。没验过的恒真断言，与没有断言是一回事。
     ★ 只靠哈希会漏掉的只有两类：身份（节点号，哈希刻意不含）与水位，两者单独断言。
     ★ 别忘了"写端确定性"这一条：同一份修订写两遍必须字节相同（池按首次出现编号，遍历顺序
       固定）。否则往返虽然对，diff 与缓存键都会失效。

101. ★ **读端按"能不能读出来"放宽，会把种类与载荷不符的文件读成正常文档**（2026-10-19）。
     修订层的载荷按种类决定（文本带字符属性、段落标记带段落覆盖、控件带控件记录），读端若
     只"看见哪个键就读哪个"，一份把段落覆盖写进文本节点的文件会被读成"文本节点 + 一份被忽略
     的段落覆盖"，看起来一切正常，下一次编辑对它做错事。
     ⇒ 每种载荷只认自己那几个键，别的一律拒绝；根形状（Document 下正好一节）同理 ——
       `bodyOf` 只认第一节，多一节是静默忽略，不是兼容。

102. ★ **行内容器与块级容器在段落定位上不是一回事**（2026-10-19，表格进载荷时踩）。
     `rev::locate` 里 `off` 记的是"这一段已累积了多少码点"，用来把 (段号, 段内码点) 换成
     某一层孩子表里的落点。这个口径对行内容器（内容控件）成立：控件里的文字就是当前段
     文字的延续。对表格不成立 —— 格里的段落是**另一段**，`off` 必须从 0 起。
     ⇒ 第一版把表格按行内容器处理，症状是"第一格能打字、第二格往后的落点永远偏出两格
       （或整格）文字"，而插入本身不报错。
     ★ 规则：容器分两类。行内容器（ContentControl）参与当前段的码点累积，有"在该段 cp 处
       进入它"这种落点；块级容器（Table / TableRow / TableCell）自成段落序列，只认"这一段
       在它里面"，段号减去容器起点、码点原样就是段内坐标，离开时 `off` 归零。
     ★ 判据：格内插字落在指定格（不是相邻格），以及"改一格文字的损伤正好是那一块"。

103. ★ **改了列宽却报"没有损伤"，是两条规则各缺一半**（2026-10-19，TRAPS 97 的落地）。
     97 条说"损伤集合 = 内容损伤 ∪ 容器几何损伤"，只说对了一半。实测要两处同时改：
     ① 投影的块哈希要并进外层容器的自身哈希与格路径，否则重排时命中排版缓存、画面停在
        旧列宽（损伤报对了也没用）；
     ② 损伤下降要先比自身哈希（不含孩子），变了就整段记账，否则容器属性变化时孩子哈希
        全相同，下降走完一处都不记，报"没有损伤"。
     ⇒ 两条各自可证伪：去掉 ① 是"表内五块的哈希全变"红；去掉 ② 是"改列宽的损伤是整张表"
       红。只做一条会觉得另一条"反正也用不上"。
     ★ 范围按容器层级定，不是一律整表：列宽影响整张表，行高只影响那一行。

104. ★ **原子盒子的算法只有一份，否则两条路会在某个岔路上分叉**（2026-10-20）。
     图片/公式的显示尺寸有四条岔路（绝对宽 / 只给一边按原图比例 / 都没给但有像素 /
     连像素也没有用默认框），两条路（编译与投影）各写一份时，分叉的表现是"同一份文档在
     两条路上行高差一截"。它不报错、不崩，只有逐字段比较抓得住。
     ⇒ 抽成 `src/core/doc/atom_map.*`：输入是与模型无关的 `AtomGeometry`，输出盒子磅值 +
       "相对长度"标记，诊断由调用方按自己的节点号记（文案共用）。
     ★ 盒子必须延到落段时才算：公式的默认框按段落字号估，而字号是段落属性。两条路都是
       "先记一枚原子，落段时补齐"。
     ★ 判据：四种形状逐一对值 + 与编译产物逐字段相同；变异（宽高对调）必须红。

105. ★ **派生值不能进内容哈希**（2026-10-20，域进载荷时定）。
     `FieldSpec::cache` 是求值结果。把它算进内容哈希，"同一份文档求值前后"就是两个哈希，
     撤销回到旧修订时对不上 —— 而内容一个字都没改。
     ⇒ 哈希只算作者内容（种类、属性名），cache 照样落盘（重新打开先显示旧值），
       往返判据对域另做一份逐字段比对。
     ★ 同族判断：凡是"由排版/求值写回节点"的字段都属这一类。加字段时先问"它是内容还是
       结果"，再决定进不进哈希。

106. ★ **迁移路径表示不了就拒绝，不做"能搬多少搬多少"**（2026-10-20）。
     `rev::fromTree` 的第一版很容易写成"遍历、能搬的搬过去"，多节文档于是丢掉后面几节 ——
     得到的是一份看起来完整的修订，而调用方没有任何办法知道它不是同一份文档。
     ⇒ 签名带 error：认不出的根、多节（节的记录还没进载荷）直接返回 false 并说明原因。
     ★ 判据：多节文档必须被拒绝，且 error 非空。

107. ★ **"增量 vs 全量"的自审证明不了实现正确，只证明两条路径一致**（2026-10-20）。
     排版自审的参照物是 `layoutDocument(...)` —— 与增量路径同一份代码。所以把错误改在
     排版实现里（实测：表格行矩形的 y 加 0.5 pt），自审照样全绿：两侧一起错。
     ⇒ 自审只能抓"增量续排与整篇重排不一致"。要证明它真的看得见某一类数据，得**只改参照侧**
       （`ref.placed_tables[0].placed[0].y += 0.5f`），看断言是否变红。本次两个方向都验过。
     ★ 同源的坑：审计只比它比过的字段。`placed_tables` 不在 glyphs / lines 里，所以在这之前
       整张表错位、行高错算、跨页切点错，diff 全是 0。加字段时先问"这个几何进哪条判据"。

108. ★ **断行与分页拆开时，竖排的容量是变量，横排的不是**（2026-10-20，步 3 第一刀）。
     横排的断行容量是块的可用宽度，与页无关，所以可以"一次切完整块"；竖排的容量是"这一条
     带还剩多高"，而换带由已经排了几列决定 —— 容量随排版推进变化，只能一列一列地断。
     ⇒ 抽 `breakLine`（切一行 + 算度量，无页号无 y）+ `breakBlock`（横排的循环）。
       强行让竖排也用"一次切完"会先按整页高度切、再换带，跨带的列会被切错位置。
     ★ 顺带：横排的行高与竖排的列宽是同一个式子（行距与内容撑高取大），原本是两份逐字
       相同的代码，现在只有一份。

109. ★ **重构锁（摘要固定值）的失效方式是"谁改谁重打一个数"**（2026-10-20）。
     逐位摘要能把"只改结构"的重构钉死，但它不是正确性判据：它只证明前后相同。一旦有人为了
     让测试变绿而重打常量，这把锁就彻底失效，而且失效是静默的。
     ⇒ 使用纪律写进注释与文档：**有意**改变排版行为时才允许重新取值，并且必须写清改了什么、
       为什么。没有这两句，改常量就是掩盖回归。
     ★ 摘要要覆盖得够宽才有意义：行盒（含簇的 9 个字段）、字形（14 个字段）、表格行片段、
       段落索引、簇起点表、统计。只比行数或页数等于没锁。
     ★ 浮点按位入哈希；字体指针按首次出现顺序编号（指针值跨进程不同）。

110. ★ **断言落在"值已封顶"的地方就是恒真的**（2026-10-20，会话层判据）。
     撤销栈有上限，吃掉上限之后再断言"深度没变"：深度怎么变都是同一个数 —— 给它注入
     "空编辑也入栈"的错误，断言照样绿。同族：在缓存命中率为 100% 的场景里断言耗时、在
     空文档上断言页数、在只有一段的文档上断言分段后段号。
     ⇒ 判据要放在**值还没饱和**的地方：本次把"被拒的一步不占栈""没变化的一步不占栈"两条
       从吃了上限的会话挪到 limit=10 的新会话上，注入的三条错误（不清重做栈、空编辑入栈、
       changed 判定失效）才全部被抓住。
     ★ 自查办法：改一处代码，看预期的那条断言是否变红。变不红就是位置错了。

111. ★ **撤销存旧值，不存逆操作**（2026-10-20，会话层）。逆操作要写"删的逆是插、合并的逆是
     分段"的对照表，每一对都必须与正向实现严格对称 —— 两份实现迟早分叉，而分叉的表现是
     "撤销之后内容对了一点、光标与格式不对"。修订不可变、旧值一直在，撤销就是把它拿回来。
     ⇒ 代价是内存，结构共享让一份旧修订只多出根到落点的那条路径。
     ★ 三条必须成对记在判据里的规矩：撤销后编辑必须清空重做栈（否则重做跳到另一条分支）；
       没有变化的编辑不占撤销栈（否则按一次撤销像没反应）；被拒绝的编辑不动状态也不占栈。

112. ★ **产物有两种形状时，只比一种等于没比**（2026-10-20，引擎差分判据）。
     编译产物是两块：块流（排什么）与表格结构（框在哪）。差分判据只比块流时，把
     `fromTree` 里的 `row_span` 丢掉（合并格变普通格），48 轮对照全绿 —— 跨度不进块，
     块的 cell_path 只记(表, 行, 格)下标。
     ⇒ 判据必须覆盖每一种产物：加 `EditorEngine::tableSpecs()`（与 blocks() 同一层），
       逐张比宽度/列宽/行规则/每格跨度/每格块区间。补上之后同一处变异第 0 步就红。
     ★ 同族：只比 glyphs 不比 lines（或反过来）、只比块不比控件跨度、只比帧不比覆盖层。
       加一种产物时先问"哪条判据看得见它"，看不见就等于没有。
     ★ 与 107 的区别：107 是"参照物与被测共用同一份代码"，这条是"判据只看了一半产物"。

113. ★ **段落格式落地会重置"段落层面"的每一个位，包括别人设的**（2026-10-20，分节分页）。
     分节强制分页要落成"下一段的段前分页"。第一版在 flush 开头设 `page_break_before = true`，
     块上读出来却是 false —— 后面 `applyParaFormatToBlock` 按段落覆盖面把这一位重写成了
     作者的取值（默认 false）。
     ⇒ 凡是"由容器/结构推导出来、最终写在段落属性上"的位，都必须放在段落格式落地**之后**；
       放在前面等于没设。同族：段落样式解析会覆盖块级字号、行距、语言。
     ★ 判据要能分辨"设了但被覆盖"与"没设"：只比两条路的最终产物看不出哪一侧错，
       所以断言写成"第二节第一段是 true、第一段是 false"（一半真一半假才说明来源）。

114. ★ **按节点号找节点的实现漏了根，流位置 0 上的一切操作都会失败**（2026-10-20，
     引擎改持修订）。`rev::findNode` 第一版从 `doc.root->children` 起压栈，根自己不在里面。
     `FlowIndex::posAt(0)` 返回的容器正是根（流的第一个位置落在各节之前），于是
     `findNode(root)` 拿到空指针 → 插入报"插入位置不在文档里"、删除报"区间起点不在文档里"。
     症状集中在"文档最开头那一位"，其余位置全好 —— 很容易被当成"某种特殊形状"。
     ⇒ 凡是"按 id 找节点"的函数，根必须在候选集里；判据要有一个用例把光标放到 0 再编辑。
     ★ 同族：`parentOf`（从根的孩子起找父）同样要能返回根作为父。

115. ★ **按区间删除必须校验"覆盖总和 == 区间长"，否则会静默只删一半**（2026-10-20，
     引擎改持修订）。修订层的 `eraseFlowRange` 与命令层的 `deleteWholeRange` 都按"起点
     所在那一层的孩子"收集覆盖。区间伸出这一层（起在容器边界、跨格、跨控件）时，收集到的
     只是其中一段 —— 删除"成功"，另一半内容还在。
     表象：浏览器探针里退格整条不生效（`deleteWholeRange` 发出跨层区间 → 修订层拒 → 整批
     失败 → 命令层返回 false → 按键被吞），35 条断言红；而 native 单测全绿（那边没有这种
     形状）。**判据没覆盖的形状，错了也是绿的。**
     ⇒ 两处都加"覆盖总和必须等于区间长，不满足就拒/返回空"，让跨层区间退回按文本节点切分
       的那条路。宁可编辑失败，也不要删一半。
     ★ 同族：任何"按结构收集再逐项删除"的实现都要有这条求和校验。

116. **跨模型比较时，身份字段不可比**（2026-10-20，引擎差分改参照侧）。
     修订转回模型树（toTree）会重新分配节点号，于是三类身份字段两边不同源：
     `InlineObject::owner`、`CellSlot::table`、`LayoutTable::handle`。
     逐号比较的判据恒不相等（恒红），干脆不比又会让"owner 错位"这类缺陷漏掉（恒绿）。
     ⇒ 比较口径统一放在 `tests/block_compare.h`：块比较抹掉 owner 与 cell_path 的 table，
       表格比较用 `sameTableShape`（不比 handle）；身份的另一半由"控件成对计数"与
       "段的 first/mark 流位置一致"两条独立判据盯住。

117. **性能数字要写清"一次性的"还是"每次的"**（2026-10-20，量步 4 的退步）。
     `longDoc.fullMs` 是 `run(7)` 装载 2000 段之后的**首次全量排版**（复测 79~183 ms，
     随机器负载波动），10.13 初稿把它当成"每次编辑多花的时间"写进了文档 —— 高估一个量级。
     真实的每次成本只读 `rebuildCompileMs` / `rebuildFlowMs` / `rebuildCopyMs` / `layoutMs`：
     2000 段敲一个字 = 投影 2.2~3.6 + 流 0.3 + 副本 0.3 + 增量排版 1.9 ≈ 5~7 ms。
     ⇒ 引用性能数时同时写三件事：**在哪台/哪个构建上量的、覆盖的是哪一步、一次性还是每键**。
     `out/_perf.mjs` 是这组数的复现脚本（移光标 / 敲键 / 撤销 / 缩放四档）。
     ★ 同族：`editStats` 里 `totalMs` 只含"排版 + 帧指纹 + 绘制"，不含投影 —— 拿它当
       "一次编辑的总耗时"会漏掉最贵的那一段。

118. **为省一次拷贝而建的索引，可能比它省下的还贵**（2026-10-20，投影复用第一版）。
     `project` 接上一轮产物时，第一版按段落标记建 `unordered_map<NodeId,int>` 当索引：
     两千次堆分配 + 两千次查找，实测 3.5 → 4.0 ms，**比不复用还慢**。
     换"顺序游标 + 24 格有限探测"（块按序产出，天然对齐）+ 延迟构造 `ProjectedBlock`
     （身份与哈希先用局部变量算），才落到 0.85 ms（全量 1.5~3.7）。
     ⇒ 缓存不是免费：建索引的开销要算进同一笔账，并且**改完当场量**，别按"缓存一定更快"推断。
     ★ 同族：复用只省"物化"，走树与算哈希仍要过一遍 —— "接了缓存"与"O(改动规模)"是两件事，
       报告里必须分开写（这次写进了 10.14 的"仍然欠着的两笔"）。

119. **Worker 宿主下 `editStats` 晚一拍，读到的是上一轮**（2026-10-20，`out/_perf.mjs`）。
     在 `textarea` 上派发 keydown 之后立刻读 `window.__heditor.editStats`，`reused` 还是 0，
     看上去像"没复用"；连打几次之后从第二次起才读到 1999。原因：编辑经 `postMessage` 进
     worker，宿主这边的读数在消息回来之前就取了。
     ⇒ 性能探针要么在每次编辑后等一次 quiesce/present，要么按"连打 N 次、读第 N 次的数"
       理解；把 0 当成缺陷会白查一轮。

120. **换成访问器之后，裸写成员的地方编译器不会提醒**（2026-10-20，块流归零那一刀）。
     `blocks_` 改成 `blocks()`（按筛名单返回两份之一）之后，四处裸写 `blocks_` 的代码
     没改：`layoutDocument(fonts_, blocks_, ...)` 三处、`for (... : blocks_)` 一处。
     编译器一声不响 —— 因为 `blocks_` 还在，只是"不筛"时它是空的。
     症状是"排版 0 字形、页数 1"，而不是崩溃或编译错误。
     ⇒ 把成员换成访问器时，**先 grep 该成员的全部出现**（含作为实参传递的裸名），
       再改；判断"改没改全"靠判据（字数、页数），不能靠编译通过。
     ★ 同族：`blocks()` 返回引用，`&blocks()` 取的是"哪一份"的地址 —— 视图里存了这个
       指针之后，筛/不筛切换必须重摆视图，否则视图指着一份、排版读另一份。

121. **after 坐标的区间，不能直接拿去删 before 的块**（2026-10-20，原地更新块流）。
     splice 的直觉写法是 `erase(lo, hi); insert(lo, fresh)`。分段之后 after 多一块，
     旧块流对应的区间是 `[lo, hi - shift)`（shift = m - n），按 `[lo, hi)` 删会多删一块，
     症状是"分段之后少一段、合并之后多一段"，而每一块的内容都是对的。
     ⇒ 区间跨两份修订使用时，先写清"这个下标属于哪一侧"；两侧块数不同时，右端要补 shift。

122. **不能"先按复用跳过内容、失败再降级"**（2026-10-20，投影复用第二版）。
     第一版让 `flush` 在损伤区间内直接搬块、连内容都不收集；坐标一旦报偏（`src` 越界）
     就 `plan_.active = false` 退回物化 —— 但内容已经被跳过了，物化出来是空块。
     症状是"某一段的字整段消失"，51 条判据同时红。
     ⇒ 判定的位置必须早于"不可逆的那一步"：要么先算完哈希再决定搬不搬（内容已收集，
       降级只是重新物化），要么把"降级"做成整篇重来（这次用的是后者：splice 前校验
       fresh 的块数，不等就清空重跑）。


123. **Step 里的流位置是按某个可见性算的，而应用步骤时没人知道是哪一个**（2026-10-20 发现并修复）。
     引擎的 `flow_` 在表单/只读模式下按 `Display` 建（隐藏控件整棵摘除），命令层用它算出
     `Step::at`；但 `rev::applySteps` 内部五处 `FlowIndex` 写死 `Design`。只要有一个隐藏控件，
     它之后的每个落点都偏移"隐藏子树的流位数"。
     实测（`AABB` + 隐藏控件 `XX`）：呈现态位置 4 是"两个 B 之间"，按 `Design` 读却落在
     隐藏控件的内容起点 —— 结果是 `AAZXXBB`（字进了隐藏字段，屏幕上不变），而不是 `AAXXBZB`。
     ★ 第一版探针取位置 2，那在隐藏子树**之前**，两种口径本来就相同 —— 别拿它当反例。
     ⇒ 流位置是二元组（位置，可见性）。`applySteps` / `Session::applySteps` 必须带
       `FlowVisibility`（无默认值）；`Edit`（para, cp）不受影响，因为 `collectParas` 不过滤隐藏。
       判据在 `rev_test` [23] 与 `edit_test` [34](g)：两条互为反向（同一整数两种口径两个落点）。

124. **damage 的块数按 Design 数，投影按 Display 数 —— 块会被搬重**（2026-10-20 发现并修复）。
     `damage()` 的坐标来自 `Node::paras`（数所有段落标记），而 `project` 在呈现态跳过隐藏子树。
     隐藏控件里含段落标记时，`after_blocks` 比真实块数大，`shift = after - before` 随之算错，
     splice 的旧区间右端 `max(0, hi - shift)` 变成 0 ⇒ 一块都不删、再插新块，块流里多出一块，
     表现为**段落重复**。`project.cpp:63` 的 `fresh.size() != hi - lo` 抓不到：它校验区间长度，
     而错的是总数（1 == 1）。
     ⇒ `damage(before, after, vis)`；节点上存第二个顺序统计量 `paras_display`
       （`hidden ? 0 : Σ 孩子`，不进哈希）；`DamageWalker` 里块的加减一律走 `vp(node)`，
       两边都隐藏时整棵跳过；`endsOpen` 按 vis 取最后一个可见叶子。
       判据：[23] 的 `after_blocks == project(..., vis).keys.size()`、隐藏/显示切换各一条、
       增量投影后的块数与全量相同；注入验证：把 `vp` 改回 `paras` 时"隐藏"那条当场红。

125. **"从这里起全脏"的脏区不能走后缀复用**（2026-10-20 发现并修复）。
     后缀复用把 `[from + m_new, 末尾)` 整段搬回来，等于断言"那之后一个字都没变"；而
     `markLayoutDirty(para)` 只给起点，两者一起用就是矛盾。
     症状不显眼：括号占位是占位簇，宽度变了但断行没变，续排状态（页号 / 行数 / 游标 y）
     比对通过，搬回来的是带着旧括号的旧行盒。
     实测：8 段文档、两个字段（第 0 段与第 5 段）、聚焦档；光标从第 5 段挪到第 0 段之后，
     第 5 段的括号仍在版面上（`placeholder` 簇数 2 而非 0）。注入验证：把"右端已知才复用"
     去掉，"聚焦换字段之后占位真的挪了"当场红。
     ⇒ 排版的脏区必须带右端：`layout_dirty_from_` / `layout_dirty_to_`（-1 = 未知）。
       只有已知右端才允许后缀复用；未知时退回"从 from 续排到末尾"。
       另：换字段的脏区是两个字段各自段跨度的凸包（`markLayoutDirtyForBracketPlans`），
       不是"从最靠前的控件段到末尾" —— 后者在聚焦档下等于整篇重排。
       判据在 `edit_test` [56](d)。

126. **按节点号开数组的索引，占用会随会话长度增长**（2026-10-20，`FlowIndex` 紧凑下标）。
     不可变树每次编辑都分配新节点号、旧号不回收，`next_id` 是递增水位，而活节点数不增长。
     按 `next_id` 开三个数组（`by_id_` / `first_` / `span_`）等于让派生索引的占用只随时间
     变差：2000 段文档编辑一万次之后约 0.5 MB，而且每次构造都要整份清零。
     ⇒ 派生索引的下标按活对象重新编号，节点号只作查表键。查表用开放寻址哈希（容量取
       `2 × 活节点数` 的 2 的幂，负载 ≤ 0.5，`id = 0` 当空槽），不要再用 id 直接下标。
       构造顺序可以是"先遍历、后建表"——遍历只写不读，不必边插边查。
     ★ 判据必须带前提：先断言水位真的涨了，否则"占用不变"在编辑没发生时恒真（110）。

127. **账挂在呈现上，多一次呈现就会把它抹掉**（2026-10-20，`editStats` 发布时机）。
     `relayout()` 已经算出这一轮排了多少段、花了多久，但 `relaid_*` 要等
     `presentInternal` 才从 `last_*` 抄过去；而"本轮没重排"的分支会把它们连同耗时一起清零。
     宿主的一次操作常常呈现两次：`app.js` 的 `undo()` 内部走 `undoEdit()`（已重排重绘），
     随后又 `present()` 一次 —— 第二次落到清零分支，`_perf.mjs` 读到的排版账是 0，
     看上去像"撤销没有排版"。
     ⇒ 账在产生它的那一步发布：排版组由 `relayout()` 写，文档规模组由重建写。呈现只结算
       "本轮有没有发生"（`layout_ran`），并且只清标志、不清数字 —— 数字的语义是
       "最近一次"，不是"这一拍"。合计（`total_ms`）用标志决定要不要把排版与页指纹加进来，
       否则闪烁拍会每 530ms 重复上报一次排版耗时。
       判据：`edit_test` [56](e) 两次连续呈现、`edit_probe` [3] "不抹掉"两条。

128. **按页缓存的像素，版本号要含"配置"，不能只含内容指纹**（2026-10-20，5A 页位图）。
     页指纹只哈希字形与行盒几何；页面底色、页边框、格线、原子框、缩放、连页这几项
     一个都不在里面。只按页指纹判"这份像素还作数"的后果是：改了底色或边框之后，
     屏幕一直是旧的，直到某一页的内容变了才跟着换。
     ⇒ `setConfig` 里显式比这几项，任一不同就整份清掉页缓存；判据是 `auditPage`
       （它绕开缓存从零光栅，缓存没作废时两边立刻对不上）。`edit_test` [57] 末条守着。

129. **自审的参照物不能读被审的那一份缓存**（2026-10-20，`auditBase` 清页缓存）。
     页缓存出现之后，"底图强制全建再比"只是把同一批页位图又搬了一遍，比出来的是
     搬运的确定性，不是光栅的确定性 —— 页位图本身写错它照样全绿。
     ⇒ 自审一律先丢掉被测的那一层：`auditBase` 先清页缓存，`auditPage` 画到临时位图
       而不是缓存里。与 `auditGlyphPages` 同源：同一个代码路径当判据必然恒绿。

130. **页位图搬进帧的取整，必须与 refresh 矩形同一口径**（2026-10-20，行带搬移）。
     `copyRectFrom` 按 floor(起点) / ceil(起点 + 高) 取像素，而按页搬的接口收的是整数带。
     直接截断终点会少搬一行，症状是"版面上留一条旧墨迹"，且只在恰好跨半像素时出现
     （`auditFrame` 抓得到，肉眼看不出规律）。
     ⇒ 搬移范围与 refresh 那个 Rect 由同一组 floor/ceil 算出，不要各算各的。

131. **`setFontCacheConfig` 之后，字体的存储读账恒为 0（现状，未修）**（2026-10-20）。
     实测同一条压力文档（2000 段，lazy 模式重装字体）：不调该配置时读 343 次、
     常驻 1.34 MB、命中 31571 / 未命中 343；先调 `setFontCacheConfig(4096, 768)` 再重装，
     五格全 0（命中与未命中也是 0）。
     ⇒ 这不是渲染层的问题：full 模式同样为 0，而 full 模式不走页缓存的任何判据。

       在修好之前，不要把这几条红色当成"渲染或排版退步"的证据。

132. **页位图不含瞬态，帧含瞬态**（2026-10-20，5B 的第一条判据）。

     选区 / 表单标记；不藏光标去比，永远差那一块，而失败只报 "3/4"，看不出差在哪儿。
     ⇒ 任何"页 vs 帧"的像素判据先 `showCaret(false)` + `repaint()`，比完再放回来。
       反过来说，这也正是 5D 要拆层的理由：两者本来就不是一份东西。
     ★ 比"整页上传"更值得记的是它的量级：一次光标移动现在只该传 72 px²，
       整页是 102000 px² —— 差三个数量级。判据落在面积上，才挡得住"又退回整页"。

133. **读命令不能有副作用，`pageRgba` 不负责补光栅**（2026-10-20，5B）。
     如果 `pageRgba(page)` 在页不新鲜时顺手光栅一次，读一次诊断就会把 `raster_glyphs_`
     算大，下一次 `present` 报出来的"这一拍画了多少字形"就是假的。字形账是"增量到底有没有
     发生"的证据，被一次读污染之后，所有性能断言都失去意义。
     ⇒ 读接口只给"已经有了且作数"的那一份，不新鲜就给空视图；补光栅只发生在
       `presentInternal` 里。`pageDirtyRects` 则是"取走即消费"，读后清零 —— 与
       `takeBlitBox` 同一套语义，宿主必须在 `present` 之后读。

134. **帧整窗重贴之后，旧瞬态在帧上没了，在页画布上还在**（2026-10-20，5C）。

        `transient_dirty`，与增量分支同一口径。
      ★ 这一条**目前没有判据**：能触发它的两个入口（切只读模式、改字段只读属性）都会让
        页位图或标记位置跟着变，整页脏正好盖住它。试过两版判据都是恒真 —— 第一版让光标
        与字段同页（新光标兜住），第二版改只读属性（新旧括号位置重合，新括号兜住），都已删。
        补这几行是为了不依赖那个巧合：将来标记不再随排版走时，它是唯一的保障。

135. **"引擎算了脏矩形"与"宿主按矩形贴"是两件事，判据必须落在宿主那侧**（2026-10-20，5C）。

137. **`putImageData` 六参数 + 负 dy 在 OffscreenCanvas 上会裁错**（2026-10-20，5C）。

142. **连页接缝：一行会被条带边界切穿，凡是"按页归属"的读取都要按几何相交重做**（2026-10-21）。
      连页把内容切成固定高度的条带，行不会为条带边界让位 —— 于是一行常常有半截在上一条带、
      半截在下一条带。判据：`edit_test` [59] 把同一份文档切成 15 带再拼起来，与切成一条
      整带逐字节比（注入故障实测 27 行不同、首行正好是第一条接缝）。
      原来有三处各自按"页号"归属，全都错，而且错法不同：
      - 字形页号按**基线**取（竖排是对的，横排整行共用一个基线 → 整行被塞进下一带、
        页内 y 为负、上半截被位图裁掉）；

      ⇒ 三条规则，缺一条就是半行字或半行高亮：
        横排字形跟行盒同属一条带（竖排保持按字形自己的 y，因为列本来就是一列到底）；
        下一条带在顶部补画上一条带越过带底的那一截（`rasterIntoBitmap` 的 spill 趟，
        字形 / 原子框 / 格线 / 括号与小点都走同一趟，`dy = -带高`）；
        页指纹把越过带底的字形同时混进下一条带（否则永不失效）。
        瞬态同一条规矩：`collectTransient` 把上一条带里越过带底的选区与光标在本带再记一份。
      ★ 判据不能只看"接缝处没有空白"：旧实现在接缝处也没有空白 —— 它是把整行挪到了
        下一条带、上半截画在位图外。只有"分带 == 整带"这种逐字节比才照得出。
      ★ 别把 `EngineConfig::continuous` 当成 `page.continuous`：后者由 setConfig 装配，
        直接在 page 上置位不生效，测试会静默跑成分页（我在这条上栽过一次，
        症状是"连页判据全绿而接缝全错"）。

144. **内存里的表示不是文件格式：落盘前先问"这份文件给谁看"**（2026-10-21）。
      阶段 6 第一刀把保存打通之后，打开文件看到的是
      `"t":[24739,32773,24739,...]` —— `rev::RunPayload::text` 是
      `std::vector<uint32_t>`，序列化直接 `j[kText] = p.text`，于是内存表示（码点数组）
      原样成了文件格式。它读得回来、往返判据全绿、哈希也对，**没有一条断言会红**：
      判据比的是"读回来还是不是同一份文档"，而它确实是。同理 `"fi":0` 把字体库下标写进
      文件 —— 换台机器装载顺序一变，同一个 0 就是另一张脸。
      ⇒ 判据要加一条**人能读**的：`edit_test` [60] 里 `saved.text.find("\"t\":\"保存第 0 段")`
      与 `"fonts":{"0":"NotoSansSC-VF.ttf"}`。这两条不比语义、只比"打开文件看得到内容"，
      正是往返判据看不见的那一半。
      ★ 反过来也要小心：**可读不等于可以替换字符**。写端遇到孤立代理时若用
        `codepointsToUtf8`（它把非法码点换成 U+FFFD），文件写出去了、读回来是另一份文本，
        而所有字段都"看起来正常"。要么整份失败，要么不写。
      ★ 版本号语义：v1 → v2 是**改含义**，所以 `kRevFormatVersion` 加一、读端按类型分派
        而不是按版本分派（字符串 / 数组各自自证），`kMinReadableVersion` 留给老文件。
        没有"只改解析不升版本"这条路 —— 那样 v1 的读者会把 v2 的文件读成一份空文档。
      ★ 字体身份要跨装载方式稳定。同一份字体，full 那条路给引擎的名字是 label
        （`Noto Sans SC`），lazy 那条是 MEMFS 路径（`/NotoSansSC-VF.ttf`）。存进文件之前
        先取 basename，两个名字才会落到同一个标识上。
      ★ 再进一步（同日）：文件名连"跨装载方式"都还没稳住，更稳的是**字体自己报的名字**。
        PostScript 名（name 表 ID 6）是 OpenType 里唯一性有规范保证的那一个；族名不区分
        字重，只能当第二级；文件名可以改，只能当第三级。三级匹配的顺序就是稳定性的顺序。
        读名字用 hb_ot_name_get_utf8；按需装载也读得到，因为 name 表留在骨架里
        （FontSource::inSkeleton 是黑名单式，只剔轮廓与位图表）。
      ★ 可变字体的 ps 是**默认实例**的名字（NotoSansSC-VF.ttf → NotoSansSC-Thin），
        与引擎实际钉的 wght 400 不符 —— 当文件身份准（同一文件同一 ps），
        当"用了什么字重"不准。要准得等字体变体进模型，与粗体/斜体是同一件事。

148. **增量平移不能"老坐标 + 大增量"：行盒要自己记 ascent / descent / 行高**（2026-10-21）。
      症状：删掉一整张表之后，"增量 == 从零重排"的摘要对不上；差的是 `block_hi_pt` 的末位
      （41.199997 vs 41.200001、54.757797 vs 54.757812），`block_lo` 有时也差一位。
      根因有两层：
      · `lb.block_lo_pt += dy`（dy = 新位置 - 老位置）是 `old + (s - old)`。老的与新的离得远
        （跨页几页）时，这个重新结合会把末位舍掉；离得近（同一页里挪一行）时恰好精确，
        所以过去一千多条断言全是绿的 —— **不是没这个洞，是没踩到**。
      · 反推也不行：`ascent = axis - lo`、`descent = hi - axis` 看着能还原，但 `placeLine`
        的 lo 本来就是 `(top + ascent) - ascent`，减回来不一定等于原来的 ascent。
      ⇒ 让行盒把自己那三样记下来：`LineBox::ascent_pt / descent_pt / advance_pt`
        （breakLine 给的 ascent / descent / line_h）。平移时按同一公式重建：
        基线 = 行顶 + ascent、上边 = 行顶、下边 = 基线 + descent、`s += advance`。
        `placeLine` 的行顶也改成直接记 `top`（不再绕基线减一次），这样"行顶"是唯一锚点。
      ★ 代价：摘要 A/B 重取（180 行/3231 字形/17 页 与 157/927/15 一字未变，只有个别行的
        上边差一个末位）。**这是有意改口径**，重取时必须在测试里写清原因。
      ★ 顺带修掉一个真 bug：平移原来拿 `size_pt * line_factor` 当行高，而真正的行高是
        `max(pitch, ascent + descent + leading)` —— 行里有比文字更高的行内原子时它更大，
        那个后缀会被排错，只是当时没有"含原子的后缀"判据。
      ★ 判据形状：这类末位错**只能**靠逐位对拍（digest）或 `auditLayout` 之外的精确比较看见。
        `auditLayout()` 是量化的（0.01pt），它对这件事恒绿 —— 别拿它当"逐位相同"的判据。

153. **Emscripten 交叉编译里 WIN32 是假的；find_program 会把 `tsc.cmd` 认成 `tsc`**（2026-10-22）。

154. **从 C++ 抽 JSON 键：注释里的 ASCII 引号会把结构流搅乱**（2026-10-22）。

158. **`flush()` 的唤醒点要挂在真正的回话点上**（2026-10-22）。

      `await flush()` 直接卡死（3 s 探针超时，而几何早就更新完了）。原因是**普通写不推 ack**：

      （行首是 `bool`），一直走到更早那一段块 —— 于是 `@param x_pt_doc` 被记在
      `canUndo` 头上，报告里的行号看着毫无道理。⇒ 声明与注释块必须分行；判据看不出这类
      粘连，只能靠"同一块里出现了不属于它的参数名"这种怪现象反推。

177. **修注释缩进不能 `' * ' + text`**（2026-10-22）。
      项目里的块注释有悬挂缩进（`     *   续行`，`*` 之后还有两个空格）。按"标准化"
      重排会把它们全压平 —— 104 行看着"修好了"，实际丢了排版信息。⇒ 只改 `*` 之前的
      前导空格，`*` 之后的字节原样搬运。同理，`*/` 的缩进是 `/**` 的缩进 + 1。

178. **隐藏的槽画布还留着上一个页号**（2026-10-22）。
      `SlotCanvases.sync` 把窗口外的槽 `display:none` 之后没有摘 `data-page`，于是
      "这张画布显示的是哪一页"这个读数在隐藏槽上说谎；按 `pageCanvasList()` 数"一页一张"
      会数到固定槽数（8），页号数组是 `[0,1,2,3,4,null,null,null]`。
      ⇒ 隐藏时 `delete dataset.page`；判据只看 `display !== 'none'` 的那些（槽数是实现
      细节，两种传输都满足"一页一张"）。

179. **判据不要读自己的构建产物，除非没有别的路**（2026-10-22）。
      `idl_check` 读 `web/engine_api.js`（vite 打的 IIFE）取 IDL，代价是多一条"先构建"
      的顺序约定，而它自己那条 mtime 检查在 `const problems` 之前引用 `problems` ——
      "产物过期"于是表现为 ReferenceError。`api.ts` 零 import，转译后可以直接执行；
      读源码之后，"核对的是不是当前源码"不再靠约定。
      ⇒ 同类问题的判据：先看真源能不能直接跑（TS 用 `transpileModule`，注意 R4 不许在
      注释里写"早先/原来"这类流水账，写结论）。

180. **`textarea.focus()` 会把滚动容器滚到它当前的位置**（2026-10-22）。
      承接键盘的 textarea 是绝对定位在文档流里的（贴在光标处）。焦点给它时，浏览器会
      把它滚进视野 —— 而它此刻还停在上一次光标的位置。Worker 传输下"落光标"是异步的，
      `mousedown` 里 `focus()` 先于落点完成，于是点第二页时视口先被拽回上一次光标那一页。
      ⇒ `focus({ preventScroll: true })`；滚视口只由 `scrollCaretIntoView` 按落点算。

181. **worker 的 `settle()` 不是同步点**（2026-10-22）。
      它是纯本地读 `mirror.stats`，而 `write()` 只是排队 —— 写完立刻 settle，拿到的是
      上一拍的统计（光标页、光标 y、页数全是旧的）。上层拿它决定"滚不滚视口""IME 摆哪"，
      症状是多页文档上点一下跳回上一处。⇒ `settle` 先 `await whenIdle()`（在途写与查询
      都收到回话、那一条状态也落了地）再回 `{ stats }`。
      同族：`settle` 回的是 `{ moved, scrolled, stats }`，调用方必须取 `.stats` ——
      直接当 stats 用会让 `caretPage/caretY` 全是 undefined。

182. **闪烁相位不能跟着"每一拍"重置**（2026-10-22）。
      `finish()` 每份状态都跑（Worker 每拍都推），在里面 `resetBlink()` 会把相位按回
      可见、重启计时器；可画面已经按上一拍的相位画过了。结果每一拍都是"相位可见 → 翻成
      隐藏 → 画隐藏"：点一下亮一拍，之后永远不亮。
      ⇒ 相位只跟用户动作走：`afterEdit` 在 settle 之前写一次"可见"（这一拍才画得出来），
      settle 之后重启计时器；`start()` 起一次。`finish` 不碰闪烁。

183. **"归零滚动位置"这种一次性信号要就地消费**（2026-10-22）。
      引擎换文档时把滚动位置清了，用一份随状态送出的标记通知宿主。宿主若攒着等下一次
      `finish` 再消费，就会在用户已经滚到别处之后才生效 —— 表现是"点一下页面跳回顶部"。
      ⇒ 标记在哪一层到达就在哪一层用掉（worker 在 `onState` 里直接 `host.resetScroll()`）。

184. **自定义剪贴板类型在系统剪贴板上必须带 `web ` 前缀**（2026-10-22）。
      `navigator.clipboard.write([new ClipboardItem({'application/x-foo': blob})])` 不会抛，
      但写入时把这个类型**静默丢掉**，读回来只剩 `text/plain`。症状是"复制粘贴能用，只是
      控件与表格都没了"，而每一层都报成功。⇒ 写系统剪贴板用 `web application/x-foo`，
      读端两种名字都认；事件的 `clipboardData.setData` 那条路用不带前缀的名字（那边认）。

185. **事件里的 `DataTransfer` 只在处理期间可写**（2026-10-22）。
      copy / cut 事件异步回来之后再 `ev.clipboardData.setData(...)` 不报错、也不生效 ——
      剪贴板是空的，而调用方拿到的是 `true`。Worker 传输的复制是一次往返，正好落在这个坑里。
      ⇒ 判断载荷是不是同步回来的：同步 → 写事件的 DataTransfer；异步 → 写
      `navigator.clipboard`（`then1` 折叠两条路，但"写进哪里"必须按同一个标志分）。

186. **程序化改 `scrollTop` 之前必须先把滚动高度对齐，改完必须当场发视口消息**（2026-10-22）。
      连续粘贴把文档撑长时，"滚动"发生在宿主、"换窗"发生在引擎、"建画布"发生在收尾，
      分属三拍。Worker 传输下 `pages.sync` 只在 `finish` 里跑，而 `scrollCaretIntoView`
      在它之前 —— 容器还按上一拍的页数算高度，赋值 `scrollTop` 被浏览器**夹在旧底边上**。
      夹过之后值根本没变，浏览器不会再派发 `scroll` 事件，于是窗口永久停在旧位置：
      症状是"pages 容器一路涨到几十页，末尾那一段永远没有画布，粘贴的字也看不见"。
      ⇒ 滚动前先 `pages.sync`（幂等，只补高度）；改完用 `nudgeViewport` 主动把新位置
      交给引擎并把 `lastScrollTop` 记成新值（免得 `onScroll` 再发一遍）。

187. **窗口的滞回判据取"引擎这一刻的窗口"，不能取"上次请求过的锚点"**（2026-10-22）。
      `setViewportAnchor` 只是存值，真正生效在 `present` 里 —— 而 `repaint()` 会把越界锚点
      **夹回文档范围内**。请求值不跟着变，两者一分叉，滞回就一直拿着夹之前的数判
      "盖得住"，窗口再也不换（读数上 `geometry().window` 一直停在旧页，而 `scrollTop`
      已经是新位置）。⇒ `retarget` 里 `cur` 用 `mod.windowFirstPage()/windowPageCount()`。

188. **`#pages` 容器不许画"纸底"背景**（2026-10-22）。
      用 `linear-gradient` 给"还没渲染的页"铺白纸，会让"这里没有画布"和"一张空白页"
      看起来一模一样 —— 排查时被它误导过一整轮（截图里 8 页高、canvas 只有 2..7，
      看到的"白"全是背景）。真白纸由引擎的页位图给（`alpha:false` 的不透明画布），
      缺画布就该露出 `#stage` 的底色。代价是甩滚时未及渲染的页会闪一下底色，接受。

189. **inline 的页画布必须 `position:absolute`，`#pages` 必须是定位祖先**（2026-10-22）。
      `PageCanvases.canvasFor` 只 `appendChild`、不设定位，而 `#pages` 又是 `static` ——
      画布于是**参与文档流**：`style.top` 完全不生效（页间距丢失、逐页漂移），换窗时
      `remove` / `appendChild` 改变流的高度，浏览器据此做**滚动锚定**，把 `scrollTop`
      往上拽（实测 3000 → 1244）。症状是"滚轮往下滚自己弹回来、只能拖着滚动条下去"，
      以及"下面一段没有画布"。关键在于：**`Element.prototype.scrollTop` 的 setter 抓不到
      这次改写** —— 它来自浏览器的布局动画，不是 JS。
      Worker 侧的 `SlotCanvases.acquire` 一直带着 `position:absolute; display:block`，
      所以这个 bug 只在 inline 传输上显形。
      ⇒ `canvasFor` 里补 `className='pg'`、`position:absolute`、`left:0`、`display:block`；
      `ensureMarkup` 的 `#pages` 带 `position:relative`，`createDomHost` 再兜底补一次
      （库升级前造的旧骨架没有这条）。判据：`clipboard.spec` 的"往下滚不弹回、可见页
      都有画布也有墨"（滚轮序列单调 + 可见页抽样有墨）。

190. **读命令在 `api.ts` 里已经 `JSON.parse` 过了，门面不能再按字符串解析**（2026-10-23）。
      协议表那批读（`caretStyleJson` / `charFormatAt` / `paraFormatAt` …）返回的是**对象**，
      而同线程宿主给的是原样文本。门面若只认 `typeof raw === 'string'`，回显会**永远是
      空补丁** —— 而它不报错：`parseJsonObject` 的约定就是"坏数据当空对象"，于是工具栏
      一个按钮都点不亮，`formatAt()` 恒为 `{}`，`format()` 却返回 `true`（写确实成功了）。
      查这条时的错误方向：怀疑引擎的流位置、`intervalOf`、`hasFlow`，甚至给 C++ 加诊断
      导出 —— 而真相在 TS 的一行 `typeof`。
      ⇒ 读数一律按"对象或 JSON 文本"两种形状接（`parseJsonObject`），判据要写
      "设完之后读回来等于刚设的值"，不能只判"命令返回 true"。

191. **库内骨架不许用 id**（2026-10-23）。
      `#stage` / `#pages` / `#ime` 在一份文档里只能有一个实例的：同页挂两个编辑器时，
      `document.getElementById` 只会给第一个，库若按文档去查就会**静默操作另一个实例的
      舞台**（滚动、坐标换算全错，而画面看起来仍在动）。即使所有查找都按容器作用域，
      重复 id 本身也是无效 HTML，页面的 CSS（`#stage { ... }`）还会同时命中两个实例。
      ⇒ 类名 + 容器作用域：`heditor-stage` / `heditor-pages` / `heditor-ime`（`host/parts.ts`），
      页画布 `heditor-pages__canvas`，错误面 `heditor-error__title` 等。**旧 id 的兼容分支
      不留**（开发阶段不做向后兼容，用户 2026-10-23 明确）：查一次类名，没有就是没有。
      判据：`multi.spec` 的"骨架不带 id（同页两个实例不会撞）"与"两个实例各看各的舞台"。

192. **段级整形指纹必须覆盖"换字体实例"的一切输入，字重尤其容易漏**（2026-10-23）。
      段级整形缓存（`ShapingCache`）的键是 `shapingFingerprint`：文本、书写模式、run 边界、
      字体下标、字号、回退链、语言。**字重漏了**——而字重换的是 `FontInstance`（可变字体的
      wght 轴），字形对象与推进宽度都跟着变。于是一段文字"整段加粗"时文本没动、run 边界也
      没动，指纹不变 → 命中上一轮的整形结果 → 画面停在旧字重上，改一下字号才跟着变。
      只改选区一部分时不出这个问题（切分改了 run 边界，指纹变了），所以症状是"有时候"。
      ⇒ 指纹是"缓存的新鲜度判据"，必须覆盖缓存条目的全部输入；斜体与下划线可以不在里面
      （它们不改字形与推进，`stampRunMarks` 摆字形时按 run 现取）。
      判据：`format.spec` 的"整段改字重/斜体：增量排版必须跟全量一致"——用
      `diag.auditLayout().diff` 与 `diag.auditCompile().diff` 都为 0 来钉。这一条也是
      "改了但画面没变"这类问题的通用探针：自审能看见，像素与返回值都看不见。

193. **工具栏的"读—改—写"动作必须排队，取反必须现读**（2026-10-23）。
      两个独立毛病，症状都是"有时候点了没反应"：
      - 用回显缓存（`mark.bold`）取反：缓存滞后于文档，连点两下算出来的是同一个目标值，
        第二次被幂等判定吃掉 → "连点两下只走一档"。
      - 不排队：第二次 `formatAt()` 在第一次 `format()` 落地之前发出，读到的是写之前的值,
        结果同上。
      ⇒ 动作排进一条 promise 链（`enqueue`），取反/步进一律 `await formatAt()` 现读；
      回显的刷新用"读在进行时只记一笔，落地后再补一轮"（并发读会互相覆盖）。
      UI 侧的判据在 `smoke.spec`（连点两下走两档、每个按钮点一遍都有反应）。

194. **"把选区换成 X"与"作用于这一段"是两种语义，不能共用一条入口**（2026-10-23）。
      引擎的 `indent()` / `outdent()` 是 Tab 语义：有选区就把选区换成缩进（`edit_test` 的
      ★ 判据钉着），而工具栏的"增加缩进"是段落语义。直接复用会让"点一下缩进"把用户选中的
      几个字删掉。⇒ 门面 `setIndent` 先把光标收到**选区左端**再调命令（收到右端会把空格插进
      句子中间）。要改 Tab 语义得先想清楚键盘那一侧怎么变，别只改命令层。

195. **页内容指纹必须覆盖"画出来不一样"的一切 —— 斜体、下划线、字号、字重**（2026-10-23）。
      页位图的新鲜度是 `pb.fp == page_fp_new_[page]`，而 `fp` 由 `computePageFingerprints`
      按**字形**混出来：glyph_id / x / y / rotate / cluster / 颜色。斜体是合成倾斜（不改
      advance）、下划线是另外画一条线、单字行的字号与字重都不改 x/y —— 于是"只改画法"的
      那几种格式改了之后指纹一模一样，页位图被判成"还新鲜"，**跳过重画**。症状极具迷惑性：
      命令返回 true、`formatAt()` 读回也对、`auditLayout()` 的 diff 还是 0（它比的是排版，
      不比像素），只有肉眼和截图能看见"画面停在旧帧"；动一下字号（x 变了）才一起显形。
      ⇒ 绘制层的输入必须进指纹：`italic`、`underline`、`size_pt`、`weight`（`PlacedGlyph`
      新增 `weight`，由 `stampRunMarks` 填）。判据 `format.spec` 的"画面重画"——**比截图
      摘要**，这是唯一能看见这件事的判据；用"一行一个字"的文档，避免位置变化顺带把指纹改了。
      同理：`shapingFingerprint` 漏字重是"排版没跟上"（TRAPS 192），两条是不同链路，
      修好一条不代表另一条对。

196. **"在段落末尾敲字"的落点其实在段落标记上，不是容器的一个槽**（2026-10-23）。
      `FlowIndex::measure` 给非文本、非容器的节点各记 **1 个流位置**（段落标记就是这一类），
      `posAt` 对它们走 `leaf_head`（`flow == cfirst && cfirst < cend`）直接下沉。于是
      "甲乙丙丁"末尾（flow 4）解析出的是 `Pos{标记节点, 0}`，而 `marksAtFlow` 原来只处理
      "文本节点"与"容器的槽"两种形状 —— 这两种都不匹配，返回**空标记**，新敲的字就成了
      普通字（表现：粗体后面敲出不粗的字）。⇒ `marksAtFlow` 统一成"取同层最近的文本兄弟"：
      节点是文本就用它；否则定位到（父容器, 下标），**先往左找、没有再往右找**（段落开头
      左边没有字，Word 也是沿用右边那一段）。判据 `format.spec` 的"敲字继承"。

197. **工具栏按钮会抢走焦点，之后键盘全废**（2026-10-23）。
      `<button>` 的默认按下行为把 `activeElement` 挪到按钮上，而键盘输入只认聚焦的元素、
      输入层挂在承接用的 textarea 上。于是"点一下加粗"之后敲字、Ctrl+Z 全落进按钮里 ——
      用户说的是"点了没反应"。⇒ 按钮 `mousedown` 里 `preventDefault()`（只拦焦点与选择，
      click 照常）；`<select>` 必须拿到焦点才能展开，所以选完由外壳统一 `editor.focus()`
      （`chrome.ts` 在功能区上挂 click / change 各一次）。判据 `smoke.spec` 的"点完按钮：
      键盘还在编辑器里"——它比的是 `document.activeElement` 与"敲一个字进没进文档"。

198. **重建 wasm 与跑浏览器判据不许并发**（2026-10-23）。
      `web/heditor.js` / `heditor.wasm` 是判据的运行时输入：一轮 `cmake --build --preset wasm`
      会在几秒内先后替换胶水与二进制，正在跑的用例于是拿到"半新半旧"的组合，报的是
      `WebAssembly.instantiate(): Import #0 "env": module is not an object or function` 或
      `BufferSource argument is empty` —— 10 条用例一起红，看起来像代码坏了。实测白跑一轮
      2 分钟。⇒ 构建完再起判据（或先起判据、别动产物）；同一轮里也别让 `npm test` 与
      `cmake --build` 并行。

199. **公开成员清单被门面捕获进闭包，热更替不掉 —— 页面会继续用旧白名单**（2026-10-23）。
      给公开面加一个方法要动三处：`types.ts` 的接口、`editor.ts` 的实现、以及
      `public_members.gen.ts`（脚本生成）。第三份被 `guard.ts` 在**建实例那一刻**捕获，
      而 dev 服务器热更只会换模块、不会重建已经挂在 `window.__demo` 上的门面 —— 于是页面
      里还是 41 项的白名单，调新方法报"不是公开 API"，读起来像代码写错了。
      ⇒ 示例页在 HMR 里看着 `public_members.gen` / `guard.ts` / `types.ts` / `engine/api.ts`
      的更新就整页重载（`app/main.ts` 末尾）。加成员之后先刷新页面再判断"到底通没通"。

200. **"接着写"取错了邻居：边界位置 `posAt` 归给右边那个叶子**（2026-10-23）。
      两个文本节点之间的流位置，`posAt` 走 `leaf_head` 下沉到**右边**那个文本节点（"容器的
      第 0 槽位与第一个孩子的第一个位置是同一个，规范表示取最内层"）。`marksAtFlow` 原来
      见文本节点就直接采用 ⇒ 敲字沿用**右边**的格式。表现很怪但很稳定：在一段加粗字**前面**
      敲出来的是粗的，紧跟它**后面**敲反倒变普通 —— 正好与"接着已有的字往下写"相反。
      ⇒ 文本节点只有 `offset > 0` 才算"在里面"（左边就是这个节点的字）；`offset == 0` 与
      容器槽位、段落标记、原子一起走"同层最近文本兄弟，先左后右"。另一条别混：**打字盖住
      选区**取选区第一个字（`marksAtSelectionStart`），混用会让"选中加粗的一段重打"掉格式。
      判据 `edit_test` [63]（左右两边界互为反向 + 连打第二下不漂 + 段尾对照）、
      `format.spec`「落点继承」。

201. **下拉框"一点就收回去"：外壳把焦点抢回编辑器**（2026-10-23）。
      为了让"点完按钮还能接着敲字"，外壳（`app/ui/chrome.ts`）在功能区上挂了 `click` →
      `editor.focus()`。原生 `<select>` 靠焦点展开，于是点开的那一下焦点被抢走、弹层立刻收起，
      一个选项都选不了（用户说的是"下拉框一点就收回去，用不了"）。⇒ click 收尾必须跳过
      `select, input, textarea, label`（下拉框外面还包着一层 label）；选完（`change`）再交回。
      同一轮的另一半是**回显**：工具栏的字体 / 字号读的是 `formatAt({effective:true})` ——
      默认口径只报"显式写了什么"，正文一个字没改过时字段全缺席，控件显示空白，看着同样像
      "没有回显"（字即使没改过也有字体有字号）。判据 `demo.spec`「下拉框拿得住焦点，字体与
      字号有回显」（`activeElement` 仍是那个 select + 两个控件都填上了值与 `effective` 一致）。

202. **自绘图形的 AA 覆盖率随画布高度变 —— 连页接缝逐字节判据当场红**（2026-10-23）。
      编辑标记（换行符）的箭头是自绘三角形：顶点落在半像素上、开着抗锯齿时，同一枚图形画在
      "整带画布"（高 6000 磅）与"分带画布"（高 150 磅）上，边缘覆盖率的档位不同 ——
      接缝处差出 250/251 这种一个色阶的像素，`edit_test` [59] 报"差 2 行"。字形不受影响
      （走 Skia 的字体渲染路径），几何图元会。⇒ 画在页位图里的自绘图形必须**顶点对齐整数
      像素 + 关抗锯齿**，平移量（连页补画的 -带高）在缩放与取整之后加：
      `bar_lo = round(cross*zoom - k) + dy_px`，写成 `round((cross + dy/zoom)*zoom)` 会引入
      末位误差，同样红。判据 [59] 与 [64]。

203. **给滚动内容加外边距，就得把所有 scrollTop 换算一起扣掉它**（2026-10-23）。
      页容器加了上外边距（居中 + 呼吸空间）之后，`scrollTop = 0` 时页顶还没到视口顶 ——
      而宿主有四处在拿 `scrollTop` 当"文档纵坐标"：healWindow 的可见页两端、onScroll、
      nudgeViewport、resize。少扣一处，窗口就整体落后一截，**边缘那一页判成"不在窗口里"**
      （表现：滚到底之后最后那一页没有画布）。⇒ 收敛成 `docScrollTop() =
      scrollTop - pages.offsetTop`，四处共用。另一条：**只加上边距，别加下边距** ——
      下边距会在文档末尾造出一段可滚空白，可见页会算到文档之外（判据报"不存在的页号"）。
      判据 `clipboard.spec`「粘贴撑长之后：可见页都有画布」。

204. **自定义 MIME 穿不过浏览器剪贴板 —— "复制粘贴丢样式"看起来像片段的错**（2026-10-23）。
      引擎侧片段（fragment JSON）一直带着字符标记（`collect` 的截断分支 / `specOf` /
      `materialize` 三处都搬），全选复制再粘回是逐字段等价的（判据 `edit_test` [65]）。
      丢样式发生在宿主：paste 事件的 `getData` 只给标准类型，`navigator.clipboard.read`
      没授权时整条拒绝 ⇒ 退化到 `text/plain`，走 `pastePlainText` ⇒ 样式没了；而纯文本以
      换行结尾会多拆出一段空段 ⇒ 同时出现"高度高了一点"。⇒ 宿主留一份最近写出去的载荷，
      纯文本相等就用它（`recallPayload`），程序化粘贴读不到剪贴板就用 `latestPayload()`；
      写空片段要把缓存一起清。判据 `clipboard.spec`「编辑器内复制粘贴」。

205. **"改了没用"先怀疑热更：闭包在实例化那一刻就定死了**（2026-10-23）。
      宿主的 paste/copy 处理器、剪贴板模块里的 `lastPayload`、拖选控制器、白名单、协议表，
      全都在 `createEditor` 那一刻被捕获。Vite HMR 只换模块，换不掉已经挂在页面上的实例 ——
      于是改了逻辑、页面照旧跑旧函数，看起来就是"改了没用"（这一轮复制粘贴就是这么被误判成
      "没修好"的；在全新页面上真键盘复现一切正常）。⇒ 示例页的 HMR 规则是"`web/src/**`
      或 `web/app/**` 有任何更新就整页重载"（早先只覆盖白名单那几个文件，见 TRAPS 199）。
      验证任何"改完不生效"的行为前，先硬刷一次（Ctrl+Shift+R），或直接开新页。

206. **浏览器里"引擎改了没反应"：先确认页面加载的是哪一份产物，别急着改逻辑**（2026-10-23）。
      这一轮空段选区与格式求交两条，`edit_test` [66] 六条判据全绿（3 条矩形、混合选区不报
      bold），但同一个操作在浏览器里仍然只有 1 条矩形、仍然报 bold:true —— 说明页面跑的是
      旧引擎。默认素材地址是 `build/wasm/web/heditor.js`（`web/src/editor.ts` 的缺省值），
      由 vite 从仓库根的 build 目录提供；`bust` 默认是空串，浏览器与 Worker 可能拿缓存。
      试过在开发期给 `bust` 拍时间戳：胶水与 **wasm** 都会带戳，而 vite 对带查询串的
      `.wasm` 会回落到 index.html（`CompileError: expected magic word, found <!DO`），所以
      这条路要连 `api.ts` 里 wasm 的取址一起改（那里已经有一句"只给胶水加戳、不给 wasm 加，
      就成新胶水配旧 wasm"的注释），不能只在 editor.ts 里加。**没修完之前，判据以 native 为准，
      浏览器那一侧看到的现象不可信。**

207. **"引擎改了没反应"不是缓存 —— 别在缓存上再花时间**（2026-10-23 续）。
      给开发服务器的 `/build` 与 `/assets` 响应加了 `Cache-Control: no-store` 之后，浏览器里
      空段选区仍然只有 1 条矩形、混合选区仍然报 `bold:true`，与 native [66] 的 6 条全绿
      完全相反。⇒ 缓存不是原因。下一步必须分别量**两条不同的路**：
      `e.selection().rects` 走的是 `selectionReport`（`selectionRectsVisible`，按窗口页筛），
      `e.formatAt({effective:true})` 走的是门面的合并逻辑（可能压掉了引擎的"缺席"）。
      先直接用引擎读（`diag` 的 `charFormatAt` / `selectionRects`）对比门面读，再决定改哪一层。
      旁路结论保留：生产环境的 bust 要用 **wasm 内容哈希**（`scripts/write_wasm_hash.cmake`
      已写好，CMake 里还没接上），时间戳会让"没改动的重建"也换 URL。

208. **页指纹只认字形 ⇒ 没有字形的排版变化不重光栅**（2026-10-23）。
      文档末尾连按回车建空段：只多出几条行盒，一个字形都没多。`computePageFingerprints`
      只混字形，页被判成新鲜，一次都不重光栅 —— 新那几枚段落标记永远不出现，而
      `auditLayout` 仍然是 0、命令也照常返回成功。改一次文字样式（字形变了）它们全冒出来，
      于是看起来像"画布没更新"。⇒ 行结构也是画出来的东西：把 `computeLineFingerprints`
      的产物按页混进页指纹（只混重算范围内的页；范围外的页要留上一轮的指纹，再混一次
      会让它永远不新鲜）。行指纹本身补 `size_pt` 与 `bracket_axis_pt` —— 标记的笔画宽度
      与基线都由它们定，而行盒的长宽可能一点不动。判据 `edit_test` [67]。

209. **段落标记在流里占一位，却不属于任何一块的内容 ⇒ 末段那枚永远选不到**（2026-10-23）。
      `rev::project` 的 flush 里 `extent.span` 只数内容（文本 / 原子 / 边界），段落标记夹在
      两块之间；`selectAll` 与 `setSelection` 的钳位上界都是"最后一块的段内末端"，而那正好
      是标记位本身 ⇒ 末段的标记不在任何选区里。空段（span = 0）更彻底：上界就是块起点。
      字处理软件在这一点上分方向：正向扩选到文档末算选中，从末尾往回拖不算。
      ⇒ `selectionRectsIn` 按"正向（anchor < focus）且焦点在文档末"给末行补一条：空段走
      原来那条窄条分支，有字的末段把那枚的宽度并进本行矩形（另推一条会与它首尾相接甚至
      重叠，半透明选区叠两次就是一道深色缝）。流的口径一位都没有动。判据 `edit_test` [67]。

210. **跨页切片只挪行盒、不挪字形 ⇒ 字画在上一页，新页上一个字都没有**（2026-10-24）。
      `sliceRowByPage` 把切到下一页的行盒改 `page` 并平移 `y`，字形那一段只加了 `dy`、
      没改 `g.page`。字形是按页号区间画的（`glyphRangeOnPage`），所以那一行整个留在旧页上，
      按平移后的 y 叠在别的字上；新页上空着。三份自审全是 0：`auditLayout` 比的是增量与全量
      （两边同错）、`auditPage` 比的是位图与从零光栅（光栅读的就是错页号）、
      `auditGlyphPages` 比的是 `glyphRangeOnPage` 与 `g.page`（同一份错）。
      ⇒ 判据必须自己交叉：**每个字形页号 == 它那一行的页号**（`edit_test` [72] 与
      `table.spec` 的"折行之后的字必须画出来"按像素数墨）。修法见 layout.cpp 的 Shift。
      表现就是用户嘴里的"单元格文字换行后还是没渲染出来"与"新增的换行符不显示"。

211. **连页下表格行的进给是块轴绝对位置，不是片段的页内下沿**（2026-10-24）。
      `sliceRowByBand` 给的 `box_bottom` 是页内坐标；`closeRow` 用它写回 `f.row_top` /
      `cursor_y`，于是连页下第二行起整张表塌回第一条带的顶上（`openCell` 又把 cursor_y
      设成 row_top + pad）。表象是"表格飞到页面外面去了"。单行的表看不出来 —— [70] 的
      连页用例只有一行。⇒ 分页下进给用 `pieces.back().box_bottom`，连页下用 `top + row_h`。

212. **续排片段上的格可能一条行盒都没有 ⇒ 命中与整格反白都不能按行盒推**（2026-10-24）。
      一行跨页切开时，内容已经在上一页结束的格在这一页没有行盒。按行盒找最近的，
      会把点空格子的那一下判给同一行里唯一还有行盒的那一格（"点空格子光标跳进有字的格"）；
      整格反白按行盒铺也只在有行盒的那一页画出高亮。⇒ 命中先按"表 + 行片段 + 列边界"
      定出格（`PlacedTable::cellAt`），再只在这一格的块区间里挑行；整格反白按
      `cellBoxOnPage` 逐页铺。反向判据要有：小表里点格子的空白处仍落在这一格。

213. **连页接缝的溢出判据按"基线越过带底"筛 ⇒ 下半截越过接缝的字永远补不画**（2026-10-24）。
      `emitGlyphs` 的 spill 那一趟只取 `pg.y_pt > slab - 1`，而 `y_pt` 是基线：
      基线在带底之上、字身（descent 与 AA）越过去的那一截，本带被位图裁掉、下一带又不画。
      一行偏一像素，`edit_test` [59] 的分带/整带逐字节判据会红（差 1 行、首行正好是带边界）。
      ⇒ 判据改成"墨迹可能触到带底"（按字身外扩）。默认段距从 10 磅改 6 磅之后行位置整体上移，
      这个潜伏的缺陷才露出来。

214. **页指纹不含表格片段几何 ⇒ 切过页的边框留在旧位置**（2026-10-24）。
      页指纹混的是字形与行指纹，而格线、跨页切口那两条边是"行片段的上下沿"画出来的。
      一条行从"在页底被切开"变回"整行落在这页"（或反过来）时，片段的下沿从页底挪到行底，
      这一页可能一个字形、一条行盒都不变 ⇒ 页被判成新鲜，边框停在旧位置；而这类变化
      通常伴随某一行也在动，于是 `computeBand` 给出一条行带，边框又落在带外。
      ⇒ `computePageFingerprints` 混进每页的 `tablePieceDigest`（表位置 / 列边界 /
      各片段的上下沿与切口标记），`computeBand` 发现摘要变了就返回 0（整页重画）。
      判据：`edit_test` [72] 的"跨页之后敲字：每一页的位图都与从零光栅相同"。

215. **"行数组按页单调 / 数组相邻就是版面相邻"这两条在表格里都不成立**（2026-10-24）。
      `lines` / `glyphs` 按流顺序追加；一条高格切到第二页时，它的续排行先追加，同一行其余
      各格的行还在上一页 ⇒ 页号不单调。同一个格子里的第 2 行之后，数组紧跟着的是另一格的
      第 1 行（在它上面）⇒ 数组相邻 ≠ 版面相邻。
      三处消费方都按这两条假设写的，于是同一批症状：
        · `glyphRangeOnPage` / `linesOnPage` 二分取"这一页的区间" ⇒ 漏掉后半截列
          （字形不画 = "文字没渲染"，行漏 = 标记不画）；
        · 页指纹只混二分区间里的字形 ⇒ 漏掉的字形让页面被判成"新鲜"，屏幕停在旧像素；
        · `lineBand` 用数组相邻项推上下边界 ⇒ 带被压成零高，那一行永不重画，
          段落标记一帧一帧往上叠（用户嘴里的"一堆换行符"）；
        · 行带两端取"变化行里下标最小/最大"的两条 ⇒ 表格里最大下标不一定最靠下，
          带只盖住页首（页下半截的字与标记全部留在旧像素上）。
      修法：`LayoutResult::page_lines` / `page_glyphs`（页 → 下标表，排版收尾与"拼接"路径
      重建；先数后填、按页 reserve）；`pageLineBands(page, ...)` 按块轴排序分组、相邻组取中线；
      行带两端取**所有**变化行（含新旧两版）的并集。判据：`edit_test` [73]
      （页索引覆盖 + 每条空行都有标记的墨 + 格内逐字输入每步页位图 == 从零光栅），
      `table.spec` 的"空格的段落标记：每一页上每一格都要画出来"。

216. **页索引每敲一个字建两遍，把增量排版拖到全量的 57%**（2026-10-24）。
      第一版用 `std::vector<std::vector<int>>` 边推边扩容，且在排版函数与 `relayout` 收尾
      各建一次；2000 段 / 4.5 万字形下 wasm 实测增量排版 59.2 ms（全量 227 ms），
      编辑面那条"增量 < 全量 20%"的判据当场红。
      修法：先数一遍、按页 `reserve` 再填；只在"拼接"那一路（`reuse != None`）补建
      （整篇与续排都走排版函数，那里已经建过）。同一测量点降到 7.0 ms（2.9%）。
      ⇒ 任何"每次排版都重建"的派生结构，都要先量它在 2000 段文档上的单价。

217. **`| Select-Object -First N` 会把脚本掐死在中途，副作用只做一半**（2026-10-25）。
      验证 `skia_fetch.ps1` 的解包路径时写成 `& script.ps1 2>&1 | Select-Object -First 20`：
      输出到第 20 个对象时管道提前收工并向上抛 `PipelineStopped`，脚本在
      `Move-Item`（树已就位）与 `WriteAllText`（写戳记）之间被终止 —— 结果是一棵 308 MB
      的完整源码树**没有戳记**、日志还少几行。当时差点判成"戳记根本没写"的脚本 bug，
      换成 `*> log` 后一次就复现不出来。
      ★ 纪律：核对**副作用**（文件、目录、产物）只用 `*> file.log` 再 `Get-Content`，
      不许在管道上挂 `Select-Object -First` / `head` 之类的提前收工装置；
      `2>&1 |` 尤其危险（它把错误记录也接进管道，更容易先到限额）。

218. **PS 7 上全绿的脚本，用户用 `powershell`（5.1）跑会炸**（2026-10-25）。
      `build_skia_native.ps1` 原先把 gn 参数拼成 `"--args=target_os="win" ..."` 递给 gn：
      本机的 PowerShell 工具是 7.6（`$PSNativeCommandArgumentPassing = 'Windows'`），内嵌
      引号会被正确转义，gn 正常；用户那边 `powershell -File` 是 5.1，**不转义内嵌引号**，
      gn 收到 `target_os=win` / `extra_cflags=[/MD]`，`ERROR at the command-line "--args":
      Invalid token` 直接退出 —— 两台机器同一份脚本，一边过一边不过。
      修法：参数写成 `<out>/args.gn`、`gn gen <out>` 不带 `--args`（wasm 那份一直这么写）。
      ★ 纪律：凡是**要交给用户用 `powershell -File` 跑**的入口，自测必须在 5.1 下再跑一遍
      （`powershell -ExecutionPolicy Bypass -File ...`）；"我这台 7 上过了"不算数。
      ★ 同族：第 19 条（码页）、第 43 条（MSVC 环境）—— 坑都在"命令/环境怎么递到子进程"。

219. **脚本自己是 CRLF 时，多行 here-string 比 tar 解出来的 LF 文件恒不匹配**（2026-10-25）。
      `build_skia_wasm.ps1` 的 `Patch-File` 用 here-string 里的整段原文 `Contains` 目标文件：
      本仓库的 `.ps1` 是 LF，用户那台检出成 CRLF → `$old` 每行带 `\r`、目标来自 tar 恒为
      `\n`，于是两个**多行**补丁全落空（单行那条没事），报"补丁点找不到（工具链改用
      emcc.exe）—— 上游可能改了结构"，把人往上游引；实测同一份函数 CRLF 版必失败、LF 版通过。
      修法：`ReadAllText` 后先 `-replace "\r\n","\n"`，`$old`/`$new` 同样归一，写回一律 LF。
      判据：真树两个 gn 文件换回原版 + 整份脚本的 CRLF 副本 → 三个补丁全打上，产出与旧成品
      **逐字节一致**（`Get-FileHash`），ninja `no work to do`。
      ⇒ 凡"拿脚本里的字面文本去匹配外部文件"的地方，匹配前先归一行尾。

220. **页间落点夹到页框而不是内容区，跨页表格一拖就整行反白**（2026-10-25）。
      表格跨页切开时，页底最靠下的行盒全在高的那一列上。指针落进页底边距或页间空隙，
      `hitTestPt` 的 clamp 把纵向夹到**页高**，那一点不在任何行片段里 —— 退回"最近的一行"
      就永远取到高的那一列。从别的列往下拖，`syncCellSelection` 的矩形包络横跨整行，
      用户看到的是"一到两页之间，整行都被选中"。
      修法：clamp 夹到**内容区**（margin..页高-margin，仅分页模式）；夹进去之后格框命中
      恢复正常，列由指针的横坐标定。
      判据：`edit_test` [74]（第三列下拖两页之间：落点仍在该列、没有跨列矩形；反向：
      第一列上的点落回第一列）。
      ⇒ 凡是"夹到最近的有效位置"，先问一句最近的是按什么几何算的 —— 页框不是内容框。

221. **给画布改 CSS 高度会把位图压扁，不是裁掉**（2026-10-25）。
      连页末尾要按内容裁掉最后一条条带的多余白纸，直觉做法是把那张 canvas 的 CSS 高度
      改成"还差多少"。canvas 是替换元素：CSS 尺寸一变，整张位图被缩放，整页字变扁。
      正解：画布 CSS 尺寸恒为整页，由页容器的 `overflow: hidden` + 容器高度（总高）裁；
      容器高度必须同时改小，否则绝对定位的画布照样把滚动区撑大（可滚区与容器高度对不上，
      症状是"末尾还能滚出空白"）。
      判据：`demo.spec` 的"连页末尾：滚动高度跟着内容走，至少留一页"——可滚区等于容器高度、
      最后一页画布仍伸到容器外。

222. **"没有控件就让表单退回可编辑"是把策略关掉，不是体贴**（2026-10-25）。
      原先有个 `formDegraded()` 安全阀：表单模式下"一个可编辑控件都没有"就整篇按文档模式
      放行，理由是"用户会以为坏了"。它在真机上换来的却是反的：一份还没配字段的表单
      被点开就能随便改，用户看到的是"表单模式根本不起作用"；而文档模式与表单模式的
      唯一区别就是这条策略，退化了就等于没有表单模式。
      ⇒ 三档模式的差别必须只有一处（落点/编辑能力/隐藏控件），别为了"手感"加一整档旁的
      分支；要更宽松就换模式，不要偷偷换策略。

223. **括号那四条"进出字段"的删除规则是文档模式的，套到填表上就是事故**（2026-10-25）。
      `bracketBackspace` 的规则是"光标在闭括号右面就进字段删左边那一项、空控件就删控件"。
      设计态用它很顺（作者要能删空字段、能一层层进出），填表时它做的是：删到字段空了
      再退一格 → 控件被删掉 / 光标被带到 `[` 之前。用户的原话是"删着删着跑到括号外面了"。
      ⇒ 删除的边界按模式分：表单模式 `eraseInControl`（只删光标所在控件的内容、不删控件、
      不带出括号），文档模式才走括号四条规则。

224. **"两端都可编辑"不等于"删除区间合法"**（2026-10-25）。
      两个字段紧挨着时 `][` 共享同一个偏移：光标在 c 的内容起点按退格，删的是 c 前一个
      字（在 b 里）——两端都可编辑、`canEditRange` 放行，于是从 b 里偷了一个字。
      判据要锚在"光标所在控件的内容区间"上（`eraseInsideCaretControl`），而不是只看两端
      的编辑能力；原子删除同样要过这一道。
      ⇒ 凡是"区间判定"落到共享边界上，都要问一句"区间与锚点在同一个容器里吗"。

225. **选区与光标混成一件，光标会出现在打不进字的地方**（2026-10-25）。
      文档曾明确写"落点不受限"，得到的是：表单模式里光标停在正文、只读模式里插着一条
      竖线，用户以为能改，敲下去一个字没有。正确切法是把两件事分开 —— 选区（高亮）
      自由，插入点只存在于可打字的地方：表单模式限于可编辑控件内容，只读模式一个都不画。
      实现是"画不画"（`caretInsertable`）+ "走到哪"（`confineCaret` 夹回所在字段），
      而不是给光标造第二份状态。

226. **裁剪标记默认关，等于把"页边距设错了"藏起来**（2026-10-25）。
      它是页边距内沿唯一的直接读数；默认关掉之后，用户只能靠"正文看起来离页边偏了"猜。
      臂长还必须固定物理尺寸（18 磅 = 1/4 英寸，印刷裁切线的惯例），不跟字号、页边距、
      缩放走 —— 跟着变的话同一份文档在不同页上就凑不成一套标记。

227. **页边距只有一个数是模型欠账，四边迟早要分开**（2026-10-25）。
      `PageMetrics::margin_pt` 让"上 2 厘米、下 2.5 厘米"这种最常见的版式表达不出来，
      补页面设置时才发现 60 多处使用点都假定四边相等。四边分开（`PageMargins`）之后，
      每一处都要问一句"这里用的是哪一边"：正文起点用 top/left、内容高度用 top+bottom、
      页底让位用 bottom、裁剪标记四边各取各的。

228. **`blocks_` 不是块流真源，读它判"文档有没有内容"会整条判错**（2026-10-25）。
      `blocks()` 是 `filter_active_ ? blocks_ : blocks_full_` —— 括号常显时 `syncInlineObjects`
      会 **把 blocks_ 清空**、让排版直接吃 blocks_full_。给"光标画不画"加判据时写了
      `!blocks_.empty()`，于是只要走过一次括号筛选（插入控件后重编译、切只读），文档模式
      也被判成"不可插入"：位置还在跳、屏幕上一根竖线都没有，用户的原话是"点哪儿都没反应"。
      ⇒ 读块流一律走 `blocks()`；判"有没有内容"干脆不参数化块流（空文档的 caretRectPx
      本来就是 0 宽）。同族：第 3 条（派生量只留一份）。

229. **内容区间从流索引取，别用"文字区间 + 括号排布"反推**（2026-10-25）。
      控件在模型里不是容器节点，只是一段文字区间 + 流里的两枚括号占位。于是"它的内容
      区间在哪"这件事，引擎侧曾经自己反推：`range.start/end` 加 `sideFromHint` 算两头。
      同一个偏移上压着六枚括号时（三枚空控件套起来 `[[[]]]`），反推要先知道"这是第几枚"，
      而那份知识 `FlowIndex::intervalOf` 早就算好了 —— 两套口径必然分叉，症状是光标进得去
      最内层、往右一格走不动（三层内容区间全退化成一点）。
      ⇒ 区间一律查 `intervalOf(node_id)`（含两枚括号，宽 2 = 空控件），内容区间退掉两头。
      为补反推加的那个 `sideAtClose` 随之删掉 —— 补丁消失才是收敛的证据。
      ⇒ 顺带：判"这一格归谁"取最内层（起点最大、同起点取跨度短），不能按遍历顺序取第一个
      命中的，否则外层可编辑会替内层只读作证。

230. **"某位置的归属"曾经有三份实现，收敛时先分清两种输入**（2026-10-25）。
      原来 `CaretResolver::hintFromRel`（段内对象表）、`ControlSet::innermostAt`（文字区间树）、
      `Engine::innermostControlAt`（流区间）各算一遍，三者一致时看不出来，一旦分家就是
      "光标画在 A 里、宿主报在 B 里、编辑按 C 判"。
      现在收成两处，因为**输入不同、不能互相替代**：
      - 文字位置（段号 + 偏移）→ `ControlSet::innermostAt`（区间树）。`defaultSideAt` 与
        `controlAtPt` 用它：同一偏移上压着好几个插入点时，靠内那几格可能已属于下一个字段，
        只有区间树知道"这个偏移归谁"。
      - 流位置（已含侧别）→ `control_spans.h` 的 `innermostControlAtFlow`。落点判据、
        编辑删除边界、命中归属、宿主报的归属都走它。
      教训：**收敛不是在两种判据里挑一个，而是让每个问题只有一处实现**。中途试过把
      `defaultSideAt` 也改成按流位置判，50 条判据立刻红（两个字段紧挨着时落点跳过边界），
      回滚才绿 —— 那条"文字位置 + 侧别 = 流位置"的链是有方向的。

231. **改了 `web/src/engine/api.ts` 必须 `npm run build:worker`，dev 模式也一样**（2026-10-26）。
      引擎的读写映射表（`api.ts` 里的 handler 表，含 `tableState` 这类 JSON → 类型化对象的
      逐字段折返）不是在页面里跑的，它在 **Worker 壳**（`web/dist/heditor_worker.js`，构建产物）里。
      漏了这一步的症状极具误导性：wasm 已经是新的、命令也生效了（`tableOp('removeTable')` 返回
      true），可读回来的对象里就是没有新字段 —— 看着像"引擎没写这个键"。
      ⇒ 判据红在这种地方时，先 `grep 新字段名 web/dist/heditor_worker.js`：没命中就是壳旧了。
      同族：wasm 改了要重链（`cmake --workflow --preset wasm`），壳改了要重打包，两件事分开算。

232. **行指纹也要覆盖"画法变了但坐标没动"的那几样 —— 裁切、行高、行槽顶**（2026-10-27）。
      页位图新鲜度是 `pb.fp == page_fp_new_[page]`，而页指纹里的行那一路由
      `computeLineFingerprints` 混出来：行盒上下边、行内起止、字号、括号基线、簇表、字形。
      漏了 `clip_text`（画不画都要裁到行槽）、`advance_pt`（裁多高）、`lead_top_pt`（从哪起裁）。
      症状：**只有一行**的段落把「多倍行距」改成「固定值 8 磅」时，基线不动、字形坐标一个
      字节都没变，唯一的差别是"字要被裁到 8 磅"，于是行指纹、页指纹全都没变 —— 页被判成
      还新鲜，一次都不重光栅。命令返回 true、`paragraphFormatAt()` 读回也对、`auditLayout()`
      还是 0（它比排版不比像素），只有截图/读帧能看见画面停在旧帧上；换一台全新引擎排同一份
      文档又是对的（全新光栅不走缓存）。反过来（固定值→多倍）也一样，屏幕上留着裁过的墨。
      ⇒ 三样一起混进行指纹（页指纹混的是行指纹，自然跟着走）。判据：`edit_test` [93] 在同一台
      引擎上 auto→exact 8→auto 量帧上的墨深（14.5 → 7.5 → 14.5），再来一次 exact 4（→0），
      后两条只有"行高也进了指纹"才过得去；`format.spec` 的「固定值与最小值」用同一把尺子在
      浏览器上量一遍（引擎 → 脏矩形 → 画布 整条链）。教训与 195 同族：**指纹必须覆盖绘制层
      的      全部输入**，加任何"画的时候才用到"的行盒字段（裁剪、行槽、格子框）都要回头看这一处。

233. **覆盖层的配色也是"画法输入"，必须进 `overlayRoot`**（2026-10-30）。
      脏区由"新旧覆盖场景的差集"给出，而差集只比 layer + 矩形（`overlayHas`）。改光标色、
      选区色、图片手柄色时矩形一个都没动，两个循环都不标脏 ⇒ 脏区为空 ⇒ 宿主不重贴，
      画布停在旧色上，直到那片区域因别的原因（光标闪烁、选区变化）再次被判脏。
      命令返回 true，`config().caretStyle` 读回也是新值，`repaintedPixels` 是 0。
      ⇒ `OverlayScene` 带 `style`（三色指纹）并混进 `overlayRoot`；present 里
      `prev.style != now.style` 就把新旧两边所有矩形全标脏。
      读引擎导出的帧永远看不见它（帧是现场拼的，已经是新色）；判据读页画布才暴露。
      同族 232：指纹与差集必须覆盖绘制层的全部输入，颜色与裁剪、行槽同一档。

234. **行带的首组上界是页顶、末组下界是页底 ⇒ 单行页等于整页重画**（2026-10-30）。
      `lineBandsForPage` 按"组"切页：相邻组取中线（为了不啃相邻行的抗锯齿边），
      首组顶边写 0、末组底边写 page_h。整篇只有一行时，那一组既是首组也是末组，
      带就是整页 —— 打一个字重贴 89 万像素。
      ⇒ 首组/末组只比自己的墨迹多留一档余量（`kLineBandPadPt`，6 磅），页边距那段
      空白不算进任何行。新旧两拍的带由 `diffPageScene` 取并集，"行变高、旧墨在上方"
      仍被覆盖，所以不需要靠"拉到页顶"来保证擦干净。
      判据：`edit_test` [3] 与 `edit-core` [2] 都从"整页"改成"只覆盖那一行"；
      `render.spec` 的那条从 `test.fail()` 改正。

235. **滚动判据看"页 / 行别"⇒ 改一次格式，视口跳到文末**（2026-10-30）。
      `afterEdit` 判"光标挪没挪"用的是五项（段、偏移、侧别、行别、页）。后两项是排版
      给的：全选之后改行距，文档变长，同一个位置从第 6 页跑到第 8 页、折行处行别也翻，
      于是判成"挪了"，`scrollCaretIntoView` 把视口拽到文末。切样例时看到的就是
      "全选 → 跳到末页 → 回到第一页"。
      另一半是基线：选区类命令（select / selectAll / clearSelection）走 `caretOp`，
      不更新 `lastState`，那次位移留给下一条命令去消费。
      ⇒ 拆成两个函数：`caretsMovedInText`（段、偏移、侧别）管滚动，
      `caretRelocated`（再加行别、页）管 caret 事件与输入法框；`caretOp` 的非 reveal
      分支调 `dom.noteCaret(stats)` 只记基线（不能塞进 `finish()`：Worker 每一拍都调它，
      会把基线推到下一条命令之前，连续粘贴就不滚了）。
      判据：`view.spec`「全选之后改段落格式，视口不跳到文末」（反向一半：setCaret 到文首
      仍然会滚）。同族 232/233：**派生量（页、行别、相位）不能进"要不要动"的判据**。
