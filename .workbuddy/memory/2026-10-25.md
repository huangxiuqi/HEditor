## Skia 取数收成一条路：`scripts/skia_fetch.ps1`

查下来是三件事叠在一起，不是"忘了写进 toolchain_init"这么简单：

- 取数代码原来长在 `build_skia_wasm.ps1` 里，只有 `-Fetch` 才走到 —— 文件叫 wasm，
  native 侧却要跑去用它，名不副实；
- `build_skia_native.ps1` 发现树与 pin 不符时**直接 throw**，让你去跑那条 `-Fetch`；
- `build_skia_wasm.ps1` 的入口在第 0 步就体检 `Emsdk / Gn / Ninja`，而**取数不需要 emsdk**
  （只要 curl + tar）。于是"native 只要 gn + ninja + 这棵树"被 2 GB 的 emsdk 挡着，真 bug。

改法：

- 新增 `scripts/skia_fetch.ps1`：源码 + 六个外部依赖，**唯一取数入口**，只依赖 curl / tar；
- `build_skia_wasm.ps1` 删掉 `-Fetch` 与整段取数（约 120 行），成树前 `& skia_fetch.ps1`；
  `build_skia_native.ps1` 同样（不是 ok 就先取），不再拒绝构建；
- `toolchain_init.ps1` 加 `-WithSkia`，且排在 emsdk **之前**（native 只需 gn + ninja + 这棵树）；
- 同步 `CMakeLists.txt` 的报错文案、`AGENTS.md`、`docs/依赖与工具链管理.md`（5 节 / 5.1 / 5.2）。
- 顺手修：pin 被打印两遍（两个构建脚本各一遍 + fetch 一遍），只留 fetch 那一处。

判据（都实跑，不是"看着对"）：

- 真树空转：`源码已是这一版（ok），跳过下载` + `外部依赖就位`，exit 0；
- 隔离的全新树（目录里只有 pin 的 tar，没有源码）：解包 → `跳过 1 个符号链接` → 写戳记
  → 六个依赖 → 308 MB；
- 隔离的坏包（4 KB 假 tar）：`build_skia_native.ps1` 被取数的 throw 挡住，**没走到 gn**
  （`out/win-x64` 不存在）—— 顺带证明了 `& child.ps1` 里的 throw 会传到调用方；
- 真树 `build_skia_native.ps1` exit 0（gn gen 106 targets / 18 s、ninja no work、25.5 MiB）；
  `build_skia_wasm.ps1` exit 0（`libskia.wasm.a` 7.7 MB）；
- `cmake --preset native` / `--preset wasm` 配置各 exit 0；`ctest --preset native` 4/4（278 s）。

★ 踩到的坑（已记入 TRAPS 217）：验证脚本副作用时用了 `& script 2>&1 | Select-Object -First N`，
管道提前收工会把脚本**掐死在中途** —— 那次"源码树解出来了、戳记却没写、输出还少几行"就是它，
不是脚本的 bug。核对副作用只看文件系统 + 完整日志（`*> log` 再 `Get-Content`）。

## 续：F: 那台一跑 native 脚本就 `Invalid token`（PS 5.1 吃引号）

用户贴的报错：`gn gen` 时 `ERROR at the command-line "--args":1:685: Invalid token`，
参数串里的引号全没了（`target_os=win`、`extra_cflags=[/MD]`）。

机制（实测复现，不是猜）：`build_skia_native.ps1` 把参数拼成
`"--args=target_os="win" ..."` 传给 gn。本机的 PowerShell 工具是 **7.6**
（`$PSNativeCommandArgumentPassing = 'Windows'`），内嵌引号会被转义、gn 收到的是对的；
用户用 `powershell -File` 跑的是 **5.1**，它不转义内嵌引号 —— 我写了个最小探针在 5.1 下
跑 `gn gen ... '--args=target_os="win" is_debug=false'`，gn 报
`Undefined identifier`（`target_os=win`），复现成立。

修法：参数改写成 `out/win-x64/args.gn`（28 条，带注释），`gn gen $OutDir` 不带 `--args`
—— 与 wasm 那份同一种写法，与 shell 引号规则无关，args 还留在 out/ 里能直接看。

判据（5.1 下实跑）：`powershell -ExecutionPolicy Bypass -File scripts\build_skia_native.ps1`
exit 0（`Done. Made 106 targets` → `ninja: no work to do` → 25.5 MiB，说明 args 与旧的一致，
没有触发重建）；同一次 5.1 复测里 `toolchain_init.ps1 -SkipEmsdk` 与 `build_skia_wasm.ps1`
也都 exit 0。

★ 纪律（TRAPS 218）：凡是交给用户用 `powershell -File` 跑的入口，自测必须在 **5.1** 下再跑
一遍；"我这台 7 上过了"不算数。

## 续二：F: 那台 wasm 脚本报"补丁点找不到（工具链改用 emcc.exe）"

用户贴的：`pwsh -File scripts\build_skia_wasm.ps1` 在 `Patch-File` 上抛"补丁点找不到"，
提示"上游可能改了结构"。上游没改（commit 钉着），是**脚本自身 CRLF**。

机制（两版探针实测）：`Patch-File` 拿 here-string 里的整段原文去 `Contains` 目标文件。
我这个仓库里 `.ps1` 是 LF，F: 那台检出成 CRLF → `$old` 里每行带 `\r`，而目标文件来自
tar、恒为 `\n` → 两个**多行**补丁全落空，单行的那个（`SKVX_DISABLE_SIMD`）反而没事。
报错文案把人往"上游改了结构"上带，是这条最坑的地方。

修法：`Patch-File` 里 `ReadAllText` 之后先 `-replace "\r\n","\n"`，`$old`/`$new` 同样归一，
写回一律 LF。

判据：把同一个 `Patch-File` 函数分别存成 CRLF / LF 两份探针，打同一份从 tar 取出的原版
`gn/toolchain/BUILD.gn` —— 改之前 CRLF 那份必失败（复现用户原话），改之后两份都成功；
再把真树那两个 gn 文件换回原版、用**整份脚本的 CRLF 副本**跑一遍：三个补丁全打上，
产出与改之前的成品**逐字节一致**（`Get-FileHash` 比过），ninja 也 `no work to do`，
说明不会因为这次修改触发重建。事后 PS 7 与 PS 5.1 各跑一次幂等路径，都是"已打过补丁"。
