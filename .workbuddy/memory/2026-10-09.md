## 接入 Skia 作为 wasm 光栅后端（并揪出"一个字都画不出来"的真 bug）

### 1. 决定性发现：自写光栅器一直什么都没画

`tests/edit_test.cpp` 的 [9] 里那条像素级断言（"新页上确实画出了字形"）**早就红了**，
根因不在分页，在 `src/core/render/bitmap.cpp` 的 `rasterizeGlyph`：

- `cov` 改成成员 `cov_scratch_` 复用之后，**每行开头** `std::fill(cov+xa0, cov+xb0, 0)`，
- 而把 cov 搬进 mask 的那次 `memcpy` 还留在**整个 y 循环之外**，
- → 每一行都被填上"最后一行"的覆盖率；最后一行是 `rawY1-1 = ceil(maxY)`，比墨迹还低一行，几乎恒空。
- 症状：mask 尺寸/位置/`cacheable` 全对、`cov` 恒为 0 → `blitMask` 里 `a <= 0.0015f` 全跳过 → **一个字都没有**。
- 为什么长期没被发现：`edit_test` 里只有 [9] 查像素；[10] 的"缓存路径与直接光栅逐字节相同"
  和 PNG 的 SHA-256 在**两边都空**时照样成立。浏览器探针 47 条全查引擎状态，不查像素。
  → 这正是用户原话"有时看不到输入的东西"的来源。

**修法**：改成**逐行算完立刻 memcpy 落定**（`out->w/h/x0/y0` 与 `out->cov.assign` 提到 y 循环之前）。
修复后：第 1 页 2400 个墨迹像素 / 第 2 页 1023 个 / 4 页样本文档 37289 个（0.816% 全帧）。
**新增防线**：[10] 里加了"两遍渲染都真的画出了字形（墨迹像素数相同且 > 2000）"。

**教训**：等价性断言（A == B）必须配一条"确实有东西"（A != 空），否则空白可以通过任何等价性检验。

## 22:30 追加：用户反馈"字好浅" → 揪出**中文被渲染成 Thin(100)** 的严重 bug

### 现象与定位过程

用户说"看起来字好浅啊"。做了**同一浏览器 / 同一文档(scenario 6, 14pt@1.5=21px) /
同一区域 / 同一颜色**的双后端对照（只换 wasm 后端，其他变量全部固定）：

| 后端 | 墨迹像素 | 平均灰 | 逐列墨迹 |
|---|---|---|---|
| 自写光栅器 | 754 | **90** | 8~18 像素/列 |
| Skia | 607 | **163** | 4~8 像素/列 |

字形包围盒**完全一致**（宽 344 vs 345、行高同为 31），所以不是"画小了"，
是**笔画细了一半**。

★ 中途走过两个弯路，都靠测量否掉了，记下来免得重走：
1. 先怀疑 **hinting**：`kNone` → `kSlight`，平均灰 158 → 163，**几乎没动**。
   hinting 不是原因。
2. 更早还拿 native PNG 跟浏览器截图比过，那是**无效对照** ——
   native 的样例是 12pt，浏览器 scenario 6 是 14pt，字号不一样。
   **做 A/B 之前先确认两个输入逐项相同。**

### 真根因

`assets/fonts/NotoSansSC-VF.ttf` 的 `fvar`：**wght 轴 min=100 / 默认=100 / max=900**
—— 默认实例是 **Thin**，不是 Regular。

- 引擎在 `FontInstance::init` 里显式钉 `wght=400`（可变字体必须钉）。
- 自写后端：轮廓来自 HarfBuzz，**变体已经应用过** → 画的是 Regular。
- Skia 后端：`makeFromData()` **不带变体参数** → FreeType 取字体**默认实例 = 100** → Thin。

→ **修法**：从 `hb_font` 把归一化变体坐标读回来，按 OpenType 规则还原成设计坐标，
用 `fontMgr->makeFromStream(SkMemoryStream::Make(data), SkFontArguments{...})` 建 typeface。
（`makeFromData` 没有接收 `SkFontArguments` 的重载，只能走流。）
缓存键也要带上变体指纹 —— 同一个 face 上 wght=400 与 700 是两张脸。

修复后：平均灰 163 → **108**，墨迹 607 → **773**（自写后端 754/90），
视觉上笔画有了实心黑芯。47/47 + 85/85 全绿。

★ **这条要记住的规矩**：凡是从 `hb_font` 过桥到 Skia typeface，
**变体坐标必须一起带过去**。默认实例 ≠ 引擎要求的实例，这个差异是静默的。

### 同批修掉的：画布不是 DPI 感知的

`web/app.js` 从来没读过 `devicePixelRatio`，`#cv` 又挂着 `max-width:100%; height:auto`。
在缩放 ≠ 100% 的屏上，浏览器会把整块画布重采样一遍 → 文字整体发虚。
修法：CSS 尺寸按 `w/dpr` 折算（1 帧像素 = 1 设备像素），并把 `max-width` 去掉
（装不下就让 `#stage` 滚动）。`positionIme` / 点击命中用 `cr.width / cv.width` 求比例，
折算后正好是 `1/dpr`，比原来更准。

## 23:10 追加：用户报"光标往后走、插入处的字不动、叠在一起"

### 复现不出来，但找到了**机制**并把它钉死了

先说结论：在开发机上按"真人节奏"复现不出来。新增回归 `edit_probe.mjs [2b]`
（60 字、跨换行、**闪烁保持开着**、按键间隔 110ms、**每一次按键都查**）：

- 屏幕像素 == 引擎帧：全部相同
- 增量重绘的帧 == 一次性插入的帧：逐字节相同
- 每次按键都是整页重画（最小 1128138 vs 全量 1128045）

★ 两个刻意的设计，别省（省了就测不到东西）：
1. **闪烁必须开着**（原来的探针一律 `stopBlink()`）—— 闪烁每 530ms 自己 present 一次，
   那是最容易出错的那条交错路径；
2. 两次采样之间不能插 await 之外的任何东西，否则光标相位不同，差异里混着闪烁。

### 但是：`selfCheck()` 当场抓到一个真的不一致（9372 像素）

`__ced.type()` 这个**探针钩子**只调引擎、**不 blitFrame**。于是：
引擎内部已经画完了 → 画布还停在旧文字上 → 紧接着任何一次"只有光标脏"的 present
（闪烁 tick、或 stopBlink 后的 present）只会贴光标那一小块 →
**画布永远停在旧文字上，光标却在前移**。症状和用户描述的一字不差。

→ 修法：`__ced.type/backspace/deleteForward` 一律补上 `blitFrame`。
   **探针钩子必须和真人路径一样把画面收尾，否则它自己就是 bug 的制造者。**

这一段的价值：它证明"引擎已更新 + blit 的脏矩形只覆盖光标"就足以产生这个症状，
所以用户那边的真凶大概率也是**某一处 blit 用错了脏矩形**，而不是排版算错。

### 新增给用户用的取证入口

`__ced.selfCheck()`：把**屏幕真实像素**和引擎那一帧逐字节比一遍，并回报
`screenVsEngineDiffPx`（>0 = 上屏贴错；=0 = 问题在引擎侧）、diff 包围盒、
`dpr` / `canvas.cssSize` / `canvas.rectPx` / `framePx` / `zoom` / 后端名。
用户复现不出来时，让他在出问题的机器上跑一次即可定位方向。

### 未解

用户那张截图里 CJK 的墨迹平均灰 ~145，落在 Thin(163) 与 Regular(108) 之间
（他的图只有我的一半分辨率，所以偏高属正常），**无法据此断定他刷没刷到新包**。
有待他用 `selfCheck()` 回报 dpr / cssSize / diff。

## 23:20 技术选型咨询（四个方向）→ 架构判断，后续按此走

用户确认"bug 好了"，问的是全新的领域：富内容、导出、表单、自定义控件。

### ★ 结论 1：HarfBuzz 的职责边界（用户常有误解）

HarfBuzz 只是 **text shaping**（码点+字体 → 字形 id + 位置），
**不做**断行/分页/光标/命中测试/绘制。所以"图片/公式/控件能不能渲染"与它无关，
取决于 **Skia** 与 **文档模型**。
- Skia 的绘制能力本来就有：`drawImage` / `drawPath` / 渐变 / blend / clip / mask。
- 但 `args.gn` 目前 **关掉了** `libpng/libjpeg/libwebp decode`、`skia_enable_pdf/svg/gpu`、
  `icu`、`expat` —— 要用哪个开哪个（每开一个要重编 `libskia.wasm.a` 并记账包体）。

### ★★★ 23:25 用户纠正了上面的判断 —— **控件是「区间」，不是「矩形」**

我第一版把控件当成"浮在文档上的固定矩形 / DOM 浮层"，**方向错了**。用户的原话要点：
文本输入控件**不是固定大小**，**里面就是普通文字**（一样参与排版），**甚至能嵌套其他控件**，
"只是为了在表单模式下加个编辑边界"。**其他控件都是这个思路**，且**打印也要看到**。

#### 正确模型：`Control = 码点区间 + 类型标记`

```
Control {
  start: TextPos, end: TextPos     // 码点区间，可跨块
  kind: '文本输入' | '日期' | '数值' | '单选组' | '重复区' | ...
  state: { read_only, placeholder, constraints }
  children: [ Control ]            // 区间嵌套：内层区间包含在外层内
}
```

由此推出的几条（**替掉上面所有错误结论**）：

- 控件内容 = 普通文字 → **自动参与断行/分页/竖排/可变字体 → 不需要第二套布局**。
  （← 第一版说"病历表单是固定版式 + 独立排版"，**错**。）
- 控件大小 = 内容的自然大小 → **不是矩形**，随内容增长、可跨行。
- 嵌套 → 区间包含区间（树）；编辑时取**最内层**的策略。
- **"编辑边界" = 编辑策略层（纯逻辑）**，不是几何。
  表单模式：只允许改可编辑区间、光标在边界 clamp；文档模式：全改。
- 打印/导出 → 控件内容本来就是普通文本，**天然在引擎帧里** ✓（用户说的"打印也要看到"自动满足）。

★ 最好的类比：**Word / OOXML 的 content control**（`w:sdt`）——
设计模式才显示边框，阅读/打印时就是普通文字，看起来毫无区别。

#### DOM 层的正确定位（修正）

DOM 覆盖层**不是控件本体**，而是**瞬时交互 UI**：日历弹层、下拉列表、颜色选择器
—— 点开、选完就消失的东西。**选完的结果写回区间里的文本**，所以打印仍然正确。
`#ime` 那层仍是这套机制的原型（服务输入法，属同一类）。

★ 判据一句话：**会出现在页面上的内容 → 引擎；一瞬即逝的交互 UI → DOM。**

#### 表单模式要加的东西（比第一版少得多）

1. **`Control` 标注层**：码点区间 → 类型/状态/子控件。挂在文档模型旁边，**不动块结构**。
2. **`EditPolicy`**：`canEdit(TextPos)` / `canEditRange(a, b)`，拒绝区间外的插入/删除。
   纯逻辑，量级小。（编辑入口在 `engine.cpp:622` 那一组：`insertTextUtf8`/`typeTextUtf8`/
   `backspace`/`deleteForward`，加一道判定即可。）
3. **模式开关** `FormMode` / `ReadMode`：只影响（a）编辑策略（b）画不画边界。
4. **边界的可视化**：表单模式下给区间画底纹/虚线框。
5. **嵌套解析**：区间树 + 取最内层策略。

★ **不用做的**（第一版误以为要做）：第二套布局系统、固定矩形、模板/数据强分离。

#### 自定义控件与 JS（修正）

- **控件本体**（类型 + 行为规则 + 校验）→ 在**引擎侧注册**：它决定排版与编辑策略，
  且必须能被打印/导出。扩展点 = 内建类型表 + 新 `kind` 的 C++ 实现。
- **JS 能做**：(a) 瞬时弹层 UI（日历/下拉）；(b) 校验/格式化回调；(c) 数据进出。
- **仍然反对**：JS 注册"每帧绘制回调" —— 内容必须引擎自己画，否则打印/导出/高 DPI 全崩。

#### 打印 / 导出（判断不变，且更简单）

控件即普通文本 → 导出天然包含，无需特殊处理。三条路（`window.print()` / JS 库 /
**Skia 的 SkPDF**，包体 +300~600KB）与地基（**离屏、目标 DPI、逐页、无光标**的渲染模式）
同前，不变。

#### 现状（已核实）

`src/` 里**没有**区间/选区概念（只有单个 `caret: TextPos`），**没有**模式概念。
要做表单，这两个是新增项 —— 但都只是加一层，不动现有管线。

## 23:50 落地：表单能力（区间标注 + 编辑策略）已实现并验证

### 引擎接入（engine.h/.cpp）

- 编辑入口 `insertCodepoints/backspace/deleteForward` 加策略判定（判定用**吸附后**的位置）；
  被拒时 `++blocked_edits_` 并返回 false。
- 光标 clamp：`clampToAllowed(pos, dir)`，接在 `setCaret / moveCaretBy / moveCaretToLineStart/
  LineEnd / hitTestPt` 上。dir>0 往后找、<0 往前找、**找不到就原地不动**（"停在边界"）。
- 绘制：`paintPageIntoBase` 里，表单模式下画控件底纹（字形**之前**）+ 边框（字形**之后**，
  否则笔画会盖断框线）。
- `controlRects(i)` —— 区间 → 矩形，**跨行返回多个**。
- `focusControl(forward)` —— Tab / Shift+Tab 在可编辑字段间循环。
- `setEditMode / setControls` 都重算 `computePageFingerprints()`。

### ★ 两个必须记住的设计（都踩过/证伪过）

1. **模式必须进页指纹**（`controlsFingerprint()` 混进每一页）。
   切模式**不改任何一个字形** → 不混进去就会"内容没变 → 跳过重画"，
   底纹在切回文档模式后**残留**。表象是"随机不刷新"，从代码上极难看出来。
   **已证伪**：把 mode 从指纹里去掉 → 恰好 1 条断言变红（`fill_doc == 0`）。
2. **区间伸缩的两个端点比较规则不同**（control.cpp）：
   起点 `> at` 才右移（在 start 处插入 → 起点不动，新字符进字段）；
   终点 `>= at` 就右移（末尾追加 → 变长）。
   写成同一个比较符，会出现"在字段开头打的字立刻变成不可编辑"。
   **已证伪**：把 `adjustControlsOnInsert` 短路 → 8 条断言变红。

3. **谁改文档谁负责 relayout**。`setControls` 刻意不 relayout（区间不参与排版），
   所以它**假定 layout_ 已与 blocks_ 同步**。
   真踩到：wasm 的 `loadFormSample` 换了文档却没重排 → 控件投影到**上一次的行盒**上，
   探针当场抓到"4 个字的字段给了 2 个矩形块（42pt）"。修好后是 1 块 56pt。

## 01:10 追加：括号**进文档流**（占位），且"显示才占位"

### 实现：占位簇

**全部要改成 setCaret 之后再取**。两处都因此红过（差一个括号宽度）。

## ★★ 2026-10-10 凌晨：「括号盖在文字上」的真正根因（用户看出来的）

**上一段结尾那句"内容起点从 351 退到 358，就是括号把它挤开的直接证据"是错的。**
那是我在同一张缩略图上量错了列。用户直接指出"括号不还是盖在文字上吗"，
顺着量下去，发现是**排版与绘制各算各的**这一级的 bug。

### 根因（一行）

`layout.cpp` 的横排字形放置：

```cpp
pg.x_pt = pen_x + sg.x_offset * usToPt;   // ← 字形位置
...
pen_x += sg.x_advance * usToPt;           // ← 只按**字形**推进
```

而行盒那一侧用的是 `ax += bs.cluster_adv_pt[i]`（**簇**推进）。

- 对**普通**簇两者恒等（`cluster_adv_pt` 就是该簇字形 advance 之和）→ 一直没露馅；
- **占位簇没有字形**（`g0 == g1`）→ 内层循环一次都不执行 → `pen_x` 在它身上纹丝不动，
  而 `cluster_adv_pt` 是括号宽度。

于是形成一劈两半的状态：

| 用哪把尺子 | 谁 |
|---|---|
| `cluster_adv_pt`（**含**占位） | `LineBox::clusters` / `inline_end_pt` → 光标、控件矩形、命中测试、`controlRects` |
| 字形 advance 连加（**不含**占位） | `PlacedGlyph::x_pt` → **真正画出来的字** |

→ 光标与控件矩形按"文字让开了"算，画出来的字却没让开 ⇒ **方括号正好压在文字上**。
竖排那段同病（`gy += sg.x_advance / -sg.y_advance`），一起改。

### 修法（结构性，不是补丁）

横排：每个簇开头 `pen_x = cx + ax;`，簇尾 `ax += bs.cluster_adv_pt[i];`
—— 字形位置**从簇位置派生**，两者共用一个累加器，结构上不可能再不一致。
竖排同理：`gy = pen_y + ay;` / `ay += bs.cluster_adv_pt[i];`。
对普通簇是恒等变换，不改任何既有结果。

### 顺手修的第二处：占位不该在**文档模式**插

原来 `relayout()` 无条件传 `focusedControlIndex()`，于是文档模式下标着同一份控件、
光标又落在字段里时，**不画括号却照样把正文推开** —— 凭空一段空隙。
新增 `EditorEngine::occupiedControlIndex()`：

```cpp
int occupiedControlIndex() const {
    return policy_.mode() == EditMode::Form ? focusedControlIndex() : -1;
}
```

engine.cpp 里 8 处 `focusedControlIndex()` 全换成它（含 `relayoutIfFocusChanged`
的"变没变"判定、`setEditMode` 里"切模式可能改变占位"那一处）。
`setEditMode` 本来就已经是"先捕获 foc_before → 改模式 → relayoutIfFocusChanged"的顺序，
换掉函数即可自动接上，没有额外改动。

### 为什么之前所有断言都是绿的（这次最值得记的教训）

- **单测 (b)** 断言 `inline_end_pt` 变大 —— 那正是 `cluster_adv_pt` 的和，
  和"字形画在哪"是**两套数**。断言查了错的那一半，结构上永远抓不到。
- **单测 (f) / 穷尽不变式** 只查"括号有没有出现在左缘竖带里" —— 它确实出现了，只是压在字上。
- **浏览器 [2b]** 比"增量帧 == 一次性插入帧" —— 两边走同一条（坏的）绘制路径，当然相等。
- **截图** 我按 3～5 倍缩放看，把 7px 的错位当成了 AA。

→ **教训：几何元数据与绘制结果必须分别断言，不能拿前者替后者。
   而且像素断言的判据要按实测位置定，不能按几何直觉估。**

### 新加的可证伪断言

**单测 [11](b2)**（native，12pt，字段 k1=[5,9)、k2=[12,16)）：

```
字形 x 位移：患 56.700→56.700（Δ0.000）｜ 反 116.700→120.755（Δ4.055）
             ｜ 三 Δ8.109 ｜ 。 Δ8.109 ｜ 括号宽 4.055 pt
```

- 字段**之前**的字不动（患 Δ0）—— 证明占位是局部的，不是整体平移；
- 字段**第一个字**右移**恰好一个括号宽**（Δ4.055）—— 这条一旦是 0 就是上面那个 bug；
- 字段之后、行尾各移**两个**括号宽（Δ8.109）；
- ★★ 最强的一条：**字形 x == 控件矩形左缘**（绘制与几何同一把尺子）。
- (b3) 文档模式下**不占位**：`文档模式字形 x=116.700（无表单基线 116.700）｜ 表单模式 120.755`。

**证伪**：把 `pen_x = cx + ax` + `ax += ` 拆掉（还原成 bug 版）重编 →
`反 116.700→116.700（Δ0.000）`，恰好 2 条断言变红。恢复后全绿。

★ 但第一次证伪时发现另外两条（`三`/`。`）**退化通过了**：
它们写的是 `fabs(Δ - 2*bw) < 0.05`，而 bw 在同一轮测得为 0 ⇒ `fabs(0-0)` 恒真。
已改成 `Δ > 1.0f && fabs(Δ - 2*bw) < 0.05f` —— **"真的动了"和"动的量对"缺一不可**。

**浏览器探针 [8]** 新增像素级断言：同一段文字（scenario 6）两遍，
一遍不带表单、一遍带表单且光标在字段里，只比**最右墨迹列簇的左缘**：

```
[PASS] ★★ 行尾字形真被推开了两个括号宽   行尾墨迹左缘 402 → 416（Δ14 px，期望 9.1~15.2）
```

★ 给的是区间而不是等号：量的是"第一个被判为墨迹的像素列"，是一次**阈值穿越**，
受 AA 影响有 ±2px 抖动（几何上是 12.2px，实测 14px）。区间 (1.5, 2.5)×括号宽
仍能把"没让开(0)"和"只让一个括号(≈6)"都判红。

## ★★★ 2026-10-10（第三段）：用户那个 bug 找到了，而且**逐字节复现**了

用户第二次报"还是不对"，附了 F12 的 `__ced.auditFrame()` 与 `__ced.selfCheck()`
两段输出。**那两组数字把根因直接指出来了**，不用再复现、也不用再猜。

### 用户给的两组数字（决定性）

```
__ced.auditFrame()  →  { diff: 0, frameW: 893, frameH: 1263, box: null }   ← 引擎帧**完全正确**
__ced.selfCheck()   →  screenVsEngineDiffPx: 1145
                       screenVsEngineDiffBox: [191, 92, 435, 115]
                       repainted: { pages: 0, pixels: 993, w: 166, h: 35 }   ← 最后一轮只贴了 166×35
```

- `auditFrame` 0 + `selfCheck` 1145 ⇒ **方向唯一**：引擎是对的，**上屏贴漏了**。
- `repainted.w/h = 166×35` 是个**很小**的盒子，而引擎这一下重排了整行
  ⇒ 那一轮 present 根本不该只有这么大；说明**"改了排版的那一轮"的账被丢了**。

### 根因（一次操作两次 present，宿主用了后一轮的账）

`web/app.js` 的 `afterEdit()`：

```js
const st = JSON.parse(mod.editStatsJson());   // present① 的账（改排版那次，整帧）
if (!st.caretVisible) {                        // ← 闪烁正停在"隐藏"半拍时成立
  mod.showCaret(true);
  mod.present();                               // present②：只写光标与标记
  blitFrame(JSON.parse(mod.editStatsJson()));  // ← ★ 用 present② 的账上屏！
}
```

而 `setCaretAndPresent()`（鼠标点画布走的正是它）里的 `present()` 是**裸
`mod.present()`，不 blit**：所以 present① 那次整帧重绘**从头到尾没上屏**，
随后只用 present② 的 166×35 贴了一小块。

**"有时"的来源**：闪烁相位是 50/50，只有停在"隐藏"那半拍才触发。
而**此前所有断言开头都调过 `stopBlink()`** —— 正好把这一半概率整个屏蔽掉了。
这就是它一直没被抓住的原因。

### 复现（逐字节对上了用户那两组数字）

先写了临时诊断 `scripts/diag_twopresent.mjs`，把两步拆开逐步报账：

```
present① 换字段：pages=1  px=1128207  box=[0,0,893,1263]  caretVisible=false
present② 补救 ：pages=0  px=1086      box=[269,85,166,35]  caretVisible=true
```

`1128207` / `893×1263` / `166×35` 与用户面板和 selfCheck 里的数字**完全一致**。

★ 第一次证伪**失效**（我撤掉累加器后探针仍全绿）：因为新的 `blitFrame` 在
  累加器为空时会退化到**整帧 putImageData** —— 等于兜住了。把 `blitFrame`
  也退回"用 editStats 的本轮账"之后，探针立刻红：

```
[FAIL] ★★ 隐藏半拍换字段：屏幕像素也必须等于引擎帧
       差 1145 px，盒=[191,92,435,115]
```

**与用户截图里 selfCheck 的输出一字不差**（1145 / [191,92,435,115]）。
用户截图里那个残留的 `[`，位置正好就在旧区域的**左边缘 x=191**。
打字路径也复现：`差 39 px，盒=[446,104,453,111]`。

### 修法（三层，从"结构性"到"减少冗余"）

1. **★★ 引擎：待上屏脏矩形累加器（真正的修复）**
   `EngineEngine` 新增 `noteBlitDirty()` / `takeBlitBox()`：
   `presentInternal` 每轮把实际写过的 bbox 并进 `blit_acc_`，
   **读一次即清零**。宿主 `blitFrame()` 改成读 `mod.takeBlitBox()`。
   于是宿主拿到的永远是"**自上次上屏以来**引擎写过哪些区域"，
   而不是"这一轮写了多少" —— "引擎写了、宿主没贴"**在结构上不可能**。
   `editStats.repaintedX/Y/W/H` 保持不变："**本轮**写了多少"（面板要的就是它）。
   ★ `takeBlitBox()` 无待上屏时返回 0×0 → 宿主退回整帧 putImageData（安全兜底）。

2. **引擎：`repaintAfterEdit()`** —— 内容编辑（typeText/backspace/deleteForward/
   indent/outdent/focusControl）的收尾**先把 `caret_visible_` 置真再重绘**。
   于是 `editStats.caretVisible` 恒真，宿主那条补救路径自然不再触发。
   ★ **光标移动（moveCaret / Home / End）刻意仍走裸 `repaint()`**：
     移动不是编辑，光标该继续自己闪；而且单测里"光标隐藏时写入量更小
     （只擦不画）"量的正是这条路径，改掉它那条断言就没意义了。

3. **宿主：`setCaretAndPresent()` 在 present 之前 `showCaret(true)`** ——
   把"一次点击产生两次 present"这层冗余也去掉。

② 换字段后 present① 的本轮账：893×1263 px（整帧 893×1263）

两条红，且差值 `1145 / [191,92,435,115]` 与用户完全一致。

### 这次最该记住的三条

1. **`selfCheck`（画布 vs 引擎帧）与 `auditFrame`（帧 vs 整帧重画）必须成对用。**
   只有前者 → "引擎自己错了"抓不到；只有后者 → "上屏贴漏了"抓不到。

## 2026-10-10（第四段）：字段末尾的光标跑到 `]` 外面 + 括号与正文贴在一起

用户报两条，其实是**同一个根因的两面**：

> "右括号和最后一个字像是连起来了，光标从最后一个字左边直接跑到右括号右边了"

### 根因：占位簇只知道自己的 cp，不知道自己是开括号还是闭括号

`LineBox::inlineOffsetFor(cp)` 的规则是"**最后一个 cp <= target 的簇**的起点"。
对普通文本它等于"target 那个字的插入点"，没问题。但占位括号破坏了它：

字段 k2 = [12,16)，行内簇序列（`pc.cp` = 它**后面**那个真实簇的 cp）：

```
... ，(11)  [ph cp12 Open]  加(12) 重(13) 一(14) 天(15)  [ph cp16 Close]  。(16) ...
```

- 光标在字段**起点** 12：循环走到 ph(12) 再走到 加(12) → best = 加.inline = `[` **之后** ✓ 正确。
- 光标在字段**末尾** 16：循环走到 ph(16) 得 `]` 的位置，**继续**走到 。(16) 又把 best 覆盖掉
  → 落点跑到 `]` **之外**（`]` 右边缘之后一整个槽）。**这就是用户看到的"直接蹿出框外"。**

**修法**：给占位簇加 `BracketSide{Open,Close}`，`inlineOffsetFor` 走到**闭括号占位就立刻返回**
（它是这次查找的终点）；开括号不返回（内容在它右边，光标要落在它之后）。
`layout.h` 的 `BracketSide` 注释里写了这一整段推理。

★ 还有一个坑：`if (cp >= last_cp) return inline_end_pt;` 这句短路**必须放到循环之后** ——
字段末尾正好是段尾时，闭括号占位的 cp 就是段长哨兵（== last_cp），先短路就又跑到括号右边了。

### 第二个问题：`字]` 贴在一起

括号字形自带的那点左侧边距在 12pt 下只有 ~1px，看着就是连成一个字。
**间隙必须进排版**，不能画的时候往外挪 —— 挪了就是"槽"和"字形"两套账
（括号会盖到相邻的字上，或者槽里空一条而字已经走了），
和"括号进文档流"是同一条道理。所以：

- `layout.h` 新增 `kControlBracketSlotGapPt = 1.5f`（**排版与绘制共用的唯一常数**）；
- 槽宽 = 括号 advance + 该间隙；
- 绘制时字形贴住**朝向内容的那一端**（`[` 画在槽首、`]` 画在槽尾），
  间隙才对称地落在括号与正文之间。

### 证伪（两条都命中，而且与用户描述逐字对应）

**native `[13]`**（新增）：`插入点 x` 在 off12/13/15/16 →
`206.255 / 218.255 / 242.255 / 254.255`，控件矩形 `[206.255, 254.255]`。
撤掉闭括号短路后 **off16 = 259.809 = R + 一整个槽** —— 恰好 1 条断言红。

**浏览器探针 `[8]`**（新增，像素级）：量"光标那一行最靠右的标记墨迹"（＝ `]` 字形），
要求光标右边缘在它左边。撤掉短路后：`光标 x∈[438,441] ｜ 最右标记墨迹 x=437`
—— **光标左边缘已经越过括号**，1 条断言红。

### ★★ 顺手修掉两条**脆弱断言**（都是这次被"弄红"才发现的）

1. **比"最后一个墨迹列簇的左缘"** —— 量出来：无表单 `[402,427]`、带表单 `[441,446]`，
   左缘跳 39px、右缘只跳 19px。原因不是排版错，是**分组重组**了：字距一变，
   `。` 和它前面的字就从"同一组"（间隙 ≤3px）变成"两组"。
   → 改成比**右缘**（只跟"最后一个字画在哪"有关，单调）。
2. **围绕标记色的矩形色容差（±20）** —— 括号是**字形**，笔画细，大部分像素是
   "标记色↔白"的混色。字形位置一变（加间隙→亚像素相位变），矩形色容差数出来的像素
   从 241 掉到 33，而括号画得好好的。→ 改成**方向性判据**
   （`r>45 && b-r>60 && b>140`，与 `markCheck`/`bandAt` 同口径）：实测 139 px。

★ 教训：**相位/分组一变就翻脸的断言，等于没有断言。**
  像素断言的判据要选"单调、不随分组变化"的量（右缘、方向性判据），
  不要选"会被重组/会随亚像素相位抖动的量"（左缘、精确色计数）。

## 2026-10-10（第五段）：用户确认光标移动已正常 + 一条口径纠正

### 口径纠正（重要，别再做错）

用户原话："右括号和最后一个字像是连起来了，光标从最后一个字左边直接跑到右括号右边了"

  所以它现在的作用是"把光标和括号分开"，不是"把括号和正文分开"。

  排版与绘制共用这一个常数，一处改完两边同步。

## ★ 2026-10-10（第六段）：方向键**不许跨控件**（用户明确要求）

用户："移动方向键不要自动跨越控件"

### 改之前是什么行为

`moveCaretBy` 的做法是：**整段走完**，再用 `clampToAllowed(&q, dir)` 把结果
**投影到最近的合法位置**。那个投影**不认方向、只认距离** —— 于是"走一步"
变成了"瞬移到另一头"：

```
从 #2（aggravate [12,16)）起点按一次 ←  ：12 → 9   （跨过只读字段 #1 [9,11)，一次跨 3 个偏移）
从 #0（complaint [5,9)）末尾按一次 →   ：9  → 12  （同样跨过 #1）
```

用户就是从浏览器里看到这个的（他原话"光标移动跨两个字符"）。

### 改法

1. **`moveCaretBy`：逐簇走，下一步不可停就 `break`（停在原地）**，不再投影。
   - 实现上把"算下一步"落到**临时量 `next`**，`canPlaceCaret(next)` 通过才提交 `p = next`。
   - 对**多步**移动（|dcp|>1）语义自然成立：尽量走，停在最后一个合法处。
2. **Home/End：新增 `clampToFieldEdge(pos, to_start)`** —— 目标在**当前字段**内就照常，
   否则退到本字段的起点/终点；光标不在任何字段里就返回 false（不动）。
   改之前 Home 在 #2 里会落到 #0 的起点 5（同样是跨控件）。
   ★ **刻意不用 `clampToAllowed`** —— 已在它的声明注释里写清楚：
   "投影"只适合**鼠标点击/程序化定位**（点击给的是粗略的点，投影是"猜你想要哪儿"），
   **不要**拿它做键盘移动。
3. `clampToAllowed` 保留给 `setCaret`（点击）。**点击仍然会吸附到最近的可编辑字段**
   —— 这是有意的，用户没提；如果他也觉得算"自动跨越"，把 `setCaret` 也换成
   "不可停就不动"即可。

### ★ 代价（必须说清楚，这是行为变更不是修 bug）

**字段之间不再能靠方向键走过去** —— 中间（字段外的正文）不是可停位置。
要进另一个字段就**点鼠标**。这是"不跨控件"的必然结果。
面板文案已同步（原来写着"字段之间用鼠标点或方向键走"）。

### 证伪（精确命中）

还原成投影逻辑后重编：

```
[FAIL] ★★ 再右移：原地不动（10 已经在只读字段 #1 里）
[FAIL] ★★ 在 #2 起点左移：原地不动
[诊断] #2 内左右各走 8 步：单步最大跨度 3（应为 1），始终在字段内=0
[FAIL] ★★ 单步跨度恒为 1
[FAIL] ★★ 走完一趟，光标从未离开 #2
共 7 项断言红
```

★ 那个 `单步最大跨度 3` 就是用户看到的"跨两个字符"（实测是 3 个偏移）。
  **判据必须是"逐步"的** —— 只看终点抓不到（终点"落在某个合法位置"照样成立）。

### 新断言

- **native [11](d) 重写**：9→停、12←停、往返各 8 步单步跨度恒为 1、从不离开 [12,16)、
  Home→12、End→16、再按 Home 停在 12。
- **浏览器 [8] 新增**（真实键盘路径）：在 #2 起点按 ← 仍是 12；
  从 12 右走 5 步 `13 → 14 → 15 → 16 → 16`，最大单步跨度 1。
- 浏览器 [3]（文档模式的方向键/Home/End）**不受影响**：文档模式下 `canPlaceCaret` 恒真。
