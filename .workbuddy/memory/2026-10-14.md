# 2026-10-14（承接 10-13 夜里那一刀）

## 第三刀：批量画字形 + 画布池 + 窗口策略

用户报的痛点是**回车**（"每次输入到新增一行的时候就会卡一下"），截图那次的实测是
**48.7 ms**，其中 **paint 40.7 ms**（3 页全窗重画）、layout 只有 8 ms。
所以病根不在"该不该重画"，在**重画一次太贵**：`drawGlyph` 是**一个字形一次 Skia 调用**
（每次新建 SkPaint、装配一遍字形运行、算一遍包围盒），一页约 700 个字形就是这么变成 10 ms 的。

### 做法
1. **`Bitmap::drawGlyphs`（批量入口）**：同一字体/颜色/朝向的字形攒成一段，一次交出去。
   `drawGlyph` 退化成 `drawGlyphs(count=1)` 的壳 —— 两条入口只能有一条实现，
   否则"逐字形画"与"整段画"会各长一套、差一点就是两边对不上的幽灵。
   侧倒竖排（`rotate_deg != 0`）退回逐字形：旋转是每个字形各绕自己的原点转，一次调用表达不了。
   自写后端只是逐个转调（那一侧固定开销本来就小，不值得长出第二套光栅）。
   ★ 段内次序不能动：它就是绘制次序，重叠字形靠它决定压盖。
2. **记账改批量**：`SkFont::getBounds` 的批量重载一次取完所有包围盒 ——
   逐字形 `getBounds` 每次都要进一遍字形缓存（一次全局查找），上千个字形时这笔能盖过 blit。
3. **新增"这一轮画了几个字形"**：`Bitmap::paintedGlyphs()` / `EngineStats::painted_glyphs`，
   与 `paint_glyph_ms` 配对算"每字形微秒"。判"字形光栅贵不贵"必须看这个商 ——
   只看总耗时是分不出"字多"与"每个字贵"的，而两者修法完全不同。
   ★ 记**底图**不记帧：字形只画在底图上，帧那边是从底图搬像素过来的
   （第一版读 `bitmap_.paintedGlyphs()` 恒得 0，就是这个）。
4. **宿主画布池**（`canvasPool`）：换窗口时卸下来的页画布留着复用，不销毁。
5. **窗口策略**：`desiredWindow` 以**可见页**为准，光标页只在挨着可见页时才并进来。

### 剩下的两条杠杆（都还没做）
1. **段数变化时复用后缀**（省 layout + pageFp ≈ 4 ms）：现在 `para_count_changed_` 一置位就
   禁止后缀复用，理由是"复用判据是第 from+1 段开始时的状态与上一轮相同，而段号一变，
   第 from+1 段已经不是同一段了"。要修得让编辑侧给出"插入/删除了几段"这个元数。
2. **行级位图平移**（把"整体下移"变成 memcpy）：页边界是整数像素，窗口平移好办；
   但回车那种**页内整体下移**是小数像素 —— 平移与从零重画的抗锯齿会差一堆像素，
   而"增量帧 == 从零重画的帧"是本项目的硬判据，不能为了快把它放宽。
   解锁前提：让字形的纵向位置落在**整数设备像素**上（那时 mask 与绝对位置无关，
   平移逐字节精确）。这是一条更大的刀，动的是呈现层的定位口径。

## 两个小问题（都真，且第一个是我上一轮引入的）

### 1. 重编 wasm 后页面恒报"旧副本"
**根因**：wasm 里编进去的 `HEDITOR_BUILD_STAMP` 现在是**配置时刻**（上一轮为省"每次构建
重编那几个 TU + 重链"改成配置期生成），而页面拿它与产物文件的 **mtime（构建时刻）** 相减、
超五分钟就判旧副本 —— 差值恰好等于"构建比配置晚了多久"，所以只要构建发生在上次配置
五分钟之后，就**恒报**，而页面跑的其实是最新那份。纯误报。
**做法**：`heditor_wasm` 加 POST_BUILD，把"这次构建用的配置戳"写到产物旁边
（`build/wasm/web/heditor.buildstamp`，内容与编进 wasm 的值同源）；页面改成与它对照。
旁证只在构建成功时刷新 ⇒ 构建失败时仍报"一致"（磁盘上那份本来就是上次成功构建的产物）。
**判据含反向一半**（实测）：正常时 `stale` 为空、状态栏"就绪"；把旁证改成 2020-01-01
再刷新 ⇒ 红色警报 + 状态栏写明两个戳。改完复原。
★ 顺便说清一个坑：`cmake --workflow --preset wasm` 每次都会重新配置 ⇒ 戳变 ⇒
wasm_main.cpp 重编 + 重链（~90 s）。只想重编就用 `cmake --build --preset wasm`。

## 第五刀：页指纹从 O(文档) 变 O(1)（回车 66.0 → 34.4 ms）

用户问"pageFp 这个指标是啥意思，全 0 正常吗" —— 全 0 正是这一刀要的结果，而它同时也是**这一刀
上一版的 bug 现场**（详见 `MIGRATION.md` 第五刀 与 `TRAPS.md` 第 33 条）。

**pageFp 是什么**：每页内容的指纹（字形 id/位置/朝向/颜色 + 行盒几何 + 簇表）。排版改完之后，
引擎靠它判"这一页的画面还对不对"—— 指纹变了才重画那一页。它的代价与"要重算多少页的字形"成正比。

**为什么原来是 21 ms**：后缀整体平移那一级（回车 / 合并 / 敲字敲到换行）会去哈希**整条后缀**
（2000 段 = 81 页 / 10000 段 = 33.9 ms），而那件事的答案是已知的：后缀每一行都沿块轴挪了，
它在的每一页内容都变了。续排路径（末尾敲字）更是直接 `fp_lo = -1` ⇒ 整篇重算。

**做法**：`markPagesChangedFrom()` 直接标脏（不算哈希）+ 续排路径按"脏段新旧两版更靠前的那一页"
框范围 + `EditStats::total_ms` 把 pageFp 也算进"合计"（以前不含它，显示 18 ms 而操作实际 39 ms）。

**效果**：回车·中段 66.0 → **34.4 ms**；回车·末段 21.4 → 14.8；末段敲字（3000 段）14.4 → 6.4。
★ pageFp 现在与文档规模无关（10000 段也是 0.0），剩下的 paint 在 2000/10000 段完全相同（21.6 ms）。

**踩的坑（我自己的）**：标脏值写成常量 ⇒ present 之后底图也变成那个值 ⇒ 第二次编辑读出来是
"没变" ⇒ **连续换行只有第一次把文档推下去**（用户就是这么报的）。判据落在帧上：
`edit_test` 新增"连续两次回车：画面变了多少像素 + 与从零重画差多少"，
反向验证 84 px / 750062 px（通道差 231）vs 修复后 750148 / 562（通道差 3）。

**判据**：native 803 / **721** / 55；`edit_probe` / `stress_probe`；lint 0。
`diag_perf` 加"连续两次回车"（浏览器侧也能自己看见这一条）与"连按 30 次回车"两节。
★ 另一条经验（TRAPS 第 35 条）：**跨轮比绝对耗时不可信** —— 同一 build 连跑，场景 7 装载
分别是 171 / 245 / 331 ms（装载路径一个字没改），所以判"省了多少"只看同一操作内部的分项。

## 严重 bug：跨段控件下的增量重编译（"删一个字，前面一串字与所有控件一起没了"）

**现象**（用户报，三连可编辑控件示例）：光标放到「天」后面回车，再把光标放到「悸」后面退格 ——
结果「患者主诉：反复心悸」九个字与三个控件**整个消失**，只剩一行「三天」。

**取证路径**：先按用户的两步在 `edit_test` 里复现（`setCaretAtSide(0,11,0)` → `splitParagraph()` →
`setCaretAtSide(0,9,0)` → `backspace()`），四个侧别组合各跑一遍，并且每一步之后读
`auditCompile()`。结论两条：
- 回车**本身**是好的（`auditCompile() == 0`），它把段落标记插进了控件内部 —— 第三个字段因此
  变成**跨段**（`c(0:9..1:0)`）。这是正常形态（`compile.h` 的 `BlockSource` 就写着"跨段控件会让
  中间那些块的 mark 落在控件内部"），不是缺陷。
- 退格**那一步**才出错：`auditCompile()` 报 **4** 项差异，段变成 `[三天][，加重一天。]`、控件 **0** 个。
  再切一次编辑模式强制全量重建，段与控件又全都回来了（`[患者主诉：反复心三天][，加重一天。]`
  + 三条区间）⇒ **树是对的，坏的是引擎那份"块视图"**。

**根因**：`rebuildParagraphFromTree(para)` 按"结束标记的父容器"取子节点区间来增量重编译。当标记
落在控件内部时，那一段的内容其实**起自控件之外** —— 只编控件里那一截子节点，产物就成了半个段落
（前半段的字与控件自己的边界一起丢掉）；更糟的是 `block_src_` / `block_flow_` 被这半个产物覆盖，
`exportControlsFromBlocks` 随之导出空集合，**之后每一次编辑都在错的坐标上算**。

**修法**：加一条形状判据 —— 段落起点（`block_src_[para].first`）的祖先链要经过 `container`，且它
在 `container` 下的下标落在 `[begin, mark_idx]` 内；不满足就退回全量编译（`rebuildFromTree`）。
表格单元格里的段落在同一个单元格内，不受影响，增量照走。

**反向验证（实测两组数）**：

| | 退格后的文本 | 控件数 | `auditCompile` |
| --- | --- | --- | --- |
| 去掉判据（改前） | `[三天][，加重一天。]` | 0 | **4** |
| 加上判据（改后） | `[患者主诉：反复心三天][，加重一天。]` | 3 | **0** |

**判据**：`edit_test` 新增 [31]（9 条：回车后的跨段形态、退格后的文本与三条区间、再退一格到零宽
字段、`auditLayout == 0`、光标所在字段仍归 #1），native model 803 / **edit 736**（721 → 736）/ shaping 55；
`edit_probe` 新增 [14.10]（5 条：文本 / 控件区间 / `auditCompile` diff 0 / `selfCheck` 差 0 px），
浏览器 **212 项 0 失败**；`lint_comments.py` 110 文件 0 违规；`format.ps1 -Check` 合规；三个后端构建 0 警告。
截图 `out/web/ctl-split-then-backspace.png`（第一行 `患者主诉：[反复][心][三天`、第二行 `]，加重一天。`）。
★ 陷阱记进 `TRAPS.md` 第 36 条；顺手记下第 37 条：`hidden` 一旦有设置入口，
`eraseOnTree` 的坐标会立刻在 Design/Display 两个位置空间之间错位（目前恒等，因为没人设 `hidden`）。

## 第二次：段首是一枚闭括号（同日稍后）

用户报：三连字段里「天」后回车、再「悸」后回车，然后把光标放到「天」后面退格 ⇒ 第二段段首的
两枚边界成对消失，**控件从 3 个掉到 1 个**。

**根因**：上一轮的形状判据用 `block_src_[para].first` 找祖先，而 `first` 是编译层记下来的 ——
`noteFirst` 只在文本与开括号处调用，**闭括号没记**。第二次回车把段落标记插进了第二个字段内部，
于是第二段的第一枚内容是"第一个字段的闭括号"，`first` 退化成第二段自己的结束标记（必然在容器内）
⇒ 判据放行 ⇒ 编出缺边界的半段；`exportControlsFromBlocks` 对半截边界整对丢弃，控件就整批消失。

**修法两条**：① `compile.cpp` 里闭括号也 `noteFirst`（契约本来就写着"第一个吃进内容的元素，
含控件边界"，是实现漏记）；② `rebuildParagraphFromTree` 的判据改成比**流位置** —— 段的流起点
（上一枚标记之后那一位）必须与 `container.children[begin]` 的区间起点重合，不依赖来源记法。

## 三、控件边界的可见性与"删/改控件"的入口（同日稍后）

**需求两条**（用户原话）："编辑模式下不显示控件边界了，我都不知道哪块是控件"；
"编辑模式下，光标在控件后面，退格就是删除控件"。经确认的两个决策：文档模式用**方括号**
（与表单一致，不是细线框）；删/改控件**先做引擎命令**（宿主 UI 稍后）。

### 1. 可见性：文档与表单都画，只读不画

- 判据落在三处同一个条件上：`bracketedControls` / `bracketPlanId` / `drawControlMarks`
  —— 文档与表单都占位、都画；只读是呈现与打印态，一个都不占、一个都不画。
- "占位/不占位"的差别是**正文有没有被推开**，截图上分不出来 ⇒ 判据取占位槽清单。
- 切模式仍然整帧重贴（`frame_needs_full_refresh_`）：底图不含标记，页指纹不会变。
- 连带改掉 6 条旧判据（`edit_test` 的 b / b3 / f 三处）+ 探针 [8] 里那一对（原为
  "切回文档模式标记一个像素都不剩"，现为"只读模式一个像素都不剩 / 文档模式照常出现"）。

### 2. 删控件 / 改控件：两条引擎命令，一套门

- `removeControl(index, keep_content)`：`keep_content` 真 = 拆壳（内容上提为正文）。
- `setControlProp(index, prop, value)`：只收 hidden / readonly / required / structureLock。
- 都只动树，改完交给 `commitOnTree` 一次重建 —— 撤销、重排、重绘、记账自动一致。
- 门复用 `canDoStructureOp`（**逐控件**的 `structureLock`，表单默认锁住、文档放行、只读拒绝）。
- 步骤层新增 `UnwrapNode` / `WrapNode` 两个原语（互为逆操作，共用一份记录、字段一一对应）。
- 另补两个 `*AndRender` 组合入口（与 `indentAndRender` 同一口径），并把 `undoEdit` / `redoEdit`
  暴露到 wasm 与宿主机门面（**没有绑键位** —— 绑什么由宿主决定，与 `tabCaret` 同一个处理方式）。

### 3. 退格删控件：判据只能落在流位置

- 命中条件 `hi == 光标流位置`（光标紧贴闭括号）；**必须排在"段首退格 = 并入上一段"之前**
  （控件跨段时闭括号落在下一段段首）。
- 同一枚闭括号，"在它后面"与"在内容末尾"是同一个 (段, 偏移)，只有流位置分得开。
- 策略拒绝**不吞按键**：回落成普通退格并记进 `blocked_edits_`。

### 4. 本轮踩到的新陷阱：槽位下标活不过一次规范化（`TRAPS.md` 第 39 条）

现象：删控件后**撤销能过、重做红**（"拆开节点：槽位里的孩子个数与步骤记录不符"，算出 0 / 记的是 1）。
根因：`normalizeDocument` 每次提交与撤销都跑，把相邻同标记的文本节点并成一个 ⇒ 槽位整体前移，
步骤里的 `at` 全失效。修法三步：`slotForFlow`（文本内部折到两半之间）、`runForFlowRange`
（切片一次性算，不再两端各自换算）、`slotAtFlow`（`applyStep` 里按流位置当场重算 + 切回文本）。
★ 区间一律取"这一步所在状态"里的地址（`UnwrapNode` 在拆之前、`WrapNode` 在拆之后）。

### 5. 构建目录里存着 15 个 `#deps 0` 的依赖条目（`TRAPS.md` 第 40 条）

**45 个 obj 里 15 个是 `#deps 0`**（含 `engine_layout.cpp.obj`）—— 头依赖一条都没记，
改头文件不重编、混链而断言照绿（第 19 条的历史残留）。修法：`ninja -t clean` 后全量重编；
复核口径见第 40 条。★ 教训：改完头文件若"只重编了一两个 TU"，先怀疑依赖表，别先怀疑工具。

## 四、撤销键位与撤销粒度（同日稍后）

用户两条："undo 和 redo 先绑成 ctrl+z 和 ctrl+y"；"单个输入的字符和退格删除的字符，undo 不能
合并啊"。

### 1. 键位：Ctrl/Cmd+Z 撤、Ctrl+Y 与 Ctrl+Shift+Z 重做

- 位置是关键：必须插在 `onKeyDown` 那句"带 ctrl/alt/meta 一律放行"**之前** —— 否则按键被直接
  交给浏览器，而本页没有可撤销的 DOM 编辑（键盘承接层是只读 textarea），表现为"按了没反应"。
- 走 wasm 的 `undoEdit` / `redoEdit`（引擎 `undoAndRender` / `redoAndRender`），与 Backspace/Enter
  同一个模式：引擎收尾重排重绘，宿主只管上屏。
- 比较前转小写 —— Ctrl+Shift+Z 时真键盘给的是大写 `'Z'`（探针专门派了大写去钉这一格）。
- ★ 这一对成了 `[2]` 段那条"Ctrl/Alt/Meta 组合一律不吞"的**唯一例外**。那条判据经查用的是
  `key: 'x'`，不受影响；但注释已补上例外说明，否则下一个人会以为矛盾。
- 页面说明（`web/index.html`）补了键位；顺手改掉一句因上一轮口径变更而陈旧的：
  "切回文档模式标记会消失" → "切到只读模式标记才会消失"。

### 2. 撤销粒度：取消合并（`canMerge` 退役）

- 原口径：`canMerge` 把相邻同标记的 `InsertText` 并进栈顶（"连续输入算一笔"）。
- 问题（用户指出）：那只对插入生效，退格是另一种步骤 —— 敲五个字一步退掉、退五个字却要五步。
  同一件事两种粒度，用户无从预期。
- 改法：删 `canMerge`（声明 + 定义 + `commit` 里的合并分支），`commit` 直接压栈。
  `transaction.h` 文件头、"事务与撤销粒度"那一节、`docs/文档模型设计.md` 三处口径同步改写。
- 判据：`model_test` 1.3 的"分组"小节重写为"粒度"小节 —— 五笔连续输入 = 5 个撤销单位、
  连撤五次逐次回到对应状态；接着的 / 加粗的 / 隔开的三笔 = 3 个单位。
- ★ 注意粒度变细不等于"一笔事务一个字符"：一次 `typeTextUtf8` 插 4 个空格（Tab 缩进）仍是一笔。

## 五、撤销上限与 Tab 的最终口径（同日再往后）

### 1. 撤销栈的深度上限（做成可配置）

用户问"现在 undo 和 redo 的最大历史记录是多少" —— 查证结论：**原来没有任何上限**（`done_` /
`undone_` 都是无界的 vector，唯一的 clear 是提交时清重做栈）。取消合并之后这意味着栈按**字符**
增长，所以这一问来得正好。

查了一圈主流实现的默认值（用户要求"看看其他编辑器默认是多少"）：

| 实现 | 默认上限 | 超限行为 |
| --- | --- | --- |
| Word / Excel / PowerPoint | **100**（官方支持页：默认保存最近 100 个可撤销操作，可改注册表） | 丢最旧的 |
| Quill（网页富文本，最接近本场景） | **100**（`history.maxStack`） | **丢最旧的一条** |
| Photoshop | 50 个历史状态（可调到 1000） | 丢最旧的 |
| Illustrator | 100 | 丢最旧的 |

定：`EngineConfig::undo_limit = 100`（0 = 不限制），超出丢最旧的 —— 与 Quill 同一条口径。
★ **要知道的差别**：我们的粒度比 Quill 细（它另有 1 秒的合并窗口把连续输入并成一条），
所以同样 100 条覆盖的输入更短；嫌少就调这个数。

- 实现：`UndoStack::setLimit` / `trim`（`commit` 压栈后裁、`setLimit` 调小时**当场裁**）。
  重做栈不用单独裁 —— 它只由撤销栈弹出来，规模不可能超过上限。
- 配置链路：`EngineConfig::undo_limit` → `setConfig` / `setDocument` 转发给栈 →
  wasm 的 `setUndoLimit` / `undoLimit` → 宿主门面同名方法。
- 判据：`model_test` 1.3 两组（六笔留三笔、调小当场裁到 2、0 = 不限制、**撤的是最后两笔**）；
  `edit_test` 新增 **[36]**（配置项真的落到栈上 —— 引擎漏转发时只有这一节会红）；
  探针 `[16]` 新增 (h)（默认值 100 + 门面到栈一整条线）。
- **反向验证**：去掉 `commit` 里的 `trim()` ⇒ native **3 项红**（model 1 + edit 2，报出"实际 6"）。

### 2. Tab 定为"保持缩进"（用户选定）

用户看过现状（插 4 个空格、制表符零宽、模型预留了 `NodeKind::Tab` 但排版层没有制表位）之后
选了**保持现状**。于是把口径在四处写清，免得"文档模式 Tab = 制表符"那句设计表述被当成已实现：

- `engine_config.h` 的 `tab_spaces`：补上"制表符原子已预留但排版层不认，所以文档模式也插空格"。
- `engine.cpp` 的 `tabCaret`：文档模式不消费 Tab 是"那一步还没落地"，不是"已经插制表符了"。
- `edit_capability.h` 的 `tabFrom`：明确写"这个能力目前没有默认键位"。
- `app.js` 的 Tab 分支与 `index.html` 的页面说明：两种模式都是缩进；
  "Tab 插真制表符"与"Tab 跳下一个字段"都还没做。

## 七、大文档（2000 段）的内存账：一个 20 倍的坑（细节见 ENV.md）

用户追问"大文档呢，比如那个 2000 段的文档"。实测两条路（诊断 `out/_diag_big.mjs`）：

| 路径 | 帧 | 帧面积 | 每实例堆 | 装载 + 首次排版 |
| --- | --- | --- | --- | --- |
| 不设视口（整篇帧） | 1191 × 109540 | 130.46 Mpx | **1031.6 MB** | 1583 ms |
| 窗口 3 页（宿主正常路径） | 1191 × 5108 | 6.08 Mpx | **82.6 MB** | **115 ms** |
| 窗口化后滚到第 30 页 | 不变 | 6.08 Mpx | 82.6 MB（不涨） | — |
| 两个实例都装 2000 段 | — | — | **165.2 MB** | — |

每实例 82.6 MB 的构成：字体 16.9 + 引擎底与排版结构约 41.4 + 窗口帧 24.3。
（同期"只灌字体不装文档"是 36.3 MB ⇒ 2000 段文档本身约 46 MB。）

★ **坑在哪**：两条路是**同一份文档、同一个引擎**，只差宿主有没有调 `setViewportAnchor`。
`count <= 0` 就是整篇（代码里的默认），单页文档看不出问题，长文档直接把实例撑到 1 GB。
第一版诊断就是这么撞上去的 —— 只调 `relayoutAndPaint()`，没设视口，`frameHeight` 量出来
109540 px 才反应过来。宿主 `app.js` 在 boot 时设了（`app.js:270`），**产品宿主自己写极易漏**，
而且漏了不报错。已在 `engine.h` 的 `setViewportAnchor` 与 wasm 包装两处补上实测数字。

**对多实例结论的影响**：方案 A 依然合适；给产品宿主的两条硬要求 —— ①装载后必须设视口
②按 **82.6 MB/实例**（2000 段量级）估内存，多实例线性叠加。

## 八、参照 DCWriterLite 查证：字体怎么处理、多实例怎么布局（细节见 ENV.md）

用户问两件事：文档用不同字体是不是都要加载进来（看 DCWriter 怎么做）；它的内存布局为什么能
同页开很多实例。

**字体**：它的字**不在 wasm 里**，全在浏览器。`PageContentDrawer.EnsureFontInstall(fontNames,
element)` 是全部机制 —— 只处理"这份文档用到的字体名"；从全局表 `window.__DCFontSourceList`
（字体名 → URL）查地址，**没配 URL 的当系统字体用、不下载**（所以整个项目里一个字体文件都没有）；
配了 URL 的用 `new FontFace(name, 'url(...)')` + `document.fonts.add()` + `load()` 注册进
**浏览器进程级的字体集**（N 个实例共享一份）；加载完成后投 `FontLoaded` 任务触发重排重绘
——否则先用回退字体画的那一版会被当成定稿。度量走 `measureText`（带字宽缓存）、绘制走 `fillText`。

**实例模型**：Blazor 只有一个 .NET runtime（框架形态），多实例 = 同一 runtime 里的多个
`WriterControl` 对象（`private static int _CtlInstanceCounter`）。所以"同页很多实例"能成立，
是因为**最贵的两样都被共享了**：一份 runtime + 一份浏览器字体。它就是"一份 wasm + N 个引擎
对象"的形态 —— 即前面讨论的**方案 B**。

**为什么不能照抄**：把度量交给浏览器就等于放弃确定性排版 —— 我们那套"关缓存逐字节等价"的
判据、竖排与蒙文连写 shaping，都建立在自绘与自带字体之上。**能学的三条**（都不动渲染路线）：
① 按文档实际用到的字体加载（现在 demo 无条件装 3 个 = 20 MB）；② 字体子集化（16.9 MB → 1~3 MB，
收益最大）；③ 若将来支持"文档声明字体、按需拉取"，要配套异步补加载 + 加载完成重排。

**架构判据**：个位数实例 → 方案 A（现状可用、C++ 零改动）；十几二十个 → 方案 B（字体也能共享）。

## 九、"能共用的共用、能借的借用"实测（细节见 ENV.md）

用户要求：实例之间能共用的尽量共用，能管浏览器借的也借；并直接问"浏览器加载的字体我们不能
只用它的内存吗"。

**实测（诊断 `out/_diag_share.mjs`，三种写法 + 字体）**：
- wasm 字节**预取一次**、多实例复用（`wasmBinary`）：**可行** —— 每实例实例化 **85 → 33 ms**
  （plain 74/99 ms 对 36/31 ms）。
- 共享 `WebAssembly.Module`（`instantiateWasm` 钩子）：**不可行** —— 两次尝试都失败（一次 embind
  冲突、一次回调不被调用而挂起 20s）。
- 字体字节在 JS 侧存一份给所有实例：行，但**只省网络**；每实例仍要把 16.9 MB memcpy 进自己的堆
  （实测 5 ms 拷贝 + 7 ms 解析，堆 16 → 36.3 MB）。
- **借浏览器的字体内存：原理上不行** —— ①浏览器为渲染加载的字体不通过 JS 暴露字节（`FontFace`
  只给 status 与 `load()`）②wasm 沙箱只能读写自己的线性内存，没有"指向浏览器字体内存的指针"，
  不是缺 API 而是内存模型不共享 ③我们能灌进去靠的是 `fetch` 到的字节，与浏览器那份是两份拷贝。
  ⇒ 除非改走浏览器渲染路线（放弃自绘与确定性排版），字体只能在 wasm 堆里。

**踩到并记下的坑**：`CreateHEditor(arg)` 的**参数对象会被消费**（它就是 emscripten 的 Module）。
两次实例化复用同一个对象 ⇒ 第二次抛
`BindingError: Cannot register multiple overloads of a function with the same number of arguments`。
这个坑一开始被误读成"共享 module 不行"，把两件事分开测才看清。已在 `web/app.js` 的
`CreateHEditor` 调用处加注释（现在是字面量，天然满足；多实例宿主必须自己守住）。

**结论**：能共用的只有"wasm 字节"（省 60% 实例化时间）；字体真要共享只有方案 B（多引擎同实例、
共用一份 `FontLibrary`）。落地时机放在 `app.js` 工厂化那一步一起做。

## 十、DCWriter 是不是每实例一个 wasm 堆？——不是，只有一个（细节见 ENV.md）

用户追问。查证结论：**一个**。证据在 `Source/WriterControlForWASM_JavaScript.cs`：

```csharp
private static List<WeakReference<WriterControlForWASM>> _ControlInstances = new ...;
[JSInvokable]
public static DotNetObjectReference<WriterControlForWASM>
CreateWriterControlForWASM(string containerElementID) {
    var ctl = new WriterControlForWASM();      // 同一 runtime 里的普通对象
    ctl._ContainerElementID = containerElementID;

```

Blazor WASM 只有一个 .NET runtime = 一个 wasm 实例 = 一块线性内存；控件对象都在这块堆上，

"另一个编辑器的文档莫名其妙坏了"，这类 bug 极难定位。所以方案 A / B 的对比必须把
**隔离性**单列一栏（表见 ENV.md）。

## 十一、字体族与"豆腐块"：查证与结论（2026-10-14）

用户三连问：① 用户看到豆腐块那还能行了？② 一个文档里又有宋体又有微软雅黑，怎么处理？
③ 像 DCWriter 有几十种字体可选，子集化能做？

### 1. 豆腐块的根因：**回退链是空的架子**

- `FormatRun` / `BlockSpec` 都有 `fallback_font_indices`，`layout.cpp:452-457` 也在拼 chain、逐字按 cmap
  切段（`itemizeByFont`）—— **机制齐备**；
- 但**没有任何地方填 `fallback_font_indices`**（编译层搜 `font_index =` 一处都没有）⇒ **链长恒为 1**，
  等于没有回退；
- `fallback.cpp:92-94`：链里没有能提供该字形的 face 时**落回 `chain[0]`（主字体）**⇒ 主字体没这个字
  ⇒ `.notdef` = **豆腐块**，同时 `missing_count` +1（`statsJson.missingGlyphCount`，现在只有计数、没有清单）。

### 2. 多字体文档：缺的是"字体名 → 资源 → 候选链"那一层

- `CharFormat::font_index` 存的是**字体库下标（int）**，注释原文："字体（引擎侧是字体库下标；**字体名与
  回退链到 1.6 的样式表再定**）" —— 而 1.6 落地的只有 `ParaFormatPatch`/`StyleSheet`/三层解析，
  **字体名与回退链没做**；
- `FontLibrary` 只有 `addFaceFromMemory(name, ...)`（name 存进 `FontFace::path_`），**没有 byName / indexOf**；
- ★ **wasm 里没有系统字体**（UNS Editor 源码注释原文 "no system fonts in WASM"）⇒ 文档里写"宋体"，
  自绘路线下**必须映射到一份真实字体文件**；而"宋体""微软雅黑"是**中易/微软的商业字体，不能随便分发**
  —— 这是法务约束，不只是技术约束。参照 Word 的 **font substitution / font mapping**：文档写一家、
  产品装另一家，按规则替换；替换表也拿不到就落到默认链。

### 3. "几十种字体可选" 与子集化

- DCWriter 的"几十种"是**字体名列表**（`fontToDetect` / `baseFonts` 用 span 宽度对比法**枚举系统字体**），
  只有配了 URL 的才下载（`window.__DCFontSourceList`），**其余零下载** —— CSS 字体路线白拿浏览器红利；
- 自绘路线的算术（本机实测）：全量 17.77 MB/族、GB2312 子集 **4.09 MB/族**（23%）。N 种字体 =
  N × 全量 或 N × 子集 —— **量级没变，还是 N 份**；且可编辑文档里用户随意输入，子集外必豆腐块；
- ⇒ **"可选字体多"不花钱，"同时加载的字体多"才花钱**。正解不是子集化，而是
  ① **字体名与资源解耦**（替换表 + 别名）② **按文档实际用到的字体加载**（一份文档通常 1~3 种）
  ③ **链尾必须是全量兜底字体**（保证永不豆腐块）④ 缺字清单（现在只有计数）作为补加载前提。

### 4. 附带

`MEMORY.md` 超限被截断，已精简重写（181 行 → 120 行；备份 `out/_MEMORY.md.bak-2026-10-14d`）：
把可搬进卫星文件的细节压成索引，新增"字体是自绘路线的成本项与定位项"一节。

## 十二、按需加载字体：Skia / HarfBuzz 的现成入口（2026-10-14 查证，**修正上一轮的判断**）

用户问："Skia 和 HarfBuzz 怎么使用字体数据？如果定制化把它们改成 load(font, id) 这种按需加载，
完整字体放硬盘、用的时候再读、做好加载卸载，有没有可行性？"

上一轮我说"Skia 的 FreeType 后端不用 FT_Stream ⇒ 从硬盘按需读走不通"——**那是错的**。
本轮直接读 vendored 的 Skia 源码（`.toolchain/skia/src/skia-main`），证据如下。

### 1. Skia 有两条路，开关是 `getMemoryBase()`

`src/ports/SkFontHost_FreeType.cpp` 的 `SkFontScanner_FreeType::openFace()`（约 2091-2120）：

```cpp
const void* memoryBase = stream->getMemoryBase();
if (memoryBase) {
    args.flags = FT_OPEN_MEMORY;              // ← 内存流：整份常驻
    args.memory_base = ...; args.memory_size = stream->getLength();
} else {
    ftStream->size = stream->getLength();
    ftStream->descriptor.pointer = stream;
    ftStream->read  = sk_ft_stream_io;        // ← 流：按需 seek+read
    ftStream->close = sk_ft_stream_close;
    args.flags = FT_OPEN_STREAM;
    args.stream = ftStream;
}
FT_Open_Face(...)
```

而 `sk_ft_stream_io`（同文件 278-300）就是**用户设想的那个 load**：

```cpp
static unsigned long sk_ft_stream_io(FT_Stream ftStream, unsigned long offset,
                                     unsigned char* buffer, unsigned long count) {
    SkStreamAsset* stream = static_cast<SkStreamAsset*>(ftStream->descriptor.pointer);
    if (count) { if (!stream->seek(offset)) return 0; count = stream->read(buffer, count); }
    return count;
}
```

`FaceRec` 持有的是 `std::unique_ptr<SkStreamAsset> fSkStream` + `FT_StreamRec`，**不是 SkData**；
`SkTypeface_FreeTypeStream` 只持 `SkFontData`（含 stream），`onOpenStream` = `fData->getStream()->duplicate()`，
`onMakeFontData` = 拷一份 SkFontData（指针级）⇒ **全程不把数据读进内存**。

**入口是公开的**：`SkFontMgr::makeFromStream(stream, args)`（`src/core/SkFontMgr.cpp:193`）
→ `SkFontMgr_Custom::onMakeFromStreamArgs`（`src/ports/SkFontMgr_custom.cpp:208-211`）
→ `SkTypeface_FreeType::MakeFromStream`。另有 `onMakeFromFile` → `SkStream::MakeFromFile(path)`（现成）。
`SkStream::getMemoryBase()` **缺省返回 nullptr**（`include/core/SkStream.h:145`），只有 `SkStreamMemory`
强制非空 ⇒ **我们只要写一个不继承 SkStreamMemory 的 SkStreamAsset 子类，就自动走 FT_OPEN_STREAM**。

### 2. HarfBuzz 侧同样是现成的

`third_party/harfbuzz/src/hb-face.h`：`hb_face_create_for_tables(hb_reference_table_func_t, user_data,
destroy)`（第 106 行）+ `hb_reference_table_func_t`（第 102 行，按 hb_tag_t 提供表）—— 官方的
**表级按需**钩子。另有 `hb_face_create_from_file_or_fail`（第 72 行）。

### 3. 我们现状（为什么现在是全量）

- `src/core/render/bitmap_skia.cpp:222-233`：`SkData::MakeWithProc(...)` + `font_mgr->makeFromData()`
  ⇒ 包成 `SkMemoryStream` ⇒ `getMemoryBase()` 非空 ⇒ **FT_OPEN_MEMORY**（整份常驻）；
- `src/core/text/font.cpp:34`：`hb_blob_create(..., HB_MEMORY_MODE_READONLY, ...)` ⇒ HarfBuzz 也全量。

### 4. 结论：接线 > 改源码，但性能账必须实测

**不必改 Skia / HarfBuzz 一行源码**，要做的是三处接线：
① 写一个按需 `SkStreamAsset`（`getMemoryBase()` 留空）→ 接 `SkFontMgr::makeFromStream`；
② HarfBuzz 用 `hb_face_create_for_tables` + 自解析 SFNT 表目录 + provider 自缓存；
③ 存储层（wasm 内 = WASMFS/IDBFS/OPFS 或 MEMFS）。

**性能账（真问题，且只能实测）**：字体访问是**随机小读、高频** —— FreeType 按字形读 `glyf`/`loca`，
一页 2000 字 ≈ 数千次 read；而 `cmap`/`hmtx`/`loca` 这些**会被整表加载**（省不掉），能省的只有
`glyf`/`CFF`/`gvar` 里未用到的部分与未用表。每次 read 若跨 JS 边界是 µs 级，而常驻内存访问约 100 ns。

**建议的最小实验（零风险、可证伪）**：写一个**统计访问足迹**的包装 stream（不改数据布局），
跑一次"装载 + 排版一页"，得出真实足迹：只碰 10~20% ⇒ 按需有意义；碰 80%+ ⇒ 老老实实常驻。

**另：用户说的"做好加载和卸载"这一半独立成立**——`FontLibrary` 只有 add、**没有 removeFace**；
卸载还要清 `bitmap_skia.cpp` 的 `typefaces` 缓存与字形缓存（本轮已确认 `bitmap_skia.cpp:154-176` 两处缓存）。

## 十三、按需加载的性能怎么保证：表构成实测 + 分层缓存（2026-10-14）

用户否掉"值不值"的讨论（**按需是必须的能力，没有值不值一说**），问"按图里的建议能否解决随机加载的
性能问题"。图（WASM 侧 OPFS 接入）：传统 Emscripten OPFS VFS 每次 I/O 都代理到别的线程 + 带外通道
= "性能消亡之地"；推荐 **SAHPool VFS 或 WasmFS + 同步句柄**（在 Worker 里用 OPFS 同步访问句柄，
绕开线程边界，I/O 是传统方案的 3~4 倍，且**优势随批次增大而扩大**）；社区反馈多线程并发读同一大
文件时 WASMFS 的 OPFS 后端可能锁竞争，不如加载到内存的 IDBFS；单线程顺序解析 ⇒ WasmFS/SAHPool
理想。

### 1. 表构成实测（决定性数据）

`NotoSansSC-VF.ttf` 表数据合计 **16.95 MB**：

| 表 | 大小 | 占比 | 能否按需 |
| --- | --- | --- | --- |
| `glyf` | 9.68 MB | **57.1%** | ✅ 按字形（`loca` 索引） |
| `gvar` | 6.75 MB | **39.8%** | ✅ 按字形 |
| `loca` | 0.12 MB | 0.7% | ❌ 整表（`glyf` 的索引） |
| `hmtx`/`vmtx` | 各 0.12 MB | 0.7% | ❌ 整表 |
| 其余（GPOS/GSUB/HVAR/cmap/name/head…） | < 1 MB | ~1% | ❌ 整表，但很小 |

⇒ **97% 的体积在"按字形可寻址"的两张表里**，必须整表的部分**不到 1 MB**。
⇒ **按需的收益上限 ≈ 16 MB（94%）**；"省不掉"的那部分可忽略。（上一轮说"cmap/hmtx/loca 省不掉"
方向对，但**量级被我高估**了。）

### 2. 图里的建议定位：解决"能不能"与"单次开销"，**不解决"次数"**

- 主线程**没有同步文件 I/O**（`createSyncAccessHandle` 仅 Worker；IDBFS 是异步），而
  `sk_ft_stream_io` / FT_Stream 是**同步回调** ⇒ 要"从硬盘读"，WASMFS+OPFS / SAHPool（或整个引擎
  搬进 Worker）是**前置条件**，不只是优化；
- 但它自己写"优势随批次增大而扩大"，而字形读是**最小批次**（`loca` 项 4 字节、轮廓几十~几百字节）
  ⇒ 3~4 倍在小批次下会缩水；
- 一页 2000 字形 × 2~3 次读 ≈ **数千次 I/O** —— 文件系统再快也不改**次数**。

### 3. 性能靠分层缓存（挂载点现成）

```
FT_Stream / hb_reference_table 的同步读请求
  ↓ ① 小表常驻：loca/hmtx/vmtx/cmap/GSUB/GPOS/head…（< 1 MB，一次读全）
  ↓ ② 块缓存：glyf + gvar 按固定块（如 64 KB）LRU，1~3 MB
  ↓ ③ 存储：MEMFS（先）→ OPFS SAHPool / WASMFS（后）
```

挂载点：`sk_ft_stream_io`（需自定义 `SkStreamAsset`）与 `hb_reference_table_func` ——
**两个回调都在我们自己的代码里**。预期常驻 **2~4 MB**（vs 现在 16.9 MB）。

### 4. 性能判据（不是"值不值"）

① 缓存命中率 **> 95%**；② 每页存储读次数 **个位数~几十**（不做缓存是数千）；③ 每帧 I/O **< 1 ms**
（16.7 ms 预算）；④ 常驻 **≤ 4 MB**。

### 5. 现状与前置代价

现状实测：**无 `-pthread`、无文件系统**（CMakeLists 的 wasm 参数只有
`EXPORTED_RUNTIME_METHODS=HEAPU8,HEAPU32`）、**宿主无 Worker**（`web/` 只有 app.js + index.html）。
上 OPFS 同步句柄要付：`-pthread` + `PTHREAD_POOL_SIZE` ⇒ SharedArrayBuffer ⇒ 部署发
**COOP: same-origin + COEP: require-corp**；或把引擎整体搬进 Worker（OffscreenCanvas + 消息协议）。
★ **折中起点**：先用 **MEMFS**（默认文件系统、同步可用、零部署代价）把"①② + 按需接口"整条链路
验对，再换存储后端（那时才付 pthread/COOP-COEP）。风险分离。

## 十四、"引擎搬进 Worker"的收益与代价评估（2026-10-14）

用户问："如果引擎搬进 worker 会有什么问题，这样不阻塞主线程不是更好吗？"

### 1. 收益是真的，且可量化

主线程上还压着的长任务（前几轮的账）：**回车 34.4 ms**（其中 paint 24.5 ms 是 wasm 里"窗口那 2 页
整页重画"）＋ **装载 2000 段 115 ms** ＋ 滚动帧 p50 16.7 ms。搬 Worker ⇒ 这些不再占主线程
⇒ 输入/滚动更跟手。顺带还满足"**同步文件 I/O 只能在 Worker**"这个约束（OPFS 的
`createSyncAccessHandle` 仅 Worker 可用）。

### 2. 四处耦合（含一处**修正**）

| 耦合 | 位置 | 搬 Worker 后的影响 |
| --- | --- | --- |
| **IME**（最硬） | `ta = $('ime')`（app.js:47）、composition 三件套（541-543）、宿主用 `pagesEl/stageEl.getBoundingClientRect()` 算位置（656/840/1232/1435） | 候选框定位要"光标在屏幕上的坐标"（引擎派生量）⇒ 新增一条光标几何通道（往返或推送）。★ 几何本身还在：`transferControlToOffscreen` 后 canvas 元素**仍有布局盒** |
| **`preventDefault` 的同步语义** | `onKeyDown` 三处（747 Ctrl+Z / 804 普通字符 / 873） | **唯一无法异步替代的**：判断"这个键归不归引擎"要等 Worker 就来不及 preventDefault ⇒ 必须把"按键归属"留在主线程（或预推模式状态） |
| canvas 不可逆 | `getContext('2d',{alpha:false})`（129）＋ `putImageData`（618） | ★ **修正：几乎无影响** —— 探针的像素统计读的是 `window.__heditor.rawFrame()`（edit_probe.mjs:562/584），**不读 canvas**；`frameCanvasProxy.getContext()` 本就返回 null（app.js:110）。主线程若要做导出/打印，走引擎接口即可（那才是权威像素） |
| **探针 465 处同步调用** | `grep -c "eval(" scripts/edit_probe.mjs` = **465**，256 项判据全同步调 `window.__heditor.*` | 真正的改动面。可用"主线程影子状态 + 异步 RPC"的 shim 把改动压小，但**影子一致性**是新风险 |

### 3. 一个澄清

**搬 Worker 本身不需要 COOP/COEP**（postMessage 够用）；只有用 SharedArrayBuffer / 同步句柄才需要。
所以"搬 Worker"与"上 OPFS 同步句柄"是**两个独立的决定**，别混在一起。

### 4. 按目标选最便宜的路

| 目标 | 最便宜的路 |
| --- | --- |
| 同步文件 I/O（按需字体） | **只搬 I/O**：pthread + SAB + WASMFS/SAHPool —— 引擎/canvas/事件/IME/探针**全不动**，只改构建参数与部署头 |
| 输入不被长任务卡 | 只剩渲染那块（paint 24.5 ms）⇒ 而渲染搬走 ≈ 引擎搬走，这是**唯一"必须搬引擎"的动机** |
| 首次装载 115 ms | **任务卸载**或**分帧 yield**（我们的画布本来就是按页切的，宿主可以按页调、页间让出主线程）—— 不必搬引擎 |

### 5. 结论与顺序

若最终目标确实是"输入绝不卡"，搬 Worker 是正解，但顺序要对：
① **先做"主线程影子状态 + 异步 RPC"**（让探针几乎不改，这是前提也是最大隐性成本）；
② **按键归属表留主线程**（解决 preventDefault）；
③ **光标几何通道**（解决 IME 候选框）；
④ 最后搬引擎 + OffscreenCanvas。
若目标只是"按需字体" ⇒ **别搬引擎，只搬 I/O**。
★ 多实例：搬 Worker **不解决字体共享**（每个 Worker 一份堆）；一页多实例 = 多 Worker。

## 十五、SharedArrayBuffer：Worker 能不能用、能不能多实例共享（2026-10-14）

用户问："worker 不能用 SharedArrayBuffer 吗，这种不能多实例共享内存吗？"

### 1. Worker 能用 SAB，但门槛是**页面的 cross-origin isolation**

SAB 要求 **`COOP: same-origin` + `COEP: require-corp`**，而这是**整个 agent cluster 的属性**
（页面 + 它创建的 Worker 一起）：COI 页面创建的 Worker 能用；**非 COI 页面里主线程与 Worker 都拿不到**
（`new SharedArrayBuffer()` 抛，`postMessage` 传 SAB 也抛 DataCloneError）。
⇒ **"用不用 Worker"与"能不能用 SAB"是两件独立的事**；要 SAB 就必须发那两个头。
★ 澄清我上一轮"搬 Worker 不需要 COOP/COEP"——那是指**不用 SAB**时（postMessage + transferable
零拷贝够用）；要用 SAB 则无论主线程还是 Worker 都要 COI。

**我们现状（实测）**：`scripts/dev_server.py` 只发 `Cache-Control`/`Pragma`/`Expires`，**没有 COOP/COEP**
⇒ 不是 COI ⇒ **现在拿不到 SAB**；CMakeLists 里 wasm 参数只有 `-sMODULARIZE=1`，**没有 pthread /
SHARED_MEMORY / IMPORTED_MEMORY**；宿主与探针里 `SharedArrayBuffer` **一处都没用**。

### 2. SAB 共享的是"线程之间"，**不是"wasm 实例之间"**

关键约束：**wasm 只能访问自己的线性内存**，它无法解引用"另一个 SAB 里的指针"。
SAB 的真实用途是让**一个** wasm 实例的线性内存变成 shared ⇒ 别的线程（Worker）能**直接写进去（零拷贝）**
← 这正是 WASMFS / SAHPool 的形态（一个实例 + 一个 I/O worker）。

要让 N 个 wasm 实例共享同一份字体，只有两条路，**都不通或与 SAB 无关**：
1. N 个实例**导入同一块** shared memory（`-sIMPORTED_MEMORY` + shared）：它们会**共用同一个堆与
   malloc arena**，两套 dlmalloc 状态互相踩 ⇒ 实践上不成立。（pthread 是"一个实例多线程"，不是
   "多实例共享"。）
2. **一个 wasm 实例里放 N 个引擎对象**（方案 B）⇒ 共用一份 `FontLibrary` ⇒ **真共享，与 SAB 无关**。

### 3. 四个"共享"诉求，只有一个真的要 SAB

| 诉求 | 手段 | 要 SAB 吗 |
| --- | --- | --- |
| 字体字节在**网络/磁盘**上只一份 | HTTP 缓存 / OPFS | ❌ |
| 字体字节在**同一 wasm 实例内多引擎**间共享 | 方案 B（共用 `FontLibrary`） | ❌ |
| 位图/帧跨线程传递 | `postMessage` **transferable**（所有权转移，零拷贝） | ❌ |
| **I/O worker 直写 wasm 线性内存** | `WebAssembly.Memory({shared:true})` = SAB | ✅ |

### 4. ★ 修正 + 第三条路：MEMFS 比想的更有用（**上一轮我说错了**）

上一轮我说"MEMFS 的数据仍在 wasm 堆里、不省内存"——**不准确**。Emscripten 的 MEMFS 把文件内容放在
**JS 侧**（node.contents 是 JS 的 `Uint8Array`），wasm 读文件时才拷进线性内存。于是：
- `FS.createDataFile(parent, name, data, canRead, canWrite, **canOwn**)` 的 `canOwn = true` 语义是
  **直接持有、不拷贝**（**待验证**）；
- ⇒ 字体字节 = **JS 侧一份 ArrayBuffer**，**可被多个实例共享**（建多个视图 / 多次 createDataFile）；
- ⇒ 每实例的 wasm 堆只放"用到的块"（块缓存 1~3 MB）；
- ⇒ **零 COI、零 pthread、零 Worker**。
代价：那 17 MB 常驻 JS 堆（但**多实例只占一份**）；"字节真在硬盘上、内存一份不留"这一半没有。

★ 结论：**若诉求是"省 wasm 堆内存"，MEMFS + 共享 ArrayBuffer + 块缓存就够，不需要 SAB**；
只有诉求是"字节真在硬盘、内存里一份都不留"才需要 OPFS 同步句柄 ⇒ 才需要 SAB ⇒ 才需要 COI 头。
（要加 `-sFORCE_FILESYSTEM` 才有文件系统，目前构建没开。）

## 十八、共享 wasm 堆崩溃后有没有转储（2026-10-14 查证）

用户问：如果实例共用一个 wasm 堆，崩溃后有类似 C++ 的转储吗？

### 1. wasm 里没有"段错误"，也没有 OS 级 core dump

崩溃形态只有 **trap**（越出线性内存、非法指令、除零、unreachable、栈溢出、间接调用类型不符），
表现为 JS 的 `RuntimeError`、**可捕获**；trap 后该实例不能继续执行，但**线性内存仍可读**
⇒ "事后解剖"有空间，但没有 OS 层的 core dump（wasm 里没有进程与信号）。

### 2. ★ 关键：wasm 的沙箱边界是"线性内存边界"，不是"对象边界"

- 越出线性内存 ⇒ 必然 trap（不会静默破坏别的进程）；
- **但线性内存内部的野指针与越界写是静默的**。官方文档的佐证：Emscripten 里
  **解引用空指针不会立即段错误**（0 是 wasm 内存里的正常地址），只有开 `ASSERTIONS` 时
  才用一个"地址 0 的魔法 cookie"在程序退出时检测到它被写过 —— 而且只检测写、不检测读、
  也不告诉你写在哪。
- ⇒ **共享堆里 A 引擎写越界写进 B 的区域不会 trap**（仍在内存范围内）。
  **共享堆 = 丢掉 trap 保护 + 拿不到 OS core dump，两头不占。**
  症状：另一个编辑器状态莫名其妙坏了、不复现、不带栈。

### 3. 能补的手段（按代价从低到高）

| 手段 | 作用 | 代价 |
| --- | --- | --- |
| `-sASSERTIONS=1/2` | 常见错误的运行时检查；退出时检测"地址 0 被写" | 小（默认 -O0 开、优化关） |
| `-sSTACK_OVERFLOW_CHECK=1` | 栈末写魔法值，检测栈越界 | 小 |
| `-sSAFE_HEAP=1` | Binaryen 插桩的额外内存检查，定位解引用 0 与对齐问题 | 中 |
| `-fsanitize=undefined`（+ `-fsanitize-minimal-runtime`） | **精确到行号**；minimal runtime 是为生产设计的 | 中 |
| `-fsanitize=address`（ASan） | 抓缓冲区溢出与堆越界，**支持多线程**，**连 JS 侧越界访问也抓** | 大：要 `INITIAL_MEMORY>=64MB` 或开 growth；只能调试/CI |
| 自制"事后转储" | trap 时导出 `HEAPU8` 整体 + 调用栈（需 `-gsource-map`）⇒ 离线分析 | 小（约 50 行 JS） |
| **分区 arena + canary** | 每个引擎一份独立 arena，边界放魔数定期校验 ⇒ 能检测越界并定位是哪个引擎 | 校验开销 |

★ **分区 arena 还是方案 B 的必要配套**：共享堆里两套 dlmalloc 状态会互相踩（前面只提了
"70 个导出函数加句柄"，漏了这条）。给每个引擎一个自定义 arena allocator 既解决分配器冲突，
也天然提供 canary 分区的落点。

### 4. 我们现状

wasm 构建**全关**（CMakeLists 里没有 ASSERTIONS / SAFE_HEAP / STACK_OVERFLOW_CHECK / source map），
宿主只有 `window.addEventListener('error')` 与 `unhandledrejection` 收集页内错误。
建议加一个**调试预设**（开 ASSERTIONS + STACK_OVERFLOW_CHECK + `-gsource-map`），不影响 release。

## 十九、共享堆 vs 多堆：取舍的口径要摆正（2026-10-14）

用户的判断："出现内存问题说明代码有问题吧？那这种一个堆和多个堆感觉没太大影响，哪个都有可能坏，
也可能一起坏。"

**对的部分（要承认）**：内存越界/野指针**是代码 bug**，不是架构问题；**单堆多堆都不降低它的概率**。
所以"用架构来防 bug"是错的动机 —— 这是主要投入方向（判据、反向验证、工具链）该干的事。

**不成立的部分**：差别不在"会不会坏"，而在**坏了能碰到谁**，这是三条不对称：

1. **故障域不对称（本质）**：多堆时每个实例是**独立地址空间**，越界再远也只能落在自己那一块里
   ⇒ 故障域**物理上锁死在 1**；单堆时所有引擎共享一块地址空间 ⇒ 一次越界可能落在**别人的活跃
   数据**上 ⇒ 故障域 = N。★ 所以"一起坏"**不是两边都可能 —— 它是共享堆独有的性质**（多堆物理
   上做不到）。
2. **失败形态不对称**：多堆下越界若逃到**自己的线性内存之外** ⇒ **trap**（可捕获、有栈、内存事后
   仍可读）；单堆下"逃到邻居那里"比"逃出内存"容易得多 ⇒ **静默损坏**（无信号、无栈、可能落盘）。
   同一批越界 bug，多堆下有一部分当场响，单堆下全部悄悄坏。
3. **可诊断性不对称**：trap 有现场可抓；静默损坏没有现场（只有 canary 周期校验能"事后发现"，
   且不知道是何时写的）。

**用户直觉里的真判断**：若内存 bug 率高到"必然发生"，该修的是工具链与判据，不是换架构。
⇒ 两件事分开做：① 用工具把 bug 率压到低（主要投入）② 用故障域限住残留 bug 的代价（保险）。
★ 架构选择的前提是"代码可能有 bug 且我们无法证明没有"（C++ + Skia/HarfBuzz/FreeType 第三方 +
快速演进）。医疗场景的判据是**数据完整性**：一个实例坏 vs N 个一起坏且不知哪个是对的，差别巨大。

## 二十、wasm 调试档：预设 + 让 source map 真的映射到本工程的源码（2026-10-14）

用户点头"先加吧"（指上一轮建议的调试预设）。

### 1. 加了什么

| 位置 | 内容 |
| --- | --- |
| `CMakeLists.txt` | `option(HEDITOR_WASM_DEBUG ...)`；wasm 段条件追加 `-g2 -gsource-map -sASSERTIONS=1 -sSTACK_OVERFLOW_CHECK=1` |
| `CMakePresets.json` | `wasm-debug` 三处（configure / build / workflow），照 `wasm-noskia` 的先例：独立 binaryDir `build/wasm-debug` |
| `web/app.js` | `?wasm=debug` 切换产物目录（`WASM_DIR`），默认仍是交付档 |
| `scripts/verify_web.ps1` | 新增 `-Wasm <档名>` 参数（默认 wasm），拼进页面 URL 并检查对应产物 |

用途：trap（越界、非法指令、栈溢出）时能拿到**可读的 C++ 栈与源码位置**，而不是一句
"RuntimeError: memory access out of bounds"。共享堆那种"越界写进邻居不 trap"它抓不到（那要 ASan），
但把"响的那一半"变可读。

### 2. 踩到的两个坑

① **新 preset 配置失败**（`Configuring incomplete, errors occurred!` + `failed with: unknown error`）：
   CMake 探测 ninja 时选中了 PATH 里**第一个** `D:/Develop/depot_tools/ninja`，而**那个文件根本不存在**
   （坏链，`No such file or directory`）；release 档不踩是因为它的 cache 里存着当初探测到的
   `.toolchain/ninja/ninja.exe`。
   修法：`wasm-debug` 预设里显式 `"CMAKE_MAKE_PROGRAM": "${sourceDir}/.toolchain/ninja/ninja.exe"`
   （与 release cache 一致，跨机器可复现）。
② ★ **source map 里没有本工程的源码**：只在**链接期**加 `-g2` 时，`.wasm.map` 的 318 个源文件
   **全是 emsdk 自带的**（libc++ / embind），`src/core/**` 一个都不在 —— 等于拿不到自己的源码位置。
   修法：**编译期**也要带行号 —— 在 `heditor_target_flags` 里，`EMSCRIPTEN AND HEDITOR_WASM_DEBUG`
   时给每个 target 加 `-g2`。（Skia 是预编译静态库，它的内部不会有映射，可接受；关键是自己那层。）

### 3. 验证

- 调试档跑浏览器探针：**268 项全绿**（断言 + 栈检查不破坏功能）
- 交付档不受影响：重新构建后仍是 **3440 KB**、**没有 `.map`**（默认档不带调试信息）
- 符号在：`EditorEngine` / `FontSource` / `loadFontFromFile` 都能在 wasm 里找到（`-g2` 的 name section）
- 体积：调试档 wasm 4603 KB / js 194 KB（交付档 3440 / 83）

### 4. 补记：`-g2` 不够，要 `-g`

- 编译期加 `-g2` 后**编译命令确实带了它**（41/42 个 TU），但 `.wasm.map` 的 sources 仍是 318 个，
  **全是 emsdk 自带的**，本工程一个 .cpp 都不在 ⇒ `-g2` 不足以让 `-gsource-map` 收集行号。
- 换成 **`-g`**（编译期与链接期都是）之后：sources **473 个**，其中 **63 个是本工程的**
  （`../../../src/core/engine/engine_stats.h`、`.../src/core/utils/types.h` …）✓
- **代价**：wasm 4603 KB → **16456 KB**（DWARF 进了 wasm），且 em++ 报
  `warning: running limited binaryen optimizations because DWARF info requested`
  —— 链接期优化受限（只影响调试档，不影响交付档）。
- 想再压体积可以换 `-gline-tables-only`（只留行号表，正是 source map 要的）——**未试**，
  留作后续；当前 `-g` 已经能用，调试档也不走网络分发。

## 二十一、方案 A 下"共用字体"到底行不行：实测（2026-10-14）

用户问："方案 A 就没有任何办法能共用字体内存了吗？" —— 前面我说得太粗，**实测下来答案是
"能共用的已经共用了，而且比我说的彻底"**。

### 1. 实测（`out/_diag_fontshare.mjs`，3 个实例）

| 项 | 实测 |
| --- | --- |
| 同一个 `Uint8Array` 交给两个实例的 MEMFS（`canOwn=true`） | **`same_buffer: true`** ⇒ **零拷贝共享** ✓ |
| 按需装载（骨架 + 块缓存）后各实例 wasm 堆 | **16 MB**（连 `INITIAL_MEMORY` 都没撑破） |
| 装 1500 段文档并排版后 | **仍是 16 MB** |
| 整份装载的对照实例 | **36.3 MB**（涨 20 MB ≈ 字体本体） |
| 三个实例合计（2 按需 + 1 整份） | **68.3 MB**（若三个都整份则是 108.9 MB） |

### 2. 机制

`FS.createDataFile(parent, name, data, canRead, canWrite, **canOwn=true**)` 在 canOwn 为真时
**直接持有、不拷贝** ⇒ **多个实例的 MEMFS 节点可以指向同一个 ArrayBuffer**。

⇒ **方案 A 能共享的**：① 字体字节本体（网络/磁盘/JS 侧一份，多实例零拷贝引用）；
② 骨架（0.4 MB，各解析一份，很小）。
⇒ **只有"用到的字形数据工作集"必须各一份**（≤ 3.3 MB）—— wasm 线性内存互不可见，这是物理边界。

### 3. 剩下的两条"理论上能共享"的路，都不值

- **共享 `WebAssembly.Memory` + 手工分区**：要定制 emscripten 的堆布局（各实例的 sbrk 范围），
  且一旦越界就是静默损坏（前面第十八、十九节讨论过）。
- **multi-memory 导入第二块只读字体内存**：需要给 Skia/HarfBuzz 的每次访问加 address_space 标注
  ⇒ 改它们的源码。
⇒ 两条的收益上限都只有 **3.7 MB/实例**。

### 4. 重算 A 与 B 的账（按需之后）

- A 总 = 字体一份（JS 侧共享）+ N × (文档 + 位图 + **3.7 MB**)
- B 总 = 字体一份（wasm 堆里共享）+ N × (文档 + 位图)
- ⇒ **A 只比 B 多 3.7 MB/实例**（N=3 时 11 MB）
- 而 B 的代价：70 个导出函数加句柄 + 分区 arena + 诊断能力退化 + 两套 dlmalloc 互踩风险
- ⇒ **为 3 个实例省 11 MB 去改整个引擎架构，不成立**。方案 A（配按需）在内存上基本追平 B。

★ 另注：按需还让"每实例初始内存"可以放心定在 16 MB（骨架 + 缓存 + 文档装得下），
不必为字体本体预留 —— 整份装载那条路才需要涨到 36 MB。

## 二十二、"字体数据在一页下只有一份"：诉求澄清与三条路（2026-10-14）

用户澄清了我上一轮的偏差：**不是"JS 侧共享一份拷贝"**（那是 MEMFS 的产物，换成 OPFS 之后那份
ArrayBuffer 根本不存在了），而是 **"字体数据在一个页面下只有一份"** —— 内存里的那一份。

### 1. 先把"一份"拆成两处看

- **磁盘/传输层**：一份是天然的 —— CDN 一份、HTTP 缓存一份、OPFS 一份。这一层**已经成立**。
- **内存层**：方案 A 下每个实例把"自己用到的块"拷进**各自的线性内存** ⇒ N 份工作集
  （实测 3.7 MB/实例，其中骨架 0.4 MB 是必需的）。
- ⇒ 要"内存里只有一份"，**唯一机制是共享内存** —— wasm 线性内存互不可见，这是物理边界，
  不是"没实现"。

### 2. 三条路与查证现状

| 路 | 现状 | 代价 |
| --- | --- | --- |
| **multi-memory**（多导出一块只读内存） | 浏览器：Chrome/Edge **120+**、Firefox **125+**、Opera 106+、Samsung 25+ **已支持**；**Safari 不支持**（STP 250 已实现，stable 未发）；Node/Deno 不支持。Emscripten：**工具链支持有限** —— 维护者明确回复过"C++ 只有一个统一地址空间，堆指针与栈指针无法区分，load/store 都走同一块 memory" | 我们的字体访问是**拷贝式回调**（`FT_Stream.read` 拷进调用方给的缓冲、`reference_table_func` 返回表 blob），**从不需要长期持有字体字节的指针** ⇒ 理论上只需让 `FontStorage::readAt` 能读 memory 1，Skia/HarfBuzz **一行都不用改**（C++ 侧要 `address_space` 标注，clang 对该标注在 wasm 上的支持程度待查） |
| **side module（动态链接）** | Emscripten 官方给"多模块共享一个地址空间"的答案：`-sSIDE_MODULE`，由主模块负责加载，各模块有自己的 `__memory_base` / `__stack_pointer` | 构建形态大改（引擎编成 side module、宿主变主模块）；多个同构 side module 实例的支持度待查 |
| **共享 `WebAssembly.Memory` + 手工改 sbrk 起点** | `-sIMPORTED_MEMORY` + 实例化后在 JS 侧改各实例的 sbrk 指针，让两套 dlmalloc 从不同起点分配 | hack、依赖 emscripten 内部布局、且**越界=静默损坏**（在共享内存里） |

★ 公开警告（StackOverflow 那条讲得最直白）：共享同一块 memory 的两个模块**会互相覆盖对方的
malloc 缓冲** —— 与前面"两套 dlmalloc 互踩"是同一件事。

### 3. 判断

- 三条路**都能**达成"内存里一份"，都不是"没有办法"；但都要改内存模型。
- 收益上限 = **省掉每实例的工作集**（3.7 MB，其中 0.4 MB 必需）。
- ⇒ 值不值只看一个判据：**同页实例数 × 3.7 MB** 与"改造代价 + Safari 不支持 multi-memory"相比。
  N=5 时是 18 MB，N=10 时 37 MB —— 到这里才值得认真考虑。

## 二十三、一个字占多少字节，以及 64 KB 的块到底浪费多少（2026-10-14 实测）

### 1. 一个字的字节数（fontTools 读 `loca` 逐个字形算）

**轮廓（`glyf`）**：
- 全部 31036 个字形：平均 **326 B**、中位 320、p10 165、p90 496、p99 682、最大 1636
- 其中汉字 20976 个：平均 **339 B**、中位 327、p90 496、最大 1122
- 具体例子：一 26 B、十 40 B、口 50 B、A 71 B、医 176 B、心 184 B、患 243 B、
  的 261 B、疆 344 B、悸 351 B、赢 496 B
**变体（`gvar`）**：平均 **228 B/字形**
⇒ **合计约 555 B/字形**（轮廓 + 变体；度量与索引 `hmtx`/`loca` 各约 4 B）

### 2. 这决定了 64 KB 的块有多浪费

- 64 KB 块 ≈ **118 个字形**（65536 / 555）
- 实测（2000 段 x 20 字、**800 个不同字形**）：读了 **155 块 = 9.53 MB**
- 而 800 个字形的实际数据 ≈ 800 x 555 = **444 KB**
- ⇒ **放大 21 倍**。命中率 99.1% 只是"次数上好看"，**带宽上浪费约 95%**
- 根因：字形在 `glyf` 里按**字形号连续**，而一段文本用到的字形号是**散的**
  ⇒ 块读的"顺带拉进来"的几乎全是用不到的

### 3. "块大小该取多少"取决于存储后端

按"800 个字形散布在 glyf+gvar（16.4 MB）里"的模型推算（实测每次读的固定开销约 20 µs）：

| 块大小 | 涉及块数 | 读入字节 | I/O 次数 x 固定开销 |
| --- | --- | --- | --- |
| 64 KB | ~250（实测 155） | 15.7 MB（实测 9.5） | 155 次 = **3.1 ms** |
| 16 KB | ~560 | 8.75 MB | 560 次 = 11 ms |
| 4 KB | ~729 | 2.85 MB | 729 次 = 15 ms |
| 按字形精确读 | 800 | **0.44 MB** | 800 次 = 16 ms |

★ **块越小：带宽越省（附带读的无关数据少）、次数越贵**。哪个划算取决于后端：
- **MEMFS（内存）**：带宽便宜（memcpy）、次数贵（每次调用）⇒ **大块更优**（现状合理）
- **OPFS / 真磁盘**：带宽才是真成本（读放大 21 倍）⇒ **小块或按字形精确读更好**

⇒ **64 KB 是随手定的、没有依据**（当时只想着"减少读的次数"）。换成 OPFS 之后这个参数要重新定，
方向是**调小**；而且块缓存的空间效率同样受影响（常驻 3 MB 里装着大量顺带拉进来用不到的字节）。
