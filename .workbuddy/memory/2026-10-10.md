## 表单括号改为「常驻」（默认全部字段一直显示），并修掉「字段删空后括号消失」

### 用户报的现象（原话）
「文本控件删除最后一个字符后，括号也不渲染了，但是好像括号位置还占着，输入一个字符后括号出现，
括号应该一直在，不然不知道这块可以输入了」
补一句放宽：「或者用来配置是否一直渲染，默认一直渲染」。

### 两个独立的根因
1. **绘制层按「控件矩形」遍历**。空区间（start == end）投影不出矩形 → `controlRects` 返回空
   → 一个标记都画不出来；而占位槽照插（排版侧不关心内容长度）→ 表象就是
   「位置还占着、什么都看不见」。另外旧实现还要在那一行**扫一个已存在的字形**当参考
   （拿字体/基线），字段被删空后连参考字形都没有 → 直接 `continue`。
2. **`inlineOffsetFor` 的闭括号短路条件太宽**（只在多字段时暴露）：闭括号占位记录的是字段
   结束偏移，而查找会**路过**前面字段的闭括号 → 查询字段 #1 之后的所有位置都被拉回到
   #0 的 `]` 之内（实测 off12=off13=off15=off16=170.255，光标"逐字右移"完全不动）。
   修法：短路再加一个条件 `c.cp == cp`（只在这个边界码点上才当终点）。

### 结构性改动（别再改回去）
- **绘制几何全部从排版派生**：位置 = 占位簇的 `LineCluster::inline_pt`、
  朝向 = `bracket_side`、字体与基线 = 新加的 `LineBox::bracket_font` / `bracket_axis_pt`。
  槽在哪就画在哪，和"那一行有没有字形"无关 → 空字段天然覆盖。
  ⇒ `drawControlMarks()` 不再扫 `layout_.glyphs` 找参考字形，也不再遍历控件矩形。
- **显示范围是一张名单**：`EngineConfig::form_brackets`（新枚举 `FormBracketScope`）：
  `All`（默认，全部字段常驻，只读字段照样画但用灰色）/ `Focused`（旧行为：只显示光标所在字段，
  其余画小点）。名单由 `EditorEngine::bracketedControls()` 产出，排版只认名单
  （`layoutDocument(..., const std::vector<int>* bracketed)`），不认识"聚焦"。
- **占位集合与光标解耦**：`bracketPlanId()`（-1 无 / -2 全部 / >=0 单个）取代
  `occupiedControlIndex()`；`relayoutIfFocusChanged` → `relayoutIfBracketPlanChanged`。
  All 档下它是常数 ⇒ **光标跨字段移动不再重排**（实测换字段上屏 288×35 px，整帧 893×1263）。
- `markPlanSignature()` 在 All 档**不把焦点**算进去（否则每跨一次字段就整帧重贴）。
- `setConfig()` 里检测到 `form_brackets` 变化要**自己重排**（占位变了）。
- `LineCluster::read_only` / `BlockShaping::Cluster::read_only`：括号颜色（蓝/灰）由排版侧
  随占位一起带出来，绘制层不用反查控件（相邻/嵌套字段反查有歧义）。

## 追加（11:09 用户报）：相邻字段的括号顺序反了 → `[]` 应为 `][`

### 现象
截图 `患者主诉：[反复心悸[]三天]` —— 前一字段的**右**括号画到了后一字段**左**括号的右边。

### 根因
同一处边界（A.end == B.start == 同一个偏移）上落着两个占位槽，而插入时
**一律"开在前、闭在后"**（`const BracketSide order[2] = {Open, Close}`）。
那条规则只对**空字段**成立（同一个字段的一对 → `[]`）；相邻字段要的是**闭在前**
（A 的内容在左、B 的在右）。

### 改法（`layout.cpp` 的占位插入）
槽不再按"开/闭"分两个计数器，改成**每个边界一个 Slot 列表 + 优先级**：
`0 = 内容结束处的闭括号`、`1 = 开括号`、`2 = 空字段自己的闭括号`，插入前
`std::stable_sort(at[i], by prio)`。三种形状于是都对：`][`（相邻）、`[]`（空字段）、
`[[ … ]]`（嵌套同区间）。★ 顺序取决于**槽属于谁**，不是"开还是闭"。
（注：光靠"每个控件先 push Close 再 push Open"也能凑对相邻这一种，但控件列表顺序
不保证是左右序 —— 所以排序是**承重**的，不能删。）

### 验证
- native `ced_edit_tests` **211 项 / 0**（新增 [14]：结构性断言"共享边界占位顺序 = [闭,开]"
  + 几何"闭槽紧贴 A 内容右缘且 < 开槽" + **颜色判据**"亮蓝 `]` 整个在灰 `[` 左边"，
  只读灰括号单独一条 `isGray` 判据（三通道接近且 ∈[140,195]：上限排掉页边框 206，
  下限排掉黑字 AA）；[11] 的 (f6) 补了"空字段的一对是 `[开,闭]`"）。
- 浏览器探针 **98 项 / 0**（新增：表单样例里 complaint(蓝) | duration(灰) 这一对，
  量窗口内蓝/灰墨迹范围，要求 `blueHi < grayLo`；实测蓝 286..290 < 灰 295..298）。
- 压力探针 69 次动作 0 不一致；ctest 2/2；wasm 3284.4 KB。
- **注入证伪**：把 prio 改成 `Open=0 / Close=1`（=旧的"一律开在前"）→ [14] 的 5 条
  全红、而"空字段 `[]`"那条仍绿 —— 正好证明两条断言各管一种形状。已恢复并重建。

### 教训（写在这里因为踩到了）
C++ 字符串里写断言文案时，不要用 ASCII 双引号（"一律"开在前"" 会把字符串提前截断，
编译器报的错在很远的地方）。用「」。

### 档 2 步骤 2：后缀原样复用（splice 快路）
- 判据：脏段排完之后，续排状态 {页号, cursor_y, 行号} 与上一轮"后缀开始时"的那个
  逐位相同 → 后缀里每一行的断页/全局行号/坐标必然与上一轮一致 → 整块搬回。
  只有脏段自己的行盒与字形要换（erase + insert 各一次 memmove），后续段的切片
  平移 dline/dglyph；页数不动（后缀起点状态没变 ⇒ 文档结束状态没变）。
- 两个必须的额外条件：① 括号占位计划不能伸进后缀段（端点会被插入/删除移动，
  内容没变而占位变了）；② 用 `layout_needs_full_` 把"整篇都脏"与"从第 0 段起脏"
  分开 —— 后者仍然可以复用后缀（"没有前缀"≠"必须重排全篇"）。
- 效果（200 段 / 400 行，native 中位数）：全量 2.23 ms；尾部敲字 0.117 ms（5.2%）；
  中部敲字 0.143 ms（6.4%）。中部从 27.5% 降到 6.4% —— 位置不再决定成本。
  浏览器：重排 1 段 / 复用 49 段 / 共 200 段，增量 0.2 ms，auditLayout diff 0。
- 账目新增 `EditStats::reused_paragraphs`（后缀原样搬回的段数）；面板改为
  「重排段 / 复用段 / 总段」。
- 测量口径修了两个坑：① `stats_.layout_ms` 原来在 syncStatsFromLayout **之后**
  赋值 → 面板读到的是上一轮的值；② layout_ms 一度把每轮都跑的页指纹记账算进来
  （O(全篇)，会盖过排版本身），现在只量排版本身（拼接/续排/全量都算）。
- 分支覆盖：快路（重排 1 段/复用 99 段）与反面（把脏段撑出一行 → 状态变了 →
  老实重排 100 段）都在 [15] 里，两条都过 auditLayout。
- 证伪：把状态判据放宽成"只比页号" → 3 条断言红（后缀重排后与全量不符、
  60 步随机全部不符）。已恢复并改→编→跑重验。
- 验证：native 231 项断言、ctest 2/2、编辑探针 110/0、压力探针 69 动作 0 不一致、
  注释 0 违规、格式 0 差异。
- 下一步候选：① 行结构变了的那条路（后缀重排）仍与后缀长度成正比 —— 可做
  "平移复用"（重算页码/块轴坐标、复用断行结果）；② 页指纹记账是 O(全篇) 的固定
  开销，增量编辑时它已经是主要成本（可按受影响页做增量指纹）；
  ③ 跨段编辑（回车分段 / 退格合并段）。

### 档 2 步骤 3+4：增量页指纹 + 后缀平移复用
- **#1 页指纹增量化**：`computePageFingerprints(dirty_lo, dirty_hi)`。依据两条：
  ① 页数不变且上一轮指纹数组还在（否则退化成整篇）；
  ② 字形数组按页单调，于是用 `lower_bound/upper_bound` 二分出受影响页的字形区间，
  只重算那几页的哈希，其余页沿用上一轮的值。脏页区间由 `trySuffixReuse` 出参带回
  （脏段新旧两版行盒的页并集）。效果：整篇 0.33 ms → 敲字 0.021 ms（6%）。
  这条不变式在单测 [15] 里用断言钉住（三次：全量后 / 原样复用后 / 平移后）。
- **#2 后缀平移复用**（`SuffixReuse::Shifted` / `shiftSuffixBlockAxis`）：
  行结构变了（撑出一行）时不再重排后缀，而是把后缀每一行沿块轴平移到新位置、
  重编页码与全局行号，字形跟着自己的行一起挪；断行结果与字形行内位置一个字节都不重算。
  依据：横排块轴推进是一条纯折线（每行 size_pt*line_factor、段间 space_after_pt、
  放不下换页），只要知道后缀**开始**时的续排状态，整个后缀的新位置就唯一确定。
  规则与 layoutDocumentRange 横排分支同源，靠 auditLayout 兜住分叉。
  竖排后缀不吃这条规则（列与"块吃掉整页"是另一套）→ 返回 false 走常规续排。
  先空跑一遍做校验（字形数必须正好走完），通过后再真改 —— 避免"改到一半发现对不上"。
  顺带必须更新**每一段**的 `state_at_start`（页号/块轴位置/行号都变了）。
  效果：后缀 100 段 0.35 ms vs 续排 0.95 ms（37%）。
- **审计的浮点容差**（重要）：平移的坐标是"旧值+偏移"，比全量"从 cursor_y 累加"
  多一次舍入（实测最大 6.1e-05 pt，整型字段 0 处不符）。所以
  `sameGlyph/sameLine/sameParaIndex` 对浮点坐标用 1e-3 pt 容差（比舍入噪声大 16 倍、
  比引擎自己的量化步长 1/16 pt 小 30 倍），**整数与标志仍严格相等**。
- **新增单测 [16]：增量上屏 == 从零上屏**（整帧逐字节）。存在理由：`auditFrame()`
  比的是"帧 vs 从底图重贴"，底图自己漏画时两边一起错、它照样是 0。办法是拿第二个
  引擎（同文档同配置同光标、从零重排重画）当参照比整帧像素。严格档要求 0 差异；
  平移之后允许"≤十万分之一像素且通道差≤1"（实测恰好 6 个像素、每个差 1 —— 坐标末位
  差在抗锯齿边界上翻的一格）。**证伪**：让页指纹只重算第 0 页 → [16] 五个场景全红
  （5232 像素差、通道差 231 = 整行残影）。
- 证伪二：平移时不更新 `state_at_start` → auditLayout 红 + 随机 60 步全不符。
- 测量口径再修两处：① `EngineStats::page_fp_ms` 新增（页指纹的耗时独立上报，
  混进 layout_ms 会得出"增量没省多少"的错误结论）；② 所有耗时对照改 3 次取最小
  （单次会被调度尖峰打出一个数量级的假数字：实测报出过 4.08 ms，同一操作随后 0.206 ms）。
- 验证：native 253 项断言 0 失败、ctest 2/2、编辑探针 115/0（新增平移与页指纹断言）、
  压力探针 69 动作 0 不一致、渲染探针 6 场景、注释 0 违规、格式 0 差异、wasm 3304 KB。
- 实测（本机噪声较大，看相对值）：全量 1.70 ms ｜ 尾部敲字 0.080（4.7%）｜
  中部敲字 0.121（7.1%）。端到端里**呈现占 80% 以上**（敲 1 字 1.96 ms，其中呈现 1.96…），
  排版只占 0.16 ms。⇒ 下一个瓶颈是"平移之后 9 页都要重画"（14.9 ms）：
  若能让"整页内容只平移一个常数"的页走位图平移（memmove + 补边缘），
  收益比继续压排版大得多。
- 未做：跨段编辑（回车分段 / 退格合并段）。

### 档 2 步骤 5：跨段编辑（回车分段 / 段首退格合并 / 段末 Delete 合并）
- **前提：空段落必须占一行**。以前空段落整段跳过（没有行盒）→ 回车的落点在几何上不存在
  （光标画不出来），表现就是"回车没反应"。现在空段落产出一个"零真实簇"的行盒：
  只可能有括号占位簇、inline_end_pt 由占位宽度给出；参与翻页判定；竖排走一列。
  顺带把"字段所在整段被删空就看不见括号"这个老问题一起修掉了。
- **括号占位抽成 `withBracketSlots(...)`**：原来那段逻辑内联在主循环里，空段落走的是
  提前返回，于是空段落里的字段边界没有括号。现在两条路共用一个函数 —— 顺序规则
  （][ / [] / [[ ]]）只有一份，空段落与有内容段落不会各画一套。
- **区间适配**（control.h/.cpp）：`adjustControlsOnSplitPara(pos)`（端点 >= pos 的搬到
  新段：段号 +1、偏移 -= pos.offset；更靠后的段号整体 +1）、
  `adjustControlsOnMergePara(para, prev_len)`（p+1 段的端点重基到 p 段；更后的段号 -1）。
  两端点同一条规则 ⟹ 不可能出现 start > end；"恰好落在断点上的空字段"归新段，
  与"回车后光标落在新段段首"同一口径。分段 + 合并 = 区间逐字段回到原样（往返不变，有断言）。
- **策略**（edit_policy）：`canSplit(pos) = canInsert(pos)`、`canMerge(join) = canInsert(join)`
  —— 回车就是"在断点插一个段落分隔符"，合并就是"删掉它"，刻意不另立一套规则。
  join 取前一段末尾（include_end=true），于是"并进只读字段"被拒、"把只读字段并走"允许
  （只读保护跟着区间走，不会因为搬动而失效）。
- **排版**：新增 `para_count_changed_` —— 段数变了必须禁掉**后缀复用**：复用判据是
  "第 from+1 段开始时的续排状态"，而段号一变第 from+1 段已经是另一段了，比出来毫无意义
  （碰巧相等就会把整个后缀错当成没变）。但"段数变了"不等于整篇重排：前缀 [0, dirty_from)
  一个字都没动，照走常规续排。重排完成即清零。
- **宿主**：Enter → `splitParagraph()`；段首退格 / 段末 Delete 由 backspace/deleteForward
  自动走合并（不需要宿主改动）。wasm 多导出三个显式入口；`__ced.allText` 给探针核对字符账。
- **判据**：单测新增 [17]（31 条）：空段落有行且有光标几何；分段的文本账守恒、样式继承、
  page_break_before 清零；光标的落点；控件区间的适配与往返；合并两入口对称；
  只读/表单模式的拒绝与计数；策略函数直接测；随机 40 步（含跨段）每步 auditLayout==0
  且**整篇重排的步数恰好等于"脏段为第 0 段且段数/行数变了"的步数**（11 == 11）；
  整帧逐字节比对（分段/合并之后 0 像素差）。探针新增 [10]：真实 Enter 按键 → 段数 +1、
  光标在新段段首、字符账守恒、auditLayout/selfCheck/auditFrame 全 0；段首退格并回。
- **证伪两条**：① 不调 adjustControlsOnSplitPara → 5 条区间断言红；
  ② 合并后不设 para_count_changed_ → 随机序列审计红 + 逐帧比对红。均已恢复并重验。
- 验证：native 317 项断言 0 失败、ctest 2/2、编辑探针 126/0、压力探针 69 动作 0 不一致、
  渲染探针 6 场景、注释 0 违规、格式 0 差异、wasm 3311 KB。
- 实测（200 段文档在第 100 段回车）：重排 101 段（前缀 100 段复用，后缀一律不复用），
  端到端 ~24 ms —— 其中**呈现占绝大部分**（后缀整体下移，其后的 9 页都要重画）。
  所以下一个瓶颈仍在光栅侧：可做"整页内容只平移一个常数时走位图平移"；
  排版侧则可做"段号整体平移复用"（把后缀的 ParaIndex 整体挪一格 + 复用断行结果），
  让回车也只剩 1 段重排。


## 相邻字段共享边界：两处括号错位（打字 / 删空）

- **现象一（打字）**：两个相邻字段，在第一个字段末尾打字，边界上的括号从 `][` 变成 `[]`
  （截图：`患者主诉：[反悸[▏]三天]，[加重一天]。`）。根因不在排版，在区间伸缩：
  插入点同时是 A 的末尾与 B 的开头，`adjustControlsOnInsert` 的两条端点规则同时命中
  （A 的终点 >= at 右移、B 的起点要 > at 才右移）→ **一个字同时落进两个控件**：
  A=[5,10)、B=[9,12) 重叠。排版于是把 B 的左括号画到 A 右括号的左边。
- **修法**：先定"落笔点归谁"（`innermostAt(at, include_end=true)`，与 canInsert / 光标
  判定同一口径），主人按"内含"伸缩（起点 > at、终点 >= at），其余按"平移"伸缩
  （起点 >= at、终点 > at）；包住主人且新字接在主人末尾的外层控件跟着长（否则父子区间
  会互相穿过）；空控件整对端点同进同退（否则写出 start > end 的死区间）。见 control.cpp。
- **现象二（删空）**：把第一个字段的内容全删光，它变成零宽空字段，边界上有三个槽
  （左？没有 / 空字段的开、闭 / 后一个字段的开）。旧优先级让后一个字段的开括号插进空字段
  的那一对中间，画成 `[[▏]`。修法：优先级改成 **闭(内容结束) 0 → 空字段开 1 → 空字段闭 2
  → 开(内容开始) 3**，空字段的一对永远连着。见 layout.cpp 的 Slot::prio。
- **判据**：单测 [18] 扩到 (a)~(h)：区间不重叠 / 新边界占位顺序 [闭,开] / 蓝 `]` 在灰 `[`
  左边（像素）；空字段相邻时主人是谁；空控件端点同进同退（直接调区间伸缩函数）；
  删空后三槽顺序 [开,闭,开] + 光标在那一对之内；(h) 三连可编辑字段删空中间那个 →
  四槽顺序 [闭,开,闭,开] + **差分像素**（只把中间改只读，两帧之间变的列就只有那一对括号，
  要求它整对夹在左右字段的括号之间）。为什么不用"灰"颜色本身当判据：正文黑字的抗锯齿
  尾巴正好落在灰带里（实测压在左边第一个槽之前），会把两侧墨迹混进窗口。
- **证伪**：① 注入旧区间伸缩规则 → [18] 红 9 条；② 注入旧 Slot::prio → 红 4~6 条
  （含差分像素：灰的右括号落到右字段开括号右边）。均已恢复并重验。
- **演示样例**：`loadFormSample(2)` = 三个可编辑字段紧挨着（[5,7) [7,9) [9,11)），
  前端加了 variant 下拉（`web/index.html` 的 formVariant + `app.js` 的 formHint）。
- 验证：native 354 + 55 项断言 0 失败、ctest 2/2、编辑探针 138/0（含三连样例的
  区间链 + auditLayout + selfCheck）、压力探针 69 动作 0 不一致、注释 0 违规、格式 0 差异。
- 探针新增：`edit_probe.mjs` [11] 段共用边界打字（结构 + 矩形不越界 + auditLayout）与
  三连样例；截图 `out/web/shared-boundary.png`、`out/web/three-adjacent-fields.png`。

## 三连可编辑字段：删空后进不去 + 方向键跨字段（边界策略层）

- **现象**：三个可编辑字段连排，把中间那个删空之后 ① 光标再也进不去、字也打不进去
  （打字落进了左边那个字段）；② 左右方向键能从左字段一路走到右边字段（跨控件）。
- **根因（两条，都在"边界策略"这一层）**：
  1. **区间树是快照**：`depth/parent` 只在 `setControls` 时算一次，而区间随编辑移动。
     删空后那个字段变成零宽 `[7,7)`，被左右邻居按闭合区间包含 —— 本该是最内层、于是最优先，
     但 depth 还停在 0 → `innermostAt(7)` 判给左邻居（下标更小者胜）。表现就是"进不去、
     打不进字"。修法：`adjustControlsOnInsert/Erase` 末尾各加一次 `ctrls.normalize()`
     （控件是几十个量级，重算是微秒级）。
  2. **"不跨控件"判据写错了对象**：原判据是 `canPlaceCaret(next)`（"下一步是否合法"）。
     邻居只读时它恰好等价；邻居**可编辑**时下一个格子正好落在隔壁字段里，一律放行 ——
     三连字段就是这种情况。修法：`moveCaretBy` 在移动前钉住"出发时所在字段"
     （`innermostAt(caret_, true)`），整次移动都不许离开它的 `[start, end]` 闭区间。
- **代价（写进注释了）**：字段之间不能靠方向键走，换字段用鼠标点；空字段零宽，方向键在里面
  原地不动，打一个字或点别处才出得来。
- **判据**：单测 [18] 新增 (i)：删空后 `#1.depth == 1`、偏移 7 归属 #1、打字进 #1
  （#0 不许被撑大）、从 5 连按 6 次右键落点 6 7 7 7 7 全在 [5,7]、从 8 左走只在 #2 内。
  探针 [11] 段补三条：光标停在空字段位置、方向键走不出左字段（到 7 停）、在空字段位置打字
  进它自己。
- **证伪**：① 注入"区间树不重算"（`if (false) ctrls.normalize();`）→ 红 5 条
  （含"字进了空字段"与"从 #2 左走只在 #2 内"）；② 注入"去掉出发字段约束"→ 红 2 条
  （落点序列变回 6 7 8 9 9 9）。均已恢复并重验。
- 验证：native 364 + 55 项断言 0 失败、ctest 2/2、编辑探针 141/0、压力探针 69 动作
  0 不一致、注释 0 违规、格式 0 差异、wasm 3311.8 KB。
- **遗留（同类隐患，未做）**：① 零宽字段投影不出矩形 → 点不到它（只能靠键盘走到，
  或走 `focusControl`），要修得给"最小可点宽度"；② 仍没有显式的"当前字段"状态，
  归属还是从几何+光标现推 —— 要彻底消除这类歧义应维护 `focused_control` 并给一个
  换字段键（Tab 已归缩进）。

## 验证台"改了没生效"：静态服务改成 no-store + 界面显示实际加载的构建时间

- **现象**：wasm 明明在 17:16 重编过（`build/wasm/web/ced_editor.*`），浏览器里还是旧行为。
- **根因**：`python -m http.server` 只发 `Last-Modified`、**不发 `Cache-Control`**，浏览器于是按
  启发式新鲜度（约距 Last-Modified 的 10%）直接用磁盘缓存，连问都不问服务器 —— 这次
  app.js 那次踩的是同一个坑（`verify_web.ps1` 里原来用 CDP 关缓存绕开）。
- **修法两条**：
  1. 新增 `scripts/dev_server.py`（no-store + `.wasm`/`.ttf` MIME）并让 `serve_web.ps1` /
     `verify_web.ps1` 都走它；实测响应头 `Cache-Control: no-store, no-cache, must-revalidate,
     max-age=0`、wasm 的 Content-Type 是 `application/wasm`。
  2. 界面自证：`web/app.js` 启动时 HEAD 一次胶水层、把 Last-Modified 显示在工具条
     （`#build`，形如 `wasm 10-10 17:16:58`），boot 面板也加一行 —— "当前跑的哪一版"一眼可判。
- 提醒（一次性）：已经开着的旧页面仍可能用缓存，需要**硬刷新一次**；之后普通刷新都会拿真文件。

## "没好"的可验证化：版本号加载 + wasm 内嵌构建时间 + no-store

- 关键实测（三连，删掉中间 `[7,9)`）：区间树给零宽字段 `depth=1 / parent=2`
  （成了**右邻的孩子**），而括号把它画在右邻**左边**；光标 `归属=1` 却渲染在左邻 `7]160.9`

- 关键实测（三层嵌套，一次删掉 `[7,11)`）：树仍是 depth 0/1/2 嵌套，
  但槽序为 `7]`(d1) `7]`(d0) `7[`(d2) `7]`(d2) → 画成 `[反[复]][ ]`，最内层的空字段被画到最外。

  改成按 depth 降序则嵌套对了、并列又错（会把两个并列空字段排到左邻闭括号**里面**）。
  冲突根源：一处偏移上"空字段属于哪一层"在 `(start,end)` 二元组里推不出来，
  删空那一刻信息就丢了。所以只能二选一，不存在两者都对的反推规则。
- 方案 A（推荐）：把控件边界做成文档流里的一等位置（`Item = Text(cp) | Boundary(id, side)`），
  控件只存身份不存 `start/end`；嵌套由一次栈扫描得出；光标用流位置。

  `normalize()`、`adjustControlsOn*` 四个函数、`preferred` 参数、`caret_field_` 全部删除，净减代码。

  且明确"Plcfld 不允许有重复 CP"；OOXML `w:sdt` 把内容包成可嵌套的真实元素、
  `w:fldChar` 用 begin/separate/end 标记；ProseMirror 的位置是 token 序号，
  **进入或离开非叶节点各算 1 个位置**（所以"在节点边界上"与"在节点里"是两个位置）。

### TextRun 澄清（回答"TextRun 是个什么东西"）

- 定义：一段**共享同一套标记（marks）的连续文本**。名字借自 Word 的 `w:r`（run），
  OOXML / ProseMirror / Slate 用同一概念。它存在的理由是字符属性必须以**区间**附着：
  整段共用一份就是现在的 `BlockSpec`（无 run 级样式），每字符各带一份又太重。
- 关键区分：**段落标记是流里的真实元素，`TextRun` 是被切分出来的叶子**。判据只有一句
  ——**能不能跨过流元素**：能跨的是位置（段落），不能跨的是内容（`TextRun` 与原子）。
  于是 `TextRun` 的边界是**算出来的**：用户不会"新建 run"，只会"给这段加粗"。
- 参照项目实测（补齐证据链）：运行时**没有 run**，流是 `DomCharElement`（单字符，带
  `styleIndex`）序列——`new DomCharElement` 在 `DomContainerElement` / `DomDocument` /
  `DomFieldElementBase` / `WriterUtilsInner` 多处创建。`DomStringElement`（= `XTextStringElement`
  = run）**全库只有一个创建点** `WriterUtilsInner.cs:1081`，且在**输出文本**的循环里，
  三条合并判据是 `CanMerge`（`_StyleIndex` 相等）+ `HasSameParent` + `IsBackgroundText` 相同。
  这与 `DomParagraphElement` 的"只在加载或保存文档时临时生成"是同一类手法：
  **run 与段落都是派生量，参照项目两个都放在运行时之外**。
- 我们文档的差别：参照项目把 run 做成纯派生（输出时切），我们选**规范化维护的叶子**
  （第二条不变量"相邻且标记集合相同的文本节点必须合并"），与 ProseMirror / Slate 一致。
- 文档改动三处：第二节不变量新增"`TextRun` 不跨流元素"一条 + 一段"能不能跨过流元素"的判据说明；
  第三节 `TextRun` 定义改为"叶子，完整落在同两个流元素之间"，并补三点来历说明。
- 名字保留 `TextRun`：它是业界通用词，改名反而增加阅读成本（对比 `InputField` 改名
  `ContentControl` —— 那个是语义不符，这个是通用术语）。

### 本轮需求：控件的能力与宿主接口（已写入第七节）

- **控件外观**：`appearance { width, underline, align, placeholder, styleRef }`。
  固定宽度是**占位宽度**，与输入上限 `maxLength` 分开存；长度类型要加一档 `Chars(n)`
  （不能用 `Em(n)`，中文全角 1 em / 数字半角约 0.5 em，不然数字字段算成一半宽）；
  它是引擎侧"边界有宽度"的加强版。**下划线是边界装饰，不是字符的 underline 标记**
  ——混淆会变成"给内容加标记、删字后线也没了"。`placeholder` 不进文档，否则会被 `getValue` 取出来。
- **值的读写**：**内容即值**（容器型的值就是它的内容，`getValue` = 拼 TextRun）；
  因此必须有**控件索引**（`key → 控件`、`控件 → 内容位置`，随编辑步骤增量更新）——
  没有索引，"列出全部控件"与"批量取值"每次全篇扫描，性能与老编辑器一样差。
  三个 API：`listControls()` / `getValues(keys?)` / `setValues([(key,v)…])`。
- **批量设值**的价值不是少几次函数调用，而是**合成一个事务**（一次编译/标脏/排版/上屏/撤销）。
  三条判据：设 1000 个字段与设 1 个耗时同一量级；只 1 个撤销步骤；最终帧与逐个设置逐像素一致。
  **代价**：脏区散布全篇，`layout_dirty_from_`（一个后缀）可能不够——这是第六节那个风险的
  第一个真实用例，先退化全量、测出数字再决定是否扩展成集合。
- **校验钩子**：`beforeChange(change) → Allow | Deny(reason)`，`change` 带 `source: user | program`。
  只允许同步决策（异步要服务端校验的场景 = 宿主先查再调 `setValue`）；
  **返回拒绝原因**（ProseMirror 的 `filterTransaction → boolean` 被取消后没有回执，是它的公认短板）；
  **只拦用户交互、不拦编程设值**（回填顺序本来就可能先填空的）；钩子内禁止调用编辑 API。
- **批次**：`beginBatch()` 期间只改模型，不编译/不排版/不上屏；`commitBatch()` 时合成一个事务。
  老编辑器慢的根因不是函数调用开销，而是每次 `setValue` 都触发一整轮重排 + 上屏；
  本项目上屏占端到端八成以上（敲 1 字 1.96 ms 里排版只 0.16 ms），所以要做在"抑制中间的上屏"。
- **句柄**：用 id / key 字符串，不用节点指针（节点会因编辑失效）。对外 API 对"容器型 vs 原子型"
  完全一致。顺带澄清：原子型控件（复选/单选/下拉）是叶子，**文本控件按方案一是跨度、不是叶子**。
- 迁移表新增 **1.5（控件索引与宿主 API）**，判据即上面三条；第十六节新增第八、九项待确认
  （固定宽度溢出行为、批量设值的脏区）。
