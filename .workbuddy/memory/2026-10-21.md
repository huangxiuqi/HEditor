## 浏览器打印：形态与判据（讨论结论，无代码改动）

结论：`window.print()` + 一份**只用一次的打印 DOM**，但这条路有三个变量不受我们控制
（页眉页脚、边距、缩放），所以"打印必与屏幕 1:1"只有 PDF 能给。

结构性前提（决定了实现形状）：

- 宿主只为**窗口内**的页建画布（`pageCanvases` 是 页号→元素的 Map），窗口外没有任何元素。
  所以"打印全文"必须另建 DOM，不能让编辑 DOM 直接进打印。
- 分页不用重做：`PageMetrics` / `stats_.page_count` 已经算好，打印 DOM 每页一个盒子即可。
- 连页模式必须强制分页：导出要在一份**单独**的 `LayoutResult` 上跑（用分页度量重排），
  不能把 `cfg_` 改成分页再改回来 —— 那会让屏幕中途按分页重绘一次。
  由此导出器必须是纯函数（吃 LayoutResult + 配置），不能读引擎成员。

三条实现要点：

- `@page { size: <页宽pt> <页高pt>; margin: 0 }`，`.pg { width: 595.276pt; height: 841.89pt;
  overflow: hidden; break-after: page }`；最后一个 `break-after: auto`。
- `beforeprint` 里建 DOM 是同步的，200 页会卡住且浏览器可能超时。改成"先建（带进度）再
  `window.print()`"，`afterprint` 里拆掉。`document.title` 会变成页眉与另存文件名。
- canvas 打印受光栅分辨率限制：200 dpi 一页 1654×2339×4 = 15.5 MB，300 dpi 34.8 MB ——
  全文打印不可行。矢量导出没有这个问题，所以打印与预览共用同一个 SVG 导出器。

判据（现有 CDP 探针就能做，`conn.send` 是通用的）：

- `Emulation.setEmulatedMedia({media:'print'})` 之后量每个 `.pg` 的 `getBoundingClientRect()`
  == 页宽磅 × 页高磅，容差 0；
- `Page.printToPDF` 出来数页数 == `stats_.page_count`，每页 MediaBox == 页度量；
- 改一次页度量（A4 -> Letter），上面两条跟着变（反向一半，防恒真）。

1:1 的退路：SkPDF 出 blob → `window.open` 让用户在阅读器里打印。CSS 这条路上永远有
对话框里的三个变量，产品若要求"用户不需调设置"，只能走 PDF。

### 参照：DCWriterLite（2026-10-21 查证）

README 原话：自建 DOM、XML 存文档、"employs Canvas for document rendering and SVG for
document printing"（Apache-2.0，Blazor WASM，GDI+ 移植）。即"canvas 渲染屏幕 + SVG 打印 +
自己分页"是同族做法，不是理论。要点：

- 它是在**自建文档 DOM 上重放**出 SVG，不是从画布抓像素 —— 与"从 layout_ 序列化"同构。
- 它的字体靠客户端安装（WinForm 血统：公文/病历系统要求装宋体仿宋），所以它输
  `<text>` + font-family 才成立；我们字体是自加载 TTF，**必须走轮廓 path**，不能照抄。
- 未查证：它的 SVG 是否用 `<text>`、是否做 `<use>` 去重（决定体积与可选中）。
- 它把纸张类型/方向/边距列为打印设置 —— 说明页度量进排版参数、打印前按纸张重排一次，
  与"导出一律分页、在单独 LayoutResult 上跑"是同一结论。

## 5D 之后内存不降反升：定位到一处白账（08:50，只诊断未改）

用户反馈 5D 做完后内存占用更大。查到一处确定的白涨，与"帧已删"这件事直接矛盾：

- `statsJson()`（`src/wasm/wasm_main.cpp:574`）里带 `"frameBytes": g_engine.frameBytes()`
  这个字段。`frameBytes()` 走 `ensureFrameExport()`（`engine.cpp:547`）→
  `assembleWindow(true, &frame_export_)`，**真的分配一张窗口大小的位图**并逐页 memcpy。
- `presentInternal` 每拍把 `frame_export_valid_` 置 false（`engine_paint.cpp:622`），
  所以下一份状态一上报就重拼一次：5 页 × 3.57 MB ≈ 18 MB 拷贝 + 一页 3.5 MB 合成拷贝，
  同步发生在 `sendState` 里（算进 packAvgMs）。
- `sendState` 每份状态都调 `statsJson`（`web/engine_api.js:352`），而 JS 侧没有任何地方读
  `frameBytes`（`web/*.js` 零命中，只有 `tests/edit_test.cpp` 用 C++ 的 `frame()`）。
  即：**为了报一个没人读的数字，分配并每拍重拼 18 MB。**

账（5 页窗口、96 dpi、3.57 MB/页）：页缓存 7 页 25.0 + `page_export_` 3.6 +
`frame_export_` 18.2 = 46.8；5D 之前 `base_` 18.2 + `bitmap_` 18.2 + 页缓存 25.0 = 61.4。
净省 14.6 MB 而不是预期的 36 —— 一半被这张"窗口读视图"吃掉了。

另一层原因（不是 bug，是口径）：wasm 的 `Memory` 只增不减，`HEAPU8.length` 是**高水位**；
旧版 61 MB 是一次性要到的，新版 25 MB 随窗口逐页长、18 MB 的导出图之后才要，两次增长夹着
碎片，水位可能反而更高。所以判断"省没省"不能用 heap 大小，要用活字节数 —— 现在没人报。

修法：`statsJson` 的 frameBytes 改成算术（`frameWidth * frameHeight * 4`），不碰
`ensureFrameExport`。`frame()` 留给 tests 与探针的显式入口。验证必须**新开页面**比 heap，
已长的 heap 不会退回来。

## worker 模式画面全空（5D-2 收尾后由用户发现）

现象：worker 宿主切过去一片空白（页框可见、字一个没有）。探针全绿。

根因：页画布挪进 `#pages` 容器之后，`worker.html` 给的样式是
`position:absolute; top:0; left:0; overflow:hidden`。子元素全是绝对定位 → 容器的
收缩宽度是 0 → `overflow:hidden` 把 794 像素宽的页裁得一个像素不剩。
像素探针比的是 canvas 背衬，背衬一直正确，所以 369 ×2 / 74 / 35 全绿。

修法：`worker_host.js` 在拿到 `#pages` 之后统一钉
`position:absolute; top:0; left:0; right:0`。写在这里而不是各页 CSS：多实例页给的是
`position:relative; flex:none`（流内 flex 项，宽度同样收缩成 0），且它的舞台是 flex
居中 —— 流内容器还会被整体平移，而画布坐标按它的 left 算，会横向偏半个舞台。

判据：`worker_probe` 新增一条"每一张页画布在屏幕上都真的可见"，
`document.elementFromPoint(页中心) === 该画布`。注入故障（去掉那三行）实测 0/1 可见、
命中 stage；恢复后 75 项全绿（原 74 + 新的 1）。

复验：`edit_probe` 369 ×2（只剩 4 条字体存储账，TRAPS 131）、`worker_probe` 75、
`multi_probe` 35。截图确认：分页两页有字、滚动到第二页有字、连页无间隙连续。
TRAPS 141 记录。

## 连页接缝：半行字与半行高亮（用户报的第二个现象）

现象：连页下接缝处一行字只有下半截（上半截被切掉），选区矩形同样只剩一半。

根因是**三处各自按"页号归属"读内容**，而连页里一行本来就跨条带：
1. 横排字形页号按**基线**取（`layout.cpp` 的 `gpage = slabOfY(pen_y)`，注释是为竖排写的）。
   整行共用一个基线 → 整行走下一带、页内 y 为负 → 上半截被位图裁掉，上一带里又没有它。
2. 行盒、选区矩形、光标矩形按**行顶**归到上一带，超出带底的部分没有第二条带接着画。
3. 页指纹只哈希"属于这一页"的字形 → 改一行只重画上一带，下一带留着旧的半行。

修法（三条必须同时成立）：
- 横排字形跟行盒同属一带（`gpage = lb.page`）；竖排保持逐字形按 y（列本来一列到底）。
- `rasterIntoBitmap` 增加接缝趟：下一条带在顶部补画上一条带越过带底的那一截。
  字形 / 原子框 / 格线 / 括号与小点走同一趟（`dy = -带高`，`spill_only` 只取越界部分）。
- `computePageFingerprints` 把越界字形同时混进下一条带；`collectTransient` 把越界的
  选区与光标在本带再记一份。

判据 `edit_test` [59]："切 15 带拼起来 == 切 1 整带"，逐字节比（含全选态）。
注入故障（关掉接缝趟）实测 27 行不同、首行正好 150（第一条接缝）；恢复后 0 不同。
浏览器侧：找到一条真被切穿的接缝（第 2 页底 26 个墨点 / 第 3 页顶 23 个），截图确认
接缝从一行字中间穿过、上下两半完整。

顺带修好 `out/_continuous.mjs`：它还在用 5D-2 删掉的 `frameSlots` 与"连页只有一张画布"
的旧口径（两处判据、输入法框的坐标换算），现在按"一页一张画布 + 页内 y"重写。

判据：native 4/4（150 / **1439** / 845 / 297）、`edit_probe` 369 ×2（4 条已知字体账）、
`worker_probe` 75、`multi_probe` 36、`out/_continuous.mjs` 全绿；lint 0、格式合规。

## 字体身份从文件名换成 PostScript 名（v2 → v3）

用户问："字体不是应该用类似 font-face 的名称吗？字体文件名如果改了怎么办"。对的 ——
v2 的字体表值是 `"0":"NotoSansSC-VF.ttf"`，文件一改名，同一份文档就指向不了同一张脸。

改成三级匹配（顺序 = 稳定性）：
- `ps`：**PostScript 名**（OpenType name 表 ID 6，唯一性有规范保证）—— 身份
- `family`：排版族名（ID 16 优先，退到 ID 1）—— 给人看，也当第二级
- `file`：文件名 —— 只作最后一级

`FontFace` 新增 `postScriptName()` / `familyName()`，在 `buildFromData` 末尾由
`readNames()` 从 `hb_ot_name_get_utf8` 读（HB_LANGUAGE_INVALID = 英文优先，OpenType 要求
每个名字至少有一份英文记录）。按需装载（lazy）也读得到 —— name 表很小，留在骨架里
（`FontSource::inSkeleton` 是黑名单式，只剔轮廓/位图表），S5 那条判据专门盯它。

真实的一行（中英混排场景）：
```json
"fonts":{"0":{"ps":"NotoSansSC-Thin","family":"Noto Sans SC","file":"NotoSansSC-VF.ttf"},
         "2":{"ps":"NotoSans-Regular","family":"Noto Sans","file":"NotoSans-Latin-VF.ttf"}}
```

**已知边界（写进文档与 TRAPS）**：可变字体的 `ps` 是文件**默认实例**的名字
（NotoSansSC-VF → `NotoSansSC-Thin`），而引擎钉的是 wght 400。当文件身份准（同一文件同一
ps），当"实际用了什么字重"不准 —— 要准得等字体变体进模型，与粗体/斜体是同一件事。

版本 2 → **3**（又是"改含义"，所以升一格），读端仍收 1~3；v2 的字符串值按类型分派读成
"只有文件名的那一侧"。

判据：
- `rev_test` +4（字体项是对象 / 族名认脸 / 文件名兜底 / v2 的字符串值仍读）→ **314**
- `saveload_probe` +2（[S5] 按需装载也写得出 ps 与 family）→ **18 条 x 2 宿主**
- `edit_test` [60] 的字体断言改成 `"ps":"Noto` + 文件名兜底，仍 1462
- native 4/4（150 / 1462 / 845 / 314）；`edit_probe` 369 x2、`worker_probe` 74、
  `multi_probe` 36、`error_probe` 19 x2、`web_probe` 6、`stress_probe` 69；lint 0、格式合规

没做的：文档里还没有"字体槽名"（CSS `@font-face` 那个由使用方起的别名）—— 那属于
样式表/字体资源进文件，与"文档级字体表"一起做。现在用的是字体自报的名字。

## 表格走进增量：表里改一个字不再整篇重排

`relayout()` 里的硬拦截（`can_resume` 要求 `tables_.empty() && !had_tables`，
`trySuffixReuse` 同样有表即退）拆掉了。病历大量用表格，所以这一条之前等于"每敲一键全篇重排"。

改法：
- `PlacedTable::first_block`：表在块流里的起始段（格 → 段映射的产物，与位置无关）。
- `EditorEngine::tableAlignedFrom(from)`：脏区落在表里 → 起点对齐到**最外层**表的起始段。
  内层表也要从外层算起 —— 行高是行的性质，不是格的。
- `truncateLayoutAt(para)` 连 `first_block >= para` 的 `PlacedTable` 一起丢。不丢的话续排
  重新 openTable 会再 push 一条，同一张表两份几何（重影，只有整帧对拍看得见）。
- `can_resume` 不再看表格；`trySuffixReuse` 仍然拦（它假定后缀只沿块轴平移，而表格行高
  由格内容结算、整行放不下还要回挪）。

**一处口径修正，是判据逼出来的**：`ParaIndex::state_at_start` 原来记在"表格上下文切换之后"，

- 47 段样例（表前 8 + 3x3 表 + 表后 30）一次敲键：**全量 0.62 ms → 增量 0.13 ms**，

## 位置索引：第三种方案（只存局部量，绝对位置惰性累加）

用户追问"俩都有隐患，没有更好的方案吗"之后想清楚的一条 —— 比"投影记绝对位置 + 后缀加 delta"更好，
因为它**不存任何需要平移的量**：

- 每块存两个局部量：`span[i]`（本块内容占几位；含控件边界，只有投影走子树时数得出来）与
  `gap[i]`（第 i-1 块与第 i 块之间占几位：普通段界 = 1，格边界 = 2，节首 = 1）。
- 绝对位置 = `Σ(span + gap)`，按需累加（带"水位"缓存的惰性前缀和，编辑时只把水位退到脏块）。
- 于是：**后缀天然不动**（没有绝对的量要平移）；**两处 max 消失**（格边界那两位由"边界种类"
  给出，不再靠两个读数取大）；**漂移不可能静默**（错在哪个边界就错在哪一块，可本地断言）。

两条判据不需要参照物（不是同一公式自拍）：
1. 全局恒等式：`Σ span + Σ gap == flow_->size()`；
2. 每块：`posAt(start[i])` 落在本块内容里、且 `start[i] < start[i+1]`。

代价：`block_flow_[i]` 的直读变成 `startOf(i)` 调用（约 20 处），API 只给 `startOf/rangeOf`，
不给数组 —— 防止有人在循环里调成 O(n²)。

## 位置索引收口：块位置只存局部量（span + gap）

复核报告 2.2 的尾巴。原来投影算内容、之后另起一趟拿 `intervalOf` 递推块起点（每块 3 次
查表），两处 `max` 在调和"块起点有两个说法"。改成：投影走树时维护流游标，`flush` 时记下
两个**局部量** —— `span`（本块内容几位）与 `gap`（它前面那道界几位）。绝对位置一个都不存。

改法：
- `rev::BlockExtent{span, gap}` + `Projection::extents`（与 keys 同长同序）。
- `Walker` 加 `flow_` / `block_start_` / `prev_end_`：容器两端各一位、文本按码点、原子与
  标记各一位，与 `FlowIndex::measure` 同一套展开规则。`noteFirst` 顺手钉 `block_start_`。
- `block_flow_` / `block_flow_span_` 退化成前缀和缓存，每轮 `buildBlockFlow()` 一次加法循环
  重算；两处 `max` 与"标记查不到"的兜底删除。
- 复用块也在 extents 里 —— **`canReuse` 在 `flush` 里，跳过的是"物化块"不是遍历**，
  所以游标一直是对的（复核报告里"复用跳过了它们"那句对的是物化）。

判据：
- `edit_test` [62]（19 条）：起点回读到段首、块间距 ≥ 1、`Σ(span+gap) + 末尾边界 == 流总长`
  （右边来自流索引，独立来路）。三个文档：正文 + 隐藏控件（两种模式）、表格在中间、以表结尾。
- `auditCompile` 加精确对拍：带标记的块 `start + span == 标记起点`（独立于块流）。
- 故障注入（删"出格"那一位）红 11 条：`[62]` 两条守恒各差 4（2×2 表四道格边界），另有多条

## 载荷类型化：wasm 能不能生成 TS / schema 生成两端的方案（2026-10-21 夜）

用户问两件：wasm 无法直接生成 ts 吧？一份 schema 生成两端要用什么方案？

**第一件的答案**：wasm 里没有类型可导出。`WebAssembly.Module.exports()` 只给 `{name, kind}`，
参数只剩 i32/f64，参数名与字段名编译时擦掉；DWARF 只描述 C++ 实体、release 又剥掉。
能生成的只有**声明**，输入必须是源码或 schema。三条输入实测：
- 本机只有 `clang-format.exe` / `clang-tidy.exe`，**没有 clang.exe**（`VC/Tools/Llvm/bin` 与
  `C:/Program Files/LLVM/bin` 都没有）⇒ "从 C++ 结构体反射生成"得先装 LLVM。
- 就算装了也只覆盖 46/62（16 个键不是字段名）。
- 从手拼源码正则抽键名可行：**19 份载荷 / 245 个键**（`out/_extract_payloads.py`）。
  但**抽不准种类**：`o.precision(3)` 是流的全局设定，同流里的整数不受影响 ⇒ 数字键的
  int/小数位只能靠人声明。

**第二件的答案**（推荐方案）：schema 只接管"没人守的那一半"。
`o << "\"relaidLines\":" << e.relaid_lines` 一行里两个标识符：`e.relaid_lines` 有编译器守，
`"relaidLines"` 没有 —— 漂移只可能发生在后者。所以 schema 存 (载荷, 键名, 粗种类)，
**不生成表达式**；C++ 侧生成 `constexpr K relaidLines{"relaidLines"}`，调用点
`o << kv(pk::edit_stats::relaidLines) << e.relaid_lines`，两边就都被守住了。

产物三份：`docs/payload_schema.json`（唯一手写）+ `src/core/engine/payload_keys.gen.h`
+ `web/payload_keys.gen.js`（键表 + readPayload + JSDoc）；生成器 `scripts/gen_payloads.py`
带 `--check`。

**校验放哪的实测**（`out/_bench_validate{,2}.mjs`，62 键对象，node 22）：
- 朴素 `in` + `Object.keys(spec)` 每次：**18.3 µs（parse 的 +203%）** —— 键表每次重建。
- 预取键表 + typeof：**4.2~4.3 µs（+45%）**。
- C++ 写侧一次 strcmp/键：≈ 300 ns/份 ⇒ 可以常开。
⇒ 结论：写侧断言常开、读侧校验默认关（`?strict=1` 与探针里开）。

规模：19 份载荷 / 245 个键 / 79 个跨载荷重名（键表必须按载荷分组）/ 16 个写出函数 /
33 处 `JSON.parse(mod.X)`。样张在 `out/_sample.gen.h`、`out/_sample.gen.js`。

### 追加：方向修正（用户澄清）

用户两条修正：① 要的类型化是**给外部用的**，内部类自己写自己用，不给外部看的不必；② 但为了好维护，
**内部最好也类型化**。⇒ 真相的位置反过来了：**契约在前，C++ 在后**（我上一版提议的是"schema 存
键表供内部写出器用，.d.ts 是副产物"，方向反了）。

公开面实测（`web/engine_api.js` 三张表）：WRITE 51 条 / 39 条带参 / 36 个参数名 / **57 处静默强转**；
READ 50 条 / 8 条带参 / 7 个参数名 / 7 处强转；SILENT 1 条。READ 返回：21 份对象、5 份数组、
**24 条裸值**（frameWidth / text / buildStamp …）。合计 102 条命令、45 个参数名、64 处强转。

内部类型化的三档保证（都要 table 驱动）：
1. 键名不来裸字符串（生成 `Key<Kind::num>` 常量）；
2. 值的类型对（`w.num(Key<Kind::num>, v)` 只吃数，传布尔键编译错）；
3. 每个键恰好写一次（`w.end()` 断言，≈300 ns/份）——这条编译器做不到，只有断言能。

引导办法：跑一遍引擎，把 50 条 READ 的返回值 dump 成形状，冻结成 `api.json` 的 payloads 初稿
（与摘要常量同构：从现状取基准，然后由它守）。

### 外部接口现在长什么样（2026-10-21 夜，为类型化定范围）

用户问"给外部的接口也是 read/write 这种吗"。实查下来是**三张面**，read/write 只占一张：

1. **向下（命令面）**：`api.read(name, args)` / `api.write(name, args)`，字符串派发 102 条
   （WRITE 51 / READ 50 / SILENT 1）。Worker 侧同表走消息 `{t:'do'|'ask', name, args, ts|id}`。
   另有 15 个具名方法：boot / do / ask / view / pageCanvas / viewMode / setViewMode / relayout /
   sendState / geom / attach / engine / scrollY / viewSize / state。
2. **向上（状态面）**：`{t:'state'}` **25 个字段**，内嵌 **6 份载荷**（controls / dirtyPages /
   selection / layout / caretStyle / selectionStyle）。同一份 stats 既能被 `read('stats')` 拉、
   又被 state 推 —— 两条到外部的路，声明必须同时覆盖。
3. **反向（宿主适配）**：`host` **10 个回调**，8 个必需（blitPages / invalidateSlots / slotCount /
   pagesMissing / setViewMode / loadGlue / blitStats / addCanvas）+ 2 个只给 selfCheck
   （ctxOfPage / canvasCount）。
传输：宿主发 **7 种**消息（boot / pageCanvas / viewMode / view / do / ask / zoom），引擎回 4 种
（state / ack / reply / error）。

**查出真 bug（尚未修，待用户点头）**：`worker_host.js:1498` 在 DPR 变化时 post
`{t:'zoom', zoom, dpr}`，而 `engine_worker.js` 只认 6 种 —— **从来没有 zoom 分支**
（`git log -S "m.t === 'zoom'" -- web/engine_worker.js` 为空，`{t:'zoom'}` 由 c875715 引入）。
后果：窗口拖到另一块显示器 → 薄壳抛"未知消息类型 zoom" → 宿主显示红色错误条 + **缩放没生效**
（仍按旧密度）。单线程宿主走的是 `api.engine().setZoom()`（app.js:692），没这个问题。
★ 为什么一直没发现：探针跑在无头 Chrome 上，DPR 永远不变；而消息类型是字符串，编译不报、
  探针不报。**这正是"契约没有声明"的代价**，也说明 `.d.ts` 里 `t` 必须是字面量联合。

类型化要写的是 4 个 interface + 1 个联合：EngineApi / HostAdapter / StateMessage / Payloads /
WorkerRequest（`{t:'boot'}|…|{t:'zoom'}`）。

### 用户指出：外部接口是毛坯房，应该是"实例化编辑器 + 调它的方法"

对。**`createEngineApi` 不是使用者接口，它是传输侧门面**（要求调用方提供 post 与 10 个宿主
回调）。编辑器对象其实已经有了，只是不像 API：

- `createEditor(container, {chrome})` → `facade` **111 个成员平铺**（诊断 audit*/selfCheck/
  markCheck/rawFrame 与产品方法 type/undo/selection 混在一层，还夹着 textarea/canvas/container/
  hostErrors 这些内部件）。
- `createWorkerEditor(...)` → `host` **62 个成员**，用**四种方式**拼出来（对象字面量 / 逐条赋值 /
  `Object.defineProperty` / `Object.defineProperties` 访问器表），没有一个地方能看全。
- 两边交集只有 **46**：同一件事两个形状，探针只能挑交集用。共用的那 46 里还包括 stats/editStats
  这种账本。
- 构造参数只有 `(container, opts.chrome)`：字体、初始文档、页模式、传输方式、只读都不在里面。

目标分层：L3 `Editor`（产品面，要类型化的就是它）/ L2 宿主实现 / L1 `engine_api`（传输面，
只对"自己写宿主的人"开放）/ L0 wasm。诊断另开 `editor.diag`；一律 Promise 但返回可同步读的
thenable（沿用路 C 的 then1，in-thread 不进微任务，探针"调完立刻读"不变）。

顺序：① 先分组（产品 / 诊断 / 内部）+ 一份 `Editor`/`Diag` 声明（不改行为，两边的 65 个差
当场显形）→ ② worker_host 收成同一形状 → ③ `createEditor` 收成统一入口（内部选传输）→
④ 才生成 `.d.ts`。

## 外部 API 设计（2026-10-21 深夜，出文档 + 契约）

产出两份：`docs/外部API设计.md`（424 行）+ `web/types/editor.d.ts`（287 行，`tsc --strict` 0 错，

设计要点：
- 35 个成员：文档 5 / 编辑 8 / 光标选区 9 / 控件 4 / 视图 3 + `configure` `config` `flush`
  `destroy` `element` `on`；诊断 33 个进 `editor.diag`。
