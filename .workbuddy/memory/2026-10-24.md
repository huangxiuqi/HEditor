## 表格内边距 / 行距 / 基线吸附 —— 按 Word 口径改掉（已落地）

三条改动，全部改完并重跑判据：

- **单元格内外边距拆开**：`kTableCellPadXPt = 4.0f`（左右，原有）/ `kTableCellPadYPt = 0.0f`
  （上下，Word 默认）。行高 = 内容高（+ 0），新插 3×3 表从 27.2pt 变成一行高（12pt/1.0 → 17.376pt）。
  行高兜底下限改成 1pt：`row_h <= 0` 会让格线、命中与翻页同时退化。
- **行距换成 Word 语义**：`pitch = (ascent + descent) × line_factor`，单倍行高是字体自己的
  1.448 em（NotoSansSC 的 hhea 1160/288）。倍数从此线性：12pt 下 1.0 → 17.376 / 1.5 → 26.06 /
  2.0 → 34.75pt。空段也走同一个基准（原来空段是 `size × lf`，与有字的段差 5.4pt）。
  竖排列宽（`block_line_h`、`col_w_max`）同步换基准。默认 `line_factor` 1.6 → 1.0
  （ParaFormat 与 BlockSpec 两处），示例文档的倍数按 /1.448 换算（1.5→1.05、1.6→1.1、
  1.75→1.2、1.8→1.25、1.85→1.275、1.9→1.3）。
- **基线吸附整设备像素**：`Bitmap::drawGlyphs` 里 `pos = (xs[i], round(ys[i]))`，横向保留小数。
  对照实测（同文档、96dpi）：一整页墨迹像素的中间灰占比 80.1% → 78.8%，实地墨 +5%；
  逐字看是"横笔从跨两行各 50% 变成一行实地"。页画布 CSS 尺寸 round(pw/dpr) 那条次因没动。

判据跟着改的：`shaping_test` [9] 的列宽/行高三条改成按字体度量算（原来写死 `size × lf`）、
整行换页那条把页高从 60 改成 45 才构造得出换页；`edit_test` 竖排光标宽度、连页行距两条同样
改按字体度量；`edit_test` 三个排版摘要（A/B/C）重取成 0xb27e1602e6412913 / 0xe4def2d955859da1 /
0xb84b78929b637322（行数、字形数一字未变，只有页数变）；`model_test` 默认格式断言 1.0。

## 改之前的口径（留作对照）

- 单元格内边距：`kTableCellPaddingPt = 4.0f`（layout.h:322），四边同一个常数，排版与绘制共用
  （layout.cpp:924 / 939 / 1052-1059）。不来自样式，TableStyle 未落地。
- 没有引擎级最小行高：行高 = max(最高格内容高 + 8pt, RowSpec.height_pt)（layout.cpp:939），
  8pt 那条只对"完全无内容"成立。空段也有一枚行盒（layout.cpp:1139-1168），高度取
  `b.size_pt * b.line_factor` —— 默认 12×1.6 = 19.2pt，所以新插的 3×3 表行高是 27.2pt。
  `demoTableTree` 第二行显式 AtLeast 36pt（demo/demo_documents.cpp:396），那才是"字再小也不变"。
- 行距：`line_h = max(max_size * line_factor, ascent + descent)`（layout.cpp:381-387）。
  NotoSansSC-VF 的 hhea 是 1160/288 → 下限 1.448 em，于是 1.0 / 1.25 / 1.448 三档输出逐像素
  相同，1.5 只比 1.0 高 3.6%（17.376 → 18.0pt）。语义等于 CSS unitless line-height，
  不是 Word 的"倍数 × 自然行高"（Word 的 1.5 倍 ≈ 2.17 em）。
- 空段与有字的段是两套式子：空段 = size×lf（无下限），有字 = max(size×lf, 1.448×size)。
  lf=1.0 时空行 12pt、有字的行 17.376pt，同一格式下空行反而矮 5.4pt。
- 字重不是问题：非加粗 400（`kWeightRegular`）、加粗 700；实测 16px 汉字竖笔落在正文色 24
  （全覆盖），不是 VF 默认实例 100。
- 发虚的三个来源：灰度 AA（帧是 RGBA，用不了 LCD 子像素，bitmap_skia.cpp:360-362）；
  基线不吸附整像素（engine_paint.cpp:399 直接给 float px，`setBaselineSnap(false)`）；
  只做纵向 hinting（kSlight）。12pt/1.6 的行高 19.2pt × 4/3 = 25.6px，基线逐行漂 0.6px：
  首行 2cm+13.92pt → 94.15px（.15），第五行 .55。一页正文 78~81% 的墨迹像素是中间灰。
- 次因：页画布 CSS 尺寸 round(pw/dpr)（pages.ts:190-191），小数 DPR 下与背衬差半像素，
  整页被浏览器重采样一次。

## 表格七条缺陷 + 工具栏表格尺寸下拉

### 排版层：行跨页改成"按行盒自己的纵向位置分页"
`splitRow` 原来按**数组后缀**搬行：一行里几个格的行盒在数组里是"格序"而不是"纵向次序"，
搬「第 k 个之后」会把同行其它格的行盒一起搬走 → 空格子的光标跑到下一页。
现在 `closeRow` 里分两条路：`sliceRowByPage`（按行盒的 `block_lo - row_top` 稳定排序后
逐条归片，切点落在行与行之间）与 `sliceRowByBand`（连页只按条带切绘制片段，行不拆）。
片段记 `RowPiece{page, box_top, content_top, box_bottom, cont_top, cont_bottom}`，
`PlacedRow` 由它直接产出。
**顺带修掉的静默溢出**：原判据 `f.row_top > cy + 0.01` 让"从页顶起排且比整页还高的行"
完全不切，内容排到页外被裁掉（"格内换行之后字没了"的形态之一）。现在页顶也切；
只有"本页剩余连一行都放不下"才整行挪走（`sliver`）。
字形平移只在真被切过时走一遍，且只看 `f.glyph_begin` 之后那一段（大表上的 O(行×字形) 回归）。

### 绘制：跨页切口补线，条带切口不补
`emitTables` 里 `skip_cut = cont`：分页模式两条切口边照画（用户要的"第一页下边框、
第二页上边框"），连页模式不画（条带不是页边界，画了就是断口）。判据是像素级的
`lineLike()`（整行 75% 以上是深色才算一条线，避开文字）。

### 连页表格"断成两截"的真实原因
`EngineConfig::continuous` 才是开关，`PageMetrics::continuous` 是 `setConfig` 装配出来的
派生量 —— 判据里写 `page.continuous = true` 是无效的（我第一次就这么写，白跑两轮）。
另外旧代码里 `pr.y` 首片用块轴**绝对** y、续片用 `cy`，两种口径混在一份几何里，
连页下整张表被推到带外。现在两条路都只写页内坐标。

### 命中：落在格框里的行盒优先
`hitTestPt` 只按块轴距离比，同行的多行格低位行盒永远更近 → 点空单元格下半部分跳到多行格。
加了 `rank`：点同时在 `[cell_box_lo, cell_box_hi]` 与 `[cell_top, cell_bottom]`（页内口径，
连页要先折回带内）之内时压过其余行盒。**格的纵向范围必须用整格，不能用行盒**。

### 空单元格的字符格式：落到段落标记上
`rev::MarkPayload` 加 `CharFormat marks`；`SetParaMarkFormat` / `InsertParaMark` /
`RemoveParaMark` 同步带上它（分段与合并要传下去，否则分段即丢格式）；`canApply` 的
"原值比对"要连 marks 一起比。`applyCharFormat` 遇到段落标记也落笔，
`marksAtFlow` 找不到文本兄弟时读标记那一份（敲字继承），`charFormatAtCaret` 同理，
`BlockSpec` 加 `weight/italic/underline` 三个块级默认字段让 `effectiveRuns()` 也读得到。
落盘：`m` 键两个载荷共用，读端的一致性检查改成"Run 认 m、Mark 也认 m、其余不认"。

### 单元格上下内边距 = 2pt
`kTableCellPadYPt` 从 0 改成 2：零内边距时光标正好压在上下格线上（"光标凸出来"）。
行高 = 内容高 + 2×内边距；`shaping_test` 的行高判据、`edit_test` 的排版摘要
（0xe4def2d955859da1 → 0x6e4147ed798fdb6c，157 行 / 13 页）都按新口径重取。

### 工具栏：表格尺寸面板
新增 `web/app/ui/{popover,menu,grid-picker}.ts`，`Item` 多一支 `Menu`（`panel(dismiss)`）。
`main.ts` 的表格按钮改成一个 8×8 网格 + 标题行开关，选完即插。弹层用 `position: fixed`
贴锚点、点外面 / Esc / 滚动都关；面板每次打开新建一份，状态不跨开关累积。

### 判据
native 新增 [70]（格内换行 / 超高行切片 / 连页切片 / 命中，31 条）与 [71]（空单元格格式，
13 条）；`insert.spec` 新增"格内换行第二行要画出来（auditFrame/Base/Page 全 0）"与
"表格按钮先出面板再按所选行列插入"；`smoke.spec` 的表格那一步改成先点开面板。
结果：native 4/4（edit 1562+ / shaping 151 / doc 846 / rev 338）、`npm run check` 全绿、
格式化 126 文件全合规。

## "偶发红"查清：一个测试基建缺陷 + 一个产品缺陷 + 一处读数顺序错

**结论：不写"偶尔/偶发"这种结论。** 判据要么绿要么红，红了必须给机制。这一轮把出现过
的三种红都追到了根上：

1. **`edit.spec` 撑破超时（测试基建）**：它一份就有 367 条判据、13 个场景、七次装载，
   单跑 95~120 s；12 份 spec 并行时同时有两份 wasm 引擎与两个 Chromium，实测超过全局
   `timeout: 180_000`，报 `page.evaluate: Test timeout of 180000ms exceeded`（不是某条
   判据红）。修法：`test.setTimeout(600_000)` 只给这一份，全局预算留给普通用例 ——
   超时是挂死检测线，不是性能门槛。
2. **拖选抬手丢最后一次移动（真产品缺陷）**：`drag.end()` 当场把 `st` 置空，把"抬手前
   还在飞的那次命中"连排队点一起丢掉；Worker 宿主上一次命中是一次往返，所以快速松手时
   选区停在抬手之前那一格（判据 `拖出去再拖回来收成空选区` 红，报 anchor 1 / focus 36）。
   修法：抬手点补一次 `applyAt`（`mouseup` / `pointerup` 才补，`pointercancel` 不补）；
   `end()` 拆成"摘监听 → 等队列排空再清状态"（`closing` 标记 + `gen` 让旧回包作废）。
3. **光标色判据采样到白色（读数顺序错）**：`stopBlink()` 只写相位、不 present（它要留着
   上一次全量的账），而那段把 `setCaret` 写在 `stopBlink` 之前 —— 读到的是"相位正好关着"
   的那一帧。修法：先 `stopBlink`、再 `setCaret`（带 present）。这条不是负载问题，
   以前偶发只是相位运气。

验证：`edit.spec --repeat-each=2` 并行连跑全绿；全量 48 条并行连跑两遍 48/48
（4.3 min / 4.0 min）；验收口径（`test:dist`，`npm run build:app` + 48 条）也全绿（3.6 min）。

## 表格跨页三连 + 外壳四件（2026-10-24 下午）

用户报的九条里，六条落在表格跨页上。查清四个机制（细节见 TRAPS 210~213）：

1. **切片只挪行盒、不挪字形**（210）：`sliceRowByPage` 改了行盒的 page 与 y，字形只加了
   dy、page 留在旧页。字形按页号区间画 ⇒ 切到下一页的那一整行字画在上一页、按平移后的 y
   叠在别的字上，新页上一个字都没有。三份自审（layout / page / glyphPages）全是 0，
   因为两边同错。这就是用户说的"格内换行没渲染""新增的换行符不显示"。
   修法：位移表里带上 page，字形跟着改。
2. **连页下行的进给取了片段的页内下沿**（211）：第二行起整张表塌回带顶（"表格飞了"）。
   修法：连页用 `top + row_h`（块轴绝对位置），分页仍用 `box_bottom`。
3. **续排片段上的格没有行盒**（212）：命中先按"表 + 行片段 + 列边界"定格
   （`PlacedTable::cellAt`），再只在这一格的块区间里挑行；整格反白改按
   `cellBoxOnPage` 逐页铺（原来是按行盒，只在有行盒的那页出高亮）。
4. **连页接缝按"基线越过带底"筛溢出**（213）：字身越过去的那一截永远不补画。
   默认段距从 10 磅改 6 磅之后行位置整体上移，`edit_test` [59] 的分带/整带逐字节判据
   当场红（差 1 行、首行正好是带边界）。判据改成按字身外扩。

外壳四件：未保存离页拦截（`beforeunload` + dirty 标记）、左下角页数/字数
（`statusbar.setCounts`，字数 = 非空白码点数）、工具栏"模式"下拉（编辑/表单/只读）、
默认行距 1.0 与段后 6 磅（`wasm_main` 的 `loadTextDocument` 原来写死 1.05）。

判据：native 新增 [72]（37 条，跨页命中/整格反白铺两页/字形页号一致/连页逐行下推/
小表反判据），`edit_test` 摘要 B/C 因默认段距重取（行数与字形数未变）；
新增 `web/tests/specs/table.spec.ts`（5 个用例，含"折行之后的字按像素数墨"），
`smoke.spec` 补模式三档与页数字数。结果：native 4/4（1713 条 edit）、
Playwright 13 份全绿（53 条）、`npm run check` 全绿、格式化 126 文件全合规。

**遗留（未改）**：`caret().rect` 是设备像素、`selection().rects` 是磅，两者都不等于契约里
"CSS 像素"的口径；改它要连 13 份 spec 的坐标一起动，单独开一轮。

**补一条（同一轮查出来的第五个机制）**：页指纹不含表格片段几何 —— 一条行从"在页底被切开"
变回"整行落在这页"时，片段下沿从页底挪到行底，这一页可能一个字形、一条行盒都不变，
页被判成新鲜、边框停在旧位置（用户说的"渲染没更新"）。修法见 TRAPS 214：
`tablePieceDigest` 进页指纹 + `computeBand` 摘要变了就整页重画。

最终：native 4/4（edit 1713 条含新增 [72] 36 条）、Playwright 13 份 53 条全绿、

## 表格第二批：页索引与行带（2026-10-24 傍晚）

用户报的三条（第二页的空行没有段落标记、第一行后面几列的空格也没有标记、第二行第一格的
第二行文字没渲染）指向同一批假设，查出来两个机制（TRAPS 215 / 216）：

1. **行数组不按页单调、数组相邻也不等于版面相邻**。表格里一条高格切到第二页之后，
   它的续排行排在兄弟各格的前面（页号倒退），而"同一格第 2 行之后紧跟的是另一格第 1 行"
   （在它上面）。旧代码四处按这两条假设写的：`glyphRangeOnPage` / `CaretResolver::linesOnPage`
   二分取页区间（漏字形 = 文字不渲染，漏行 = 标记不画）、页指纹混的也是二分区间（漏掉的
   字形让页判成新鲜）、`lineBand` 用数组相邻项推上下沿（带被压成零高，那一行永不重画，
   段落标记一帧帧叠成"一堆换行符"）、行带两端取"变化行的最小/最大下标"（表格里最大下标
   不一定最靠下，带只盖住页首）。
   修法：`LayoutResult::page_lines` / `page_glyphs` 页索引（排版收尾 + "拼接"路径重建）、
   `pageLineBands` 按块轴排序分组取中线、行带两端取所有变化行的并集。
2. **页索引建得太贵**：第一版在 2000 段 / 4.5 万字形下把增量排版拖到 59.2 ms
   （全量 227 ms，编辑面那条 <20% 的判据红了）。先数后填 + 只在拼接路径补建 → 7.0 ms。

判据：native 新增 [73]（18 条：页索引覆盖、每条空行的标记都有墨、格内逐字输入每步
页位图 == 从零光栅、正文反向对照）；`table.spec` 新增"空格的段落标记：每一页上每一格都要
画出来"。结果：native 4/4（edit 1746 条）、Playwright 14 份 54 条全绿、
`npm run check` / `check_docs_cpp` / `lint_comments`（168 文件 0 处）全绿、
`format.ps1 -Check` 126 文件全合规。

## deps_init.ps1：另一台机器上 `rev-parse FETCH_HEAD^{commit}` 退出码 128

症状：`git submodule update` 与 `fetch` 都成功（日志有 `* tag 14.6.0 -> FETCH_HEAD`），
紧接着 `git -C <submodule> rev-parse FETCH_HEAD^{commit}` 退出 128，脚本中断。

判定：这条是脚本里**唯一带 `^` 的命令**，前面所有 git 调用都不带 `^` 且全部通过 ——
所以差异在环境而不在逻辑。两种环境差异都能造成 128：
`git` 被 `.cmd`/`.bat` 垫片包着（cmd 把 `^` 当转义符，实参变 `FETCH_HEAD{commit}`，
git 报 ambiguous argument）；或 `FETCH_HEAD` 不可引用（临时文件被并发 fetch 覆盖 / 剥不出
commit）。本机复现了第一种的错误形态：`git rev-parse 'FETCH_HEAD{commit}'` → 128。

修法（不再依赖这两种机制）：fetch 用显式 refspec 落到本地 tag 引用
`+refs/tags/<tag>:refs/tags/<tag>`，剥 commit 改用 `git rev-list --no-walk refs/tags/<tag>`
（同样 peel，但不需要 `^`）。`Get-GitOut` 原来 `2>$null` 把 git 的 stderr 全吞了、
只报"退出码 128"，现在失败时连 stderr 一起抛 —— 这条比修法本身更重要，否则下次还是瞎猜。
文档同步：`docs/依赖与工具链管理.md` 那句"从 `FETCH_HEAD^{commit}` 解析 commit"已改。

注意：`$HbTag:refs` 在双引号里会被当成驱动器限定变量，必须写 `${HbTag}`。

## 工具链（`.toolchain`）补了引导脚本

原来 emsdk / gn / ninja 三件全是手工放置，`deps_init.ps1` 不管、`build_skia_wasm.ps1` 缺了只
抛一句"需要先就位"，版本记录也只活在一句注释里。新增 `scripts/toolchain_init.ps1`，pin 如下：

| 件 | pin | 判据 |
| --- | --- | --- |
| gn | `2222 (3c7785ec2008)`，源码 commit `3c7785ec2008e43c9efeae4ade0522cd36873833` | `gn --version` 原样输出 |
| ninja | 1.13.1 | zip SHA-256 `26a40fa8…`，解出的 ninja.exe 与机器 1 的**逐字节相同** |
| emsdk | 安装器 commit `35ff8a6d` + SDK `6.0.12` | `upstream/emscripten/emscripten-version.txt` |

关键结论：**gn 没有可下载的制品**。`.toolchain/gn/gn.zip` 里是 `out/gn.exe`（源码构建的布局），
CIPD 的 `gn/gn/windows-amd64` 里查不到那个 commit（`git_revision:3c7785ec…` 回 `no such tag`，
翻两页 400 条实例也没有；`version:2222` 也是 404），Skia 自己 `bin/fetch-gn` 钉的是更旧的
`2175 (b2afae12)`。所以脚本对 gn 只校验、不下载，缺了就报错并给出"拷 2.3 MB 的 exe 或现编"
两条路。顺序上把 gn 排在最前（fail-fast），免得白等十几分钟下完 emsdk 才发现这一步过不去。

两个实现细节值得记：`Expand-Archive` 在 5.1 上会把进度条刷满控制台且慢一个数量级，
改用 `System.IO.Compression.ZipFile::ExtractToDirectory`；emsdk 的 GitHub 归档**字节不稳定**
（同一 commit 两次下载的 zip 哈希不同）所以只钉 commit 不钉哈希，否则必误报。

★ 第一版把解包目标写成 `%TEMP%` 下的**固定名字**，解包前"目录已存在就 throw"，于是**失败一次
之后每次重跑都卡在同一句报错上**（另一台机器上就是这么撞的）。引导脚本必须可重跑，改成：
ninja 直接从 zip 里取 `ninja.exe` 条目落盘（没有暂存目录）、缓存的包按 sha256 判断能不能复用；
emsdk 的安装器解包后写一枚 `.heditor-emsdk-repo` 标记，重跑时标记对得上就只补
`emsdk.py install`（能接着上次的下载继续），对不上才把旧树改名挪开重取；整棵解包前先清掉
上次留下的半棵树。判据是四遍跑：全新（下载+解包+install 失败）→ 失败后立刻重跑（不再报
"已存在"，接着 install）→ 删掉 ninja.exe 留着 zip（哈希命中，不重下）→ 删掉标记（改名挪开重取）。

## Skia 取源码那条路：三个"白下/卡死"都修了

`build_skia_wasm.ps1` 的取数（Skia 源码 80 MB + 6 个外部依赖）原来有三处会让大文件白下：

- curl 直接写最终文件名，断了就是一份 77 MB 的半截包；`Test-Path` 放行、体积检查（>20 MB）
  也放行，于是每次解压失败、**永远不重下**，只能人手工删。
- 没有续传，也没有重试。
- 钉住的归档里有**一条符号链接**（`src/ports/fontations/Cargo.toml -> ../../../bazel/...`），
  Windows 自带的 tar 建不了（要开发者模式/管理员），`Invalid argument` 让整次解包 exit≠0 ——
  也就是说"换 Skia 版本重取"这条路本来就是断的，跟这轮改动无关。

改法：下载写 `.part`、`--retry 5 --retry-delay 3 -C -` 续传、成功才改名；解包先用
`tar -tvzf` 扫出符号链接逐个 `--exclude=` 跳过；解不开时用 `tar -tzf` 分辨两种原因 ——
清单读不出（包坏了）→ 改名 `.bad` 下次重下，清单读得出（文件系统拒绝某类条目）→ 保留包，
别白扔 80 MB。六个外部依赖同样处理，只是解不开就直接删包重下（都只有几 MB）。

★ 扫符号链接**不能按列号切**：`tar -tv` 的列随 locale 变，中文 Windows 上是
`lrwxrwxrwx  0 root   root   0 10月 09 18:19 <path> -> <target>`（多一列链接数、日期带中文），
只能拿 `\d{1,2}:\d{2}\s+` 当时间锚。按列切的写法一条都没匹配上，表现就是"改了等于没改"。

判据：把 `$SkiaPkg` 指向隔离目录跑 `-Fetch`（真树不动）—— 跳过 1 个符号链接、源码就位、
戳记写出、六个依赖到位；再把包截到 25 MB —— 认出来、改名 `.bad`、报错说明重跑会重下。
真树事后复核：`skia-main` 只有一棵，戳记、`out/wasm/libskia.wasm.a`、7 个 externals 都在。
（`out/_untar_probe` 是测试留下的 182 MB 残留，删除守卫挡了批量删，留着待清。）

## CMake 改成无本机路径：`msvc_env.ps1` 取代 `CMakeUserPresets.json`

问题：`CMakeUserPresets.json` 里写死了 VS 的版本号目录（`14.44.35207`、SDK `10.0.26100.0`），
升级 VS 或换机器就得手改；预设名还因此分叉成 `native-local`。

做法：`CMakePresets.json` 只留一份、不含任何本机路径；MSVC 环境由
`scripts/msvc_env.ps1` 进 —— 它是微软 `Enter-VsDevShell` 的薄封装（vswhere 取 instanceId，
已进过就跳过），跟开始菜单的「Developer PowerShell for VS 2022」是同一件事。用法
`.\scripts\msvc_env.ps1` 之后 `cmake --preset native`。`CMakeUserPresets.json` 已删，
`native-local` 这个预设法消失。`CMAKE_MAKE_PROGRAM` 从用户预设搬进 `CMakePresets.json` 的
`base`，四个预设共用。

★ **我先前那条"沙箱里 cmd 不可用"是错的**：cmd.exe 只在**命令文本**这一层被校验层拦
（"Invoking cmd.exe from Bash bypasses all command validation"），运行期能起 ——
`Enter-VsDevShell` 内部就是 `cmd /c VsDevCmd.bat`，在 PowerShell 工具里跑得好好的。
所以不必像第一版那样自己拼 INCLUDE / LIB / Path（那一版还把 SDK 根目录少取一层，
拼出 `Include\Lib\...`，构建期才以 `LNK1181 无法打开输入文件 kernel32.lib` 暴露）。
教训：被拦的是我的命令串，不是那个程序；先试官方封装，再决定要不要自己造。

另外 VS 生成器在这台机器上配不起来，报 MSB6001「已添加项。字典中的关键字:'HTTPS_PROXY'
所添加的关键字:'https_proxy'」—— 沙箱进程环境里同名不同大小写的两个代理变量，MSBuild 的
.NET 字典大小写敏感（和当年 PATH/Path 同族）。系统环境里没有这两个变量，所以只影响沙箱内的
MSBuild，不影响 Ninja。

判据：`cmake --preset native` 1.4 s 完成、`cmake --build --preset native` 通过、
`ctest --preset native` 4/4（166 s）、`cmake --preset wasm` 配置通过（预设里新加的
`CMAKE_MAKE_PROGRAM` 对 wasm 无副作用）。
