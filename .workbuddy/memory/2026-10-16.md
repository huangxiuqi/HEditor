## 一、拖选"第一次拖不动，必须再拖一次"：根因与修复

**症状**：焦点不在编辑器上时（刚点过别处），第一次在正文上按下并拖动，选区不动；
第二次就正常。两宿主都复现。

**根因**：`web/drag_select.js` 把 `blur` 当拖选收尾信号，挂在 **window 的捕获阶段**。
`blur` 不冒泡，但**捕获阶段会经过 window**，于是任何一个元素失焦都会命中它。而宿主在
按下的同一条链里末尾就是 `ta.focus()`（不这么做键盘会整个失灵），焦点从别处挪到输入框
必然派发一次 blur —— 刚 `begin()` 起来的拖选当场被 `end()` 收掉。

**证据**（`scripts/diag_selperf.mjs` 新增 L 段，单线程宿主）：

- 修复前：先把焦点挪到 body 再拖 → `drag.active=false`，选区停在 `1..1`、0 条矩形。
- 修复后：同一手法 → `drag.active=true`、选区 `1..6`、1 条矩形，与前两次完全一致。

**修复**：`blur` 只在**窗口自己失焦**时收尾（切标签、切应用 —— 那之后 mouseup 真的不会
到达页面）。做法是注册时不带捕获，再加 `ev.target === window` 判据。

**反证**（同文件 N 段，两宿主都跑）：窗口失焦必须收尾（`true → false`），元素失焦必须
不收尾（`true → true`）。只验后一条的话，"把收尾信号整体删掉"也会被判成对的。

## 二、"两个宿主都不跟手"的结论：远程桌面软件的延迟

用户确认之前是通过远程软件操作的；**真机上没有延迟**。这一轮把每条可能的代码路径都量了，
结论一致：JS 侧没有瓶颈。

`scripts/diag_selperf.mjs` 新增 M 段（一次移动占主线程多久：窗口捕获阶段一前一后两条监听
夹出宿主处理一次 mousemove 的耗时，外加 rAF 帧间隔）：

| 场景 | 处理一次移动占主线程（中位 / 最大） | 拖动期间帧间隔（中位 / 超 25 ms 帧数） |
| --- | --- | --- |
| 单线程·短样例 | 2.2 / 5.2 ms | 16.5 ms / 0 |
| 单线程·2000 段小选区 | 2.7 / 4.2 ms | 16.5 ms / 0 |
| 单线程·2000 段整篇已选 | 3.4 / 5.4 ms | 16.6 ms / 0 |

## 三、光标与选区的样式做成可配置参数

**引擎**：`EditorEngine::setCaretAndSelectionStyle(caret, widthPt, selection)`（`engine.h/.cpp`）。
与 `setConfig` 分开的理由是代价：`setConfig` 会置 `base_valid_ = false` ⇒ 底图全建 ⇒
窗口里每一页重新光栅（3 页约 32 ms），取色器连续改时每一下都付这笔钱。样式参数只在绘制期用
（光标与选区都画在帧上，见 `presentInternal`），所以这条路径**不动底图**，也**不清**
`caret_rect_px_prev_` 与 `selection_rects_prev_` —— 那两份正是下一次呈现用来把旧样式的像素
从帧上擦掉的依据。宽度下限 0.4 磅提到匿名命名空间的 `kMinCaretWidthPt`，与 `setConfig` 共用。

**wasm 门面**：`setCaretStyle(r,g,b,a,widthPt)` / `setSelectionStyle(r,g,b,a)` /
`caretStyleJson()` / `selectionStyleJson()`；色通道在入口夹到 0~255。

**两宿主门面**（形状逐字对齐）：`caretStyle` / `selectionStyle` 取值器，
`setCaretStyle({color, widthPt})` / `setSelectionStyle({color})`。缺的字段按**现状**补全，
默认值只在 C++ 的 `EngineConfig` 里有一份。单线程宿主补一次 present（`presentStyleChange`，
不滚动视口）；Worker 侧两条运算进 `PRESENT_ALWAYS`，样式随 state 推过来（宿主侧同步读）。

**演示页**：`index.html` 工具栏加"光标（取色器 + 宽度）"与"选区（取色器 + alpha）"，
初值从引擎读；`worker.html` 的工具条同样加一组，首份 state 到之前不接收 input。

**判据**（`scripts/edit_probe.mjs` 第 [21] 节，两宿主各 14 条）：正面是"改了样式，帧上那个
像素真的变成新颜色"（读 `rawFrame` 采样）；反面是"改这一拍**不整窗重光栅**" —— 参考臂量整篇
重绘的写入量（1127952 px / 帧 1127859 px），改样式那一拍只有 186 px，判据取"少一个量级以上"。
另有宽度参数改的是**画出来的粗细**（数整帧上光标色的像素面积：0.4 磅 vs 6 磅）、宽度下限夹取、
通道越界夹取、选区矩形内像素取纯红。

**踩到的单位坑**：`selection.rects[].x/y/w/h` 是**页面磅**（另带 `page`），**不是帧像素** ——
第一版按帧像素取矩形中心，读回来一片白（判据红了才发现）。换算：
`x = pt.x * zoom`，`y = (page - windowFirstPage) * (pageH + gap) + pt.y * zoom`。

**判据现状（全绿）**：`edit_probe` 361（两宿主）· `worker_probe` 68 · `multi_probe` 35 ·
`error_probe` 19（两宿主）。注释违规基线 149（本轮前后持平）。

## 四、页懒加载：把"换窗那一拍"的钱挪到空闲帧里

**症状**：匀速滚到末尾时页面一直是空的，停下来还要几百毫秒才渲染出来；Worker 更差。

**量出来的事实**（`scripts/diag_selperf.mjs` 新增 O 段：页面内逐帧推进 scrollTop，
每帧记账"可见页里有几张没有画布"、窗口改写次数、最贵那一拍、停下后多久画对）：

- 一次换窗（3 页窗口）中位 **19~25 ms**：字形 8~11 ms + 铺面积 4~6 + 帧搬运 5~12；
  首次见到某页（冷字形）要 **40~90 ms**。
- 每 3 s 滚动里窗口改写 14~28 次，**可见页缺画布出现在 6~17% 的帧**（每帧缺 1 页）。
- 视口越高越差：视口 1200 → 1800 → 2600 px 时缺画布比例翻倍（1 页 → 2 页可见）。
- Worker 比单线程差：每帧缺口多 1~2 帧（建画布要一次往返），停下后要 141~151 ms 才画对
  （单线程 46~74 ms）。
- **无头浏览器复现不出"一直空白"**：`--disable-gpu` 下滚动不是合成器线程驱动的，
  滚动位置与主线程渲染串行，窗口永远不会落后于画面。真机上的空白来自"合成器继续滚、
  而主线程在长任务里"—— 只能靠数字推。

**关键陷阱：重复文档会把字形缓存烘热。** 医疗样例是重复文本，画过一页之后字形全命中
（第 20 页冷 12.8 µs·字形 → 第 40 页 5.1）。用它量冷缓存必然得出"预热没用"的假结论。
正确做法是**同一页号、两次独立装载**做 A/B（Q 段）。

**改动**：

1. **字形预热**（`EditorEngine::prewarmPageGlyphs`）：把一页的字形画进一条页宽的临时窄带
   （`prewarm_`），只为把 mask 送进字形缓存，画面一个像素都不动。A/B 实测同一页：
   冷 14.57 µs·字形 / 整拍 44.5 ms → 预热过 6.97 µs / **25.7 ms**。
   ★ **必须 `prewarm_.shareFonts(base_)`**：Skia 的字形缓存按 strike 规格索引，而规格里含
   SkTypeface 的身份 —— 各建一份字体表就是两份互不相见的缓存，预热会静默地毫无效果
   （这就是第一次 A/B 得出"没起作用"的原因）。为此把 `font_mgr`/`typefaces`/`fonts`
   提成 `SkiaFonts`，由 `Bitmap::shareFonts` 共享。
2. **自适应窗口**：`maxWindowPages()` = 视口能装几页 + 2，上限 8，替掉写死的 3。
   实测窗口改写次数 **28 → 13~14 次/3 s**，可见页缺画布 **16~17% → 9%**（单线程）。
   ★ **必须按视口高度算，不能按可见页 `first..last`**：那个数随页边界在 n 与 n+1 之间跳，
   窗口尺寸跟着跳 ⇒ `range_resized` ⇒ 整窗重建 —— edit_probe 那条"逐页下滚走平移复用"
   当场就红了。
3. **预热的限量**：一轮换窗只排**一页**，且要**静下来 90 ms** 才跑。不限量时 Worker
   这条唯一线程被预热占死（实测 worker_probe/edit_probe 的求值超时，单次跑 5 分钟）；
   限量后回到 45 s 内。连续快滚时它几乎不跑 —— 那是对的。
4. 判据更新：`worker_probe` 的 W10 前提从"滚 2 页"改成"滚 count+1 页"（窗口变大之后
   2 页可能整段落在余量里，子集合本来就不该换）。

**还没修的那一条（Worker 更差的主因）**：Worker 上新页的画布要等
"回推几何 → 主线程建画布 → 转交 Worker → blitPage"两次往返，每帧缺口 2~3 帧。
方向是让**主线程按同一条窗口策略提前把画布建出来**（两宿主已经各有一份窗口策略，
再对齐一份即可），这样换窗时画布已经在 Worker 手里，缺口能压到 1 帧。

## 五、"感觉没啥变化"：换窗那一拍的 48 ms，与"贴到窗口边缘才换窗"这条判据

**先排除掉的两件事**（都用读数否掉了，不是推理）：
构建是最新的（`heditor.wasm` 10:24 编、里面确有 `prewarmPageGlyphs`），页面侧有
`?v=<last-modified>` 缓存绕开 + 工具条上的构建戳，所以"跑了旧副本"这条不成立；
`PREFETCH_DELAY_MS = 90` 那层虽然把预热挡在连续滚动之外，但预热本身是"把 mask 送进
缓存"，命中省下的只是冷光栅的一半 —— 它是把一笔钱挪个位置，不是省掉。

**量出来的真相**（`out/_diagO.mjs`，只跑 diag_selperf 的 O 段 + 长任务计数，四臂）：

| 视口 1800·12000 px/s | 旧策略 | 新策略 |
| --- | --- | --- |
| 换窗那一拍 paint 中位 / p90 / 最大 | 48 / 56 / 221 ms | 14 / 18 / 19 ms |
| 其中字形 / 铺面积 / 帧搬运 | 25 / 8 / 14 | 5 / 2 / 7 |
| 长任务（>50 ms）次数 · 合计 | 11 次 · 705 ms | 0 次 · 0 ms |
| 可见页没有画布的帧 | 8%（最多缺 1 页） | 0% |
| 换窗次数 / 3 s | 11~13 | 27（单拍便宜 3.5 倍） |

**根因不是"换窗慢"**，是**触发时机**：旧滞回要求"窗口盖得住可见页"，于是换窗恰好发生在
可见页贴到窗口边缘那一刻 —— 余量为 0。而这一拍本身 48~67 ms 里合成器照用户速度继续
往前滚（12000 px/s 就是 600 px），那一段必然空白。三秒滚到底就是闪十几次白。

**改法**（`web/app.js` + `web/engine_worker.js`，两宿主同口径）：
1. 窗口余量 2 页 → **3 页**（`maxWindowPages` 下限 4、`+3`）；
2. 新常量 `kWindowLookaheadPages = 1`：滞回判据改成"盖得住 要求 + 滚动方向上 1 页"，
   于是触发那一刻前方还剩约 1 页（83 ms @12000 px/s）可以垫；
3. `targetWindow` 不再两边各留一半，而是**把多出来的页偏向滚动方向**（往下滚：锚后 1 页、
   前 2 页），只改锚不改长度 ⇒ 不会来回滚就整窗重建。

**改的过程中掉进去并修掉的一个坑（值得记）**：`needFirst = req.first - look` 在第 0 页
会算出 **-1**，那是个**永远满足不了的判据**（窗口不可能从 -1 页起）⇒ 文档顶端往上滚过
之后每次 `applyWindow` 都判"盖不住"、白换一次窗，而那次 setViewportAnchor 与引擎窗口
其实一样，于是只重画一个光标 —— 把上一拍整篇重绘的账冲成 186 px，`edit_probe` 的样式
参考臂就是这么红的。★ 教训与判据纪律同族：**给滞回加一个方向的余量时，必须同时把它夹
回文档范围**，否则判据会从"恒绿"翻成"恒红"。两处 `needFirst/needLast` 都夹了。
另外 `desiredWindow` 的可见页数按 `maxWindowPages()` 封顶：范围是拿 getBoundingClientRect
算的，滚动位置刚变的那些拍能虚高好几页，虚高的后果是白换一次窗（同上）。

**判据侧的三处"靠巧合"**（改动把它们翻出来了，都不是产品缺陷，但得修）：
- `逐页下滚走平移复用`：只滚 4 页，余量 3 页时只赶上一次换窗 ⇒ 滚 8 页；
- `按需与整份渲染同一页的墨迹一致`：原来数**整帧**的墨迹，而帧是窗口大的 ⇒ 测的其实是
  "窗口盖着哪几页"（第 17 段把锚点挪到过第 50 页）。改成只数**第一页那几行**，并在两次
  取墨迹前都把锚点钉回 (0,3) ⇒ 53687 vs 53608（差 0.15%）；
- `参考臂：整篇重排重绘写了大半个帧`：`run(6, ZOOM)` 在"这个场景已经装着"时是空操作，
  读数变成上一拍（改样式那一拍）的 186 px ⇒ 先 `run(7)` 再 `run(6)`。

**判据现状（全绿）**：全量回归 `out/_allprobes.sh` 十套全 FAIL=0 ——
edit_probe 361×2 宿主 · worker_probe 68 · multi_probe 35 · error_probe 19×2 ·
stress_probe / web_probe。注释违规 **149**（与本轮前持平）。

**顺手留下的两条能力**：`glyphCacheBytes` / `glyphCacheLimit` 进 `statsJson`
（Skia 的 mask 缓存占用与上限，占用贴上限就说明缓存随时会被整份抹掉）；
`Bitmap::setGlyphCacheBudget` + `EditorEngine::ensureRenderSetup()` —— 后者是"懒做一次"的
入口，因为 **wasm 宿主不走 `init()`**（它直接 `fonts().addFaceFromMemory`），摆在 init 里
的设置在那条路上一次都不会执行（实测：预算写 48 MB，面板读回来还是 2 MB）。
预算本身是保险：本样例占用只有 490 KB，离默认 2 MB 还很远 —— 所以它**不是**这轮变慢的
原因，别把它当结论记住。大文档（字形集合长得多的）才需要它。

## 二、甩滚时一片空白：真滚轮量法、"追不上就放弃"、以及页纸底

**症状**（用户真机）：2 秒匀速滚完 2000 段（160 页）的示例，滚动期间**连画布都看不见**；
非 Worker 停下后很快出来，Worker 停下后要等约 1 秒、而且"中间的窗口一个一个在渲染"。

### 旧量法为什么量不到

`scripts/diag_selperf.mjs` 的 O 段（与 `out/_diagO.mjs`）是**写 `stage.scrollTop`** 驱动滚动的。
写它是"主线程有空就滚一格"，主线程每拍都跑得完；真机滚轮走浏览器输入管线、滚动在**合成器
线程**上，主线程被占死时它照样往前跑。所以"窗口追不追得上"这个问题只在真事件下才出现。
**新探针 `out/_diagReal.mjs`**：用 CDP 的 `Input.dispatchMouseEvent{mouseWheel}` 驱动，
**发送时不要 await**（逐个 await 会把速率压到 19 个/秒，实测 120 个事件耗掉 6.4 s，滚动
速度只有真机的一半，问题跟着消失），页面内用 rAF 采样；收尾轮询"停下后多久画对"。
★ 另外 `out/_run.sh` **只转发 `--port/--url`**，其它参数走环境变量（`REAL_MS` 等）。

### 复现读数（单线程宿主，2 秒滚完 160 页 = 每秒 80 页）

采样 83 帧/2014 ms（41 fps）、**可见页缺画布 55% 帧**、**整屏一页画布都没有 33% 帧**、
窗口落后可见首页 中位 3 / 最大 8 页、paint 中位 50 ms / 最大 154、**长任务占用 74%**。

### 两个先入为主的假设，都被读数否掉了

1. **"字形缓存没生效、每个字形都在冷光栅"** —— 错。逐页扫一遍（`out/_diagGlyph.mjs`）：
   第 0~2 页 116 ms（装载后整窗重建、全冷），**第 3 页起稳定 5~7 ms**，反向再走一遍同样
   5~9 ms。**单页只要 5~7 ms**，缓存对高频字是有效的（占用稳定在 490 KB，约等于高频字那
   几百个 mask，不需要更大）。先前以为的"每页 25 ms"其实是**一次重画 4 页**的合计。
2. **"把窗口余量加大就能跟上"** —— 错得更多。余量 3→8 之后：换窗 94~286 ms、落后从 3 页
   涨到 8~28 页、占用 169~318%。原因是**换窗的成本正比于窗口长度而不是位移**：窗口往后
   一跳超过一个窗口长时，引擎走整窗重建（重画 count 页），余量 8 就是重画 9 页。
   余量回到 **4**（窗口 5 页）。

### 真正的天花板

单页成本 ≈ 25 ms（换窗那一拍：字形 33 + 铺面积 11 + 帧搬运 10，两页）。而 80 页/秒 时
**一页在屏幕上只停留 12 ms**。渲染速度比需求慢 2~4 倍，**任何窗口策略都补不上内容** ——
追只是把主线程占死（300% 占用）而画面照旧空白。

### 改了什么

- **放弃判据**（`web/app.js` 的 `tooFastToFollow`）：`成本 × 速度 > 提前量` 时这一拍**不换窗**，
  把主线程让给合成器。成本取**最近对齐里最便宜的一次**（`followCostMs`，乘 1.05 缓慢上爬）
  —— 这条是关键：取"最后一次"会自锁（放弃一次之后，下一次必是追了很久的整窗重建，60~150 ms，
  于是判据永远说追不上；实测这自锁把每秒 40 页那一档从"整屏全空 0%"打成 87%）。
  ★ 另一个坑：判据原本用 `lastBlit.settleMs`，它只有 **5 ms** —— 引擎那一段（`present()`）
  **不在 settle() 里**，所以要用自己量的"对齐到上屏完成"整段墙钟。
- **收尾对齐**（`alignAfterScroll`）：放弃期间挂一个 140 ms 定时器，安静下来就对齐一次。
  为什么必须有：**停下之后不会再有 scroll 事件**，没有事件就没有下一拍，画面会停在旧位置。
- **页纸底**（`syncPageBackdrop`，两宿主）：`#pages` / `#spacer` 上铺一层纯 CSS 的页形渐变
  （白页 + 页间隙）。甩滚跟不上的时候，看见的是"一页页白纸在滚"，而不是"什么都没有"。
  零主线程成本（浏览器自己画），且**它是占位不是内容** —— 真正的字仍然只在画布上。
  Worker 宿主还要按 `lastPageX` 横向摆到页的位置，否则白纸会横铺满整个舞台。
- **Worker 侧 `view` 单飞**（`web/worker_host.js`）：滚动事件每秒上百个，而 Worker 是一条线程
  逐条处理 —— 不限量就是"命令排队执行"，用户看到的正是"已经到底了，中间那些窗口还在一个
  一个渲染，停下后还要等 1 秒"。门闩压成"一条在飞 + 一个待发标记"，过期位置根本不进队列
  （带 250 ms 兜底放行，避免回话丢失把滚动永久锁死）。
- 窗口余量 3 → 4、提前量 1 → 2、上限按页数 8 与帧像素 24 Mpx 双封顶。

## 四、worker 的"排队"：量出来了，而且发现还有第二条

起因：用户问"那 worker 那块的排队也没处理？"。上一轮只做了宿主侧的单飞门闩（`viewFireAndForget`），
没有量过它到底压掉了多少、也没查 worker 那条线程上还有没有别的排队。这一节把它做完。

### 4.1 先把度量做实

- **worker 侧自报耗时**：`view` 分支里计时，随 ack/state 带回 `workMs`（只有视口那条路填）。
- **宿主侧按 ts 记账**：`viewSentAtByTs` 记发出时刻，收到回话算 `rtt`，两者之差分解往返。
- **诊断口 `host.viewDiag()`**：`sent / coalesced / released / settled / canvasMsgs / packAvg / packMax`
  + `rtt[] / work[] / handle[]`（各留 512 条）。`out/_diagReal.mjs` 打印"发出 N（合并 M / 放行 R）、
  回话 N'、另发画布消息 K 条"，以及"停下之后又完成几条"。
- ★ **别把 `rtt − work` 叫"排队等待"**：它还含回话打包、跨线程、主线程受理三段。于是又补了两个读数：
  worker 的 `packAvgMs`（构造那份状态 + 结构化克隆，围绕 `post` 计时）与宿主的 `handle`（`onState` 耗时）。

### 4.2 量到的三档（worker 宿主，真滚轮，160 页）

| REAL_MS | 页/秒 | 整屏一页都没有 | 可见页缺画布 | 落后中位 | 换窗 | 那一拍 paint 中位 | 停下后画对 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2000 | 80 | 91~94% | 91~94% | 18~29 页 | 8~12 | 9~154 ms | 102~270 ms |
| 4000 | 40 | 12 / 11 / 46% | 34 / 24 / 58% | 3~4 页 | 42~64 | 31~58 ms | **6 / 5 / 8 ms** |
| 6000 | 27 | 20~21% | 30~33% | 3 页 | 74~85 | 33~35 ms | 6~8 ms |

**同一份代码、同一个进程、关掉提前量的 3 遍对照**（4 秒档）：整屏全空 **91/82/95%**、缺画布 95/87/96%、
落后中位 7/7/11 页、那一拍 64/39/77 ms、停下后 **103/1869/245 ms**。⇒ 提前量不是"调参"，是分水岭。

`rtt` 拆三段（4 秒档 65 条样本）：渲染 `workMs` 中位 26~36、**打包 `packAvgMs` 0.3**、主线程受理 `handle` 0.9，
**剩下稳定在 18~22 ms 就是"跨线程与调度"**。★ 我先猜的是"状态打包贵"，量出来只有 0.3 ms —— 猜错了，
靠这个读数当场改口。

### 4.3 结论：两块，一块处理了、一块没有

1. **视口消息自己的队列：处理了。** 4 秒档发出 65 条、**在飞期间合并掉 163 条**、放行 0 条；
   停下后只多完成 0~1 条；2 秒档同样（合并 151~164 条、放行 0）。
2. **worker 那条线程上还有第二条队列：画布消息**（`dropPage` + `pageCanvas`）。4 秒档 **300 条**
   （是视口消息的 4 倍），每条在 worker 里要新建一页背衬 + 整页 `putImageData` + 回推一份**完整状态**
   （含整段文本、控件、选区、光标报告、排版账）。它与视口消息**排在同一条线程上** ⇒ 上面那 18~22 ms
   的"跨线程与调度"就是它。这条**没处理**，是下一步。
3. **每页光栅 17 ms（zoom 1.5、DPR 1）是硬墙**：4 秒档要 40 页/秒 × 17 ms = **68% 的线程**，加画布与
   窗口开销就满了（缺画布 24~58%）；2 秒档要 **136% ⇒ 补不上**。⇒ 2 秒档"看得见字"这件事，
   靠窗口策略与队列都做不到。

  `dead` 时不再记在飞；★ **报预测位置**（`trackScrollSpeed` + `viewLeadPx`，夹 ≤ `kViewLeadMaxPages = 4` 页）；
  ★ **`armViewSettle`**：提前量只用来选窗口，但会留在引擎 `scrollY` 上（定位输入法候选窗要用）⇒

- `out/_diagReal.mjs`：接上队列读数（发出/合并/放行/停下后又完成/rtt 三段 + 主线程受理）。

### 4.7 用户提的"预建全部画布、不销毁、到窗口再更新内容"——实测过，钱不在他以为的地方

探针 `out/_diagCanvasAlloc.mjs`（页内量耗时 + 进程外量 `PrivateMemorySize64`，**两把尺子**）。
2000 段那份 = 160 页；zoom 1.5 / DPR 1 ⇒ 每页背衬 893×1263 = **4.30 MB**（全篇 688 MB）。

| 这一笔 | 160 张合计 | 内存变化 |
| --- | --- | --- |
| 建空元素 + 摆位 | **0.9 ms**（0.006 ms/个） | **-1 MB**（连默认 300×150 的背衬都没实体化） |
| 设成页背衬尺寸 | **0.2 ms** | -1 MB |
| `getContext('2d')` | 4.3 ms | 0 |
| `transferControlToOffscreen` | 11 ms（0.07 ms/张） | 0 |
| **每张第一次真画**（`putImageData`） | **425 ms**（2.65 ms/张） | **+696 MB** |
| 同一张重复贴 | 0.7 ms/张 | 0 |

- ★★ **背衬不是设尺寸时分配的，是"第一次真画"那一下才实体化的** —— 所以"设 width 只 0.2 ms"
  是**假绿**：它只说明这一下是空登记，不说明位图存在。同族证据：页内 `performance.memory`
  从建到清理**全程恒定**（背衬不在 JS 堆里）。
- ★★ **归零能把内存还回去**：前 100 张 `width = height = 0`（**元素留着不摘**）74 ms，
  内存 696 → 234 MB（应还 430）。全清回到基线。⇒ **"预建全部元素、只让窗口附近实体化"成立。**
- "复活"（从 0 设回页尺寸）中位 **0 ms**，但要重新首画才实体化（即 2.65 ms，不是 0.7 ms）。
- 两个推论：
  ① **全预建 + 全实体化** = 一次性 425 ms + **688 MB 常驻**（真机 DPR 2 且保持视觉大小 ⇒ 4 倍 = 2.75 GB），
     换滚动期**零引擎成本**（内容都在画布上，浏览器自己搬像素，连光栅都不用做）；
  ② **预建元素 + 按活名单实体化** = 一次性约 17 ms（0.9 + 4.5 + 11）+ 常驻只算活页，
     **能把 300 条画布消息降到 0** —— 正对着上一轮量到的那稳定 ~20 ms 跨线程与调度。
- ★ 顺带纠正本轮之前的一处归因：换窗时"每张 2.7 ms"不是"背衬重分配"的耗时，
  `el.width = pw` 本身是 0.001 ms；那 2.65 ms 是**该页第一次真画**（首次触碰页表 + 补零）。
  所以"造元素贵"这个说法只在下游（首画）成立。

## 五、单页绘制 17 ms 拆开之后：钱分在四堆，光栅只占一半

探针 `out/_diagPagePaint.mjs`（单线程宿主 + `stats` 的分段账；2000 段 = 160 页 / 总字形 **118393** /
4000 行 / 页 893×1263 gap 21 / 视口只有 **0.83 页**）。

★★ **量法上先栽了一次**：跳页后只等两帧就取数，三次读数**一模一样到小数位** —— 那不是"稳定"，
是**同一份账被读了三次**。快滚时宿主会主动放弃对齐（`tooFastToFollow`），140 ms 安静后才补。
判据改成"等宿主与引擎各自报的窗口首页相等、且连续两次相同"。**同族：读 stats 必须绑住"这一跳真的落定"。**

| 换窗形态 | paint | 铺面积 | 字形 | 帧搬运 |
| --- | --- | --- | --- | --- |
| 远跳（整窗重建 5 页） | 59.6 ms | 12.4（2.5/页） | 37.1（7.4/页） | 13.0（2.6/页） |
| 平移一页（`shiftVertical` + 重画 1 页） | 18.6 ms | 2.5 | 6.3 | 9.5 |

- 「帧搬运」是 `paint_ms - fill - glyph` 的**余量**，含 `copyRectFrom`、光标/选区、记表单标记、
  以及全部记账 —— 所以它偏大，不能当成纯 memcpy 读。
- 远跳那 13 ms 对应 5 页 22 MB 拷贝 ⇒ **1.7 GB/s**；而 `copyRectFrom` 是**逐行** `memcpy`
  （行宽 3.5 KB，1263 行 × 5 页）。**整页宽时行是连续的，一次 memcpy 就能搬完。**
- 平移一页的 9.5 ms ≈ `base_` 与 `bitmap_` 各 22 MB 的 `shiftVertical`（44 MB）。

### 可省的五项（按确定性排）

1. ★★ **worker 宿主换窗时 `blitPages(null)` 贴全窗**（`engine_worker.js` 的 view 分支）：
   平移一页时**只有新露出来那页的画布需要新像素**，其余页的画布在文档流里位置没变、像素本来就对。
   现在每拍 5 页 × 4.4 MB 的 `putImageData` —— 这正是上一轮量到的"跨线程与调度 ~20 ms"的大头。
2. ★★ **`bitmap_.shiftVertical` 在 worker 宿主可整条省**：帧只有"每页那一段"被 `blitPage` 读
   （`srcY = local * step`），不平移也不会读到旧页的旧位置。省 22 MB memmove。
   ⚠️ 但单线程宿主与 `auditFrame` 读**整帧** ⇒ 不能直接删，得要一个开关。
3. ★ **整页分支的底色填了三次**（页内白 → 页背景含间隙 → 页内白），第三次只为抹掉第二次在页内
   刷上的背景。**改成"先背景后白"就是两次**，省一次整页写（4.4 MB ≈ 1 ms/页）。
4. ★ `copyRectFrom` 逐行 memcpy → 连续块一次 memcpy（1.7 GB/s 明显低于带宽上限）。
5. 字形段 7.4 ms/页：**要 noskia 对照才说得清还有多少**（`build/wasm-noskia` 尚未构建，
   配好即可跑同一份探针；两后端都在仓库里，只有光栅实现不同）。

估算：平移一页 18.6 → **约 7 ms**（-60%），整窗重建 59.6 → 约 45 ms。
★ 口径提醒：这些数**全在 wasm 侧**（`paint_ms` 不含 JS 的 `putImageData`）。

### 5.1 ★ 撤回上一节第 1 项：`blitPages` 的账实测只有 0.1 ms

给 Worker 加了自报的"这一拍贴了几页、花了多少毫秒"（`blitMs` / `blitPages`，随 state 回推，
`host.viewDiag()` 里读）。真滚轮 4 秒档、干净重跑两遍：

| | 第 1 遍 | 第 2 遍 |
| --- | --- | --- |
| 有贴的那几次 | 16 次，中位 0.1 ms（最大 4.2） | 11 次，中位 1.5 ms（最大 5.3） |
| 合计 / 占往返合计 | 28 ms / **1%** | 15 ms / **0%** |

★★ 所以上一节第 1 项（"worker 换窗贴全窗是 20 ms 跨线程的大头"）**是错的，撤回**。
它最多值 4~5 ms（贴满 5 页时），而我原先按"5 页 × 4.4 MB 的 putImageData"去推，
**推的量级比实测大一个数量级** —— 又一次"没量就归因"。要改的优先级因此降到最后。
（同族教训见 4.6 节那条：判据/归因都得有实测。）

### 5.2 真滚轮下的每拍账（4 秒档 = 40 页/秒，两遍）

- `paint` 中位 **55 / 56 ms**（p90 92 / 131，最大 129 / 210）；换窗 40~44 次。
- 换窗那一拍拆开（中位）：**字形 30~33 / 铺面积 11~12 / 帧搬运 14 ms，重画 3 页**。
  ⇒ 真滚轮下每页约 **10 + 3.7 + 4.7 = 18.4 ms**（比稳定态探针的 12 ms/页贵，与"甩着滚"的
  缓存/内存状态有关）。
- 「剩下没归到三段」（跨线程与调度）中位 **20 ms**：`blitPages` 只占 1 ms 量级，
  余下的嫌疑是 **266~272 条画布消息**（每条要在 Worker 里建背衬 + 整页 `putImageData` +
  **回推一份完整状态**）。**下一优先要量的是它，而不是 blitPages。**

## 6. 三项搬运改动：两项成立，一项撤回（引擎侧）

5.3 节列了三项"按确定性可省"的搬运开销。动手之前先用 native 宿主
`heditor_native --repeat 25` 量了一遍基线（原因见 6.3 的噪声说明），结论是
**两项成立、一项不成立**。

### 6.1 成立并已做

**① `copyRectFrom` 整幅宽时改一次连续 memcpy**（`bitmap.cpp` + `bitmap_skia.cpp` 各一处）。
理由：逐行搬时每行只有 3572 字节（一页宽），一千多行的调用开销与搬运本身同量级。
它成立的前提是"refresh 的矩形绝大多数就是整幅宽"—— 这一点在代码里核实过：
`frame_w == page_px_w`（`engine_paint.cpp` 定帧尺寸处），所以页矩形、整帧重贴、
行增量那几条带全都是整幅宽。

**② 整页底色从三次填充降到一次**（`engine_paint.cpp` 的 `paintPageIntoBase`）。
原先非带分支是：页内底色 → 整个页矩形擦背景 → 页内底色再填一遍。中间那次"整个页矩形"
里九成九是页内区域，擦完立刻又被第三笔盖回去，等于多写一整页。改成"上下两条半格间隙
擦背景 + 页内填一次"。两条间隙的边界按整数像素算，与原整页矩形的 floor/ceil 同值 ——
native 的底图/帧逐字节自审整套通过就是这条的判据。

### 6.2 撤回：`bitmap_.shiftVertical` 不能省

5.3 节第 1 项说"按页取帧时 `bitmap_.shiftVertical` 可整条省"——**这个推理有漏洞**。
它只看到"Worker 只按页读帧（`blitPage` 取 `local * step` 那一段）"，漏了下一跳：
换窗时 `refresh` 只贴新露出的那条带，帧里其余页若不跟着平移，就整体停在旧窗口的
内容上 ⇒ 画面错一页。要省它必须同时把 refresh 改成整帧重贴，而那只省下一条带的
贴回（4.5 MB，约 1 ms），不划算。**不做。**

### 6.3 读数：同一把尺子，用"未动的字形段"归一

wasm 侧的读数噪声太大 —— 同一探针连跑两遍，字形段 37 → 57 → 91 ms（那是没改的

## 5.5 一页满字能不能 <10 ms：先把账量准（16:55）

用户定规矩：**基准一律以 wasm 为准**。native 的数字只能当"同一份代码换档"的参照 ——
这一点直接推翻了上一节的对比方向。

### 5.5.1 换后端：wasm 内 A/B，`wasm-noskia` 预设

同一份满字文档（2040 字形 / 3 页窗口）、同一探针、同一次宿主：

| 段 | Skia | 自写后端 |
| --- | --- | --- |
| 铺面积 | 3.0 ms | 1.8 ms |
| **字形** | **23.0 ms** | **284.6 ms** |
| 帧搬运（残差）| 8.2 ms | 6.1 ms |
| 宿主上屏 | 4.2 ms | 3.0 ms |

⇒ **wasm 基准下 Skia 比自写后端快 12.4 倍**（自写 139 µs/字形：曲线离散化 + 4 倍纵向
超采样扫描线，在标量 wasm 上就是这个量级）。**"Skia 性能差"是误判**；上一节拿 native
2.4 µs/字形当 Skia 的参照是方向性错误。

★ **`wasm-noskia` 能配起来，但必须手工给 ninja**：
`cmake --preset wasm-noskia -DCMAKE_MAKE_PROGRAM=D:/Develop/editor/.toolchain/ninja/ninja.exe`
—— CMakeUserPresets 只给 `native-local` 摆了 `CMAKE_MAKE_PROGRAM`，预设里默认那个是
`depot_tools/ninja`（一个脚本），CMake 探测 `ninja --version` 会 direct 报 unknown error。

### 5.5.2 一页满字的现状：≈ 35 ms/页

自造满字文档（60 段 × 900 字 ⇒ **1520 字形/页**，zoom 1.5，893×1263 px，单线程宿主 + Skia）：

| 段 | 平移一页（滚动路径） | 整窗重建（远跳） |
| --- | --- | --- |
| 铺面积 | 1.4 | 8.1（5 页）|
| 字形 | 21.8（其中记账 0.1）| 128.4（其中记账 1.0）|
| 帧搬运（残差）| 9.7 | 13.2 |
| 宿主上屏 | 2.3 | 5.6 |
| **合计** | **≈ 35 ms** | — |

⇒ 每字形 **14.3 µs**（全命中状态下；自造文本只有 34 个不同字，缓存 350 KB 装得下）。

★ **`paint_present_ms` 是残差，不是"帧搬运"**：`paint_ms - fill - glyph`（engine_paint.cpp:764）。
它装的是 reset/clear、**两次 `shiftVertical`（底图 22 MB + 帧 22 MB）**、`copyRectFrom`、
光标与标记。证据：平移一页时 `copyRectFrom` 只搬 4.4 MB（1 页），这一段却仍是 9.7 ms。

### 5.5.3 记账那一笔：0.1 ms，不值得动（并记下怎么被骗的）

新加了产品计时字段 `paintGlyphBoundsMs`（含在 `paintGlyphMs` 里，见 EngineStats），
量到**记账 0.1 ms / 1520 字形 = 0.5%**。

★ **在它落地之前，我用"临时短路记账 + 重编"量到过 23.5 → 9.5 ms，并据此写过
"记账占字形段 60%"——那是噪声。** 反证拦住了它：源码恢复并重编后，同一参数三次跑出
15.6 / 10 / 11.6 ms（既没回到 23.5，也没停在 9.5）。同族症状还有：同一产物在不同时刻
跑出 14.4 / 11.3 / 6.3 / 7.0 µs/字形。
**做法上的结论：一次短路实验不构成证据**，要么跑分布，要么把这一笔做成产品里的计时字段
（本次选后者，因为它永久可观测，且不必反复改源码）。

### 5.5.4 结论与可动项

现状 35 ms/页，目标 10 ms，**需要 3.5 倍**。按实测排：

- **字形 21.8 ms（62%）**：15 µs/字形的装配 + mask blit，**缓存全命中下**。自写后端更慢
  12.4 倍 ⇒ 换后端不是出路。未试过的杠杆只剩 Skia 库本身的编译档（见 5.5.5）。
- **帧搬运残差 9.7 ms（28%）**：主要是两次 shiftVertical 共 44 MB。改成"每页一块位图"
  可免掉这笔平移（免 22 MB 帧平移 + 22 MB 底图平移，代价是 refresh 改整帧重贴，净省约 4.6 MB
  但换来一次连续 memcpy）—— **这一项是纯结构改动，收益约 9 ms**。
- 铺面积 1.4 + 上屏 2.3：小项，先不动。
- 记账 0.1：**已排除**。

⇒ **只做分页位图能到 ≈26 ms；要 <10 ms 必须让每字形从 15 µs 降到 ~3 µs，而这一项目前
没有已验证的手段。**

### 5.5.5 还没试的"特性"（用户问的就是这个）

`scripts/build_skia_wasm.ps1` 的 args.gn 是 `target_cpu="wasm"`、`is_official_build=true`，
**没有 `-msimd128`** ⇒ Skia 的 SkOpts 在 wasm 上退到标量实现，clang 也不允许生成 SIMD
指令。重建 libskia 带上 `-msimd128`（或 `-msimd128 -msse4.1` 之类）是唯一还没验证的
"编译档"杠杆。另一条是 `setSubpixel(false)`：它只让缓存条目 ÷4（**不影响稳态 blit**），
预期收益小，但一次改动就能证伪。

### 5.5.6 探针与量测口径（两个假结论都是口径造成的）

- `_diagPagePaint.mjs` 原本是**单线程宿主**口径（`stats` / `editStats` 是取值器）。
  Worker 宿主只有 `engineStats()` / `engineEditStats()` 两个**异步**入口，字段名混用会
  读到 `mirror` 里的另一本账 ⇒ 表现为"同一份产物快了一倍"。已改成按
  `typeof H.engineStats === 'function'` 分流，两宿主通吃。
- 探针的 A/B/C 三段**在文档页数 < PP_FAR 时会被滚动夹住**，三次跳到同一位置、读到同一份
  账 —— 症状是三个数一模一样到小数位（看着像"很稳定"）。造满字文档时要连 `PP_FAR` 一起调。
- 新增读数：`repaintedPixels`（帧真的写下去多少像素，配 present 才知搬了几页）、
  `blitStats` 四段（宿主上屏）、`PP_TEXT=段数x每段字数`（造满字页）。

**验证**：native 三套件 94 / 996 / 809 失败 0；注释违规仍是基线 149；
worker 宿主 `edit_probe` 361 项 FAIL=0。

## 5.6 打开 wasm SIMD（17:2x–18:1x）

**起因**：用户问"一页满字有没有可能优化成整体 10 ms 以下"，上一轮的结论是"不能 ——
缺口在每字形 14.3 µs 与固定项 11 ms"。随后用户下了"移除自建光栅器，只保留 skia，
同时开启 simd"，中途改成"那自带光栅器现保留吧" ⇒ 本轮范围收敛为**只开 SIMD**，
自写后端、`wasm-noskia` 预设、native 宿主一律不动。

### 5.6.1 三处改动（缺一处就出静默错误）

| 位置 | 改动 |
| --- | --- |
| `scripts/build_skia_wasm.ps1` | args.gn 加 `extra_cflags = [ "-msimd128" ]` |
| 同脚本新的第 4b 节 | patch `gn/toolchain/wasm.gni`，撤掉 `wasm_defines` 里的 `SKVX_DISABLE_SIMD` |
| `CMakeLists.txt` | 契约宏列表删掉 `SKVX_DISABLE_SIMD`；`heditor_core` 编译加 `-msimd128`（PUBLIC）；`heditor_wasm` 链接加 `-msimd128`（仅 USE_SKIA） |

★ 这几条是**成对**的：只加 `-msimd128` 而不撤那条 define，`SKVX_USE_SIMD` 仍被强制为 0，
等于白加；只改库而不改主程序的编译宏，则主程序按标量版理解 SkVx、而库是 SIMD 版 ——
属于 ODR 违规（这正是 CMakeLists 那段"契约宏一个都不能少"的注释警告过的事）。
链接那条是 wasm-ld 的要求：对象文件与库的 `target_features` 必须一致。

### 5.6.2 顺手修掉的两个既存缺陷（都不是本轮引入的）

1. **patch 的幂等判据拿"整段替换文本"当指纹**。磁盘上的 `BUILD.gn` 是**旧脚本
   `prepare_skia.ps1`** 打的补丁（注释里写着那个名字），脚本改名为 `build_skia_wasm.ps1`
   之后 `Contains($new)` 与 `Contains($old)` 同时为假 ⇒ 脚本直接抛错。
   改成独立标记 `# heditor-patch: <标签>` 后，替换文本再变也不会误判。
   ★ 恢复办法已写进 throw 的提示里：从 `skia-main.tar.gz` 取原版覆盖再跑。
2. **`param([int]$Jobs = 0)` 与第 7 步的 `$jobs = @()` 撞名**：PowerShell 变量名不区分
   大小写，给强类型变量赋数组报"无法将 System.Object[] 转换为 System.Int32"。
   这也解释得通"为什么磁盘上留着旧脚本的补丁" —— **改名后这个脚本大概没被实测跑完过**。

### 5.6.3 SIMD 是否真进去了（硬证据，不靠配置推断）

## 5.8 SIMD 的回退路径：先只做"探测加准确提示"，兼容回退记为待办（18:5x）

### 5.8.1 技术底线：同一份产物内做不到运行时降级

`-msimd128` 是**模块级 target feature**：二进制里只要有一条 v128 指令，整个模块就要求引擎

"整份产物换掉"，不存在"检测到不支持就换条代码路径"。

SIMD 全球覆盖 **94.92%**（Can I Use 数据集，2026-08-24 更新），**是 Wasm 各 post-MVP

## 5.9 管线全貌 · Skia 的 GPU 后端可行性 · 两宿主差价（全部实测）

三个新探针：`out/_hostboot.mjs`（装载账，两宿主）、`out/_gpuprobe.mjs`（运行环境图形
能力）、加上既有的 `out/_diagReal.mjs` 这次在单线程宿主上跑同档。

### 5.9.1 管线（图已出，此处只记结论性事实）

出口是 `frameRgba()` = `emscripten::typed_memory_view(g_engine.frameBytes(),
g_engine.frame())` ⇒ **零拷贝**，帧就是 wasm 堆上那段 RGBA。两条上屏路都建 ImageData
视图再 `putImageData`，**这一步就是 CPU 到 GPU 的唯一一次上传**（每脏页 4.5 MB @1.5×）。
底图与帧各是一整块（`base_` / `bitmap_`），换窗时 `shiftVertical` 各一次。

### 5.9.2 GPU 后端：一条可做、一条缺料

- `gn/skia.gni:101-102`：`skia_use_webgl = is_wasm`、`skia_use_webgpu = is_wasm`；
  `:142` wasm 且开 ganesh 时 `skia_gl_standard = "webgl"`。**上游本来就支持 wasm 的
  WebGL**，且 `src/gpu/ganesh` 就在源码树里（tar 里 `src/gpu/` 有 1245 条）。
- WebGPU 那条：`skia_use_dawn = false` 是默认值，`:195` 断言 `!skia_use_dawn ||
  skia_enable_graphite` —— **Dawn 只服务 Graphite**；而 `third_party/externals/`
  **没有 dawn**（只有 emsdk / expat / freetype / harfbuzz / libjpeg-turbo / libpng /
  libwebp / zlib 八个）。取 Dawn 要联网 + git，本工程禁 git 写 ⇒ 得用户手工。
  emsdk 侧有 `tools/ports/emdawnwebgpu.py`。
- emscripten 侧缺的开关：`src/settings.js:550` `USE_WEBGL2` 已废弃（注释明说要写
  `-sMAX_WEBGL_VERSION=2`，默认 `:567` 是 1）；`:1806` `OFFSCREENCANVAS_SUPPORT = false`
  —— 我们的画布是转移给 Worker 的，这条必须开。
- **真正的门槛不是配置而是地基**：帧现在"是可读内存"，判据大量依赖逐字节 memcmp 与
  `auditFrame`。改 GPU 后要么重建判据，要么加回读路径 —— 而回读正是想省的那一笔。

### 5.9.3 本机**测不出** GPU 收益（这条比上面都重要）

`out/_run.sh` 起 Chrome 时带 `--disable-gpu`。实测（`out/_gpu.log`）：
`webgl2 = true` 但 `glRenderer = "ANGLE (Microsoft, Microsoft Basic Render Driver
(0x0000008C) Direct3D11 vs_5_0 ps_5_0, D3D11)"` —— **软件 D3D11 驱动**；
`navigator.gpu` 存在但 `requestAdapter()` 返回 **null**。`offscreenWebgl2 = true`（这条
是好消息：Worker 里能拿 WebGL2）。⇒ 任何"GPU 快多少"的实测必须换一台有真 GPU 的机器
或去掉 `--disable-gpu`，本机只能做可行性论证，不能报数。

### 5.9.4 性能：GPU 的理论上限约 6 ms，而瓶颈在它够不着的地方

一拍（换窗那次重建，@1.5× 满字页）≈ 14 ms：帧搬运 **8**（两次 shiftVertical + 贴回）
+ 字形光栅与铺面积 **4** + 宿主 putImageData **2.3**。
- GPU 能碰的是后两段（≈6 ms）；**帧搬运那 8 ms 它碰不到** —— 要省得先放弃可读帧。
- Worker 每拍另加**跨线程与调度 16~32 ms**，比整拍还大，GPU 一行都碰不到。
- 而且换 GPU 光栅不等于更快：SIMD 后 CPU 光栅已是 ~1.2 µs/字形（满字页 1.6~1.8 ms）。
⇒ **方向性结论：当前瓶颈是"每拍一次跨线程往返"与"固定 8 ms 的 memcpy"，不是光栅。**
先做分页位图（免掉两次 shiftVertical）收益比换后端更确定。

### 5.9.5 两宿主差价（同探针同机同档，4 秒滚完 160 页，两遍）

| 指标 | 单线程 | Worker |
| --- | --- | --- |
| 引擎 paint 中位 | 12 / 12 ms | 11 / 24 ms |
| paint > 50 ms 的拍 | 10 次（含一次 172）/ 0 | 0 / 3 |
| 窗口落后可见首页（中位） | 1 / 2 页 | 2 / 3 页 |
| 缺画布 | 7% / 4% | 4% / 39% |
| 整屏全空 | 0% / 0% | 0% / 19% |
| 停下后画对 | 2 / 5 ms | 7 / 10 ms |
| 视口 rtt 中位 | 无（同线程） | 29 / 54 ms |
| 其中跨线程与调度 | 无 | 16 / 32 ms |
| 画布消息 | 无（元素可复用） | 318 / 314 条 / 4 s |

`paint` 两宿主同源（都是引擎的 `paintMs`，不含宿主上屏）⇒ 可比。**引擎那一段两宿主
没有差别**；Worker 多的是"一拍一次跨线程往返"，它表现为窗口落后多 1~2 页、缺画布率高

★ **方差很大**（Worker 第 2 遍缺画布 39% vs 第 1 遍 4%）⇒ **单遍不能下结论**，要报两遍

### 5.9.6 装载账：总时间几乎一样，差的是"活干在哪个线程"

4 遍中位：**单线程 473 ms / Worker 477 ms**（导航到就绪，墙钟几乎持平）。
差别在构成：单线程的主线程要 fetch + 解析 **19.3 MB 字体**（3 份，54~115 ms）；
Worker 的**主线程侧资源计时全是 0** —— 胶水、wasm、字体都在 Worker 里抓的，主线程一个
字节都不碰。Worker 引擎自报启动中位 148 ms（其中字体约 100 ms）。
⇒ 结论：**Worker 不增加装载时间，它把装载的活搬离主线程。**

## 5.10 跨线程往返的 16 ms 与"分页位图"的原理（20:5x，用户问）

### 5.10.1 口径先钉住：残差是逐条算的，"开始之前那一等"没有读数

`out/_diagReal.mjs:256` 的残差 `rest[i] = rtt[i] - work[i] - packAvg`，**逐条相减后取中位**
⇒ 16.2 会比 `28.8 - 13.6 - 0.4`（13.9）大，不是算错（见 TRAPS #52）。
4 秒档两遍（`out/_real_wk2.log`）：rtt **28.8 / 53.5**、work **13.6 / 23.2**、pack 0.4 / 0.4、
handle 0.9 / 1.2、残差 **16.2 / 31.6**。

### 5.10.2 结论：钱不在"消息机制"，在两端各自的队列

- 机械成本很小：构造那份状态 + 结构化克隆 **0.4 ms**（峰值 3.5），主线程受理 0.9~1.2 ms。
- ★ `handle` 在 `onmessage` 回调**内部**起表（`worker_host.js:705`）⇒ 只量"开始之后"，
  **主线程"消息到了但还在忙"那一等没有任何读数**，它就藏在残差里。
- Worker 侧：`self.onmessage` 串行、`view` 分支无 `await` ⇒ 消息**不可抢占**，只能等手上那条跑完。
  手上排着的：上一拍 `present`（paint 中位 11~24 ms）+ `blitPages` + **310~326 条画布消息**
  （4 s，318 条 ≈ 每 12.6 ms 一条 ⇒ 队列几乎不空）；每条画布消息 =
  `getContext` + 一页 4.5 MB `putImageData` + 一份**完整状态**（`engine_worker.js:820`）。
  ⇒ 4.6 节那条"第二条队列"就是这 16 ms 的出处，**不是消息传递本身贵**。
- 主线程侧：state 到了也要等事件循环空出来（滚轮 / rAF / `syncPageCanvases`）。
- 佐证：两遍残差占 rtt 比 **56% / 59%**（固定开销该摊薄，实测没摊薄）；work / rtt / 残差
  三者同向同幅（1.7~1.9 倍）⇒ 同一个因（积压）的三个面。

### 5.10.3 要接着量就补两条"占用率"读数（自洽时钟，不跨线程）

Worker 侧把每条消息的进入/退出串起来算忙碌占比与任务间最长空档；主线程侧把
滚轮 / rAF / 建画布三段耗时加起来。两个占用率一乘，即可把 16 ms 分成"等 Worker"与"等主线程"。

### 5.10.4 分页位图：把"窗口"从"像素"里拆出来

现状：`base_` 与 `bitmap_` 都是 `frame_w × frame_h`（5 页 + 4 间隙 = 893 × 6399 ≈ **22.9 MB**），
页在里面的位置 = `local × (page_px_h + gap_px)`。换窗一页 ⇒ 两次 `shiftVertical(-1284)`
（`engine_paint.cpp:474-475`），每次 = `memmove` 5115 行（18.3 MB）+ `memset` 1284 行（4.6 MB）
（`bitmap.h:147`）⇒ **合计约 46 MB 触及**，就是那一拍"帧搬运 8~9.5 ms"的主体
（按残差口径 ≥5.7 GB/s，是**下界** —— 残差里还有 reset/clear、copyRectFrom、光标、记账）。
**不是实现写差了，是"窗口变了"被实现成了"像素搬家"。**

原理：**让每页像素有一个按页号固定的家**，窗口退化成一张**页号清单**；换窗 = 丢一页、
加一页，指向的位图一个字节都不动。屏幕上照样"内容往上走" —— 那是宿主按文档流摆画布
（CSS 的 top），与内存搬不搬无关。出口那一侧早就是这个模型：`blitPage(p)` 读 `local × step`，
改成 `srcY = 0` 即可，两宿主各 3~5 行。

收益：那一拍帧搬运 8~9.5 → 近 0。按 5.6.4 的账，满字页整页 8.1~9.3 ms 里字形只 1.6~1.8、
铺面积 0.4~0.5，其余正是这笔 ⇒ 是目前**最大且最确定**的一块。

★ **代价不在内存**（5 × 4.5 MB 与 22.9 MB 同量级），**在判据地基**：

1. 帧现在是"可读、连续、逐字节可比"的一块：`frameRgba()` 零拷贝导出、`auditFrame`
   拿帧与每页画布比、`auditBase` 拿底图比、`ink` / `markCheck` / `rawFrame` 都扫它。
   拆开后这些要么重建、要么读取时**临时合成**一张窗口帧。
2. ★ 一旦 `frameRgba()` 变成"从页位图拼出来"，任何"帧 vs 页位图"的比较就是**拿自己比自己**
   （恒绿）。必须保住两条独立路径：引擎侧合成 vs **宿主 `putImageData` 之后的画布像素**
   （`auditFrame` 现在正是这条），并配反证：改坏一块页位图，**只有那一页的画布该红**。
3. ★ **装饰层（光标 / 表单标记 / 选区）画在帧上、底图里没有它们，这个分离是承重的** ——
   底图更新判据是页指纹，指纹里没有选区，带上就"拖一次选就整页重光栅"。
   拆成按页之后装饰要么单独一层、要么接受这条判据变松。**这才是这一步真正要设计的东西。**

## 5.11 澄清：宿主"一页一张画布"≠ 引擎"一页一张位图"（易混，先钉住）

用户读 5.10 时提出两问："canvas 不是一页一个了吗，一页更新重绘那一页不就行了" 与
"页面上只看到 canvas，没有 5 个页面"。**两问都源于把两层当成一层看**，值得单独记：

- **宿主 DOM 层**：确实一页一张 canvas，而且是**窗口里每一页各一张**。
  `syncPageCanvases`（`worker_host.js:453-489`）按 Worker 推来的 `first/count` 建，
  `el.style.top = 页号 × pageStep / dpr`（`:486`），数量写进 `host.pageCanvasCount`。
  **5 张都在 DOM 里**，只是 1.5× 下一页高 1263 px、视口装不下第二张 ⇒ 用户只"看见" 1 张，
  其余 4 张挂在视口上下方。同页内的滚动**引擎一个字都不干**（原生滚动搬已画好的画布），
  这正是 `engine_worker.js:173-176` 那条滞回注释说的"浏览器把画布搬走就行"。
- **引擎 Worker 层**：**没有"一页一张位图"这回事**。只有一整块连续 RGBA，
  `frame_h = count × 页高 + (count-1) × 间隙`（`engine_paint.cpp:214-215`），
  `blitPage(p)` 从这块里切 `srcY = local × step`（`engine_worker.js:105`）贴给该页画布。
  ⇒ **DOM 的 N 张 canvas 是这一整块条带的取景窗，不是每页各自的存储。**

- ★ **"一页更新只重绘那一页"已经成立，且早就落地**，只是它不吃那 8~9.5 ms：
  编辑路径 = 引擎报脏页清单 → `blitPages(only)` 只贴那几页（`engine_worker.js:123-135`）
  + 底图只重画页内那条带（`paintPageIntoBase(local, page, band)`）。**编辑确实只碰一页。**
  那 8~9.5 ms 只在**滚动跨页**那条路：`shift_pages != 0` ⇒ `shiftVertical`。
- ★ **为什么挪窗口就得搬**：`local = p - windowFirstPage` —— **条带格号 = "在当前窗口里排第几"，
  不是页号**。窗口一滑，第 p+1 页从"第 1 格"变成"第 0 格"，**每页格号全变** ⇒ 像素必须跟着挪。
  这是"帧 = 视口窗口"模型的必然结果，**不是实现写坏了**。5.10 的改造正是把格号换成页号。
- 窗口 5 页的来历：`maxWindowPages()`（`engine_worker.js:197-203`）
  = `max(视口页数, min(8, 像素封顶, 视口页数 + 4))`；1.5× 下 viewH≈850、step≈1284 ⇒ 视口 1 页,
  byPixels = floor(24 Mpx / (893×1263)) = 21 ⇒ `min(8, 21, 5) = 5` ⇒ **1 可见 + 4 余量**
  （余量是"滚上来即刻可见"，不能省成 1）。

## 5.12 环缓冲方案评估（用户提议：滚动不搬、只上下加数据）

**判定：方向正确**，与 5.10 的"分页位图"是同一件事的两种写法。连带把帧到画布的映射钉死如下。

### 映射（口径，别再靠推断）

`frame_w = pagePxWidth() = 893`、`page_px_h = 1263`、`gap = 21` ⇒ `step = 1284`；
`frame_h = count × 1263 + (count-1) × 21`，5 页 = **6399 行**，
整帧 `893 × 6399 × 4 = 22 857 228 B`（22.9 MB）；第 p 页字节起点 = `local × 1284 × 893 × 4`
= `local × 4 586 448`（4.59 MB）。

两宿主是同一映射的两种切法，**都不拷像素**：

- Worker：`new Uint8ClampedArray(fv.buffer, fv.byteOffset + srcY*fw*4, fw*ph*4)` 再
  `new ImageData(..., fw, ph)`、`putImageData(img, 0, 0)`（`engine_worker.js:99-108`）。
- 单线程：建**一份整帧** ImageData，每页走脏矩形重载
  `putImageData(img, 0, -srcY, 0, srcY, w, ph)`（`app.js:1049-1068`；`dy` 取 `-srcY` 的理由
  在 `:1057-1061` —— 重载的目标位置是 dx+dirtyX 之和）。

页间隙那 21 行**不贴**给任何画布，它只是让 `srcY = local × step` 一条式子够用的对齐量。
`putImageData` 是全程唯一一次 CPU→GPU 上传（每脏页 4.5 MB），与环无关。

### ★ 环的必要约束：环长取 step 的整数倍

不取整数倍时，槽边界相对"环尾接缝"会随头指针**漂移**，偶发一页横跨接缝
⇒ 那一页要拆两段、两次 `putImageData`。取整数倍（槽数 × 1284）⇒ 页恒落在一槽内，恒一次。

取 **7 槽 = 8988 行 = 32.1 MB**（现 22.9 MB，两块共 +18 MB），
余量正好是 2 页位移（`8988 ≥ 6399 + 2×1284 = 8967`）。位移超出余量仍退回整窗重建。

收益口径要诚实：省掉的是**搬**那一笔（一次换窗 18.6 ms 里的 9.5 ms，即两次 `shiftVertical`）；
**新页光栅那 8 ms 省不掉** —— "上下加数据"本身就是把新页画进空槽。

### 三个真实门槛（比搬字节难）

1. `frameRgba()` 是**单视图**契约：`typed_memory_view(frameBytes(), frame())`
   （`wasm_main.cpp:380-382`）—— 环上"当前窗口"未必连续。
2. `Bitmap::copyRectFrom` 要求两图同尺寸、按同位置拷贝（`bitmap.cpp:332-334`）——
   底图到帧那一趟要跟着同一套旋转。
3. 探针侧把它当一整块扫：`rawFrame()`（`app.js:2126`）、`auditFrame`
   （`app.js:2166-2174` / `engine_worker.js:685-700`）、`ink` / `markCheck`；
   且 `blitFrame` 拿 `view.byteLength !== w*h*4` 当校验（`app.js:1036-1038`）
   ⇒ **"帧高"从契约里去掉是接口层的事**，不是像素的事。

★ **好消息：审计独立性不受影响**。`auditFrame` 的另一端是画布 `getImageData`
（经浏览器往返），不是引擎自己的位图 ⇒ 合成出来的帧仍是**独立读数**。
"恒绿"只在"帧 vs 页位图"那一种比法上出现，避开即可（5.10 第 2 条已记）。

结论：形态取**槽级环**（= 分页位图，一块内存切片），下一步先出接口与判据改造清单。

## 5.13 显示链路（钉死）与多页横排评估

### 内存到屏幕：四步，只有第三步花钱

1. 帧在 wasm 线性内存（`Bitmap::px_`）。
2. `frameRgba()` = `typed_memory_view(frameBytes(), frame())`（`wasm_main.cpp:380-382`）——
   **堆上视图，零拷贝**；宿主再切 `srcY` 一段（`engine_worker.js:106-107`）。
3. `new ImageData(视图, fw, ph)` **构造不拷字节**（直接引用）→ `putImageData(img,0,0)` 写进
   画布背衬 —— **全程唯一一次 CPU→GPU 上传**（每脏页 4.5 MB）。
4. 引擎退场：canvas 在 `#stage` 里绝对定位，**滚动由浏览器原生做**，搬的是已栅格化的画布。

⇒ 这解释了 5.11 的两条：同页内滚动引擎零开销；`auditFrame` 拿画布 `getImageData` 是
**独立读数**（`putImageData` 之后画布与引擎内存已脱钩、各持一份）⇒ **环缓冲怎么改都不动这条审计**。

DOM 三件（`worker.html:21-31`）：`#stage` 滚动容器兼视口裁剪；`#spacer`（`worker_host.js:561-585`）
撑滚动高度 + 用 `linear-gradient` 铺"页纸底"（给未渲染的页一张白纸）；`#ime` 透明 textarea 只接
输入法与候选窗。画布 CSS 尺寸 = 设备像素 / dpr ⇒ 1:1 不重采样（`app.js:1047-1048`）。

### 多页横排：分两种，代价差一个数量级

- **一页内多栏**（3 栏排在一张 A4 里）：排版层的事（`docs/文档模型设计.md:161` Section 的"分栏"）。
  **帧结构不动。**
- **多页并排**（3 页横排换行 / 2-up 对开）：**视图布局**，不是文档结构。

★ **排版层不用动**：`layout.cpp` 已在每个 LineBox / PlacedGlyph 上盖绝对页号
（`:576 / :758 / :899`），页内坐标是页本地的（换页 `cursor_y = cy` 重置，`:598-600`）。
横排只是把**一维页号映射到二维屏幕位置**。

要改的层（都核过；★ 这张表**修正过一次**，见下面的"修正"）：

| 层 | 现在 | 横排后 |
| --- | --- | --- |
| 帧尺寸 / 页偏移 / 平移 | `frame_w = 页宽`、`frame_h = count×页高+间隙`、`off_y = local×step`、`shiftVertical`（`engine_paint.cpp:214-215 / 220 / 244 / 474`） | **一个字不改** |
| 宿主切片 | `srcY = local×step` + 连续子视图（`engine_worker.js:105-107`） | **一个字不改**，仍是零拷贝单视图 |
| 宿主摆画布 | `top = 页号×step`（`worker_host.js:486`）、`left` 居中（`:468-469`） | 拆 (row, col) —— 纯 style |
| `#spacer` | 高 = 总页数×step、页纸底一维 gradient（`:561-585`） | 高按行数、底图二维 —— 纯 style |
| 点画布到帧坐标 | 从页容器 rect 算帧内 y（`app.js:1372`、`framePointAt`） | 从**被点中那张画布**的 rect 算页内局部坐标，页号取 `dataset.page`（`worker_host.js:477` 早已备好），再合成帧坐标 |
| 窗口判据 | `visibleRange` / `desiredWindow` / `maxWindowPages` 全一维（`engine_worker.js:178-207`） | `first = 行号 × cols`；`vis` 要乘 cols；★ **8 页封顶与 24 Mpx 封顶会立刻咬住**（3 列 ⇒ 可见页数 ×3） |
| 环余量 | 1 页 = 1 槽 | 不变（窗口仍是**连续页范围**，见下） |

★★ **修正（同日晚）**：这张表上一版把"帧尺寸"与"宿主切片"两行写成"要改成二维 ⇒ 零拷贝失效"，
**那是错的** —— 错在把**帧的内存几何**与**DOM 的几何**绑成了一件事。依据：`blitPage` 只认五个
引擎自报量（`frameWidth` / `pagePxHeight` / `pageGapPx` / `windowFirstPage` / `windowPageCount`，
`engine_worker.js:92-97`），**没有一个知道"列"**；帧宽就是页宽，不是"窗口宽"。只要帧保持
"**一列页的条带**"（页号沿 y 递增），DOM 把画布摆成网格与它毫无关系 —— 横排换的是**画布元素在
文档里的落点**，不是像素在内存里的落点。二维帧是我自己附带的设计选择，不是横排的必要条件。
⇒ **引擎的像素层 / 光栅 / 窗口 / 环：一行都不用动；引擎里唯一与坐标有关的那处（`hitTestPt` 的
页号反推）也能由宿主合成帧坐标绕开**（`engine.cpp:2457-2463` 连碰都不用碰）。

★ 让上面成立的两个前提（要记住）：
① **网格下可见页集合仍是连续页号**（page-major 排 ⇒ 视口盖住第 r..r+1 行 = 页 `cols×r` 起共
   `2×cols` 个）⇒ 窗口、`desiredWindow`、环这套**一维结构原样可用**；
② 拖选跨页/跨行时，宿主每次移动都要重算"这次落在哪张画布上"，再用它的 rect 算局部坐标。

★ **建议的预备动作（现在做近乎免费）**：把宿主侧"屏幕点 → 帧坐标"收敛成一个
`framePointAt(clientX, clientY) -> {page, frameX, frameY}`（一维实现里 page 由页容器 rect 反推）。
以后横排只换它的实现；引擎侧连这一步都不必知道。别现在就做通用网格求解器 —— `cols` 是配置常量。

# 5.15 缩放默认档改成 Web 标准（96 dpi）

★ **换算恒为 `dpi / 72`**：引擎 `zoom` 的单位是"设备像素 / 磅"（`engine_config.h:54`：
`2.0 ≈ 144dpi`）。⇒ **96 dpi 对应 `4 / 3`**：`round(595.276 x 4/3) = 794`、
`round(841.89 x 4/3) = 1123`，页间隙 `round(14 x 4/3) = 19`。原先写死 `1.5` = 108 dpi
（893 x 1263，比标准大 12.5%）。

★ **"磅当像素"不是可选项，是定义**：1 磅 ≡ 1/72 英寸 ⇒ "1 磅 = 1 像素"必然意味着 72 dpi。
所以"以 96 dpi 为 1 倍"在引擎口径里只能写成 4 / 3 —— **用户视角的"100% 缩放"与变量视角的
"zoom = 1.0"本来就是两个基准点**，不是谁对谁错。

**改动**：三个宿主文件各加一份 `kZoomBase = 4 / 3`（`app.js` / `engine_worker.js` /
`worker_host.js`，沿用 `kPageWidthPt` 那套"每个文件各声明一份"的做法），默认值全部引用它；
`index.html` 的 range 步长改 1/12（4 / 3 正好落在格点上）、value 与 `worker.html` 的 number
同步。**引擎侧一行未动**，native 判据与 `PageMetrics::A4()` 不受影响。

**验证**：新探针 `out/_zoomcheck.mjs` 两宿主都 **794 x 1123、间隙 19、PASS**；
★ **探针自己显式传 zoom**（`edit_probe` 默认 1.5）⇒"探针全绿"证明不了默认值，
这条必须单独量，且要在 boot 之后、任何 run/reset 之前取数。
全量串行复跑（`out/_seq.sh`，新）：edit_probe 两宿主各 **361 / 0**、`worker_probe` **68 / 0**、
`multi_probe` **35 / 0**、`error_probe` 两宿主各 **19 / 0**、`stress_probe` 69 次点击 0 不一致、
`web_probe` 缺字 0。注释基线 **149**。

★★ **两宿主的 `#zoom` 文本做不到逐字相同 —— 别试图统一**：单线程宿主是 `range`，

# 5.16 界面收"倍数"、引擎收"密度"（同日晚，5.15 的收尾）

★ **问题**：默认档已是 96 dpi，但界面上那一格显示引擎口径的 `1.33`（密度：设备像素 / 磅）。
用户读到的应当是"100%"，即倍数 `1`。**两个口径都正确，错在把物理量直接摆上 UI。**

**改法（选"接缝换算"，不是改引擎单位）**：引擎、native 判据、所有诊断读数**一行未动** ——
`zoom` 的语义（设备像素 / 磅）本身没错，光栅化 / 字形度量 / 页高换算全都建立在磅上。
换算只做在**界面接缝**上，每宿主一对纯函数：

- `engineZoomOf(factor) = factor * kZoomBase`（倍数 → 密度）
- `uiZoomOf(density) = density / kZoomBase`（密度 → 倍数）

★ **两侧都要过换算，漏一侧就错**：读输入框要乘（`:890` 的 input 事件、`:1026` 的 `run()`），
写输入框要除（单线程 `:105` 的 boot / run 回写、Worker `syncZoomInput`）。默认值统一引用
`kZoomBase`（单线程 `:92`、Worker `:134`，以及两处 `reset` 的缺省参数），
Worker 宿主的 boot 消息也从裸值改成 `zoom: kZoomBase`（`:1432`）。

★ **门面同时暴露两个口径**（两宿主同形）：`zoomLevel` = 密度（**引擎与判据读它**）、
`zoomFactor` = 倍数（**界面那一格与它一致**）。另加 `zoomToFactor(f)` —— 按倍数调就走它，
`zoomTo(z)` 仍是按密度。**判据侧不要再读输入框**，读门面。

★ **探针侧的口径迁移**（这是本次改动的主要扩散面）：凡是把 `#zoom` 的值当换算因子的
脚本，全部改读 `window.__heditor.zoomLevel` —— `edit_probe`（3 处）、`worker_probe`
（`zoomGeom` 改走 `zoomToFactor`，判据由"写 1.5 读回 1.5"改成"写倍数 1.5 ⇒ 密度 2"）、
`multi_probe`（改 `zoomToFactor`，期望 `zoomLevel === 2.5`）、`diag_sweep`、
`diag_gap`、`diag_nested_gap`、`diag_caret_float`、`diag_del_jump`、
`diag_split_empty_field`、`_diag20`、`out/_sweep`、`out/_head_edit_probe`（已废弃品也一并改，
免得留一处旧口径）。这些脚本**本来就该改**（其余探针早就在读 `zoomLevel`）。

**验证**：`out/_zoomcheck.mjs` 两宿主双向 PASS（默认档 界面写 `1` / 门面 `4/3` / 页 794 x 1123；
驱动输入框写倍数 `1.5` ⇒ 门面密度 `2`、页 `1191 x 1684`、间隙 28）——
★ **双向都要量**：验收探针全走门面，换算接错也照样全绿，所以必须**像用户那样派发真实
`input` / `change` 事件**驱动输入框（这条是反证，不是复述）。

# 5.17 密度基准含 DPR：高分屏上界面仍是 1 倍，但按屏幕画足像素

★ **问题**：宿主里 `devicePixelRatio` 原先只用在"帧像素 → CSS 像素"的显示换算上
（`style.width = pw / dpr`），**没进引擎的渲染密度**。于是 DPR=2 的屏幕上同一份代码
渲染 794 设备像素、再除以 2 显示成 397 CSS 像素 ≈ 4.13 英寸 —— **只有 A4 的一半**，
字也跟着小一半。尺寸正确、清晰度也对三者只能取二。

★ **改法**：**密度基准 = `kZoomBase x dpr`**，界面那一格仍是 1（倍数）。
每宿主一对纯函数就够了：`engineZoomOf(f) = f x baseDensity()`、
`uiZoomOf(d) = d / (kZoomBase x zoomDpr)`；`baseDensity() = kZoomBase x 现读的 DPR`。
⇒ DPR=2 时引擎画 1587 x 2245、显示回 794 CSS 像素：**尺寸与清晰度同时成立**，
代价是内存按 dpr 平方涨（一页背衬 3.40 → 13.6 MiB，5 页帧 17.3 → 69 MiB，底图与帧各一份）。
★ 引擎侧、native 判据**一行未动** —— 引擎只是收到一个大一点的 zoom。
★ **DPR=1 下与改动前逐位相同**（本机就是 DPR=1），这是"没有回归"的来源，也是
"探针全绿证明不了这条改动"的来源。

★★ **两个必须记住的口径**（细节见 TRAPS 55）：
1. **读倍数要用"这份密度是按哪个 DPR 算的"**，不能用当前屏幕那个 —— 否则换屏那一拍
   会读到一个缩掉一半的假倍数，反推回去变成恒等空操作。两宿主各记一个 `zoomDpr`，
   改密度统一走 `setZoomDensity`，与调用顺序无关。
2. **屏幕像素比不要缓存**：单线程宿主本来就是每处现读；Worker 宿主原先缓存在顶层
   `const` 里、只靠监听刷新，事件一漏就整片错。已把 Worker 侧 41 处引用改成现读
   （`dprNow()`），与单线程宿主同构。
★ 另给两宿主各加一个换屏监听：`(resolution: Ndppx)` 的 `change`，触发后按新基准把
同一个倍数重设一次（引擎重排 + 重建画布尺寸，走既有路径）。

**验证**（新探针 `out/_dprcheck.mjs`，两宿主各三节，全 PASS）：
| 节 | 单线程 | Worker |
| --- | --- | --- |
| 启动 DPR 1 | 794 x 1123、CSS 794 | 同左 |
| 启动 DPR 2 | 引擎 **1587 x 2245**、CSS **793.5** | 引擎 **1587 x 2245**、CSS **794** |
| 运行中按新 DPR 重设 | 帧 1587、显示 793.5 | 帧 1587、显示 794 |
★ **不变量就一条**：设备像素随 DPR 翻倍（1.999），**显示宽倍数 1.000** —— 物理尺寸不动。
★ **探针口径**：本机 DPR=1，只能用 `Emulation.setDeviceMetricsOverride` 覆盖；而覆盖
**只更新媒体查询的 `.matches`，不派发 `change` 也不派发 `resize`**（`out/_dprevents.mjs`），
Chrome 又**不复用 MediaQueryList 对象** ⇒ 换屏事件在本机驱动不了，第三节量的是
"触发之后那一步"（走门面重设同一个倍数），**事件接线本身留待真机**。
★ **本轮自己踩的一个坑**（写进 TRAPS 55 第一条）：第一版监听写成
`engineZoomOf(uiZoomOf(currentZoom))`，两个函数都用**现读** DPR ⇒ 恒等，整段空操作；
第二版探针也被同一个坑绊了一次（`zoomToFactor(zoomFactor)` 在 dpr 2 下读到的倍数是 0.5）。
根因都是"读倍数用了新屏幕的 DPR"。
★ 注释违规一度涨到 150（"顺手"触发 R11），改词后回 **148**。

## 5.18.2 每拍固定成本的分解（`out/_fixedcost.mjs`，两宿主同机）

| --- | --- | --- |

★★ **结论三条，全部反直觉**：
1. **跨线程消息本身近乎免费**（纯往返 0.3~0.6 ms）—— "往返 30 ms"那个数是**排队**，
   不是消息机制的机械成本。
2. **一整份状态回推 + 宿主落地也近乎免费**（0.2 ms 以内）—— 状态里那十几个字段

3. **固定成本几乎全在 `present()` 里**（3.6~8.3 ms），而其中引擎自报只有 1.0~1.3 ms、
   且**什么都没改（重画 0 页、排版没跑）** ⇒ 那 1.0~1.3 ms 是**纯帧搬运地板**
   （reset/clear + copyRectFrom 之类），每次交互都要付；剩下的是宿主 `onState`（≈1.5 ms）
   与跨线程/打包（≈1 ms）。
★ 方差极大：同一探针三次跑出 `present()` 8.3 / 5.5 / 3.6 ms。**单遍不算数**，要报区间。

# 5.20 画布改按「页号模槽数」取槽（5.19 遗留那条 22% 的收尾）

**改动**：`slot = 页 - 窗口首页` -> `slot = 页 mod N`。窗口平移时不再"所有槽都换页"，
只有**新进窗口的那几页**落到旧内容的槽上，其余槽里的页一动没动。配套一张
"每槽当前画着哪一页"的表（`slotPage`），判据 = **脏（在 only 里）或 槽过期**；

★ **N 不能钉死**：引擎的窗口页数是 `max(视口页数, min(8, ...))`（`maxWindowPages` 里那个

**两侧从同一份几何现推**（宿主用 `gm.viewH/pageH/gap`，worker 用 `viewH/pagePxHeight/gapGapPx`），

# 5.26 帧缓冲改"固定分槽"——方案设计（2026-10-17）

设计文档：`out/_design_slotframe.md`。这一轮只设计，未动代码。

## 5.26.1 结论：不做真环形，做"固定分槽"

三个候选对比之后选 B：

| 候选 | 出口零拷贝 | 换窗成本 | 结论 |
| --- | --- | --- | --- |
| A 真环形（头指针 + 逻辑环形） | 当前窗口可能跨接缝，要拆两段 | O(1) | 不需要头指针 |
| **B 固定分槽（槽号 = 页号 mod N）** | **是**（页永远整行连续） | 只重画新进窗口的 k 页 | **选它** |
| C 每页一张位图 | 否（子矩形切不出连续视图） | 只画新页 | 破坏出口与审计独立性 |

★ **B 不需要"环"的原因**：只要 `N >= 窗口页数`，任意连续 N 个页号 mod N 互不相同
⇒ 页永远落在槽的整数倍行上、**永不跨接缝**。所以没有头指针、没有跨接缝拆分，
帧仍然是一块普通连续位图 —— A 的全部复杂度都来自"环长可能小于窗口"，那是自找的。

## 5.26.2 N 的取法（本方案的关键决策）

`N = max(当前窗口页数, 历史最大值)`，上限 8（防御 64）。**单调不降**。

为什么不能取 `N = 当前 count`：文档末尾 `count` 会从 5 掉到 1（`vp_count_` 被
`total - first` 夹过），N 跟着变就会"进出末页反复整窗重建"。
为什么不能取 `N = 8`：内存 +60%（3 个空槽 x 2 块），而视口变化本来就少。

## 5.26.3 内存账（真值，不是估算）

`frame_h` 从 `count*ph + (count-1)*gap` 变成 `count*step` ⇒ **只多一格页间隙**。

| 档 | 页像素（实测） | 现在 | 分槽 | 增量 |
| --- | --- | --- | --- | --- |
| **96 dpi（默认）** | `[794, 1123, 19]` | 18.07 MB/块（5691 行） | 18.14 MB/块（5710 行） | **+59 KB** |
| 1.5x（旧默认） | 893 x 1263，gap 21 | 22.86 MB/块 | 22.93 MB/块 | +73 KB |
| DPR 2 | 1587 x 2245，gap 37 | 72.2 MB/块 | 72.4 MB/块 | +229 KB |

两块合计增量 **约 0.3%**。
★★ **修正上一轮的估算**：5.24 里写的"7 槽 +28 MB"是错的 —— 那是按"槽数比窗口页数
多 2"算的，而按需增长（N = count）根本不会多。**内存要按"实际槽数 = 窗口页数"算，
不是按"上限 8"算。**

## 5.26.4 最大风险：两侧的 N 不是同一个数

宿主侧 `slotN = max(8, ceil(视口高/步距))`（画布槽，下限 8），引擎侧 `N = max(历史, count)`
（本机 5）。**两者默认不等** ⇒ `blitPage` 的 `srcY` 会算错、贴错页。

解法：`geom` 增一个字段 `frameSlots`（引擎的 N），宿主**切帧**用 `frameSlots`、
**画布槽**仍用 `max(8, ...)`。两套槽号并存，注释必须写明"画布槽管内存复用、
帧槽管像素位置，二者不是同一件事"。
★ 这是本方案唯一的语义复杂度来源，也是最容易写错的地方。

## 5.26.5 判据：哪条盖得住，哪条变弱

# 5.27 画布槽的两侧 N 不同：复现、修复，以及它与帧方案是同一个问题（2026-10-17）

## 5.27.1 复现

新探针 `out/_slotsync.mjs`（读两侧各自的槽数比相等，不比画面 —— 错位时"每一页都错得
很均匀"，看截图反而不容易发现）。CDP 覆盖视口高度 + 派发真实 resize
（覆盖本身不派发 resize，见 TRAPS 55），Worker 宿主：

| 场景 | 宿主槽数 | 引擎槽数 | 结果 |
| --- | --- | --- | --- |
| 启动（900 px 高） | 8 | 8 | 一致 |
| 视口拉到 12000 px 高 | 11 | 11 | 一致 |
| **视口缩回 900 px 高** | **11** | **8** | **槽号错位** |
| 再换一次窗口 | 11 | 8 | 错位 |

根因：**两侧对"槽数"的定义不同**。
- 宿主用"已建槽数"当模数（`slotOf(p, slotCanvases.length)`），而槽**建了就不回收** ⇒ 只增；
- 引擎用"当前视口算出的页数"（`slotCountNow() = max(8, ceil(viewH/步距))`）⇒ 可增可减。

视口从很高变矮：宿主停在 11、引擎回落到 8 ⇒ 引擎把第 p 页画进 `p mod 8` 号画布，
宿主却把 `p mod 11` 号画布当成第 p 页 —— **画面上每一页都是别的页的内容**。

★★ **现有判据全盖不住它**：`auditFrame` / `selfCheck` 两侧都用引擎自己的 `slotOf`，
在引擎看来"页 p 就在 p mod 8 槽里"完全自洽；错位只发生在"那张画布被宿主摆在哪儿"。
这是"同一条代码路径当判据必然恒绿"（TRAPS 62 那一族）的第三个实例。

## 5.27.2 修法：真源移到宿主

画布在宿主手里 —— "实际有几个槽"只有它知道（它建了几个、就交了几条画布过来）。

- 宿主 `sendPageCanvas(slot, el, gm, slots)`：把 `slotCanvases.length` 随消息报出去；
- 引擎删掉 `slotCountNow()` / `syncSlotCount()`，改 `setSlotCount(m.slots)` 照单全收；
- 宿主的建槽循环从"边建边发"改成**先建齐再发** —— 否则中途那几条带的是 1、2、3……，
  引擎每收一条就要把槽表整体作废一次；
- `invalidateSlots()` 改成 `slotPage.length = slotN; slotPage.fill(-1)`（槽数变大时数组要跟上）。

## 5.27.3 它与帧槽方案是同一个问题

用户问的两件事，答案是：

**是同一件事。** 两者都在解"页在某个东西里的位置被绑在窗口上"：
- 画布槽：位置绑在窗口 ⇒ 换窗就建销画布（302 条消息）；
- 帧槽：位置绑在窗口 ⇒ 换窗就 memmove 像素（11 ms）。

**能复用，而且必须复用**，否则就是同一个 bug 的第三次出现。复用的形态是"一个 N"：
`N = maxWindowPages()` 由 Worker 单点计算，三处消费（宿主建槽 / Worker 槽号 / 引擎帧槽）。

★ 关键发现：**`maxWindowPages()` 本来就是那个数** —— 它与文档位置无关，本机是 **5**。
而宿主此前用的是 `max(8, ceil(viewH/步距))`，那个**下限 8 是错的**：它既大于窗口页数
（浪费 3 个槽），又与引擎的口径无关（一旦窗口真的超过 8 页就分叉）。

所以宿主的下限 8 应当去掉，改取 `geom.maxWindowPages`。这一步单独就有收益：
画布槽 8 -> 5，且帧槽化时不会多出 3 个空槽（那会是 +11 MB/块）。

## 5.27.4 设计文档已改

`out/_design_slotframe.md` 的第三节（N 取法）与第六节（最大风险）重写：
- 第三节：`N = maxWindowPages()`，三处消费的表格，以及"为什么不用 max(历史, count)"
  （短文档时 count < cap，引擎按历史最大算会与宿主分叉）；
- 第六节：把这次的 11 对 8 完整记进去，并写明"现有判据全盖不住"；
- 第九节：实施顺序加了**第 0 步：统一 N**（与帧无关，可独立验收）。

## 5.27.5 验收

- `out/_slotsync.mjs`：修复后四个场景两侧全部相等（8/8、11/11、11/11、11/11）。

# 5.28 统一槽数（帧槽化第 0 步，2026-10-17）

## 5.28.1 改动

槽数从"宿主按 max(8, 视口装得下几页)"改成"**窗口页数上限 `maxWindowPages()`，单点计算**"：

- `engine_worker.js` 的 `geom()` 增一字段 `maxWindowPages: maxWindowPages()`
  （本机 **5**；与文档位置无关，只随视口与页度量变）；
- `worker_host.js` 的 `syncPageCanvases`：`nSlots = max(1, gm.maxWindowPages, count)`，
  删掉宿主那份 `kSlotCount = 8` 与"视口装得下几页"的算法；
- 单线程宿主**不受影响**：它是"页号 -> 元素 + 池（最多 8 个备用元素）"，
  没有按模取槽，两侧不存在 N 的问题。

那个最后的 `max(..., count)` 是**下限保护**：门面允许外部把窗口页数指到上限之外（探针会），
槽少了会让两页共用一个槽、那几页永远缺画布。

## 5.28.2 为什么下限 8 是错的

- **它大于窗口页数**：本机窗口 5 页，8 槽白占 3 个（帧槽化之后那 3 个空槽是
  3 x 1142 行 x 794 x 4 = **13.9 MB/块**，两块 28 MB）；
- **它与引擎的口径无关**：`maxWindowPages()` 才是引擎将来帧槽要用的数，
  两边各算一次就是 5.27 那个 11 对 8 的翻版。

取 `maxWindowPages()` 之后，槽数与窗口页数上限**是同一个数**，所以"帧槽数 = 画布槽数"
成立 —— 帧槽化不用再引入第二套 N。

## 5.28.3 实测

`out/_slotsync.mjs`（Worker 宿主）：

| 场景 | 宿主槽数 | 引擎槽数 |
| --- | --- | --- |
| 启动（900 px 高） | **5**（原 8） | 5 |
| 视口 12000 px 高 | 11 | 11 |
| 视口缩回 900 px 高 | 11 | 11 |
| 再换一次窗口 | 11 | 11 |

真滚轮（4 秒、两遍）：画布消息 **0 条**、缺画布 4%、paint 中位 13/14 ms、
换窗那一拍 字形 2 / 铺面积 1 / 帧搬运 9~10 ms —— 与 N=8 时同档（槽数只影响
"够不够用"，不影响每拍成本）。

## 5.28.4 判据

`out/_slotsync.mjs` 现在是第 0 步的验收：**读两侧各自的槽数比相等**，且第一行必须
是 5（不是 8）—— 后者是"下限 8 已被去掉"的证据。
★ 不比画面：错位时"每一页都错得很均匀"，看截图反而不容易发现。

# 5.29 收敛"页 -> 帧内偏移"（帧槽化第 1 步，2026-10-17）

## 5.29.1 改动

新增 `EditorEngine::frameOffsetOfPage(page)`（engine_layout.cpp），一维实现就是
`(页号 - 底图首页) x (页高 + 页间隙)`。行为与改前逐字节相同，只是把散在七处的同一个
算式收成一个函数：

| 位置 | 原写法 | 现写法 |
| --- | --- | --- |
| `presentInternal` 的页矩形 lambda | `pageRectLocal(local)`，`local x 步距` | `pageRectOfPage(page)` |
| `paintPageIntoBase` 的落点 | 入参 `local` x 步距 | 入参只剩页号，内部调 `frameOffsetOfPage` |
| 增量分支只重贴一条带 | `i x 步距` | `frameOffsetOfPage(page)` |
| `drawControlMarks` 的括号 | `(lb.page - 底图首页) x 步距` | 同上 |
| `drawControlMarks` 的焦点小点 | `(cr.page - 底图首页) x 步距` | 同上 |
| `caretRectPx` | 同左 | 同上 |
| `controlRects` | 同左 | 同上 |

`paintPageIntoBase` 的窗口内下标参数直接删掉（它只用于算偏移），五个调用点跟着改。
留着它的话，以后有人会拿它再算一遍偏移 —— 那正是要收敛掉的东西。
改完 grep 该算式的三种写法在全仓已无残留。

## 5.29.2 为什么要先做这一步

帧槽化（`out/_design_slotframe.md`）只需要换 `frameOffsetOfPage` 一个实现，其余绘制代码
一行不动。若不先收敛，第 3 步的改动面会从 1 处变成 7 处，且漏掉任何一处都只表现为
"某一层偏几页"（例如光标对、表单括号偏一页）—— 最难查的一类错。

## 5.29.3 收敛暴露出来的一个隐含顺序（这次踩到的坑）

改成绝对页号之后第一次跑 `edit_probe` 失败 9 项：底图与"从零全建"逐字节差
3005940 px（框 [0,0,594,5121]），另有"按需模式下帧上有字 81 px（应 53687）"。

根因：页的位置现在由 `frameOffsetOfPage(page)` 现算，而它读 `base_first_page_` 这个成员 ——
原先传的是"窗口内下标"，算式里没有这个依赖，所以"先画页还是先更新首页"是随意的；
改成绝对页号之后它变成显式的先后关系，而两个重建分支里原来的顺序都是"先画页、后更新首页"，
于是整窗页被画偏 shift_pages 页。

修法：把 `base_first_page_ = first_page;` 提到两个分支的画页循环之前（全建、平移各一处）。
值得记：把隐含依赖变成显式参数，会连带暴露调用顺序上的约定 —— 原来靠"参数里没有它"
躲过去的顺序问题，收敛之后必须写对。判据是现成的（`edit_probe` 里"滚动换窗之后底图 ==
从零全建"那条逐字节比对），它一次就抓住了。

## 5.29.4 验收

- `python scripts/lint_comments.py` 为 0 处。
- native `ctest --preset native-local` 为 3/3（59 秒）。
- web `out/_seq.sh` 串行全绿：`edit_probe` 两宿主各 361/0、`web_probe` 缺字 0、
  `worker_probe` 68/0、`multi_probe` 35/0、`error_probe` 19/0 x 2、压力 69 次点击 0 不一致。
- 这一步不该有任何性能变化（同一个算式），所以不量收益 —— 只验行为不变。

# 5.30 帧改"按页号分槽"（第 2+3 步，2026-10-17）

## 5.30.1 改了什么

一维条带 -> 槽布局。页在帧内的行偏移 = `(页号 mod 槽数) x 步距`，与窗口开在哪里无关。

引擎侧：
- `frame_slot_count_` / `slot_page_`（槽 -> 当前装着哪一页）/ `slotOfPage()`；
- `frameOffsetOfPage()` 改槽实现；**未设槽数时退回旧条带算法**（native 单测与审计宿主
  不调那条门面，见 5.30.3）；
- 帧高 = 槽数 x 步距（不再是"窗口页数 x 页高 + 间隙和"）；
- **删掉整个平移复用分支**：`range_moved` / `far_moved` / `shift_pages` / `shiftVertical`
  / dy 折算 / `eraseStillVisible` / 新露条带铺背景，约 60 行。窗口平移不再是特殊路径，
  它只是"有些槽过期了"，与"页内容变了"合并成同一套增量判据（槽过期时必须整页重画，
  行带判据在那时无效 —— 它比的是同一页的上一个版本）；
- `notePage`（帧矩形 -> 页号）改走槽表，并只记窗口内的页；
- `hitTestPt` 的帧坐标反推改走槽表（与 `frameOffsetOfPage` 严格对称），槽表里查不到时
  退回旧算法；
- 新门面 `setFrameSlots(n)` / `frameSlots()`。

宿主侧：
- 单线程：`frameSlotOf(page)`（切帧 / 自审 / 光标滚动定位 / IME 定位四处）、
  `syncFrameSlots()`（幂等，只在变化时真发）、`presentNow()` / `relayoutNow()` 两个包装
  把所有呈现入口都罩住；
- Worker：`syncFrameSlots()`（render / paintFull / view 分支三处）、`blitPage` 按
  `mod.frameSlots()` 取源行、`geom` 报 `frameSlots` 与 `maxWindowPages`。

## 5.30.2 一个必须写明的语义：帧槽数与画布槽数可以不等

- **画布槽**：建了就不回收（已转移的画布不能再转移第二次，缩回去再涨就得新建 + 首画），
  所以它是"历史最大"；
- **帧槽**：只是内存，跟着窗口页数上限走，可增可减。

`blitPage` 用两个槽号分别取"源行"（帧槽）与"目标画布"（画布槽），各自自洽。
`out/_slotsync.mjs` 的判据据此分成两条：画布槽两侧必须相等（5.27 那个 11 对 8 的错位），
帧槽必须 >= 窗口页数且 <= 画布槽。实测：视口 12000 px 时三者都是 11，
缩回 900 px 后帧槽回到 5 而画布槽停在 11 —— 这是对的，不是错位。

## 5.30.3 途中三次「判据比实现先错」

**一、引擎不能假设"槽数一定被设过"**。native 的 `edit_and_caret` 立刻报红：单测宿主
从不调 `setFrameSlots`，于是槽表是空的、命中测试全部返回 false。修法是在
`frameOffsetOfPage` 与 `hitTestPt` 各加一条退化：**未设槽数 = 旧条带布局**。

**二、全建时把没用的槽也搬了一遍**。`edit_probe` 报"单段文档敲字仍是整页重画"
（112 万 vs 全量 573 万）。根因：帧尺寸变化时 `refresh` 覆盖**整个帧**，而帧现在
是"槽数 x 步距"，单段文档下整帧 544 万像素、真正用到的只有 91 万。
修法：空槽用 `bitmap_.clear(cfg_.background)` 铺一次背景（**不记账** —— repaintedPixels
描述的是"上屏搬了多少"），`refresh` 只覆盖窗口内那几页。★ 空槽必须是背景色而不是 0：
`ink` / `markCheck` 数的是"非背景"像素，透明黑会被当成墨迹。

**三、三条以"整帧"为分母的判据随槽数一起松掉**。`framePixels = frame_w x frame_h`
现在含空槽，于是"整页重画写入 ≥ 半帧"这类判据会越来越松（槽越多越松，最后恒真）。
已改成以"窗口内几页的像素"为分母（`windowPages x frameW x pageH`）：
`edit_probe` 的"整页重画写入 ≥ 半窗"与"参考臂"两条。

★ 还有一条**我自己造成的**：把 `mod.present()` 全局替换成 `presentNow()` 时，
替换把**刚写的包装函数自己**也改成了自递归（`presentNow` 里调 `presentNow`），
单线程宿主启动即栈溢出。教训：全局字符串替换之后要回看被替换点的邻域，
尤其是"刚新增的、名字相近的函数"。
