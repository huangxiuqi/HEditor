## 阶段 1 第三刀：行度量按行算

上一刀之后混合字号的字形已经按各自的 run 整形，但**行盒高度、基线、行高还是块级那套** —— 24 磅的
run 装在 12 磅的行盒里，大字会溢出到相邻行上。这一刀把它补上。

**做了什么**：`layout.cpp` 加 `LineMetric{size_pt, ascent_pt, descent_pt}`；每段按簇预算一张
`cluster_metric`（按"簇所在 run 自己的字体与字号"取，只在换 run 时查字体），再算整段最大
`para_metric`。横排**按行取本行所有簇的最大 ascent/descent/字号**，`LineBox::size_pt` 因此不再是
"块的字号"而是"这一行的字号"；竖排取**整段**最大（列位是等宽推进的，逐列变宽要连列序与页内列数
一起重算，不做）。只有 `line_factor` 与段后距仍是块级。

**★ 判据逼出了两个真 bug**（都是上一刀留下的、只有混合字号才露出来的那一类）：

其一，**`walk` 那条增量路径按块级字号推页高**。`engine_layout.cpp` 的 `shiftSuffixBlockAxis` 里
`lh = b.size_pt * b.line_factor` 是"与 layoutDocumentRange 同一套规则"的旧写法，改成
`lb.size_pt * b.line_factor`（行盒自己的字号）。

其二，**排版层用基线累加推进行**。`baseline += line_h` 看着对，其实基线 = 行顶 + **本行** ascent，
混排字号时上一行的 ascent 会串到下一行，翻页之后落点就错；而且"本行放不下"的判定
（`baseline + (line_h - ascent) > cy + ch`）用的是**上一行**的高度去估下一行 —— 下一行更高时会漏判。
改成推进**行顶**（`top`），并把页底判定挪到本行度量已知之后。

**判据（edit_test [23] 新增 (h)(i)(j)，499 → 507）**：`(h)` 混合字号那一行的行盒字号取 24 磅、

## 第七刀-A：段落身份与流位置桥接（15:20 起）

**为什么先做这一段**：树上编辑的地基是"引擎的 (段, 段内码点偏移) 与模型的流位置互换"。两者
隔着控件边界（开闭括号各占一位）与节边界（起止各一位），而段的码点里没有它们 —— 靠算式互换
必然分叉。

**做了什么**
- `compile.h`：`CompileResult` 加 `sources`，每块一条 `BlockSource{first, mark}`（first = 本块吃到的
  第一个在流里占位的元素：文本节点 / 控件节点 / 空段时它自己的结束标记）。
- `compile.cpp`：`noteFirst()` 在文本与控件边界入账时记首个元素；`flush` 收进 `sources` 并复位。
- `engine.h/.cpp`：加 `std::optional<FlowIndex> flow_` + `block_flow_`（每块内容起点）+
  `block_flow_span_`（文本码点数 + 边界数）+ `block_src_`，全部在 `rebuildFromTree()` 里与块流一起
  重建（分两次建就会"块按新树、流位置按旧树"）。公开 `flowPosAt(段, 偏移, 归属提示)` 与
  `flowToTextPos(流位置)`。

**三条硬约定**
- 块起点**只认 FlowIndex**（`intervalOf(BlockSource::first)`），推定值只在查不到时退化使用。
- 同一处边界上"控件之前 / 进入控件"是两个流位置：无提示取**最外侧**，提示指到该控件时贴**内侧**
  （开括号贴它之后、闭括号就是它自己）。
- **不持树（旧 setBlocks 路径）桥不存在**：`flowPosAt` 返回 -1、`flowToTextPos` 返回 false，不猜。

**判据**（`tests/edit_test.cpp` [26]，新增 18 项）：块起点与模型自算的流位置逐项一致（1 / 8 / 11）；
两段起点之差 = 首段内容位数 + 段落标记 1 位；开括号上的归属分侧；闭括号就是内容末尾；段末落在
标记那一位；**正向换出去再反向换回来逐项相同**；段间位置归到端点；不持树时桥消失。

**验证**：native `edit 576 / model 784 / shaping 55` 失败 0；wasm 构建通过；浏览器探针 **192 项
失败 0**；注释 lint 0 违规；五个改动文件 clang-format 全绿。

## 第二批用户反馈：括号外侧那两段点不进去（已修）

**用户报的**（截图是 variant 3 三层嵌套）："反字和后面的左括号之间""天和左边的右括号之间"
光标都进不去。用户同时质疑"你是在浏览器上测试的吗" —— 探针 192 项全绿但没覆盖这一格，
因为它的点选判据全落在**字的格**上，没有一条落在**括号那一格**上。

**先复现**：写了 `scripts/diag_nested_gap.mjs`（横扫整行 + 打印占位槽表 + 打印每个偏移上
"括号之前 / 之后"两个位置），`verify_web.ps1 -Probe` 跑。结果一目了然：x∈[140,160] 整段
点击后光标一律画在 x=152（＝中层 `[` 之后），**146（括号之前）那一格没有任何插入点落得进去**；
闭括号那一侧同理（点 `]` 右边，光标被拉回 `]` 之内）。

**根因（不在归属，在渲染）**：`inlineOffsetFor` 无归属时一律贴括号内侧。而 flow.h 早就定了
"控件之前与进入控件是两个流位置"，`flowPosAt` 也是按"无提示取最外侧"实现的 —— 渲染侧却把
"最外侧"画成了内侧。于是那两个位置**根本没有可表达的画法**，点选时命中测试给什么归属都没用。

**修法（三处，缺一不可）**：
- **渲染**：新增 `LineBox::outerOffsetAt(cp)` = 该偏移上"所有控件之外"那个位置（所有闭括号之后、
  所有开括号之前）；`inlineOffsetFor` 认哨兵 `kInlineOffsetOuter`（= -2）走它；另外"归属控件在
  这一处没有自己的边界"（落点在它内容的某个嵌套边界上）也走它 —— 于是**点"天"不再被拉回 `]` 之内**。
- **命中测试**：占位簇按**左右半边**分（与真实字簇同一条中点规则）。开括号左半边、闭括号右半边
  都是"控件之外"→ 归属给哨兵；另两种半边照旧按括号主人算。
- **归属链**：`caretFieldHint()` 认哨兵，`slotOwnerOf` 把负数原样传给排版，`setCaretAt` 收下它。
  **无归属（键盘移动、`setCaret`）不变** —— 字段起点仍画在开括号之内（那条被 [21] 时代的老判据
  `光标在字段起点 → 落在 [ 之内` 钉着，第一版把无归属也改成"括号之前"，当场被它拦下，回滚）。

**踩的坑**：① 第一版只改"无归属"那一条 → 老判据红，且点选仍进不去（命中测试给的归属是括号主人）；
② 老判据 `x12 == 控件矩形左缘` 说明"字段起点画在括号之内"是**故意**的，不是 bug —— 所以要区分
"字段自己的起点"（贴内侧）与"嵌套边界"（可贴外侧）；
③ 探针三处"点 [ 归后一个字段"的点击位置用的是"两枚括号间距的一半"，那落在括号格的**正中偏左**
（差 0.05pt），改按左右半边判之后整组红 → 改成"取内侧插入点再往左半磅"；
④ `window.__heditor.caret.x` 是**帧像素**（乘过 zoom）且是**光标矩形左缘**，插入点要加半个光标宽
（`caret.w / zoom / 2`）—— 少算这半格，算式落点就翻到另一侧（实测点到了 x=248，命中跑到偏移 12）；
⑤ 断言消息里的"实际值"要先算动作再拼（`hitTestPt` 那条第一版打印的是初值 0，判据本身是对的）。

**判据**：edit_test **[29](g)** 六条（外侧落在括号左缘、内侧落在它之后那个字、两侧差 5.55pt；
`hitTestPt` 在开括号左半边 / 闭括号右半边给出 -2）；浏览器探针新增 **[14.7]** 三条
（点开括号左半边 → 光标 x=146.00 < 括号左缘 146.93；点闭括号右半边 → 光标 x=227.00 > 221.62）。

wasm `_c10w4.log` 通过；浏览器探针 `_c10web6.log` **195 项失败 0**；头依赖守卫 `_c10hdr.log`

## 光标侧别：位置 = 偏移 + 侧别（第三批用户现象，已收口）

用户报：**方向键在括号边界上一下跳好几格** —— "光标在反字前面时按左键直接跑到冒号前面了，
应该是在左括号前面"；"在天字前面时按左键直接跑到悸字后面了，都不知道跳了多少"；
外加"三个控件挨着的、把内容删掉之后那两个控件之间就点不进光标了"。用户给的判词很准：
"控件边界都当成一个普通字符了，怎么还这么特殊" —— 括号在排版侧本来就是一枚簇，缺的只是让光标
也按"簇"来数。

**根因是结构性的**：光标只存 (偏移, 归属)。而同一个偏移上可能压着好几枚括号（相邻空字段就是
`][][]`），"控件之前 / 进入控件 / 内容末尾 / 控件之后"是互不相同的插入点 —— 一个偏移 + 一个控件
下标根本表达不了。此前那一刀（`outerOffsetAt` + 左右半边）只是给**两个**位置补了画法，
多枚括号时就露馅：`outerOffsetAt` 在有多枚括号时返回**第一枚开括号**的位置，不是"所有闭括号之后"。

**修法**（一个概念，四处落点）：`caret_side_` = 在这个偏移上跨过了几枚括号（0 = 所有括号之前），
与 `caret_` 成对；`LineBox::offsetAtSide` 取代 `inlineOffsetFor`/`outerOffsetAt`；
`flowPosAtSide` 是桥的底层（`relAt = cp + 前面的边界数 + side`，段内相对流位置与"簇边界序号"
是同一个数）；`moveCaretBy` 在侧别上逐格走；`hitTestPt` 多给 `out_side`，宿主与 `app.js` 搬侧别
（`field` 只是它的投影）。默认侧别 = "最内层含端点"（与编辑归属同源）⇒ 相邻空字段停在它自己
那一对括号之间，"字打不进去"那条老毛病不复发。

**顺手收掉两个真缺陷**：① **陈旧侧别会复活** —— 位置变过又变回来（编辑挪走、又落回同一偏移）
骗过"位置相等"这一条；修：所有不带侧别的写入走 `setCaretRaw`（24 处赋值 + 排版收口一处），
侧别还要写在 `relayoutIfBracketPlanChanged` **之后**（重排会清侧别而位置没变）。② **聚焦档死结** ——
`focusedControlIndex` 只认推出的归属会形成 `bracketedControls → focusedControlIndex → 边界对象表`
的循环（首次排版前一个括号都排不出来）；修：保留"最内层含端点"回落。

**口径边界**：旧 `setBlocks` 路径一个字没改（`caretFieldHint` 只在持树时由位置推；旧路径仍按区间
归一次）。对象表改走 `objectsFor(para)`（持树取产物、旧路取 `blocks_`）—— 否则旧路径读到空表，
`bracketCountsAt` 全零、侧别恒 0。

**判据**：edit_test 672 → **678**（方向键走动改断言 (偏移, 侧别) 序列、零宽字段默认落点、
`flowPosAt` 无提示 = 最内层、[29](g) 改断言侧别）；浏览器探针 195 → **199**，新增 **[14.8]** 四条：
反字前按左键只退一格（光标 x 132.00 → 126.00，退 6.00pt ≈ 一枚括号宽）、天字前同理
（227.00 → 220.00，退 7.00pt）、再按一下才退到"三"之前、反向 9/2 → 10/0 10/1 11/0。
[14.2]/[14.3] 的走动判据一并改成"一次跨一枚簇"的口径（`][` 要按两下）。

**验证**：native `_c11b9.log` = edit **678** / model **803** / shaping **55** 失败 0；
wasm `_c11w3.log` 通过；浏览器探针 `_c11web4.log` **199 项失败 0**；头依赖守卫 `_c11hdr3.log`；
注释 lint **0 违规**；`engine.cpp` / `layout.h` / `engine.h` / `wasm_main.cpp` clang-format CLEAN。

**遗留**：`setCaretAt`（提示版）与 `setCaretAtSide`（侧别版）两个入口并存 —— 前者给探针与诊断用
（它们手上只有控件下标），点击路径一律走后者。彻底收掉提示那条路要等旧 `setBlocks` 路径退役。


## 删除之后的落点：位置与侧别由流位置给出，不猜（第四批现象，结构性收口）

用户报的第二批"跳格"：**三层嵌套删掉「天」之后光标落到 ]中 之前**（该在它之后）；
**三连可编辑字段先删「三天」再删「悸」，光标跑进第三个控件**。并明确要求"整体重新评估，
是不是模型、实现有问题，先不要一个劲打补丁了"。

**评估结论：模型对，实现差一层。** 模型里括号是流里的普通元素（每个边界各占一个流位置），
"一个字符一个字符地移动"本来就是在流位置上加减一；但引擎的光标存的是 (段, 码点偏移) ——
**这个坐标不含括号**，于是每次要问"这是流里的哪个位置"都得猜（"最内层含端点"这条区间规则）。
猜的入口四处：方向键、点击落点、删除区间、编辑后的落点。每猜错一次就冒一个只在边界上出现的
症状，于是修一处冒一处。上一刀补的"侧别"只解决了**点击与几何**两处，编辑落点与删除区间仍在猜。

**复现（`scripts/diag_del_jump.mjs`，真键盘）**：嵌套删「天」→ 落点 10/0（该 10/1，
光标 x=220.67 而两枚 ] 在 221.62/227.85，差一枚括号）；三连删「悸」→ 落点 8/2（该 8/0，
落进了第三个控件里）。

**修法（一条规则、六个入口）**：位置与侧别由**操作算出来的流位置**给出。
- 新增 `setCaretAtFlow(FlowPos)`：码点偏移由桥反查、侧别 = 流位置 − 偏移 − 排在它前面的边界数，
  两者一次算准；越界才退回"最内层"这条安全网。
- 新增 `textSpanAt(para, a, b, &from, &to)`：文本码点区间在流里占的那一段（括号不进区间）。
  **判定（`policyErase`）与实际删除（`eraseOnTree`）共用它** —— 两处分叉就会出现
  "判据说能删、真删却越界"。顺带修掉一个潜伏缺陷：删除区间多含一枚括号（删"天"把 ]中 圈进去）。
- 六个入口改用它：`eraseOnTree`（落点 = 区间起点）、插入（落点 = 区间终点，事务里已经算好）、
  `splitParagraph`（新标记之后那一位）、`mergeParagraphInto`（被删那枚标记的位置）、
  `undo/redo`（撤销栈给的恢复位置）、`tabCaret`（`tabFrom` 的目标）。
- `moveCaretBy` 改成**在流位置上 ±1** —— 比原来的"侧别逐格 + 跨簇"更直接，且字面就是
  "一次一个位置"，括号自然也在里面。
- `setCaret`（宿主按 (段,偏移) 程序化定位）仍走 `defaultSideAt`：那是**从文本坐标投影到流位置
  的唯一约定**，写在注释里，不再是"到处都在猜"。

**顺手收掉两个真缺陷**（都是这一刀自己引入或暴露的）：
① `cpOffsetInBlock` 直接下标 `blocks_full_` → 旧路径那张表是空的 ⇒ 段越界崩溃（`[6]` 段当场
   访问违例）。改走 `objectsFor(para)`。
② 我在 `relayout()` **开头**加了一次簇吸附 —— 那一刻用的还是**上一轮的簇表**，于是"敲字之后
   紧接一次重排"会把光标拉回旧段长（实测：连打 60 个字符后光标停在 17 而不是 68，探针
   `[2b]` 的"逐个敲 == 一次性插入"帧差 186 像素，差的正是两个光标矩形）。
   源码里那条注释早就写了"这里只夹数值范围、不吸附簇"—— 我把注释一起改掉了，教训：
   **改代码时别顺手删掉解释"为什么不能这么做"的注释**。

**判据**：edit_test 678 → **681**（新增 [29](h) 三条：嵌套删「天」→ 10/1、再退一步删「三」→ 9/1、
三连删「悸」→ 8/0）；浏览器探针 199 → **202**（新增 [14.9] 三条：10/1 且光标 x=227.00 落在

**验证**：native `_c12b6.log`、wasm `_c12w4.log`、浏览器探针 `_c12web5.log` **202 项失败 0**、
头依赖守卫 `_c12hdr.log` **9 项失败 0**、注释 lint **0 违规**、`engine.{h,cpp}` 与
`engine_layout.cpp` clang-format CLEAN。

**遗留**：`setCaretAt`（提示版）与 `setCaretAtSide`（侧别版）两个入口并存 —— 前者给探针与诊断
