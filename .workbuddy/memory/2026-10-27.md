## 整表删除之后的光标落点 / 连页增量排版的后缀平移

- **整表删除光标跑位**：整格选区盖满整张表时走 `eraseTablesCoveredByCells`，但 `plan.at`
  仍是 `selection().begin()` —— 那一端在表格**内部**（第一个被选中的格），删完这个流位置
  已经不存在，后面的内容顶上来，光标就落在下一段的段中间（用户读作"往后跑了好几位"）。
  改成 `eraseTablesCoveredByCells(FlowPos* anchor)` 带回最靠前那张表的起点，调用方拿它当
  `plan.at`；起点在所有步骤左边，删完仍有效，也正是"表格原来占住的那一处"。
- **连页增量排版塌回第一页**（大 bug）：`shiftSuffixBlockAxis` 那一趟只认分页算术 ——
  每行判 `s + lh > cy + ch` 就 `++page; s = cy`。连页的块轴是**整篇累加的绝对 y**，
  于是从第二页起的后缀每一行都判成放不下、整条被拽回条带顶部：中间空一块、下面的接不上；
  后缀里带表时表从错误的块轴位置续排，整篇塌回第一页。修法：`bandOf/localOf` 两个闭包把
  页号与页内坐标都按位置现算（与 layout.cpp 的 `slabOfY` / `locY` 同一式子），
  段前分页与翻页两支都加 `!cont` 守卫；`page_count` 取走完之后的条带号。
- **同一处还有一半**：`layout.cpp` 记 `state_at_start` 时用的是循环里的 `page_index`，
  而连页下它一路不增（不翻页），全篇每段都是 0 号条带 —— `ReflowState` 的相等判据因此
  从第二页起恒不等，增量每次都落到"后缀平移"那一路。改成连页按 `slabOfY(anchor_y)` 记。
- **判据**：原生 `[48]` +1（删完光标停在表那一处：段 0 偏移 0）、新 `[91]`（连页：中段回车
  之后后缀只让出一行 23.378906 磅、整篇块轴严格递增、增量 == 整篇重排，再带一张表验"表跟着
  下移一行、页数没塌回一页"）；浏览器 `insert` +1、`edit-longdoc` 新 `[11]`（真实 Enter，
  6 条：段数 +1、audit diff 0、页数不塌、让出一行、块轴递增）。七份 edit 367 → 372 条、
  `insert` 34 → 35，`AGENTS.md` 已同步。
- **反向验证过**：临时把 `shiftSuffixBlockAxis` 的 `cont` 写死成 false 重跑 `[91]`，4 条红
  （后缀让出 169 磅而应为 23.4、带表时表上移 140 磅、两处 audit 非 0）—— 判据不是空转。
- **文档**：`docs/文档模型设计.md` 里"有表格时不做增量排版"已过时（现在是"遇到表就在表头
  截断续排"）；`docs/跑测试.md` 的 `edit-longdoc` 行补上连页那几条。

## 第二轮：七个手感问题的根因与修法

- **缩放弹回开头**：`paintFull()` 无条件 `scrollY = 0` + 发 `scrollReset`（换文档与换缩放共用
  一条路）。改成 `paintFull(keepScroll)`：缩放按 `新密度/旧密度` 折算滚动位置、不发归零信号；
  宿主 `keepScrollAcrossZoom(before, after)` 同步折算 `scrollTop`（只折算"页顶边距之下"那段，
  上边距是固定 CSS 值）。
- **图片环绕一串毛病**（位置跳段首 / 文字在图的另一边 / 改回行内旧图还在 / 看不出上下方差别）：
  1) `lb.inline_origin_pt` 写成了 `cur_cx` 而不是本行的 `row_x` —— 四周型让宽之后，光标与
     选区落在没让开的那条边，字却画在让开之后（"选了左边、字在右边"）。
  2) 浮动图横坐标原来是"版心居中 + dx"，改成"内容区左边 + dx"（左对齐才是 Word 默认；
     居中的话两侧各留一条，文字只能走一侧）。
  3) 行内 → 浮动时按当前几何反算 `dx/dy`（`floatOffsetsFor`），图留在原处；浮动之间只换 wrap。
  4) 浮动图几何进页指纹（`floatPieceDigest` + `float_fp_prev/new`，变了整页重画）：它不占行盒，
     行带看不见它 —— 这是"渲染不更新 / 旧图擦不掉"的根因。
  5) 浮动框的纵向区间改记**块轴**（分页 = 页号 x 页高 + 页内；连页 = 绝对 y）：原来按页内坐标
     比较，连页下第二页起全部失效。
- **连页下"预先判页"会打断后缀平移**：`local + block_line_h > cy + ch` 这条提前判只在有浮动图
  时生效（那时本来就整篇重排）；没有浮动图时它会引入平移路径复现不出来的规则，
  `auditLayout` 立刻红（实测 diff 78665）。**教训**：给逐行循环加规则要看"后缀整体平移"
  能不能复现它。
- **拖动时两个光标**：起手收起正文光标（`setCaretPhase(false)` = phase + 一次 present，
  另外用 `caretHidden` 抑制闪烁 tick），松手放回；落点竖条的宽度问引擎要（`dropSpot` 载荷
  带 `w`），写死 2px 比正文光标粗一档。手形只在越过门槛之后才变 `move`。
- **点中图片不能复制/剪切**：`copySelection` 只认文本选区。补上"图片对象选区"分支
  （`rev::toSpec` + `writeFragment`），`deleteSelection` 也先认图片（剪切的后一半）。
- **格线看不出能拖**：`pagesEl` 上一帧一次的 hover 探测（复用 `hit` 的三格），
  给 `col-resize` / `row-resize`；图上给 `move` / 八向 `*-resize`。
- **图片拖动**：`moveImage` 现在同时收落点与位移 —— 行内图吃落点（插进文字流的哪儿只能靠
  命中），浮动图吃位移（抓在图身哪一点都行）。只给位移时，从右边缘起手的落点会落在图自己身上。

## 实测：整篇重排 + 重画的耗时

一次"改环绕档位"（= 拖动中每帧如果真重排要付的成本，含 Worker 往返与整页重光栅）：
20 段 7.9 ms、100 段 19.1 ms、300 段 25.0 ms、1000 段 27.1 ms。
现状：拖动 square 图只走 `previewImageMove`（只挪绘制位置、不重排），松手才绕排。
要做"文字实时绕排"，就是按上表的帧成本换；60 fps 预算 16.7 ms，50 段以上会掉到 40 fps 左右。

## 修正：整篇重排不是瓶颈，重画页数才是

上面那条「20 段 7.9 ms … 1000 段 27.1 ms」是**端到端墙钟**，被误读成排版成本。
用 `D.editStats()` 拆开（100 段 / 4 页、1000 段 / 33 页，改环绕档位 = 整篇重排）：

| 段数 | layout | pageFp | paint（重画页数） | 引擎侧合计 | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| 100 | 0.3 ms | 0.3 ms | 4.9 ms（4 页） | 5.6 ms | 22.9 ms |
| 1000 | 0.6-0.8 ms | 0.1 ms | 0.9 ms（1 页） | 1.6 ms | 13.2 ms |

同一份 100 段文档，两个操作都整篇重排（`relaid 100`、`layoutWasFull true`）：
改档位重画 4 页 → 墙钟 22.9 ms；末尾敲字只重画 1 页 → 墙钟 8.3 ms。
**每多画一页 ≈ +3.4 ms，排版不到总量 3%。**

⇒ 结论：给浮动图做"只重排涉及的那几段"没有意义（省 0.2 ms，还不到一次 Worker
往返的 1/10）。该省的是"重画哪几页"。`markPagesChangedFrom(p)` 把 p 之后所有页用
哨兵标脏（绕过指纹比对）—— 拖动一张第 1 页的图会重画到文档末尾，这是白画的。

## 实测：80 页 / 80 张浮动图（4000 段）拖动的成本

造法：4000 段文本 → 135 页 → 每 48 段插一张图（80 张）→ 全部 `square`。
视口 5 页、图在第 1 页。

拖动一帧（`previewImageMove`）：`repainted: 5`（窗口全画）、`paint 9.2 ms`、端到端 18.4 ms/步。
松手一帧（`moveImage`）：`layout 16.7 ms` + `pageFp 13.5 ms`，加光栅与传输 50 ms 以上。

三处原因：
1. `previewImageMove` 用 `markPagesChangedFrom(p)` 标脏 —— p 之后每一页写成哨兵值，
   绕过指纹比对。图在第 1 页 ⇒ 130 页全脏 ⇒ 窗口 5 页全画、每帧传 17 MB。
2. `must_full` 的 `!floats_.empty()` ⇒ 整篇重排。100 段 0.3 ms、1000 段 0.8 ms、
   **4000 段 16.7 ms**（56 倍）。文档规模一变，"增量不值得"的结论就翻了。
3. `computePageFingerprints` 里 `has_float` 让 `partial=false` ⇒ 130 页 + 13 万字形的
   哈希全算一遍（13.5 ms），而只有图那一页的几何真的变了。

## 修：80 页文档拖浮动图"要等几秒才跟上"

真因不是单帧慢，是**命令积压**：输入层每收到一个 mousemove 就发一条 `previewImageMove`，
每次要走一趟 Worker；指针 125 Hz、一帧十几毫秒，队列以两倍于消化速度增长。
再叠上引擎侧按 `markPagesChangedFrom(p)` 标脏（p 之后每一页写成哨兵），
视口 5 页全重光栅、每帧回传 17 MB。

两处一起改：
- 引擎：新增 `markPageDirty(page)`（只标一页；页数对不上时退回 `markPagesChangedFrom`），
  `previewImageMove` 改用它。`dirtyFpValue(base)` 从局部 lambda 提到匿名命名空间，两处共用。
- 输入层：`trackMove` 里只留最新坐标 —— `previewing` + `preview_next` + `preview_idx`，
  上一个预览回来再发下一个；`detach` 里把待发的作废。

实测（4000 段 / 130 页 / 80 张 square 图 / 视口 5 页）：
拖动一帧 `repainted 5 → 1`、`paint 9.2 → 2.5 ms`；CDP 连发 100 个 mousemove，
60 ms 后图已经追到目标位置（改前会排队约 1 秒）。

**还剩**：松手那一帧仍是整篇重排 15 ms + 整篇页指纹 13 ms（`!floats_.empty()` 一票否决 +
`has_float` 让指纹 `partial=false`）。要压到 5 ms 以内得做浮动图的增量排版（脏区收到图
覆盖段 + 后缀平移）。

## 浮动图拖动改成实时绕排 + 修"松手视口跳到光标"

**实时绕排**：`previewImageMove` 不再只挪绘制位置 —— 位移叠进一份浮动图表副本
（`floatsForLayout()`：`floats_` + `image_preview_` 的 dx/dy），整篇重排一次，
`placed_floats` 直接就是预览后的版面。`ImagePreview::placed` 标记"这份位移已经排进版面"，
`imagePreviewPos` 见到它就不再叠第二次（叠两次图会跑两倍远）。
衬于下方 / 上方（layout 3/4）不占版面，仍走"只挪绘制 + `markPageDirty`"。
取消拖动走新的 `clearImagePreviewAndRender`（清预览 + 重排，否则图停在预览处）。

成本（652 段 / 60 页 / 80 张 320×220 图 / 2248 行）：拖动一帧 `layout 5.7 + fp 6.7 +
paint 12.4 = 24.8 ms`（引擎侧），端到端 17 ms/步。paint 是大头 —— 图越大越贵（120×90 时 2.5 ms）。
4000 段会到 ~40 ms/帧，要再快得做浮动图增量排版。

**松手视口跳走**：`afterEdit` 无条件调 `scrollCaretIntoView`，而拖图不挪光标 ——
视口被旧光标（可能在文档末尾）拽回去。改成先比 `caretPara/Offset/Page`，没动就不滚
（`scrollCaretIntoView(st, reveal=false)` 仍同步窗口与状态，只省掉改滚动那一步）。
这条规则对"改格式""提交表单"同样成立。

判据：`image.spec` 新增 3 条（15 用例 / 72 判据）——四周型拖动中文字当场让开、
衬于下方拖动只重画一页、松手视口停在原处（反向：真打字时光标会带走视口）。
踩坑：造多页文档时 `H.setText` 的分段要 `\\n`（模板字符串里写成 `\\\\n`），否则整篇是一段；
滚动之后要等 400~500 ms 让窗口换页，否则 `FRAME()` 的顶边还是旧窗口的，点击落空。

## 四条反馈：连页缝、表格边框、热更、图片出界

**表格右边框 / 底边框可拖**：`tableGridLineAt` 的列循环放到 `i < col_x.size()`（最后一条 = 表右沿），
行循环允许表尾那一行的下边。宿主 `tableResize` 里 `col >= widths0.length` 走"只有最后一列变宽"。
`setTableGridCols` 顺手把 `TableSpec.width` 钉成列宽之和 —— 不钉的话表还是 Auto，各列之和超过它
就被整体按比例缩回去（拖了个寂寞）。`openTable` 的宽度上限从 `cw` 放到 `cw + margins.right`
（表可伸进右边距，不许越过纸张右沿），居中/右对齐时 `shift` 夹到 >= 0。

**图片不出界**：`layout.h` 新增 `clampFloatBoxToTextArea`（页内坐标，夹进版心）。三处共用：
`placeFloatsForPara`（预览与落位都过它）、`imagePreviewPos`（衬于上下方那两档只挪绘制）、
`moveImageToPt`（写进文档的 dx/dy 也夹，否则下次拖动先空走一段）。

**热更/重载**：`vite.config.ts` 加 `server.hmr: false` + `server.watch: null`，删掉 `main.ts` 的
`import.meta.hot` 重载钩子。

**连页末尾"输入不渲染"**：复现到的最实在一条是——回车 28 下正好把最后一段顶到条带底
（caret y=1119 / 页高 1123），这一行横跨两条带：4px 在上一带、字身在下一带顶部 20px。
量到的结果：字确实画出来了（截图 + auditPage 全 0），但落在下一带的顶边，与插入点那一行错开。
试过"一行不许横跨条带"（挪到下一条带顶）——`edit_test` 的「分带与整带逐字节相同」直接红
（连页的页高从此影响排版），而且缝上两条行距被压到 4px。已回退。
留下的是真洞：`computePageFingerprints` 的增量区间没带下一页，接缝那半行的重画判据会缺一页 ——
现在 `cont && dirty_hi + 1 < n` 时多算一页。

## 修：连页接缝上的段落标记"粗一档"

现象：连页末尾回车 28 下之后，那一行的段落标记比别的粗一倍（横笔两行浅灰），
文字那半只是略虚。截图里光标与标记同处一行，看着像标记单独画坏了。

真因：接缝那一趟把上一带的内容挪到本带，位移取的是 `-slab_pt * zoom`
（A4 下 842.4 磅 x 1.333 = 1122.7），而页位图是 `lround(height*zoom)` = 1123 行。
差 0.3 像素 → 段落标记的横笔（1px 线）正好跨两行，抗锯齿按覆盖率摊到两行；
`drawBreakMark` 的"先取整再加 dy"只在 dy 是整数时才保得住落点。

修：`spill_dy = -pagePxHeight()`（整像素）。位图第 0 行就是本带顶端，减一整页高
才是两带之间的真位移。字形、表格、图、标记全走这一个 dy，一并变清晰。

判据：`view.spec.ts` 新 describe「连页接缝」—— 挪上边距（步长 4 磅，小于命中窗口）
把某一行的标记顶到接缝上，断言下一页那一截只有一道横笔、与页内的一样长。
反向验证：把 spill_dy 改回浮点，剖面变成 `[{n:9},{n:9},…]`，判据红。

顺带确认：跨缝行整枚标记落在下一页时（用户那一行），修复前是 2 行横笔、修复后 7 行
完整形状（竖笔/横笔/三角）与页内一致 —— 探针里用页高扫描构造出来的对照。

## 行距几何对齐 Word：光标取行槽 / 压行 / 段前距 / lineGap

按 B → A → D → C 落地，E（行距三态）没动。全部只跑原生判据，浏览器端未跑。

- **B 光标与反白取"行槽"**：`LineBox::slotSpanPt()`（= `advance_pt`，竖排退回列宽），
  `caretRectFor` 与 `selectionRectsIn` 三处改用它。`block_lo/hi` 保持字面盒语义，
  69 处命中/脏区/表格/图片的用途一处没动。光标宽默认 1.0 → 0.5 磅（zoom 2 下 1 设备像素）。
- **A 倍数可小于 1**：`leading = pitch - natural` 不再夹 0；倍数下限 `kMinLineFactor = 0.1`
  （块轴推进不能为 0）。纯文本行 `line_h` 于是恰好等于 `pitch`。
- **D 段前距**：`ParaFormat/Patch.space_before`、编译、`BlockSpec.space_before_pt`、
  横排/竖排/空段三条路径、`shiftSuffixBlockAxis`、rev 哈希、steps 比较、wasm 的 `sb` 键、
  宿主 `spaceBefore`。规则：页顶不加（`atPageTop`：分页模式下 `pg > 0 && y <= 版心顶`）、
  与上一段段后距**相加不折叠**、文档首段照样让出。
- **C lineGap**：`FontInstance::lineGapPt()`（hb h_extents 的 line_gap），单倍行高改为
  `ascent + descent + gap`，基线不动（gap 落在 descent 之下）。自带三款字体 gap 全是 0，
  画面零变化，判据只能钉"单倍 == ascent + descent"。
- **判据**：原生 `edit_test` 新 `[92]`（43 条）—— 单倍下光标高 == 行槽、1.5 倍下字面盒不动而
  行槽翻倍、同段两行反白首尾相接、0.8 倍真的压行、倍数 0 被下限顶住、段前距 6+10=16、
  带段前距的增量 == 整篇重排、页顶不加、首段照样让出。
- **踩到的两个坑（都不是业务代码错）**：
  1. `build/native` 的 CMakeCache 里 `CMAKE_CXX_FLAGS` 与 `CMAKE_CXX_FLAGS_RELEASE` 是**空的**
     —— 没有 `/EHsc`、没有 `/O2`、没有 `/DNDEBUG`。MSVC 下 `std::variant`/`vector` 的异常路径
     等于 UB，`steps.push_back` 扩容时崩。日志里成片的 `warning C4530` 就是征兆。
     `cmake --preset native --fresh` 之后 8/8 全过，耗时 58 s → 13 s。
  2. `edit_test` 的 `main` 上万行、各节局部变量共用栈槽，加上 Skia 的 FreeType 光栅还要几层
     递归，1 MB 默认栈会在"某节之后的第一次绘制"上溢出（`SkFont::getBounds` → `TT_RunIns`，
     异常码 `0xC00000FD`）。症状极具误导性：同一段代码在另一个构建目录里跑得好好的。
     已给 `heditor_edit_tests` 加 `/STACK:8388608`。
- **教训**：判定"是崩溃还是输出被缓冲截断"要看 `setvbuf`（本套件已是 `_IONBF`）；
  判定"改动引入的还是环境带的"就另建一个构建目录跑同一份源码 —— 这次靠它排除了两轮误判。
  `scripts/msvc_env.ps1:53` 在中文 locale 下会误判 `cl` 版本（`cl` 单跑只打用法行），
  用 try/catch 绕过，脚本本身没改。
- **待办**：E（exact / atLeast）需要模型换成"规则 + 值"、`breakLine` 分叉、竖排与空段同步，
  以及**按行裁切**（现在光栅只有整页/整带一层裁剪）；`exact` 小于内容时 Word 是裁字。

## E：行距三态 exact / atLeast（含按行裁字）

模型、编译、排版、绘制、宿主、文档全线接通。原生 8/8 全绿；构建产物验收 128 条全过。

- **模型**：`LineSpacingRule{Auto,Exact,AtLeast}` + `ParaFormat.line_rule / line_factor /
  line_exact`（不折算成一个数：换字号时倍数该变、磅值不该）。补丁同三项；`empty()` 一并。
- **排版**：`LineSpacing{rule,factor,exact_pt}` 进 `BlockSpec`，行高统一走 `lineHeightFor`
  （`layout.cpp`）：auto 在单倍行高上乘倍数、atLeast 取 max(单倍, 墨迹, 值)、exact 就是值；
  `exact ≤ 0` 退回 auto。横排/竖排/空段/表内四条路径都换掉了。
- **裁字**：`LineBox.clip_text`（只有 exact 且值 < ascent+descent 时为真），绘制侧在
  `emitGlyphs` 里按行进出裁剪栈。`Bitmap` 新增 `pushClipRect / clipMark / restoreToMark`；
  **跨越多次绘制要用 clipMark/restoreToMark**，布尔配对少退一次会让画布一直被裁。
- **宿主**：`ParaFormatPatch.lineSpacing = {rule, factor?, exact?}`，**旧的 `lineFactor` 已删除**
  （不留兼容）；示例页的行距下拉加了"最小值 18 磅 / 固定值 20 磅"两项，值写成 `rule:值`。
- **JSON 键**：`lr`（"auto"/"exact"/"atLeast"）+ `lx`（磅），`lf` 仍是 auto 倍数。
- **判据**：原生 `[93]` 30 条（三档行高、字面盒不动、裁字按帧像素量深、exact=0 退回 auto、
  增量==全量）；web `format` 第 18 个用例量三档的反白高与读回。
- **踩到的坑（重要，未修）**：**改完段落格式之后页面图层不重光栅**。证据：同一台引擎
  先设 exact 8（画出来是裁过的）、再改回 auto，帧上仍是裁过的墨；`setConfig + relayout +
  repaint` 也救不回来；换一台全新引擎同一份文档就是对的（深 14.5 vs 8）。浏览器侧一样：
  设 exact 8 之后帧上的字**完全没被裁**。选区/光标那层是每拍重画的，所以表现为"半个改动生效"。
  字符格式改完是重画的（加粗比截图那条一直绿），所以只落在段落格式这条路上。
  待查：`relayout()` 给页标脏的那段（`pages_known_changed` / `computePageFingerprints`）。
- 另外：`web/vite.config.ts` 里的 `watch: null` 被去掉了（不是我改的），现在 dev 服务会跟着
  文件失效模块，之前那个"5173 发旧转译"的坑自动消失。

## 修两处观感：多倍行距字不在反白中间、软换行处起选多出小方块

用户拿 Word 并排比出来的两条：① 3 倍行距时字贴在反白顶上、下面空一大块；② 选「处理」两个字时
上一行末尾多出一个淡蓝色竖条。

- **① 的根因**：多出来的行距以前全落在行底。查下来 Word 的行为**取决于文档网格**：勾了「对齐到
  网格」时单倍行距 = 行跨度、文字垂直居中；取消后才是"上对齐"。中文 Word 默认开网格，所以用户
  看到的是居中。CSS 的 `line-height` 也是对半分。⇒ `lineLeadTopFor`：auto 上下对半（`lead =
  (行高 - 墨迹)/2`，可为负，压行时字上下都探出槽外），exact/atLeast 仍贴盒顶（Word 也这两档才
  显得偏上，且 exact 裁字只裁得到底部）。行盒因此多一位 `lead_top_pt` 与 `slotLoPt()`：
  字面盒（字形/脏区/图片锚点）与行槽（光标/反白）分开，`基线 = 行槽顶 + lead + ascent`。
  同步改了命中（纵向按行槽比，点槽里的空白也落在这一行）、增量平移、`exact` 的裁剪框。
- **② 的根因**：`selectionRectsIn` 里"零宽 ⇒ 补一条 0.35em 窄条"没有判据。软换行处的偏移与
  `lb.last_cp` 相等，选区从那里起时本行求交就是零宽，于是凭空画了一小块。改成只在"本行的段落
  标记真被选中"（`lb.last_cp >= 段长 && lo <= 段末 < hi`）时才补。
- **判据**：原生 `[92]` 追加 11 条（lead = 半条行距、字面盒顶比行槽顶低 4.34 磅、光标从行槽顶到
  行槽底、固定值 lead 为 0、软换行处起选只有 1 条反白、跨过换行处是 2 条）；web 新增
  `edit-selection` 第 `[23]` 个用例（3 条，用光标 y 跳变自己找换行点，公开面上量）。
  另修两条旧判据的语义：光标矩形比 `slotLoPt()` 而不是 `block_lo_pt`；1.7 倍正文的摘要重取
  （`0xb27e1602e6412913` → `0x65cf7bda39ea3a62`，行数/字形数/页数不变，只是字整体下移半个行距）。
- **量过的目检**：3 倍行距下反白 52.14 磅（= 3 × 17.376），字上方空 57px、下方空 52px（zoom 2
  下 ≈1.8 磅差，是字形首行笔画的位置造成的），改之前是上方 ~0、下方 ~130px。
- **坑**：web 端**改完段落格式后页面图层不重光栅**（既有问题，见上一条待查），所以"字有没有居中"
  不能靠改格式后的帧像素量 —— 判据走投影（`selection().rects` + `caret().rect`），像素只做了一次
  临时目检，没留在仓库里。
