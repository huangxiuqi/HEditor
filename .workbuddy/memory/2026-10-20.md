## 原子、域、迁移路径：步 1 与步 2 收口

图片 / 公式 / 域进 rev 载荷（`Payload` 十支），哈希与落盘补齐。关键的取舍不是 variant 多三支，
而是**盒子几何只有一份算法**：抽成 `src/core/doc/atom_map.*`（`atomContentHash` +
`resolveAtomBox`，输入是模型无关的 `AtomGeometry`，诊断由调用方按自己的节点号记）。两份实现的
分叉表现是"同一份文档在投影里比编译里高出一截"，画面看不出来，只有逐字段比较抓得住。

盒子延到落段时才算 —— 公式默认框按段落字号估，字号是段落属性。投影为此维护
`(对象下标, AtomGeometry)` 待定表，落段时补齐。

域只多一条：`FieldSpec::cache` 是求值结果，**不进内容哈希**（否则求值前后两个哈希，撤销对不上），
但照样落盘；往返判据对域另做逐字段比对。TRAPS 105。

迁移路径 `rev::fromTree(tree, &doc, &err)`：节点号原样带（身份同源）、载荷查表对应、hidden 与
水位带上；**表示不了就拒绝**（多节）。它是等价判据的桥：`project(fromTree(tree))` 与
`compileDocument(tree)` 逐字段比。TRAPS 106。

## 步 3 第一刀：断行拆出来 + 自审补上表格

`layout.cpp` 里抽 `BrokenLine`（簇区间 + 本行行高度量，**没有页号也没有 y**）、`breakLine`
（切一行 + 算行高，横竖共用同一个式子）、`breakBlock`（横排一次切完整块）。

- 横排容量 = 块可用宽度（与页无关）→ 一次切完；竖排容量 = "这一条带还剩多高"，换带由已排
  几列决定 → 只能一列一列断。两种切法一个实现（TRAPS 108）。
- 两处逐字相同的度量代码（横排行高 / 竖排列宽）因此只剩一份。
- 断行缓冲区提到块循环外复用：2000 段不会变成 2000 次分配。
- 分页仍在主循环：表格行是"等所有格排完才结算"的单元，放不下时还要回挪已落位的行
  （`moveToNextPage`/`shiftRowDown`/`splitRow`）。改成"先算完所有行再统一落位"是重写，
  判据要先有逐像素比较对象（步 5）。

**顺带补洞**：排版自审过去对表格完全失明（只比 glyphs / lines / para_index /
cluster_starts，而表格几何只在 `placed_tables`）。加 `sameTable` 逐表比位置/列边界/逻辑格/
行片段；`sameLine` 补上格几何六项与簇的绘制字段四项；`auditLayoutJson` 加 `tableDiff`。

**两个方向都验过**：
- 把表格行矩形 y 加 0.5 pt（改在排版里）→ 自审全绿。这就是 TRAPS 107：自审只证明两条路径
  一致，不证明实现正确。
- 只改参照侧 `ref.placed_tables[0].placed[0].y += 0.5f` → 带表格的五条断言全红，证明
  `table_diff` 真的接通了。

## 第六批：流索引紧凑下标 + 统计发布时机（复核建议第 6 条与 6b）

### `rev::FlowIndex` 不再按节点号开数组

原实现按 `doc.next_id + 1` 开三个数组（`by_id_` / `first_` / `span_`）。节点号是递增水位
（新建节点才分配、旧号不回收），活节点数并不跟着涨 —— 于是索引占用只随会话长度变差，
而且每次构造都要整份 `assign` 清零（一次按键构造三次上下）。

改成 `nodes_` / `first_` / `span_` 按**活节点重新编号**，节点号只作查表键；查表是开放寻址
哈希（容量取 `2 × 活节点数` 的 2 的幂、负载 ≤ 0.5、`id = 0` 作空槽）。构造顺序是"先遍历、
后建表"—— `measure` 只写不读，表在它之后一次建好。`indexOf` 是唯一入口，`by_id_` 删除。

判据 `rev_test` [24]（6 条）：三千轮分段+合并（水位 43 → 3062、段数回到 20、编辑真的发生
了），每活节点 **50 字节**（上限 96）、总量 **2056 字节**（小于水位 × 8，旧实现是 3 个数组
× 水位 ≈ 24 B/号）；反向一半是"400 段文档 49824 字节，明显更大"。
注入验证没做（判据本身就是"旧实现必红"的形状：把容量按水位算回来，第二条与第一条同时红）。

  `block_flow_*` 收进 `BlockFlow`，不动坐标口径）。

覆盖层的形态没有拍死：`putImageData` 是覆盖不是合成，alpha 混合必须发生在某处，三种做法
（两张 canvas 叠放 / 离屏画布 + `drawImage` / 引擎每页两份位图）差别只在由谁做。
**三种都不影响 5A–5C**，所以留到 5D 前用探针量一次 `drawImage`（一页 0.9 Mpx）再定：
0.3 ms 以内选第二种（DOM 不变），否则选第一种。连页模式是一张视口内容画布 + 一张视口
覆盖画布，与分页模式的"每页一张"落点不同但引擎侧接口一致。

## 第八批：连页模式的画布形态（讨论，未改代码）

用户问：连页现在是一张视口高的画布、内容在里面滚，能不能做成"真实高的一张画布"直接
撑开父容器；以及现在这种"固定在视口上"的做法挂到任意滚动容器里能不能工作。

### 测绘到的事实

- 连页**不是 CSS sticky**，全仓 `sticky` 出现 0 次。形态是：视口画布 `position:absolute`
  挂在 `stageEl.parentElement` 上，尺寸 = 视口、`top = stageRect.top - hostRect.top`
  （`web/worker_host.js:508~540`），内容每拍按 `页号 x 步距 - scrollY` 重贴
  （`web/engine_worker.js` 的 `blitPageContinuous`）。`#wrap{position:relative}` +
  `#stage{position:absolute;inset:0;overflow-y:auto}`（`web/worker.html:28~29`）。
- 连页的排版是"无翻页、页号由 y 现算"（`src/core/layout/layout.cpp:556`、`slabOfY`），
  所以**一行可以跨条带**；但每个**字形**的页号是 `slabOfY(pen_y)` 逐字算的
  （`layout.cpp:1394`），即文字天然按条带分桶。表格行按 PageSpan 分。
- 条带高度 = 页高 + 页间隙（连页间隙 0），`PageMetrics::slabHeightPt()`。
- 96 dpi 一页 = 794 x 1123 设备像素 = 3.57 MB（与 `engine_paint.cpp:247` 注释里
  "18.07 MB / 5 页" 对得上）。

### 真实高画布的天花板（推算，未实测）

| 页数 | 画布高（设备 px, 96dpi） | 内存 |
| --- | --- | --- |
| 20 | 22,460 | 71 MB |
| 50 | 56,150 | 178 MB |
| 58 | 65,134 | 207 MB（Chrome 单边约 65,535 封顶） |
| 200 | 224,600 | 713 MB |

Firefox 单边约 32,767 → 29 页；Safari 桌面约 25,600 → 22 页；老 iOS 4096 → 3 页。
dpr 2 时全部减半（Chrome 29 页、Firefox 14 页）。超限时 `canvas` **不抛错**：宽高一设，
后续绘制全变 no-op，控制台一条 warning，表现是整片空白。

### 任意滚动容器下的四个隐含假设

1. `#stage` 必须有确定高度（`inset:0` 在 `flex:1;min-height:0` 里）。塞进 `height:auto`
   的容器 → stage 高 0 → `viewSize()` 得 1x1 → 引擎只装一页。
2. 视口画布的父级必须是**包含块**（非 static）。宿主是 static 时 `top` 对到更远的祖先
   或 ICB，外层一滚画布就脱开 —— 本地开发（body 不滚）看不到。
3. 祖上有 `transform` / `filter` / `will-change` 同样改包含块。
4. 只监听 `window.resize`（`worker_host.js:1612`）。splitter / 折叠面板改容器大小
   （窗口没变）时 `viewSize` 是旧的。要 `ResizeObserver(stageEl)`。

活下来的：命中测试（`getBoundingClientRect`，外层滚动自动抵消）、IME 定位（宿主坐标）、
spacer 高度（stage 内绝对定位）。不支持的：宿主让"页面自己滚、编辑器撑成文档高" ——
`viewOp` 只在 `stageEl` 滚动时发，`viewSize` 用的是 stage 的 clientHeight 而不是与视口相交那块。

### 建议（待用户定）

连页改成**条带画布**：与分页同一条路径，只是 gap 0、不画页边框、spacer 高取 contentPx。
好处是原生滚动（滚动不再每拍重贴）、内存有界（窗口内几条带）、不撞画布上限，并且能删掉
`syncViewCanvas` / `blitPageContinuous` / `viewCtx` 这条支线。文字天然按条带分桶，
所以绘制侧不用改口径。

## 第九批：5A 页位图（渲染层第一刀）

## 第十批：分层渲染调研（只讨论，未改代码）

用户问"有的框架支持分层渲染甚至好多层也不怎么费资源，怎么实现更好"。查了 pdf.js、Excalidraw、
tldraw 5.0、Flutter、Figma、PSPDFKit/Nutrient、Chromium 与 putImageData 的资料，产出
`docs/分层渲染调研-2026-10-20.md`。

### 核心结论

- 层的成本不取决于"几层"，取决于**每层占多少像素、多久重画一次**。别人的几十层便宜，是因为
  那些层是**显示列表或稀疏 DOM**（Flutter 的 Layer 是 display list；pdf.js 的文字层是 span；
  Figma 是瓦片），不是几十张全幅位图。全幅像素层按 `W×H×4×dpr²` 收费，与内容多少无关。
- Chromium 自己的层策略是"默认合并、重叠就 squash"，DevTools 团队还说过"多个 canvas 比一个
  更大的 canvas 更贵"；tldraw 5.0 反过来把"每个一个 SVG"的 overlay 并成一张 canvas ——
  这就是元素级分层有上限的反向证据。
- 真正决定成本的是**每次上传/重画的面积**。实测现状：一次光标移动 `dirtyPages=[该页]`，
  宿主 `blitPage` 整页上传 893×1263 = **1.13 Mpx**，而光标只有 2×20。这一笔比"层不够多"
  严重得多；5B 的 `pageDirtyRects` + 5C 的 `takeDirtyPages` 本来就要修它。
- 我们这套引擎（CPU Skia → RGBA 位图）只能做像素层，预算就是 2 层；第三层起必须满足
  "稀疏 / DOM / 昂贵且几乎不变"三者之一。

### 对 5D 的修正

原方案是"每页一张透明覆盖层 + 宿主两张画布叠放"。改成**倾向单层 + 矩形合成**：引擎按矩形把
"内容 + 瞬态"合成成最终像素，宿主 `putImageData` 那一块。理由：零额外全幅缓冲、
`selfCheck` 与 365×2 条像素判据的形状不变、没有 alpha 取整与两层对齐的新风险。
备选仍是稀疏覆盖层，触发条件是出现扫描件底图/水印/批注/协同光标这类"昂贵且几乎不变"或
"有独立更新频率"的内容。

决策未拍死（用户还要看）。方案文档 2.2 加了调研补记，5D 改成两形态对照 + 判据。

### 补：水印（用户 20:44 提出）

层序定死：页底色 → 水印 → 页边框/格线/字形/原子框 → 装饰 → 瞬态。

水印视觉上最底层，但**不做第二张画布**：内容位图不透明，要让下面的水印透出来就得让内容带
alpha，字形抗锯齿的混合对象、`selfCheck`、"内容层是文档的纯函数"全要改。改成**一张共享的
页大小水印位图**（`WatermarkLayer{Bitmap px; uint64_t fp; bool valid;}`，全文档一张，含页底色），
页光栅的起点从 `fillRect(page_fill)` 换成 `blitFrom(水印位图)`；带光栅只搬那一条带，面积与
原来的整页填充相同。水印关闭时 `valid=false` 走原路径，默认零回归。

失效改成 **`raster_epoch_` 混进每页指纹**（水印 + 缩放 + 页度量 + 底色 + 边框 + 格线 + 原子框），
改水印 = 纪元 +1 = 所有页自动失效。这同时把 5A 里 `setConfig` 手动比八项收成一处，是 TRAPS 128
的正解。判据：关水印逐字节同今天；开水印后 `auditPage` 仍 0；改水印后窗口内所有页都重光栅；
摘要 A/B/C 不变（水印不进排版）。

真需要第二张底层的情况：水印动态变化（每页不同/随时间变）或必须盖在文字之上。

## 第十二批：5C 宿主按脏矩形上屏（删帧与槽并入 5D）

### 为什么改了这一刀的形状

原计划在 5C 里删掉帧与槽。实施时确认走不通：**页位图只有内容**，宿主按页贴就等于把
光标、选区、表单括号全丢了 —— 它们画在帧上，而帧是"内容 + 瞬态"的合成品。要让宿主
按页贴，得先让瞬态有一条自己能导出的路，那正是 5D。硬做只有两种收场：把瞬态烘进页
位图（擦一次就得重光栅那块内容），或每页多存一份全幅导出位图（5 页 +18 MB，更差）。

所以 5C 只落它真正独立的那一半：**上屏面积**。删帧与槽、连页条带画布随 5D。

### 做了什么

- `engine_worker.js` 的 `blitPage(p, rects)` 与 `app.js` 的 `blitFrame`：按
  `pageDirtyRects(p)` 只贴变了的块。槽过期整页贴；引擎报脏却给不出矩形时也整页兜底。
- 决定"贴哪几页"改用 **`pageDirtyPages`**（引擎新增）：矩形是累积的，某一拍的 present
  可能没被消费（窗口平移、槽重建），按本拍 `dirtyPages` 贴会永久漏几块。
- 单线程宿主的画布记录加 `fresh`：新画布/刚改尺寸必须整页贴 —— 窗口平移进来的页
  内容没变，引擎那边没有矩形，而画布是空白的。
- 上屏账：`lastBlit.px`（单线程）与 `mirror.blitPx`（worker），`__heditor.blitStats.px`
  两端同形。面板加"上屏面积（本轮）"。
- 引擎：整帧重贴分支补旧光标 / 旧标记 / 旧选区（TRAPS 134）；**页脏矩形再加一份
  `refresh`**（TRAPS 136）。

### 踩到并修掉的两处漏贴

1. `dirtyPages`（本拍）与 `pageDirtyRects`（累积）不同步 → 加 `pageDirtyPages`。
2. 按"谁画的"记瞬态清单不完备：跳字段之后画布上多出 93 px（3×31 的旧光标），
   `selfCheck` 报"画布有、帧没有"，而 `auditFrame`=0、native 全绿。查了四轮（旧光标
   x=198 不是 219、旧标记 6 条、transient 21 条、宿主贴过的 5 条矩形）才确认那块不在
   任何清单里。改成 `transient_dirty ∪ refresh` 之后消失 —— `refresh` 是按"帧上真的
   写过哪儿"记的，擦除也过它。

### 判据与实测

- `edit_test` [58]：光标移动 **72 px²**、打字 **12 338 px²**、整页 102 000 px²；
  `refresh` 兜底之后这两条仍过（ctest 4/4，150 / 1437 / 845 / 297）。
- `edit_probe` [3] 新增：光标移动之后 `blitStats.px ∈ (0, 2000)` —— 引擎算了矩形、
  宿主又整页贴时，像素判据全绿，只有这个数看得出来（TRAPS 135）。
- 试过两版"整帧重贴旧标记"的判据，都是恒真（新光标/新括号把旧矩形兜住），已删；
  结论写进 TRAPS 134 的星号段。

### 收尾时又踩的两个坑（都只在浏览器里显形）

- **worker 的 `OffscreenCanvas`：`putImageData` 六参数 + 负 dy 会裁错那一块。**
  跨页取块把帧坐标折回页内坐标，写法是 `putImageData(img, 0, -srcY, r.x, srcY + r.y, ...)`。
  index（普通 canvas）一直是对的，worker 贴完仍差 42 px —— 正好一块光标，而 `px` 也是 42，
  说明"贴的就是这一块，但没贴对"。改成逐块拷成 `new ImageData(w,h)`、两参数贴到
  `(r.x, r.y)`，立刻绿（TRAPS 137）。
- **`selfCheck` 要先结清自己的账**：两次操作之间可能有一拍只 present 没 blit（闪烁拍），
  直接比会把时序当成贴错。开头加 `host.blitPages()`（TRAPS 138）。

### 5D 前的一条设计澄清：括号只拆墨迹（23:15）

提问：表单控件括号也要拆进瞬态层吗？答：拆，但只拆"墨迹"，不拆"占位"。

三个身份：占位宽度（`LineCluster{placeholder}`，进文档流、集合一变就要重排，由
`bracketPlanId` / `bracketPlanKey` 管 —— 在排版层，不在任何位图里）、括号墨迹 `[` `]`、
Focused 档的小点。后两者今天都画在帧上、靠 `control_marks_prev_` 擦，帧要删就得一起搬。

不能把墨迹烘进页内容位图的判据只有一句：**页位图的失效判据是页指纹，而括号不参与块哈希**。
不并进指纹 → 切档 / 换字段 / 切只读时页位图被判"没变"，旧括号永久残留；并进指纹 →
Focused 档换一次字段就整页重光栅（8~9 ms），比现在的整行重排还贵。

它与光标不同频：All 档下只随文档 / 档位 / 版面变，光标跨字段时一个像素都不动。所以
5D 里它进脏列表的路径是"`markPlanSignature` 变了 → 旧 ∪ 新矩形"，不是每帧重画；版面变
则那几页整页进脏列表、顺带重画。附带收益：All 档下签名没变可整个跳过 `drawControlMarks`
（它每帧还要过一遍窗口内的行）。已写进 `docs/步5-渲染层方案.md` 的 5D 小节。

### 改判：括号与小点不拆了，搬进内容层（23:20）

用户提出产品变更：小点改成独立开关（不再跟随 focus）、控件边界字符可配置（默认 `[]`），
并直接质疑"占位变了不还是要重绘吗，拆出去的意义是什么"。这个质疑成立，而且比"配置化"
更彻底 —— **即使保留 Focused 档，括号墨迹也不该有瞬态出口**，因为它的**每一个**变化事件
都伴随重排或光栅签名变化：

| 改什么 | 占位宽度 | 排版 / 页指纹 | 光栅签名 |
| --- | --- | --- | --- |
| 边界字符 | 变 | 变 | 变 |
| 显示 / 不显示边界 | 变 | 变 | 变 |
| 小点开关 | 不变 | 不变 | 变 |
| 边界颜色 | 不变 | 不变 | 变 |

最轻一档也是整页重光栅，矩形出口永远用不上。**抽象判据**（这次真正学到的一条）：
一个东西要不要瞬态出口，看"它变的时候会不会顺带改页指纹或光栅签名"，不看"它今天画在
帧上"。之前的归类错误就是把"今天画在帧上"当成了判据。

- 瞬态只剩光标与选区两样。
- 落点：`drawControlMarks` 的绘制搬进 `rasterIntoBitmap`（页内坐标）；配置项并进
  `rasterSignature`（边界字符左右两串、两个 mark 颜色、小点开关、`control_dot_pt`）。
- 可删：`control_marks_prev_`、`mark_sig_prev_`，及它们在 `refresh` / `transient_dirty`
  里的分支。
- 三个实现要点：① 改字符必须重排（字符是排版输入，`plan_changed` 要含字符，否则按新字符
  画、按旧宽度排）；② 自定义字符缺字形要兜底（退回 `[]` 或拒绝配置）；③ 层序变了 ——
  光标从括号之下变到之上，重叠几像素画面会变，判据要跟。
- 只读不受影响：`bracketedControls()` 返空 → 无占位 → 内容位图本来就没括号。

已定（23:24）：多字符支持，一串作为一个整体（一个占位簇，光标与选区都不进入内部）；
小点开关时所有控件都画；Focused 直接砍掉并移除相关代码。
执行顺序：**5D-0（纯语义：配置化 + 砍档，绘制位置不动）→ 5D-1（搬进页位图 + 删帧与槽）**。
小点开关的代价是整页重光栅（不占宽度、不动排版，只动光栅签名；引擎没有任意矩形级的
内容重光栅，只有行带级）——8~9 ms/页，设置项不是每帧操作，第一版不做微优化。

### 判断：不做任意脏矩形（23:32）

用户问"任意脏矩形是不是最强的增量更新、以后换改动大吗、富文本有必要吗"。

- **不是最强**：再往上是 display list（`SkPicture` 式指令重放，不重画像素）—— 差一个维度。
- **改动中等**：光栅器接口 + 行/字形相交裁剪，上屏侧已经支持任意矩形（5B 做过），
  页位图的"有效"仍是整页级（失效判据是页指纹），不会引入"部分有效"状态。
- **现在没必要**：页有物理上限（1.13 Mpx / 8~9 ms），行带已把打字压到 12 338 px²；
  一次敲键 3.2~3.6 ms 里主要成本是 shaping 与排版，不是像素写入。富文本真正的增量难点
  是排版的流式性（断行点变 → 下游平移），那条线已经在做。
- **触发条件**（写进文档）：光栅耗时 > 投影 + 排版耗时；或表格编辑成为主路径
  （单元格窄、行带宽，矩形唯一明显赢过行带的地方）。
- ★ 结论句：**脏矩形解决"小改动别画大片"，分层解决"大片别每次画"**。页边框 / 表格线 /
  水印这类"面积大、变化少"的东西该进缓存层，不该靠脏矩形。富文本里后者更值钱。

### 判断：display list 换不来内存（23:48，只讨论）

用户问"改 display list（字型引用计数跨多个 list 共享）会不会省内存、能不能做到省内存
且不降速"。答：省不了大头，当前形状下净亏。

内存构成（96 dpi、5 页窗口、2000 段 ≈ 8 万字形）：

- 页缓存（窗口+2 页）×3.57 MB ≈ 25 MB；`base_` 18 MB；`bitmap_` 18 MB —— 同一页像素
  存在三份，这是最大的一笔，且与内容表示无关。
- Skia strike 缓存预算 48 MB（`kGlyphCacheBudgetBytes`），按 (typeface, 字号, 亚像素
  相位) 全局唯一、引用计数，已经是"字形共享"的终点；自己再加一层只会多一套所有权。
- 排版产物 88 B/字形（`PlacedGlyph` 56 + `LineCluster` 32）；`ShapingCache::BlockShaping`
  约 89 B/字形，按段常驻、**无上限无淘汰**，与 layout 存同一份信息的两遍。

判据（记下来）：重复的是**像素**，不是指令。display list 去重的是指令，打错地方。
**去重不降速，砍缓存降速** —— 前者是删 `base_`/`bitmap_`、字形记录 run 化、让 layout
引用整形 run；后者才是页缓存条数与 strike 预算，要量 `glyph_cache_bytes` 与 miss 率再定。

引用计数当前无对象可共享：只有一份 layout，撤销栈里是修订（模型）不是排版产物；页位图
是像素不是 list。真要共享，共享单位是整形 run，不是 mask。

回来的触发条件：一页装不下（无限画布 / 超大页 / 25% 概览一次重放几百页）、跨实例共享
排版产物（协同、缩略图、打印预览）、上 GPU 合成 —— 这三条都不在路线图上。

### 预览 / 打印：SVG 导出与 Skia 后端（23:58）

- **两个后端在构建里都是关的**：`scripts/build_skia_native.ps1` 与 `build_skia_wasm.ps1`
  都写 `skia_enable_svg=false`、`skia_enable_pdf=false`。源码树里有
  `modules/svg`（`SkSVGCanvas::Make`）与 `src/pdf`，要重开必须两份脚本一起改，
  否则 native/wasm 的库行为分叉。
- `SkSVGCanvas` 的三条限制（读源码确认）：字形默认输出 `<text>` +
  `SkSVGDevice::AutoElement::addTextAttributes` 只写 `font-family` / `font-size` /
  `font-style`，**不嵌字体、不写 @font-face**；`kConvertTextToPaths_Flag` 退成逐字形
  `<path>`，没有 `<use>` 去重；输出结构不可控（无 id、无页分组、无语义）。
- 绘制出口只有 5 个原语（`fillRect` / `strokeRect` / `blendRect` / `drawGlyph` /
  `drawGlyphs`），`rasterIntoBitmap(Bitmap& target, ...)` 直接吃 Bitmap。
  "一条绘制代码、三种落地"的成本就在把这 5 个抽成 sink，不在写渲染器。
- 判断：预览用**自写 SVG 序列化器**（从 `layout_` 出，`<defs>` 按 (face, size, glyph)
  去重 + `<use>` 引位置）；打印用 **SkPDF**（磅 == 1/72 英寸，页框零换算，带 hb-subset
  字体子集，`SK_PDF_USE_HARFBUZZ_SUBSET` 在 harfbuzz 打开时可走到）。
- 最容易错的一处：SVG 的 `viewBox` 必须取磅（`1pt = 1 user unit`），否则整篇 ×4/3。
- 不走的两条：DOM SVG 当编辑面（第二个编辑实现）；拿 DOM SVG 去浏览器打印
  （分页靠 CSS `break-after`，与 `PageMetrics` 的排版分页是两套）。
