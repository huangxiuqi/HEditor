## 工程化第一步：依赖与工具链的归路（新增 docs/依赖与工具链管理.md）

用户提问：三方依赖现在下载到 `third_party`，是否改成 git submodule？非源码依赖改成 vcpkg？

**先摸清现状（实测，不是照抄清单）**：`third_party` 只有 `harfbuzz-14.6.0`（在用）与
`freetype-2.14.3`（**零引用**，21 MB 空占）；两者都已被 `.gitignore` 排除，且
`CMakeLists.txt` 让用户去跑一个**并不存在的 `scripts/fetch_deps.sh`** —— 也就是说当前
没有任何可执行路径能重建这两份源码。Skia / emsdk / gn / ninja 在 `.toolchain` 下，
Skia 的 6 个 externals 按 commit 取（已钉），但 **Skia 主源码取的是 `refs/heads/main`**。

**结论（三条）**：
- **源码依赖走 git submodule**：HarfBuzz 钉 tag `14.6.0` + 稀疏检出只留 `src/`。
  已验证可直接替换：上游 tag 的 `src/hb-version.h` 是**入库文件**（size 2597，与本地同尺寸），
  我们不跑 meson，所以不需要额外生成步骤；`harfbuzz.cc` 的 69 条 include 全在 `src/` 内
  （没有 `../`），所以只留 `src/` 与根文件就够（108 MB → 约 10 MB，`test/` 占 92 MB）。
  版本表达方式随之改变：目录名里的版本号作废，版本 = gitlink 的 commit。
- **非源码依赖走 vcpkg**（manifest 模式 + `builtin-baseline` 钉注册表快照），
  但**只服务 native**：wasm 的 emcmake 配置不传 vcpkg 工具链。理由是不打破
  "native 与 wasm 共用同一份 HarfBuzz 源码与同一组宏"这个前提。
  本机 vcpkg 在 `D:\ProgramFiles\vcpkg`，baseline 取它当前 HEAD
  `b61e5146d2e883945beda481ca4ab42fd3c287f5`。
- **Skia 与 emsdk/gn/ninja 两条路都不走**：Skia 不是 CMake 工程、自带 DEPS 依赖同步器、
  且七条 `SK_*` 宏必须与它编译时逐条对齐（包管理器会把这些开关藏起来）。

**否决的替代方案**：FetchContent / CPM（配置期下载，把构建与网络可达绑死）；
emscripten ports（`-sUSE_HARFBUZZ=1` 只为 wasm 提供，会分裂成两套 HarfBuzz，
断行结果可能不一致，而"与全量一致"是本项目核心判据）。

**本轮落地**：新增 `docs/依赖与工具链管理.md`、`scripts/deps_init.ps1`（submodule + 浅克隆 +
钉 tag + 稀疏检出 + 哨兵校验）、`vcpkg.json` / `vcpkg-configuration.json`、
`licenses/MIT-HarfBuzz.txt`（原来许可原文只存在于被忽略的源码目录里）；
`CMakeLists.txt` 的 `CED_HB_ROOT` 改成"submodule 优先、旧目录回退"并打印用了哪一份
（顺手修掉那句指向不存在脚本的报错）；`build_native.ps1` 加 `-Vcpkg` 开关
（默认不开，三元组 `x64-windows-static-md`）；`.gitignore` 补 `vcpkg_installed/`；
`AGENTS.md` 补依赖初始化命令；架构文档与 THIRD_PARTY_NOTICES 各补一处指针。

**验证**：`scripts\deps_init.ps1` 与 `build_native.ps1` 用 PowerShell 解析器查过语法；
两个 JSON 用 json 解析过；跑了一次原生构建 → 配置期打印"迁移期旧目录"（回退分支正确）、
构建 exit 0；注释检查 0 违规。submodule 的实际拉取与提交**必须由人做**
（本仓库禁止智能体执行 git 写入），命令写在文档第七节。

## 第二轮：移除 vcpkg + 查出 submodule 钉错了版本（同一根因）

用户判断："按这个说法的话 vcpkg 没有存在的意义了，主要是供 web 使用，所以 wasm 是主线"。

**结论：同意移除，但理由要换。** 不是"wasm 是主线"这句话本身，而是两条事实：
主线上唯一有分量的候选（HarfBuzz）**永远**不可能走包管理器（它必须与 wasm 共用同一份源码，
这条约束不随主线在哪一边而变）；native 侧现在没有任何成品库可装（光栅后端是自写
`bitmap.cpp`，三个依赖没有一个落在"只服务 native 的成品库"这一档）。第四档是空集，
为它长期维护清单加开关加判据是空转，还会给人"这里有成品库在用"的错觉。

**已移除**：`vcpkg.json`、`vcpkg-configuration.json`（归档到 `out/_removed_vcpkg/`）、
`build_native.ps1` 的 `-Vcpkg` 开关与 `VcpkgArgs`、`.gitignore` 的 `vcpkg_installed/`、
`AGENTS.md` 的两条。踩过的经验（三元组 `x64-windows-static-md`、依赖必须可选、钉
`builtin-baseline`、许可证同步）没有丢，移到文档第六节"重新引入的条件"下面。

**顺手查出 submodule 落地时钉错了版本、稀疏检出也没生效**：`git submodule status` 显示
`(heads/main)`，`rev-parse HEAD` = `fd0c6c9a`（main 尖端，2026-10-10），而 tag `14.6.0`
的 commit 是 `c7a7457b`（2026-10-05）；工作区 109 MB（`test/`、`util/`、`docs/`、`perf/` 全在）。

**根因只有一个**：`git fetch --depth 1 origin refs/tags/14.6.0` 只写 `FETCH_HEAD`
（证据：`FETCH_HEAD` 里是 `a0e2a3c0 tag '14.6.0'`，而 `packed-refs` 里只有
`refs/remotes/origin/main`，没有任何 tag 引用），于是随后的
`git checkout --detach refs/tags/14.6.0` 必然失败、脚本在 `$ErrorActionPreference='Stop'`
下 `throw` 退出，稀疏检出那一步（连哨兵校验与 HEAD 打印）根本没执行 ——
"版本没钉"与"没裁剪"看着像两个 bug，其实是同一个。

**顺带坐实的两条事实**：tag 14.6.0 的 `src/hb-version.h` md5 = `671d707a`，与迁移前手工
解压那份**逐字节相同**（旧 dist 包 == tag 14.6.0）；而 tag 与 main 在 `src/` 下差 41 个
文件（+539/−2442），含 `hb-ot-layout-gsubgpos.hh`、GPOS 的 `PairPosFormat1/2.hh`、
`ValueFormat.hh` —— **kerning 走的路径**。所以"取到哪一份"会影响排版结果。

**改动**：
- `scripts/deps_init.ps1` 重写：所有 git 调用走 `Invoke-Git` / `Get-GitOut` 包装
  （临时放宽 `$ErrorActionPreference` 容错，只按退出码判定成败 —— 否则 git 往 stderr
  写进度会被 PS 5.1 当成 terminating error，命令成功也中断）；钉 tag 改成从
  `FETCH_HEAD^{commit}` 解析 commit 再 `checkout --detach`；把 `c7a7457b…` 写成常量并在
  末尾断言 `rev-parse HEAD` 等于它；稀疏检出改用 `git sparse-checkout set --cone src`
  （不手写 sparse 文件，避开 Windows 下写出 CRLF 让排除规则永不匹配的风险）；
  末尾打印体积与版本头 md5，并给出 14.6.0 的期望 md5。
- `CMakeLists.txt`：删掉"两者同内容，编译结果不受影响"那句（已被证伪，换成"内容未必相同，
  取到哪一份会改变整形结果"）。
- `docs/依赖与工具链管理.md`：结论段改写；第二节补"第四档为何几乎不可能命中"；
  第三节补 main≠tag 的证据与两个坑；第六节改成"为什么不用包管理器"（保留经验）；
  新增第七节"web 是主线，判据要跟着挪"；原第七/八节顺延为八/九并更新判据。
- `AGENTS.md`、`.gitignore`、`docs/正式化架构与迁移路线.md` 同步。

**新写进文档的推论（这才是"wasm 主线"真正的影响）**：native 光栅是 `bitmap.cpp`、
wasm 是 Skia，两者不可能逐像素一致 → `auditFrame` 在 native 上只证明"排版与光栅自洽"，
**跨后端的整帧像素判据只在浏览器探针（`verify_web.ps1`）一侧算数**；
`auditLayout` 这类纯排版判据两侧都算数，因为它不依赖光栅后端。

**验证**：两个 .ps1 用 PowerShell 解析器查过（BOM 在、语法 OK）；重跑原生构建
（`out/_native_build2.log`）→ 配置期打印 `-- HarfBuzz: submodule D:/Develop/editor/third_party/harfbuzz`
（确认取的是 submodule 那份）、exit 0；两个单测可执行文件直跑读数：
`ced_edit_tests.exe` **467 项断言、失败 0**，`ced_tests.exe` **55 项、失败 0**
（含绝对坐标断言，所以这也说明换到 main 尖端那份源码没有改变我们测试覆盖到的整形结果）。
submodule 的重新钉版本与提交仍**必须由人做**。

**教训**：日志里中文乱码时，别在双重编码上反复试；直接把被测程序重跑一遍、
用 Python `subprocess` 收字节再按 utf-8/gbk 依次试解码，一次就干净。

## 第三轮：把"版本名"这件事摆正（tag 与 commit 的关系）

用户："tag 还是改成 14.6.0 吧，这个不是 submodule 就能钉吗"。

**答复要点**：submodule 钉的确实是 commit，不是 tag —— gitlink 是裸 SHA，**存不下 tag 名**。
所以"钉 tag 14.6.0"与"钉 `c7a7457b`"是**同一个 pin**：tag 是它的名字，commit 是 git 真正
存下来的东西。能用 git 认识的方式把名字也记进仓库的只有 `.gitmodules` 的 `branch` 字段。

**改动**：
- `.gitmodules` 加 `branch = 14.6.0`（带三行注释说明：它只被 `git submodule update --remote`
  使用，普通 `update` 一律按 gitlink 检出，所以它只是标签、不影响"钉死"这个性质）。
  已用 `git config -f .gitmodules --list` 验证可解析（三个键都列出来了，制表符与注释
  都没破坏格式）。
- `scripts/deps_init.ps1`：常量 `$HbCommit` 改名 `$HbTagCommit`（7 处），定义处写清
  "tag 是入口、commit 是断言结果、升级要同时改这两个"。
- `docs/依赖与工具链管理.md` 第三节补一段，把 tag 与 commit 的关系写清。

**踩坑（重要）**：用 Python `open(p,'w')` 重写 .ps1 会把 **BOM 丢掉、LF 变成 CRLF**
（Windows 上文本模式的默认换行翻译）。而 BOM 少了，PowerShell 5.1 会按 GBK 解码中文注释、
直接报语法错。修法见 `out/_fix_deps_encoding.py`：读用 `utf-8-sig`、写出前
`replace('\r\n','\n')` 再手工补 `\xef\xbb\xbf`。以后改这些脚本一律走这个模式，
不要用 `open(...,'w')` 裸写。

## 第四轮：native 这条线还要不要留（结论：留，但收窄成验证宿主）

用户："项目主要以 wasm 为主，native 这条线现在还有没有存在的价值了，维护两条现在有点复杂"。

**先摸清两条线各自实际承担了什么（这一步是关键，不能凭定位判断）**：

- **单测 target 只建在 native 分支**：`CMakeLists.txt` 的 `if(EMSCRIPTEN)` 分支只产
  `ced_wasm`，`ced_tests` / `ced_edit_tests` / `ced_abi_probe` 都在 `else()` 里。
  所以 wasm 侧没有跑过这 522 项断言（`ced_edit_tests` 467 + `ced_tests` 55）。
- **但核心判据两边都有**：`auditLayout` / `auditFrame` 已经通过 wasm 导出
  （`src/wasm/wasm_main.cpp`），并且 `edit_probe.mjs`（12 处）、`stress_probe.mjs`、
  `web/app.js` 都在调用。也就是说"与全量一致"这些可证伪判据**不依赖 native**。
- **测试代码本身不依赖浏览器**：`tests/edit_test.cpp`（233 KB）里只有一处提到 Skia，
  而且是注释；`shaping_test.cpp` 零处。→ 技术上可以把断言搬到 wasm + node。
- **规模对比**：C++ 侧 522 项断言（含"横扫 205 点采样"这类循环地毯覆盖，原地跑是毫秒级）；
  浏览器探针 `edit_probe.mjs` 192 个断言点（每点至少一次 CDP 往返，还要起 Chrome 与静态服务）。
  两者是**分层**不是重复：探针管真实指针/按键/画布上屏/真 Skia 光栅，native 管算法级穷举。
- **native 是第二把尺子**：`CED_USE_SKIA` 只在 wasm 有效（`CMakeLists.txt` 明确
  `if(CED_USE_SKIA AND NOT EMSCRIPTEN) FATAL_ERROR`），native 一律走自写 `bitmap.cpp`。

**结论：留，但边界要写死。** 写进 `docs/正式化架构与迁移路线.md` 新增 4.6 节：
native 只做验证宿主，**新功能不得只在 native 上实现**；光栅双实现是本工程唯一被认可的
重复实现（正当性就是"第二把尺子"），两者不一致时以 Skia 为准；
内存布局诊断（`ced_abi_probe`）天然属于 native。并写清了**什么条件下才该砍掉**：
native 工具链维护成本持续高于收益时，把断言搬到 wasm + node，代价是丢 522 项现成覆盖
与独立光栅对照、每次迭代要重编 wasm。

**教训**：判断"某条线能不能砍"不能只看定位口号，要去看**判据落在哪一侧**、
以及"某侧独有能力"是否真的独有。这次一查就发现 `auditFrame`/`auditLayout` 早就
在 wasm 侧跑了 —— 这既说明 native 不是判据的唯一来源，也说明它唯一不可替代的东西
是"快 + 可调试 + 独立光栅"，而不是"独家判据"。

**用户的决定：保留并收窄。** 于是把边界从文档判断升级成仓库规则，写进 `AGENTS.md`
的构建与验证一节（三条：新功能不得只在 native 上实现；跨后端逐像素判据只在浏览器探针
一侧算数；光栅双实现不一致时以 Skia 为准）。`docs/依赖与工具链管理.md` 第七节补了
指向架构文档 4.6 的交叉引用。

## 第五轮：deps_init.ps1 跑完后的核验（一个假警报，换来一条纪律）

用户："deps_init.ps1 跑完了啊"。

**落地结果是好的**：`git submodule status` 无 `+`/`-` 前缀、HEAD = `c7a7457b`
（即 tag 14.6.0 的 commit）、`test/` 已裁掉、顶层只剩 `src/`、体积 **109 MB → 9.1 MB**、
`git -C third_party/harfbuzz status --porcelain` 为空（工作区与 HEAD 逐文件一致）。

**但出现一处"看着像不符"**：`src/hb-version.h` 工作区那份 md5 是 `8b4c92a6`、2692 字节，
而我在脚本里写的期望值是 `671d707a`、2597 字节。**根因是 CRLF**：本机
`core.autocrlf=true`，git 检出写出的文件是 CRLF；这份文件 95 行，2692 − 2597 = 95，
去掉 CR 后 md5 正好是 `671d707a`，与 blob 逐字节相同（实测该文件 95 个 CRLF、0 个裸 LF）。
**也就是说我写的那个校验本身是错的**——拿工作区文件的 md5 去比 git 里的内容。

**顺带把"旧 dist 包 == tag 14.6.0"这条判据坐实了**：`diff -rq` 直接比对报 575 处差异，
加 `--strip-trailing-cr` 后 **0 处** → 迁移前后确实是同一份源码，
"钉对版本就不改变任何输出"这条成立。

**改动**：
- `scripts/deps_init.ps1`：删掉那个错误的 md5 期望行，换成三条不依赖行尾的校验 ——
  `rev-parse HEAD` 必须等于常量；`status --porcelain` 必须为空（防"检出落在别处、
  文件还是旧内容"这种只对 HEAD 查不出的漂移）；打印 `rev-parse
  HEAD:src/hb-version.h` 作为版本头标识，并写明"不要拿工作区 md5 比 blob"。
  四条校验的实际返回值已手工预演：HEAD `c7a7457b`、porcelain 空、
  blob `8b7864cc`、`test/` 不存在。
- `docs/依赖与工具链管理.md` 第三节与第九节判据同步（md5 改成 blob 标识 +
  `--strip-trailing-cr` 的实测结论）；`AGENTS.md` 构建与验证一节加一条纪律。

**教训（会反复踩，所以进了 AGENTS.md）**：Windows 上 `core.autocrlf=true` 时，
"工作区文件"与"git 里的内容"天然不逐字节相同。任何"文件是否与预期一致"的校验都要走
git 对象标识或忽略行尾，否则会造出假的**不符** —— 而假的不符比没有校验更糟，
它会让人去查一个不存在的问题（这一轮就差点如此）。

## 第六轮：换 HarfBuzz 源码不会触发重编（真缺陷，已修 + 已加守卫）

第五轮核验时我注意到一件怪事：`deps_init.ps1` 把工作区从 main 换成了 tag，
`ced_harfbuzz` 的 obj 却停在 00:26（那时 HEAD 还是 main）没重编 ——
也就是说我第五轮报的"单测全绿"其实是**对着 main 那份 HarfBuzz 编出来的旧产物**跑的。

**根因（两个叠加）**：
- MSVC 侧**本来就没有任何自动头依赖通道**（`scripts/verify_header_deps.ps1` 的文件头
  写得很清楚：ninja 的 `deps = msvc` 拿 UTF-8 前缀匹配 cl 的 CP936 输出匹配不上，
  CMake 4.1 的 C++20 dyndep 里只有模块依赖没有头文件），所以项目用
  `ced_track_header_deps()` + `OBJECT_DEPENDS` 手工注入。
- 但那个函数**只 glob `.h/.hpp`**，而 HarfBuzz 的 `src/` 里 289 个是 `.hh`、69 个被
  `harfbuzz.cc` 直接 `#include` 的 `.cc`（实测：69 条 include 全是 `.cc`）；
  而且 **`ced_harfbuzz` 从来没注册过**。`harfbuzz.cc` 自己的 mtime 没变（它在 main 与
  tag 里逐字节相同），于是 ninja 认为无事可做 —— **换版本、改它的头，都会静默复用旧对象**。

**已修**：glob 补上 `.hh` 与 `.cc`；给 `ced_harfbuzz` 注册 `${CED_HB_ROOT}/src`。
注意这**不破坏**原有的有取舍：它只覆盖 HarfBuzz 自己的头，core 的头不在其中，
所以"改 core 头不会重编巨型 TU"这条仍然成立（守卫脚本第 4 节就是断言这条的）。

**顺带修掉守卫脚本自己的一个洞**：`verify_header_deps.ps1` 里 harfbuzz obj 的路径
写死成旧目录名 `third_party\harfbuzz-14.6.0\...`，而 CMake 现在取 submodule 路径 ——
它会去断言一个不在构建图里的文件，看着通过其实没有保护。改成按"最近被维护的那个" glob
找，并从 obj 路径反推 HarfBuzz 源码根。同时新增第 5 节：推一个 HarfBuzz 头的 mtime，
断言它的聚合 TU 必须重编（与第 4 节方向相反，缺一条就会漏掉这类静默复用）。

**验证（这次是真的）**：

## 第十一轮：表单模式的光标与嵌套（讨论中，先记依据）

- **Word 的"填写窗体"保护是连选区一起禁的。** 多方描述一致："正文内容点不动，光标进不去"、

## 选区与复制：什么进文档模型（用户提问）

**用户问**：像选区、复制等功能是否需要在文档模型这块设计体现。

**结论：选区本身不进模型，但四样东西必须进。** 依据（本地实测，不凭印象）：参照项目的
`DCSelection` 虽然放在 `Dom/` 目录下，但挂在内容元素上，`DCJsonSerialization.cs` 里与
Selection 相关的只有 `SelectionHightlightMaskColor` 与 `SelectionTextIncludeBackgroundText`
两个**外观选项** —— 选区一个字节都不落盘。成熟编辑器分工一致：ProseMirror 的 `Selection`
在 `EditorState` 不在 `doc`，Lexical 的 `RangeSelection` 不进 document JSON；剪贴板内容同理。
参照项目的选区形状是 `_StartIndex + _Length`（**整数加长度、没有方向**）+ `ContentRangeMode`
（Content / Cell / Mixed）+ 一个 `_Cells` 列表（表格可多格选取）。

**进模型的四样**：一是端点形状 = 两个流位置**加方向**（anchor / focus 分开存；参照项目没有
方向，表达不了"Shift+左/右下一次从哪端扩"）；二是**位置映射** `map(pos, assoc)`（每个步骤
提供，撤销重做走逆映射；`assoc` 是"位置落在插入/删除边界上归左还是归右"的表态，参照项目用
`FixIndex()`）；三是**区间原语** `ExtractRange`（纯读、不产生步骤）与 `DeleteRange`（写、是步骤）
—— 复制/剪切/删除/加粗/批量设值都归结为这一对（参照项目对应 `GetRange` 与 `deletedElements`）；
四是**端点规范化**：端点必须落在流元素边界上，落在控件/表格行这类不可半分单位内部时
**向外扩到整块边界**（起于控件内部就退到控件起点），于是**复制片段永远良构**；参照项目用
`SplitElements` 拆元素，我们**不能拆控件**（拆了边界就不成对），只能外扩。

**用户的两个决定**：一是**复制一律带控件身份**（`key`、`readonly`、结构操作开关、外观），
所以粘贴必须处理 key 冲突 —— 剪切（同文档移动）保留 key；复制后同文档粘贴重命名
（留与源控件的对应记录）；跨文档粘贴目标无同名 key 则保留、有冲突才重命名。**连带**：
片段里的值引用指向的 key 被重命名时，引用必须同步改写。二是**撤销恢复编辑前的选区**：
`Transaction = Step 序列 + 编辑前选区 + 编辑后选区 + 提交说明`，撤销把两份都还原、
重做回到编辑后；映射管"一次编辑之内"位置的跟随，选区快照管"跨撤销单位"回到原处。

**落地**：模型文档 5 处（第二节新增"区间与选区类"不变量组；第四节末尾新增

## 0.5：长度类型与 EMU 定点表示

**新增/改动**：
- `src/core/utils/units.h`：`Emu`（int64）+ `Unit` 枚举 + `emuPerUnit`（七个因子全整数）+
  `toEmu`/`fromEmu` + 具名包装 `ptToEmu`/`cmToEmu`/`mmToEmu`/`halfPtToEmu`/`emuToPt`/`emuToCm`/`emuToMm`。
- `src/core/doc/length.h/.cpp`：`Length`（`Abs`/`Percent`/`Em`/`Chars`/`Auto`）+ `printLength`/`parseLength`。
- `src/core/doc/para_format.h`：`size_pt` → `Length size`、`space_after_pt` → `Length space_after`。
- `src/core/doc/compile.cpp`：`absToPt` —— EMU → 磅的**唯一一处**换算，非绝对长度记诊断。

**四条约定**（已写进模型文档第十一节与第十五节）：
1. **模型存整数、引擎存浮点，编译是唯一接缝**：改错会被 0.4 那条"逐字段一致"立刻抓住。
2. 比例存**分子分母**（gcd 约分、分母恒正），倍数按**千分位取整** ⇒ 落盘与比较都不经过浮点；
   `percent(1,0)` 得到自动值（没有可表达的比例），不拿 0 做除法、也不猜分母。
3. 文本形式带**类型前缀** `abs:`/`pct:`/`em:`/`chars:`/`auto` ⇒ `parse(print(x)) == x` 且**类型不丢**；
   不写成 `2.54cm` 那种可读形式（EMU 换算成磅常是无限小数，12700 含因子 127，有限位数会丢精度）。
4. 解析**严格**（不跳空白 / 不截断 / 不夹取）；**不做求值**（`Length → EMU` 需要参照，等真有消费者的那一步）；
   **行距三态仍是独立一步**（`line_factor` 还是浮点倍数，`exact`/`atLeast` 要改引擎块轴推进公式）。

**为什么具名包装不叫 `pt()` / `cm()`**：`layout.cpp` 有 `const float pt`、`engine_diag.cpp` 有
`const Rect px`、`native_main.cpp` 有 `const long long mm` —— 裸名会被作用域里的局部变量**静默遮蔽**，
所以一律带方向后缀，其余单位走通用的 `toEmu(v, Unit::X)`。

**判据**（+14 项）：单位换算正向（量化误差 ≤ 半个 EMU，91 组取值）+ 反向（整数倍 EMU 原样，正负各走一遍）；
`Length` 五种性质往返后**种类与数值都不丢**（12 例）；文本形式定值与 gcd 约分；22 例畸形输入全被拒；
编译期拒绝非绝对长度（字号与段后距各一条）。0.4 的 `sampleDocument` 逐字段一致在新表示下依然是绿的
⇒ 顺带证明了 EMU ↔ 磅的换算精确。

**判据自身的错（又一处）**：先写了 `halfPtToEmu(21) != ptToEmu(10.5)`，想当个"不是恒真"的对照；
但半磅就是磅的一半，21 半磅 = 10.5 磅，两者**必须相等**。改成 `==` 并把它变成一条交叉校验
（五号 = 半磅 21 = 10.5 磅）—— 判据里加"看起来更严格"的断言时，先确认它真的是错的。

**验证**：原生 468 + **277**（246 → 263 → 277）+ 55，失败全 0，`exit=0`；wasm `exit=0`；
浏览器探针 192 项失败 0、`exit=0`；`lint_comments.py` 62 文件 0 违规；新写/改到的文件 clang-format 19
全绿（**只格式化自己改的那几个**：全仓 16/49 与 clang-format 19 有历史差异，整仓格式化会带出无关改动）。

## 1.5 的前一半：控件索引与宿主 API（值读写、批量、属性）

**新增** `control_spec.h/.cpp`（`ValueShape` 五形态 + `ControlValue` + `ControlProp`；记录补
`required` / `valueShape` / `value`）、`control_index.h/.cpp`（id/key 两张表 + `onStep`）、

`steps.h/.cpp` 加 `SetControlProp` 步骤、`utf8.h` 补 `appendUtf8`（原先只有 decode）。

**六条约定**
1. **一次调用 = 一个事务**：四个 setter 的入参都是数组，数组本身就是批量 ⇒ 一个撤销步骤；值与属性
   混着设用 `beginBatch` / `commitBatch`，仍是一个撤销步骤。
2. **同一次调用里同一个目标出现多次时后者覆盖前者**（与逐条调用一致）：先解析目标、顺序去重只留最后
   一次，于是"要改几个、改了哪几个"在构建步骤之前就算清楚了。
3. **索引的维护分工看"子树里有没有控件"**：没有就不动表（给文本控件设值就是"摘旧文本节点 + 插新文本
   节点"，一次批量一千个字段会走一千遍，每次重扫全篇是白费），有控件才重扫一遍（换"键表按文档顺序"
   这条正确性）。身份不在步骤里（序列化还原的 `InsertNode`）时返回"跟不上"，由调用方重建。
4. **批量里每步的流位置要按前面几步的映射推过去** —— 这是本轮抓到的真 bug：事务的约定是"每步坐标属于
   它自己那一刻"，而批量是一次把所有步骤建出来的，前面某步把文档改短，后面几步记的绝对流位置就偏了，
   `canApply` 当场判"步骤过期了"。修法不是放松校验（那会把真错也放过），而是让 API 在收每一步时用
   `mapPos` 把后面的坐标推过去。
5. **文本类设值 = 逐个摘掉现有子节点 + 插一个文本节点**（节点级步骤，比区间删除更直接）；**内部不是
   纯文本（含子控件或图片这类原子）一律拒绝并给原因**，且不产生任何编辑步骤。选择类的值在属性上，
   改它要一条"改值"的步骤 —— 本轮**显式拒绝**并说明等哪一步，不静默当文本设。
6. **取值与将来的选区复制共用一套拼接规则**（文本贡献文字、段落标记贡献换行、嵌套控件的内部内容按
   普通文本取出、域/图片/公式暂贡献空串）；**隐藏的单个节点不贡献文字**（取的是表单与打印里能看到
   的那份）。同 key 值不一致时 `getValueByKey` 带 `inconsistent` 标志，`inconsistentKeys` 给出去重清单。
