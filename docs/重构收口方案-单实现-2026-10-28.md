# 重构收口方案：只保留一套实现（2026-10-28）

## 结论

上一轮复核认定「阶段 3 加了一层、旧的没删」。本方案给出收口的可执行路线，判据是三条硬约束：
每一步都**不改输出**、都**净删代码**、都**删掉一个概念**。做不到三条里任何一条的，不算收口。

## 三个病根

### 病根一：判据冻结了浮点加法次序，于是坐标不敢搬

`block_pagination.h` 开头写着「页内坐标的加法次序不能在这里重排，否则逐位摘要会变」。
这句话把「同一份布局」定义成了「同一串浮点加法的结合顺序」，后果是任何代码都不能搬家 ——
所以新层只能算到「行顶」为止，落位留在旧循环里，于是两层都要存在。

核对结果：这条约束比它需要的更严。`placeHorizontalLine(top, page)` 只从 `top` 派生行盒，
不含跨行状态；`paginateBlockLines` 的行顶递推是 `line_top = top + prev_line_h`
（`block_pagination.cpp:32`），与旧循环 `layout.cpp:1646` 是同一个式子。只要把块起始的
`cursor_y` 传进去，两边的浮点序列**逐个操作相同**，逐位摘要因此不变。

⇒ 坐标可以搬，摘要不必 rebaseline。这一条不成立，后面五件事全部做不了。

### 病根二：同一概念有多份记录

| 概念 | 存了几份 | 位置 |
| --- | --- | --- |
| 块属于哪一格 | 3 | `BlockSpec::cell_path`、`LayoutCell::first_block`、`StructureIndex::cells` |
| 一个偏移上是第几个插入点 | 2 | `side`（整数侧别）、`LineBox::kInlineOffsetOuter` + 控件下标 hint |
| 分页结果 | 3 个类型 | `BlockPaginationResult`、`BlockFloatPaginationResult`、`BlockColumnPaginationResult` |
| 分页+落位的消费者 | 4 | `layout.cpp` 1561 / 1587 / 1624 / 1636 |

`engine_audit.cpp:477` 那条「两份记录说的是同一件事」的断言，是重复的证据，不是防线的证据：
真只有一份时不需要对照。

### 病根三：没有记账，改动无法判好坏

方案 10.2 要求 10 个结构计数器，实际只有 `relaid_lines`、`scene_built_pages`、
`scene_reused_pages`。缺 `relaid_blocks`、`blocks_reused`、`refs_copied`、`scene_items`。
现在唯一能拿出来的证据是「测试全绿 + LayoutDigest 逐位不变」，而后者证明的是行为没变，
不是复杂度下降。**没有数就没有收口，只有换了一种写法。**

## 六条总原则

1. **差分判据先于删除**。删旧路径之前，写一条测试同时跑旧路与新路，逐字段比对；
   比对通过才删。新增的临时开关只活在一步之内。
2. **输出零变化**。六步全部不改 LayoutDigest。任何 diff 按 bug 处理，不许 rebaseline。
   唯一例外是 T1 里明确列出的「退化宽度新定义」，它必须同时补一条只覆盖该情形的判据。
3. **净删**。除 T0（买可证伪性）与 T4（买有图文档的增量）两处已说明理由的例外，
   每一步的 `+行数 − 行数` 必须为负；为正且说不出理由的不允许合并。
4. **一个概念一个存储**。派生结构（索引、反查表）允许存在，但必须满足「删掉能随时重建」
   且**不参与正确性对照**。
5. **记账先行**。T0 先补最小计数器，否则 T2/T3 改完没人能说清省了多少。
6. **不碰与「减少 bug」正交的事**。门面拆分（254 → 30 个方法）、IDL 代码生成、
   Fenwick 页表都移出本方案，见「明确不做」。

## T0 先补记账（净 +18 行）

没有这一步，后面所有「净删」都只是行数游戏。

### 核对结果：清单砍到一条

  实测 `relaid_paragraphs == 1`。

## T1 删死分支：竖排旧循环与横排旧循环（实测净 −230 行）

### 现状与实测（计划里的两条猜测都被实测修正）

计划断言「竖排旧循环与横排旧循环都不可达」。埋探针跑全量之后：

- 竖排旧循环（`if (!vertical_placed)`，79 行）：**0 次命中**，确认不可达。原因是
  `project.cpp:585` 写死 `float_ok = !wm.isVertical() && cell_path.empty()`，竖排块的浮动对象
  在投影阶段就被降级成行内，`has_floating_object` 对竖排恒为假。它看起来像「兜底」而不是
  「另一套实现」，是因为新路径写在旧分支**里面**（`if (simple_vertical_block || ...)` 之后紧跟
  `if (!vertical_placed)`）。
- 横排旧 `while` 循环（106 行）：**5 次命中**，探针打出的签名是
  `cur_cw=280 tstack=0 floats=0 cellpath=1`。即「块声称自己在格里，但表框没开」——
  调用方传进来的表清单盖不住这个块时，`cell_path` 与表框栈这两份判断依据互相矛盾。

所以旧横排循环不是死代码，它是「两份依据打架」的唯一出口。删它之前必须先把那个矛盾消掉，
否则删掉的是唯一处理该情形的代码。

### 做法（两步，都不新增状态码）

1. **表框栈成为唯一权威**。`simple_block` / `simple_vertical_block` / `cell_block` 三个条件
   去掉 `b.cell_path` 那一项，只认 `tstack.empty()`。块自己的 `cell_path` 只用来开关表框，
   不再当第二个判断依据。改完之后探针从 5 次降到 0 次，判据全绿。
2. **宽度下限收到调用方**。`cur_cw ≤ 1` 仍然可达（格内容宽在 `layout.cpp:1011` 被夹到
   `std::max(1.0f, ...)`，分支条件曾是 `> 1.0f`）。没有照计划新增
   `BlockLayoutStatus::DegenerateWidth`——块层已有「宽度不为正即约束无效」的契约与判据，
   新增状态码等于给同一个问题开第二套语义。改成调用方把宽度下限提到 1 磅
   （`blockWidth` 一个 lambda），块层照常排：断行「至少放一个簇」，结果是每簇一行。
   两种取值（0 磅与 1 磅）在这个宽度区间里结果逐位相同。
3. 删除两个旧循环、旧循环专用的状态（`anchor` / `prev_line_h` / `first_line` /
   `floats_shifted` / `start_cl` / `fillLine` / `row_spans`）与三个 `*_placed` 标志。
   三条落位路径改成互斥的 `if / else if`：无浮动图、带排除带、格内 —— 条件两两互斥，
   等价于原来的「顺序执行 + 标志互斥」。

### 影响面

只有 `layout.cpp`（`+33 / −263`）。判据侧新增两条：退化格宽（1×40 窄表，每簇一行）与
T0 的表格粒度。契约不变：`layoutBlock` 对非正宽度仍报 `InvalidConstraints`。

### 判据

- `ctest --preset native` 7/7、`npm run test:dist` 129/129、格式与注释闸 0。
- 正向：1×40 窄表首格敲两个字 → 该格排 2 行、每行 1 个簇（实测 2 行 / 超一簇 0 行）。
- 反向：把三个条件里的 `tstack.empty()` 改回 `b.cell_path.empty()`，
  「竖排格内块」与「格内折行」用例必须红。
- 反向（过程判据，已用完）：临时探针命中计数从 0/5 变成 0/0，且全量仍绿 —— 这是允许
  删除的唯一依据。探针与两个旧循环一起删掉，不留开关。

### 为什么先做这个

它同时满足三件事：删掉的是同一不变式的第二份实现（表框归属）、不新增任何概念、
判据在改之前就能证伪（探针计数）。收口的第一步应该是这种「先用计数证明它可删，再删」。

## T2 分页与落位收成一条路径（实测净 −207 行，概念 3 类型 → 1）

### 现状

`layout.cpp` 里三处各写一遍「消费分页结果、逐行落位」：简单块、带排除带的横排块、格内块。
格内块还**自己累加** `top += line.line_h`（与分页层的 `top + prev_line_h` 是同一件事的
第二份写法）。三个结果类型结构相同，三个输入类型字段互为子集。

### 做法

1. **一个结果类型** `BlockPlan`：`lines[{parts, top_pt, page, line_no}] + page_index +
   line_total + cursor_y_pt + first_line_shift_pt`。三个输入类型合并成 `BlockPlanInput`
   （差异项用已有字段表达：`no_page_break` / `continuous` / `page_stride_pt` / `live_base`）。
2. **三个算法保留**。行分页、排除带驱动、列映射是三条不同的规则；合成一个函数只会把
   switch 塞进去 —— 那是搬家，不是减法。收敛掉的是类型与消费方，不是规则。
3. **一个消费循环**。`wrap_floats ? planBlockLinesWithFloats(...) : planBlockLines(...)`，
   之后只有一个 `for (line : plan.lines) placeLine(...)`；`line_total` / `page_index` /
   `cursor_y` 全部由计划给出，本函数不再推进。
4. **格内的自行累加删除**：格内块走 `planBlockLines` + `no_page_break`，行顶只有一处递推。
5. **竖排列宽不再单独传**。`BlockColumn::width_pt` 的注释写着「等于 line.line_h」，于是
   `BlockPlanLine` 只带列心（`parts[0].x`），落位时取 `parts[0].line.line_h` 当列宽 ——
   传进来就能和片段对不上。`shaping_test` 原来逐字段对照列计划的那条判据改成同时对照
   `line_h` 与 `width_pt`，把这条不变式钉住。

### 影响面

`block_pagination.h` 389 → 224 行、`block_pagination.cpp` 214 → 217 行、`layout.cpp`
三个消费点变一处；`fragment.cpp`（后缀重新分页）与 `shaping_test`（12 处调用）跟着改类型。
段前分页与段前距只对简单块交给分页层（其余块的块首已在块级处理过），避免加两次。

### 判据

- `ctest --preset native` 7/7、`native-perf` 1/1、`npm run test:dist` 129/129。
- 正向：竖排分页「页号等于带号、行号在带内重新计数、列心与列顶逐列相同」照旧通过，
  新增的 `line_h == width_pt` 对照也通过。
- 反向：把 `no_page_break` 判定写反（格内允许翻页），`table` 域「格内折行」与
  「跨页切片」用例必须红。
- 反向：把 `planBlockLines` 的 `placed.line_no` 改成 `out.lines.size()`（漏掉起始行号），
  「行号在带内重新计数」与增量行号判据必须红。

## T3 块↔格只留一份记录（实测净 +213 行 —— 四步里唯一净增的一步）

### 现状

三份记录并存：`BlockSpec::cell_path`（每块一条嵌套路径，2000 块文档上是 2000 次小分配）、
`LayoutCell::first_block/block_count`（格说"我有哪些块"）、`StructureIndex::cells/cell_extents`
（前两者的第三份投影）。`engine_audit.cpp:477` 专门写了一节对照其中两份 —— 审计在证明重复，
而不是消除重复。T1 的探针还抓到过它们互相矛盾的实例（块声称在格里、表框却没开）。

### 做法

1. **新的 `layout/cell_index.h`**：`CellIndex` 从 `LayoutTable::cells` 反推全部关系。
   表按进入顺序排列（外层先于内层），所以按表序走一遍就能定嵌套：一张表的块区间被某张更早
   的表某一格整个包住，那一格就是它的父。树结构与三条查询（`nodeAt` / `pathAt` /
   `outermostTable` / `firstBlockIn`）都在这里，只有一份实现。
2. **`BlockSpec::cell_path` 删除**：`project.cpp` 不再写、`operator==` 不再比。投影侧的
   `path_` 仍保留 —— 它进块哈希（同一张表里两格内容相同、列宽不同，排版结果不一样），
   只是不再复制进每一块。
3. **排版层自建索引**：`layoutDocumentRangeWithTables` 入口 `cell_index.build(tables, blocks.size())`，
   逐块复用同一个 `CellSlot` 缓冲。不新增入口参数 —— 调用方传一份可能过期的索引，比多建
   一次 O(块数+格数) 的整型数组更危险。无表文档里它与旧的空 `cell_path` 逐位等价。
4. **`StructureIndex` 收成持有 `CellIndex`**：`cells` / `cell_extents` / `table_spans` 三个
   独立成员改成索引的三条视图，同一次推导产出。`cellAt` 改为按值返回（旧写法返回静态常量的
   引用，越界时是个悬空陷阱）。
5. **消费者改道**：`edit_command.cpp` 3 处、`engine_table.cpp` 2 处、`engine_layout.cpp` 2 处、
   `engine_image.cpp` 1 处全走索引。`engine_layout` 的表格边界从"扫全部格求最外层"变成
   `outermostTable` + `TableSpan` 两次查表。
6. **审计收窄**：删掉「两份记录对照」与两个因此永远为 0 的计数（`path_mismatch`、
   `stray`）。留着它们就是留一个测不出来的字段。剩下的是格区间自洽：空格、越界、同表重叠、
   跨表严格包含、格里缺结束标记。
7. 载荷契约随之重生成（`auditTables` 少两个键）。

### 影响面

新增 `layout/cell_index.h` 254 行；被改的文件净删 41 行（`structure_index.h` 227 → 146、
`layout.h` 少一个成员与一处比较、六个消费者不再各自遍历）。合计净 **+213 行**。

**这是四步里唯一净增的一步，方案当初预测的是净删 40 —— 预测错了，理由是我想错了一件事**：
以为删掉三份投影能抵掉新索引。实际抵不掉：新索引要自带"建嵌套树、查路径、找最外层"三件事，
而旧的三份投影各自只存结果、不含任何推导。买到的不是行数，是「矛盾不可能发生」——
`path_mismatch` 那种永远为 0 的取证字段随之消失，审计从"两份记录对照"退化成"一份记录自检"。
按本方案自己的规矩「为正的那一步要么不做，要么先说明为什么值」，这里明确记账：值。测试里手工构造格路径的地方改成"由表的块区间表达"
—— 块的位置仍在用例里写一遍，但落成的是唯一那份记录。

### 判据

- `ctest --preset native` 7/7（637 项断言 + 其余五片）、`native-perf` 1/1、`npm run test:dist`
  129/129、格式与注释闸 0。
- 正向：嵌套表里内层两段的格路径深度为 2、两层指向两张不同的表、外表格另一格的块只有一层
  （`doc_test` 的嵌套表用例）。
- 正向：2×2 表四段各带自己的行列号（`edit_test`，改读 `cellIndex()`）。
- 反向：把 `innermost` 的覆盖顺序改成"外层后写"，嵌套表的内层两段深度会变成 1，上面那条必红。
- 反向：把 `outermostTable` 的父链方向写反，`tableAlignedFrom` 的起点会退到内层表，
  「两表·表变高：增量与全量逐位相同」必红。

### 顺带修掉的构建缺陷（比这一步本身更重要）

这一步中途出现过「同一份代码三次跑出不同结果」：`heditor_tests` 先报 28 项、再报 7 项、
清空重建后报 2 项。查下去不是代码 —— `ninja -t deps` 显示每个目标 **#deps 0**：
一条头文件依赖都没记。

根因是中文版 VS：`/showIncludes` 的提示文字是「注意: 包含文件:」，而 CMake 只认英文前缀
（`Note: including file:`），于是 ninja 把那些行当成普通输出（构建日志里就混着它们），
依赖表恒为空 —— 改头文件永远不触发重编，判据读到的是旧目标。

修法：`CMakeLists.txt` 里 `set(CMAKE_DEPENDS_USE_COMPILER OFF)`，让 CMake 自己扫 `#include`，
与 VS 语言无关。改完 `#deps 46`，改一个头文件会重编 24 个目标。

这条缺陷的影响面超出本轮：**T0 与 T1 的「7/7」是在依赖表为空的状态下读到的**，
它们只证明了「那一刻的二进制是绿的」，没有证明「当时的源码是绿的」。收口之后重跑一遍才是真值。

## T4 浮动图：让后缀锚点带上排除带，删掉「整篇重排」的开关（净 +30 行，性能大幅）

### 现状

`engine_layout.cpp:107`：`must_full = ... || !floats_.empty()`。文档里只要有一张浮动图，
每次击键都整篇重排。原因是 `ReflowState` 只有 `{page_index, cursor_y, line_total}`
（`layout.h:1652`），装不下「此刻生效的排除带」，于是续排拿不到上下文，只能全排。

### 做法

把 `ReflowState` 补成完整的后缀锚点：`{page_index, cursor_y, line_total, float_bands,
placed_float_count}`。`FloatFlow` 已经有 `shiftFrom` 与按带遍历，补一对
`snapshot()/restore()`（约 30 行）。`ParaIndex::state_at_start` 已经按段存这个状态，
不需要新容器。

然后删 `must_full` 的浮动条款。浮动框自身的移动走它自己那一条（`previewImageMove` /
`moveImage` 已经把脏区定在锚点块上）。

### 风险与判据

这是唯一一个「删得少、改得险」的任务，必须放在 T2/T3 之后。

- 正向：2000 段 + 1 张浮动图的文档改最后一个字，`blocks_relaid ≤ 2`，且
  `blocks_relaid > 0` 之后 `repaginated` 片段数等于「全量重排的片段数」。
- 正向：改图前的正文（图在后）时后缀必须真的复用：`blocks_relaid == 1`。
- 反向：改图前的正文（图在前），`blocks_relaid` 必须覆盖到图的锚点块之后 ——
  漏了这条就会出现「图留在旧位置、文字绕过去」的经典症状。
- 反向：删掉图（`floats_` 变空）之后一次编辑，`blocks_relaid == 1`（不能因为历史上有过图就永久全排）。

做不到「快照后逐位等于全量」就不做这一步 —— 保留整篇重排是慢，不是错。
宁可留着慢，不要引入一个只在有图的文档里出现的错。

## T5 控件位置：两套编码收成一套（净 −70 行，概念 2 → 1）

### 现状

同一个问题「这个偏移上是第几个插入点」有两套编码：

- `side`：一个整数，等于该偏移上闭括号的个数（`caret.cpp:150`）；
- `hint`：`-1` 表示没有控件、`-2`（`kInlineOffsetOuter`）表示在所有控件之外、
  非负表示控件下标（`caret.cpp:153`–`171`）。

两套之间还要互相翻译（`sideFromHint`），而 `defaultSideAt` 又是第三处「按最内层归属算默认值」。
`caret.cpp:178` 的 `sideForPos` 被用在删除区间的两个端点上 —— 也就是说**编辑归属仍然从
文字位置反推**，方案阶段 2 说的「位置贯穿」只做了一半。

### 做法

1. `Position` 保持 `{flow, affinity}` 不变（内部真源已经是流位置，这一点是对的）。
2. 新增唯一入口 `Position positionAt(TextPos p, Bias bias)`，`Bias ∈ {None, Before, After}`
   只由宿主点击产生。内部一律接 `Position`，不再接受 `(para, cp, side)` 三件套。
3. 删除 `defaultSideAt`、`sideFromHint`、`kInlineOffsetOuter` 与 `bracketCountsAt` 的
   侧别语义：归属统一走 `ControlIndex::innermostAt`，插入点序号由槽的 `cp` 与 owner 直接给出。
4. `sideForPos` 与 `flowPosAtSide`（25 处）逐个换成 `positionAt` / `Position`。

### 影响面与风险

`caret.cpp`、`caret.h`、`engine.cpp`（1229、2327）、`wasm_main.cpp`（990 的宿主解码）、
`edit_command.cpp`（删除区间端点）。**这是六步里风险最高的一步**：判据只覆盖了
`edit-selection` 与 `edit-boundary` 的若干组合，而边界是组合爆炸。

因此顺序是：先补「两个紧邻控件、空控件、控件首尾、软换行处」四组边界的双向判据，
再动代码。判据不全就先不做 —— 这一步的目的是删掉一类 bug，不是删掉代码行。

- 正向：`edit-selection` 的「从软换行处起选」两条臂与 `edit-form` 的空字段用例全绿。
- 反向：把 `Bias::After` 与 `Bias::None` 互换，至少一条用例必须红。
  （如果互换后全绿，说明判据没覆盖到边界，这一步暂停。）

## T6 文档与注释纠正（净 −40 行）

代码注释与实现相反，比没注释更坏 —— 它会让下一个人照着改错地方：

- `document.h:476` 写「只读孩子表：当前按连续数组存放…分块存储在后续步骤替换」，
  实际已经是 64 分块。删掉后半句。
- `document.h:42` 写「一段码点文本。当前内部仍是连续数组」，实际是
  `shared_ptr<const vector> + offset + size` 的切片。改为描述真实语义。
- `block_pagination.h:11` 写「页内坐标的加法次序不能在这里重排」，改成真实约束：
  「行顶由本层递推，行盒由 placeHorizontalLine 从行顶派生；行顶只有一处累加，
  另一处若再累加（格内块分支即如此）两边的浮点值会在末位分叉」。
- `阶段4-性能项` 与 `架构复核` 里「路径复制只换受影响块」改为准确表述：
  块共享成立，但 `rebuilt()` 仍按孩子数逐项比较、`loadKids` 仍整层拍平。

## 顺序与闸

顺序按「风险从低到高、依赖从少到多」：

```
T0 记账 → T1 删死分支 → T2 单一消费路径 → T3 表格单一记录 → T6 文档纠正 → T4 浮动增量 → T5 控件位置
```

T6 插在 T3 之后是因为它要引用 T0/T2/T3 的结论，写早了会跟着改两遍。
T4 与 T5 可以互换，但都不该在 T2/T3 之前动 —— 它们依赖一套已经收口的分页与记录。

每一步的闸（缺一条不算完成）：

1. `powershell -File scripts\format.ps1 -Check` 全合规；`lint_comments.py` 0 违规。
2. `cd web && npm run check` 全 0。
3. `ctest --preset native` 全绿，LayoutDigest 逐位不变（T1 的退化宽度新定义除外，
   它必须配一条只针对退化宽度的判据，其余文档仍然逐位不变）。
4. 该步声称「净删」的行数用 `git diff --stat` 核对，为正则不允许合并。
5. T0 起新计数器在改动前后各跑一次，把两组数写进本文件末尾的「实测」一节。
