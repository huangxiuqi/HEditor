# 重构收口方案：只保留一套实现（2026-10-28）

## 结论

上一轮复核认定「阶段 3 加了一层、旧的没删」。本方案给出收口的可执行路线，判据是三条硬约束：
每一步都**不改输出**、都**净删代码**、都**删掉一个概念**。做不到三条里任何一条的，不算收口。

## 三个病根

### 病根一：判据冻结了浮点加法次序，于是坐标不敢搬

`block_pagination.h` 开头写着「页内坐标的加法次序不能在这里重排，否则逐位摘要会变」。
这句话把「同一份布局」定义成了「同一串浮点加法的结合顺序」，后果是任何代码都不能搬家 ——
所以新层只能算到「行顶」为止，落位留在旧循环里，于是两层都要存在。

核对结果：这条约束比它需要的更严。`placeHorizontalLine(top, page)` 只从 `top` 派生行盒，
不含跨行状态；`paginateBlockLines` 的行顶递推是 `line_top = top + prev_line_h`
（`block_pagination.cpp:32`），与旧循环 `layout.cpp:1646` 是同一个式子。只要把块起始的
`cursor_y` 传进去，两边的浮点序列**逐个操作相同**，逐位摘要因此不变。

⇒ 坐标可以搬，摘要不必 rebaseline。这一条不成立，后面五件事全部做不了。

### 病根二：同一概念有多份记录

| 概念 | 存了几份 | 位置 |
| --- | --- | --- |
| 块属于哪一格 | 3 | `BlockSpec::cell_path`、`LayoutCell::first_block`、`StructureIndex::cells` |
| 一个偏移上是第几个插入点 | 2 | `side`（整数侧别）、`LineBox::kInlineOffsetOuter` + 控件下标 hint |
| 「点落在哪一格」 | 5 份实现 / 4 套容差 | `engine.cpp:2185`（0.5 / 0.01）、`tableGridJson`（1.0）、`tableGridLineAt`（1.0 / 6.0）、`caret.cpp:766`、`cellBoxOnPage` |
| 整格选区 | 6 份派生状态 | `sel_cell_` + `cell_lo_` + `cell_hi_` + `cell_blocks_` + `cell_mask_` + `cell_caret_` |
| 分页结果 | 3 个类型 | `BlockPaginationResult`、`BlockFloatPaginationResult`、`BlockColumnPaginationResult` |
| 分页+落位的消费者 | 4 | `layout.cpp` 1561 / 1587 / 1624 / 1636 |

`engine_audit.cpp:477` 那条「两份记录说的是同一件事」的断言，是重复的证据，不是防线的证据：
真只有一份时不需要对照。

### 病根三：没有记账，改动无法判好坏

方案 10.2 要求 10 个结构计数器，实际只有 `relaid_lines`、`scene_built_pages`、
`scene_reused_pages`。缺 `relaid_blocks`、`blocks_reused`、`refs_copied`、`scene_items`。
现在唯一能拿出来的证据是「测试全绿 + LayoutDigest 逐位不变」，而后者证明的是行为没变，
不是复杂度下降。**没有数就没有收口，只有换了一种写法。**

## 六条总原则

1. **差分判据先于删除**。删旧路径之前，写一条测试同时跑旧路与新路，逐字段比对；
   比对通过才删。新增的临时开关只活在一步之内。
2. **输出零变化**。各步全部不改 LayoutDigest。任何 diff 按 bug 处理，不许 rebaseline。
   唯一例外是 T1 里明确列出的「退化宽度新定义」，它必须同时补一条只覆盖该情形的判据。
3. **净删**。除 T0（买可证伪性）与 T4（买有图文档的增量）两处已说明理由的例外，
   每一步的 `+行数 − 行数` 必须为负；为正且说不出理由的不允许合并。
4. **一个概念一个存储**。派生结构（索引、反查表）允许存在，但必须满足「删掉能随时重建」
   且**不参与正确性对照**。
5. **记账先行**。T0 先补最小计数器，否则 T2/T3 改完没人能说清省了多少。
6. **不碰与「减少 bug」正交的事**。门面拆分（254 → 30 个方法）、IDL 代码生成、
   Fenwick 页表都移出本方案，见「明确不做」。

## T1 删死分支：竖排旧循环与横排旧循环（实测净 −230 行）

### 现状与实测（计划里的两条猜测都被实测修正）

计划断言「竖排旧循环与横排旧循环都不可达」。埋探针跑全量之后：

- 竖排旧循环（`if (!vertical_placed)`，79 行）：**0 次命中**，确认不可达。原因是
  `project.cpp:585` 写死 `float_ok = !wm.isVertical() && cell_path.empty()`，竖排块的浮动对象
  在投影阶段就被降级成行内，`has_floating_object` 对竖排恒为假。它看起来像「兜底」而不是
  「另一套实现」，是因为新路径写在旧分支**里面**（`if (simple_vertical_block || ...)` 之后紧跟
  `if (!vertical_placed)`）。
- 横排旧 `while` 循环（106 行）：**5 次命中**，探针打出的签名是
  `cur_cw=280 tstack=0 floats=0 cellpath=1`。即「块声称自己在格里，但表框没开」——
  调用方传进来的表清单盖不住这个块时，`cell_path` 与表框栈这两份判断依据互相矛盾。

所以旧横排循环不是死代码，它是「两份依据打架」的唯一出口。删它之前必须先把那个矛盾消掉，
否则删掉的是唯一处理该情形的代码。

### 做法（两步，都不新增状态码）

1. **表框栈成为唯一权威**。`simple_block` / `simple_vertical_block` / `cell_block` 三个条件
   去掉 `b.cell_path` 那一项，只认 `tstack.empty()`。块自己的 `cell_path` 只用来开关表框，
   不再当第二个判断依据。改完之后探针从 5 次降到 0 次，判据全绿。
2. **宽度下限收到调用方**。`cur_cw ≤ 1` 仍然可达（格内容宽在 `layout.cpp:1011` 被夹到
   `std::max(1.0f, ...)`，分支条件曾是 `> 1.0f`）。没有照计划新增
   `BlockLayoutStatus::DegenerateWidth`——块层已有「宽度不为正即约束无效」的契约与判据，
   新增状态码等于给同一个问题开第二套语义。改成调用方把宽度下限提到 1 磅
   （`blockWidth` 一个 lambda），块层照常排：断行「至少放一个簇」，结果是每簇一行。
   两种取值（0 磅与 1 磅）在这个宽度区间里结果逐位相同。
3. 删除两个旧循环、旧循环专用的状态（`anchor` / `prev_line_h` / `first_line` /
   `floats_shifted` / `start_cl` / `fillLine` / `row_spans`）与三个 `*_placed` 标志。
   三条落位路径改成互斥的 `if / else if`：无浮动图、带排除带、格内 —— 条件两两互斥，
   等价于原来的「顺序执行 + 标志互斥」。

### 影响面

只有 `layout.cpp`（`+33 / −263`）。判据侧新增两条：退化格宽（1×40 窄表，每簇一行）与
T0 的表格粒度。契约不变：`layoutBlock` 对非正宽度仍报 `InvalidConstraints`。

### 判据

- `ctest --preset native` 7/7、`npm run test:dist` 129/129、格式与注释闸 0。
- 正向：1×40 窄表首格敲两个字 → 该格排 2 行、每行 1 个簇（实测 2 行 / 超一簇 0 行）。
- 反向：把三个条件里的 `tstack.empty()` 改回 `b.cell_path.empty()`，
  「竖排格内块」与「格内折行」用例必须红。
- 反向（过程判据，已用完）：临时探针命中计数从 0/5 变成 0/0，且全量仍绿 —— 这是允许
  删除的唯一依据。探针与两个旧循环一起删掉，不留开关。

### 为什么先做这个

它同时满足三件事：删掉的是同一不变式的第二份实现（表框归属）、不新增任何概念、
判据在改之前就能证伪（探针计数）。收口的第一步应该是这种「先用计数证明它可删，再删」。

## T2 分页与落位收成一条路径（实测净 −207 行，概念 3 类型 → 1）

### 现状

`layout.cpp` 里三处各写一遍「消费分页结果、逐行落位」：简单块、带排除带的横排块、格内块。
格内块还**自己累加** `top += line.line_h`（与分页层的 `top + prev_line_h` 是同一件事的
第二份写法）。三个结果类型结构相同，三个输入类型字段互为子集。

### 做法

1. **一个结果类型** `BlockPlan`：`lines[{parts, top_pt, page, line_no}] + page_index +
   line_total + cursor_y_pt + first_line_shift_pt`。三个输入类型合并成 `BlockPlanInput`
   （差异项用已有字段表达：`no_page_break` / `continuous` / `page_stride_pt` / `live_base`）。
2. **三个算法保留**。行分页、排除带驱动、列映射是三条不同的规则；合成一个函数只会把
   switch 塞进去 —— 那是搬家，不是减法。收敛掉的是类型与消费方，不是规则。
3. **一个消费循环**。`wrap_floats ? planBlockLinesWithFloats(...) : planBlockLines(...)`，
   之后只有一个 `for (line : plan.lines) placeLine(...)`；`line_total` / `page_index` /
   `cursor_y` 全部由计划给出，本函数不再推进。
4. **格内的自行累加删除**：格内块走 `planBlockLines` + `no_page_break`，行顶只有一处递推。
5. **竖排列宽不再单独传**。`BlockColumn::width_pt` 的注释写着「等于 line.line_h」，于是
   `BlockPlanLine` 只带列心（`parts[0].x`），落位时取 `parts[0].line.line_h` 当列宽 ——
   传进来就能和片段对不上。`shaping_test` 原来逐字段对照列计划的那条判据改成同时对照
   `line_h` 与 `width_pt`，把这条不变式钉住。

### 影响面

`block_pagination.h` 389 → 224 行、`block_pagination.cpp` 214 → 217 行、`layout.cpp`
三个消费点变一处；`fragment.cpp`（后缀重新分页）与 `shaping_test`（12 处调用）跟着改类型。
段前分页与段前距只对简单块交给分页层（其余块的块首已在块级处理过），避免加两次。

### 判据

- `ctest --preset native` 7/7、`native-perf` 1/1、`npm run test:dist` 129/129。
- 正向：竖排分页「页号等于带号、行号在带内重新计数、列心与列顶逐列相同」照旧通过，
  新增的 `line_h == width_pt` 对照也通过。
- 反向：把 `no_page_break` 判定写反（格内允许翻页），`table` 域「格内折行」与
  「跨页切片」用例必须红。
- 反向：把 `planBlockLines` 的 `placed.line_no` 改成 `out.lines.size()`（漏掉起始行号），
  「行号在带内重新计数」与增量行号判据必须红。

## T3 块↔格只留一份记录（实测净 +213 行 —— 四步里唯一净增的一步）

### 现状

三份记录并存：`BlockSpec::cell_path`（每块一条嵌套路径，2000 块文档上是 2000 次小分配）、
`LayoutCell::first_block/block_count`（格说"我有哪些块"）、`StructureIndex::cells/cell_extents`
（前两者的第三份投影）。`engine_audit.cpp:477` 专门写了一节对照其中两份 —— 审计在证明重复，
而不是消除重复。T1 的探针还抓到过它们互相矛盾的实例（块声称在格里、表框却没开）。

### 做法

1. **新的 `layout/cell_index.h`**：`CellIndex` 从 `LayoutTable::cells` 反推全部关系。
   表按进入顺序排列（外层先于内层），所以按表序走一遍就能定嵌套：一张表的块区间被某张更早
   的表某一格整个包住，那一格就是它的父。树结构与三条查询（`nodeAt` / `pathAt` /
   `outermostTable` / `firstBlockIn`）都在这里，只有一份实现。
2. **`BlockSpec::cell_path` 删除**：`project.cpp` 不再写、`operator==` 不再比。投影侧的
   `path_` 仍保留 —— 它进块哈希（同一张表里两格内容相同、列宽不同，排版结果不一样），
   只是不再复制进每一块。
3. **排版层自建索引**：`layoutDocumentRangeWithTables` 入口 `cell_index.build(tables, blocks.size())`，
   逐块复用同一个 `CellSlot` 缓冲。不新增入口参数 —— 调用方传一份可能过期的索引，比多建
   一次 O(块数+格数) 的整型数组更危险。无表文档里它与旧的空 `cell_path` 逐位等价。
4. **`StructureIndex` 收成持有 `CellIndex`**：`cells` / `cell_extents` / `table_spans` 三个
   独立成员改成索引的三条视图，同一次推导产出。`cellAt` 改为按值返回（旧写法返回静态常量的
   引用，越界时是个悬空陷阱）。
5. **消费者改道**：`edit_command.cpp` 3 处、`engine_table.cpp` 2 处、`engine_layout.cpp` 2 处、
   `engine_image.cpp` 1 处全走索引。`engine_layout` 的表格边界从"扫全部格求最外层"变成
   `outermostTable` + `TableSpan` 两次查表。
6. **审计收窄**：删掉「两份记录对照」与两个因此永远为 0 的计数（`path_mismatch`、
   `stray`）。留着它们就是留一个测不出来的字段。剩下的是格区间自洽：空格、越界、同表重叠、
   跨表严格包含、格里缺结束标记。
7. 载荷契约随之重生成（`auditTables` 少两个键）。

### 影响面

新增 `layout/cell_index.h` 254 行；被改的文件净删 41 行（`structure_index.h` 227 → 146、
`layout.h` 少一个成员与一处比较、六个消费者不再各自遍历）。合计净 **+213 行**。

**这是四步里唯一净增的一步，方案当初预测的是净删 40 —— 预测错了，理由是我想错了一件事**：
以为删掉三份投影能抵掉新索引。实际抵不掉：新索引要自带"建嵌套树、查路径、找最外层"三件事，
而旧的三份投影各自只存结果、不含任何推导。买到的不是行数，是「矛盾不可能发生」——
`path_mismatch` 那种永远为 0 的取证字段随之消失，审计从"两份记录对照"退化成"一份记录自检"。
按本方案自己的规矩「为正的那一步要么不做，要么先说明为什么值」，这里明确记账：值。测试里手工构造格路径的地方改成"由表的块区间表达"
—— 块的位置仍在用例里写一遍，但落成的是唯一那份记录。

### 判据

- `ctest --preset native` 7/7（637 项断言 + 其余五片）、`native-perf` 1/1、`npm run test:dist`
  129/129、格式与注释闸 0。
- 正向：嵌套表里内层两段的格路径深度为 2、两层指向两张不同的表、外表格另一格的块只有一层
  （`doc_test` 的嵌套表用例）。
- 正向：2×2 表四段各带自己的行列号（`edit_test`，改读 `cellIndex()`）。
- 反向：把 `innermost` 的覆盖顺序改成"外层后写"，嵌套表的内层两段深度会变成 1，上面那条必红。
- 反向：把 `outermostTable` 的父链方向写反，`tableAlignedFrom` 的起点会退到内层表，
  「两表·表变高：增量与全量逐位相同」必红。

### 顺带修掉的构建缺陷（比这一步本身更重要）

这一步中途出现过「同一份代码三次跑出不同结果」：`heditor_tests` 先报 28 项、再报 7 项、
清空重建后报 2 项。查下去不是代码 —— `ninja -t deps` 显示每个目标 **#deps 0**：
一条头文件依赖都没记。

根因是中文版 VS：`/showIncludes` 的提示文字是「注意: 包含文件:」，而 CMake 只认英文前缀
（`Note: including file:`），于是 ninja 把那些行当成普通输出（构建日志里就混着它们），
依赖表恒为空 —— 改头文件永远不触发重编，判据读到的是旧目标。

修法：`CMakeLists.txt` 里 `set(CMAKE_DEPENDS_USE_COMPILER OFF)`，让 CMake 自己扫 `#include`，
与 VS 语言无关。改完 `#deps 46`，改一个头文件会重编 24 个目标。

这条缺陷的影响面超出本轮：**T0 与 T1 的「7/7」是在依赖表为空的状态下读到的**，
它们只证明了「那一刻的二进制是绿的」，没有证明「当时的源码是绿的」。收口之后重跑一遍才是真值。

## T4 有浮动图的文档恢复增量排版（实测 src +75 / −38，含新增小头）

### 现状

`engine_layout.cpp` 的整篇重排开关是 `must_full = ... || !floats_.empty()`：文档里只要有一张
浮动图，任何一次击键都整篇重排。原因不是图本身，是**续排锚点装不下排除带** ——
`ReflowState` 只有页码、块轴 y 与行号，从中间某段续排时，前面那些段落下的图所挖掉的版面
无从得知，行宽会与整篇排不同。

### 做法

1. `ReflowState` 增加 `std::vector<FloatBand> bands`（此刻仍生效的排除带，块轴坐标），
   `operator==` 一并精确比较 —— 它是"后缀能不能原样搬回"的判据之一。
2. 排版时每段的 `state_at_start` 记下当时的 `live_flow.bands`；续排入口把它们铺回
   `live_flow`。于是"从第 k 段续排"与"整篇重排排到第 k 段"拿到完全相同的浮动上下文。
3. `must_full` 去掉 `!floats_.empty()`。
4. **拼接那条路仍然不带有图文档**（`splice_ok = to >= 0 && floats_.empty()`）：拼接把后缀
   原样搬走、只挪页号与行号，而排除带是绝对位置，搬完文字与带的相对关系就变了。
   续排那条路能带上带，所以有图时走续排。
5. `truncateLayoutAt` 连浮动几何一起截：锚点落在被丢掉那一半的图，续排会重新落一遍，
   留着就是同一张图两份几何。
6. `FloatBand` 从 `float_flow.h` 拆到新的 `float_band.h`：`layout.h` 与 `float_flow.h` 都要
   它的完整类型，放在任一侧都会让两个头互相包含。

### 顺带修掉的审计缺口

`auditLayout` / `auditLayoutJson` 的对照全量走的是 `layoutDocument(...)`，它不带浮动图输入。
于是有图的文档里这条审计永远非 0，等于没有。改成用 `layoutDocumentRangeWithTables` 并把
`floatsForLayout()` 传进去 —— 对照与增量吃同一份输入，这条审计在有图场景下才有意义。

（这一步的判据正是靠它变红的：排除带快照去掉之后，`auditLayout()` 立刻报 diff。）

### 判据

- `ctest --preset native` 7/7（644 项断言）、`native-perf` 1/1（3.75 s）。
- 正向：八段正文 + 一张 120×120 的四周型浮动图，在紧挨着图的第 1 段改一个字 ——
  `layout_was_full` 为假、`relaid_paragraphs = 7 < 8`、`auditLayout() == 0`、
  `placed_floats.size() == 1`（没有重影）。
- 反向：去掉 `live_flow.bands = state.bands`，「增量结果与整篇重排逐字段一致」当场变红。
  这条反过一次：图只有 48 磅高时它压不到第二段，去掉快照也看不出差别 —— 判据要么让图盖住
  后面几段，要么它证明不了任何东西。

### 影响面

`layout.h`（`ReflowState`）、`layout.cpp`（记录与铺回）、`engine_layout.cpp`（开关与截断）、
`engine_audit.cpp`（对照输入）、`float_band.h`（新头）。`src` 净 +75 行，其中大半是契约注释；
省掉的是"文档里有图就整篇重排"这条路径 —— 原来改一个字要排全篇，现在只排脏段到末尾。

## T5 控件位置：位置到流位置只留一个入口（部分完成）

### 做了什么

编辑路径原先有七处这样写：

```
flowPosAtSide(p.para, p.offset, sideForPos(p))
```

也就是**把位置拆回三件套再拼回去**。同一个码点偏移上压着几枚括号，侧别只能由归属重新
推一次；七处各推一遍，就有了七个"推错就落错地方"的点。

现在收成 `CaretResolver::flowAt(TextPos)`：侧别在这一处归（光标那一处用光标自己存的侧别，
其余按最内层含端点），编辑路径只认它。`sideForPos` 随之删除（已经没有调用者），
`flowPosAtSide` 保留为"侧别已定时"的纯加法，宿主与测试仍在用。

`src` 实测 +23 / −18（净 +5：七处重复的拼装换成一处带契约注释的入口），行为不变：`ctest --preset native` 7/7（644 项断言，含控件边界那几组）、
`native-perf` 1/1。

### 没做什么（这条要说明白，不能算完成）

方案原定"删掉 side / hint 两套编码"，**没有做**，理由是判据不够：

- `hint`（`kInlineOffsetOuter` / 控件下标）不是编辑路径的中间量，它是**排版层行盒簇上的
  编号**（`LineCluster` 记的是"这一格属于第几个行内对象"）。删掉它要改的是行盒的簇记录，
  让簇直接带 owner 与槽序号；那会同时动排版、命中、绘制与指纹四处。
- 而控件边界的判据只覆盖了"两个紧邻控件、空控件、控件首尾、软换行处"的一部分组合，
  边界是组合爆炸。方案自己写了"判据不全就先不做 —— 这一步的目的是删掉一类 bug，不是
  删掉代码行"，按这条规矩，这一步到此为止。

剩下的那一半要单独做：先把四组边界写成双向判据，再改簇记录。在此之前，`side` 仍会作为
"位置到控件归属"的中间量存在，只是它现在只有一个产生处（`flowAt`）。

## T7 一个表只有一份「点 → 格」（实测净 +147 行，且修掉一处合并格缺陷）

### 现状（实测）

「这一点落在哪一格」有三份实现，横向与纵向各有一套容差：

| 位置 | 用途 | 容差（横 / 纵） |
| --- | --- | --- |
| `engine.cpp` 命中 | 格框优先，挑面积最小的格 | 0.5 / 0.01 |
| `tableGridJson` | 悬停取栅格（宿主画拖拽手柄） | 1.0 / 1.0 |
| `tableGridLineAt` | 拽格线 | 1.0，线 6.0 |

外加两处各自扫一遍行片段与格：`cellBoxOnPage`（求格的起始列要再扫全部格）、
`tableGridLineAt`（判"这一页有没有这张表的行"写了一遍双层循环）。

**计划里写错的两处，实测改掉**：横向 0.5 与纵向 0.01 差 50 倍是有原因的，不是随手写的
—— 横向放宽到半磅是为了抓住表的左右边框；纵向必须紧，行与行上下相接，一放宽"表下沿外
那一点"就算格内，表格后面紧跟的那一段点不进去。所以容差不是一个数，是两个具名常量
（`kCellHitTolX` / `kCellHitTolY`），定义在同一处、由同一个查询消费。
另外「整格反白扫全部表 × 格 × 页」也不成立：那个循环过滤一次二分就够，真正的浪费是
里面每格再扫一遍全部格求起始列 —— 修的是那一处，循环本身不动。

### 做法

1. `PlacedTable` 上补四个查询，成为唯一实现：`cellAtPt`（点 → 格）、`rowIndexAt`
   （页内纵向位置 → 行）、`rowBandOnPage`（行在某一页的纵向范围）、`hasRowsOnPage`。
2. `cellBoxOnPage` 不再扫格求起始列，改读 `gridColOf`。
3. 三处消费改成调用：命中测试、`tableGridJson`、`tableGridLineAt`。
4. 容差收到 `kCellHitTolX` / `kCellHitTolY` 两个常量（`layout.h`，`PlacedTable` 之前），
   点击与悬停共用，`tableGridLineAt` 的格线容差仍留在引擎侧（那是"落在线上"，另一种语义）。

### 顺带修掉的缺陷：跨行合并之后网格列整体左移

给这一步写判据时，一条属性判据红了：每个格的起始列反推回去必须还是它自己。
红的原因是起始列按"本行的格依次累加跨度"算，而跨行的格在它盖住的每一行里都占着列 ——
第二行只按自己的格从 0 数起，于是合并格右边那一列整体左移一位。后果是合并之后
点右边那一格命中不到任何格，点它左边却命中合并格。

修法是 `gridColStarts()`：从左上往右下扫一遍占位表，每格取第一段在它盖住的每一行都
空着的列。`cellAt` 与 `gridColOf` 都读它，行列定位只有一处推导。

### 影响面

`layout.h` / `layout.cpp`（`PlacedTable` 的四个查询与占位推导）、`engine.cpp`（命中）、
`engine_table.cpp`（栅格与格线）。实测 +228 / −81，净 **+147 行** —— 这是净增的一步。

账要说明白：新增的是"点 → 格 / 位置 → 行 / 格 → 起始列"这三件事的实现与它们的契约注释，
删掉的是三处消费各自写的双层遍历（命中、栅格、格线）与两处各自的扫格。行数涨了，买到的是
两样：同一查询只有一处可改；以及跨行合并之后网格列不再左移（原实现让合并格右边那一格
点不中）。按本方案「为正的一步要么不做、要么说明为什么值」的规矩，这一笔记在这里。

`cellAt` 的扫描从"累计跨度直到命中"变成"按占位表定位"，每命中一次多一趟 cells.size() 的
占位扫描；表格是几十格量级，性能判据无退化（3.83 s → 3.86 s，在噪声内）。

### 判据

- `ctest --preset native` 7/7（638 项断言）、`native-perf` 1/1（3.86 s）。
- 正向：2×2 表里第二行第二格内一点落回同一格；表下沿外 0.2 磅不算格内；表左边框外
  0.3 磅仍落在第一格；无合并时网格列等于格号。
- 正向（属性）：每个格的起始列反推回去必须是它自己 —— 这条在跨两行的合并格 fixture 上
  直接暴露了上面那个缺陷。
- 反向：把 `gridColStarts` 换回"按本行累加"，上面那条属性判据必红。
- 反向：把 `kCellHitTolY` 改成与横向同值，「表下沿外 0.2 磅」那条必红。

## T8 整格选区收成一份意图（净 +40 行，必须先记账，排在 T5 之后）（**已完成 2026-10-29**）

### 现状

整格选区靠六个字段拼出一个矩形：`sel_cell_`（粒度）、`cell_lo_/cell_hi_`（流包络）、
`cell_blocks_`（逐格的块区间）、`cell_mask_`（合并成不相交的块区间，渲染每行二分用它）、
`cell_caret_`（插入点）。矩形本身（表 + 行列范围 + 焦点格）反而不存 —— 它只在
`engine.cpp:1116-1137` 的 `syncCellSelection` 里活了几行，然后被摊平成上面那堆。

这不是"多份真相"，是**一份意图被摊平成六份派生状态，且派生过程只有一处、消费点有五处**。
它带来的 bug 类型很具体：改一处派生忘了另一处（`cell_lo_` 更新了、`cell_mask_` 没更新 ⇒
反白与删除范围不一致）。

### 做法（可选，先量后做）

保留一个 `CellRange{table, r0, r1, c0, c1, focus, caret_flow}` 作为意图，其余五份成为它的
派生缓存，**只有一个生产者** `rebuildFromRange()`。`cell_blocks_` 由 `CellIndex` 按行矩形
展开（不再由 `syncCellSelection` 现场扫 `ta->cells`），`cell_mask_` 与包络同一次产出。

`cell_mask_` 在渲染里是热路径（每行一次二分），因此必须缓存、不能每次派生 —— 所以这一步
**净增行数**，买的是「派生只有一处，改不歪」。

### 判据

- 正向：整格拖选、Ctrl+A（全选走包络那一支，无逐格信息）、跨页整格、嵌套表整格，
  四组反白矩形与改前逐位相同。
- 反向：让 `rebuildFromRange()` 只更新 `cell_blocks_` 不更新 `cell_mask_`，
  「整格反白少一整列」用例必须红。
- 反向：把 `focus` 换成矩形右下角格，`cell_caret_` 的落点用例必须红。

### 实际做法（2026-10-29）

意图落在 `CellRange`（`caret.h`）：表的身份（`CellSlot::table`，模型节点 id）、行列矩形、
焦点格。它不存 `caret_flow` —— 插入点完全由焦点格决定，留一个可覆盖的字段就是留一条
分叉（原方案列了这一项，实测下来不需要）。

唯一生产者是 `CaretResolver::setCellRange(range, CellIndex&)`：按表过滤格、按合并跨度判
相交、一次产出块区间、流包络、渲染用的合并区间、插入点。`cell_blocks_` 不再由
`syncCellSelection` 现场扫 `ta->cells` 得到，改由块↔格索引展开 —— 为此给 `CellNode`
补了 `row_span` / `col_span`（索引本来只记 slot，矩形展开需要跨度才能判相交）。

两个调用方各给一块矩形：`syncCellSelection` 给拖选出来的那块（并在展开少于两格时退回
文字选区），`selectCellAtPara` 给单格（单击格内边距带、三击）。`selectionRectsIn` 与
`cellCoversPara` 一个字没动 —— 它们读的是派生缓存，形态不变。

**判据（实测）**

- `ctest --preset native` 7/7，LayoutDigest 逐位不变；浏览器 135/135（dev 与 dist 各一遍，
  多出的一条是本步新加的焦点判据）。
- 正向四组里现有判据覆盖三组：整格拖选（`insert.spec` 的「拖选整张表的全部格」）、
  跨页整格（`table.spec` 的「整格选中空格子」）、嵌套表（`edit-sweep` 的单元格边界）。
  Ctrl+A 不走 `setCellRange`（`selectAll` 只置粒度、不吸附），因此不受本步影响。
- 反向臂一：让 `setCellRange` 只填块区间、不填合并区间 —— `table.spec` 的「整格选中
  空格子：反白铺满这条行跨过的每一页」红（页号序列变成 `[0,1,2,3,4,0,1,…]`）。
- 反向臂二：把焦点换成矩形右下角 —— 现有判据**拦不住**，为此新增
  `table.spec`「整格拖选：插入点钉在焦点那一格的末尾」（2x2 表从右下拖到左上，
  插入点必须在段 1 的末尾）。补上之后该臂红（`{"para":4,"offset":1}` 对期望的段 1）。

### 为什么排在 T5 之后

两者都动 `caret.h` 的定位与选区；同轮并行会让「判据红了」分不清是谁的锅。而且 T8 的
展开依赖 `CellIndex`（T3 已就绪），不依赖 T4/T6。

## 顺序与闸

顺序按「风险从低到高、依赖从少到多」：

```
T0 记账 → T1 删死分支 → T2 单一消费路径 → T3 表格单一记录
        → T7 点→格单一实现 → T6 文档纠正 → T4 浮动增量 → T5 控件位置 → T8 整格选区
```

T7 排在 T3 之后、T4 之前：它复用 T3 的索引，且是「表格那一族」的最后一块，
做完之后表格相关的重复记录归零。T6 排在 T3/T7 之后是因为它要引用它们的结论，
写早了会跟着改两遍。T4 与 T5 可以互换，但都不该在 T2/T3 之前动。
T8 必须在 T5 之后 —— 两者都动 `caret.h`，并行会让失败归因分不清。

每一步的闸（缺一条不算完成）：
