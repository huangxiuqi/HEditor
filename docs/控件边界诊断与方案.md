# 控件边界问题的诊断与方案

> 结论摘要：**这不是"边界处理又漏了哪里"，而是数据模型缺一层。**
> 控件边界（`[` / `]`）在实现里没有独立的位置身份，被压成了"字符码点偏移"；
> 而 n 个相邻或嵌套的控件会在同一个偏移上产生多个互不相同的位置。
> 于是凡是依赖"边界身份"的判断（括号绘制顺序、光标落在谁的哪一侧、这个位置属于哪个控件、
> 谁嵌套在谁里面）都只能在运行时**从裸区间反推**，共四条启发式。
> 它们相互之间没有一致性保证，而正确行为要求它们一致 —— 四个现象就是它们互相打架的结果。
>
> 更进一步：**其中两个现象在数学上无法用同一套反推同时修好**（第四节给出两个实测反例）。
> 所以继续打补丁只会把冲突从一个表现换成另一个表现。

## 一、复现与取证

环境：WASM 构建时间 `2026-10-10 19:32:24`（`scripts/build_wasm.ps1` 重编后的当前代码）。
样例：`loadFormSample(2)` = 三连相邻 `[5,7) [7,9) [9,11)`；
`loadFormSample(3)` = 三层嵌套 `[5,11) ⊃ [6,10) ⊃ [7,9)`。

取证脚本（新增，可重复运行）：

```powershell

powershell -ExecutionPolicy Bypass -File scripts\verify_web.ps1 -Probe scripts\diag_ctl2.mjs -Port 8790 -DebugPort 9230
powershell -ExecutionPolicy Bypass -File scripts\verify_web.ps1 -Probe scripts\diag_ctl3.mjs -Port 8790 -DebugPort 9230
```

输出落在 `out/diag_ctl.txt`、`out/diag_ctl2.txt`、`out/diag_ctl3.txt`，
截图落在 `out/web/diag3-*.png`。

### 1.1 初始状态是好的

两个样例在**未编辑时**都正确：

- 命中测试与真实鼠标点击逐点一致，整行没有死区（`diag_ctl.txt`，x 从 124.9 扫到 249.4，步长 0.5pt）。
- 每个偏移的光标渲染位置互不相同（`diag_ctl3.txt`）：三层嵌套 off=5..11 对应
  `198 / 228 / 259 / 280 / 301 / 331 / 361`（帧像素），方向键逐格移动可见。
- 括号槽顺序正确：`5[ 6[ 7[ 9] 10] 11]` —— 三个开括号在左、闭括号由内到外依次收，
  即 `[反[复[心悸]三]天]`。

所以"静止状态下点不进去"这类说法在这一版里不成立；异常全部出现在**编辑之后**。

### 1.2 现象三：删掉中间字段的内容后，光标画在了左边字段的右括号上

三连样例，光标置于 9，退格两次删掉「心悸」`[7,9)`：

```
控件  [[5,7,0,-1,1], [7,7,1,2,0], [7,9,0,-1,1]]      # 第 1 个变成零宽
括号占位 5[126.7  7]160.9  7[167.2  7]173.4  7[179.6  9]213.8
光标      offset=7  归属=1  渲染 x=240.0px
```

- `归属=1` 说明引擎认定光标属于那个零宽字段（正确）；
- 但 `渲染 x=240.0` 落在 `7]160.9` 那一枚**左邻居的闭括号**上（160.9pt × 1.5 ≈ 241px），
  而零宽字段自己的一对在 167.2 / 173.4（即 251 / 260px）。

结果：视觉上光标停在「反复」的末尾，看不出它已经在中间那个字段里 ——
对应"光标直接到复字后面了，没有留在中间控件"。
随后右方向键把偏移从 7 推到 8（即三字的右边），因为整数偏移里**没有**"在 `[` 与 `]` 之间"
这个位置可停 —— 对应"再右箭头光标直接跑到三字后面了"。

附带发现（同一份输出）：区间树把零宽的中字段判成了**右边字段的孩子**
（`[7,7)` 的 `parent=2`，而 `[7,9)` 是下标 2），
但括号把它画在了右边字段的**左边**。树与绘制方向相反。

### 1.3 现象四：两个零宽字段既点不进也走不进

三连样例，把后两个字段的内容都删掉：

```
文本      患者主诉：反复，加重一天。
控件      [[5,7,0,-1,1], [7,7,1,0,0], [7,7,1,0,0]]    # 两个零宽区间完全相同
括号占位  5[126.7  7]160.9  7[167.2  7]173.4  7[179.6  7]185.8
光标      offset=7  归属=1  渲染 x=240.0px
```

两个零宽字段的区间完全相同，命中"完全重合即兄弟"这条规则，双双退化成
`depth=1 / parent=0` 的兄弟，彼此不可区分。光标偏移只有一个整数 7，
而屏幕上有三个不同的"缝"（`]` 之后、`[` 之后、第二对 `[` 之后），
偏移根本编码不了这个区别 —— 光标只能画在最左那个，方向键从 7 到 8 直接跳过整对括号。

### 1.4 现象二：嵌套控件被删空后退化成并列

三层嵌套，一次删掉「心悸三天」`[7,11)`：

```
文本      患者主诉：反复，加重一天。
控件      [{"r":[5,7],"d":0,"p":-1}, {"r":[6,7],"d":1,"p":0}, {"r":[7,7],"d":2,"p":1}]
括号占位  5[126.7  6[146.9  7]167.2  7]173.4  7[179.6  7]185.8
```

区间树**仍然是三层嵌套**（depth 0 / 1 / 2，父子链完整），但括号的发出顺序是：

```
]  (下标1，depth 1，闭)   ]  (下标0，depth 0，闭)   [  (下标2，depth 2，空)   ]  (下标2)
```

即最内层的空字段那一对，被排到了所有闭括号**之后** —— 画出来是 `[反[复]][ ]`，
读起来像"反复是嵌套的，后面跟着一个独立的空字段"。树说它在最内层，画面说它最外，
两者相反。对应"嵌套的三个控件变成非嵌套的了"。

### 1.5 现象一：未复现

三层嵌套初始状态下，反与复之间（偏移 6）是可达的：

- 真实鼠标点击：`x ∈ [140.4, 159.9]` → `hit = 6/1`，`caret = 6`，归属=1（中层），无死区；
- 方向键：从偏移 4 连按右键得到 `4 5 6 7 8 9 10 11 12 ...`；
- 偏移 6 的光标渲染在 152.0pt，而中层左括号的槽是 146.9..152.0pt —— 正好落在左括号与"复"之间。

唯一的"怪"是这个槽本身（146.9..152.0pt）没有对应的光标位置：点上去光标会跳到槽的右边缘。
如果"点不进去"指的是这个，那它和其余三个现象同根（边界不等于位置）。
否则需要更精确的复现步骤，并确认页面上跑的确实是上面那个构建时间。

## 二、根因：控件边界没有被当成"位置"

### 2.1 现状

- 光标的全部状态是 `TextPos{para, offset}` —— 一个段内码点偏移。
- 控件是"覆盖在码点区间上的标注"：`ControlRange{start, end}`，行为全靠区间伸缩函数维护。
- 于是"边界"只是区间端点的一个**数值**，不是文档流里的一个**位置**。

一个偏移上能挂多少个互不相同的边界？对 n 个共享该偏移的控件，
最多有 `左括号之前 / 左括号之后 / 右括号之前 / 右括号之后` 几类，
而"在 `[` 与 `]` 之间"这类位置在整数偏移里**没有编码**。

### 2.2 四条反推启发式

既然位置表达不了，实现只能在运行时反推，一共四处：

| 反推什么 | 实现在哪 | 规则 |
|---|---|---|
| 括号画在谁的哪一侧、按什么顺序 | `layout.cpp` 的 `withBracketSlots` | 三分桶 `(bucket, key, tie)`：闭括号（内层先收）→ 空字段的一对 → 开括号（外层先开） |
| 光标画在括号的内侧还是外侧 | `layout.h` 的 `inlineOffsetFor` | 闭括号占位短路返回，`prefer_owner` 提示负责"贴 `[` 之后" |
| 这个位置属于哪个控件 | `control.cpp` 的 `innermostAt` | depth 最大者胜；同 depth 取下标小者 |
| 谁嵌套在谁里面 | `control.cpp` 的 `normalize` | 每次从裸区间重解包含关系，用"完全重合即兄弟"避开互相认父 |

### 2.3 四个现象都是"两条反推打架"

| 现象 | 打架的两方 |
|---|---|
| 1.2 光标不在中间控件 | 归属（`innermostAt` 判给零宽字段） ⟂ 光标画法（`inlineOffsetFor` 画到左邻的 `]`） |
| 1.3 键盘进不去 | 光标偏移（一个整数） ⟂ 三个零宽字段与三对括号 |
| 1.2 附加 | 嵌套树（零宽字段是右邻的孩子） ⟂ 括号顺序（画在右邻左边） |
| 1.4 嵌套退化成并列 | 嵌套树（depth 2，最内） ⟂ 括号顺序（三分桶把它排到最后，最外） |

另外，`adjustControlsOnInsert / Erase / SplitPara / MergePara` 每次末尾都要
`normalize()` 重建整棵树，这本身就说明嵌套关系没有稳定表示 ——
每次编辑之后都要重新猜一遍，而"猜"的依据（数值区间）在删空之后已经丢掉了信息。

## 三、为什么补丁修不好

三分桶这个启发式只对**并列**的字段成立，对**嵌套**的空字段必然出错。
而把它改成按 depth 排序，又会弄坏并列的情况。这不是规则写得不够细，是两个方向的要求互相冲突。

### 3.1 反例一：三分桶在嵌套空字段上出错（实测，1.4 节）

```
期望（按树的 depth 2/1/0 收口）      [反[复[ ]]]
实际（闭 → 空 → 开）                 [反[复]][ ]
```

### 3.2 反例二：改成按 depth 降序会在并列空字段上出错

把排序主键从 bucket 换成 depth（降序，同 depth 再按 bucket），
对 1.4 的三层嵌套确实给出正确的 `[反[复[ ]]]`；
但对 1.3 的三连（两个并列空字段 `#1[7,7)` `#2[7,7)`，depth 都是 1）会得到：

```
depth 1（空字段两对）在前，depth 0（左邻闭括号）在后
→ [反复[][]]          期望是 [反复][][]
```

两个空字段本该在左邻**外面**，depth 排序把它们放到了**里面**。

### 3.3 冲突的根源

一处偏移上"空字段属于哪一层"，是从整数区间里**推不出来**的：
区间 `[7,7)` 与"在 0 号字段之后、2 号字段之前"这两个事实，
在 `(start, end)` 这个二元组里是同一个值。信息在删空那一刻就丢了。
所以"选择哪条排序规则"等价于"选择让哪一类场景正确"，不存在两者都对的规则。

## 四、业界做法：边界本身就是位置

主流做法都不从数值区间反推边界，而是让边界**进文档流**。

### 4.1 Word / OOXML

- `.doc` 二进制格式：[MS-DOC] 规定域由文本流里的三个控制字符构成 ——
  起始 `0x13`、分隔 `0x14`、结束 `0x15`；并明确 **"A Plcfld MUST NOT contain duplicate CPs"**，
  即每个域标记自身占一个字符位置，标记可嵌套（域可以嵌套）。
- OOXML：`w:sdt`（内容控件）把内容包成一个真实元素
  （`w:sdtPr` + `w:sdtEndPr` + `w:sdtContent`），可在段落、行内、表格行/单元格各层嵌套；
  `w:fldChar` 用 `begin / separate / end` 三个标记表达域。

要点：边界是元素或标记，**在流里有自己的位置**，嵌套由结构决定，不由数值反推。

### 4.2 ProseMirror

位置是"token 序号"这一计数约定，规则见官方指南：
**进入或离开一个非叶节点各算 1 个位置**，每个字符算 1，叶子节点整体算 1。
于是"在节点边界上"与"在节点里"是两个不同位置，`ResolvedPos` 还能直接给出
父节点、层级深度、在父节点里的偏移。
Framer 那篇复盘也把"位置是边界计数"讲得很清楚，并指出文档级位置不能直接当
`TextSelection` 端点用。

### 4.3 结论

`contenteditable`（光标是 node + offset）、Slate、Lexical 是同一个思路的变体：
**光标地址里带结构上下文**，而不是一个扁平整数。

## 五、方案 A（推荐）：把控件边界做成文档流里的一等位置

### 5.1 数据模型

段落的元素序列从"纯码点数组"变成"码点 + 边界标记"的序列：

```
Item = Text(cp) | Boundary(control_id, side = Open | Close)
```

- 控件只存身份与元数据：`{id, kind, read_only, label}` —— 不再存 `start / end` 偏移。
- 控件的端点由它在流里的两个标记决定；嵌套、深度、父子关系由**一次栈扫描**得出，
  不再需要 `normalize()`、"完全重合即兄弟"这类补丁。
- 光标位置用流位置（`Item` 序号，或 (offset, 该偏移上的第几个缝)）表示，
  于是"在两个标记之间"天然是一个合法位置，零宽字段也有两个不同的位置。

### 5.2 四个现象怎么消失

| 现状 | 改后 |
|---|---|
| 括号顺序靠三分桶启发式 | 标记在流里的顺序**就是**绘制顺序；嵌套与绘制由同一份数据决定，不可能打架 |
| 光标内外侧靠 `inlineOffsetFor` 短路 + `prefer_owner` 提示 | 光标就在某个缝里；点击命中的是哪个缝就直接知道，提示机制整块删除 |
| 归属靠 `innermostAt` 反推 depth | 流位置上的开标记栈就是控件栈，归属直接可读 |
| 嵌套靠重解包含关系 | 栈扫描一次得出；`rangeContainsForNesting` 与它要避的自环一起消失 |
| 编辑后靠 `adjustControlsOnInsert/Erase/SplitPara/MergePara` 改端点 | 编辑就是往流里插删 token，标记自动跟着走；四个函数全部删除 |
| `preferred` 参数、`caret_field_` / `caret_field_at_` | 一并删除 |

净结果是**代码变少**，而且整类缺陷（边界身份与位置表达力不足）从此不存在。

### 5.3 迁移步骤（按可独立验证的顺序）

1. 段落容器加一层元素流（`cp_text` 保留为派生视图，供整形与断行使用），
   先只支持"标记不参与长度账"，其余逻辑不动，跑现有单测应全绿。
2. `ControlSet` 改为只存身份；标记的建立与拆除由"区间 → 标记对"的一次性转换完成；
   老的 `Control` 结构暂时保留为视图，便于逐步切换调用方。
3. 光标与命中测试改为流位置；`inlineOffsetFor` 改为"按标记自身的流位置取缝"，删掉短路与提示。
4. `withBracketSlots` 改为按流序发出槽；删掉三分桶，`owner` 直接取标记自己的控件。
5. 编辑入口（插入 / 删除 / 分段 / 合并）改为流操作；删除 `adjustControlsOn*` 与 `normalize()`。
6. 重写与"括号顺序 / 归属 / 光标侧别"相关的单测与探针断言
   （现有 `[18]` 等用例编码的正是被替换掉的启发式）。这一步不能省，否则回归无从判断。

### 5.4 代价与风险

- 出现两套索引（流位置与码点偏移），必须约定唯一口径：对外 API 一律说流位置，
  码点偏移只作为派生量。这是本方案唯一的结构性风险。
- 排版侧改动有限：整形仍按"连续文字 token 拼成 run"喂给 shaper；
  标记是零宽闸门，断行与占位逻辑与现在同源。增量排版的脏段机制不受影响。
- 跨段控件在标记模型下反而变简单（标记落在不同段落即可），不再是"只做标注与判定"。
- 单测要改一批，这是实际工作量的大头。

## 六、方案 B：控件树 + 路径光标

段落内容是一棵控件树，光标 = `(路径, 段内文字偏移)`（同 DOM Range / Slate / Lexical）。

- 表达力最强，是"字段真的是节点"的形态。
- 但要同时改光标、选区、命中测试、排版入口，"控件是覆盖在普通文字上的标注、
  正文是一条扁平码点序列"这个前提会被打破，改动面比方案 A 大得多。
- 若将来要做"字段本身就是结构、可整块拖动/复制/校验"，才值得付出这个代价。

## 七、不改模型的立即缓解（可选，按优先级）

1. **零宽字段给一个最小可点宽度**：现在 `rects` 为空，鼠标完全点不到它；
   给它一个最小投影宽度，至少能用鼠标定位。
2. **光标画法对齐归属**：`inlineOffsetFor` 遇到"归属是零宽字段"时不要走闭括号短路，
   把光标画进去（做到"看到的就是归属"），能立刻消掉"光标跑到复字后面"的观感。
3. **显式的当前字段状态**：维护 `focused_control` 并给一个换字段键（Tab 已被缩进占用），
   归属不再从几何现推；这也能顺带缓解"键盘进出不去"的困惑。
4. 这些缓解都只是让冲突换一个表现方式，**不会**同时修好 1.3 与 1.4（第三节已证明）。
