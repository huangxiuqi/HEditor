# 文档模型设计

> 本文是 `docs/正式化架构与迁移路线.md` 第四层（文档模型）的细化设计，两份冲突时以本文为准。
>
> 目标产品：富文本编辑器（文字、图片、公式）加上病历表单模式（文本输入框、单选复选、下拉），
>
> 并支持编辑 / 表单 / 只读三模式切换。参照项目 `D:\Develop\DCWriterLite` 为 GPLv3，
>
> 本文只借其架构思想与功能清单，不使用其代码。

---

## 一、已确定的骨架

四个决策已定，本文全部设计从它们推出：

| 决策      | 选择                 | 直接后果                             |
| ------- | ------------------ | -------------------------------- |
| 位置与节点身份 | 留协同扩展位             | 节点带稳定 ID，位置用 (节点 ID, 偏移)；不把下标当身份 |
| 表单数据    | 值内联进文档 + 控件带稳定 key（可重复） | 归档自足，同时保留按 key 取数 / 回填 / 导出的通道   |
| 行内表达力   | 容器与原子并存            | 控件是跨度、可跨段落标记；图片、公式是不可断的原子              |
| 编辑操作    | 可逆步骤               | 每步带逆操作，撤销即执行逆操作，天然存在差量           |

另外三项：

本期需要的结构（标题与列表、引用与代码块、分节、修订留痕与批注）都是跨段落标记的用法；

样式走**命名样式 + 内联覆盖**；

域按值的来源分两类（排版结果 / 运行时刻），只出现在页眉页脚；患者信息是控件值而不是域。

本项目现状是最扁的一档：`BlockSpec` 是码点数组加一份字体参数，位置是 `TextPos{para, offset}`。

本次改造要把"一块文本 + 一组字体参数"替换为**元素流 + 容器树**，同时保持排版引擎的输入契约基本不变。

## 二、不变量

文档模型的价值不在"能表达什么"，而在"什么表达不出来"。下面每一条都必须是**可断言**的，

写进单测，任何编辑操作之后都要重新满足。

**结构类**

- 根节点唯一，其下是节序列，节序列覆盖全部内容且无缝隙。
- 每个节点的子节点类型与数量都满足 schema 声明（哪些能装哪些、最少几个、最多几个）。
- 没有孤立节点：除根以外每个节点都挂在一棵树上，且只有一条路径可达。
- **隐藏的控件只在编辑模式下在流里**：表单与只读模式下它不参与流位置展开、不参与排版，
  但节点与值仍挂在树上（按 `id` / `key` 取值与设值仍有效）。切换隐藏是结构性编辑，
  必须标脏并按结构变化处理。

**文本与标记类**

- 文本节点非空。相邻且标记集合相同的文本节点必须合并为一个。
- `TextRun` 不跨流元素：一个 `TextRun` 完整落在同一个容器内、同两个流元素
  （段落标记或成对边界）之间。
- 标记没有重复项；标记集合内的顺序由 schema 固定（保证序列化确定）。
  用"结构体 + 可选字段"表示标记（`char_format.h`）时，这两条在表示上就不可违反，
  不需要另立规则去查；1.6 若把标记改成表，才重新需要判定。
- 标记区间是"落在文本上"的，不允许零宽标记区间。

**身份类**

- 同一文档内节点 ID 唯一。
- 控件 id 唯一。控件 key（业务编码）**不要求唯一**：多个控件可以共享同一个 key
  （正文与页脚镜像同一个字段就是这么做的），它与 id 一样不随编辑改变。
- 节点 ID 在保存与重新打开之后仍然有效（否则批注、书签、引用会全部失效）。
- **段落没有 ID**（它是派生量）。要引用段落，只能引用那个段落标记元素的 ID，
  或引用"元素 ID + 偏移"。这条约束是第三节方案一的直接代价，写在这里以免后来者误加。

**容器边界类**

- 容器的开闭标记成对、有序、不交叉。要么嵌套，要么并列，不存在第三种关系。
- 成对边界落在同一个容器内，不做跨容器的跨度；结束边界不排在起始边界之前。
- 容器内的元素序列被段落标记完整切成若干段，无缝隙：每个元素必属于某一段。
- 段落标记可以被容器边界跨过（这正是"控件里能有多段"的实现方式），也可以不被跨过。

第三条要强调：它把"元素归哪一段"变成全函数——任意元素都能唯一定位到一段，
所以不存在"既不属于这段也不属于那段"的元素，也就不存在无处安放的光标位置。
上一条则保证边界可以跨段落标记而不是必须跨，所以行内用法（`主诉：[____]`）与
块级用法（一栏里多段）是同一个机制的两个取值，不是两个类型。

`TextRun` 与 `ParagraphMark` 的区别是这两条约束的直接结果，值得单独说清：
**段落标记是流里的真实元素，`TextRun` 是被切分出来的叶子**。所以段落可以被容器跨过
（它是位置上的分段线），`TextRun` 不行——它必须完整落在同两个流元素之间。
判据只有一句：**能不能跨过流元素**。能跨的是位置（段落），不能跨的是内容（`TextRun` 与原子）。

**表格类**（见第九节）

以下三条是对**派生网格**说的：模型里只有跨度，没有网格，续格在模型里根本不存在。

- 每行的跨度之和相等，等于网格列数。
- 网格中不存在重叠的单元格；不存在无主的空洞格位。
- 纵向合并的续格必须紧邻其原点格，且中间不被打断。

**这四条里只有两条是可判定的数据规则**（1.7 落地为 `checkInvariants` 的第 11 条），
另两条由结构或算法保证、数据层构造不出反例：

| 条目 | 为什么 |
|---|---|
| 每行的跨度之和相等、等于列数 | **可判定**：推一遍网格，看每行的格位是否被完整覆盖。注意它说的是"这一行**被覆盖**的格位数"，含从上面跨下来的合并 —— 不是"这一行自己的格子的跨度之和"，纵向合并覆盖的行本来就没有那么多自己的格子 |
| 无空洞 | **可判定**：同上，同一遍推导就报得出来（少一格或多一格都会留下没主的格位） |
| 无重叠 | 放置算法总是把格子放在第一个空闲格位，两个格子落不到同一个格位。**不可构造**，只在推导里留一条守卫 |
| 续格紧邻原点格 | 模型里根本没有续格（被合并掉的格位不存在），这条由结构本身保证。**不可构造** |

**别把不可构造的两条当成"查过了"**：它们留在推导里是为了在改放置算法时先亮，
不是覆盖范围的一部分。规则名仍沿用"跨度之和相等、无重叠、无空洞、有列定义则数据行不许合并"
这一串（与散文里的措辞对齐），但下面那条列定义约束才是它真正多出来的一半。
- **有列定义的表格（即列上绑了字段的表格），数据行不允许合并**：每行格数等于列数，
  否则"第 i 列"不再是确定位置，按列落值无从谈起。表头行不受此限。

**域类**

- 求值只更新缓存值，不改变文档结构，也不产生编辑步骤（否则打开文档就会污染撤销栈）。
- 只有"排版结果类"域允许迭代，且迭代必须在上限内终止。

**编辑能力类**（见第七节）

- **可编辑集合取交集**：一个位置可编辑，当且仅当**包住它的每一层**控件都允许编辑
  （模式策略、控件的 `readonly`、以及将来的锁）。任何一层不允许，这个位置就不可编辑。
- 可编辑集合是**作用于光标落点的谓词**，不是"被删掉的元素"：文档结构不受模式影响。
- 光标落点必须在可编辑集合内；**选区的端点与范围不受此限**（可以跨出控件）。
- 编辑动作的落点也必须在可编辑集合内；不在就拒绝并给原因，不静默裁剪范围。

**取值与嵌套类**（见第七节）

- **值即内容的控件**（文本类）取值等于它子树内全部可见文字的按序拼接，**含嵌套控件内部的文字**；选择类控件的值在属性上（`value`），不读内容。
- 内部含子控件（或其它非文本元素）时，整体设值必须被拒绝并给原因，不静默替换内容。
- 同 `group` 的单选最多一个选中；同 `group` 的复选属于同一个多选集合（彼此不互斥）。
- **控件是跨度，内部内容（含标签文字）与普通文本一样占位**：选区端点可以落在标签内部，
  所以标签能部分选中；编辑动作落在控件内部的描述性内容上被拒（改它走控件设置）。
- **真原子（图片 / 公式 / 域 / 制表符）在流里是一个位置**，选区覆盖它时它在文本输出
  （取值 / 复制 / 导出）里贡献自己的**文本表示**（域是缓存值，制表符是制表符，
  图片与公式暂为空）。覆盖它的粒度是整体，不落内部。

**区间与选区类**（见第四节末尾）

- **选区是会话状态，不是文档数据**：不进文档树、不落盘、不参与序列化
  （第十三节只落它的外观选项）。同一份文档可以同时有两个互不相干的选区。
- 选区端点是两个位置**加方向**：`anchor`（不动的那端）与 `focus`（跟着光标走的那端）
  分开存，方向决定下一次 Shift 扩展从哪一端继续。
- 端点存**流位置**（整数下标），不用节点 ID：节点会因编辑失效（平移、分裂、合并），
  流位置不会。编辑步骤同时负责把端点映射到新位置（第四节末尾）。
- **区间端点必须落在流元素边界上。** 区间涉及不可半分的单位（控件、表格行、单元格）时，
  一律**向外扩到整块边界**，不允许出现"半个控件"的区间——半个控件会破坏
  "成对边界同容器"（容器边界类），所以这是结构上的强制，不是显示上的偏好。

## 三、节点类型系统

三类节点（容器、原子、文本）加一种流内分隔元素。这套类型不是照搬任何一家，
是按本项目已有能力与需求裁出来的。**段落不是节点**，是流里的范围——这是本节最关键的一条，
依据在节末"段落是节点还是范围"。

**容器**：持有子元素的序列，在流里表现为"起始边界 … 内容 … 结束边界"。

```
Document        根，持有节序列、样式表、控件表、资源表
Section         节：纸张、页边距、页眉页脚、页码起始、分栏
Table           表格
TableRow        表格行
TableCell       单元格
ContentControl  内容控件：跨度可越过段落标记，所以"一栏"里能有多段
Quote           引用块
CodeBlock       代码块
ListItem        列表项：列表属性（层级、编号）挂在自身边界上
Link            链接：跨度不跨段落标记
HeaderFooter    页眉页脚的内容片段：装块级内容，不在正文流里，由节的记录引用
```

**原子**：不可再分，在流里是一个带宽度、参与断行的叶子。

```
Image           图片：资源 ID + 宽高 + 定位与环绕方式
Formula         公式：表达式 + 排版后端标识
Break           软换行
PageBreak       分页符
Tab             制表符
Field           域：种类 + 缓存值（页码、总页数、打印日期、文档属性）
```

**这里没有"复选框""下拉"这类名字，是刻意的。** 它们是**业务类型**（控件的一个字符串属性、
可以注册，见第七节"控件表"），不是节点种类：结构上控件只有容器型与原子型两种形态，而
**节点种类上只有 `ContentControl` 一种**。业务类型若写进枚举，等于每加一种控件都要同时改
容器判定、不变量检查器、编译与序列化四处。0.1 已按这个口径收窄完毕，判据是"加一种业务控件
不改任何 C++ 枚举"（见第十五节的进度）。

**文本**：叶子，完整落在同两个流元素之间，不跨段落标记，也不跨容器边界。

```
TextRun         一段共享同一套标记（marks）的连续文本；边界由标记集合的变化决定
```

`TextRun` 是这类模型里最容易被误解的节点，值得说清三点。名字借自 Word 的 `w:r`（run），
OOXML、ProseMirror、Slate 用的是同一个概念。它存在的理由是字符属性必须以**区间**形式附着：
整段共用一份属性就是现在的 `BlockSpec`（没有 run 级样式），每个字符各带一份属性则又太重，
中间这层就是"一段连续的、属性完全相同的文本"。所以**它的边界是算出来的，不是用户划出来的**——
用户不会"新建一个 run"，只会"给这段加粗"；加粗区间一落，相邻的标记集合就变了，
`TextRun` 随之被切开或合并。这就是第二节那条合并不变量的由来。

**流内分隔元素**：既不是容器也不是原子，它标记段落的结束，是段落属性与空段落字符格式的唯一宿主。

```
ParagraphMark   段落结束标记：段落 = 同一容器内两个标记之间的范围
```

带标记的区间（`MarkedSpan`）不在这张表里——它只在编辑过程中临时存在，
规范化时被合并进相邻 `TextRun` 的标记集合，落盘与排版都看不到它。

**没有"行内"与"块级"的分类。** 上面这张表刻意不带这个二分。容器之间的差别只有两条：
**接受哪些元素类型**（一个位标志的并集，防止把表格塞进链接这类无意义组合），
以及**跨度是否跨过段落标记**——跨过就是块级语义，没跨就是行内语义。
后者是位置差别，不是类型差别，所以不需要两个类型，也不需要"行内升级为块级"的提升规则。
这一条是从参照项目 58,875 行源码里读出来的，完整依据在节末。

这张图把容器与流的关系摆在一起。左边是树，右边是同一份内容在流里的样子——
**段落只在流里存在，树上看不到段落节点**。

树视图：

```
Document
 └─ Section ─────────────────────── 节属性：纸张 / 页边距 / 页眉页脚 / 页码起始
     ├─ ContentControl [key=chief]   跨度越过一个段落标记
     │   ├─ TextRun("反复")
     │   └─ TextRun("心悸三天")
     ├─ Quote
     │   └─ TextRun("注意复查")
     └─ Table
         └─ TableRow
             └─ TableCell
                 └─ TextRun("36.8")
```

流视图（`Section` 内的一条扁平序列，光标与断行都在这条序列上）：

```
TextRun("患者主诉：")
ContentControlStart [key=chief]       起始边界：行内叶子，有宽度，参与断行
TextRun("反复")
ParagraphMark                         段落 1 结束（段落属性挂在这里）
TextRun("心悸三天")
ContentControlEnd                     结束边界
ParagraphMark                         段落 2 结束（患者主诉这一段到此为止）
TextRun("注意复查")
ParagraphMark                         段落 3 结束
Image {res,w,h}                       原子
Field {pageNo}                        原子，排版时求值
LinkStart … LinkEnd                   跨度不跨段落标记
```

控件那一段要看清：`ContentControlStart … ContentControlEnd` 之间跨了一个 `ParagraphMark`，
所以它内部"有两个段落"。真正的结构是**一个跨度跨过一个段落标记**，
不是"容器里装着两个段落节点"。这正是"行内位置放不下块级内容"这个矛盾不存在的原因。

### 为什么控件是跨度而不是带属性的原子

病历里最典型的用法是 `主诉：[______]` 这种**行内嵌入**——控件在段落流之中；
而"一栏里有多段"又要求它能跨过段落标记。做成原子就两样都做不到：内部文本塞进属性之后，
字体、行距、多段、换行全部要另立一套表达，等于把排版引擎的能力在属性里重写一遍。

参照项目的 `DomInputFieldElement` 继承自容器元素，走的是同一条路。代价是流里多一对边界元素、
规范化规则多几条，这笔代价在选"容器与原子并存"时已经认下。

### 原子与容器的统一处理

两者的差别只有一条：**能不能装子内容**。所以基类上是一个 `isContainer()` 判定，
位置计算、遍历、序列化、命中检测全部走同一条路径，只在"取子节点"处分叉。
不要为原子单独写一套遍历，那是重复代码的源头。

### 段落是节点还是范围：参照项目实测

如果反过来把 `Paragraph` 做成节点、把 `ContentControl` 归为容器（即下面的方案二），
就会撞上"行内位置放不下块级内容"这个矛盾。参照项目用一个决定就消掉了它，
以下是 58,875 行源码与 23 份真实病历模板的实测结果。

**它根本没有"行内 / 块级"这个分类。** 全库搜不到 `IsBlockElement` / `IsInlineElement` 之类判定。
子节点约束只有一个方法 `RuntimeAcceptChildElementTypes()`，默认返回 `ElementType.All`；
全库只有三处重写——字符串元素只收文本、表格只收行与列、表格行只收单元格。
**`DomInputFieldElement` 一处都没重写，它不限制子节点。**

**段落不是节点，是流里的范围。** `DomParagraphElement` 的注释原话是
"本对象只在加载或保存文档时临时生成"，运行期没有段落节点。段落由 `DomParagraphFlagElement`
（一个 EOF 叶子元素）在流里分隔，范围由 `GetParagraphEOFElement(element)` 导出——
实现就是从元素下标往后找同一个列表里第一个段落标记。

**段落属性挂在段落结束标记上。** `GetParagraphStyle(element)` 先找到本段标记，
再取它的 `RuntimeStyle`。每个元素自带 `StyleIndex` 管字符样式，段落样式来自标记。

**域的边界是流里的两个真实元素。** `DomFieldBorderElement`：运行期惰性创建
（`CheckStartEndElement()`）、有宽度（`ViewWidth = max(Width, 12.5f)`）、参与断行；
与字符、段落标记、图片同层——取屏幕矩形时这四类走同一条分支。

**域的内容内联进父流。** 布局时域的展开是 `[起始边界] + 域内容 + [结束边界]`，
三者追加进**同一个累加器**（`content.FastAdd2(se)` … `FastAdd2(ee)`）。所以域的内容
不是独立子流。边界元素**不进序列化**——落盘写的是嵌套节点
`<Element xsi:type="XInputField"><XElements>…`。运行期是扁平边界式、序列化是嵌套节点式，
两者之间靠加载与保存时的一次转换衔接。

**23 份真实模板的统计。** 段落标记的父元素有 **22 处是 `XInputField`**；
域的父元素有 **27 处是域**（5 处直嵌正文、22 处嵌在表格单元格里的域里）；
域的父容器分布是单元格 1069、正文 211、页眉 51、页脚 7。

**光标也在流下标上。** `DCContent` 本身就是元素列表，`MoveLeft()` 就是下标减一。
关键在位置换算 `GetPositonInfo()`：命中**起始边界**归一化为 `(域的父容器, 域的下标)`
即"域之前"，命中**结束边界**归一化为 `(域, 域.Elements.Count)` 即"域内末尾"。
这正是上一轮那四个缺陷的解法——"域之前"与"域内"是两个不同的位置，
不需要在整数偏移上反推。它还对 LTR / RTL 分别比较了 `LayoutIndex`。

**结论：采用方案一**，也就是本节的形状。

| | 方案一（参照项目做法，已采用） | 方案二（Word 与 ProseMirror 做法，未采用） |
|---|---|---|
| 段落 | 流里的范围，属性挂在结束标记上 | 节点 |
| 控件 | 一个类型，跨度可越过段落标记 | 拆成 `InlineControl` / `BlockControl` |
| schema | 不需要例外 | 需要"行内升级为块级"的提升规则 |
| 与编译的关系 | 模型与编译产物同构 | 要先展开成方案一的形状再喂引擎 |

选方案一不只是少一个类型：引擎本来就只吃"段落序列 + 行内盒子序列"，
方案一让**模型与编译产物同构**；方案二要多一层翻译，也就多一处可能不一致的地方，
而且那条"行内升级为块级"的提升规则本身很难写对。

代价说清楚：段落的 O(1) 定位要靠派生下标数组维护（每条容器一条扁平流加一个标记下标数组）；
增量的 `layout_dirty_from_` 仍然成立，但"段落的身份"从节点 ID 变成标记位置。

## 四、位置与节点身份

### 位置

```
Pos = { container: NodeId, offset: int }
```

`offset` 的含义由所在容器决定：容器节点里是**子元素槽位序号**，文本节点里是**码点下标**。

关键在**边界是流里的真实元素**，于是"在控件之前"与"在控件之内"是两个不同的位置。
把一个行内控件周围的流位置摊开（`first` 是它的起始边界、`end` 是"控件之后"那一格）：

```
控件之前     first        父容器里"起始边界之前"那个槽位
内容开头     first + 1    (控件, 0)
内容末尾     end - 1      (控件, k)，或结束边界那一位
控件之后     end          父容器里"结束边界之后"那个槽位
```

对**删空的控件**（内容长度为零）这一族位置一个都不消失：槽位数是
`children.size() + 1 = 1`，于是"内容开头"与"内容末尾"合成同一个流位置 `(控件, 0)`，而
**"控件之前 / 内容 / 控件之后"仍是三个互不相同的流位置**（起始边界与结束边界各占一个）。
这正是上一轮 `docs/控件边界诊断与方案.md` 里那四个缺陷的结构性解法——那时"在 `[` 与 `]` 之间"
在整数偏移里没有编码，位置会撞在一起；现在它是独立的一格。

### 流位置是模型与引擎的对接口

把整篇按深度优先遍历展开，得到一个**线性的流位置**（第 n 个元素）。方案一之后它的地位变了：
段落既然是流里的范围，**段落序号、脏段标记、行内盒子下标全部定义在流位置上**。
它不是"等价但更快的视图"，而是模型对外的第二套索引：

- 段落序号 = 该位置之前遇到的 `ParagraphMark` 个数加一。
- 脏段标记 = 流位置区间的两个端点，而不是节点 ID（节点会因前面的插入而失效，位置不会）。
- 与引擎的接口 = 流位置到"行内盒子下标"的映射，这一段几乎是恒等。

约定：**节点级 API 用 `Pos`，段级与引擎级 API 用流位置**。两者换算必须双向互逆，写进单测。

### 节点 ID

- 64 位整数，局部递增分配器持有"已用最大值"，不依赖全局随机。
- 文档内唯一，跨保存有效，所以序列化时必须落盘。
- 不回收（删除的 ID 不再复用），避免"旧引用指向新节点"。

### 标记与身份的关系

标记（粗体、颜色这类）**不带 ID**。它们是文本节点上的属性集合，随规范化自动合并拆分。
把标记也做成带 ID 的节点会让"合并相邻同格式文本"这条不变量无法成立。

带 ID 的是两类：**容器**（链接、内容控件、表格等——它们有自己的语义与属性）与
**段落标记**（段落属性挂在它身上）。段落本身不带 ID，见第二节身份类那一条。

### 区间与选区：什么进模型、什么不进

**选区不进模型。** 它是会话状态（第二节），不是文档数据。本地实测：参照项目的
`DCSelection` 虽然放在 `Dom/` 目录下，但它挂在内容元素上，序列化时与 Selection 相关的
只有 `SelectionHightlightMaskColor` 与 `SelectionTextIncludeBackgroundText` 两个**外观选项**，
选区本身一个字节都不落盘。成熟编辑器分工一致：ProseMirror 的 `Selection` 在
`EditorState` 而不在 `doc` 里，Lexical 的 `RangeSelection` 不进 document JSON。
剪贴板内容同理——那是系统剪贴板的外部格式，不是文档的一部分。

**但四样东西进模型**，缺了它们命令层会各自发明一套，改模型时全部失效：

**一是端点的形状**：两个流位置**加方向**（`anchor` 与 `focus` 分开存）。方向不是可有可无，
它决定"Shift+左"与"Shift+右"下一次从哪一端继续扩展。参照项目的选区只有
`_StartIndex + _Length`、**没有方向**，所以它表达不了这件事。端点用流位置而不是
`Pos{node, offset}`：后者里的 ID 在节点被删掉之后悬空、无法复位。

**二是位置映射（mapping）。** 位置是整数下标，所以编辑之后要有人把旧位置搬到新位置。
这件事由**步骤**负责：每个步骤提供 `map(pos, assoc) → pos`，撤销与重做走逆映射。
`assoc` 是"位置正好落在插入/删除的边界上时归左边还是右边"的约定——同一位置有两个合法
归宿时，这是唯一能表态的地方。参照项目用一个 `FixIndex()` 做同样的修正。

**三是区间原语。** 复制、剪切、删除、加粗、批量设值全都归结为两个操作：
`ExtractRange(range) → 片段`（纯读，不产生步骤）与 `DeleteRange(range)`（写，是步骤）。
步骤表里现在只有 `DeleteRange`，缺的是读的那一半。参照项目对应的也是这一对：
`content.GetRange(absStart, absLength)` 取、`deletedElements` 删。

**四是端点规范化。** 端点必须落在流元素边界上（第二节）：落在控件、表格行这类不可半分
单位内部时，**向外扩到整块边界**——选区起于某控件内部，退到该控件起点。于是
**复制出的片段永远良构**（控件边界成对同容器），这由结构保证，不靠调用方自觉。
参照项目是 `SplitElements` 拆元素再取区间；我们**不能拆控件**（拆了边界就不成对），
只能外扩——差别就在这里。

## 五、编辑操作：可逆步骤

### 步骤

```
struct Step {
  virtual void apply(Document&) const = 0;   // 应用
  virtual StepPtr inverse() const = 0;       // 逆步骤
  virtual bool applicable(const Document&) const = 0;  // 是否可应用
  void toJson(JsonWriter&) const;            // 序列化
};
```

内置步骤集合（尽量少，其余用组合表达）：

```
InsertText      在文本位置插入码点序列
DeleteRange     删除一个区间的行内内容
InsertParaMark  在位置处插入段落标记（回车分段）
RemoveParaMark  删除段落标记（段首退格、段末删除的合并）
InsertNode      插入节点（图片、公式、控件、表格）
RemoveNode      删除节点
MoveNode        移动节点
SetAttr         设置节点属性
SetMarks        设置区间标记（加粗、取消加粗）
SetStyle        设置样式引用
```

**已落地的是前六个**：`InsertText`、`DeleteRange`、`InsertParaMark`、`RemoveParaMark` 是内容级
（按流位置区间增删文本与段落标记），`InsertNode`、`RemoveNode` 是节点级（整棵子树挂上、拿下，
所以不会出现"半个控件"这种中间态）。**不用 `MoveNode`**：移动就是一个事务里的 `RemoveNode` 加
`InsertNode`，既是一个撤销单位，又不必为它单写一份位置映射；代价是被移动的子树重新分配 id ——
与粘贴一致（第七节：唯一要新分配的就是 id）。`SetAttr` / `SetMarks` / `SetStyle` 还没落地，
各按 1.5 与 1.6 的需要来。

**节点级步骤带一个"已经摘下的子树"的身份**（`InsertNode.detached` / `RemoveNode.detached`）：
构造 `InsertNode` 时先把子树物化成一棵**不在树上**的子树，于是应用、撤销与重做都是同一棵树在
挂上、拿下之间来回，节点的 id 不变。这条不是优化：控件是有身份的（宿主持着它取值与回填），
"撤销之后重造一棵内容一样的"会让外部引用全部悬空。节点也不在撤销时销毁 —— `eraseChild` 只解开
它与父节点的链，整棵子树留在池里等下一次挂回。

### 为什么是可逆步骤而不是快照

三条理由，都与本项目已有特性咬合：

**撤销不需要快照。** 撤销就是执行逆步骤。快照式撤销要保存整篇文档，对于几百段的病历

是内存与垃圾回收的负担；更要紧的是，**回退到快照会让整篇变脏**，直接击穿增量排版，

而增量是这个项目最贵的那部分资产。

**差量天然存在。** 一次编辑改了哪些节点，`Step` 自己知道。序列化的增量保存、

排版脏段标记、审计对照，都能直接吃这个信息，不必再比较前后两份文档。

**为协同留了门。** 步骤可序列化、可传输、可重放、可逆，这套东西正是 OT 与 CRDT 的输入。

本期不做协同，但结构上不挡路——这就是"留扩展位"的具体含义。

### 代价与纪律

每个步骤都要额外写逆操作，且逆操作要能通过同样的校验。这是纪律问题，靠两件事守：

- **往返判据**：`apply(step)` 之后 `apply(step.inverse())`，文档必须与之前**逐字段相同**。

  这条判据对每个步骤类型都要跑一遍，参数用随机生成。
- **规范化不与之耦合**：步骤只做最小改动，规范化（合并相邻同格式文本、清理空节点）

  在事务提交前统一跑一次。否则逆操作会还原出"未规范化"的中间态，往返判据失效。

### 事务与撤销粒度

```
Transaction = Step 序列 + 编辑前选区 + 编辑后选区 + 提交说明
```

撤销粒度就是一个事务：**一笔编辑一个撤销单位，不做合并**。事务层一度定过"相邻的同类编辑
（连续输入）并成一个单位"，但那条规则只对 `InsertText` 成立 —— 退格是另一种步骤，于是同一件
事有了两种粒度：连续敲五个字一步退掉，连续退五个字却要五步。粒度宁可细一点，也不要把两件
事并成一件。

**撤销恢复编辑前的选区。** 事务同时记下编辑前后的两份选区快照，撤销时把两份都还原，
重做则回到编辑后。只回退内容而把光标留在原地，用户看不出撤销了哪里——Word 与多数
编辑器都恢复选区。它与"位置映射"（第四节末尾）是两条互补的路：映射管**一次编辑之内**
位置的跟随，选区快照管**跨撤销单位**回到原处。

## 六、样式系统

### 三层解析

```
文档默认值（docDefaults）
  → 段落样式链（based_on 逐级继承）
  → 字符样式链
  → 元素上的内联覆盖
```

后者覆盖前者，逐属性合并。解析结果是运行期样式，**排版引擎只吃解析后的结果**，

不认识样式表。这样样式系统的复杂度不会渗进排版层。

### 三类样式

```
ParagraphStyle   字体、字号、行距、对齐、缩进、段前段后、编号、制表位
CharacterStyle   字体、字号、粗细、斜体、下划线、删除线、颜色、高亮、上下标
TableStyle       边框、底纹、单元格边距、行高列宽默认值
```

样式表存在 `Document` 上，元素只存**样式引用 + 与样式不同的那些属性**。

这一条与序列化"不写默认值"是同一个原则，直接决定病历文档的体积。

**这一条已经落进结构里（1.6）**：段落标记上挂的是 `ParaFormatPatch` 而不是完整的
`ParaFormat` —— 后者带着全部默认值，一挂上就"处处都是内联覆盖"，样式再也起不了作用。
`CharFormat` 本来就是三态的可选字段，两边的口径因此一致。解析在编译时做一次：
文档默认值 → 样式链 → 内联覆盖，出完整格式交给引擎。段落样式的字符级属性（它规定了字体）
也算进去 —— 只算字符样式会漏掉那部分。

### 为什么不做"只允许命名样式"

用户已经选了"命名样式 + 内联覆盖"。补一句代价：

内联覆盖会让"解析后的样式"依赖上下文，因此**样式解析结果必须缓存并随编辑失效**，

不能每帧重新走一遍继承链。缓存键是元素 ID 加样式表版本号，样式表一改就整体失效。

**落地形状（1.6）**：`StyleCache` 记下读到时的版本号，每次查询前对一次；不一致就整体清空。
命中与计算次数都计数 —— 判据要证明的是"第二次查不重算"，只比结果相等证明不了这一点（重算
也相等）。此外还有单元素失效：元素自己的内联覆盖改了、文本被重写了，只失效它一个，不必
惊动全篇。字符格式那一侧的缓存还要记下"上一次用的是哪个段落样式名"：同一个 run 换了所在段落
的样式就是另一份结果，键里少了这一段就会拿旧结果顶替。

**成环与未知样式名都降级而不拒绝**。`based_on` 走出环时在重复处截断并记一条诊断，链上已经
解析到的部分仍然生效；名字不存在时按已解析到的部分降级，同样记诊断。两者都不把整篇拖死，
也不能静默 —— 导入外部文档时这两种情况都会出现。

**编译侧的形状（阶段 1 第二刀）**：解析结果进引擎输入时，段落那部分进块级字段，字符那部分进
run（`FormatRun`）。两条与解析层直接相关的约定：段落样式链的字符部分**一段解析一次**
（`paragraphRunBase`），再按每个文本节点叠字符样式链与内联覆盖（`resolveRunFormatFrom`）——
逐节点重解会把"未知段落样式"按节点数重复报出来；run 以**段落默认字符格式**（就是块级字段
那组）为底、解析结果盖在上面，于是"没有字符格式的文本"的 run 恒等于段落默认，加 run 之前的
行为逐字段不变。文本段因此必须**缓存到段落结束才解析** —— 段落样式挂在结束这一段的那枚标记
上，走到文本节点时还看不到它。相邻且格式相同的文本段并成一个 run。

### 样式变更的差量

改一次段落样式，影响的是**所有引用该样式的段落**。这些段落可能散布在全篇，不是连续后缀。

所以样式变更只能按"受影响的段集合"标脏，不能复用后缀脏段机制。

这一点的正确处理方式是把脏段集合从"一个数"扩展为"一个数加一个集合"，

或者干脆在样式表版本号变化时走全量。先按全量做，测出瓶颈再优化。

## 七、表单控件

### 控件表

控件定义（类型、选项列表、格式约束）放在文档级的控件表里，节点上只存控件 id。
值内联在节点上。这样控件定义可以跨文档复用，而单份病历仍然自足。

**控件分三层，只有第一层是封闭的：**

```
结构形态    引擎能力决定，只有两种    容器型（有可寻址内部，是跨度，可跨段落标记）/ 原子型（内部没有可寻址位置，一个不可断的盒子）
业务类型    开放，字符串、可注册      text / richText / date / number / checkbox / radio / dropdownList / …
值形态      由业务类型决定，约束取值  text | bool | enum | list | resource
```

**结构形态按"内部有没有可寻址的位置"判定，不按"值放在哪里"判定** —— 那两件事正交，
把它们绑在一起会立刻自相矛盾：选择控件的值明明在属性上，可它必须是**跨度**
（标签要能逐字选中）。按结构判就不会：文本控件是容器型而值就是内容，选择控件也是容器型
（标签是它内部的内容）而值在属性上。值在内容还是属性归**值形态**管。

为什么这样分层，而不是给每种控件一个节点种类：**结构形态是引擎能力**（能不能装子节点、
占几个流位置、是不是一个带宽度不可断的盒子），它只有两种；**业务类型是文档数据**
（这个框是填日期还是填身份证号），它会一直增加，而且宿主可能自带一种。
这个分法是 OOXML 的做法——`w:sdtPr` 里 `Type` 是**所有内容控件的共同属性**，
十五种类型（Text / RichText / CheckBox / ComboBox / DropDownList / Date / Picture /
RepeatingSection / Group …）共用同一个 `w:sdt` 结构与同一套共同属性。
所以加一种业务控件是加一条数据，不是改枚举。

**控件记录的形状：共同层加类型特有层。**

```
Control {
  共同层（所有控件都有，与结构形态、业务类型都无关）
    id, key, controlType, structure, readonly, required, structureLock, hidden,
    format?, options?,       格式约束与选项来源，没有就不写
    appearance { … },        见下
    validate?                校验钩子或规则引用

  值：放在哪里由值形态决定，与结构形态无关 ——
      文本类（text / richText）的值就是它内部的内容，没有 value 字段；
      选择类（bool / 枚举值 / 选项索引 / 资源 id）的值在 value 上

  类型特有层（按 controlType 填，是可扩展的部分）
    radioButton   { value: bool, group? }   一个选项：图形加标签文字；可选 group 互斥
    checkBox      { value: bool, group? }   同上；可选 group 把这些复选构成一个集合
    radioGroup    { value }                 一个控件含多个选项，互斥，值是选中的那个
    checkBoxGroup { value }                 一个控件含多个选项，可多选，值是选中集合
    dropdownList  { options, value }        下拉，值是选中的那个（选项在弹出层里，见下面"标签"）
    button        （无特有属性）              无值：点击触发事件
    panel         （无特有属性）              无值：纯容器，内部内容即它的跨度内容
    日期与数字的 min / max / decimals 归 format 一族
    标签不在这里 —— 它是控件**内部的内容**（见下面"标签是控件内部的只读内容"那条）
}

appearance {
  width, overflow, underline, border,       结构性的：占多宽、值长了怎么办、线画在哪几边
  glyph,                                    图形：图元名 + 线宽 / 颜色 / 尺寸（内置或注册）
  align, placeholder, styleRef, invalidStyleRef
}
```

`width` 是长度值（第十一节），`overflow` 是超出显示档位，
`border` 是四边各自的边框，其余是常规样式。

**这份记录是逐步落地的，到现在落了这几项**：`key`、`controlType`、`valueShape` + `value`
（值形态与属性上的值）、`readonly`、`required`、`structureLock`、`appearance`、`validateRef`
（`src/core/doc/control_spec.h`，挂在 `Node` 上，与 `para` / `marks` 同一个理由——按流顺序取）。
`id` 就是 `Node::id`，`hidden` 已经是 `Node` 上的字段（流位置换算要看它）。还差的是业务类型
特有层的 `options` / `group` 与 `format`，它们要等 1.7 的选项控件与表格一起做，不先摆空壳。
名字不叫 `Control` 是因为引擎侧已有一个同名的旧表示（按 `TextPos` 记区间，待迁移），
两者含义不同，不能共用一个名字。

**值形态写在记录上，不由 `controlType` 现推。** 按业务类型推断默认值形态要等控件类型注册表
（宿主注册一条自带值形态），注册表给的是**默认值**，记录上这一项仍然留着。这样"记录自足"
这条不受注册表影响：换一个没有该类型注册表的宿主，文档照样知道该控件装的是什么值。

**属性入口只收四个运行时状态与策略**（`hidden` / `readonly` / `required` / `structureLock`，
见下面"值的读写"）。设计期属性不走它，标签也不走它。

**`readonly`、`required`、`format` 属于所有控件，不只属于容器型**——复选框当然也能是
只读的（审核时不许改），下拉当然也能是必填的。早先把这三个只写在容器型上，
会导致"给复选框加只读"要改表结构。同理，值的字段**统一叫 `value`**，
不再有 `checked` / `selected` / `value` 三套名字（它们指的是同一件事，差别只在值的类型），
`options` 提到共同层（带选项的不只下拉，下拉树与级联选择都要），但它**只服务"选项不进流"
的那些控件** —— 选项要显示在文档里的（单选组、复选组）把标签放在内容里，
见下一节"标签"那条。

文本、日期、数字都归容器型：日期与数字只是 `format` 的差别（格式约束，不影响存储）。
早先把 `type` 列成 `{ text, date, number, select }`，那是把控件当成了原子属性，
与"控件是跨度"彼此冲突；按结构形态与业务类型两层分开之后就不冲突了。

`setValues` 与 `getValue` 是唯一的值读写入口，按值形态各自实现：
文本类替换内部内容，选择类改 `value`。这就是"值内联 + 可回填"的落点。

**自定义控件：宿主注册一条即可。**

```
registerControlType(controlType, { structure, valueType, glyph?, validate?, default? })
```

注册一条就能用，**不改任何枚举、不重编**。边界写死一条：**结构形态只能是容器型或原子型**
——引擎不认识第三种，所以宿主自定义不了**排版行为**；能自定义的是值形态、图元、校验与
格式约束（图元的扩展路径见下面"渲染形态怎么扩展：基元、图元与自定义外观"）。
这不是限制而是分工：排版是引擎的能力，业务是宿主的能力。

导入外部文档遇到**不认识的 `controlType`**时，原样保留类型与全部属性
（与"未知属性透传"同一原则），渲染降级成按值形态画的通用输入框，并记一条诊断——
不丢数据，也不假装认识。

### 四种选择控件：单控件加 group，还是集中的多选项

单选、复选、单选组、复选组是四样东西，分属两个机制，不能互相替代。

| 控件 | 在流里的样子 | 值 | `group` |
|---|---|---|---|
| 单选 `radioButton` | **一个选项**：一个图形加一段标签文字 | 是否选中（bool） | 可选，同 group 互斥 |
| 复选 `checkBox` | **一个选项**：一个图形加一段标签文字 | 是否勾上（bool） | 可选，同 group 构成集合 |
| 单选组 `radioGroup` | **多个选项集中在这一个控件里** | 选中的那个选项值 | 不需要（自身即一组） |
| 复选组 `checkBoxGroup` | 同上，可多选 | 选中的选项值集合 | 不需要 |

**单控件与组控件的区别是布局，不是选项数量。** 单控件是"一个控件等于一个选项"，
于是可以把它们**分散**摆在文档各处——最典型的是表格每一行放一个单选，行与行之间还夹着
别的内容，再用 `group` 把它们关联成一个互斥组，表达"只能选一行"。组控件是"一个控件等于
一组选项"，选项**集中**在它内部，是通常说的多选项。

两者在表单数据上形态相同（一个字段一个值），但排版与编辑体验完全不同：前者的选项跟着
周围的内容走（可以跨单元格、跨段落），后者作为一个整体参与断行。所以这是四样东西，
不是"两个东西的两种写法"。

**四种选择控件在流里都是跨度，不是原子。** 单控件的跨度内容是"一个图形位置加一段标签
文字（码点级位置）"，组控件是"每个选项各一个图形加一段标签"。都是跨度，所以标签能被
逐字选中（见上面标签那条），选项多了也能折行。它们与文本控件的差别不在结构、在**值放在
哪里**：文本控件的值就是它的内容（可编辑），这四种的值在属性上（`value`，内容只读）。
值形态与结构形态是两个正交的维度，这一节正好是它的实例。

按第三节"控件是跨度而不是带属性的原子"，这四种同样不能做成原子：做成原子，标签就只能
画出来、不能逐字选中，也就满足不了"选区表现与普通文本一致"这条要求。

**`group` 与 `key` 是两个正交维度，不要合并。** `key` 是业务编码，管取值与回填
（多个控件同 `key` 表示同一个字段的多处副本，值同步）；`group` 只回答"这几个单选谁跟谁
互斥"——同 group 的单选最多一个选中，同 group 的复选属于同一个多选集合，但**不要求它们
是同一个字段**。一个控件可以同时有 `key` 与 `group`，也可以只有其一。合并两者看似少一个
概念，代价是"互斥"与"值同步"永远绑死，"只要互斥、不要同值"就做不到了。

**标签是控件内部的只读内容，不是另存的一份属性。** 单控件的标签、组控件每个选项的标签，
都**在控件内部**、是它内容的一部分；**改标签走控件设置，不在文档里打字**。
这样"标签能被逐字选中"不需要任何特殊机制 —— 它就是普通文本内容：

- **流位置与选区表现与普通文本完全一致，包括部分选中。** 可以拖选标签里的任意一段，
  端点落在标签内部（第 3 个字后面）也是合法位置，因为它本来就是流里的文字。
  这正是第三节"控件是跨度而不是带属性的原子"落在标签上的结果。
- **不可编辑。** 标签是控件的描述性内容，不是填进去的值，编辑动作落在这段位置上一律拒绝，
  要改就走控件设置。"能选中"是**读**的需求，"不能直接编辑"是**写**的需求，两者互不妨碍。
- **取值不含标签。** 选择控件的值在属性上（`value`），不读内容，所以标签天然不进取值；
  文本控件（值就是内容）不带内嵌标签 —— "主诉："这类前缀是控件**外面**的普通文字。
- **文本输出一致。** 纯文本复制与导出按这段位置的文字走，与选区看到的一致；
  剪贴板里的富文本那一份仍按结构化内容带走整块控件（含它的 `key` 与设置）。

若允许在文档里直接改标签，控件设置面板与文档正文就成了两条互相打架的改标签的路，
所以"不可编辑"这条是刻意的，不是还没做。

**下拉是例外。** 它的选项列表在弹出层里、本来就不进文档流，所以那份列表保持为控件数据
（`options`），不展开成内容。而**选项值与业务码的对应归宿主**（同 `fieldRef` 那条：
编辑器只搬运文字，不解释它代表什么）。

### 渲染形态怎么扩展：基元、图元与自定义外观

**会出现在纸上的内容必须由引擎绘制。** 引擎输出的光栅是打印与导出的**唯一真相源**，
叠在光栅之上的东西进不了导出——宿主画的层与引擎输出的位图是两条路。所以宿主渲染
只能做**编辑期辅助**（光标、选中框、拖拽手柄、隐藏控件的占位提示），**不承担文档内容**。

这条约束直接回答了"自定义控件能不能自定义绘制"：**能用引擎的基元组合出图形，
不能交给宿主一段绘制代码**。分两层看：

- **基元（primitive）**：引擎的绘制能力。现在只有"矩形与字形"两种
  （`fillRect` / `strokeRect` / `drawGlyph`，加 `blitMask`），连控件括号都是取 `[` / `]`
  的字形贴上去。**要补到一小组**：圆角矩形、椭圆、线段、折线（各带填充与描边），加图片。
  基元是**闭集**，随引擎版本演进——它就是"引擎能画什么"的边界。
- **图元（glyph）**：由基元构成的**具名图形**。勾选框 = 圆角矩形加一条折线勾；
  单选圈 = 椭圆加填充圆点；下拉箭头 = 折线。控件只挑一个图元并给样式：

```
glyph {
  kind,                                      图元名（字符串，指向内置或注册的图元）
  size, strokeWidth, color, activeColor, …   样式
}
引擎按 (kind, 矩形, 是否选中, 样式) 画
```

**`kind` 是字符串而不是编译期枚举**，这是刻意的：宿主注册自己的图元时不必改字段形状、
不必改格式版本。所以先把引擎的基元补齐（这是本期的事），内置图元用它们实现。

**自定义图元 = 一份配方（数据），不是一段代码。** 宿主注册图元时给的是基元组合：

```
registerGlyph(name, { primitives: [ { prim, 相对几何(0..1), 样式槽 }, … ] })
```

于是"自定义控件有独有外观"成立，而**图形仍由引擎画**——所以它进得了打印与导出，
在 native 与 wasm 两个后端也一致（同一份配方、各自的基元实现）。这条路线有现成先例：

- **PDF 的外观流**（ISO 32000-2 的 appearance stream）就是**声明式的绘制操作序列**，
  不是程序。它被写进规范的理由与我们一字不差：**不存外观，每个阅读器就各画各的**；
  存了才能在任意合规阅读器里像素一致。图片它也放不进流里，而是引用图片资源。
- **OOXML 的 DrawingML** 是同一件事分成两档：**预置几何**（187 个具名形状加调整值）
  与**自定义几何**（`a:custGeom` 的显式路径）。两者都是文档里的数据，没有一条是代码。

**凡配方表达不了的，走图片。** 签名笔迹、图表、位图 Logo 这类"任意图形"落成**图片资源**
（外置方式见第十节），引擎贴图。代价是静态、缩放与随值变化受限；收益是任意形状都能上纸。

**不允许宿主提供"决定页面内容"的绘制回调。** 三条理由：打印导出的唯一真相源是引擎光栅，
宿主叠层进不去；native 与 wasm 会不一致；文档格式会被可执行渲染绑架（与"代码不进文档"
同源）。宿主回调只能做编辑期辅助，那些本来就不该打印。

**"加控件"、"加图元"、"加基元"是三件事。** 加一种业务控件（`controlType`）不改任何枚举；
加一种**新图形**是注册一个图元（数据，宿主可做）；加一种**新绘制能力**（真正的曲线路径）
才要动引擎——那是一次引擎改动，但**不改结构形态**。结构形态回答"占多宽、能不能断、
内部有没有可寻址的位置"，对选择类控件永远是"跨度"，与图形怎么画无关。

**未知图元跳过不画、并记一条诊断**（文档里有、引擎版本没有），其余照画——与"未知属性
透传、不假装认识"同一条纪律。字形仍是**退路**不是主路：能在字体里找到的符号（`☑`、`●`、
条形码字体）可以零改动先用，但外观受字体摆布，正式的选择类控件走图元。

**还有第四件事，要单独说：数据驱动的图形（图表）。** `glyph` 与配方画的都是**静态图形** ——
形状由基元与几何决定，与数据无关。而体温单这类"坐标纸加折线"是**数据到几何的映射**：
把"08:00 的 38.5 ℃"落到坐标系里一个点，再把相邻点连成折线，还要按来源换点形（口温 ●、
腋温 ✕、肛温 ○、耳温 △）。这不是图元能表达的东西，而是引擎的**另一种绘制能力**：

| | 画的是什么 | 数据的作用 |
|---|---|---|
| 图元 / 配方 | 静态图形（勾选框、星形、箭头） | 只有"选中 / 未选中"这类少量状态 |
| 图表 | 数据驱动的图形（曲线、散点、柱） | 每个数据点决定几何 |

OOXML 正是这么分的：**图表从来不是"一个形状"**，它有自己的部件（`xl/charts/chart1.xml`）、
自己的命名空间与内容类型，模型是"数据源 → 序列 → 坐标轴 → 绘图区"；在 Word 里它的数据
还另存为一个内嵌的工作簿部件。我们的对应物更简单：**值就是序列数据**，不需要内嵌工作簿。

**体温单这个例子要分清三件事：**

- **它是数据驱动的图形，不是图元组合。** 静态配方画得出一张**定格的**体温单，但数据一变
  （补录一次体温）就得重画整份配方 —— 那退化成"把图存下来"，不是控件。
- **不要用表格当坐标纸。** 体温单的格子是**图的坐标系**（行高列宽由刻度决定），不是数据
  容器；用表格实现会被"列绑定等于字段""数据行不允许合并"这些表格规则绑住，还会让折线跨过
  单元格 —— 而跨单元格的线不是任何一格的内容。
- **它仍然是一个普通控件。** 块级跨度，值是序列数据，外观是轴与样式的配置。**文档模型一行
  不改** —— 流位置、光标、选区、命中、序列化、事件全都不变；要动的是引擎新增一种绘制能力。

**本期不做**，边界先定：图表是引擎的**独立绘制能力**（与图元平行），不是图元的特例；
与交互的接法是 `click` 事件的上下文里带**命中的数据点**（宿主据此编辑那一个点的值）。

### 按钮与容器：不承载值的控件

`button` 与 `panel` 是两类"不是表单字段"的控件：它们不参与取值与回填，
但在文档里有身份、有外观、能被处理函数按 key 引用。

- **`button`**：一个可点的按钮，没有值、也没有特有属性 ——
  点它不改文档，而是触发 `click` 事件（见下一节）。在流里的形态与选择控件一样是
  **跨度**（图形加标签文字），标签同样可被逐字选中。
- **`panel`**：一个**纯容器**，用途是把一段内容包起来，好整体操作。它没有值
  （内部内容就是它的跨度内容），也没有特有属性；有用的东西都在共同层：
  `hidden`（整块隐藏）、`key`（供处理函数引用）、`appearance`（边框、背景）。

**`panel` 的存在理由就是"一个区域整体切换"这种场景**：发起会诊时会诊答复区域要整块隐藏，
而那个区域里有段落、有其它控件。用 `hidden` 一条就够——第七节已定"隐藏容器型控件时
整棵子树一起摘除"，所以不需要给内部每个元素各设一次。`panel` 不必有别的能力：
它解决的是**分组与批量操作**，不是新的内容类型。

**`key` 在这两类控件上是"标识"而不是"字段编码"。** 它们仍用 `key` 被处理函数引用
（`setPropertiesByKey(…)`、`setValuesByKey(…)`），但不会被当成表单字段导出——
`listControls()` 的描述里带 `controlType`，宿主按类型决定该不该取它的值。

### 控件的外观

**固定宽度（`width`）。** 病历表单里"体温 \[____\] ℃"的底线长度必须恒定，否则值为空时
控件塌成零宽、后面的内容跟着往前跑。所以它表达的是**占位宽度**，与值的长短无关。三条约束：

- **宽度与输入上限是两件事，要分开存**：`width` 是显示宽度（长度值，见第十一节），
  `maxLength` 是编辑动作的输入上限（落在控件声明上，由编辑能力表读）。
  常见组合是两者相等，但不等的时候更多——住院号栏可以固定 6 字符宽却允许输入 10 位。
- **长度类型要加一档 `Chars(n)`**，不能拿 `Em(n)` 代替。中文全角字是 1 em，
  但数字与字母是半角（约 0.5 em），"3 个字符宽"在数字字段上会算成一半。
  `Chars(n)` 表示"n 个全角字符位"，与文档网格的"每行多少字"是同一个度量。
- **它是引擎侧的新增约束。** 第十四节说边界元素"有宽度"（参照项目取
  `max(宽度, 12.5)`，保证鼠标点得着）；固定宽度比那条更强，它是**指定的**宽度。

**值超出固定宽度（`overflow`，属性配置）。** 三种处理方式做成一个属性，
因为同一条病历里不同字段的诉求本就不同——体温底线必须恒定宽度，
诊断名称则希望整条看得见。三档取值与各自的排版后果：

| `overflow` | 值超过 `width` 时 | 后果 |
|---|---|---|
| `expand`（撑开） | 宽度是下限，框跟着值变宽 | 断行与后续内容位置随之改变；不丢数据、不遮字 |
| `clip`（裁切） | 框宽不变，超出部分不绘制 | 值完整但看不见；要求 `maxLength` 保证"能输入的放得下"，否则记诊断 |
| `spill`（溢出） | 框宽不变，超出部分照常绘制 | 值看得见，但可能盖住后面的内容 |

默认 `expand`——不静默丢数据。`clip` 只用在"`format` 或 `maxLength` 已把长度限死、
overflow 只是防御性兜底"的字段上；否则会出现"值存在、光标能进去、屏幕上却什么都看不见"
的状态，这种组合列出诊断，不靠纪律。

**不做控件内横向滚动。** 控件是流里的跨度，不是带滚动视口的盒子，
没有自己的滚动位置，也没有滚动条。值超出只有上面三档处理：
要么已按 `expand` 排开占位，要么被裁掉不再绘制。
"把超长的那一段横向滚动出来看"这个说法不成立，它对应的状态在这里不存在。

**下划线（`underline`）。** 三档：仅空白处显示（Word 表单域的经典做法，文字下面有线、
空着的地方也有线）、整段显示、无。

要紧的是它与**字符的 `underline` 标记不是一回事**：

| | 由谁决定 | 编辑之后 |
|---|---|---|
| 控件下划线 | 控件身份，是边界装饰 | 不变（只要控件还在） |
| 字符下划线标记 | 内容上的 marks 区间 | 跟着文字走，可能延续也可能消失 |

混淆会产生一个怪现象：给控件勾了下划线，实际变成给内容加了一堆标记，删掉文字后线也跟着没了。
实现上控件下划线是**编译到引擎时挂在边界盒子上的装饰**，不进 marks、也不进内容
（它作为 `appearance.underline` 属性随控件落盘，见下）。

**边框（`border`）。** 四边各自独立，缺省表示，该边不画：

```
border { left?, right?, top?, bottom? }
Border { style ∈ { none, solid, dashed, dotted }, width, color }
```

三条要点：

- **与下划线同源，但不合并。** 两者都是挂在边界盒子上的装饰，都不进 marks、不进文档内容；
  差别在下划线有"仅空白处也显示"的档位语义，普通边框没有，所以下划线独立保留。
- **边框与下划线都进序列化。** 两者都是作者设定的外观（要打印、要保存）；
  `placeholder` 同样落盘（见下），只有校验状态不落盘。
- **四边独立而不是"边框开关加统一宽度"。** 病历表单常见只画下边（填空线）、
  或只画左右边（栏位分隔），统一边框表达不了这两种。

**`placeholder` 落盘，但它是独立字段、不进内容。** 提示文字是**作者设定的**
（"请填写住院号"），属于设计的一部分，所以写进文件——与 `hidden` 同理，默认值必须存得住。
它**不是内容**：值存在内容或 `value` 上，提示文字存在自己的字段里，所以 `getValue`
不会把它当成值取出来。早先"不进文档"的顾虑（怕取值取到提示文字）只来自"把它当内容存"，
放在独立字段上就不存在。
**只读与打印模式不绘制 `placeholder`**，否则空白字段会把提示文字一起打印出来——
这是渲染策略，与它落不落盘无关。

### 隐藏：只在编辑模式下不生效的显示策略

`hidden` 是控件的**落盘属性**，表达**作者设定的默认可见性**——表单里有些字段默认隐藏
（什么时候显示由业务逻辑在运行时决定），有些默认显示，这个初始值是设计的一部分，
所以要存进文档。它既不是"画成透明的"，也不是"所有模式都不占位"，
而是**按模式生效的显示策略**：

| 模式 | 隐藏的控件 |
|---|---|
| 编辑 | **照常显示**：参与排版、占位置、可选中可编辑 |
| 表单 | 不显示、不占位、不可选中 |
| 只读 / 打印 | 与表单模式相同（打印是给最终用户的，隐藏字段不该出现在纸上） |

**编辑模式必须不生效**，否则作者没法选中它去编辑、也没法把它改回可见。
三种模式里只有编辑模式看得见隐藏控件，这是它们唯一的分歧点。

**落盘的是默认可见性；运行时要改它就是一次普通编辑。** 宿主按业务逻辑改变可见性时
（"性别选了男就不显示孕产史"），改的就是这个属性，所以它进撤销栈、也会落盘。
若宿主只想做"本次会话临时隐藏"、不希望污染文档，应该在它自己的表单逻辑层过滤，
不要把 `hidden` 当临时状态用。这与 `validationState` 正好相反：那个是纯运行时状态、
**不落盘**（否则会出现"上次的红框被打印出来"），而这个**必须落盘**（默认可见性
是设计的一部分）。

**"不占位"的代价要写清。** 在表单与只读模式下，隐藏控件是**从流里摘除**的
（不是"占位但零宽"——零宽会让它成为"存在却永远到不了的位置"，比摘除更怪）。
代价是：**同一份文档在编辑模式与表单模式下的流位置与段落序号不同**，
所以切模式要重排一次，位置换算要带模式参数。这是"不占位"的必然代价，不是实现瑕疵。

**隐藏容器型控件时整棵子树一起摘除。** 子树里的段落标记也随之不在流里，所以
**段落数与流位置都会变**。依赖段落号的判据（脏段标记）必须按"结构变了"处理，
不能假设它们稳定。

**它是结构性编辑，不是外观改动。** 切换 `hidden` 改变流结构（在表单与只读模式下多一个
或少一个元素），所以要标脏、重排、产生一个可撤销的步骤——与插入删除同一类。
编辑模式下改它不改变版面，但它仍是一次编辑，同样进撤销栈。

**找得到它这件事不成问题。** 隐藏只在非编辑模式生效，所以"隐藏之后找不到它"
不存在——切回编辑模式就能选中它。将来若要在表单模式下也看见隐藏控件（设计或排错用），
可以加一个辅助查看开关，但那属于视图工具，不是 `hidden` 的语义。

**隐藏的字段默认不参与必填校验。** 用户根本填不了，若还拦提交，表单会永远提交不过去。
这一条只约束默认行为——宿主在自己的校验里想让它仍然必填（隐藏字段由程序回填），
那是宿主的选择。

**取值与列控件不受隐藏影响。** `getValue(id)`、`getValues()`、`listControls()` 照常把它
包含在内（`listControls()` 的描述里带 `hidden`，宿主按需决定怎么用）。隐藏只改变
"它在不在版面里"，不改变"它有没有值"。

### key 是业务编码，不要求唯一

`key` 是业务编码（比如 `chief_complaint`），**同一文档里可以有多个控件用同一个 key**，
且不随编辑改变。它与 `id` 的分工是：

- `id` 是模型内部身份，文档内唯一，随节点走，用于位置、引用、撤销。
- `key` 是业务编码，**可重复**，用于按字段取数、回填、导出，以及与外部系统的字段映射。

**同一个 key 绑多个控件，就是正文与页脚镜像同一个字段的做法。** 页脚要显示姓名，
不是放一个"去正文取值"的占位符，而是**再放一个普通控件、填同一个 key**：

```
正文  患者：[张三]      key = patient_name
页脚  姓名：[张三]      key = patient_name     ← 同一个 key
```

按 `key` 批量设值，两处一起更新，所以不存在"两份数据对不上"的问题——
它们本来就是同一个字段的两处显示。

**同 key 的多个控件，值不保证一致，但不静默。** 按 `id` 设值只改那一个控件；
按 `key` 批量设值一次改掉全部。宿主决定何时同步（常见做法是一次编辑结束后按 key 刷一次）。
按 `key` 取值时若发现同 key 的值不一致，记一条**可发现的信号**（按 key 去重、不弹窗、
不阻塞），而不是静默取一个。理由与别处一致：不一致是合法状态，但用户与宿主都该能发现它。

**粘贴时不需要重命名 `key`。** 复制一律带控件身份（`key`、`readonly`、结构操作开关、
外观），而 `key` 本来就可以重复，所以剪切（同文档内移动）与复制粘贴都**保留 `key`**；
唯一要新分配的是 `id`，而 `id` 本来就是每个节点自动分配的。
早先那三条规则（剪切保留、同文档复制重命名、跨文档按冲突重命名）在这里全部作废——
它们依赖"key 唯一"这个前提，而那个前提已经不成立。

### 值的读写：内容即值、控件索引、批量

**内容即值。** 容器型控件没有"值字段"，它的值就是它内部那段内容。只有一份真相，
不存在"值属性与内容不一致"这类错误。代价是**读取要遍历**（拼接规则见下面
"嵌套控件"一节），于是下面"控件索引"这条变成必需项。

**控件索引。** 文档里维护三张表：`id → 控件`、`key → 控件列表`、`控件 → 内容位置`，
随编辑步骤**增量更新**。注意第二张是**一对多**——同一个 key 可以有多个控件，
这是"编码非唯一"的直接后果。这条不是优化而是必需：**"列出全部控件"与"按 key 批量取值"
如果每次全篇扫描，性能与老编辑器一样差**。差别不在 API 形状，在有没有索引。
索引维护挂在编辑步骤上，不做手工同步。

**批量读写。** 分两组：**值**（可编辑内容，填进去的东西）与**属性**（控件自己的状态与策略）。
两者形状对称，都按 `id` 精确或按 `key` 覆盖同编码的全部，都合成一个事务。

```
listControls()                           控件描述数组（id / key / controlType / value / readonly / required / hidden）
getValue(id) / getValues(ids?)           取单个 / 一次取全部或指定几个的值
getProperties(ids?)                      读回属性（hidden / readonly / required / structureLock）
setValues([{ id, value }, …])            按控件 id 批量设值，只改指定控件
setValuesByKey([{ key, value }, …])      按业务编码批量设值，每个 key 覆盖其全部同编码的控件
setProperties([{ id, props }, …])        按控件 id 批量设属性
setPropertiesByKey([{ key, props }, …])  按业务编码批量设属性，同上（改掉所有同 key 的控件）
```

按 `id` 与按 `key` 是两条独立的路：前者精确到控件实例（只改正文那一处），
后者一次覆盖同 key 的全部（正文与页脚一起改）。**四个 setter 的入参都是数组，数组本身就是批量** ——
按 key 的也一样，一次给多个 key 赋值（"回填患者信息"要把姓名、住院号、性别一起刷）。
同一次调用里同一个目标出现多次时，按出现顺序**后者覆盖前者**（与逐条调用一致）；
要按 `id` 与按 `key` 混着设，用 `beginBatch` / `commitBatch` 包住两次调用。

**属性入口只收"运行时状态与策略"这四个**：`hidden`、`readonly`、`required`、`structureLock`。
设计期属性（`controlType`、`format`、`options`、`appearance`）不走它 —— 改它们等于重新定义
控件（可能改变取值形态、要重建节点），属于设计操作，不该由表单模式下的脚本或回填流程触发。
**标签也不走它**：标签是控件内容，改它是改内容，走正常编辑步骤。

**`hidden` 与其余三个不同类。** 切换它**改变流结构**（摘除子树、段落数变化），所以含 `hidden`
的批次要重排；只改 `readonly` / `required` / `structureLock` 的批次不重排。两类混在一批时按
"含 `hidden` 就重排"处理，**仍然是同一个撤销步骤**。

**值与属性可以在同一批里设。** 联动的典型形状是"勾了'有过敏史'就显示过敏原字段并清空它" ——
一条值加一条属性，用 `beginBatch` / `commitBatch` 包住两次调用即可，不必再引入第三个合并 API。

批量设值与批量设属性共用的价值不是"少几次函数调用"，而是**合成一个事务**：一次编译、
一次标脏、一次排版、一次上屏、一个撤销步骤。判据写死三条，两组共用 —— **设 1000 个字段与设
1 个字段耗时同一量级**、**只产生 1 个撤销步骤**、**最终帧与"逐个在独立事务里设置"逐像素一致**
（前两条看性能，第三条守正确性）。

**句柄用 id 与 key，不用节点引用。** `listControls()` 返回的是轻量描述，不是活的节点指针——
节点会因编辑失效（位置平移、分裂与合并）。这里顺带澄清一个说法：**所有控件都是跨度、不是叶子**
（标签是它们内部可寻址的内容，见上面"标签是控件内部的只读内容"那条），真正是叶子的是
图片、公式这类**非控件原子**。对外 API 对控件完全一致，宿主不需要知道"文本控件的值是内容、
复选框的值是属性"——这正是门面层的价值。

**批量设值有一个必须提前知道的代价。** 它会让脏区**散布全篇**（100 个字段分布在各页），
而当前的 `layout_dirty_from_` 是"连成一段的后缀"。这是第六节末尾那个风险
（样式变更的散布式改动）的**第一个真实用例**，也是它从"将来可能"变成"马上就要遇到"的地方。
两条路：先退化全量（正确但慢），或把脏段标记从"一个数"扩展成集合。
建议先测出真实数字再定，别提前设计。

### 嵌套控件：取值递归、设值拒绝

控件内部可以再嵌控件（"一栏"里既有静态文字又有子字段）。这种嵌套的取值与设值各有一条
规则，方向相反。

**取值递归：把里面的文字全取出来。** 对**值即内容的控件**（文本类），`getValue(id)`
返回该控件**整棵子树**的可见文字，按文档顺序拼接，**包括嵌套控件内部的文字**
（选择类控件的值在属性上，不走这条）：

```
外层 key = summary 的内容    主诉：[反复心悸]        ← 内层控件 key = duration
getValue(summary) = "主诉：反复心悸"
```

所以对外层取值不是"只取它直接拥有的那段文字"，而是"取它里面显示的整段内容"。这样取出来的
东西与用户看到的、将来打印出来的一致，导出时不会出现"外层值缺了内层那一截"。

拼接规则按元素类型定：文本节点贡献它的文字，段落标记贡献一个换行（否则多段控件取出来会粘成
一行），嵌套控件的内部内容（单控件的标签、组控件的选项标签）**按普通文本取出**，
真原子按它的**文本表示**取（域是缓存值，制表符是制表符，图片与公式暂为空，要的话将来给
替代文本）。**取值与选区复制走同一套规则**：两者用同一份文字，所以"复制出来的内容"与
"取值取到的内容"不会不一致——这是它们将来不会各写一套的依据。

**设值要求内部是纯文本。** 内部含**子控件**时，整体设值（`setValues`、`setValuesByKey`）
一律**拒绝并给原因**，不静默把子控件冲掉：

```
setValues([{ id: summary, value: "x" }])  →  Deny("控件内含嵌套字段，不能整体设值")
```

理由是这条动作是破坏性的：整体替换内容会把里面的子控件连同它们的 `key`、值、校验设置一起
删掉，而调用方通常只是想改一段文字。要改这类控件，只能**分别设内层控件的值**，或者先删掉
内层控件再整体设值——两条路都要显式做，不做隐式补救。

判据与"越界编辑拒绝并给原因"统一：**拒绝带原因，且不产生任何编辑步骤**（文档逐字段不变）。
图片、公式这类不可半分的原子落在同一个判据下——内部只要不是纯文本就拒绝整体设值，
理由相同（整体替换会把它们静默删掉）。它们到阶段 4 才落地，届时不另立规则。

**钩子只对"编辑动作的目标控件"生效。** 内层控件的值被改时，外层的取值结果跟着变
（因为取值递归），但外层**不会**因此触发 `beforeChange` / `afterChange`——钩子认的是被直接
编辑的那个控件，不是"取值结果受影响的全部控件"。否则嵌一层就触发一串钩子，顺序与取消语义
都会变复杂。宿主若需要感知外层，收到内层通知后按 key 重取一次即可。

### 事件：绑定是数据，代码与执行归宿主

控件可以绑**事件**，形状是一张"触发器到处理函数名"的表：

```
events? {
  change?                                 值变化（选择类与文本类）
  click? dblclick? mousedown? mouseup?   鼠标
  keydown? keyup?                        键盘
  focus? blur?                           焦点
  afterSelect?                           选区落到这个控件上之后
}
每个值是一个处理函数名（字符串），指向宿主侧的代码
```

事件名这张表**不封闭** —— 宿主可以定义自己的触发器（选择器弹出、附件上传完之类），
编辑器只要求"名字到处理函数名"这个形状一致。

**核心结论：编辑器存绑定，不存可执行代码正文。** 截图上那种"事件只保存一个方法名、
正文写在代码区"的设计（WinForm 设计器也是同一形状）恰好给出判据 —— 它把事件拆成两件东西：

| 组成 | 是什么 | 归属 | 随文档 |
|---|---|---|---|
| 绑定（哪个控件的哪个事件 → 哪个处理函数） | 数据 | 编辑器 | 是 |
| 代码正文（处理函数里写什么） | 程序 | 宿主 | 否 |

WinForm 里这两件都编进**同一个应用**，所以"只存方法名"够用 —— 它没有"文档要能脱离应用
单独打开"这个前提。我们的表单有：模板会跨宿主、跨机构流转，只带一个方法名的文档到了别的
宿主上，事件什么也不做。**这是这套分工的代价，接受它** —— 行为随宿主走，文档只描述"该在
什么时候通知谁"。要让它连行为一起带走，就得把代码正文写进文档，那正是下面要避免的。

**代码不进文档，三条依据：**

- **执行环境本来就该在宿主。** 只有宿主知道自己能提供什么沙箱、什么白名单、当前登录的人
  有没有权限。文档里躺着一段可执行代码、由视图层去运行，是宏病毒的经典形态。
- **行业在往"代码离开文档"走，证据就是 Office。** VBA 宏与文档同权限（能读写本机文件与
  注册表），管理上只有"全禁 / 全开 / 只准签名"三档粗粒度，出了事隔离不了单个宏；
  Office Scripts 换成**只能操作文档的沙箱**、拿不到用户令牌、能按租户或用户组开关、有审计
  日志。这条演进正是"代码与执行收进宿主"的过程。
- **Office Scripts 干脆取消了事件**（只支持手动或流触发的"跑完即止"）。这说明脚本化的事件
  响应本身就是治理难题 —— 我们保留事件，但把它绑到宿主注册的处理函数上，正是为了既留住
  事件、又不让文档携带代码。

**编辑器要提供三样东西，缺一样这套机制就落不了地：**

- **绑定的数据形状**（上面那张表），外加派发：触发器命中时把
  `{ controlId, key, eventName, value, source, context }` 交给宿主。
- **一个稳定的脚本 API 面**（白名单）：`getValue` / `setValuesByKey` / `setPropertiesByKey` /
  `focusControl` / `addTableRow` 之类 —— 值、属性、焦点、结构操作各留少量入口。处理函数通过
  这些操作改文档，**不持有控件引用、不直接碰节点**。截图里那种按变量名抓另一个控件的写法
  （`BAX311.setVisible(false)`）在这套口径下应写成
  `setPropertiesByKey([{ key: 'BAX311', props: { hidden: true } }])` —— 理由与"句柄用 id 与 key、不用节点引用"
  一致：按 key 操作才能在编辑之后仍然有效。
- **派发的两条纪律**：整次派发**包在一个批里**（处理函数里改十个值，仍只产生一个撤销步骤）；
  **抑制重入**（由派发引起的值变化不再触发事件，否则"改了 A 触发改 B、B 又触发改 A"会自成
  死循环）。

**编辑器不提供：代码编辑器、脚本执行、语法检查。** 那不在它的职责里 —— 写不出 IDE 该有的
东西（高亮、报错、断点），做了也没法负责。宿主若要一个代码区（像截图那样），它自己接一个
（CodeMirror、Monaco 之类），编辑器只管把绑定与 API 面交出去。

**两条纪律：**

- **只在表单模式生效。** 编辑模式是设计态（点控件是选中它，不是触发它），
  只读模式不响应输入（第七节已定）。
- **不绕过事务层。** 处理函数改文档都走正常编辑 API，因此产生编辑步骤、可以撤销。

**与 `beforeChange` / `afterChange` 的分工**：那两个是**命令式**的宿主回调
（宿主初始化时注册，管全部控件、适合全局策略）；`events` 是**声明式**的控件属性
（作者在设计器里给某个控件配上，随文档走），适合"某个字段的局部逻辑"。
两者不冲突，也不要互相替代。

**可复用判据：绑定是数据、代码是程序 —— 凡是"换一个宿主仍要生效"的，只能是数据。**
本设计里行为不随文档走，是这笔取舍的结果，不是缺陷。

### 与业务交互：校验钩子、异步裁决与批次

**结论先说：钩子允许异步，但语义是"持有候选变更，裁决通过才应用"，
不是"先应用，结果回来再回滚"。** 这两者体验差别极大——后者就是"先勾上、再弹回去"，
是必须避免的那一帧。异步本身不是问题，"乐观应用加回滚"才是。

**校验钩子的形状。**

```
beforeChange(change) → Decision | Promise<Decision>
  change   = { controlId, key, oldValue, newValue, source: user | program }
  Decision = Allow | Deny(reason)
```

宿主返回同步的 `Decision` 时走**原路径**：判定、应用、产生一个撤销步骤，
中间不多出任何帧，也没有额外状态。返回 Promise（含 `async` 函数）时，编辑器**悲观持有**：

- 交互先产生一个**候选变更**，它放在文档之外。文档不变、撤销栈不变、不排版也不上屏。
- 控件进入 `pending` 展示（样式可配，比如浅灰边框），**不显示新值**。
  用户因此看不到"已经勾上了"，也就没有"勾上再撤销"那一帧。
- 结果到达后：`Allow` 把候选变更当普通事务应用（此时才产生撤销步骤、才排版上屏）；
  `Deny` 丢弃候选变更，值保持原样，并按下面的校验状态显示原因。

四条约束管住等待期间的状态：

- **同一控件再次交互时取消前一次等待**（最后交互为准）。旧 Promise 的结果到达时
  按"已取消"丢弃，不产生任何应用，也不误报失败。
- **目标区间失效就丢弃。** 等待期间文档可能被别的编辑改过（控件被删除、段落被合并）。
  结果到达时先确认锚点仍指向同一个控件，失效则丢弃，不做补偿动作。
- **超时按拒绝处理，不静默放行。** 钩子可配 `timeout`（默认给一个保守值，比如 5 秒），
  超时判 `Deny("校验超时")`，值保持原样，用户再点一次即可。
  放行一颗从未校验过的复选框，比不放行更危险。
- **钩子内禁止调用任何编辑 API**（会重入当前事务），与同步路径同一条纪律。

**只拦用户交互，不拦编程设值**（`source` 区分）。回填时顺序上可能先填空的，
被"必填"卡住就是错的；宿主自己发起的 `setValues` 由宿主自己负责。
这条同时保证了**批量路径完全同步**：`setValues` 是 `program` 源、不进钩子，
所以批次里不会出现"一半在等异步、一半已提交"的混合状态。

**返回拒绝原因，不只是"是否允许"。** ProseMirror 的对应机制是
`filterTransaction(tr, state) → boolean`（事务应用前调用，返回 false 即取消），
但它有一个社区讨论多年的短板：**被取消的事务没有回执**——宿主想在用户面前提示
"这一项现在不能勾"，只能把副作用塞进过滤函数里，破坏它的纯函数性。
我们的钩子返回原因，且原因是给用户看的文案，不是给日志看的错误码。

### 校验状态与样式提示

校验的产出不止"拦不拦"，还有"当前这一项对不对"。这份状态是**运行时的**：

```
validationState ∈ { none, pending, invalid }     每个控件一份
validation { state, message }
```

- `pending` 就是异步等待期间的状态；`invalid` 由 `Deny` 自动置位，
  也可由宿主主动置位——API `setValidation(keys, state, message)`。
  主动置位这条是必需的：异步校验的结果有时晚于一次编辑，
  宿主拿到结果时已经没有对应的事务了。
- **样式提示走外观。** `appearance.invalidStyleRef` 指向一套样式（红框、红底、
  波浪下划线等），渲染层按它画。模型只存"状态、提示文字、用哪套样式"，不存怎么画。
- **不落盘：** 它是"这次会话里这一次校验的结果"，
  不是文档内容，重新打开由宿主重算。若存进文档，
  会出现"上次的红框被打印出来"这类错误。
- **只读与打印模式下不画 `pending` 与 `invalid` 的样式**（除非导出审核版），
  与 `placeholder` 同一处理。

### 通知类回调

`afterChange`（值已变更的通知）不参与决策，因此它不该阻塞编辑：
事务提交后把通知排到任务队列执行。三条纪律：回调里抛错不影响文档；
回调里要发起编辑必须开新事务（不能重入）；
`setValues` 返回一个可等待的批次结果，宿主 `await` 它就能串起"设值完成再提示"这类流程。

**交互被拒也走通知。** 落点被拒、编辑被拒、越界点击这些"交互本身没成立"的情形，
编辑器**不在界面里做任何提示**（不弹、不闪、不改外观），而是交给宿主：
`onBlockedInteraction({ kind, pos, controlKey?, reason })`，`kind` 区分点击落点 /
方向键 / Tab / 编辑 / 结构操作。纪律与 `afterChange` 一致：排任务队列、不阻塞输入、
回调里抛错不影响编辑。**此外必须去重**：按住方向键或连点会让同一处越界每秒触发几十次，
同一 `kind` 在同一个位置上的连续触发只报一次，位置或 `kind` 变了才再报。
它与 `beforeChange` 的 `Deny(reason)` 分工不同：那个是"值变更被拒"（已产生变更候选），
这个是"交互本身被拒"（值根本没轮到变更）。

分工要说清：**校验钩子决定"能不能改"；通知回调有两类——"改完了告诉你"（`afterChange`）
与"这次交互没成立"（`onBlockedInteraction`），都不参与决策，也都不由编辑器渲染提示。**
把校验逻辑塞进通知回调，等于默认变更已经生效，就退回"先应用再回滚"那条路了。

### 批次

`setValues` / `setProperties` 与"回填整篇病历"走同一条路：

```
beginBatch() … 期间只改模型，不编译、不排版、不上屏 … commitBatch()
```

提交时把批次内所有变更合成**一个事务**，然后才编译、标脏、排版、上屏各一次。
这是性能需求的正解——老编辑器"循环调用性能差"的根因不是函数调用开销，
而是**每次设值都触发了一次完整的重排与上屏**。在这个项目里上屏占端到端八成以上
（敲一个字 1.96 ms 里排版只占 0.16 ms），所以批量能力必须做在"抑制中间的上屏"这一层，
而不是"少调几次函数"这一层。

### 患者信息就是控件值

患者姓名、住院号、性别、年龄这些**不是域**（见第八节），而是绑定了业务 key 的控件值。
更新有两条路径：按 `id` 的 `setValues([{ id, value }])` 与按 `key` 的 `setValuesByKey([{ key, value }])`。
页眉页脚要显示时**放一个同 key 的控件**（见上面"key 是业务编码"一节），
两处由同一次批量设值一起更新。这样不需要"数据源"这个额外概念，
也不必让域去理解业务字段，连"值引用"这个机制都不需要。

### 三模式是策略，不是三套控件

沿用现有的 `EditMode` 三档与 `edit_capability` 的落点判定（`canEditAt` / `canEditRange`），
扩展成"能力裁剪表"：

| 模式 | 光标（插入点） | 编辑        | 隐藏控件 |
| -- | --------- | --------- | --------- |
| 编辑 | 全部        | 全部        | 显示（参与排版） |
| 表单 | **只在可编辑控件的内容里** | 只有在可编辑控件内插入删除 | 摘除（不显示、不占位） |
| 只读 | **一个都不出现** | 一律拒绝      | 摘除（同表单） |

要点：三种模式都**不改文档结构**，只在三处裁能力 ——"光标能不能停在这一点"、"能不能编辑"、
以及"隐藏的控件是否参与流"（第三项是唯一会动到流位置的：表单与只读下隐藏子树整棵摘除，
位置换算因此要带模式参数，见上一节），
所以是策略而不是三套控件。**选区与复制在三种模式下都不受限**：Shift 扩展、鼠标拖拽、
双击选词、三击选段、全选都可以跨出控件；核对上文与复制是病历的刚需。

**选区与光标是两件事。** 选区是"读到哪一段"的高亮，光标是"字会打进哪里"的插入点。
同一份 `Range` 里 anchor/focus 可以落在任何位置，而插入点只存在于能打字的地方：

- **表单模式的插入点只在可编辑集合内**。点击、方向键普通移动、Home/End 的落点若在控件
  之外，就收束回"移动之前所在那个控件"的内容区间 —— 视觉上是"停在字段边界上"，而不是
  把光标摆到一个打不进字的地方。方向键因此走不出字段；换字段用 Tab 或鼠标。
  **嵌套时每一层都要走得到**：三枚空控件套在一起（`[[[]]]`）时六枚括号压在同一处偏移上，
  内层的内容区间退化成一点，往外的每一层各占"开括号之后"到"闭括号之前"的一段；光标
  逐格往外走到最外层的内容末尾才停住。
- **只读模式一个插入点都没有**：点击照旧建立选区（要能选、能复制），但光标不画，
  也不接受任何编辑。它是呈现与打印态，插一条竖线在那里只会让人以为能改。
- **选区自由**：拖选、Shift 扩展、全选都能跨出控件，端点落在只读区也照样高亮。
- **编辑动作的落点必须在可编辑集合内**：越界就拒绝并给出原因（接在 `Deny(reason)`
  的回执上），**不静默把范围裁到可编辑部分**——静默裁剪会让用户以为整段被删掉。
- **表单模式的删除不越过控件边界**：退格 / 前删只在光标所在控件的内容里进行，
  空控件不删、括号不碰、光标不被带出字段；选区删除要求整个区间落在同一个控件内。
  括号那四条"进出字段"的规则属于文档模式（设计态要能删空字段、能一层层进出）。

**Tab 是唯一按"可编辑"选目标的移动键**：它在可编辑控件之间前进 / 后退（`tabFrom`），
判据是"控件的内容起点在可编辑集合内"，到最后一个就放行给宿主，不绕回第一个。
方向键不做这件事 —— 它一次跨一枚簇，但只在可插入位置之间走（见上）。

**可编辑集合是一个交集，不是"在某个控件内即可编辑"**：只读控件里再嵌一个可编辑控件，
那个内层位置**仍然不可编辑**。写成不变量见第二节。

不要把这条限制做到文档结构上：**它只是一个作用于光标落点的谓词**，不要为表单模式造
一个"只剩可编辑部分的视图"。段落、命中、坐标与脏段都建立在"流是完整的"这个前提上，
挖掉一块会让模型与排版输入不一致。

**别把它和 `hidden` 混成一件事。** 两者的区别是"这个位置能不能放光标"与"这个元素在不在流里"：

- **可编辑集合是谓词**：结构不动，只是"落在不可编辑处不移动光标、越界编辑被拒"。
- **`hidden` 是作者声明的属性**：非编辑模式下它确实把子树从流里摘除，**代价明确**
  ——流位置与段落序号随模式变，所以位置换算要带模式参数、切模式要重排一次。
  这笔代价是记账的，不是偷挖一块。

**区间查询只有一个面。** 控件在模型里不是容器节点（一段文字区间加流里的两枚括号占位），
于是"它的区间在哪、这一格归谁"引擎、编辑命令与光标解析三处都要问。各写一套必然在边界
上分家：同一个偏移压着六枚括号时（三枚空控件套起来），按"括号排布 + 第几格"反推的那一套
会把三层内容区间缩成一个点，症状是光标进得去最内层、往右一格走不动。现在统一走
`control_spans.h`：区间只从流索引取（`FlowIndex::intervalOf`），归属取最内层。

两个入口对应两种输入，**不能互相替代**：**文字位置**答"这个偏移归谁"（控件的文字区间树，
`ControlSet::innermostAt`），**流位置**答"这个插入点归谁"（流索引，`innermostControlAtFlow`）。
它们是同一条链的两端（文字位置 + 侧别 = 流位置），拿流位置去算"默认侧别"会跳过字段边界
—— 两个字段紧挨着时，同一偏移的靠内几格已经属于后一个字段。

**嵌套按交集处理，不需要 `w:group` 那种例外。** OOXML 的 `w:group` 允许内层控件覆盖
外层的"不可编辑"（规范原文：这条限制可以被它内部包含的任何结构化文档控件推翻），
它存在是因为 OOXML 在**默认可编辑**的文档里做局部保护；我们的表单模式默认就是
"只有控件内可编辑"，所以"整段只读、只留一处可填"只要把静态文字放在任何控件之外即可。
镜像字段值要用**同一个 `key` 的控件**，不要用嵌套的 readonly 控件——后者是两份互不
相干的数据，改了一处另一处不会跟着变；同一个 key 的多个控件能被一次批量设值一起更新。
只有"一段独立的静态文字"才适合用 readonly 控件。

只读模式则是所有编辑步骤被拒绝、控件不响应输入。

### Tab 与结构操作

**Tab 按模式分工**（同一个键不能同时干两件事，所以由模式决定它此刻算什么）：

- **编辑模式**：Tab 是**制表符**——模型里它就是一个 `Tab` 原子元素，参与制表位计算。
- **表单模式**：Tab 与 Shift+Tab 在**可编辑控件之间前进与后退**。这里有意**不照抄**
  Word 在富文本内容控件上的做法：它为了支持插入制表符而把 Tab 留在控件内，结果
  "**Tab 不出来**"，官方论坛给的解法是让用户改用鼠标、或把富文本控件换成纯文本控件。
  我们的文本控件是 `richText`（内部可含段落），照抄就会让填表单变成鼠标操作。
- **表单模式下不给"插制表符"留默认键位。** Word 的对应办法是在字段里按 `Ctrl+Tab`
  （与表格单元格同一个惯例），但**这条在浏览器里不成立**：`Ctrl+Tab` 被浏览器保留，
  Chrome 根本不给页面派发事件，Firefox 派发但 `preventDefault` 无效（见下面的键位纪律）。
  需要制表位的内容应当在**编辑模式**里由作者做好；填表时想缩进用**段落缩进**
  （它是 `ParagraphStyle` 的属性，不是字符，本来就比插制表符正确）。
  命令层仍然提供 `insertTab`（模型里有 `Tab` 原子元素），但**默认不绑快捷键**，
  绑什么由宿主决定——宿主是 web 应用，它最清楚自己能拿到哪些键。

**默认键位要避开浏览器保留键。** 裸 `Tab` 可以用——页面能拿到 keydown 并
`preventDefault`（这正是表单模式能用它切控件的前提）；但**一旦带上修饰键就不一定**：
`Ctrl+Tab` / `Ctrl+Shift+Tab`、`Ctrl+T` / `Ctrl+N` / `Ctrl+W`、`Ctrl+Shift+T` /
`Ctrl+Shift+N`、`F5` 这类由浏览器在页面之前处理：Chrome 下页面收不到事件，
Firefox 下收得到但拦不住。可覆盖的是常规那批——`Ctrl+B` / `Ctrl+I` / `Ctrl+U` /
`Ctrl+Z` / `Ctrl+Y` / `Ctrl+S` / `Ctrl+P` / `Ctrl+F` 等。
**所以任何默认快捷键都要先过这张表，尤其不要在 `Tab` 家族上做设计。**
- **只读模式**：**放行** Tab，让焦点落到编辑器之外的下一个元素——只读模式吞掉 Tab
  会把键盘用户困在编辑器里（键盘陷阱），而它没有任何东西可以换。
- 表单模式的**最后一个可编辑控件**上按 Tab 也要放行。不要学 Word"在最后一个单元格按 Tab
  就静默加一行"——那会让人往一行不存在的表格里打字。

**结构操作是控件属性，默认关闭。** OOXML 的 `w:lock` 把"内容能不能编辑"与
"控件能不能整体删除"分成两件独立的事（`unlocked` / `sdtLocked` / `contentLocked` /
`sdtContentLocked`），我们照这个分解，不造新概念：内容可编辑性已由 `readonly` 表达，
再补一个**结构操作锁** `structureLock`（默认 `true`，即锁住）。于是表单模式的默认是
**内容可编辑、控件不可删**——把表单填错与把表单结构改坏是两件事，后者该由作者显式开放
（把 `structureLock` 设为 `false`）。它是作者意图，随控件落盘（与 `readonly` 一致）。
注意它只在表单模式生效：文档模式下作者要能自由增删控件，只读模式下一律拒绝。
增删行列这类操作的目标不是控件，开关挂在被操作的元素上（表格 / 行 / 单元格），
不要造一个通用的"操作白名单"。

打印预览走同一条路径，不要另做一个渲染器。

### 控件族的落地形状（2026-10-26）

**共同层是扁平的，类型特有层是变体。** `ControlSpec` 只留所有控件都有的那几项
（key、controlType、valueShape、value、readonly、required、structureLock、appearance、
validateRef），特有层是 `ControlDetail`：`monostate`（纯文本）、`TextDetail`（数值过滤）、
`ChoiceDetail`（标签、选项、互斥组、多选、光标屏障）、`DropdownDetail`（选项、自由输入）、
`DateDetail`（格式、可选单位）、`CustomDetail`（宿主自定义类型的属性袋）。

  变体而不是"一个结构体挂满可选字段"：文本控件带 options、日期控件带 group 这类永远用不到
  的字段会让"这个控件有哪些属性"变成一句空话，序列化也要为每个字段判一次默认值。
  拿到 `ChoiceDetail` 就说明它一定有选项语义 —— 这件事交给类型系统，不交给约定。

**选择类的显示文字是数据的投影，不是作者打的字。** 单控件的标签存在 `ChoiceDetail::label`，
组控件的每个选项标签存在 `ControlOption::label`；它们由 `controlDisplayText` 生成进内容
（`○ 选项甲  ◉ 选项乙`），切换时整段重建。内容仍然可被逐字选中（它是普通文字），
但不可编辑、光标也进不去，所以"标签是只读内容"这条要求不靠机制，靠生成。

**光标屏障三档都生效。** 四种选择控件的整块内容不是可写正文，光标落在里面不算可插入位置：
点击被夹到块外、方向键跨过整块、编辑入口直接拒绝。选区不受限 —— 端点走进屏障是读的需求。
开关是 `ChoiceDetail::caret_barrier`（默认打开），引擎按数据判，不按类型名判。

**值是唯一真相，内容是它的缓存。** 下拉的值是选项值、日期是 ISO 串，显示文字由
`controlDisplayText` 按选项表与格式串生成。写值一次提交里同时改记录与内容，于是不存在
"值改了、画面还是旧的"这一档中间态；撤销一下回到改之前。

**日期的格式与单位分开。** `format` 决定显示（yyyy / MM / dd / HH / mm / ss 与字面字符），
`units` 决定选择器里能选哪些单位，两者不互相推导 —— 显示可以带秒而不许选秒（只读展示）。

**互斥规则在引擎里，不在宿主里。** 单选组只能有一个选中；单控件按 `group` 互斥时，
点第二个会把同组里原本选中的那个一并取消，整批一次提交（撤销一下回到"两个都没选"之前）。

**记号是自己画的，不是字体里的字形。** 复选用 `☐`/`☑`（U+2610/2611，语义正确：复制、导出、
别的渲染器都认），但本工程的字体里没有这一对字形 —— 宽度借 `□`（U+25A1）的（成形时把
codepoint 换掉，块流里的字一个都不改），图形由绘制层画：方框是四条描边，选中时在里面补
两条斜线当对勾。单选沿用 `○`/`◉`，同样在绘制层按记号色重画一次。
颜色取 `Appearance.glyph.color`，全透明表示跟随那一段文字的颜色（默认）。

  为什么不用字体字形：`☑` 没有；而 `○` 有字形却只能跟正文色 —— 一处配不出颜色，另一处
  配得出，规则就分裂了。绘制层按"这个码点是不是某个选项的记号位置"判定（`controlMarkerAt`），
  正文里打的 `○` 照旧由字体画。

**整块删除。** 内容不是作者打的字（值在记录上：四种选择控件、下拉、日期）的控件，在编辑上
是一整块：贴着它退格 / 前删删掉整块，不进去删字；选区只盖住它一部分时向外扩到整块边界。
判据是值形态（`valueShape != Text`），与光标屏障用的不是同一个开关 —— 下拉与日期只读、
没有屏障，但同样不该被删成半截。

**插入之后光标落在整块之后**（选择类）。可编辑字段摆在内容末尾（"接着填这个字段"）；
选择类的内容里根本停不住，摆进去等于把光标塞进一个按不动的格子，而下一次插入又会落进
它的内容里 —— 表象就是"连点两次单选，第二个嵌进第一个"。

**控件外观必须进页指纹。** 边界不占字形，换记号色、改边框粗细时位置一个都不动；页指纹
若不比外观摘要，那一页被判成新鲜，命令成功、读回的值也对，画面却停在旧帧（与"空段标记"、
"表格片段"同一族：页指纹必须覆盖绘制层的全部输入）。摘要由 `controlAppearanceDigest`
算，两个编译入口（模型树与投影）与行指纹共用这一份。

**定义可以改，而且只有一条写入路径。** `SetControlSpec` 整份替换记录并带 `before` 原值，
逆操作因此自足；`canApply` 比 `before` 与当前记录（对不上就是步骤过期）。命令层收的是
`ControlPatch`（每个字段都是 `optional`），只改给出的项 —— "不改"与"改成空"是两件事。
四个运行态开关（hidden / readonly / required / structureLock）不在这条路上，它们走
`SetControlProp`：同一个字段开第二条写入路径，两条迟早分叉。

改完要跟两件事，都在同一次提交里：**内容按新定义重建**（值形态不是 Text 时），以及
**指向已删选项的值跟着清掉**（不然就是"值不在选项表里"的脏数据：显示时找不到标签、
报出去业务侧不认，而画面上只是少了几个字）。两件事与定义改动同属一步撤销。

类型不可改：换类型是"删掉重插"，值形态、内容形状、命中归属会一起变。补丁里 `type` 只用来
把那种调用显式拒掉，不进记录。收不下的字段也拒（给文本控件送 options 之类）—— 静默忽略的
后果是调用方以为改成了、实际什么都没发生。

**控件记录的特有层必须整个进哈希。** 修订层的"内容没变"是按根哈希判的：漏一个字段，
改它的那一次修订会被当成"没变"直接丢掉，画面不变、也不报错。`rev_test` 里那份"逐字段
构造只差一个字段的两份记录"的清单要与 `hashControlSpec` 同步，特有层每一族的每个字段都在里面。

## 八、域

域是"值在排版或导出时才确定的内容"。**按值的来源分两类，只有第一类会产生迭代**。

| 类别 | 例子 | 值从哪来 | 是否迭代 |
|---|---|---|---|
| 排版结果 | 页码、总页数 | 本次排版的结果 | **是**（唯一有循环风险的） |
| 运行时刻 | 打印日期、文档属性 | 文档之外 | 否 |

页眉页脚要显示控件值（姓名、住院号）时**不用域**——放一个同 key 的控件即可（第七节）。
早先把"控件值引用"列成第三类域，现在删掉：按编码批量设值已经把"两处显示同一个字段"
这件事解决了，不需要多一种域，也不需要多一条"引用必须指向存在的 key"的不变量。

### 为什么只有"排版结果"会循环

页脚写"第 3 页 / 共 9 页"就是现成例子：

**按上一轮算出的 9 排版 → 实际排出 10 页 → 域文本从"共 9 页"变"共 10 页"，
多了一两个字符的宽度 → 可能让某一段多折一行 → 总页数变 11 → 再求值……**
每一轮的值都依赖上一轮的排版结果，收敛不了就互相追着跑。两个解法，按域类型分别用：

- **总页数用预留宽度**：按"最宽可能值"估宽（比如固定 4 位数），宽度不随值变，
  排版一次就稳定，迭代退化为 1 次。代价是页脚多一点空白。
- **页码用迭代上限**：最多 3 次，位数变化本来就少，通常第一轮就收敛。

日期**不会循环**：它的值与排版无关，取出来就固定；宽度变化最多让版面重排一次，
不会反过来改值。把三类混在一张表里，会让"循环"看起来像所有域的通病，那是不对的。

### 患者信息是控件值，不是域

患者姓名、住院号、性别、年龄这些**不是域**，而是绑定了业务 key 的控件值（见第七节）。
更新走 `setValuesByKey([{ key, value }])`。页眉页脚要显示时**放一个同 key 的控件**，
两处由同一次批量设值一起更新。域因此只剩"排版结果"与"运行时刻"两类。

### 模型形状

```
Field { kind, cache }
  kind ∈ { pageNumber, pageCount, printDate, docProperty }
```

`docProperty` 另带一个属性名（`name`），其余种类不带。域记录与求值函数在
`src/core/doc/field_spec.h`；求值只写 `cache`、按上下文幂等、不产生编辑步骤（1.8）。

去掉了早先的 `expr` 与 `custom`（本期不需要通用表达式求值）。`date` 改名 `printDate`——
它的语义是"导出或打印那一刻"，不是"打开那一刻"，否则昨天打开的文档会一直显示昨天的日期。

### 两条纪律

- **求值只更新缓存值，不产生编辑步骤。** 否则打开文档就会往撤销栈里塞东西。
- **域只出现在页眉页脚，正文不开放插入入口。** 病历正文没有"动态页码"的场景，
  页码位置本来就是固定的。但页脚里不能退化成 `Section` 上的一个属性字段——
  因为页脚不是只有页码，典型写法是连着排：

  > 第 3 页 / 共 9 页　　姓名：张三　　住院号：12345

  页码与同 key 的姓名、住院号控件是**混排**的。做成属性字段就没法混排，
  所以它仍得是页脚内容里的一个行内占位符，
  只是位置天然固定在页眉页脚。这样页脚就是一段普通的内容片段（能装段落、能装占位符），
  规则只有一套。

### 位置

域元素在流里是**原子**：占位宽度按缓存值算，参与断行，不可被拆开。

### 缓存值为空时的宽度

页码取零宽（尚未分页时不存在）。提示文字（`placeholder`）不进内容、不参与宽度计算，同理。

## 九、表格

已定两条：**跨页时纵向合并的单元格拆成两半显示**（Word 行为）；

**被合并掉的格位可寻址**（落在合并区域内时返回原点格）。

模型走向是"保存 rowspan / colspan、运行时派生网格矩阵、单元格的覆盖范围以跨度为唯一真相"
（列数由跨度派生；只有列上要绑字段时才有可选的列定义，见本节末尾"列定义是可选的"）。

下面先摆清三种做法的差别，再给出与这两个选择匹配的规范。

### 三种做法的实际差别

**OOXML 的做法**：表格声明一个网格（`tblGrid` 的若干 `gridCol`，定义列数与列宽），

每个单元格用 `gridSpan` 声明跨几列、用 `vMerge` 声明是否纵向合并的起点或续格。

网格是坐标系统，**每个单元格都必须起始和结束于网格线**。

纵向合并的续格在 XML 里**真实存在**（是空单元格），只是标记为"续接"。

**HTML 的做法**：`rowspan` / `colspan` 直接写在单元格上，

被合并掉的那些格位**在文档里根本不存在**，任何一行都不会提到它。

**参照项目的做法**：单元格带 `RowSpan` / `ColSpan` 两个属性，

配有 `FixRowSpan` / `FixColSpan` 做越界夹取（跨过表格末尾时截断）。

它同时维护 `Rows` / `Columns` / `Cells` 三个列表。

### 差别在哪里会咬人

**一是"被覆盖的格位存不存在"。** HTML 里不存在，OOXML 里存在（对纵向合并）。

这直接决定"在某处插入一列"要怎么算：HTML 模型下要遍历所有单元格判断是否被跨过；

OOXML 模型下续格是显式的，但要多一步"续格是空的、不能有内容"的约束。

**二是"逻辑单元格列表不反映物理列"。** 这是 python-docx 文档里专门写的一节：

`row.cells` 返回的是逻辑列表，跨列合并之后它的长度仍然等于网格列数，

但同一个单元格会在其中重复出现。所以**绝不能靠遍历 `row.cells` 累加跨度来推列边界**，

必须为每个单元格显式计算 `(start_col, end_col)` 区间。

**三是 Word 自己的 API 在非均匀表上会直接报错。** Word 的 `Table.Rows(n)` 遇到纵向合并

就会抛异常，`Cell.Column` 遇到横向合并也抛。这不是可以效仿的行为。

### 建议的规范

既然选定"跨度是真相、网格是派生"，那**派生的结果必须是不变量**，才有意义：

- 推导函数 `buildGrid(table) -> Matrix<CellRef>`，返回每个网格格位指向哪个单元格。
- 不变量：第二节"表格类"那三条。
- 所有行列操作（插入行、删除列、合并、拆分）都先改跨度，再重新推导网格，

  然后**断言不变量**。断言失败就是 bug，不是"数据就是这样"。
- 对外寻址一律用网格坐标 `cell(r, c)`，落在合并区域内时返回该区域的**原点单元格**

  （左上角）；为什么只能这样，见下面"被合并掉的格位可寻址"。

### 两个已定的选择与它们的实现含义

**跨页拆成两半显示。** 采用 Word 行为：纵向合并的单元格跨过分页线时，在该页重复显示其内容。

实现含义有三条：

- 这是**排版产物，不进模型**。分页器在分页线处把一个逻辑行拆成两页上的两个显示行。

  与域缓存同一个道理——模型只表示"当前内容"，不表示"怎么排"。若不这样定，

  复制一段跨页表格会凭空多出内容，命中与选区也会多出错位的目标。
- 模型里**续格根本不存在**（模型形状见下），所以不存在"续格内容与原点不一致"这类错误，

  不需要额外不变量守住。
- 网格推导要能接受"页内片段"这个上下文：`buildGrid(table, rowsInPage)`。

  对整表调用返回完整网格，对页内片段调用返回该页可见的网格。

**被合并掉的格位可寻址。** 规则：`cell(r, c)` 落在合并区域内时返回该区域的**原点单元格**（左上角）。

这是唯一能让 `cell(r, c)` 在任何表上都可用的规则，也与 python-docx 的做法一致；

否则调用方每次都要先自行判断"这个格位是不是被别人合并了"。

由此确定的模型形状：

```
Table        { rows: TableRow[], gridCols?: Length[] }
TableRow     { cells: TableCell[] }
TableCell    { rowspan: int, colspan: int, content: Node[] }
```

**被合并掉的格位在模型里根本不存在**（HTML 式），只在派生网格里出现且指向原点格。

选了 rowspan 式就彻底一点，不要像 OOXML 那样在模型里再留续格：

好处是"续格不能有独立内容"这条不变量由结构本身保证，不需要单独写检查。

派生网格：`buildGrid(table) -> Matrix<CellRef>`，`CellRef = (origin_row, origin_col)`。

不变量是 `grid[r][c] == (r, c)` 当且仅当 `(r, c)` 是原点格。

**落地的形状（1.7）**：跨度挂在单元格节点上（`Node::cell`，`CellSpan{row_span, col_span}`），
表格自己的记录挂在表格节点上（`Node::table`，`TableSpec`）。网格不存，每次推：

```cpp
TableGrid grid;
std::string why;
if (!buildGrid(tree, table, &grid, &why)) { /* 记诊断，不当完整结果用 */ }
const GridCell* g = grid.at(row, col);   // 越界返回空；落在合并区域返回原点格
```

`GridCell` 里存的是**原点**坐标（不是当前格位坐标），所以"落在合并区域返回原点格"
这条规则就是"查任意格位都拿到同一个原点"。`sameOrigin` 用它回答"这条网格线有没有被合并跨过"，
行列操作全靠它判断哪一格吸收新列。

**行列操作不是新的步骤类型**，而是"先算清楚跨度怎么变、再由既有步骤组合出一批"：
插一列 = 几个格子的跨度加一（跨过插入线的那些，按原点格去重）+ 其余行各插一个新格子；
删一列 = 跨过的格子跨度减一，跨度降到 0 的连内容一起删；删行则要先把从上面跨进来的纵向合并
各缩短一格。这批步骤合成一个事务，于是撤销一次全回来。

由此多出一条 `SetTableCellSpan`（跨度是唯一真相，所以"插一列"落到步骤上就是"几个跨度变了
+ 插了几个新格子"），以及一条纪律：**批次里每步的坐标属于它自己那一刻**，所以后面的步骤要按
前面几步的位置映射推过去（`pushMappedStep`，与批量设值共用）。

**两条边界**：删最后一列、删最后一行都拒绝 —— 留下"有行没有格"或"有格没有行"的表格是合法的，
但没有意义，不如显式说不支持。新插入的行里不许有 `rowspan > 1` 的格子（会与下面的行重叠），
要跨行合并请在插入之后再做。

### 跨页要拆成三件事说，它们不是一件事

"表格跨页"下面压着三个互不依赖的行为，混在一起谈会把实现顺序与判据都搞乱：

- **行跨页断开**（Word 的"允许跨页断行"）。一行太高、当前页放不下时，在页边界处把这一行切开：
  上半留在本页，下半接着排到下一页。切点处**没有横向边框** —— 格子左右那两条边框在页底截断、
  下一页接着画，中间那一段是被裁开，不是被分出一条线。这是每段可设的开关，默认允许。
- **重复标题行**（Word 的"在各页顶端以标题行形式重复出现"）。表跨页时，把开头几行在每一页的
  表格顶端再画一遍。它与"行拆不拆"无关：一行都不拆、每页只放整行，只要表跨页表头照样重复。
  它是**逐行属性**，落在 `TableSpec::header_rows`（前几行是表头）。
- **纵向合并的格跨页**。一个 `rowspan` 跨过分页线的格，在下一页重复显示它的内容（本节开头
  已定的那条）。这条**依赖**第一条：行不允许跨页，合并就跨不过页。

所以实现顺序是：行跨页断开（含合并格跨页）是一条，重复标题行是另一条，后者可以晚做。

**未定的一处**：重复出来的表头行在模型里只有一份，排版产物里有多份（每页一份）。命中测试
点中重复副本时落到哪里要定一条规则 —— 落回原件（第一页那一份），还是这一份干脆不可编辑。

**"表头"默认没有，它是一条逐行开关。** Word 里叫"标题行重复"，对应 `w:tblHeader`：标在哪几行
就重复哪几行，**与"表格的第一行"没有关系**。本设计的对应字段是 `TableSpec::header_rows`
（前几行是表头），默认 0 表示一行都不重复。病历里那种"空白书写区"的表格（薄薄一行写栏目名、
下面一大格用来写字）通常根本没有表头行，跨页时什么都不重复 —— 行被页边界裁开、接着往下写，
就是跨页的全部内容。

**这一小节顺带暴露了两处模型缺口**，都在这类表格上才看得见：

- **行高没有字段**。`TableSpec` 只有列宽（`grid_cols`）与表头行数，`CellSpan` 只有跨度。
  而"空白书写区"靠的是行高（Word 的 `trHeight`，至少两档：`atLeast` 与 `exact`）—— 没有它，
  一格空段落排出来只有一行高，没地方写字。行高要挂在行上：`TableRow` 需要一份自己的记录，
  与 `Node::cell` 对 `TableCell` 的关系同构。
- **边框 / 内边距 / 底纹只有设计**：本节说它们走样式表的 `TableStyle`（边框、底纹、单元格边距、
  行高列宽默认值），但代码里还没有这个结构 —— 样式表目前只有段落与字符两类。第一刀至少要有一个
  "表格画不画边框"的最小来源，否则产物里连格线都没有。

### 表格 / 行 / 单元格的属性：第一刀取这些

属性集先按参照项目过了一遍（`DomTableElement` / `DomTableRowElement` / `DomTableCellElement`），
再按"病历表格能不能用"裁出必要项。

**行（新加一份记录，挂在 `TableRow` 上，与 `Node::cell` 对 `TableCell` 同构）**：

| 字段 | 类型 | 默认 | 干什么 |
|---|---|---|---|
| `can_split_by_page` | bool | 真 | 允许被分页线切开（= `CanSplitByPageLine`） |
| `is_header` | bool | 假 | 标题行：跨页时在每页顶端重复（= `HeaderStyle`） |
| `page_break_before` | bool | 假 | 行前强制分页，效果同分页符（= `NewPage`） |
| `height` + `height_rule` | `Length` + `{Auto, AtLeast, Exact}` | Auto | 行高。空白书写区靠它；`AtLeast` 是不小于（字多了会长高），`Exact` 是固定（超出裁切） |

参照项目用一个 `SpecifyHeight` 的**符号**编码三档（0 自动 / 正数不小于 / 负数固定）。我们已经有
带标签的 `Length`，所以拆成"值 + 规则"两个字段：比符号可读，也不必约定"负数表示固定"。

**表格（`TableSpec`，在现有字段上加减）**：

| 字段 | 类型 | 默认 | 干什么 |
|---|---|---|---|
| `width` | `Length` | Auto | Auto = 撑满可用宽度（Word 默认）；Percent 相对内容区；Abs 固定 |
| `align` | `Align` | Start | 表格在内容区里的水平位置（只在宽小于可用宽度时才有意义） |
| `columns` / `grid_cols` | 已有 | 空 | 列定义（可选）与显式列宽 |
| ~~`header_rows`~~ | — | — | **删掉**，标题行改成逐行开关，见下 |

**单元格（`CellSpan` 就地扩成 `CellSpec`，三个字段）**：

| 字段 | 类型 | 默认 | 干什么 |
|---|---|---|---|
| `row_span` / `col_span` | int | 1 | 已有 |
| `v_align` | `{Top, Center, Bottom}` | Top | 单元格内垂直对齐（Word 的 `w:vAlign`，在 `w:tcPr` 上而不在样式里） |

垂直对齐另立一个枚举而不是借用节的 `VerticalAlign`：后者有 `Both`（两端对齐）这一档，而单元格
没有这个取值 —— 借一个值域更宽的枚举，等于让"非法值"有地方可待。

**外观（边框 / 内边距 / 底纹）第一刀不进模型。** 按设计它们归样式表的 `TableStyle`，而样式表还
没有这一类；第一刀用引擎配置里的常数（格线颜色与线宽、单元格内边距），等 `TableStyle` 落地再接。
这样"表格画不画得出来"不依赖样式层，也不会把一份临时的外观字段写进文件格式。

**把 `header_rows` 换成逐行开关的连带后果**：

- "带列定义的表，数据行不许合并"这条约束要从"第 n 行之后"改成**"非标题行"** —— 判据更直接，
  也不再依赖"表头一定在前面"这个隐含前提。
- 多一条不变量：**标题行必须是从第 0 行起的连续前缀**。逐行开关允许标出"第二行是标题、第一行
  不是"，而"重复哪几行"只有连续前缀才有意义（Word 也只允许从第一行起选）。于是"几个标题行"
  变成派生量（`headerRowCount(tree, table)`），不再是存下来的字段。

**明确不取**（参照项目有，但这一刀不必要）：逐行 / 逐格的边框与底纹（走样式）、逐格内边距覆盖
（表级默认够用）、`TabStop`（表单模式下 Tab 跳过某格，等表单接表格）、`CellID`（`NodeId` 就是
身份）、`IsSelected` 与 `IndexInSelectionCells`（会话状态，不进模型）、`IsOverrided`（内部缓存）、
`NeastLevel`（嵌套层数，从树派生）、`DomDisplayName`（调试用）、`DataRow`（它只用来决定"分页时
插不插临时标题行"，我们用 `is_header` 直接表达）。

### 列定义是可选的：普通表格由跨度派生列

**普通表格不需要列定义。** 它的列由**单元格跨度派生**（本节前半：保存 rowspan 与 colspan、
运行时派生网格），所以"插一个 m 乘 n 的表格"就是建 n 行、每行 m 个单元格，
不需要另外维护一份"有哪几列"的声明。**合并单元格照常允许**——列数在派生网格里只是一个
推出来的宽度，合并不会让它失去意义。

**列定义只有一种情况需要：列上要绑字段。** 它是一份可选的**列定义数组**：

```
Column {
  fieldRef,               业务字段标识：不透明字符串，编辑器不解释它的含义
  title?,                 列标题（也可以放在表头行的单元格里）
  dataType?,              字符 / 数字 / 日期 / …——影响编辑与校验，不改存储形态
  editorStyle?,           输入框 / 下拉 / 日期选择 / 只读…
  width?, align?          版式
}
```

填了它，这张表就能按数据落值（下一节）。**它同时带来一条约束：数据行不允许合并单元格**
——每一行的格数必须等于列数。

**为什么这条约束是必需的**：列绑定的全部意思就是"第 i 列对应哪个字段"，所以"第 i 列"
必须是一个**确定的位置**。数据行一旦可以合并，同一个格子在派生网格里会横跨多列，
"第 i 格是不是第 i 列"就不再确定，按列落值也就无从谈起。

**表头行不受这条限制**——它不承载数据，跨列合并（比如"手术信息"横跨两列）是常见的排版
需求，它也不影响数据行的列对应关系。

**所以合并不是一律禁止，而是"按位置定位的东西不允许被跨过"。** 这与第二节那条
"区间端点必须落在流元素边界上、涉及不可半分单位时向外扩"是同一类约束：
一个位置要能被寻址，就不能有东西横跨在它上面。

**表格不分成两个类型**（没有 `table` 与 `dataTable` 两种 `controlType`），
但列定义这份可选配置填与不填，决定了同一张表能不能按数据落值。

### 动态表格：行是内容，数据按列落值

病历里"用药记录""检验结果""诊断列表"这类表格的共同形状是**列固定、行数可变**，
行数由绑定的数据决定。

**先立判据**：能不能把光标放进"第 3 行第 2 列"的中间、在那里打字？能，那些行就**必须**
是文档内容。病历表格几乎都是这种（医生要往格子里填），所以**不采用"数据渲染出行"**——
Word 的重复节走那条路，代价是行不在文档里，光标、选区、复制、坐标都要为它开特例，
与第二节"流是完整的"这个前提冲突。

行是文档内容，行带**行标识**（表内唯一，表示"这一行对应哪条数据"）。同步走一对 API：

```
setTableRows(tableKey, [ { rowKey, values: { fieldRef: 值, … } }, … ])
getTableRows(tableKey)
```

按行标识做**差量**：同标识的行**只更新单元格的值**（不重建，所以不丢用户在这一行里的手工
编辑）、新的插入、缺的删除，全部合成**一个编辑步骤**（撤销一次全回来）。
**值按列的 `fieldRef` 落进对应列的单元格**——绑定只在列定义上声明一次，
不必在每个格子里各放一个控件。

**"数据元素"这类概念不进编辑器。** `fieldRef` 只是一个不透明字符串：编辑器负责"把它标在
列上、按它落值、按它取值"；至于它指向业务系统的哪个数据元素、怎么建立映射，是**业务层**
的事（宿主自己维护"字段标识 → 数据元素"的表）。这条边界让文件格式保持稳定：换一套业务系统
不影响文档，只需宿主换一张映射表。

**这套机制不是新造的**：它与第七节"按业务编码批量设值"（`setValuesByKey`）是**同一套思路**，
只是粒度从"一个控件"上升到"一行乘一列"。判据也同一条：**同步 N 行与同步 1 行耗时同一量级、
只产生 1 个撤销步骤、最终帧与逐行手工设置逐像素一致。**

**新增行的结构来自"行模板"**（表格声明一个模板行，设计时定）；模板行**不参与正式渲染**
——表单、只读、打印都不画它，只有编辑模式显示它（虚线框提示），否则作者没法编辑模板。
它是**结构性标记，不是 `hidden`**：那个是运行时可改的显示策略，而模板行是"永远不渲染"。

**所以动态表格不需要"数据绑定"这个新概念**：文档是唯一真相源，数据是"一次同步的来源"，
同步的边界由 `setTableRows` 一次调用划定，差量与撤销都由它兜住。

### 落地形状（阶段 5，2026-10-19）

属性清单原样落地，三处口径在实现时定下来：

- **行记录挂在 `TableRow` 上**（`Node::row`，`RowSpec`），与 `Node::cell` 对 `TableCell`
  的关系同构。行高是"值 + 规则"两个字段，规则 `Auto` 时值不被解释（给了值记诊断）。
- **表格宽度与单元格垂直对齐都进了模型**（`TableSpec::width` / `align`、`CellSpec::v_align`），
  边框、底纹、单元格内边距**没有进** —— 它们走引擎配置常数，等样式表有 `TableStyle` 再接。
- **`header_rows` 已删**：标题行是逐行开关，`headerRowCount(tree, table)` 是派生量，
  不变量"标题行是从第 0 行起的连续前缀"守着坏形状。

编译与排版的形状：表格**扁平化**进块流（每块带 `cell_path`，嵌套表格路径更长一条），
所以"单元格里放控件、放图片、再放一张表"不需要新概念；排版按格矩形断行与结算行高，
跨页按 `can_split_by_page` 分两档（按行盒切片 / 整行挪走），切点不画横线由绘制层按
`cont_top` / `cont_bottom` 跳过那条边来完成。**有表格时不做增量排版**：续排的状态只有
三个标量，"第几行第几格"续不上。

**仍未落地的三件**：标题行重复（模型与编译已就位，排版要在产物里复制行片段，而"点中重复
副本落到哪里"这条规则还没定，见上文"未定的一处"）；`TableStyle` 与逐格边框底纹；
竖排文档里的表格（按整页宽排，不做静默的错误格布局）。

**这一半还没落地**（1.7 只做了结构那一半）：`setTableRows` / `getTableRows`、行标识与行模板
都要等"行带身份"这件事定下来。同理，`buildGrid(table, rowsInPage)` 的那个"页内片段"上下文也
留着 —— 它的语义取决于分页器怎么切（跨页的原点格算不算在这一页里），没有分页器时加个参数
只能靠猜。

## 十、节与页面设置

先把现状差距摆出来：引擎的 `PageMetrics` 只有 `width_pt` / `height_pt` / `margin_pt`

三个字段——**四边共用一个边距**，而且全篇只有一套页度量。下面是需要补全的完整清单。

### 纸张与页边距

```
Section {
  paper:    { name: A4|A5|B5|Letter|Legal|Custom, orient: 纵向|横向, size?: {w, h} },
  margins:  { top, bottom, left, right },        // 四边独立
  gutter:   { size, side: 左|上 },                // 装订线
  mirrorMargins: bool,                            // 双面打印时奇偶页镜像
}
```

纸张用**名称加方向**表示，尺寸是派生值（理由见第十一节）。只有自定义纸张才存显式宽高。

页边距必须四边独立——现在的单一 `margin_pt` 撑不住病历排版，常见的是上窄下宽、左右不同。

### 页眉页脚

- 三组变体：**首页 / 奇数页 / 偶数页**，各自独立（对应 Word 的 `titlePg` 与

  `evenAndOddHeaders`）。三组都是可选，未设置时按"继承上一节或留空"处理。
- 每组是**独立的内容片段**（装块级内容），不是段落属性。它需要自己的编译路径，

  但可以复用同一套块级节点。
- 各自的距边界距离（页眉距上边、页脚距下边），这两个量与页边距是两回事，

  页眉可以落在页边距以内。
- **链接到前一节**标志：默认继承上一节的页眉页脚，显式断链才独立。

  这是一个状态，必须存，否则"改了一节的页眉"会莫名其妙影响后面的节。

页眉页脚里可以放域（页码、总页数、日期、患者信息），所以第八节的域机制要能被它们引用。
模型已落地（1.8）：三组变体各一个 `HeaderFooter`（内容片段根 + 距边界 + 链接标志），片段根是
一种不在正文流里的容器（`NodeKind::HeaderFooter`），走 `compileFragment` 编译；渲染与按节排版
仍等引擎支持。域在片段里照常求值（`evaluateFields` 会按节的记录走进这些片段）。

### 页码与计数器

页码格式（阿拉伯 / 罗马 / 中文数字）、起始值、本节是否重新编号。

### 节排版

- 节类型：连续 / 下一页 / 奇数页 / 偶数页，决定节与节之间的分页行为。
- 垂直对齐：上 / 居中 / 下 / 两端，内容在页面上的垂直分布。
- **文字方向：横排 / 竖排**。引擎把书写模式当一等公民，所以这一项要与段落的

  `WritingMode` 协调：节给默认值，段落可覆盖。
- 分栏：栏数、栏宽、栏间距、分隔线。
- 页边框、行号。
- 文档网格（东亚排版的字符网格 / 行网格）。

### 脚注尾注

位置（页底 / 文末）、编号格式、起始值。脚注**正文**是独立的内容片段，与页眉页脚同类。

### 文档级属性

节之外，`Document` 上还要挂这些全局表：

- **字体表**：字体名、回退链、是否嵌入。
- **样式表**：见第六节。
- **编号定义表**：多级列表的编号格式、层级、起始值、缩进。
- **资源表**：图片与嵌入对象的二进制，按 ID 索引（架构文档 4.5：二进制资源外置）。
- **主题**：颜色方案与字体方案。
- **书签表**：名字到区间的映射（节点 ID + 偏移），交叉引用靠它。
- **文档属性**：标题、作者、创建与修改时间、自定义属性。
- **保护与权限**：只读区域、可编辑区域、编辑口令。

### 一条设计原则：能存住，不必全理解

文档模型对页面设置的态度是**完整保留、按需理解**。引擎不认识打印机设置、兼容性标记、

主题色这类属性，但必须原样存住、往返不丢。

这条对病历系统尤其重要：导入外院文档或历史文档时，不认识的部分不能丢，

否则"打开再保存"就会悄悄损坏文档。实现上就是**未知属性透传**——

节点与节上留一个可容纳任意键值的属性袋，序列化时原样写出。

### 读写范围（已定）

"完整保留"与"引擎理解"是两件事，本期按下面这条线切：

| 范围    | 属性                                                   | 代价              |
| ----- | ---------------------------------------------------- | --------------- |
| 真正生效  | 纸张（名称 + 方向）、四边页边距、页眉页脚、页码                            | 要动引擎：分页、页度量、页指纹 |
| 只原样存住 | 装订线、镜像页边距、分栏、垂直对齐、页边框、行号、脚注尾注、文档网格、打印机设置、兼容性标记、保护与权限 | 只要属性袋，序列化原样写出   |

本期**引擎真正理解**的是第一行；第二行完整保留、往返不丢，但对排版不产生作用。

最要紧的一个取舍：**文档网格只存不生效**，所以中文排版里"每行多少字"这类设置

不会被引擎遵守。这一点要在导入外部文档时明确告知，免得用户以为格式丢了。

### 风险

节是唯一会让"页度量"在文档中途变化的机制。当前的页指纹与增量上屏按"页"组织，

需要确认它们能容纳"同一篇文档里页宽不同"。这一条要么先做一次探针验证，

要么在本期只支持"全篇同一节"，把多节留到下一阶段。

**1.8 的落地结论**：引擎的 `PageMetrics` 只有一套（单一页宽与单一边距），所以"同一篇文档里页宽

不同"现在做不到 —— 探针不必做，结论由接口本身就定了。本期模型把纸张与四边页边距完整存住并

只支持"全篇同一节生效"；分页行为（节类型）不受影响，因为它落成的是引擎已认识的段前分页。

按节生效的页度量属于引擎侧扩展，与"文档模型的节"是两件事，模型已经就位。

## 十一、单位与长度

### 两层要分开：显示单位与内部精度单位

"以厘米为基准"这个说法把两件事混在了一起：

- **显示单位**是用户看到的。国内病历场景习惯厘米与毫米，这个诉求成立，

  纸张显示"A4"、页边距显示"2.54 厘米"都是对的。
- **内部精度单位**是算排版用的。它要满足的不是"像公制"，而是"常用单位都能精确整除"。

这两个可以完全不同。**显示用公制、内部用一个能整除所有单位的整数**，是这一节的全部结论。

### 为什么内部不以厘米为基准

三条理由，都有据可查：

**一、文字排版的基本量全部以磅定义。** 字号的行业单位是半磅（OOXML 的 `w:sz` 就是半磅，

小四 = 24、五号 = 21），行距是磅或倍数，线宽是 0.5 / 0.75 / 1 磅。

若内部以厘米的倍数计，每次字号参与计算都要乘一个循环小数系数——

12 磅写成厘米是 0.42333…，无法精确表示。

**二、毫米对排版来说太粗。** 1 毫米 = 2.83 磅，而排版要对齐到千分之一磅量级

（`auditLayout` 的坐标容差就是 1e-3 磅）。要做到这个精度，厘米基准必须细分到

约 1/28000 厘米——细分到这个程度，"可读性"这点好处也就没了。

**三、公制整的纸，英制不一定整，反之亦然。** A4 在厘米下是 21 × 29.7（整），

折成磅是 595.276 × 841.89（不整）；Letter 在磅下是 612 × 792（整），

折成厘米是 21.59 × 27.94（两位小数）。**只有一种单位能让两边同时精确**，

那就是下面说的 EMU。

主流格式的选择也印证这一点：CSS 的绝对长度单位里明确写着 **px 是 canonical unit**

（`1in = 96px = 72pt`），即 CSS 也锚在英制关系上；WordprocessingML 用缇（1/20 磅）；

PDF 原生用磅。**没有一个主流格式以厘米为内部基准。**

换算表保留以便对照：

| 单位     | 到磅                   | 备注                     |
| ------ | -------------------- | ---------------------- |
| 磅 pt   | 1                    | 印刷与 PDF 的原生单位          |
| 缇 twip | 1/20                 | WordprocessingML 的原生单位 |
| 像素 px  | 3/4                  | CSS 像素，1 in = 96 px    |
| 英寸 in  | 72                   | 精确定义                   |
| 厘米 cm  | 3600/127 ≈ 28.346457 | 循环小数                   |
| 毫米 mm  | 360/127 ≈ 2.834646   | 同上                     |

注意厘米与毫米是**循环小数**：A4 宽 21 cm 恰好是 75600/127 磅。任何有限精度都表示不精确，

这不是缺陷、无法回避。所以下面两条比"选哪个单位"更要紧。

### 语义与数值分开

**纸张用名称加方向表示，尺寸是派生值。** `A4 + 纵向` 是一个精确的语义；

它的宽高换算成磅会舍入，但语义没丢，用户看到的仍是"A4"而不是"595.28 磅"。

只有自定义纸张才存显式宽高，而且要**连同用户输入的原单位与原数值一起存**，

这样往返显示才是"21 厘米"而不是"595.276 磅"。

页边距同理：存 EMU，但记住用户习惯的显示单位（国内默认厘米），显示时换算并舍入到两位小数。

### 内部精度单位选 EMU

EMU（English Metric Unit，1/914400 英寸）是**唯一一组让磅系与公制同时精确整除**的单位。

名字本身说明了它是为这个目的造的，OOXML 的 DrawingML（图片、图形、形状尺寸）用的就是它：

| 单位              | EMU    | 是否精确 |
| --------------- | ------ | ---- |
| 磅 pt            | 12700  | 精确   |
| 半磅（字号单位 `w:sz`） | 6350   | 精确   |
| 缇 twip          | 635    | 精确   |
| 像素 px（CSS）      | 9525   | 精确   |
| 毫米 mm           | 36000  | 精确   |
| 厘米 cm           | 360000 | 精确   |
| 英寸 in           | 914400 | 精确   |

作为对照，先前考虑的 1/1000 磅（微点）方案：

| 单位     | 微点       | 是否精确 |
| ------ | -------- | ---- |
| 磅 pt   | 1000     | 精确   |
| 缇 twip | 50       | 精确   |
| 像素 px  | 750      | 精确   |
| 毫米 mm  | 2834.65  | 不精确  |
| 厘米 cm  | 28346.46 | 不精确  |

**定成 EMU。** 不止因为公制精确：

- **精度更足。** EMU 步长 7.87e-5 磅，比 `auditLayout` 的 1e-3 磅容差细 12.7 倍；

  微点步长恰好等于容差，余量为零。
- **与 OOXML 图形零换算。** 将来导入导出图片尺寸、形状位置时直接用 EMU。
- **范围够用。** A4 高是 10,692,000 EMU，int32 上限约 21.5 亿（约 59 米），

  装在 32 位里绰绰有余；要更大范围再换 int64。

为什么必须定点整数而不是沿用 float，三条理由：

**相等比较可靠。** 增量排版要判断"这一行有没有变"。float 现在能比较，是因为同一份代码

在同一台机器上算出同样的值；一旦模型重建（重新打开文件、撤销重放、跨平台），

最后一位就可能不同，于是"没变的东西被判为变了"，增量的正确性判据会开始闪红。

**序列化无歧义。** 整数直接写。浮点要靠"按十进制字符串写"这条补丁（架构文档 4.5），

定点整数是从根上解决。

**跨平台一致。** 不依赖浮点单元的融合乘加行为。

代价要说清楚：数值比磅大 12700 倍，直接读不直观（A4 宽是 7560000 而不是 595.276）。

所以**必须配一对转换函数**，任何手写的 EMU 字面量都算错误 —— 写 `ptToEmu(12.0)`
而不是 `152400`。

0.5 已按这条落地（`src/core/utils/units.h` 与 `src/core/doc/length.h`）：通用的一对是
`toEmu(v, Unit)` / `fromEmu(e, Unit)`，`emuPerUnit` 里七个单位的因子都是整数。
具名包装刻意带方向后缀（`ptToEmu` / `cmToEmu` / `mmToEmu` / `halfPtToEmu` / `emuToPt` …），
**不叫 `pt()` / `cm()`**：现有代码里已有同名局部变量（`layout.cpp` 的 `float pt`、
`engine_diag.cpp` 的 `const Rect px`、`native_main.cpp` 的 `long long mm`），
裸名会被作用域里的局部变量静默遮蔽，而遮蔽不报错。

长度的落盘形式（`printLength` / `parseLength`）也在这里定：模型里只有整数与整数比，
所以文本形式不含浮点，`parse(print(x)) == x` 天然成立，不需要"浮点按十进制字符串写"
那条补丁来保证精度。五个分支各有一个前缀（`abs:` / `pct:` / `em:` / `chars:` / `auto`），
于是**类型不会在往返里丢掉** —— 这是 0.5 的另一半判据。可读的显示形式（厘米两位小数）
是视图层的事，不在模型里。

边界在哪里：**模型保存的是"用户输入的意图"（精确值），引擎算的是"排版结果"（可以有误差）**。

所以整数在模型层、浮点在引擎层，编译时做一次乘除。

### 长度不只有"绝对"

这是比换算更要紧的一层：**长度的"性质"有三类 —— 绝对、相对、自动 —— 必须用类型区分，
不能一律塞成数字。** 相对这一类里有三种参照（百分比、字号倍数、字符位），各自的场合不同：

```
Length = Abs(EMU) | Percent(分子, 分母) | Em(倍数, 相对字号) | Chars(n, 全角字符位) | Auto
```

`Chars(n)` 不能拿 `Em(n)` 顶替：中文全角字是 1 em，但数字与字母是半角（约 0.5 em），
"3 个字符宽"在数字字段上会算成一半（第七节的控件固定宽度里会用到）。

各自出现的场合：绝对用于字号、页边距、纸张尺寸、边框宽度；

百分比用于表格列宽、图片宽、缩进；em 倍数用于行距；`Chars(n)` 用于按字符数计的首行缩进
与控件固定宽度；自动用于表格 autoFit、图片按原始尺寸、列宽按内容。

把它们混成一个 `float` 会在三处直接出错：表格算列宽时不知道百分比相对谁、

行距的倍数无法与固定值区分、`Auto` 没有数值可以表达。

### 行距是一个具体的坑

Word 的行距有三态（`w:spacing` 的 `lineRule`）：

- `auto`：倍数，相对**单倍行高**（字体的 ascent + descent）。现在 `BlockSpec::line_factor = 1.0`
  就是这一态，与 Word 的单倍行距同口径：加一倍就松一倍，不以字号为基准（以字号为基准时
  字体的纵向留白会把小倍数吃掉，1.0 到 1.45 落在同一个行高上）。
- `exact`：固定值，行高恰好等于该值，字大了会裁切。
- `atLeast`：最小值，取"内容高度"与该值的较大者。

三态的排版行为不同，模型里必须能区分，不能只存一个数字。现状只有 `line_factor`，

属于 `auto` 态；补另外两态时行高计算要分叉，而这一点会影响增量续排的块轴推进公式

（见 `engine.h` 里那段"横排的块轴推进是一条纯折线"的注释）。

### 像素与 DPI

模型里**不应出现像素**，因为像素是设备相关的。屏幕渲染时的"磅到设备像素"

是 `EngineConfig::zoom` 的事（现在是 2.0，约 144 dpi），属于视图层。

唯一例外是**图片的原始尺寸是像素**：`Image` 需要

`{ 像素宽, 像素高, DPI, 显示尺寸 }`，显示尺寸是 `Length`。

若只给像素不给 DPI，按 96 DPI 假设换算，这也是行业惯例。

### 换算的三个边界

- **入口**：用户输入、导入文档 → 换算成 EMU，只发生一次。
- **出口（显示）**：EMU → 用户偏好单位，舍入到显示精度（厘米两位小数）。
- **出口（渲染与导出）**：EMU → 磅交引擎；导出 PDF 原生用磅；导出 HTML 用像素。

绝不出现"存厘米、算磅、再存厘米"这种往返换算。

### 图片的落地形状（2026-10-26）

**字节不进文档，像素由宿主解码之后注册。** 引擎里没有解码器：宿主（浏览器里的
`createImageBitmap` + canvas，或原生宿主的解码器）把图变成 RGBA，按资源 id 交给
`registerImage(id, w, h, rgba)`。这条选择的代价是宿主必须管住内存（资源表有总量上限，
超了拒绝而不是静默淘汰），收益是 wasm 产物不涨、不需要给 Skia 链 codec，而格式支持
跟着浏览器走。换台机器打开时由宿主重新注册 —— 与字体同一条纪律：资源外置、文档存 id。

**显示尺寸只算一次，在编译层。** `ImageSpec` 存像素宽高、DPI 与两个 `Length`；
两边都 Auto 时按像素与 DPI 折算，只给一边时按原图比例推另一边（`resolveAtomBox`）。
拖拽把手把尺寸钉成绝对长度，于是 Auto 就此让位给"作者就是要这么大"。

**选中与拖拽是瞬态层。** 点图片给的是对象选区（`image_sel_`，与文本选区互斥），
拖拽框与八个把手画在呈现用的像素上，不进页位图、不进导出 —— 与光标、选区同一条纪律。
命中先判把手再判图身：把手有一半在框外，顺序反了贴边那几磅就永远拖不动。

**一次拖拽只留一步撤销。** 每帧都改尺寸、每帧都提交，但提交带"这是同一次连贯操作"
的标记（`rev::MergeRun`）；会话层据此只在第一帧压旧修订。不做这件事的话，一次拖拽会在
撤销栈里留下几十步。

**改尺寸是设计动作**：文档模式放行，表单与只读模式拒绝（版式归作者，填表的人只管内容）。

## 十二、修订留痕与批注

这是本期工作量最大的一块，但**它恰好能被"可逆步骤"大幅简化**。

### 两条路线

**Word / OOXML 路线**：把修订标记写进文档树。插入内容包在 `w:ins` 里、删除内容包在

`w:del` 里（**被删的内容仍然留在文档里**，只是标了删除），格式变更另用 `w:rPrChange`。

每个标记带作者、时间、修订 ID 与 RSID 分组。

这条路线的问题是模型污染：文档树里同时存在"当前有效内容"和"待定的影子内容"，

于是遍历、排版、命中、序列化全都要判断"这个节点有没有被删"。参照项目里

`DomElement` 上的 `Modified`、`DCContent` 与 `DomDocument` 里的修订相关字段，

就是这类污染的痕迹。

**步骤叠加路线**：文档是**基线**，修订是一串**未被折叠的步骤**叠加在基线之上。

接受一条修订 = 把它折叠进基线；拒绝 = 丢弃它（或应用其逆）。

显示时把待定步骤以装饰形式画在视图层。

这条路线是干净的：文档树本身永远只表示"当前内容"，修订是视图态的叠加。

它与 ProseMirror 的 Decoration 是同一个思想——**临时标记不污染真相**，

而"真相"恰好就是我们已经有的可逆步骤。

### 建议

走步骤叠加路线。具体形状：

```
RevisionLog = [{ step, author, time, state }]   state ∈ { pending, accepted, rejected }
```

- 文档内容 = 基线 + 已接受的步骤（展开后）。
- 界面上显示的是"展开后"的结果，`pending` 的步骤以作者颜色与删除线呈现。
- 接受与拒绝只改 `state`，然后重新从基线展开。
- 序列化时基线落盘、`pending` 的修订一并落盘，`accepted` 的已经进基线。

代价要说清楚：**与 Word 互导需要一层适配**，把步骤序列翻译成 `w:ins` / `w:del` 标记。

这是边界适配器的事，与"内部用 JSON"是同一个道理。

### 1.9 的落地结论

模型这一期就把步骤叠加做全（`src/core/doc/revision.h`）：`RevisionLog` 持有**一份基线的独立值拷贝**
（`NodeTree::assignFrom`）加一串有序的修订；`record` 只收内容级五个步骤，`accept` / `reject` 只改状态，
`expand(NodeTree&)` 把"基线 + 全部未被拒绝的步骤"按序应用出来并规范化一次，产物因此与正常编辑路径
的文档逐条相同（判据就是这样比的）。

三条要记住的取舍：

- **基线是存下来的，不是算出来的。** 撤销那条路避免快照是因为"回退快照会让整篇变脏"；修订留痕不同，
  "这些编辑之前长什么样"本来就是它要记住的东西，序列化时也要落盘（1.10）。为它加的是显式入口
  `assignFrom` / `clone`，不提供拷贝构造 —— 整棵树的深拷贝很贵，不该藏在按值传参这种看不出代价的地方。
- **拒绝一条早的修订，后面修订的坐标要搬回来。** 每条修订的坐标是"记录它那一刻的文档"里的坐标，
  展开时按序应用本来天然对得上；但前面某条被拒绝之后，它后面那些步骤的坐标就落在了含它的文档里。
  处理办法是穿过那条修订的**逆步骤**映射一次（`mapStepPositions`，倒着搬：最后被跳过的先搬，
  这样每搬一次时映射的前提都成立）。位置正好落在被恢复内容的插入点上时留在左边。
- **结构步骤与属性步骤不作为修订记录。** 它们的位置含 `Pos`（槽位），单靠流位置映射搬不动，
  硬记下来只会在拒绝别的修订时错位，所以 `record` 显式拒绝并给原因。这是"宁可拒绝，不产出半截"
  这条口径的又一次应用（同 1.2 的区间提取）。

**批注仍不在这一期**：它是"挂在某个节点区间上的附注"，用节点 ID 加区间做锚点，不需要进文档树，
因此"节点 ID 必须落盘"那条不变量在这里派上用场 —— 它随 1.10 一起做。

批注比修订简单：它只是"挂在某个节点区间上的附注"，用节点 ID 加区间做锚点，

不需要进文档树。所以**节点 ID 必须落盘**这条不变量在这里派上用场。

## 十三、序列化形状

接上一轮结论（JSON 做语法、包做容器、压缩做体积，见架构文档 4.5）。模型这一侧要定三件事：

**扁平不嵌套。** 序列化成"节点表 + 样式表 + 属性表 + 子节点索引数组"，而不是嵌套对象。

理由有二：更小（没有嵌套括号），以及更适合差量落盘——嵌套树改一处要重写整个文件。

数据形状是"节点数组 + 每个节点的子节点区间"，本质是把树按深度优先序拍平，

再用 `child_count` 重建层级（这也是上一轮测二进制时用过的 payload 形状）。

**段落不落盘。** 段落是派生量（第二节）：落盘的只有 `ParagraphMark` 元素与它的属性，重新打开时由标记重新导出段落。这样不会出现"段落对象与标记不一致"这类错误。

**ID 落盘。** 节点 ID、控件 key、样式名都要写进文件。

**控件的作者设定落盘。** `controlType`、`readonly`、`required`、`structureLock`、`hidden`、
`format`、`options`、`appearance`（含 `placeholder`）都是作者意图，随控件一起写进文件——
默认可见性、提示文案这些"设计的一部分"必须存得住。
**只有运行时状态不落盘**：`validationState`（这次会话的校验结果，落盘会出现"上次的红框
被打印出来"）。选区同样是会话状态（见下面"选区不落盘"）。

**判据：作者意图落盘，运行时状态不落盘。** 遇到一个新字段不必逐个争论，问一句
"它是设计的一部分，还是这次会话的结果"就够了——默认可见性（`hidden`）、提示文案
（`placeholder`）、约束（`required` / `format`）、外观（`appearance`）、锁（`readonly` /
`structureLock`）都是设计的一部分，落盘；校验结果（`validationState`）、选区、段落实体
是本次会话或本次推导的结果，不落盘。这条判据是 `hidden` 与 `placeholder` 先后被修正为
落盘之后沉淀下来的，写在这里，免得下次再逐个推。

否则重新打开之后，批注锚点、跨文档引用、样式引用全部失效。

代价是文件略大，收益是引用关系可持久。ID 用局部递增的整数而非 UUID，配合符号表编码。

**选区不落盘。** 选区是会话状态（第二节）：序列化只落它的外观选项（高亮色、
是否含背景文字这类），不落选区本身。参照项目就是这么做的——它的 JSON 里与 Selection
相关的只有 `SelectionHightlightMaskColor` 与 `SelectionTextIncludeBackgroundText` 两个键。

**字段名进符号表。** 节点类型、属性名、样式名各建一张符号表，正文里只出现下标。

实测这一条把体积从 84.8% 降到 25.4%（架构文档 4.5.1）。

浮点按十进制字符串写这条已有结论继续适用：坐标、字号、行高都要过

`parse(print(doc)) == doc`。

### 1.10 的落地结论

形状与上面几条一致，另外定死了四件事：

- **JSON 库用 nlohmann/json 3.12.0**（单头文件、MIT），且**只在 `serialize.cpp` 里 include** ——
  它的类型不进任何公共头，换库不动别处的签名。取回方式与校验见
  `docs/依赖与工具链管理.md` 第二节末尾（头文件库走脚本化取回，不走 submodule）。
- **枚举按名字写，不按枚举值写。** 按值写的话，将来重排或插入一个枚举成员，旧文件里的数字
  会静默变成另一个意思；名字不会。为此给每个落盘的枚举配了 `xxxFromName`，
  它拿 `xxxName` 当唯一真相，不认识的名字一律报错。
- **浮点写十进制字符串，9 位有效数字**（float 的往返充分条件），读回用 `strtof` 并要求
  整串被消费 —— 截断的输入要报错，不静默取前缀。
- **写出之前自己校验 UTF-8。** JSON 库对非法字节的处理是抛异常（有异常的环境）或终止进程
  （wasm 关掉了异常），两条路都不该走到。查到了就返回失败并说明是值还是键、多少字节。

**落盘不带两样东西**：摘下的子树（撤销留在池里的节点不是文档内容），以及样式表与资源表
（它们还没挂到 Document 上，随那一步一起进来）。**分配器水位必须落盘**，否则重新打开之后
新分配的 id 会与文件里引用过的 id 撞上。

## 十四、与排版引擎的接口

这是全案最容易出问题的地方，因为它决定"引擎要不要改"。

**保持单向编译。** 树到引擎输入的转换是单向的、可缓存的：

```
Document (树)
  → compile() → 段落序列（每段：书写模式、字体、行距 + 一段"行内盒子"序列）
  → 引擎整形 / 断行 / 分页 / 增量续排
```

引擎仍然只认识"段落 + 段落内的行内序列"，不认识树。而**方案一让这一步几乎是恒等映射**：
模型的流被段落标记切成若干段，就是引擎要的段落序列；流里的元素逐个映射成行内盒子，
容器的边界元素映射成行内叶子，图片、公式映射成不可断的盒子。不需要"把树展开成流"这一步
翻译，因为模型本身就是流——这正是选方案一时的首要理由。

0.4 先落了这条通道的文本子集（`src/core/doc/compile.h` 的 `compileDocument`）：先是只认文本与
段落，段落格式暂借 `BlockSpec` 的形状。随后补上了**成对边界元素**：内容控件的两个边界编成段内的
行内对象（`BlockSpec::objects`），锚点是那一刻当前段已累积的码点数，次序由遍历自然给出；
行内原子（图片、公式）已在阶段 4 补进来（各产一枚 `InlineObject`，盒宽高在编译层定死）；
固定宽度的边界仍未做。

**脏段标记怎么来。** 流顺序就是段落顺序，所以"改动落在流里的哪个位置"可以直接映射到
"第几段变脏"，中间不需要遍历树。现有的 `layout_dirty_from_` 是"一个数"（连成一段的后缀），
这对编辑是够的；但对样式表变更、节变更、批量设值这类**散布式改动**不够用（见第六节末尾）。
先按全量处理，测出瓶颈再扩展成集合。

**引擎真正的新输入有两样。** 一是**行内原子**：图片、公式要作为"不可断的盒子"参与断行，
宽度计入行盒、不能落在行中间被拆开、增量排版要能识别"这一个盒子没变"。
二是**边界元素**：控件的起始与结束边界也是行内叶子，而且**有宽度**
（参照项目取 `max(宽度, 12.5)`，保证鼠标点得着）；设了固定宽度的控件比那条更强，
它是**指定的**宽度（见第七节）。产出端与占位已经落地：编译层把它们编成段内的行内对象
（`BlockSpec::objects`，引擎侧的类型见 `src/core/layout/layout.h`），排版层按对象表插占位簇。
还差两件：固定宽度，以及"结束边界不排到起始边界之前"的显式断言 —— 后者在本实现里由遍历
顺序天然成立（同一处边界上闭的先出、开的后出），写成断言是为了防将来的重构破坏这条性质。
行内原子与这两件都在阶段 4 做专门验证。

**表格是第三样新输入，而它的形状要先定下来。** 引擎的输入现在是"扁平的块序列"，表格要求在
这条序列里表达嵌套（格里有段落，段落里还可能有嵌套表格、控件）。两种形状：

- **扁平化 + 单元格路径**：块序列不变，每个块多带一条"它在哪些格里"的路径（`[表, 行, 列,
  内层表, 行, 列]` 这样的栈）。排版按"格 → 行 → 表"递归：每个格用自己的可用宽度独立排
  （格内的块 = 路径以它为前缀的那些连续块），行高取该行各格高度的大者，表高是各行之和；
  嵌套表格在内层格的宽度里递归同一个过程。
- **嵌套表块**：输入本身长成一棵树（表 → 行 → 格 → 块序列）。结构上不可能把块挂错格，
  但增量那一套（`ParaIndex`、前后缀复用、续排状态）都要改成在树上工作。

建议选扁平化，四条理由与四个条件：

1. 帧、画布、增量、光标、命中全建立在"扁平行盒序列"上，换成树要动的是整条链路；
2. 排版产物无论如何都要加一张**单元格表**（矩形、逻辑行列、原点格、所在页、页内片段号）——
   一个格的矩形不由某一行决定，`LineBox` 推不出来，所以产物的形状与输入形状无关；
3. 路径由编译层在下钻树时顺手写出来，它编不出错的路径；再加一条判据"每个块的路径与树一致"，
   嵌套输入那点结构保证就补回来了；
4. `LineBox` 只多带一个格下标，命中、光标矩形、选区裁剪全从单元格表派生。

**一条边界要写下来：表格是块级容器**，它切断当前段落（Word 也是如此，表格不能行内插在一句话
中间）。格子里放控件、放嵌套表格都不需要新概念 —— `acceptsChild` 对单元格是"什么都收"，
流索引也已经给表 / 行 / 格各算了一对边界位置，所以"格里的位置"本来就是流位置。

**跨行合并的格与行高的关系要在第一刀就定**：`rowspan > 1` 的格比它覆盖的那些行高时，多出来的
高度怎么摊（摊给第一行 / 平均摊 / 摊给最后一行）会影响行高算法与判据。第一刀建议"只算进它
覆盖的第一行"，Word 那种"不足时把差额摊给各行"留到后面。

**不变量的对应关系。** 引擎已有两个可证伪判据（`auditFrame` 逐像素、`auditLayout` 逐字段）。

模型层要补第三条：**编辑往返判据**——随机生成编辑序列，全部应用后再全部撤销，

文档必须与初始状态逐字段相同。这条判据覆盖的是模型层，与引擎的两条互补。

实现 0.1 时有三个约定需要写死，它们决定后面所有步骤能不能共用同一套坐标：

- **流位置按码点级展开**：文本节点占"码点数"个位置，其余叶子各占一个，
  容器占"起始边界 + 全部子节点 + 结束边界"。粒度与光标一致，
  所以"流位置到行内盒子下标几乎恒等"（差别只在簇与码点）。
- **根不含边界**：Document 不嵌在别处，没有任何位置指向"根之前 / 之后"，
  所以它的展开只有内容。
- **容器的槽位数是 `children.size() + 1`**，于是**空容器只有一个内容槽位** ——
  它的"内容起点"与"内容终点"是同一个流位置。空容器上仍然互不相同的三处是
  "容器之前 / 内容 / 容器之后"（起始边界与结束边界各占一个流位置），
  这才是上一轮四个边界缺陷的正面判据。

- **标签是控件内容**（第七节），所以它按普通文本节点参与展开 —— `flow.cpp` 不需要为
  "标签展开码点级位置"单写一套规则。这是把标签定成"内容"而不是"属性"的收益之一。
- **`FlowIndex` 带可见性口径**：编辑态（`Design`）隐藏的控件照常参与流；表单与只读

0.5 的长度层定了几条，它们决定"模型存什么、引擎吃什么"这条边界的形状：

- **模型存整数、引擎存浮点，编译是唯一的接缝**：`Emu`（1/914400 英寸）与 `Length` 都在模型层，
  `BlockSpec` 仍然是磅值。换算只在 `compileDocument` 里做一次，所以这条边界只有一处实现，
  改错了立刻会被 0.4 那条"逐字段一致"的判据抓住 —— 它现在顺带证明了长度换算的精确性。
- **五种性质不是五个数，是一个带标签的联合**：`Abs` / `Percent` / `Em` / `Chars` / `Auto`。
  比例存分子分母（按 gcd 约分、分母恒正），倍数按千分位取整，于是落盘与比较都不经过浮点。
  分母为 0 不是可表达的比例，构造它得到的是自动值，而不是一个拿 0 做除法的长度。
- **文本形式自带类型前缀**（`abs:` / `pct:` / `em:` / `chars:` / `auto`）：这一层要的是
  `parse(print(x)) == x`，所以不写成 `2.54cm` 这种可读形式 —— EMU 换算成磅常常是无限小数
  （12700 含因子 127），有限位数会丢精度。可读形式留给视图层。
- **解析严格**：不符合语法的输入一律拒绝，不跳空白、不截断、不夹取。静默纠正会把"文件坏了"
  变成"读出来一个别的值"，比报错难查得多。
- **不做求值**：`Length → EMU` 需要一个参照（字号、容器宽度、字符宽度）。没有参照的求值只能猜，
  等真有使用它的那一步（表格列宽、首行缩进、控件固定宽度）再把参照带进来。
- **行距三态仍是独立的一步**：`line_factor` 还是浮点倍数（三态里的 `auto`）。`exact` 与
  `atLeast` 要改引擎的块轴推进公式，不塞进这一步。

1.1 的规范化层定了几条，它们决定"形状"这件事由谁负责：

- **只做两件事**（`src/core/doc/normalize.h`）：相邻且标记集合相同的文本节点合并成一个、
  清理空的文本节点。两条边界都不越：跨容器不合并（容器边界是结构），空容器不清除
  （"删空的控件"是合法状态，有身份、有属性，与空 run 不是一类）。空 run 之所以可以清掉，
  是因为它不承载任何字符、也没有身份。
- **规范化与编辑步骤解耦，在事务提交前统一跑一次**（见 1.2）。步骤只做最小改动，否则逆操作
  会还原出"未规范化"的中间态，往返判据失效。由此推出不变量检查器的口径是"已提交的文档"：
  事务内部的中间态可以暂时不满足"相邻同标记必须合并"。
- **结构体表示让半条规则消失**：标记用"结构体 + 可选字段"而不是键值列表，"无重复"与
  "顺序固定"在表示上就不可违反，不另立检查（写个恒真检查比不写更差）。余下的零宽标记区间
  要等 1.2 的临时带标记区间。
- **规范形状唯一**：合并可结合、清空幂等，所以输出与处理顺序无关，跑第二遍没有任何改动。
  判据因此可以只读改动读数，再加一份结构化快照兜住"改了却没计数"。

1.2 的区间与步骤层定了几条，它们决定"编辑"这件事的形状：

- **可编辑集合是文本与段落标记**。含其它元素的区间在提取时就被拒，并写明是哪一个
  （`ExtractResult` 带原因）：把控件整棵取出来需要节点级的片段，而节点级步骤
  （`InsertNode` / `RemoveNode`）属于后面的步。这一版宁可拒绝，也不产出一个半截的片段。
- **端点外扩只对非空区间做**。光标（空区间）不扩 —— 它取不出东西，扩了反而把"点在控件里"
  变成"选中整个控件"。非空区间按端点在区间里的角色扩：起点收到单位起点、终点放到单位终点，
  方向（anchor 在哪一端）保留。
- **不可半分单位由"是不是分段容器"决定**。控件、表格与它的行列、链接不可半分；文档、节、
  引用、代码块、列表项是分段容器。端点落在文本内部天然合法，原子只占一个流位置、没有"严格
  内部"这种位置，所以两者都不需要特殊处理。
- **步骤只做最小改动，规范化不参与**。插入时若紧邻的文本节点标记相同就并入它（插入不该平白
  造出一个同标记的邻居），删除时把两端所在的文本节点截断而不是切成两段。于是"应用加逆操作"
  能精确相消，这正是往返判据成立的前提。规范化在事务提交前跑一次（1.1），所以往返判据的
  次序是"应用 → 规范化 → 逆应用 → 规范化"。
- **位置映射的边界由 `assoc` 表态**。插入点上、删除区间两端的整数位置各有两个合法归宿，
  这是唯一能表态的地方。往返判据的口径因此是明确的：区间之外的位置用同一个 `assoc` 映射过去
  再映射回来必须回到原处；被删区间内部的位置没有原像，一律塌到区间起点，这一段是单向的。
- **节点级步骤的坐标是 `Pos` 加一个流位置**（`InsertNode` / `RemoveNode` 各带 `at` 与
  `at_flow`）：`Pos` 说明动的是哪个槽位（第四节：节点级 API 用 `Pos`），流位置让位置映射不必
  读文档 —— 两份记录由 `canApply` 互相核对，对不上就拒（"步骤过期了"），所以这份冗余不会被误信。
  子树自己会算跨度（`NodeSpec::span`，与 `FlowIndex` 同口径），映射因此是纯算术。
- **节点级步骤带"已经摘下的子树"的身份**：构造 `InsertNode` 时先把子树物化成一棵不在树上的
  子树，应用与撤销就是 `attachChild` 与 `eraseChild` 这一对，同一棵子树的 id 在往返中不变。
  判据因此必须用**带身份的快照** —— 只比内容的话，"重造一棵内容一样的"也会被当成通过。
- **"含整棵节点的区间"仍然不能提取**（选了含控件的一段去复制）。控件走节点级步骤，而区间提取
  只支持文本与段落标记；这条限制写成了一条断言，好让"还没做"是可发现的，而不是让人以为已经
  支持。要做它需要"节点级片段"，这是下一步的事。

1.3 的事务层定了几条，它们决定"撤销"这件事的粒度：

- **事务 = 步骤序列 + 编辑前后两份选区 + 提交说明**（`src/core/doc/transaction.h`）。撤销按逆序
  应用逆操作，所以不需要文档快照 —— 快照式撤销会让整篇变脏，直接击穿增量排版。
- **不做合并：一笔编辑就是一个撤销单位**（`UndoStack::commit` 直接压栈）。事务层一度有过
  "相邻连续输入并成一个单位"的规则，但那只对 `InsertText` 成立（退格是另一种步骤），于是同一
  件事有了两种粒度：敲五个字一步退、退五个字要五步。粒度宁可细一点，也不要把两件事并成一件。
- **撤销栈有深度上限**（`EngineConfig::undo_limit`，默认 **100**，0 表示不限制）。超出时丢最旧
  的 —— 与 Quill 的 `maxStack` 同一条口径；100 这个数也与 Office 系（Word / Excel / PowerPoint
  默认保存最近 100 个可撤销操作）和 Quill 的默认值一致。粒度比它们细（没有 Quill 那样的时间
  合并窗口），同样 100 条覆盖的输入更短，嫌少就调这个数。上限只影响栈，不影响呈现。
- **规范化在提交时跑一次**，不在每步跑。它只改节点边界、不改流位置（合并同标记的相邻文本节点、
  清理零宽 run 都不改变长度），所以提交之后逆操作用的坐标依然成立：撤销能直接在规范化之后的
  文档上工作，不必再记一份"规范化前"的坐标。这条性质有单独的断言守着。
- **选区快照与位置映射是两条互补的路**：映射管一次编辑之内位置的跟随（调用方用 `mapPos`），
  选区快照管跨撤销单位回到原处（撤销写回编辑前选区、重做写回编辑后）。
- **提交中途失败整条作废**：已经应用的步骤按逆序撤回，文档与栈都回到提交前。半个事务留在文档
  里，比失败本身难查得多。

1.4 的控件与落点层定了几条，它们决定"表单模式到底限制什么"：

- **`EditMode` 住在模型层**（`src/core/doc/edit_mode.h`）。三档是同一份文档上的策略差异，
  模式值属于模型：编辑能力（`edit_capability`）、可见性（`compile`）与宿主门面共用这一个
  定义，引擎只把它存成一个字段。
- **落点判定是纯查询，不改文档结构**（`src/core/doc/edit_capability.h`）。可编辑集合是一个
  **交集**：包住这个位置的每一层 `ContentControl` 都允许，位置才可编辑 —— 于是只读控件里嵌一个
  可编辑控件时，那个内层位置仍然不可编辑。实现上是沿"哪个孩子严格包含这个流位置"一路下降，
  收集祖先控件链，逐层判 `readonly`。
- **落点由"光标 / 选区"两条口径分开**：选区端点自由（拖选、Shift 扩展、全选都跨得出去），
  插入点受限 —— 表单模式只在可编辑集合内，只读模式一个都不出现。方向键因此走不出字段，
  换字段用 Tab；Tab 按"内容起点在可编辑集合内"挑目标。理由与实现见第七节。
- **Tab 的判据复用同一个谓词**：一个控件是 Tab 落点，当且仅当它的内容起点在可编辑集合内。
  于是"只读控件"与"只读控件里的可编辑控件"被同一个条件挡掉，不必另写一套嵌套判定。文档模式
  不消费 Tab（那里它是制表符，默认键位由宿主定），只读模式放行（吞掉会变成键盘陷阱），
  表单模式没有下一个可编辑控件时同样放行。
- **非空编辑区间多一道闸门**：两端可编辑之外，区间**不允许整块包住一个只读控件** —— 只查两端
  会漏掉"跨过只读控件"，而它恰好能删掉只读控件的全部内容（含它的一对边界），把 `readonly` 绕开。
- **结构操作锁 `structureLock` 默认 `true`（锁住）**，只在表单模式生效：文档模式放行（作者在
  设计表单），只读模式一律拒绝。这与第七节"默认控件不可删"是同一件事，字段按"锁"的方向命名，
  默认锁住。

**这一层只回答"该不该"，不分发按键。** 方向键与 Tab 的实际键位绑定、`insertTab` 默认不绑键、
以及"点了没反应"的外观提示，都在命令层与宿主（`EditCapability` 只给出目标位置或放行信号）。
点击落点的几何（哪个像素对应哪个流位置）仍是引擎侧命中测试的产物，这一层吃的是它算出的流位置。

1.5（控件索引与值读写、外观与异步裁决）定了几条，它们决定批量、回填与异步校验这件事的形状：

- **索引是两张表 + 挂在步骤上的维护**（`src/core/doc/control_index.h`）：表一 `id` 到业务编码，
  表二是 `key` 到控件列表（**一对多**，同一个 key 绑多个控件是合法状态）。顺序枚举走一遍树 ——
  枚举本身就是要 O(n)，不值得再维护一张顺序表。维护的语义分工是：**文本级步骤什么都不做**
  （敲字是最高频的路径，控件索引不该为它付代价），结构级步骤只碰被增删的那棵子树。
  跟不上的步骤（序列化还原出来的 `InsertNode` 没有子树身份）返回"跟不上"，由调用方重建 ——
  宁可多做一次重建，也不静默维护错。
- **一次调用 = 一个事务**：四个 setter 的入参都是数组，数组本身就是批量，一次调用合成一个事务
  ⇒ 一个撤销步骤。要按 id 与按 key 混着设、或者值与属性一起设，用 `beginBatch` / `commitBatch`
  把几次调用包住，仍然是一个撤销步骤。
- **同一次调用里同一个目标重复时后者覆盖前者**（与逐条调用一致）。实现上先解析目标、顺序去重只留
  最后一次，于是"要改几个控件"与"改了哪几个"两件事都能在构建步骤之前算清楚。
- **值分两半，落点不同而 API 相同**：文本类的值在内容里，走"逐个摘掉现有子节点 + 插一个文本
  节点"（节点级步骤，比区间删除更直接，也不受"区间编辑只认文本与段落标记"的限制）；Bool / Enum /
  List / Resource 的值在记录上，走 `SetControlValue` 步骤（带原值，逆操作自足）。`getValue` 按
  值形态读对应的那一半，所以调用方只看值形态，不看落点。
- **属性入口只收四个**（`hidden` / `readonly` / `required` / `structureLock`），一次只改一项，
  `SetControlProp` 步骤带着原值所以逆操作自足。**含 `hidden` 的批次标 `needs_relayout`** ——
  它改的是呈现态的流结构（那是重排，不是把某个位置搬到别处），所以这一步的位置映射是恒等。
- **取值与将来的选区复制共用一套拼接规则**：文本节点贡献文字、段落标记贡献换行、嵌套控件的内部
  内容按普通文本取出、域与图片公式暂贡献空串（两处一起补）。**隐藏的单个节点不贡献文字** ——
  取的是用户在表单与打印里能看到的那份。
- **同 key 值不一致是可发现的状态，不静默取一个**：`getValueByKey` 带上 `inconsistent`，
  `inconsistentKeys` 给出按 key 去重的清单。

1.5 的后一半（外观、属性侧的值与异步裁决）也定了几条：

- **外观是设计期属性，不走属性入口**（第七节）：改它等于重新定义控件，所以直接写在记录上，
  与标签（内容）和四个运行时策略（走 `setProperties`）分开。`Appearance` 里 `width` 是带类型的
  长度（不丢 Abs / Percent / Em / Chars / Auto），`border` 四边各自独立，`glyph.kind` 是字符串
  —— 加一种图元是加数据，不改枚举、不改格式。`placeholder` 是独立字段，进不了内容，
  所以 `getValue` 不会把它当值取出来。
- **校验规则引用是名字，不是代码**：`validateRef` 存在记录上，宿主把它映射到自己的钩子。
  这条与控件事件同一条判据 —— 绑定是数据、代码是程序，凡"换一个宿主仍要生效"的只能是数据。
- **异步裁决门的语义是"持有候选变更，裁决通过才应用"**（`src/core/doc/validation.h`）。
  登记候选时控件进 `pending`，**文档与撤销栈一概不动、也不显示新值** —— 所以不存在
  "先勾上再弹回去"的那一帧。`allow` 才把它当普通事务应用（此时才产生撤销步骤、才排版上屏）。
- **一个控件同时最多一个等待**：同一控件再次交互时前一次按取消丢弃（最后交互为准），
  旧结果到达时返回 `Dropped`。四态而不是布尔：`Dropped`（这次等待已作废）既不是通过也不是拒绝，
  更不该被当成失败去提示用户。
- **超时不静默放行**：`expire` 等价于 `Deny("校验超时")`。放行一颗从未校验过的复选框比不放行更危险。
  计时在宿主 —— 模型层没有时钟，也不假装有。
- **锚点失效就丢弃，不做补偿**：等待期间文档可能被别的编辑改过（控件被删、段落被合并），
  结果到达时先确认锚点仍指向同一个控件；失效则丢弃。补偿只会把一次已经过期的决定硬套到新内容上。
  ★ 判"锚点还在"**不能只看按 id 查得到**：被摘下的子树留在池里（撤销要把它们原样挂回，
  所以节点不销毁、id 不回收），按 id 照样查得到它。要连"挂没挂"一起判（`isAttached`）——
  只看非空会把已经删掉的控件当成活的，裁决结果就写到一个不在文档里的位置上了。
- **只拦用户交互，不拦编程设值**：`setValues` 是 `program` 源，不进这一层，所以批量路径完全同步
  —— 批次里不会出现"一半在等异步、一半已提交"的混合状态。反过来说，编程设值也不会取消等待。
- **校验状态是运行时状态，不落盘**：`pending` 与 `invalid` 都在内存里，重新打开由宿主重算；
  它不进 `ControlSpec`（那个结构是随控件落盘的），所以"上次的红框被打印出来"在结构上不可能发生。
- **控件类型注册表**（`registerControlType`）推迟到 1.7。它注册的是默认值形态与默认校验引用，
  唯一的消费者是新建控件与导入外部文档；两处都还没落地，现在做它只剩一张没人查的表。

1.6（样式与三层解析）定了几条：

- **元素只存差异，完整形式是算出来的**：段落标记挂 `ParaFormatPatch`（九个字段各自三态），
  文本节点挂 `CharFormat`（本来就是三态）。两者都是"未设置即继承"，与 OOXML 的
  `w:pPr` / `w:rPr` 同一个口径。挂完整形式等于处处都是内联覆盖，样式再也起不了作用 ——
  这不是洁癖，是把样式表变成一个死字段。
- **样式引用是节点上的一个字符串字段**（`Node::styleRef`）：段落标记上指段落样式，文本节点上
  指字符样式。两种含义共用一个字段，与 `para` / `marks` / `control` 一样按种类取用 ——
  解析里它们本来就是两条独立的链，节点上不需要两个字段。
- **样式引用是内容的一部分，凡是搬内容的地方都要带上它**：`NodeSpec`（节点级步骤与撤销）、
  `Piece`（复制粘贴）、`InsertText` / `InsertParaMark` / `RemoveParaMark`（三个内容级步骤）
  都记它。少一处就是"复制一段带样式的段落，粘回来样式没了"这类静默丢格式。
  `insertTextAt` 的并入条件因此也要比样式引用：只比标记会把"同标记但字符样式不同"的两段文字
  合成一个节点。
- **解析在编译时做一次，产物给引擎**：引擎不认识样式表。非绝对长度的诊断、未知样式名与成环
  的诊断都在这一刻汇总进 `CompileResult::diagnostics`，于是 `ok()` 一个判断就能让调用方
  知道"这份产物不能当完整结果用"。
- **缓存按元素加样式表版本号**（第六节），版本号由 `StyleSheet` 的每个改动方法推进 ——
  没有拿到内部引用的可变访问器：漏推一次的表现是"改了样式但屏幕上没变"，很难查。
- **段落没有身份，所以撤销段落标记是"造一个新的"**。判据因此比形状而不是比节点 ID ——
  要求 ID 不变等于给模型加一条它本来没有的约束（第二节：段落标记的身份是流位置）。

1.7（表格）定了几条：

- **跨度是唯一真相，网格是派生的，续格不存在**（第九节）。这条与"段落不是节点、是流里的范围"
  是同一个路子：模型只存作者改得动的东西，其余每次推。收益是"续格不能有独立内容"这条不变量
  由结构本身保证，代价是行列操作必须先算清楚哪些格子被跨过。
- **行列操作不新增步骤类型**：先算跨度怎么变，再用既有的 `InsertNode` / `RemoveNode` 与一条
  新的 `SetTableCellSpan` 组合成一批，一批一个事务。撤销、位置映射、不变量检查因此都复用
  同一套机制，不必为表格另写一遍。
- **批次里每步的坐标属于它自己那一刻**：后面几步要按前面几步的位置映射推过去
  （`pushMappedStep`，与批量设值共用同一份实现）。方向键走一步不会有这个问题，凡是"一次把
  所有步骤建出来"的都会。
- **不可构造的检查要标出来**。"无重叠"与"续格紧邻原点格"数据层构造不出反例，它们留在推导里
  当守卫，不算在"查过了"的范围里（第二节列了那张表）。把它当成已覆盖，等于给自己一个
  虚假的安心。
- **两条边界显式拒绝**：删最后一列、删最后一行；新插入的行里不许有 `rowspan > 1` 的格子。
  留下"有行没有格"的表格是合法的但没有意义，不如说不支持；跨行合并请在插入之后做。
- **结构操作在表单模式下默认锁住**（与控件结构的默认一致）。第九节说这个开关挂在被操作的
  元素上，而那个开关要等表格自己成为控件才有地方挂 —— 在那之前按"默认锁住"处理。

1.8（域与节）定了几条：

- **域只存种类与缓存值，值由求值写入**（`src/core/doc/field_spec.h`）。缓存值随域落盘，重新打开
  时先显示已有的值而不是空，但它是派生值：求值函数不接收事务、也不返回编辑步骤，所以在结构上
  不可能往撤销栈里塞东西。四种取值都只依赖上下文（页码 / 总页数 / 打印日期 / 文档属性），
  于是"同一份上下文跑两遍结果相同"是幂等的全部内容，第二遍的更新计数为 0。
- **只有排版结果类需要迭代**：页码与总页数依赖上一轮的页数（页脚同时写两者时互相追着跑），
  打印日期与文档属性来自文档之外、取出来就固定。`isLayoutResult` 是这条分类的唯一判据。
- **文档属性缺失给空串**：属性缺失是常规状态，不猜也不报错。域在流里是原子（占一个位置、
  参与断行），含域的区间与含控件一样被拒并给出原因 —— 取不出整块就不产出半截片段。
- **节的纸张只存名称与方向，尺寸派生**：只有自定义纸张才存显式宽高，且必须是绝对长度，
  否则给零尺寸（没有参照的长度推不出 EMU）。横向是交换宽高，不改写规格本身。
- **能存住、不必全理解**：装订线、镜像页边距、垂直对齐、书写模式、页码设置都进记录，
  引擎不认识的页面设置（打印机设置、兼容性标记、主题色）进属性袋 `extra`。节记录因此不提供
  按值相等的默认实现（书写模式没有相等比较），比较用 `sameAs`，它连属性袋里的一个键都比。
- **页眉页脚是独立的内容片段**，由节的记录按三组变体（首页 / 奇数页 / 偶数页）引用。
  片段根是新的一种容器（`NodeKind::HeaderFooter`），它**不在正文流里** —— 位置换算、段落序号与
  正文编译都看不到它，走自己的 `compileFragment`，但复用同一套块级节点与三层样式解析。
  `linked_to_previous` 默认真：不设就是继承前一节，显式断链才独立。
- **分节强制分页落成引擎已认识的段前分页**：进入第二节及以后时，若节类型不是连续，就把下一个
  落下的段落标上段前分页。于是分节不引入新的排版路径，"与全量一致"由引擎既有的段前分页机制
  保证（判据在 `tests/edit_test.cpp`：模型编译产物喂给引擎，分页之后增量与全量逐字段一致）。
  奇数页与偶数页现在与下一页等效，补空白页要引擎支持页码奇偶。
- **按节生效的页度量还没有**：引擎的 `PageMetrics` 只有一套（单一页宽与单一边距），所以模型把
  纸张与四边页边距完整存住，但真正按节生效要等引擎支持"同一篇文档里页宽不同"。这是第十节
  那条待确认项的落地结论，不是模型的缺口。

1.9（修订留痕）定了几条：

- **文档树只表示当前内容，修订留在文档之外**（`src/core/doc/revision.h`）。把修订标记写进树会让
  遍历、排版、命中、序列化全都要判断"这个节点有没有被删"，模型从此被污染。步骤叠加把这件事留在
  视图态：树永远干净，修订是叠加。
- **基线是一份独立的树值拷贝**，由 `NodeTree::assignFrom` / `clone` 提供。不提供拷贝构造：
  整棵树的深拷贝很贵，隐式拷贝会藏在看不出代价的地方（按值传一个 `NodeTree`）。
- **接受与拒绝只改状态，展开由它算出来**：`expand(NodeTree&)` = 基线 + 全部未被拒绝的步骤，
  按记录顺序应用，最后规范化一次（规范化是为了与正常编辑路径的产物可比 —— 那条路在提交时规范化）。
  于是"接受之后展开成什么样"是可手算比对的，这正是这一步的判据。
- **拒绝一条早的修订要把后面修订的坐标搬回来**：每条修订的坐标属于"记录它那一刻的文档"，
  前面某条被拒绝后，它后面那些步骤的坐标就落在了含它的文档里。穿过那条修订的**逆步骤**映射
  （`mapStepPositions`），倒着搬（最后被跳过的先搬，映射的前提才成立）。位置正好落在被恢复内容
  的插入点上时留在左边（`Assoc::Before`）。
- **结构步骤与属性步骤不作为修订记录**：它们的位置含 `Pos`（槽位），单靠流位置映射搬不动；
  `record` 显式拒绝并给原因，不产出一个会在拒绝别的修订时错位的记录。
- **展开失败不交半成品**：某条修订应用不了（坐标过期、越界）时返回失败并写明是哪一条，
  同时把目标树还原成基线 —— 展开到一半的文档比"展开失败"难查得多。
- **记录这一层不校验坐标**：`record` 手里没有文档，无从判断位置是否越界；越界在展开时才暴露。
  这是刻意的分工，不是漏检。

1.10（序列化）定了几条：

- **扁平不嵌套，按深度优先序拍平**（`src/core/doc/serialize.cpp`）。每个节点只记自己的孩子个数，
  孩子就是紧跟其后的那一段 —— 比给每个节点写一串孩子 id 更小，也仍然是一次线性读。
- **符号表只收重复出现的开放集合**：节点种类名与名字字符串（样式名、控件业务类型与 key、
  校验规则名、语言标签）。属性名本身是封闭的一小组短键（一到三个字符），为它们建表只会多一层
  间接、省不下字节 —— 这一条与"字段名进符号表"的原始措辞有出入，理由是那份实测里的键名来自
  XML 标签名（长且重复），而本格式的键名本来就短。
- **默认值不写**，缺失即默认值。于是读端的分工很明确：键不存在就跳过，键存在而类型不对才报错。
  这一条最容易漏的是那些"默认值为真"的字段（`structureLock`、`linked_to_previous`），
  它们只在放开时写。
- **id 必须原样回来**，所以还原不走 `insertChild`（它会另分配 id），走
  `reset` + `createDetachedWithId` + `attachChild`。水位也照记录推进：
  文件里的水位可能比现存最大 id 还大（保存前删过节点）。
- **先在临时树上装好，成功了再交给目标树**。读坏了目标树一个字节都不改 ——
  "给了失败回执"与"文档没变"必须是同一件事，否则调用方会在一个半截的文档上继续干活。
- **摘下的子树不落盘，但它占过的 id 要留着**（水位带过去）。所以"保存再打开"之后
  新分配的 id 仍然不与旧 id 撞上，即使那些旧节点已经不在文件里。
- **反序列化不校验不变量**：检查器是独立的一层（0.3），读回来之后由调用方决定跑不跑。
  序列化只保证"写出去的能原样读回来"，把两件事混在一起会让"文件坏了"与"文档不合法"分不清。

0.2 的元素流与分段也定了几条，它们同样决定后面能不能共用一套坐标：

- **改结构只有两条路径**：`insertChild`（在第几个槽位插入什么）与 `eraseChild`
  （摘下第几个孩子，连同它的子树）。不提供第二种插入方式（例如"插到某个兄节点之后"）——
  不变量检查器（0.3）与派生索引的增量维护都要挂在每一条改动路径上，多一条就多一处能漏掉的地方。
  摘下的节点留在池里、ID 不回收：撤销要把它原样搬回去，而"搬回去"要求身份不变。
- **这两条原语属于 0.2，不属于 1.2**。1.2 的编辑步骤（逆操作、位置映射、撤销分组）建在它们之上；
  之所以在 0.2 就给出，是因为本步的判据要求"插入删除后仍相同"——没有增删就没法验增量维护。
- **分段的口径**：容器的孩子里标记的下标是 `m1 < ... < mk`，第 j 段是孩子在
  `[m(j-1)+1, mj]` 上的范围（`m0` 记作 -1），也就是说**标记属于它结束的那一段**。
  于是"段落序号 = 该槽位之前的标记个数加一"在容器内成立。内容末尾还没插入标记时，
  那一段照样算一段（只是没有属性宿主）；而"内容末尾那个槽位"的序号可以比段落数大 1，
  因为它属于还没开始写的下一段。空容器是 0 段。
- **段落索引与流索引分成两个类**（`ParagraphIndex` 与 `FlowIndex`）：它们的变化面不同 ——
  改一个字符只动流位置、不动标记数组；插入删除一个元素才动数组。合成一个类会让"改文字"
  这条最高频的路径也背上重建标记数组的成本。可见性口径两者共用 `FlowVisibility`，
  该枚举现在放在 `node.h`（它的成因是 `Node.hidden` 这一条属性，两个派生索引都只是受它影响）。
- **增量维护要管到"被增删的子树自己"**：插入一个容器时它自己也多一条记账项，
  摘下一棵子树时它内部所有容器的记账项都要去掉。判据（每步与重建结果整体比对）
  第一次跑就抓出了这处遗漏——只维护父容器那条数组是不够的。
- **第四节的全局段落序号不在这步**：它要流位置参与，而流位置属于流索引；两者的组合
  留给真正用它的那一步（1.2 的脏段标记），避免这一步先造一张没人调用的全局表。

位置换算还有一条规范化约定：**同一个流位置有多种 Pos 写法时取最内层**。
例如"容器的第 0 个槽位"与"第一个孩子的第一个位置"是同一个流位置，
换算一律返回后者（在文本里就报文本内的偏移），编辑时才好判断"字要插进谁里面"。

## 十六、未决项与已定项

本节每条都标了状态：**待确认**（需要一次探针或一次选型才能定，会影响排期）、
**待测**（做法已定，判据待实测）、**已定**（决策记录，实现时照它做）。

### 待确认（按优先级）

**一、分节要不要本期做（1.8 已定，见"已定"第十二项）。** 分节就是 Word 里"不同纸张"那个功能，

但不止纸张——页眉页脚、页码重编、分栏、文字方向都能按节变化，见第十节。

它是唯一会让页度量在文档中途改变的机制，而页指纹与增量上屏现在按"页"组织。

建议先做一次探针：构造一篇两节的文档（前节 A4 纵向、后节 A4 横向），

跑 `auditFrame` 与 `auditLayout`，看增量结果与全量是否逐像素 / 逐字段一致。

一致则本期可做分节，不一致则本期只支持单节。

**二、修订留痕的互导要求。** 若病历必须与 Word 或院内系统交换带痕文档，

步骤叠加路线要多写一个 `w:ins` / `w:del` 适配器，需要单独排期。

**三、公式的排版后端**（架构文档已有此项）：本期只要"能插入、能显示、能存"，

还是"可编辑、可参与计算"。

### 待测（做法已定，判据待实测）

**四、异步校验钩子的 pending 呈现。** 钩子返回 Promise 时，编辑器悲观持有候选变更、
控件停在 `pending`，等待期间文档与撤销栈必须逐字段不变。判据：
用一个人为延迟 200 ms 的钩子做探针，等待期间 `auditLayout` 全等、
撤销栈深度不变、控件不显示新值；`Deny` 后值与校验状态与交互前一致。

**五、批量设值的脏区。** 批量设值会让脏区散布全篇，`layout_dirty_from_`
这个"一个后缀"的表达可能不够用。先退化全量、测出真实数字，再决定是否把脏段标记扩展成集合。

### 已定（决策记录）

**六、表格（决策见第九节）。** 跨页拆两半显示、被合并格位返回原点、模型里续格不存在。

待验的是 `buildGrid` 与分页器的配合，放在阶段 1.7 的判据里。

**七、内容控件在段落内的嵌入位置（方案一）。** 段落降为流里的范围、控件是跨度之后，
"行内嵌入"（`主诉：[____]`）与"一栏里多段"是同一个机制的两个取值，不需要
`InlineControl` / `BlockControl` 两个类型，也不需要"行内升级为块级"的提升规则。见第三节。

**八、固定宽度下值超出时的显示行为（属性配置）。** `overflow ∈ { expand, clip, spill }`
三档，默认 `expand`（不静默丢数据）；`clip` 与 `maxLength` 的一致性由诊断守。
不做"控件内横向滚动"——控件是流里的跨度、没有滚动视口，值超出只有这三档处理。
见第七节。

**九、浮动图片与文字环绕（本期只做内联，模型留位）。** 内联图片只是一个不可断的行盒，

引擎已有这类盒子的处理路径（括号占位就是这么做的），成本低。

浮动图片的成本**几乎全在引擎侧，模型侧近乎为零**：

| 能力             | 需要动的地方                                |
| -------------- | ------------------------------------- |
| 浮于文字上 / 下（不环绕） | 段落外新增浮动层 + 光栅分两趟绘制                    |
| 四周环绕           | **断行核心**：每行的可用宽度不再是一个常数，而随浮动框横向范围变化   |
| 绝对定位与锚点        | 图片挂在某段上但显示在别处；跨页时要定跟随规则               |
| 增量             | 浮动框移动会让影响范围内的**所有行**重排，脏区不再是"连成一段的后缀" |

后两行是与现有架构冲突的地方：断行"左右边界是常数"与脏段"后缀"两个假设都要改。

所以分期做：本期内联；下一期做"浮于文字上下方"（不动断行）；最后才做环绕。

模型这边只需在 `Image` 上留好定位方式与环绕方式两个枚举，节点类型不变，

所以**先留位、后补引擎**不产生返工，它也不该拖住阶段 0 与 1。

**十、页面设置的读写范围。** 真正生效的是纸张、四边页边距、页眉页脚、页码；

其余（装订线、镜像页边距、分栏、垂直对齐、页边框、行号、脚注尾注、文档网格、

打印机设置、兼容性标记、保护与权限）本期只原样存住、不参与排版。完整清单见第十节末尾。

**十一、渲染形态的扩展路径（基元 / 图元 / 配方 / 图片）。** 页面内容一律由引擎绘制，所以
"自定义绘制"只能是"用引擎的基元组合出图形"，不是给宿主一段绘制代码。分两层：**基元**
（引擎的绘制能力，闭集）与**图元**（基元构成的具名图形，内置若干、宿主可注册）。
`appearance.glyph.kind` 用**字符串**，注册新图元不改格式；宿主注册图元时给的是**配方**
（基元名加相对几何加样式槽，是数据不是代码），于是自定义外观仍进得了打印导出、两个后端
也一致。配方表达不了的（签名笔迹、图表、位图 Logo）走**图片资源**。**不允许**宿主提供
决定页面内容的绘制回调——只能用于编辑期辅助。**图表（体温单这类数据驱动图形）是引擎的
另一种绘制能力、与图元平行，不是图元的特例**（图元与配方画静态图形，图表画数据到几何的
映射）；本期不做，边界先定。依据与先例见第七节。

**十二、分节的模型与生效范围（1.8 决策记录）。** 文档模型这一期就把节做全：纸张（名称加方向）、
四边页边距、装订线、镜像页边距、节类型、垂直对齐、书写模式、页码设置、三组页眉页脚引用，
外加一个装未知页面设置的属性袋；多节的结构、按序访问、页眉页脚片段与分节强制分页都已落地并
有判据。**真正按节生效的只有分页行为**（节类型落成引擎已认识的段前分页），纸张与四边页边距
在引擎侧仍是全篇一套 —— 引擎的 `PageMetrics` 只有单一页宽与单一边距，容纳"同一篇文档里页宽
不同"是引擎侧的活。这条边界与第十节"能存住、不必全理解"是同一条：模型存全，引擎按需理解。
