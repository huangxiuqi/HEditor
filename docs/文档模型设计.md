# 文档模型设计

> 本文是 `docs/正式化架构与迁移路线.md` 第四层（文档模型）的细化设计，两份冲突时以本文为准。
>
> 目标产品：富文本编辑器（文字、图片、公式）加上病历表单模式（文本输入框、单选复选、下拉），
>
> 并支持编辑 / 表单 / 只读三模式切换。参照项目 `D:\Develop\DCWriterLite` 为 GPLv3，
>
> 本文只借其架构思想与功能清单，不使用其代码。

## 一、已确定的骨架

四个决策已定，本文全部设计从它们推出：

| 决策      | 选择                 | 直接后果                             |
| ------- | ------------------ | -------------------------------- |
| 位置与节点身份 | 留协同扩展位             | 节点带稳定 ID，位置用 (节点 ID, 偏移)；不把下标当身份 |
| 表单数据    | 值内联进文档 + 控件带稳定 key | 归档自足，同时保留按 key 取数 / 回填 / 导出的通道   |
| 行内表达力   | 容器与原子并存            | 控件是跨度、可跨段落标记；图片、公式是不可断的原子              |
| 编辑操作    | 可逆步骤               | 每步带逆操作，撤销即执行逆操作，天然存在差量           |

另外三项：

本期需要的结构（标题与列表、引用与代码块、分节、修订留痕与批注）都是跨段落标记的用法；

样式走**命名样式 + 内联覆盖**；

域按值的来源分三类（排版结果 / 文档内引用 / 运行时刻），只出现在页眉页脚；患者信息是控件值而不是域。

本项目现状是最扁的一档：`BlockSpec` 是码点数组加一份字体参数，位置是 `TextPos{para, offset}`。

本次改造要把"一块文本 + 一组字体参数"替换为**元素流 + 容器树**，同时保持排版引擎的输入契约基本不变。

## 二、不变量

文档模型的价值不在"能表达什么"，而在"什么表达不出来"。下面每一条都必须是**可断言**的，

写进单测，任何编辑操作之后都要重新满足。

**结构类**

- 根节点唯一，其下是节序列，节序列覆盖全部内容且无缝隙。
- 每个节点的子节点类型与数量都满足 schema 声明（哪些能装哪些、最少几个、最多几个）。
- 没有孤立节点：除根以外每个节点都挂在一棵树上，且只有一条路径可达。

**文本与标记类**

- 文本节点非空。相邻且标记集合相同的文本节点必须合并为一个。
- `TextRun` 不跨流元素：一个 `TextRun` 完整落在同一个容器内、同两个流元素
  （段落标记或成对边界）之间。
- 标记没有重复项；标记集合内的顺序由 schema 固定（保证序列化确定）。
- 标记区间是"落在文本上"的，不允许零宽标记区间。

**身份类**

- 同一文档内节点 ID 唯一。
- 控件 key 唯一，且在编辑过程中稳定（不随插入删除改变）。
- 节点 ID 在保存与重新打开之后仍然有效（否则批注、书签、引用会全部失效）。
- **段落没有 ID**（它是派生量）。要引用段落，只能引用那个段落标记元素的 ID，
  或引用"元素 ID + 偏移"。这条约束是第三节方案一的直接代价，写在这里以免后来者误加。

**容器边界类**

- 容器的开闭标记成对、有序、不交叉。要么嵌套，要么并列，不存在第三种关系。
- 成对边界落在同一个容器内，不做跨容器的跨度；结束边界不排在起始边界之前。
- 容器内的元素序列被段落标记完整切成若干段，无缝隙：每个元素必属于某一段。
- 段落标记可以被容器边界跨过（这正是"控件里能有多段"的实现方式），也可以不被跨过。

第三条要强调：它把"元素归哪一段"变成全函数——任意元素都能唯一定位到一段，
所以不存在"既不属于这段也不属于那段"的元素，也就不存在无处安放的光标位置。
上一条则保证边界可以跨段落标记而不是必须跨，所以行内用法（`主诉：[____]`）与
块级用法（一栏里多段）是同一个机制的两个取值，不是两个类型。

`TextRun` 与 `ParagraphMark` 的区别是这两条约束的直接结果，值得单独说清：
**段落标记是流里的真实元素，`TextRun` 是被切分出来的叶子**。所以段落可以被容器跨过
（它是位置上的分段线），`TextRun` 不行——它必须完整落在同两个流元素之间。
判据只有一句：**能不能跨过流元素**。能跨的是位置（段落），不能跨的是内容（`TextRun` 与原子）。

**表格类**（见第九节）

以下三条是对**派生网格**说的：模型里只有跨度，没有网格，续格在模型里根本不存在。

- 每行的跨度之和相等，等于网格列数。
- 网格中不存在重叠的单元格；不存在无主的空洞格位。
- 纵向合并的续格必须紧邻其原点格，且中间不被打断。

**域类**

- 求值只更新缓存值，不改变文档结构，也不产生编辑步骤（否则打开文档就会污染撤销栈）。
- 值引用必须指向存在的控件 key；悬空引用是错误，不能静默渲染为空。
- 只有"排版结果类"域允许迭代，且迭代必须在上限内终止。

**编辑能力类**（见第七节）

- **可编辑集合取交集**：一个位置可编辑，当且仅当**包住它的每一层**控件都允许编辑
  （模式策略、控件的 `readonly`、以及将来的锁）。任何一层不允许，这个位置就不可编辑。
- 可编辑集合是**作用于光标落点的谓词**，不是"被删掉的元素"：文档结构不受模式影响。
- 光标落点必须在可编辑集合内；**选区的端点与范围不受此限**（可以跨出控件）。
- 编辑动作的落点也必须在可编辑集合内；不在就拒绝并给原因，不静默裁剪范围。

**区间与选区类**（见第四节末尾）

- **选区是会话状态，不是文档数据**：不进文档树、不落盘、不参与序列化
  （第十三节只落它的外观选项）。同一份文档可以同时有两个互不相干的选区。
- 选区端点是两个位置**加方向**：`anchor`（不动的那端）与 `focus`（跟着光标走的那端）
  分开存，方向决定下一次 Shift 扩展从哪一端继续。
- 端点存**流位置**（整数下标），不用节点 ID：节点会因编辑失效（平移、分裂、合并），
  流位置不会。编辑步骤同时负责把端点映射到新位置（第四节末尾）。
- **区间端点必须落在流元素边界上。** 区间涉及不可半分的单位（控件、表格行、单元格）时，
  一律**向外扩到整块边界**，不允许出现"半个控件"的区间——半个控件会破坏
  "成对边界同容器"（容器边界类），所以这是结构上的强制，不是显示上的偏好。

## 三、节点类型系统

三类节点（容器、原子、文本）加一种流内分隔元素。这套类型不是照搬任何一家，
是按本项目已有能力与需求裁出来的。**段落不是节点**，是流里的范围——这是本节最关键的一条，
依据在节末"段落是节点还是范围"。

**容器**：持有子元素的序列，在流里表现为"起始边界 … 内容 … 结束边界"。

```
Document        根，持有节序列、样式表、控件表、资源表
Section         节：纸张、页边距、页眉页脚、页码起始、分栏
Table           表格
TableRow        表格行
TableCell       单元格
ContentControl  内容控件：跨度可越过段落标记，所以"一栏"里能有多段
Quote           引用块
CodeBlock       代码块
ListItem        列表项：列表属性（层级、编号）挂在自身边界上
Link            链接：跨度不跨段落标记
```

**原子**：不可再分，在流里是一个带宽度、参与断行的叶子。

```
Image           图片：资源 ID + 宽高 + 定位与环绕方式
Formula         公式：表达式 + 排版后端标识
CheckBox        复选框
RadioButton     单选按钮
TextBox         单行文本框（不含段落的轻量输入，用于表格内）
DropDown        下拉
Break           软换行
PageBreak       分页符
Tab             制表符
Field           域：种类 + 缓存值（页码、总页数、值引用、打印日期）
```

**文本**：叶子，完整落在同两个流元素之间，不跨段落标记，也不跨容器边界。

```
TextRun         一段共享同一套标记（marks）的连续文本；边界由标记集合的变化决定
```

`TextRun` 是这类模型里最容易被误解的节点，值得说清三点。名字借自 Word 的 `w:r`（run），
OOXML、ProseMirror、Slate 用的是同一个概念。它存在的理由是字符属性必须以**区间**形式附着：
整段共用一份属性就是现在的 `BlockSpec`（没有 run 级样式），每个字符各带一份属性则又太重，
中间这层就是"一段连续的、属性完全相同的文本"。所以**它的边界是算出来的，不是用户划出来的**——
用户不会"新建一个 run"，只会"给这段加粗"；加粗区间一落，相邻的标记集合就变了，
`TextRun` 随之被切开或合并。这就是第二节那条合并不变量的由来。

**流内分隔元素**：既不是容器也不是原子，它标记段落的结束，并且是段落属性的唯一宿主。

```
ParagraphMark   段落结束标记：段落 = 同一容器内两个标记之间的范围
```

带标记的区间（`MarkedSpan`）不在这张表里——它只在编辑过程中临时存在，
规范化时被合并进相邻 `TextRun` 的标记集合，落盘与排版都看不到它。

**没有"行内"与"块级"的分类。** 上面这张表刻意不带这个二分。容器之间的差别只有两条：
**接受哪些元素类型**（一个位标志的并集，防止把表格塞进链接这类无意义组合），
以及**跨度是否跨过段落标记**——跨过就是块级语义，没跨就是行内语义。
后者是位置差别，不是类型差别，所以不需要两个类型，也不需要"行内升级为块级"的提升规则。
这一条是从参照项目 58,875 行源码里读出来的，完整依据在节末。

这张图把容器与流的关系摆在一起。左边是树，右边是同一份内容在流里的样子——
**段落只在流里存在，树上看不到段落节点**。

树视图：

```
Document
 └─ Section ─────────────────────── 节属性：纸张 / 页边距 / 页眉页脚 / 页码起始
     ├─ ContentControl [key=chief]   跨度越过一个段落标记
     │   ├─ TextRun("反复")
     │   └─ TextRun("心悸三天")
     ├─ Quote
     │   └─ TextRun("注意复查")
     └─ Table
         └─ TableRow
             └─ TableCell
                 └─ TextRun("36.8")
```

流视图（`Section` 内的一条扁平序列，光标与断行都在这条序列上）：

```
TextRun("患者主诉：")
ContentControlStart [key=chief]       起始边界：行内叶子，有宽度，参与断行
TextRun("反复")
ParagraphMark                         段落 1 结束（段落属性挂在这里）
TextRun("心悸三天")
ContentControlEnd                     结束边界
ParagraphMark                         段落 2 结束（患者主诉这一段到此为止）
TextRun("注意复查")
ParagraphMark                         段落 3 结束
Image {res,w,h}                       原子
Field {pageNo}                        原子，排版时求值
LinkStart … LinkEnd                   跨度不跨段落标记
```

控件那一段要看清：`ContentControlStart … ContentControlEnd` 之间跨了一个 `ParagraphMark`，
所以它内部"有两个段落"。真正的结构是**一个跨度跨过一个段落标记**，
不是"容器里装着两个段落节点"。这正是"行内位置放不下块级内容"这个矛盾不存在的原因。

### 为什么控件是跨度而不是带属性的原子

病历里最典型的用法是 `主诉：[______]` 这种**行内嵌入**——控件在段落流之中；
而"一栏里有多段"又要求它能跨过段落标记。做成原子就两样都做不到：内部文本塞进属性之后，
字体、行距、多段、换行全部要另立一套表达，等于把排版引擎的能力在属性里重写一遍。

参照项目的 `DomInputFieldElement` 继承自容器元素，走的是同一条路。代价是流里多一对边界元素、
规范化规则多几条，这笔代价在选"容器与原子并存"时已经认下。

### 原子与容器的统一处理

两者的差别只有一条：**能不能装子内容**。所以基类上是一个 `isContainer()` 判定，
位置计算、遍历、序列化、命中检测全部走同一条路径，只在"取子节点"处分叉。
不要为原子单独写一套遍历，那是重复代码的源头。

### 段落是节点还是范围：参照项目实测

如果反过来把 `Paragraph` 做成节点、把 `ContentControl` 归为容器（即下面的方案二），
就会撞上"行内位置放不下块级内容"这个矛盾。参照项目用一个决定就消掉了它，
以下是 58,875 行源码与 23 份真实病历模板的实测结果。

**它根本没有"行内 / 块级"这个分类。** 全库搜不到 `IsBlockElement` / `IsInlineElement` 之类判定。
子节点约束只有一个方法 `RuntimeAcceptChildElementTypes()`，默认返回 `ElementType.All`；
全库只有三处重写——字符串元素只收文本、表格只收行与列、表格行只收单元格。
**`DomInputFieldElement` 一处都没重写，它不限制子节点。**

**段落不是节点，是流里的范围。** `DomParagraphElement` 的注释原话是
"本对象只在加载或保存文档时临时生成"，运行期没有段落节点。段落由 `DomParagraphFlagElement`
（一个 EOF 叶子元素）在流里分隔，范围由 `GetParagraphEOFElement(element)` 导出——
实现就是从元素下标往后找同一个列表里第一个段落标记。

**段落属性挂在段落结束标记上。** `GetParagraphStyle(element)` 先找到本段标记，
再取它的 `RuntimeStyle`。每个元素自带 `StyleIndex` 管字符样式，段落样式来自标记。

**域的边界是流里的两个真实元素。** `DomFieldBorderElement`：运行期惰性创建
（`CheckStartEndElement()`）、有宽度（`ViewWidth = max(Width, 12.5f)`）、参与断行；
与字符、段落标记、图片同层——取屏幕矩形时这四类走同一条分支。

**域的内容内联进父流。** 布局时域的展开是 `[起始边界] + 域内容 + [结束边界]`，
三者追加进**同一个累加器**（`content.FastAdd2(se)` … `FastAdd2(ee)`）。所以域的内容
不是独立子流。边界元素**不进序列化**——落盘写的是嵌套节点
`<Element xsi:type="XInputField"><XElements>…`。运行期是扁平边界式、序列化是嵌套节点式，
两者之间靠加载与保存时的一次转换衔接。

**23 份真实模板的统计。** 段落标记的父元素有 **22 处是 `XInputField`**；
域的父元素有 **27 处是域**（5 处直嵌正文、22 处嵌在表格单元格里的域里）；
域的父容器分布是单元格 1069、正文 211、页眉 51、页脚 7。

**光标也在流下标上。** `DCContent` 本身就是元素列表，`MoveLeft()` 就是下标减一。
关键在位置换算 `GetPositonInfo()`：命中**起始边界**归一化为 `(域的父容器, 域的下标)`
即"域之前"，命中**结束边界**归一化为 `(域, 域.Elements.Count)` 即"域内末尾"。
这正是上一轮那四个缺陷的解法——"域之前"与"域内"是两个不同的位置，
不需要在整数偏移上反推。它还对 LTR / RTL 分别比较了 `LayoutIndex`。

**结论：采用方案一**，也就是本节的形状。

| | 方案一（参照项目做法，已采用） | 方案二（Word 与 ProseMirror 做法，未采用） |
|---|---|---|
| 段落 | 流里的范围，属性挂在结束标记上 | 节点 |
| 控件 | 一个类型，跨度可越过段落标记 | 拆成 `InlineControl` / `BlockControl` |
| schema | 不需要例外 | 需要"行内升级为块级"的提升规则 |
| 与编译的关系 | 模型与编译产物同构 | 要先展开成方案一的形状再喂引擎 |

选方案一不只是少一个类型：引擎本来就只吃"段落序列 + 行内盒子序列"，
方案一让**模型与编译产物同构**；方案二要多一层翻译，也就多一处可能不一致的地方，
而且那条"行内升级为块级"的提升规则本身很难写对。

代价说清楚：段落的 O(1) 定位要靠派生下标数组维护（每条容器一条扁平流加一个标记下标数组）；
增量的 `layout_dirty_from_` 仍然成立，但"段落的身份"从节点 ID 变成标记位置。

## 四、位置与节点身份

### 位置

```
Pos = { container: NodeId, offset: int }
```

`offset` 的含义由所在容器决定：容器节点里是**子元素槽位序号**，文本节点里是**码点下标**。

关键在**边界是流里的真实元素**，于是"在控件之前"与"在控件之内"是两个不同的位置：

```
(父容器, i)      起始边界之前          "控件之前"
(父容器, i+1)    起始边界之后、内容之前  "进入控件"
(控件, 0)        控件内容的开头
(控件, k)        控件内容的第 k 个位置
(父容器, j)      结束边界之后          "控件之后"
```

对**删空的控件**（内容长度为零）这一族位置一个都不消失：空容器的两个槽位
`(控件, 0)` 与 `(控件, 1)` 仍然互不相等。这正是上一轮
`docs/控件边界诊断与方案.md` 里那四个缺陷的结构性解法——那时"在 `[` 与 `]` 之间"
在整数偏移里没有编码，现在它是两个合法位置。

### 流位置是模型与引擎的对接口

把整篇按深度优先遍历展开，得到一个**线性的流位置**（第 n 个元素）。方案一之后它的地位变了：
段落既然是流里的范围，**段落序号、脏段标记、行内盒子下标全部定义在流位置上**。
它不是"等价但更快的视图"，而是模型对外的第二套索引：

- 段落序号 = 该位置之前遇到的 `ParagraphMark` 个数加一。
- 脏段标记 = 流位置区间的两个端点，而不是节点 ID（节点会因前面的插入而失效，位置不会）。
- 与引擎的接口 = 流位置到"行内盒子下标"的映射，这一段几乎是恒等。

约定：**节点级 API 用 `Pos`，段级与引擎级 API 用流位置**。两者换算必须双向互逆，写进单测。

### 节点 ID

- 64 位整数，局部递增分配器持有"已用最大值"，不依赖全局随机。
- 文档内唯一，跨保存有效，所以序列化时必须落盘。
- 不回收（删除的 ID 不再复用），避免"旧引用指向新节点"。

### 标记与身份的关系

标记（粗体、颜色这类）**不带 ID**。它们是文本节点上的属性集合，随规范化自动合并拆分。
把标记也做成带 ID 的节点会让"合并相邻同格式文本"这条不变量无法成立。

带 ID 的是两类：**容器**（链接、内容控件、表格等——它们有自己的语义与属性）与
**段落标记**（段落属性挂在它身上）。段落本身不带 ID，见第二节身份类那一条。

### 区间与选区：什么进模型、什么不进

**选区不进模型。** 它是会话状态（第二节），不是文档数据。本地实测：参照项目的
`DCSelection` 虽然放在 `Dom/` 目录下，但它挂在内容元素上，序列化时与 Selection 相关的
只有 `SelectionHightlightMaskColor` 与 `SelectionTextIncludeBackgroundText` 两个**外观选项**，
选区本身一个字节都不落盘。成熟编辑器分工一致：ProseMirror 的 `Selection` 在
`EditorState` 而不在 `doc` 里，Lexical 的 `RangeSelection` 不进 document JSON。
剪贴板内容同理——那是系统剪贴板的外部格式，不是文档的一部分。

**但四样东西进模型**，缺了它们命令层会各自发明一套，改模型时全部失效：

**一是端点的形状**：两个流位置**加方向**（`anchor` 与 `focus` 分开存）。方向不是可有可无，
它决定"Shift+左"与"Shift+右"下一次从哪一端继续扩展。参照项目的选区只有
`_StartIndex + _Length`、**没有方向**，所以它表达不了这件事。端点用流位置而不是
`Pos{node, offset}`：后者里的 ID 在节点被删掉之后悬空、无法复位。

**二是位置映射（mapping）。** 位置是整数下标，所以编辑之后要有人把旧位置搬到新位置。
这件事由**步骤**负责：每个步骤提供 `map(pos, assoc) → pos`，撤销与重做走逆映射。
`assoc` 是"位置正好落在插入/删除的边界上时归左边还是右边"的约定——同一位置有两个合法
归宿时，这是唯一能表态的地方。参照项目用一个 `FixIndex()` 做同样的修正。

**三是区间原语。** 复制、剪切、删除、加粗、批量设值全都归结为两个操作：
`ExtractRange(range) → 片段`（纯读，不产生步骤）与 `DeleteRange(range)`（写，是步骤）。
步骤表里现在只有 `DeleteRange`，缺的是读的那一半。参照项目对应的也是这一对：
`content.GetRange(absStart, absLength)` 取、`deletedElements` 删。

**四是端点规范化。** 端点必须落在流元素边界上（第二节）：落在控件、表格行这类不可半分
单位内部时，**向外扩到整块边界**——选区起于某控件内部，退到该控件起点。于是
**复制出的片段永远良构**（控件边界成对同容器），这由结构保证，不靠调用方自觉。
参照项目是 `SplitElements` 拆元素再取区间；我们**不能拆控件**（拆了边界就不成对），
只能外扩——差别就在这里。

## 五、编辑操作：可逆步骤

### 步骤

```
struct Step {
  virtual void apply(Document&) const = 0;   // 应用
  virtual StepPtr inverse() const = 0;       // 逆步骤
  virtual bool applicable(const Document&) const = 0;  // 是否可应用
  void toJson(JsonWriter&) const;            // 序列化
};
```

内置步骤集合（尽量少，其余用组合表达）：

```
InsertText      在文本位置插入码点序列
DeleteRange     删除一个区间的行内内容
InsertParaMark  在位置处插入段落标记（回车分段）
RemoveParaMark  删除段落标记（段首退格、段末删除的合并）
InsertNode      插入节点（图片、公式、控件、表格）
RemoveNode      删除节点
MoveNode        移动节点
SetAttr         设置节点属性
SetMarks        设置区间标记（加粗、取消加粗）
SetStyle        设置样式引用
```

### 为什么是可逆步骤而不是快照

三条理由，都与本项目已有特性咬合：

**撤销不需要快照。** 撤销就是执行逆步骤。快照式撤销要保存整篇文档，对于几百段的病历

是内存与垃圾回收的负担；更要紧的是，**回退到快照会让整篇变脏**，直接击穿增量排版，

而增量是这个项目最贵的那部分资产。

**差量天然存在。** 一次编辑改了哪些节点，`Step` 自己知道。序列化的增量保存、

排版脏段标记、审计对照，都能直接吃这个信息，不必再比较前后两份文档。

**为协同留了门。** 步骤可序列化、可传输、可重放、可逆，这套东西正是 OT 与 CRDT 的输入。

本期不做协同，但结构上不挡路——这就是"留扩展位"的具体含义。

### 代价与纪律

每个步骤都要额外写逆操作，且逆操作要能通过同样的校验。这是纪律问题，靠两件事守：

- **往返判据**：`apply(step)` 之后 `apply(step.inverse())`，文档必须与之前**逐字段相同**。

  这条判据对每个步骤类型都要跑一遍，参数用随机生成。
- **规范化不与之耦合**：步骤只做最小改动，规范化（合并相邻同格式文本、清理空节点）

  在事务提交前统一跑一次。否则逆操作会还原出"未规范化"的中间态，往返判据失效。

### 事务与撤销分组

```
Transaction = Step 序列 + 编辑前选区 + 编辑后选区 + 提交说明
```

相邻的同类编辑（连续输入）合并为一个撤销单位，用户按一次撤销应回退一整段输入，

而不是一个字。合并策略放在事务层，步骤本身保持无状态。

**撤销恢复编辑前的选区。** 事务同时记下编辑前后的两份选区快照，撤销时把两份都还原，
重做则回到编辑后。只回退内容而把光标留在原地，用户看不出撤销了哪里——Word 与多数
编辑器都恢复选区。它与"位置映射"（第四节末尾）是两条互补的路：映射管**一次编辑之内**
位置的跟随，选区快照管**跨撤销单位**回到原处。

## 六、样式系统

### 三层解析

```
文档默认值（docDefaults）
  → 段落样式链（based_on 逐级继承）
  → 字符样式链
  → 元素上的内联覆盖
```

后者覆盖前者，逐属性合并。解析结果是运行期样式，**排版引擎只吃解析后的结果**，

不认识样式表。这样样式系统的复杂度不会渗进排版层。

### 三类样式

```
ParagraphStyle   字体、字号、行距、对齐、缩进、段前段后、编号、制表位
CharacterStyle   字体、字号、粗细、斜体、下划线、删除线、颜色、高亮、上下标
TableStyle       边框、底纹、单元格边距、行高列宽默认值
```

样式表存在 `Document` 上，元素只存**样式引用 + 与样式不同的那些属性**。

这一条与序列化"不写默认值"是同一个原则，直接决定病历文档的体积。

### 为什么不做"只允许命名样式"

用户已经选了"命名样式 + 内联覆盖"。补一句代价：

内联覆盖会让"解析后的样式"依赖上下文，因此**样式解析结果必须缓存并随编辑失效**，

不能每帧重新走一遍继承链。缓存键是元素 ID 加样式表版本号，样式表一改就整体失效。

### 样式变更的差量

改一次段落样式，影响的是**所有引用该样式的段落**。这些段落可能散布在全篇，不是连续后缀。

所以样式变更只能按"受影响的段集合"标脏，不能复用后缀脏段机制。

这一点的正确处理方式是把脏段集合从"一个数"扩展为"一个数加一个集合"，

或者干脆在样式表版本号变化时走全量。先按全量做，测出瓶颈再优化。

## 七、表单控件

### 控件表

控件定义（类型、选项列表、格式约束）放在文档级的控件表里，节点上只存控件 ID。
值内联在节点上。这样控件定义可以跨文档复用，而单份病历仍然自足。

控件按**值存在哪里**分两类，这个分法是从方案一直接推出来的：

```
容器型（值就是它的内容）
ContentControl { id, key, kind, readonly, required, format, appearance }
  kind ∈ { text, richText }       内部可含段落，所以字体、多段、换行都能表达

原子型（值在属性上）
CheckBox    { id, key, checked, group, appearance }
RadioButton { id, key, group, value, appearance }
DropDown    { id, key, options, selected, appearance }

appearance {
  width, overflow, underline, border,       结构性的：占多宽、值长了怎么办、线画在哪几边
  align, placeholder, styleRef, invalidStyleRef
}
```

`width` 是长度值（第十一节），`overflow` 是超出显示档位，
`border` 是四边各自的边框，其余是常规样式。

文本、日期、数字都归 `ContentControl`：日期与数字只是 `format` 的差别（格式约束，不影响存储），
下拉归 `DropDown`。早先把 `type` 列成 `{ text, date, number, select }`，那是把控件当成了
原子属性，与"控件是跨度"彼此冲突；按"值存在哪里"分开之后就不冲突了。

`setValue(key, v)` 与 `getValue(key)` 是唯一的值读写入口，两类各自实现：
容器型替换内部内容，原子型改属性。这就是"值内联 + 可回填"的落点。

### 控件的外观

**固定宽度（`width`）。** 病历表单里"体温 \[____\] ℃"的底线长度必须恒定，否则值为空时
控件塌成零宽、后面的内容跟着往前跑。所以它表达的是**占位宽度**，与值的长短无关。三条约束：

- **宽度与输入上限是两件事，要分开存**：`width` 是显示宽度（长度值，见第十一节），
  `maxLength` 是编辑策略里的输入上限（沿用现有 `EditPolicy` 的判定）。
  常见组合是两者相等，但不等的时候更多——住院号栏可以固定 6 字符宽却允许输入 10 位。
- **长度类型要加一档 `Chars(n)`**，不能拿 `Em(n)` 代替。中文全角字是 1 em，
  但数字与字母是半角（约 0.5 em），"3 个字符宽"在数字字段上会算成一半。
  `Chars(n)` 表示"n 个全角字符位"，与文档网格的"每行多少字"是同一个度量。
- **它是引擎侧的新增约束。** 第十四节说边界元素"有宽度"（参照项目取
  `max(宽度, 12.5)`，保证鼠标点得着）；固定宽度比那条更强，它是**指定的**宽度。

**值超出固定宽度（`overflow`，属性配置）。** 三种处理方式做成一个属性，
因为同一条病历里不同字段的诉求本就不同——体温底线必须恒定宽度，
诊断名称则希望整条看得见。三档取值与各自的排版后果：

| `overflow` | 值超过 `width` 时 | 后果 |
|---|---|---|
| `expand`（撑开） | 宽度是下限，框跟着值变宽 | 断行与后续内容位置随之改变；不丢数据、不遮字 |
| `clip`（裁切） | 框宽不变，超出部分不绘制 | 值完整但看不见；要求 `maxLength` 保证"能输入的放得下"，否则记诊断 |
| `spill`（溢出） | 框宽不变，超出部分照常绘制 | 值看得见，但可能盖住后面的内容 |

默认 `expand`——不静默丢数据。`clip` 只用在"`format` 或 `maxLength` 已把长度限死、
overflow 只是防御性兜底"的字段上；否则会出现"值存在、光标能进去、屏幕上却什么都看不见"
的状态，这种组合列出诊断，不靠纪律。

**不做控件内横向滚动。** 控件是流里的跨度，不是带滚动视口的盒子，
没有自己的滚动位置，也没有滚动条。值超出只有上面三档处理：
要么已按 `expand` 排开占位，要么被裁掉不再绘制。
"把超长的那一段横向滚动出来看"这个说法不成立，它对应的状态在这里不存在。

**下划线（`underline`）。** 三档：仅空白处显示（Word 表单域的经典做法，文字下面有线、
空着的地方也有线）、整段显示、无。

要紧的是它与**字符的 `underline` 标记不是一回事**：

| | 由谁决定 | 编辑之后 |
|---|---|---|
| 控件下划线 | 控件身份，是边界装饰 | 不变（只要控件还在） |
| 字符下划线标记 | 内容上的 marks 区间 | 跟着文字走，可能延续也可能消失 |

混淆会产生一个怪现象：给控件勾了下划线，实际变成给内容加了一堆标记，删掉文字后线也跟着没了。
实现上控件下划线是**编译到引擎时挂在边界盒子上的装饰**，不进 marks、不进文档。

**边框（`border`）。** 四边各自独立，缺省表示，该边不画：

```
border { left?, right?, top?, bottom? }
Border { style ∈ { none, solid, dashed, dotted }, width, color }
```

三条要点：

- **与下划线同源，但不合并。** 两者都是挂在边界盒子上的装饰，都不进 marks、不进文档内容；
  差别在下划线有"仅空白处也显示"的档位语义，普通边框没有，所以下划线独立保留。
- **边框与下划线都进序列化。** 两者都是作者设定的外观（要打印、要保存）；
  `placeholder` 与校验状态不落盘，理由见下文。
- **四边独立而不是"边框开关加统一宽度"。** 病历表单常见只画下边（填空线）、
  或只画左右边（栏位分隔），统一边框表达不了这两种。

`placeholder`（提示文字）不进文档——它是"值为空时画什么"的渲染规则。若当内容存进去，
`getValue` 会把提示文字当成值取出来。只读与打印模式不绘制 `placeholder`，
否则空白字段会把提示文字一起打印出来。

### key 的稳定性

`key` 是业务标识（比如 `chief_complaint`），在文档内唯一且不随编辑改变。

`id` 是模型内部身份，随节点走。两者都要有：

- `id` 用于位置、引用、撤销。
- `key` 用于取数、回填、导出，以及将来与外部系统的字段映射。

用户选的是"内联值 + 可回填"，两者的分工正是这个意思：值在文档里躺着，

但随时能按 `key` 把整篇的值抽出来，或者从外部数据按 `key` 批量灌回去。

**粘贴时的 key。** 复制**一律带控件身份**（`key`、`readonly`、结构操作开关、外观），
于是粘贴必然要处理 key 冲突，三条规则：

- **剪切**（同文档内移动）：源控件已不存在，**保留 key**。
- **复制后在同文档内粘贴**：key 必然重复，**重命名**（新分配，同时留下与源控件的
  对应记录，便于追溯"这一份是从哪里来的"）。
- **跨文档粘贴**：目标文档没有同名 key 就**保留**（业务字段映射的意图得以延续），
  有冲突才重命名。

连带一条：片段里的**值引用**（`Field{valueRef}`）指向的 key 若被重命名，
引用必须**同步改写**，否则会踩中第二节域类那条"值引用必须指向存在的控件 key"。

### 值的读写：内容即值、控件索引、批量

**内容即值。** 容器型控件没有"值字段"，它的值就是它内部那段内容——`getValue(key)`
就是把该容器内所有 `TextRun` 按顺序拼起来。只有一份真相，不存在"值属性与内容不一致"
这类错误。代价是**读取要遍历**，于是下面这条变成必需项。

**控件索引。** 文档里维护两张表：`key → 控件`、`控件 → 内容位置`，随编辑步骤**增量更新**
（控件内容被插入删除时位置会平移，与控件区间伸缩属于同一类维护）。
这条不是优化而是必需：**"列出全部控件"与"批量取值"如果每次全篇扫描，性能与老编辑器一样差**。
差别不在 API 形状，在有没有索引。索引维护挂在编辑步骤上，不做手工同步。

**批量读写。** 对外三个方法：

```
listControls()            控件描述数组（id / key / kind / value / readonly / required）
getValues(keys?)          一次取全部或指定几个的值
setValues([(key, v), …])  批量设值
```

`setValues` 的价值不是"少几次函数调用"，而是**合成一个事务**：一次编译、一次标脏、
一次排版、一次上屏、一个撤销步骤。判据写死三条——**设 1000 个字段与设 1 个字段耗时同一量级**、
**只产生 1 个撤销步骤**、**最终帧与"逐个在独立事务里设置"逐像素一致**
（前两条看性能，第三条守正确性）。

**句柄用 id 与 key，不用节点引用。** `listControls()` 返回的是轻量描述，不是活的节点指针——
节点会因编辑失效（位置平移、分裂与合并）。这里顺带澄清一个说法：原子型控件
（复选框、单选、下拉）确实是流里的叶子，而**文本控件按方案一是跨度、不是叶子**（它能跨过段落标记）。
对外 API 对两者完全一致，宿主不需要知道"文本控件的值是内容、复选框的值是属性"——
这正是门面层的价值。

**批量设值有一个必须提前知道的代价。** 它会让脏区**散布全篇**（100 个字段分布在各页），
而当前的 `layout_dirty_from_` 是"连成一段的后缀"。这是第六节末尾那个风险
（样式变更的散布式改动）的**第一个真实用例**，也是它从"将来可能"变成"马上就要遇到"的地方。
两条路：先退化全量（正确但慢），或把脏段标记从"一个数"扩展成集合。
建议先测出真实数字再定，别提前设计。

### 与业务交互：校验钩子、异步裁决与批次

**结论先说：钩子允许异步，但语义是"持有候选变更，裁决通过才应用"，
不是"先应用，结果回来再回滚"。** 这两者体验差别极大——后者就是"先勾上、再弹回去"，
是必须避免的那一帧。异步本身不是问题，"乐观应用加回滚"才是。

**校验钩子的形状。**

```
beforeChange(change) → Decision | Promise<Decision>
  change   = { controlId, key, oldValue, newValue, source: user | program }
  Decision = Allow | Deny(reason)
```

宿主返回同步的 `Decision` 时走**原路径**：判定、应用、产生一个撤销步骤，
中间不多出任何帧，也没有额外状态。返回 Promise（含 `async` 函数）时，编辑器**悲观持有**：

- 交互先产生一个**候选变更**，它放在文档之外。文档不变、撤销栈不变、不排版也不上屏。
- 控件进入 `pending` 展示（样式可配，比如浅灰边框），**不显示新值**。
  用户因此看不到"已经勾上了"，也就没有"勾上再撤销"那一帧。
- 结果到达后：`Allow` 把候选变更当普通事务应用（此时才产生撤销步骤、才排版上屏）；
  `Deny` 丢弃候选变更，值保持原样，并按下面的校验状态显示原因。

四条约束管住等待期间的状态：

- **同一控件再次交互时取消前一次等待**（最后交互为准）。旧 Promise 的结果到达时
  按"已取消"丢弃，不产生任何应用，也不误报失败。
- **目标区间失效就丢弃。** 等待期间文档可能被别的编辑改过（控件被删除、段落被合并）。
  结果到达时先确认锚点仍指向同一个控件，失效则丢弃，不做补偿动作。
- **超时按拒绝处理，不静默放行。** 钩子可配 `timeout`（默认给一个保守值，比如 5 秒），
  超时判 `Deny("校验超时")`，值保持原样，用户再点一次即可。
  放行一颗从未校验过的复选框，比不放行更危险。
- **钩子内禁止调用任何编辑 API**（会重入当前事务），与同步路径同一条纪律。

**只拦用户交互，不拦编程设值**（`source` 区分）。回填时顺序上可能先填空的，
被"必填"卡住就是错的；宿主自己发起的 `setValue` 由宿主自己负责。
这条同时保证了**批量路径完全同步**：`setValues` 是 `program` 源、不进钩子，
所以批次里不会出现"一半在等异步、一半已提交"的混合状态。

**返回拒绝原因，不只是"是否允许"。** ProseMirror 的对应机制是
`filterTransaction(tr, state) → boolean`（事务应用前调用，返回 false 即取消），
但它有一个社区讨论多年的短板：**被取消的事务没有回执**——宿主想在用户面前提示
"这一项现在不能勾"，只能把副作用塞进过滤函数里，破坏它的纯函数性。
我们的钩子返回原因，且原因是给用户看的文案，不是给日志看的错误码。

### 校验状态与样式提示

校验的产出不止"拦不拦"，还有"当前这一项对不对"。这份状态是**运行时的**：

```
validationState ∈ { none, pending, invalid }     每个控件一份
validation { state, message }
```

- `pending` 就是异步等待期间的状态；`invalid` 由 `Deny` 自动置位，
  也可由宿主主动置位——API `setValidation(keys, state, message)`。
  主动置位这条是必需的：异步校验的结果有时晚于一次编辑，
  宿主拿到结果时已经没有对应的事务了。
- **样式提示走外观。** `appearance.invalidStyleRef` 指向一套样式（红框、红底、
  波浪下划线等），渲染层按它画。模型只存"状态、提示文字、用哪套样式"，不存怎么画。
- **不落盘，理由与 `placeholder` 相同：** 它是"这次会话里这一次校验的结果"，
  不是文档内容，重新打开由宿主重算。若存进文档，
  会出现"上次的红框被打印出来"这类错误。
- **只读与打印模式下不画 `pending` 与 `invalid` 的样式**（除非导出审核版），
  与 `placeholder` 同一处理。

### 通知类回调

`afterChange`（值已变更的通知）不参与决策，因此它不该阻塞编辑：
事务提交后把通知排到任务队列执行。三条纪律：回调里抛错不影响文档；
回调里要发起编辑必须开新事务（不能重入）；
`setValues` 返回一个可等待的批次结果，宿主 `await` 它就能串起"设值完成再提示"这类流程。

**交互被拒也走通知。** 落点被拒、编辑被拒、越界点击这些"交互本身没成立"的情形，
编辑器**不在界面里做任何提示**（不弹、不闪、不改外观），而是交给宿主：
`onBlockedInteraction({ kind, pos, controlKey?, reason })`，`kind` 区分点击落点 /
方向键 / Tab / 编辑 / 结构操作。纪律与 `afterChange` 一致：排任务队列、不阻塞输入、
回调里抛错不影响编辑。**此外必须去重**：按住方向键或连点会让同一处越界每秒触发几十次，
同一 `kind` 在同一个位置上的连续触发只报一次，位置或 `kind` 变了才再报。
它与 `beforeChange` 的 `Deny(reason)` 分工不同：那个是"值变更被拒"（已产生变更候选），
这个是"交互本身被拒"（值根本没轮到变更）。

分工要说清：**校验钩子决定"能不能改"；通知回调有两类——"改完了告诉你"（`afterChange`）
与"这次交互没成立"（`onBlockedInteraction`），都不参与决策，也都不由编辑器渲染提示。**
把校验逻辑塞进通知回调，等于默认变更已经生效，就退回"先应用再回滚"那条路了。

### 批次

`setValues` 与"回填整篇病历"走同一条路：

```
beginBatch() … 期间只改模型，不编译、不排版、不上屏 … commitBatch()
```

提交时把批次内所有变更合成**一个事务**，然后才编译、标脏、排版、上屏各一次。
这是性能需求的正解——老编辑器"循环调用性能差"的根因不是函数调用开销，
而是**每次 `setValue` 都触发了一次完整的重排与上屏**。在这个项目里上屏占端到端八成以上
（敲一个字 1.96 ms 里排版只占 0.16 ms），所以批量能力必须做在"抑制中间的上屏"这一层，
而不是"少调几次函数"这一层。

### 患者信息就是控件值

患者姓名、住院号、性别、年龄这些**不是域**（见第八节），而是绑定了业务 key 的控件值。
更新只有一条路径：`setValue(key, v)`。页眉页脚要显示时，用第八节的**值引用**占位符指向该 key。
这样不需要"数据源"这个额外概念，也不必让域去理解业务字段。

### 三模式是策略，不是三套控件

沿用现有的 `EditMode` 三档与 `EditPolicy` 判定，扩展成"能力裁剪表"：

| 模式 | 光标落点        | 编辑        |
| -- | --------- | --------- |
| 编辑 | 全部        | 全部        |
| 表单 | 只落可编辑控件内 | 只有在可编辑控件内插入删除 |
| 只读 | 全部        | 一律拒绝      |

要点：三种模式都**不改变文档模型**，只裁两项能力——"光标能落在哪"与"能不能编辑"，
所以是策略而不是三套控件。**选区与复制在三种模式下都不受限**：Shift 扩展、鼠标拖拽、
双击选词、三击选段、全选都可以跨出控件；核对上文与复制是病历的刚需。

**表单模式的落点口径**（与 Word 的"填写窗体"保护不同，它连选区一起禁，
因为它的用途之一是防复制；我们没有这个需求）：

- **落点受限**：鼠标点击、方向键普通移动、Tab、Home/End 的目标位置必须在可编辑集合内。
  点击落在不可编辑区时**不移动光标**。可发现性靠外观：可编辑控件画成输入外观
  （边框、底色），其余不画；否则"点了没反应"会被当成 bug。
- **选区自由**：选区的端点与范围都可以跨出控件。
- **编辑动作的落点必须在可编辑集合内**：越界就拒绝并给出原因（接在 `Deny(reason)`
  的回执上），**不静默把范围裁到可编辑部分**——静默裁剪会让用户以为整段被删掉。

**可编辑集合是一个交集，不是"在某个控件内即可编辑"**：只读控件里再嵌一个可编辑控件，
那个内层位置**仍然不可编辑**。写成不变量见第二节。

不要把这条限制做到文档结构上：**它只是一个作用于光标落点的谓词**，不要为表单模式造
一个"只剩可编辑部分的视图"。段落、命中、坐标与脏段都建立在"流是完整的"这个前提上，
挖掉一块会让模型与排版输入不一致。

**嵌套按交集处理，不需要 `w:group` 那种例外。** OOXML 的 `w:group` 允许内层控件覆盖
外层的"不可编辑"（规范原文：这条限制可以被它内部包含的任何结构化文档控件推翻），
它存在是因为 OOXML 在**默认可编辑**的文档里做局部保护；我们的表单模式默认就是
"只有控件内可编辑"，所以"整段只读、只留一处可填"只要把静态文字放在任何控件之外即可。
镜像字段值要用**值引用**（`Field{valueRef}`），不要用嵌套的 readonly 控件——
后者是两份数据，迟早不一致；只有"一段独立的静态文字"才适合用 readonly 控件。

只读模式则是所有编辑步骤被拒绝、控件不响应输入。

### Tab 与结构操作

**Tab 按模式分工**（同一个键不能同时干两件事，所以由模式决定它此刻算什么）：

- **编辑模式**：Tab 是**制表符**——模型里它就是一个 `Tab` 原子元素，参与制表位计算。
- **表单模式**：Tab 与 Shift+Tab 在**可编辑控件之间前进与后退**。这里有意**不照抄**
  Word 在富文本内容控件上的做法：它为了支持插入制表符而把 Tab 留在控件内，结果
  "**Tab 不出来**"，官方论坛给的解法是让用户改用鼠标、或把富文本控件换成纯文本控件。
  我们的文本控件是 `richText`（内部可含段落），照抄就会让填表单变成鼠标操作。
- **表单模式下不给"插制表符"留默认键位。** Word 的对应办法是在字段里按 `Ctrl+Tab`
  （与表格单元格同一个惯例），但**这条在浏览器里不成立**：`Ctrl+Tab` 被浏览器保留，
  Chrome 根本不给页面派发事件，Firefox 派发但 `preventDefault` 无效（见下面的键位纪律）。
  需要制表位的内容应当在**编辑模式**里由作者做好；填表时想缩进用**段落缩进**
  （它是 `ParagraphStyle` 的属性，不是字符，本来就比插制表符正确）。
  命令层仍然提供 `insertTab`（模型里有 `Tab` 原子元素），但**默认不绑快捷键**，
  绑什么由宿主决定——宿主是 web 应用，它最清楚自己能拿到哪些键。

**默认键位要避开浏览器保留键。** 裸 `Tab` 可以用——页面能拿到 keydown 并
`preventDefault`（这正是表单模式能用它切控件的前提）；但**一旦带上修饰键就不一定**：
`Ctrl+Tab` / `Ctrl+Shift+Tab`、`Ctrl+T` / `Ctrl+N` / `Ctrl+W`、`Ctrl+Shift+T` /
`Ctrl+Shift+N`、`F5` 这类由浏览器在页面之前处理：Chrome 下页面收不到事件，
Firefox 下收得到但拦不住。可覆盖的是常规那批——`Ctrl+B` / `Ctrl+I` / `Ctrl+U` /
`Ctrl+Z` / `Ctrl+Y` / `Ctrl+S` / `Ctrl+P` / `Ctrl+F` 等。
**所以任何默认快捷键都要先过这张表，尤其不要在 `Tab` 家族上做设计。**
- **只读模式**：**放行** Tab，让焦点落到编辑器之外的下一个元素——只读模式吞掉 Tab
  会把键盘用户困在编辑器里（键盘陷阱），而它没有任何东西可以换。
- 表单模式的**最后一个可编辑控件**上按 Tab 也要放行。不要学 Word"在最后一个单元格按 Tab
  就静默加一行"——那会让人往一行不存在的表格里打字。

**结构操作是控件属性，默认关闭。** OOXML 的 `w:lock` 把"内容能不能编辑"与
"控件能不能整体删除"分成两件独立的事（`unlocked` / `sdtLocked` / `contentLocked` /
`sdtContentLocked`），我们照这个分解，不造新概念：内容可编辑性已由 `readonly` 表达，
再补一个**可否做结构操作**（删除控件自身这类）的开关，默认 false。
于是表单模式的默认是**内容可编辑、控件不可删**——把表单填错与把表单结构改坏是两件事，
后者该由作者显式开放。它是作者意图，随控件落盘（与 `readonly` 一致）。
增删行列这类操作的目标不是控件，开关挂在被操作的元素上（表格 / 行 / 单元格），
不要造一个通用的"操作白名单"。

打印预览走同一条路径，不要另做一个渲染器。

## 八、域

域是"值在排版或导出时才确定的内容"。**按值的来源分三类，只有第一类会产生迭代**。

| 类别 | 例子 | 值从哪来 | 是否迭代 |
|---|---|---|---|
| 排版结果 | 页码、总页数 | 本次排版的结果 | **是**（唯一有循环风险的） |
| 文档内引用 | 控件值引用 | 文档内某个控件的值 | 否 |
| 运行时刻 | 打印日期、文档属性 | 文档之外 | 否 |

### 为什么只有"排版结果"会循环

页脚写"第 3 页 / 共 9 页"就是现成例子：

**按上一轮算出的 9 排版 → 实际排出 10 页 → 域文本从"共 9 页"变"共 10 页"，
多了一两个字符的宽度 → 可能让某一段多折一行 → 总页数变 11 → 再求值……**
每一轮的值都依赖上一轮的排版结果，收敛不了就互相追着跑。两个解法，按域类型分别用：

- **总页数用预留宽度**：按"最宽可能值"估宽（比如固定 4 位数），宽度不随值变，
  排版一次就稳定，迭代退化为 1 次。代价是页脚多一点空白。
- **页码用迭代上限**：最多 3 次，位数变化本来就少，通常第一轮就收敛。

日期与控件值引用**不会循环**：它们的值与排版无关，取出来就固定；宽度变化最多让版面重排一次，
不会反过来改值。把三类混在一张表里，会让"循环"看起来像所有域的通病，那是不对的。

### 患者信息是控件值，不是域

患者姓名、住院号、性别、年龄这些**不是域**，而是绑定了业务 key 的控件值（见第七节）。
更新只有一条路径：`setValue(key, v)`。页眉页脚要显示时，用一个**值引用**指向该 key。
这样不需要"数据源"这个额外概念，也不必让域去理解业务字段。

值引用与页码机制相同，但**不变量不同**：引用一个不存在的 key 是错误
（拒绝，或渲染为空并记诊断，不静默通过），而页码永远有值。

### 模型形状

```
Field { kind, cache }
  kind ∈ { pageNumber, pageCount, valueRef(key), printDate, docProperty }
```

去掉了早先的 `expr` 与 `custom`（本期不需要通用表达式求值）。`date` 改名 `printDate`——
它的语义是"导出或打印那一刻"，不是"打开那一刻"，否则昨天打开的文档会一直显示昨天的日期。

### 两条纪律

- **求值只更新缓存值，不产生编辑步骤。** 否则打开文档就会往撤销栈里塞东西。
- **域只出现在页眉页脚，正文不开放插入入口。** 病历正文没有"动态页码"的场景，
  页码位置本来就是固定的。但页脚里不能退化成 `Section` 上的一个属性字段——
  因为页脚不是只有页码，典型写法是连着排：

  > 第 3 页 / 共 9 页　　姓名：张三　　住院号：12345

  页码与控件值引用是**混排**的。做成属性字段就没法混排，所以它仍得是页脚内容里的一个行内占位符，
  只是位置天然固定在页眉页脚。这样页脚就是一段普通的内容片段（能装段落、能装占位符），
  规则只有一套。

### 位置

域元素在流里是**原子**：占位宽度按缓存值算，参与断行，不可被拆开。

### 缓存值为空时的宽度

按域类型分别定：页码取零宽（尚未分页时不存在），值引用取**占位宽度**
（避免"回填前页脚短一截、回填后跳一下"）。提示文字（`placeholder`）不进文档，同理。

## 九、表格

已定两条：**跨页时纵向合并的单元格拆成两半显示**（Word 行为）；

**被合并掉的格位可寻址**（落在合并区域内时返回原点格）。

模型走向是"保存 rowspan / colspan、运行时派生网格矩阵、跨度是唯一真相"。

下面先摆清三种做法的差别，再给出与这两个选择匹配的规范。

### 三种做法的实际差别

**OOXML 的做法**：表格声明一个网格（`tblGrid` 的若干 `gridCol`，定义列数与列宽），

每个单元格用 `gridSpan` 声明跨几列、用 `vMerge` 声明是否纵向合并的起点或续格。

网格是坐标系统，**每个单元格都必须起始和结束于网格线**。

纵向合并的续格在 XML 里**真实存在**（是空单元格），只是标记为"续接"。

**HTML 的做法**：`rowspan` / `colspan` 直接写在单元格上，

被合并掉的那些格位**在文档里根本不存在**，任何一行都不会提到它。

**参照项目的做法**：单元格带 `RowSpan` / `ColSpan` 两个属性，

配有 `FixRowSpan` / `FixColSpan` 做越界夹取（跨过表格末尾时截断）。

它同时维护 `Rows` / `Columns` / `Cells` 三个列表。

### 差别在哪里会咬人

**一是"被覆盖的格位存不存在"。** HTML 里不存在，OOXML 里存在（对纵向合并）。

这直接决定"在某处插入一列"要怎么算：HTML 模型下要遍历所有单元格判断是否被跨过；

OOXML 模型下续格是显式的，但要多一步"续格是空的、不能有内容"的约束。

**二是"逻辑单元格列表不反映物理列"。** 这是 python-docx 文档里专门写的一节：

`row.cells` 返回的是逻辑列表，跨列合并之后它的长度仍然等于网格列数，

但同一个单元格会在其中重复出现。所以**绝不能靠遍历 `row.cells` 累加跨度来推列边界**，

必须为每个单元格显式计算 `(start_col, end_col)` 区间。

**三是 Word 自己的 API 在非均匀表上会直接报错。** Word 的 `Table.Rows(n)` 遇到纵向合并

就会抛异常，`Cell.Column` 遇到横向合并也抛。这不是可以效仿的行为。

### 建议的规范

既然选定"跨度是真相、网格是派生"，那**派生的结果必须是不变量**，才有意义：

- 推导函数 `buildGrid(table) -> Matrix<CellRef>`，返回每个网格格位指向哪个单元格。
- 不变量：第二节"表格类"那三条。
- 所有行列操作（插入行、删除列、合并、拆分）都先改跨度，再重新推导网格，

  然后**断言不变量**。断言失败就是 bug，不是"数据就是这样"。
- 对外寻址一律用网格坐标 `cell(r, c)`，落在合并区域内时返回该区域的**原点单元格**

  （左上角）；为什么只能这样，见下面"被合并掉的格位可寻址"。

### 两个已定的选择与它们的实现含义

**跨页拆成两半显示。** 采用 Word 行为：纵向合并的单元格跨过分页线时，在该页重复显示其内容。

实现含义有三条：

- 这是**排版产物，不进模型**。分页器在分页线处把一个逻辑行拆成两页上的两个显示行。

  与域缓存同一个道理——模型只表示"当前内容"，不表示"怎么排"。若不这样定，

  复制一段跨页表格会凭空多出内容，命中与选区也会多出错位的目标。
- 模型里**续格根本不存在**（模型形状见下），所以不存在"续格内容与原点不一致"这类错误，

  不需要额外不变量守住。
- 网格推导要能接受"页内片段"这个上下文：`buildGrid(table, rowsInPage)`。

  对整表调用返回完整网格，对页内片段调用返回该页可见的网格。

**被合并掉的格位可寻址。** 规则：`cell(r, c)` 落在合并区域内时返回该区域的**原点单元格**（左上角）。

这是唯一能让 `cell(r, c)` 在任何表上都可用的规则，也与 python-docx 的做法一致；

否则调用方每次都要先自行判断"这个格位是不是被别人合并了"。

由此确定的模型形状：

```
Table        { rows: TableRow[], gridCols?: Length[] }
TableRow     { cells: TableCell[] }
TableCell    { rowspan: int, colspan: int, content: Node[] }
```

**被合并掉的格位在模型里根本不存在**（HTML 式），只在派生网格里出现且指向原点格。

选了 rowspan 式就彻底一点，不要像 OOXML 那样在模型里再留续格：

好处是"续格不能有独立内容"这条不变量由结构本身保证，不需要单独写检查。

派生网格：`buildGrid(table) -> Matrix<CellRef>`，`CellRef = (origin_row, origin_col)`。

不变量是 `grid[r][c] == (r, c)` 当且仅当 `(r, c)` 是原点格。

## 十、节与页面设置

先把现状差距摆出来：引擎的 `PageMetrics` 只有 `width_pt` / `height_pt` / `margin_pt`

三个字段——**四边共用一个边距**，而且全篇只有一套页度量。下面是需要补全的完整清单。

### 纸张与页边距

```
Section {
  paper:    { name: A4|A5|B5|Letter|Legal|Custom, orient: 纵向|横向, size?: {w, h} },
  margins:  { top, bottom, left, right },        // 四边独立
  gutter:   { size, side: 左|上 },                // 装订线
  mirrorMargins: bool,                            // 双面打印时奇偶页镜像
}
```


纸张用**名称加方向**表示，尺寸是派生值（理由见第十一节）。只有自定义纸张才存显式宽高。

页边距必须四边独立——现在的单一 `margin_pt` 撑不住病历排版，常见的是上窄下宽、左右不同。

### 页眉页脚

- 三组变体：**首页 / 奇数页 / 偶数页**，各自独立（对应 Word 的 `titlePg` 与

  `evenAndOddHeaders`）。三组都是可选，未设置时按"继承上一节或留空"处理。
- 每组是**独立的内容片段**（装块级内容），不是段落属性。它需要自己的编译路径，

  但可以复用同一套块级节点。
- 各自的距边界距离（页眉距上边、页脚距下边），这两个量与页边距是两回事，

  页眉可以落在页边距以内。
- **链接到前一节**标志：默认继承上一节的页眉页脚，显式断链才独立。

  这是一个状态，必须存，否则"改了一节的页眉"会莫名其妙影响后面的节。

页眉页脚里可以放域（页码、总页数、日期、患者信息），所以第八节的域机制要能被它们引用。

### 页码与计数器

页码格式（阿拉伯 / 罗马 / 中文数字）、起始值、本节是否重新编号。

### 节排版

- 节类型：连续 / 下一页 / 奇数页 / 偶数页，决定节与节之间的分页行为。
- 垂直对齐：上 / 居中 / 下 / 两端，内容在页面上的垂直分布。
- **文字方向：横排 / 竖排**。引擎把书写模式当一等公民，所以这一项要与段落的

  `WritingMode` 协调：节给默认值，段落可覆盖。
- 分栏：栏数、栏宽、栏间距、分隔线。
- 页边框、行号。
- 文档网格（东亚排版的字符网格 / 行网格）。

### 脚注尾注

位置（页底 / 文末）、编号格式、起始值。脚注**正文**是独立的内容片段，与页眉页脚同类。

### 文档级属性

节之外，`Document` 上还要挂这些全局表：

- **字体表**：字体名、回退链、是否嵌入。
- **样式表**：见第六节。
- **编号定义表**：多级列表的编号格式、层级、起始值、缩进。
- **资源表**：图片与嵌入对象的二进制，按 ID 索引（架构文档 4.5：二进制资源外置）。
- **主题**：颜色方案与字体方案。
- **书签表**：名字到区间的映射（节点 ID + 偏移），交叉引用靠它。
- **文档属性**：标题、作者、创建与修改时间、自定义属性。
- **保护与权限**：只读区域、可编辑区域、编辑口令。

### 一条设计原则：能存住，不必全理解

文档模型对页面设置的态度是**完整保留、按需理解**。引擎不认识打印机设置、兼容性标记、

主题色这类属性，但必须原样存住、往返不丢。

这条对病历系统尤其重要：导入外院文档或历史文档时，不认识的部分不能丢，

否则"打开再保存"就会悄悄损坏文档。实现上就是**未知属性透传**——

节点与节上留一个可容纳任意键值的属性袋，序列化时原样写出。

### 读写范围（已定）

"完整保留"与"引擎理解"是两件事，本期按下面这条线切：

| 范围    | 属性                                                   | 代价              |
| ----- | ---------------------------------------------------- | --------------- |
| 真正生效  | 纸张（名称 + 方向）、四边页边距、页眉页脚、页码                            | 要动引擎：分页、页度量、页指纹 |
| 只原样存住 | 装订线、镜像页边距、分栏、垂直对齐、页边框、行号、脚注尾注、文档网格、打印机设置、兼容性标记、保护与权限 | 只要属性袋，序列化原样写出   |

本期**引擎真正理解**的是第一行；第二行完整保留、往返不丢，但对排版不产生作用。

最要紧的一个取舍：**文档网格只存不生效**，所以中文排版里"每行多少字"这类设置

不会被引擎遵守。这一点要在导入外部文档时明确告知，免得用户以为格式丢了。

### 风险

节是唯一会让"页度量"在文档中途变化的机制。当前的页指纹与增量上屏按"页"组织，

需要确认它们能容纳"同一篇文档里页宽不同"。这一条要么先做一次探针验证，

要么在本期只支持"全篇同一节"，把多节留到下一阶段。

## 十一、单位与长度

### 两层要分开：显示单位与内部精度单位

"以厘米为基准"这个说法把两件事混在了一起：

- **显示单位**是用户看到的。国内病历场景习惯厘米与毫米，这个诉求成立，

  纸张显示"A4"、页边距显示"2.54 厘米"都是对的。
- **内部精度单位**是算排版用的。它要满足的不是"像公制"，而是"常用单位都能精确整除"。

这两个可以完全不同。**显示用公制、内部用一个能整除所有单位的整数**，是这一节的全部结论。

### 为什么内部不以厘米为基准

三条理由，都有据可查：

**一、文字排版的基本量全部以磅定义。** 字号的行业单位是半磅（OOXML 的 `w:sz` 就是半磅，

小四 = 24、五号 = 21），行距是磅或倍数，线宽是 0.5 / 0.75 / 1 磅。

若内部以厘米的倍数计，每次字号参与计算都要乘一个循环小数系数——

12 磅写成厘米是 0.42333…，无法精确表示。

**二、毫米对排版来说太粗。** 1 毫米 = 2.83 磅，而排版要对齐到千分之一磅量级

（`auditLayout` 的坐标容差就是 1e-3 磅）。要做到这个精度，厘米基准必须细分到

约 1/28000 厘米——细分到这个程度，"可读性"这点好处也就没了。

**三、公制整的纸，英制不一定整，反之亦然。** A4 在厘米下是 21 × 29.7（整），

折成磅是 595.276 × 841.89（不整）；Letter 在磅下是 612 × 792（整），

折成厘米是 21.59 × 27.94（两位小数）。**只有一种单位能让两边同时精确**，

那就是下面说的 EMU。

主流格式的选择也印证这一点：CSS 的绝对长度单位里明确写着 **px 是 canonical unit**

（`1in = 96px = 72pt`），即 CSS 也锚在英制关系上；WordprocessingML 用缇（1/20 磅）；

PDF 原生用磅。**没有一个主流格式以厘米为内部基准。**

换算表保留以便对照：

| 单位     | 到磅                   | 备注                     |
| ------ | -------------------- | ---------------------- |
| 磅 pt   | 1                    | 印刷与 PDF 的原生单位          |
| 缇 twip | 1/20                 | WordprocessingML 的原生单位 |
| 像素 px  | 3/4                  | CSS 像素，1 in = 96 px    |
| 英寸 in  | 72                   | 精确定义                   |
| 厘米 cm  | 3600/127 ≈ 28.346457 | 循环小数                   |
| 毫米 mm  | 360/127 ≈ 2.834646   | 同上                     |

注意厘米与毫米是**循环小数**：A4 宽 21 cm 恰好是 75600/127 磅。任何有限精度都表示不精确，

这不是缺陷、无法回避。所以下面两条比"选哪个单位"更要紧。

### 语义与数值分开

**纸张用名称加方向表示，尺寸是派生值。** `A4 + 纵向` 是一个精确的语义；

它的宽高换算成磅会舍入，但语义没丢，用户看到的仍是"A4"而不是"595.28 磅"。

只有自定义纸张才存显式宽高，而且要**连同用户输入的原单位与原数值一起存**，

这样往返显示才是"21 厘米"而不是"595.276 磅"。

页边距同理：存 EMU，但记住用户习惯的显示单位（国内默认厘米），显示时换算并舍入到两位小数。

### 内部精度单位选 EMU

EMU（English Metric Unit，1/914400 英寸）是**唯一一组让磅系与公制同时精确整除**的单位。

名字本身说明了它是为这个目的造的，OOXML 的 DrawingML（图片、图形、形状尺寸）用的就是它：

| 单位              | EMU    | 是否精确 |
| --------------- | ------ | ---- |
| 磅 pt            | 12700  | 精确   |
| 半磅（字号单位 `w:sz`） | 6350   | 精确   |
| 缇 twip          | 635    | 精确   |
| 像素 px（CSS）      | 9525   | 精确   |
| 毫米 mm           | 36000  | 精确   |
| 厘米 cm           | 360000 | 精确   |
| 英寸 in           | 914400 | 精确   |

作为对照，先前考虑的 1/1000 磅（微点）方案：

| 单位     | 微点       | 是否精确 |
| ------ | -------- | ---- |
| 磅 pt   | 1000     | 精确   |
| 缇 twip | 50       | 精确   |
| 像素 px  | 750      | 精确   |
| 毫米 mm  | 2834.65  | 不精确  |
| 厘米 cm  | 28346.46 | 不精确  |

**定成 EMU。** 不止因为公制精确：

- **精度更足。** EMU 步长 7.87e-5 磅，比 `auditLayout` 的 1e-3 磅容差细 12.7 倍；

  微点步长恰好等于容差，余量为零。
- **与 OOXML 图形零换算。** 将来导入导出图片尺寸、形状位置时直接用 EMU。
- **范围够用。** A4 高是 10,692,000 EMU，int32 上限约 21.5 亿（约 59 米），

  装在 32 位里绰绰有余；要更大范围再换 int64。

为什么必须定点整数而不是沿用 float，三条理由：

**相等比较可靠。** 增量排版要判断"这一行有没有变"。float 现在能比较，是因为同一份代码

在同一台机器上算出同样的值；一旦模型重建（重新打开文件、撤销重放、跨平台），

最后一位就可能不同，于是"没变的东西被判为变了"，增量的正确性判据会开始闪红。

**序列化无歧义。** 整数直接写。浮点要靠"按十进制字符串写"这条补丁（架构文档 4.5），

定点整数是从根上解决。

**跨平台一致。** 不依赖浮点单元的融合乘加行为。

代价要说清楚：数值比磅大 12700 倍，直接读不直观（A4 宽是 7560000 而不是 595.276）。

所以**必须配一对转换函数加一个调试打印器**，任何手写的 EMU 字面量都算错误——

写 `cm(2.54)` 而不是 `914400`。

边界在哪里：**模型保存的是"用户输入的意图"（精确值），引擎算的是"排版结果"（可以有误差）**。

所以整数在模型层、浮点在引擎层，编译时做一次乘除。

### 长度不只有"绝对"

这是比换算更要紧的一层：**长度有三种性质，必须用类型区分，不能一律塞成数字。**

```
Length = Abs(EMU) | Percent(分子, 分母) | Em(倍数, 相对当前字号) | Auto
```

各自出现的场合：绝对用于字号、页边距、纸张尺寸、边框宽度；

百分比用于表格列宽、图片宽、缩进；em 倍数用于行距、按字符数计的首行缩进；

自动用于表格 autoFit、图片按原始尺寸、列宽按内容。

把它们混成一个 `float` 会在三处直接出错：表格算列宽时不知道百分比相对谁、

行距的倍数无法与固定值区分、`Auto` 没有数值可以表达。

### 行距是一个具体的坑

Word 的行距有三态（`w:spacing` 的 `lineRule`）：

- `auto`：倍数。现在 `BlockSpec::line_factor = 1.6` 就是这一态。
- `exact`：固定值，行高恰好等于该值，字大了会裁切。
- `atLeast`：最小值，取"内容高度"与该值的较大者。

三态的排版行为不同，模型里必须能区分，不能只存一个数字。现状只有 `line_factor`，

属于 `auto` 态；补另外两态时行高计算要分叉，而这一点会影响增量续排的块轴推进公式

（见 `engine.h` 里那段"横排的块轴推进是一条纯折线"的注释）。

### 像素与 DPI

模型里**不应出现像素**，因为像素是设备相关的。屏幕渲染时的"磅到设备像素"

是 `EngineConfig::zoom` 的事（现在是 2.0，约 144 dpi），属于视图层。

唯一例外是**图片的原始尺寸是像素**：`Image` 需要

`{ 像素宽, 像素高, DPI, 显示尺寸 }`，显示尺寸是 `Length`。

若只给像素不给 DPI，按 96 DPI 假设换算，这也是行业惯例。

### 换算的三个边界

- **入口**：用户输入、导入文档 → 换算成 EMU，只发生一次。
- **出口（显示）**：EMU → 用户偏好单位，舍入到显示精度（厘米两位小数）。
- **出口（渲染与导出）**：EMU → 磅交引擎；导出 PDF 原生用磅；导出 HTML 用像素。

绝不出现"存厘米、算磅、再存厘米"这种往返换算。

## 十二、修订留痕与批注

这是本期工作量最大的一块，但**它恰好能被"可逆步骤"大幅简化**。

### 两条路线

**Word / OOXML 路线**：把修订标记写进文档树。插入内容包在 `w:ins` 里、删除内容包在

`w:del` 里（**被删的内容仍然留在文档里**，只是标了删除），格式变更另用 `w:rPrChange`。

每个标记带作者、时间、修订 ID 与 RSID 分组。

这条路线的问题是模型污染：文档树里同时存在"当前有效内容"和"待定的影子内容"，

于是遍历、排版、命中、序列化全都要判断"这个节点有没有被删"。参照项目里

`DomElement` 上的 `Modified`、`DCContent` 与 `DomDocument` 里的修订相关字段，

就是这类污染的痕迹。

**步骤叠加路线**：文档是**基线**，修订是一串**未被折叠的步骤**叠加在基线之上。

接受一条修订 = 把它折叠进基线；拒绝 = 丢弃它（或应用其逆）。

显示时把待定步骤以装饰形式画在视图层。

这条路线是干净的：文档树本身永远只表示"当前内容"，修订是视图态的叠加。

它与 ProseMirror 的 Decoration 是同一个思想——**临时标记不污染真相**，

而"真相"恰好就是我们已经有的可逆步骤。

### 建议

走步骤叠加路线。具体形状：

```
RevisionLog = [{ step, author, time, state }]   state ∈ { pending, accepted, rejected }
```

- 文档内容 = 基线 + 已接受的步骤（展开后）。
- 界面上显示的是"展开后"的结果，`pending` 的步骤以作者颜色与删除线呈现。
- 接受与拒绝只改 `state`，然后重新从基线展开。
- 序列化时基线落盘、`pending` 的修订一并落盘，`accepted` 的已经进基线。

代价要说清楚：**与 Word 互导需要一层适配**，把步骤序列翻译成 `w:ins` / `w:del` 标记。

这是边界适配器的事，与"内部用 JSON"是同一个道理。

批注比修订简单：它只是"挂在某个节点区间上的附注"，用节点 ID 加区间做锚点，

不需要进文档树。所以**节点 ID 必须落盘**这条不变量在这里派上用场。

## 十三、序列化形状

接上一轮结论（JSON 做语法、包做容器、压缩做体积，见架构文档 4.5）。模型这一侧要定三件事：

**扁平不嵌套。** 序列化成"节点表 + 样式表 + 属性表 + 子节点索引数组"，而不是嵌套对象。

理由有二：更小（没有嵌套括号），以及更适合差量落盘——嵌套树改一处要重写整个文件。

数据形状是"节点数组 + 每个节点的子节点区间"，本质是把树按深度优先序拍平，

再用 `child_count` 重建层级（这也是上一轮测二进制时用过的 payload 形状）。

**段落不落盘。** 段落是派生量（第二节）：落盘的只有 `ParagraphMark` 元素与它的属性，重新打开时由标记重新导出段落。这样不会出现"段落对象与标记不一致"这类错误。

**ID 落盘。** 节点 ID、控件 key、样式名都要写进文件。

否则重新打开之后，批注锚点、跨文档引用、样式引用全部失效。

代价是文件略大，收益是引用关系可持久。ID 用局部递增的整数而非 UUID，配合符号表编码。

**选区不落盘。** 选区是会话状态（第二节）：序列化只落它的外观选项（高亮色、
是否含背景文字这类），不落选区本身。参照项目就是这么做的——它的 JSON 里与 Selection
相关的只有 `SelectionHightlightMaskColor` 与 `SelectionTextIncludeBackgroundText` 两个键。

**字段名进符号表。** 节点类型、属性名、样式名各建一张符号表，正文里只出现下标。

实测这一条把体积从 84.8% 降到 25.4%（架构文档 4.5.1）。

浮点按十进制字符串写这条已有结论继续适用：坐标、字号、行高都要过

`parse(print(doc)) == doc`。

## 十四、与排版引擎的接口

这是全案最容易出问题的地方，因为它决定"引擎要不要改"。

**保持单向编译。** 树到引擎输入的转换是单向的、可缓存的：

```
Document (树)
  → compile() → 段落序列（每段：书写模式、字体、行距 + 一段"行内盒子"序列）
  → 引擎整形 / 断行 / 分页 / 增量续排
```

引擎仍然只认识"段落 + 段落内的行内序列"，不认识树。而**方案一让这一步几乎是恒等映射**：
模型的流被段落标记切成若干段，就是引擎要的段落序列；流里的元素逐个映射成行内盒子，
容器的边界元素映射成行内叶子，图片、公式映射成不可断的盒子。不需要"把树展开成流"这一步
翻译，因为模型本身就是流——这正是选方案一时的首要理由。

**脏段标记怎么来。** 流顺序就是段落顺序，所以"改动落在流里的哪个位置"可以直接映射到
"第几段变脏"，中间不需要遍历树。现有的 `layout_dirty_from_` 是"一个数"（连成一段的后缀），
这对编辑是够的；但对样式表变更、节变更、批量设值这类**散布式改动**不够用（见第六节末尾）。
先按全量处理，测出瓶颈再扩展成集合。

**引擎真正的新输入有两样。** 一是**行内原子**：图片、公式要作为"不可断的盒子"参与断行，
宽度计入行盒、不能落在行中间被拆开、增量排版要能识别"这一个盒子没变"。
二是**边界元素**：控件的起始与结束边界也是行内叶子，而且**有宽度**
（参照项目取 `max(宽度, 12.5)`，保证鼠标点得着）；设了固定宽度的控件比那条更强，
它是**指定的**宽度（见第七节）。放置成对边界时要保证结束边界不排到起始边界之前——
参照项目的 `CheckStartEndElement()` 就是做这件事的，我们把它作为编译期断言。
两样都在阶段 4 做专门验证。

**不变量的对应关系。** 引擎已有两个可证伪判据（`auditFrame` 逐像素、`auditLayout` 逐字段）。

模型层要补第三条：**编辑往返判据**——随机生成编辑序列，全部应用后再全部撤销，

文档必须与初始状态逐字段相同。这条判据覆盖的是模型层，与引擎的两条互补。

## 十五、迁移阶段

本节是**模型层自己的步号，与架构文档第五节的阶段号不是一套，不要混用**：0.x 对应架构的
阶段 0，1.x 覆盖架构阶段 1–6 里落在文档模型上的那些步（1.7 表格对应阶段 5、
1.10 序列化对应阶段 6），拆得更细是为了每一步都能单独转绿。顺序不能跳。

| 步   | 做什么                                | 判据                                         |
| --- | ---------------------------------- | ------------------------------------------ |
| 0.1 | 节点基类与 ID 分配器、`Pos` 与流位置的双向换算 | 换算往返相等；随机位置测试 |
| 0.2 | 元素流与段落标记、每容器一个标记下标数组 | 下标数组与从头扫描的结果逐项相同；插入删除后仍相同 |
| 0.3 | 不变量检查器（第二节逐条实现为可调用的断言） | 对现有文档跑一遍全绿 |
| 0.4 | 编译：流 → 段落序列，暂只支持文本与段落 | 编译结果与现有 `BlockSpec` 路径逐字段一致 |
| 0.5 | 长度类型（绝对 / 百分比 / 字符数 / em / 自动）与 EMU 定点表示 | 换算往返一致；长度类型经序列化后不丢 |
| 1.1 | 文本节点与标记合并规范化 | 规范化幂等（跑两次结果相同） |
| 1.2 | 编辑步骤与逆操作，先覆盖插入、删除、分段与合并；区间原语（提取 / 删除）与位置映射 | 每个步骤的往返判据；提取后删除再插回等于原状；端点落在控件内部时外扩到边界、片段始终成对；`map` 与逆映射往返一致 |
| 1.3 | 事务层与撤销分组 | 撤销 N 次回到原状态；帧仍与全量一致 |
| 1.4 | 容器元素（内容控件、链接），边界位置，表单模式的落点判定 | 上一轮四个缺陷的复现脚本转绿：同段内每个偏移的归属与渲染位置互不相同；每个合法位置都能靠方向键到达；表单模式下点击落在不可编辑区时光标不动、方向键与 Tab 跳不出可编辑集合；Shift 扩展与拖拽可以跨出控件；越界的编辑动作被拒且有原因回执；只读控件内嵌的可编辑控件位置仍不可编辑；表单模式下 Tab 只落在可编辑控件上、只读模式 Tab 放行给宿主、末个可编辑控件按 Tab 也放行、表单模式不提供插制表符的默认键位（`insertTab` 命令默认不绑键）；结构操作默认被拒，控件声明可删后才允许 |
| 1.5 | 控件索引与宿主 API（枚举、批量读写、批次、校验钩子与异步裁决、校验状态、外观属性） | 设 1000 个字段与设 1 个字段耗时同一量级；只产生 1 个撤销步骤；最终帧与逐个设置逐像素一致；异步钩子等待期间文档与撤销栈逐字段不变，`Deny` 后与交互前一致；`overflow` 三档的可见范围与预期一致；越界交互的回调按"同 kind 同位置连续只报一次"去重 |
| 1.6 | 样式表与三层解析、缓存 | 样式继承链的解析结果与手算一致 |
| 1.7 | 表格（第二节表格类不变量） | 网格推导的不变量断言；行列操作后仍成立；`cell(r,c)` 落在合并区域返回原点 |
| 1.8 | 域、页眉页脚、分节 | 求值幂等；悬空值引用报错；分节强制分页与全量一致 |
| 1.9 | 修订留痕（步骤叠加） | 接受 / 拒绝后展开结果与手算一致 |
| 1.10 | 序列化与往返 | `parse(print(doc)) == doc`；ID 与 key 往返不变 |

每一步都要求不改变对外行为，直到该步自己的判据转绿。这一步之所以能"边做边验"，

是因为模型层的判据是自足的，不依赖界面。

## 十六、未决项与已定项

本节每条都标了状态：**待确认**（需要一次探针或一次选型才能定，会影响排期）、
**待测**（做法已定，判据待实测）、**已定**（决策记录，实现时照它做）。

### 待确认（按优先级）

**一、分节要不要本期做（需一次探针才能定）。** 分节就是 Word 里"不同纸张"那个功能，

但不止纸张——页眉页脚、页码重编、分栏、文字方向都能按节变化，见第十节。

它是唯一会让页度量在文档中途改变的机制，而页指纹与增量上屏现在按"页"组织。

建议先做一次探针：构造一篇两节的文档（前节 A4 纵向、后节 A4 横向），

跑 `auditFrame` 与 `auditLayout`，看增量结果与全量是否逐像素 / 逐字段一致。

一致则本期可做分节，不一致则本期只支持单节。

**二、修订留痕的互导要求。** 若病历必须与 Word 或院内系统交换带痕文档，

步骤叠加路线要多写一个 `w:ins` / `w:del` 适配器，需要单独排期。

**三、公式的排版后端**（架构文档已有此项）：本期只要"能插入、能显示、能存"，

还是"可编辑、可参与计算"。

### 待测（做法已定，判据待实测）

**四、异步校验钩子的 pending 呈现。** 钩子返回 Promise 时，编辑器悲观持有候选变更、
控件停在 `pending`，等待期间文档与撤销栈必须逐字段不变。判据：
用一个人为延迟 200 ms 的钩子做探针，等待期间 `auditLayout` 全等、
撤销栈深度不变、控件不显示新值；`Deny` 后值与校验状态与交互前一致。

**五、批量设值的脏区。** 批量设值会让脏区散布全篇，`layout_dirty_from_`
这个"一个后缀"的表达可能不够用。先退化全量、测出真实数字，再决定是否把脏段标记扩展成集合。

### 已定（决策记录）

**六、表格（决策见第九节）。** 跨页拆两半显示、被合并格位返回原点、模型里续格不存在。

待验的是 `buildGrid` 与分页器的配合，放在阶段 1.7 的判据里。

**七、内容控件在段落内的嵌入位置（方案一）。** 段落降为流里的范围、控件是跨度之后，
"行内嵌入"（`主诉：[____]`）与"一栏里多段"是同一个机制的两个取值，不需要
`InlineControl` / `BlockControl` 两个类型，也不需要"行内升级为块级"的提升规则。见第三节。

**八、固定宽度下值超出时的显示行为（属性配置）。** `overflow ∈ { expand, clip, spill }`
三档，默认 `expand`（不静默丢数据）；`clip` 与 `maxLength` 的一致性由诊断守。
不做"控件内横向滚动"——控件是流里的跨度、没有滚动视口，值超出只有这三档处理。
见第七节。

**九、浮动图片与文字环绕（本期只做内联，模型留位）。** 内联图片只是一个不可断的行盒，

引擎已有这类盒子的处理路径（括号占位就是这么做的），成本低。

浮动图片的成本**几乎全在引擎侧，模型侧近乎为零**：

| 能力             | 需要动的地方                                |
| -------------- | ------------------------------------- |
| 浮于文字上 / 下（不环绕） | 段落外新增浮动层 + 光栅分两趟绘制                    |
| 四周环绕           | **断行核心**：每行的可用宽度不再是一个常数，而随浮动框横向范围变化   |
| 绝对定位与锚点        | 图片挂在某段上但显示在别处；跨页时要定跟随规则               |
| 增量             | 浮动框移动会让影响范围内的**所有行**重排，脏区不再是"连成一段的后缀" |

后两行是与现有架构冲突的地方：断行"左右边界是常数"与脏段"后缀"两个假设都要改。

所以分期做：本期内联；下一期做"浮于文字上下方"（不动断行）；最后才做环绕。

模型这边只需在 `Image` 上留好定位方式与环绕方式两个枚举，节点类型不变，

所以**先留位、后补引擎**不产生返工，它也不该拖住阶段 0 与 1。

**十、页面设置的读写范围。** 真正生效的是纸张、四边页边距、页眉页脚、页码；

其余（装订线、镜像页边距、分栏、垂直对齐、页边框、行号、脚注尾注、文档网格、

打印机设置、兼容性标记、保护与权限）本期只原样存住、不参与排版。完整清单见第十节末尾。
