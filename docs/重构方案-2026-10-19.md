# 重构方案：不可变修订 + 纯查询

前提：不考虑旧代码兼容与重写成本，只回答"最好的形状是什么"。
约束来自产品本身，不来自现有实现：跨段控件（字段可以从一段中间开始、到另一段中间结束）、
表格扁平进流、横竖排、分页、wasm 交付、逐像素判据。

> ★ 同日夜间追记：写完之后落了两项改动 —— 自写扫描线光栅器删除（两侧共用
> `bitmap_skia.cpp`）、两套宿主合并（`engine_api.js` + `host_core.js`）。
> 六个决定一条都没有翻转，变的是起点与两处口径：D6 的"三处写法"已收成两处（剩 C++ 侧），
> 第九节补了光栅只剩一套之后的判据归属，并顺带指出 8~9 ms 里含帧内搬运。

---

## 零、一句话

把"可变的状态机 + 手工失效"换成 **不可变修订 + 纯函数 + 按内容哈希记忆化**。

现在的引擎是"一棵可变的树 + 十几个派生的可变数组 + 一套告诉它们什么时候过期的纪律"。
新形状是"一次编辑产出一个新修订（旧的不动）+ 每个派生量都是它的纯函数 + 缓存由哈希命中，
不由形状判定"。三条现在靠纪律维持的性质会变成结构性质：写入口唯一、派生量不会失配、
增量与全量必然一致。

## 一、六个决定

### D1 文档是不可变修订

```cpp
struct Revision {
    std::shared_ptr<const Node> root;
    uint64_t seq = 0;
};

struct Node {
    NodeKind kind;
    NodeId id;                     // 宿主句柄，跨修订稳定
    uint64_t hash;                 // Merkle：kind + 载荷 + 孩子哈希
    std::vector<NodeRef> children; // NodeRef = std::shared_ptr<const Node>
    Payload payload;               // variant，按 kind 只带自己的字段
};
```

- 一次编辑 = 沿路径复制 O(深度) 个节点，其余节点共享。2000 段的文档敲一个字，
  新分配十来个节点，不是整份文本。命令顺带返回新的选区（它知道自己改了什么），
  不需要把旧位置映射过去。
- **撤销就是一串旧修订**。没有逆步骤、没有 `mapPos`、没有"删除之前光标在哪一端"、
  没有 `detached` / `attachChild` 的身份往返。
- **保存就是序列化一个修订**；打开就是反序列化成一个修订。宿主不再持有文档副本。
- 节点按种类带自己的载荷（`variant` 或按 kind 分配的 `unique_ptr`），
  不再是 1496 字节的并集结构体 —— 顺带把内存与缓存局部性拿回来。

### D2 位置只有一种：流位置，容器边界也占位置

```cpp
struct Position { uint32_t flow; uint8_t affinity; };   // affinity 只区分折行的两行
```

现在"段 + 码点偏移 + 侧别 + 行别 + 格号"五件套，是因为**多个边界挤在同一个码点偏移上**。
把每个容器的起止边界都当成一个流位置（控件今天已经这么做），五件套就只剩一个数：

- 括号的"在 [ 之前 / 进控件 / ] 之内 / 之后"是四个不同的 flow，不需要 `side`；
- 格内的位置（含空格）按格首/格尾两位寻址，不需要"格的身份是块区间"；
- 命中测试只回一个 `Position`，宿主原样送回，不需要四个出参再重建。

`Selection` 也随之只剩一条记录：

```cpp
struct CellRect { uint64_t table; int r0, c0, r1, c1; };   // 只在 gran == Cell 时有效
struct Selection { Position anchor, focus; Granularity gran; CellRect rect; };
```

格选区**仍然**是一条矩形（表 + 行列范围）而不是 flow 区间 —— 矩形在流里不连续这一点没变，
跨行拖选不能靠求交算出来。变的是它不再是四个并行字段：一条与 `gran` 同生共死的记录，
其余（流包络、插入点、每行该不该反白）全部现算。`CellBlocks`、`cell_lo_/hi_`、`cell_mask_`、
`cell_caret_` 与那三个谓词一起消失。

### D3 投影与排版是纯函数，记忆化代替形状判定

```cpp
Projection project(const Revision&, const ViewParams&);
BlockLines layoutBlock(const Block&, float column_w, float avail_h);
PageTable  paginate(const std::vector<BlockLines>&, const PageMetrics&);
Bitmap     rasterPage(const Page&, const Style&, float zoom);
```

- `project` = 今天的编译 + 流索引 + 控件导出，**一次遍历同时产出**：块（文本是修订里的切片，
  不复制）、对象表、格表、控件表、位置索引。没有 `blocks_` / `blocks_full_` / `flow_` /
  `block_flow_` / `block_src_` / `control_node_ids_` / `owner_index_` 七份东西。
- 括号显示范围是 `ViewParams` 的一项，是**参数**，不是"改产物"。`blocks_ = blocks_full_`
  那次整份深拷贝不再存在。
- 每个块带内容哈希。缓存键 =（块哈希，列宽，可用高，样式哈希）。命中就复用，
  不命中就重算 —— 不需要 `ParaDelta`、不需要 13 个 reject 码、不需要"往回扫新标记"。
  表格、控件、段落标记、任何新内容类型走同一条路：**哈希不同的块重算，其余照搬**。
- 连"损伤报告"都不需要：两个修订的 Merkle 哈希一比，不同的块就是损伤，而且精确。
  上一轮评审建议的 `Damage` 结构是给可变状态补的；状态不可变之后它自动成立。
- `ViewParams` 变了（切模式、换页度量、改括号范围）就整份重投影，这是本来就该付的；
  它不再是"一部分产物按新树、一部分按旧树"的风险源。

### D4 排版拆成两件事：断行（块局部）与分页（前缀和）

今天是"一个 fold，状态是三个标量"，于是表格续不上、竖排吃页尾续不上、只能给它们开后门。
拆开之后，两件事各自是纯的：

- **断行**只依赖（块内容，列宽，可用块轴高度）。表格的列宽来自表规格，与页码无关；
  竖排的"可用高"显式作为参数传进来，不再藏在 fold 状态里。
- **分页**是"每块多高"的前缀和：一个 Fenwick 树或一棵高度树，O(log n) 维护。
  页号只存在页表里，不写进每个字形与行盒。
  两处例外是允许跨页拆分的表格行与"竖排吃页尾"：它们在页边界上做一次局部顺推，
  范围只在一张表或一个竖排块之内，不会扩散成整篇重排。
  节是分页域：每节带自己的页度量与页眉页脚，前缀和在节内做，节与节之间只接页号。

这是性能与正确性一起拿回来的地方：今天 `PlacedGlyph` 与 `LineBox` 各自带着 `page` 与全局
`line`，于是分页一变就要重写整个后缀（`shiftSuffixBlockAxis`、`markPagesChangedFrom` 那一族）。
页号与行号是页表的投影，不是元素自己的属性；不写进去，就没有"整体平移"这回事。
顺带：118k 个字形每个少两个 `int`。

### D5 渲染的单位是页，不是帧

今天帧是"视口窗口"，页号要模槽数、帧槽与画布槽两套编号、8 本账判断"画面上是什么"。
但产品主线（worker 宿主）本来就是**一页一张画布**，帧只是历史遗留的中间层。

新形状：

```cpp
Bitmap rasterPage(page_id);            // 纯：按页内容哈希缓存
Bitmap overlayPage(page_id, sel, caret);         // 小层，变了才重画
```

- 页是天然的失效单位：改一个字只重光栅它那一页（8~9 ms，已实测）。
  滚动只需要光栅新露出来的页，其余页的位图不动。
  页内可以保留行带差分，但那是光栅器内部的缓存（键是行的哈希），不是引擎状态。
- 覆盖层不擦不补、不做新旧矩形差集，直接重画一小张透明层交给宿主合成；
  宿主按 (selection, caret) 的值缓存这张小图，值没变就不重画。
- 宿主缓存页位图，窗口 = "要哪几页"。帧、槽、`slot_page_`、`frame_needs_full_refresh_`
  整族概念消失。

### D6 门面由一份 IDL 生成，宿主只持修订号

```text
command typeText(text) -> {rev, changed_pages}
query   pageBitmap(page) -> bytes
query   serialize(rev) -> bytes
```

- C++ 导出、worker 命令表、宿主门面、TS 类型全部从这份 IDL 生成。
  `PRESENT_ALWAYS` 那种"哪些入口自己会画"的手抄表不存在 —— 协议里每个命令都声明
  "改不改状态、回不回帧"。
  宿主合并已经把 JS 那一半做掉了（`engine_api.js` 的 `WRITE`/`READ` 一份、
  `PRESENT_ALWAYS` 一处）；IDL 剩下的活集中在 C++ 侧：wasm 导出与手拼 JSON 现在
  与命令表没有对上号的判据，"漏一个导出"只有跑探针才暴露。
- 宿主状态 = `{rev, viewport, selection, mode}`，全是可序列化的值。
  没有 `g_blocks`、没有 `syncBlocksFromEngine`、没有 `mirror` 里 `m.x || mirror.x` 的兜底。
- `ControlApi` 不再是一条独立的写路径：设值就是一组命令，产出一个新修订，
  与打字走同一个 `apply`。

## 二、目标结构

```
Revision ──project(view)──▶ Projection ──layoutBlock──▶ BlockLines ──paginate──▶ PageTable
    │                            │                                                  │
    │                            └────────────── PositionIndex ──────────────────┐ │
    │                                                                           ▼ ▼
    └── apply(cmd) ◀── Command ◀── Session{rev, sel, view, history}        rasterPage → 宿主
```

- **`Revision` 是唯一的真值**；`Projection` / `BlockLines` / `PageTable` / `Bitmap` 都是它的纯函数，
  可以随便缓存、随便丢，丢了重算结果一样。
- **`Session` 只有四样状态**，全是值：当前修订、选区、视图参数、历史。
  引擎不再有 60 个成员与 8 本账。
- **`apply` 是唯一的写入口**。树不可变，所以"绕过提交路径"在类型上就做不到。

命令层（`EditCommand`）基本原样保留：落点判定、控件边界四条规则、整格删除、跨表删除，
这些是业务语义，与状态怎么存无关。变的是出口：`commitEdit` 换成 `return new Revision`。

## 三、这套设计删掉什么

| 现在 | 重写后 | 为什么能删 |
| --- | --- | --- |
| `UndoStack` + `invertStep` + `mapPos` + `caret_at_end` | 历史里的旧 `Revision` | 撤销是回到旧值，不是反向执行 |
| `InsertNode.detached` / `attachChild` / `createDetached` | 不需要 | 没有"把摘下的子树挂回去"这回事 |
| `blocks_` `blocks_full_` `flow_` `block_flow_` `block_flow_span_` `block_src_` `control_node_ids_` `owner_index_` | 一个 `Projection` | 同一次遍历产出，不再事后递推 |
| `blocks_ = blocks_full_` 整份深拷贝 | 不复制文本 | 括号筛选是参数 |
| `ParaDelta` + 13 个 reject + `rebuildAfterSplit` 往回扫 | 哈希记忆化 | 命中复用，不命中重算 |
| `ReflowState` 三标量 + `can_resume` 的 `&&` + 表格全禁 | 断行纯函数 + 分页前缀和 | 状态补全，不需要后门 |
| `CellBlocks` / `cell_lo_/hi_` / `cell_mask_` / `cell_caret_` / 三个谓词 | `Selection{anchor, focus, gran, rect}` | 一条记录 + 现算，不再四字段同步 |
| 帧 + 两套槽号 + 8 本账 + `presentInternal` 742 行 | 页位图 + 页级缓存 + 覆盖层 | 页是失效单位 |
| `g_blocks` + `syncBlocksFromEngine` + `demoTree` 重建 | `serialize/deserialize(rev)` | 宿主不持有文档 |
| `PRESENT_ALWAYS`（已收成一份，仍是手抄）+ wasm 门面 104 处手拼 JSON + `mirror` 兜底 | 一份 IDL 生成 | 协议一处定义 |
| `Node` 并集 1496 字节 | 按 kind 带载荷 | 只带自己的字段 |

## 四、性能账（为什么不会更慢）

一次按键，2000 段文档：

| 步骤 | 现在 | 重写后 |
| --- | --- | --- |
| 改树 | 就地改 + 提交事务 | 路径复制 ~10 个节点 |
| 编译 | 整段重编（0.1 ms）或整树（8.5 ms） | 一个块按哈希重算，其余共享 |
| 流索引 / 块起点 | 整树重建 + 整表递推 | 投影时顺带产出，只有改动块重算 |
| 块流副本 | 整份深拷贝 | 不存在 |
| 控件导出 | 全表导出 + normalize | 只有改动块重算 |
| 排版 | 续排到末尾（表格/控件场景退化） | 改一个块 + 分页 O(log n) |
| 光栅 | 页内行带增量 | 一页 8~9 ms，其余页位图不动 |
| 覆盖层 | 新旧矩形差集 | 一张小层现画 |

真正的收益不在"每次按键少几毫秒"，在于**最坏情况消失**：今天在长表单文档中段打字会退化到
"从脏段排到末尾"（后缀复用被对象表判据挡掉），撤销会退化到整篇；重写后这两条都只与
改动块有关（表格行拆分与竖排吃页尾是仅有的两处局部顺推）。
分页前缀和是唯一随文档变长的东西，而它是 O(log n) 的整数运算，不是重排。

## 五、会变难的地方

1. **不可变树在 C++ 里要自己写**：引用计数节点、路径复制、Merkle 哈希，约 600~900 行。
   它替换掉的是 `steps.cpp`（1238 行）+ 事务 + 引擎里那一堆重建逻辑，净账不亏，
   但第一版必须配属性测试：随机编辑序列 × 与可变树逐字段比对。
   容器节点的孩子表第一版用写时拷贝的 `vector`（一段 2000 个块时每次复制几十 KB 指针，
   微秒级）；块数真到万级再换持久化向量，接口不用变。
2. **父指针要拿掉**。现在 `mark->parent` 到处用；不可变树里父指针会悬空。
   改成"遍历时带路径"或由 `PositionIndex` 提供 id → 路径。好处是再也不会有人
   悄悄拿一个过期的父指针。
3. **缓存要从值里搬出来**。`ShapingCache`、字形缓存、页位图都必须挂在会话或全局，
   以哈希为键；值本身必须真的只读。这条纪律比现在的"重建之后要再摆一次视图"好守，
   但一开始会不习惯。
4. **竖排的"可用高"要变成显式参数**。今天它藏在续排状态里，重写后必须由分页回传；
   写错了会表现为"竖排列高对、断页不对"。这是整个方案里唯一一处需要小心设计接口的地方。
5. **探针与测试要改写法**：从"调一个会改状态的入口"变成"命令 → 新会话"。
   这是机械改动，但量大（1300+ 条断言）。

## 六、重建顺序

不是渐进兼容，而是先立骨架、再搬算法：

1. **修订层**：不可变树 + 哈希 + 路径复制 + 序列化。判据：随机编辑序列与旧实现逐字段一致；
   `deserialize(serialize(rev)) == rev`。
2. **投影层**：`project(rev, view)`。判据：与旧 `blocks_` / `tables_` / `controls_` 逐字段一致，
   含括号筛选、隐藏控件、跨段控件、嵌套表。
3. **排版层**：把 `layout.cpp` 拆成 `layoutBlock` + `paginate`。判据：与 `layoutDocument`
   逐字段一致（表格、竖排、跨页行都要覆盖）；顺带验证 `auditLayout` 对表格不再是盲的。
4. **会话层**：命令 → 新修订，历史 = 修订栈。判据：现有 1341 条编辑断言 + 撤销/重做回放。
5. **渲染层**：页位图 + 覆盖层。判据：与旧帧逐像素一致（`auditFrame` 换一个比较对象）
   —— 光栅只剩一套之后这条比较才真的同源，跨构建仍然不算数。
6. **宿主与 IDL**：生成门面，删掉 `g_blocks`、`PRESENT_ALWAYS`、手拼 JSON。

前四步做完，产品就能跑；后两步是收尾。

## 七、必须原样搬过来的

这五样是这几年真正的资产，重写时一行都不要改逻辑：

1. **整形与字体**：HarfBuzz 调用、回退链、SIMD。字形缓存已经不是自写的那一份了 ——
   用 Skia 的 strike 缓存，别再引一套 `GlyphCache` 回来。
2. **断行算法**：贪心 + 可断点回退，横竖排共用；表格格内断行。
3. **表格几何**：跨度→网格、行高结算、跨页片段、格线一条边只画一次。
4. **控件边界四条删除规则**与整格/整表删除的语义 —— 它们是产品行为，不是实现细节。
5. **Skia 的调用面**（`bitmap_skia.cpp`）：hinting 取 `kSlight` 而非 `kNone`、开亚像素定位、
   灰度抗锯齿而非 LCD 子像素、侧倒竖排的旋转、typeface 与字体表跨位图共享。
   这些是"今天的像素长这样"的全部原因；换渲染层时照抄，不要按常规重设一遍默认值。

以及那套判据态度：先有可证伪的数，再谈优化。

## 八、为什么不做另外两条路

- **换成现成的模型层**（ProseMirror 式的 JS 模型）：模型不是难点，排版才是；
  跨段控件、竖排、分页、逐像素判据都绑在 C++ 排版核上，换模型等于把最值钱的部分交出去。
- **只做渐进的局部重构**（就是现在这条路）：能减少重复，但"撤销整篇""中段打字退化"
  "宿主持有第二份文档"这三条最贵的性质不会消失 —— 它们由"可变 + 事后推导"这个形状决定，
  不换形状就只能一直打补丁。

## 九、性能：旧优化去哪了

先给结论：**只有一处会真退（整页光栅），而且可以避免；其余要么原样保留，要么被新结构取代得更彻底。**
旧优化分三类：留下的、被取代的、本来就是补丁该删的。

★ 口径说明（同日晚补）：本节写作时两侧还各有一套光栅器，当晚自写扫描线后端删除，
native 与 wasm 都链接 Skia。这不影响下面两个关键数字 —— 3.5 ms 与 8~9 ms 一直是在
浏览器探针（wasm + Skia + SIMD）上量的，自写后端只在 native 跑过，从没进过这组数字。
它影响的是判据归属：现在只剩一条像素路径，"跨后端对照"这条防线不存在了，
逐像素判据的适用面收窄成"同一构建内"，线上仍以浏览器探针为准。
另有一处对自己有利的修正：8~9 ms 里含一次帧内搬运（当时量到 5.9~7.0 ms），
新结构直接往页位图里画，这笔开销自然消失 —— 所以"整页重画"的实际退步会小于 3.5 → 9 这个差。

### 9.1 三类归宿

| 旧优化 | 新设计里的归宿 | 结果 |
| --- | --- | --- |
| 逐页画布 + 浏览器合成器搬像素（滚动零引擎开销） | 这就是 D5 | 原样保留 |
| 视口门闩、窗口滞回、滚动提前量 | 宿主侧逻辑，与引擎无关 | 原样保留 |
| 每份状态回推 text0 / controls JSON | IDL 按需查询，不随每次编辑回推 | 更强（消息更小） |
| 帧按页号分槽、两套槽号、平移复用、`frameOffsetOfPage` | 帧不存在 | 删除（它们只是"单帧"的补丁） |
| 页指纹 / 行指纹 / 行带差分 | 页哈希 / 行哈希，挪进光栅器内部 | 等价，少两本账 |
| 选区新旧矩形差集 | 覆盖层按 (selection, caret) 值缓存 | 等价，页内 O(行数) |
| 增量编译（单段 / 分段）、`BlockSource` | 块哈希记忆化 | 保留，并顺带干掉流索引、块流拷贝、控件导出三趟 |
| 后缀复用 / 前缀续排 / `shiftSuffixBlockAxis` | 断行块局部 + 分页前缀和 | 更强：页号不写进元素，平移是 O(log n) 索引更新 |
| 空转 present 0.1 ms（行/字形二分） | 页表直接给块的区间 | 更强：不需要二分 |
| `glyphRangeOnPage` 二分 | 页表就是索引 | 删除 |
| Skia / SIMD / 字形缓存 / 预热 | 不变 | 原样保留 |
| 自写扫描线光栅器（native 侧的"第二把尺子"） | 已删除，两侧共用 `bitmap_skia.cpp` | 它不是优化，是第二条像素路径；跨后端比较不给判据，只给两份要对齐的像素账 |
| 表格"一律不做增量" | 分页状态闭合 | 消失：表格也走同一条增量路 |

### 9.2 唯一会退的一处

**整页光栅。** 今天打字走行带差分，paint 中位 3.5 ms；整页满字是 8~9 ms（两者都是实测，
口径见 9.1 的追记）。如果 D5 的 `rasterPage` 每次从零画一页，打字就从 3.5 ms 变成 9 ms ——
这是真退步。8~9 ms 里那笔帧内搬运在新结构里没有了，实际差距会小一些；但"每次从零画"
这条性质本身不能留。

对策不是"以后优化"，而是**接口在第一天就定成两层**：

```cpp
// 对外：页是单位，宿主只认这个
Bitmap rasterPage(page_id, style, zoom);
// 对内：光栅器自己持一张页位图 + 每条行带的哈希，命中就不重画
void   rasterPageIncremental(PageBitmap*, const Page&, const Style&);
```

行带缓存的键是行哈希，随页对象一起丢；它不参与任何"引擎状态"，也不需要失效通知。
这条与今天的行指纹是同一种东西，只是所有权从引擎挪进了光栅器。

### 9.3 打字成本对照（2000 段，同口径：排版 + 光栅）

| 步骤 | 今天 | 新设计 | 说明 |
| --- | --- | --- | --- |
| 改树 | 就地改 + 事务 | 路径复制 ~10 个节点 | 今天另有 `blocks_` 整份深拷贝，新设计没有 |
| 编译 / 投影 | 单段 0.1 ms（整树 8.5 ms） | 1 块按哈希 ~0.05 ms | 其余块共享 |
| 流索引 / 块起点 | 1.7 ms（3000 段实测） | 0 | 投影时顺带产出 |
| 块流副本 | 整份深拷贝 | 0 | 不存在 |
| 控件导出 | 全表 + normalize | 只重算改动块 | — |
| 排版 | 续排到末尾（表单文档退化到最后一段） | 1 块 + 分页 O(log n) | — |
| 光栅 | 行带增量（未单独量；整页满字 8~9 ms） | 同左 | 依赖 9.2 的行带缓存 |
| 覆盖层 | 差集 | 页内 O(行数) | — |
| **合计** | **2.4 ms（实测）** | **1.5~3 ms（估计）** | 最坏情况差距更大：中段打字、撤销 |

撤销是这套设计收益最大的一处：今天整篇重编 + 整篇重排，新设计与刚才那次编辑同价。

### 9.4 怎么保证以后优化不再变补丁

把性能写成**结构判据**，而不是只写时间阈值。时间有噪声，调用计数没有。

| 场景 | 判据（每次操作） | 量法 |
| --- | --- | --- |
| 页内打字 | 投影重算块数 = 1；断行重算块数 = 1；分页更新 O(log n)；行带命中 ≥ 90% | 计数器 |
| 撤销 / 重做 | 重算块数 = 最近一次编辑的块数；耗时 ≤ 2× 那次编辑 | 计数器 + 计时 |
| 滚动 | 投影 0 次、断行 0 次；只允许光栅"新进窗口且未缓存"的页 | 计数器 |
| 插入一页 | 重光栅页数 = 1；其余页只改位置，不重光栅 | 计数器 |
| 每次按键 | 堆分配 ≤ 100 次、≤ 200 KB | 自定义分配器计数 |
| 内存 | 200 个修订 ≤ 文档大小 × 3；页缓存 ≤ 8 页 | 采样 |

再加两条老纪律：基准一律在 wasm 上量；语料固定四种（长文、表单、表格、竖排），
p50 与 p90 都记。判据红了就当场改，不记基线 —— 这条本来就是 `lint_comments` 那条教训。

### 9.5 为什么这次不会再长出一堆补丁

补丁的成因是**缺结构**，不是缺优化：

- 帧槽补的是"只有一个可变帧"；
- 后缀复用补的是"页号写在每个元素里"；
- 对象表扫描补的是"筛选靠整份拷贝"；
- 撤销整篇补的是"事务不记改了哪儿"。

这四样在新设计里都没有落点：没有帧、没有元素内的页号、没有筛选副本、没有"事后推导变更"。
剩下的优化只有两种形态：**改缓存键**（例如把行哈希换成段哈希）或**改算法**（例如断行策略），
两者都是局部的、可测的，不需要在驱动层加条件。

一句话：旧优化里真正值钱的是算法与光栅（Skia、整形缓存、断行、表格几何），
它们一行都不用改；被删掉的是围绕"可变状态"长出来的调度技巧，那些本来就不该存在。

### 10.1 变更定位：为什么是内容哈希，不是 diff 算法

"找出改了什么"混着三个不同的问题，混在一起就会想用同一个办法解决：

| 问题 | 谁回答 | 代价 |
| --- | --- | --- |
| 这次编辑**碰过**哪些节点 | 路径复制（没碰到的还是同一个指针） | 0，编辑时顺手就有 |
| 哪些块的**渲染输入**真的变了 | 内容哈希 + Merkle 下降 | O(改动的块 × 深度) |
| 怎样把旧列表**变成**新列表 | keyed list diff（Vue / React 那一套） | O(n)，还要算最长递增子序列 |

要的是前两个，第三个不需要。Vue / React 必须解第三个，是因为三条前提在那里都成立：
就地改 DOM、子树比较要遍历、列表元素没有稳定身份（所以才要 key）。这三条在这里恰好全不成立 ——
换修订是整棵换（旧修订还活着，撤销就是换回去）、结构共享下"子树相等"就是指针相等（一次比较，
不是遍历）、孩子有稳定身份 `NodeId`（`key` 的问题在更低一层就没有了）。

所以哈希不是 diff 的替代品，**它是 diff 的剪枝器**：根哈希相同就整棵跳过，"整篇没变"是 O(1)
的判定；不同才下钻哈希不同的孩子。这就是 git 的树 diff，只是连"操作序列"都不算。
真需要补丁形态（协作、增量保存、跨进程传）时，就在哈希判出不同的那棵子树里跑 keyed 对齐 ——
那时 `NodeId` 就是 key。两者是分层，不是二选一。

★ 现状要说清：`blockHashes` 还是整篇走一趟（`full_` 只省掉文本与对象表的物化），
`diffBlocks` 是掐头去尾的 O(n) 比较。**现在拿到的是正确性，不是局部性。** 下一步的
`damage(before, after)` 要按哈希下降走，"改动的块 × 深度"那个代价才真正落下来。

★ **一个必须在表格落地前定下的粒度缺口**：块哈希只覆盖"贡献这一块的节点"。表格的列宽是
容器级属性 —— 改一格的内容可能撑宽列，整张表的行高与分页随之全变，而兄弟格的块哈希一个都
不动 ⇒ **漏报**，症状与缓存 bug 一模一样（改了不动，且只在大表格上偶发）。所以损伤集合的
定义是"内容损伤 ∪ 容器几何损伤"：容器节点的哈希变了，它下面所有块都算损伤。判据现在就能写
（表格接通后立刻验）：把一格里的文字改长到撑宽列，整张表的块必须全在损伤区间内。

### 10.2 损伤定位落地：下降式比较，以及它的实情

`rev::damage(before, after)` 落的是 10.1 说的下降式比较，判据在 `rev_layer` 的 [11] 一节
（71 项里占 15 项）：

- **同一份修订**：`visited == 1`，块数不变 —— "整篇没变"确实是 O(1)。
- **段内改字**（块数不变）：区间与 `diffBlocks` 逐字段一致；300 步随机编辑零不一致。
  这是"不许漏、也不许白报"的差分判据 —— 快路与慢路必须同答，而不是各自看着合理。
- **合并两段**：只报合并后的那一块，与 `diffBlocks` 恰好一致（后缀对齐吸收了挪位）。
- **分段**：报两块。第 0 块是新的空段；第 1 块与旧第 0 块内容相同，只是节点被重建
  （`splitPara` 在 cp=0 时丢掉原 run、另建一个同内容的）。多报的那一块重排时命中块缓存。
  没有为它加"按哈希跨位配对"的启发式：收益只有一次缓存查询，而失效方式
  ——把两个真变化的节点当成同一份内容——是静默的。
- **`visited` 与段落文字量无关**：400 段每段 1 字与每段 200 字，visited 完全相同。

一处必须说清的实情：**visited = 802，等于全部节点数。** 孩子表是 `vector`，要确定"哪个孩子
变了"就必须扫一遍孩子 —— 单节 400 段就是 800 个孩子。所以当前拿到的是 **"不做物化"**
（0.006~0.018 ms 对 0.20 ms，快 12~32 倍，200 次平均、单机实测），**不是"与段数无关"**。
真正的 O(改动的块 × 深度) 要等孩子表分块（每块 32 个、带聚合哈希，一层降到 O(孩子数/32)，
逐层递推即 O(log)）；那一步只改 `DamageWalker` 的下降方式，调用方与判据都不用动。
`scanned` 这个计数就是给那一步留的判据。

顺带一处：`paras` 成了构造时算好的顺序统计量（删掉了 `marksIn` 的递归）。`paraCount` 由
"每次调用遍历全篇"变成 O(1)，而 `locate` 在循环里调它 —— 定位一段的代价从
O(段数 × 每段节点数) 掉到 O(段数)。这条不属于本次重构的目标，是写 `damage` 时顺手看见的。

### 10.3 控件内部的编辑：位置只有一种，层级只是路径

`locate` 给出的不再是"顶层的第几个孩子"，而是**从正文那一节往下走到落点所在那一层孩子表**的
下标链；`SiteKind` 只剩 `InRun` 与 `BeforeChild` 两种。**"在容器内部"不再是一种落点**，
只是 path 更长。于是四个原语（`insertText` / `eraseText` / `splitPara` / `mergePara`）与
`insertControl` 各只剩一条路：取到那一层的孩子表、改、沿路径换回去。

判据在 `rev_layer` [12]（19 项，总数 71 → 90）：

- 控件内部打字：字落在控件里（`前ab` → `前aXb`）、不切段、控件还在；
- 控件之前那一枚 run 仍是同一个指针 —— 容器之外的节点一个都没复制；
- 控件内部打字之后，投影与 `compileDocument` 逐字段相同；
- 控件内部回车：段落标记落进控件，控件因此跨段；`ControlSpan` 起在第 0 块、止在第 1 块，
  两块各自的行内对象与编译逐字段相同；
- 控件内分段之后 `damage` 覆盖两块；越界仍被拒且带原因。

这条改法一次消掉三处专属分支：`SiteKind::Nested`、`"位置在容器内部，编辑尚未实现"`、
`markOf` 的 nested 出参。旧模型里"段落在容器内"要另走一段代码，而那段代码踩过"退格把前面
九个字与所有控件整批抹掉"（浏览器探针 14.10 / 14.11）；这里没有第二段代码可走。

★ 一处必须记住的实现细节：路径既是递归栈也是结果 —— 成功时栈里留着整条链、失败时逐层弹。
第一版把结果写进 `Site` 的成员、栈用同一个对象（`out->path = *path`），成功那一步成了
**自赋值**：MSVC 的 `vector` 先释放再拷，落点于是退回顶层 —— 文字跑到控件外面，而"字进去了"
"控件还在""不切段"这些断言看着全都讲得通，只有内容比对能抓到。栈与结果要么是两个对象，
要么干脆不分开（现在是后者）。

### 10.4 落盘：只存形状与身份，往返判据看哈希

`rev::serialize` / `rev::deserialize`（`src/core/rev/serialize.*`）只写形状与身份：节点号、
种类、隐藏标记、载荷、孩子、分配器水位。哈希与段落数**不写**，重建时由孩子重算。

于是往返的判据不是"文本相同"，而是**重算出来的全文哈希相同**。它比逐字段比对强，因为它与
"哪些字段算内容"用的是同一份定义：任何参与哈希的字段没写出去，读回来哈希就变。身份不在哈希
里（哈希表达内容，身份表达跨修订的同一性），所以节点号与水位单独断言。

判据本身要能失败，验过两次：临时删掉 `validateRef` 的写出，[13] 报"字段没落盘：validateRef"；
临时删掉字符属性里 `italic` 的写出，哈希断言与逐项断言同时红。恢复后 `rev_layer` 116 项全绿。

记录级的编码抽成 `src/core/doc/record_json.*`，模型层与修订层共用：字符属性、段落覆盖、
外观、控件这四类记录的"字段名到 JSON"只有一份映射。不抽的后果不是重复代码，而是**分叉**：
控件那 29 个字段的映射若各写一份，加字段时只改一处，另一处读回来静默是默认值 ——
与 97 条同族（"改了它却没落盘"）。

读端的严格程度按"会不会静默做错事"定，不按"能不能读出来"定：

- 版本号不符、种类名不认识、节点号重复、水位不大于最大节点号、样式引用下标越界：拒绝。
- 种类与载荷不符（文本节点带段落覆盖）：拒绝。读成"文本节点加一份被忽略的段落覆盖"看起来
  正常，下一次编辑就会对它做错事。
- 根必须是 Document、其下正好一节：拒绝。`bodyOf` 与 `withLeafChildren` 只认第一节，
  多出来的那一节会被静默忽略。
- 失败时目标一个字节都不动：先在临时对象里建好，成功才交付。
- 嵌套深度上限 128：深度由文件决定，不能交给调用栈。

### 10.5 表格：容器几何是第二类内容

表格进载荷时遇到的第一件事不是"怎么编"，而是"改了列宽该重排什么"。块的内容一个字都没变，
但同一张表里每一行的行高、每一格的可排宽度都变了。TRAPS 97 把这件事写成：

1. **块哈希里要有外层容器的几何**。投影维护一条容器栈（表格、行、格），每个块的哈希并进
   栈里每一层的自身哈希，以及自己的格路径。少了这一段，改列宽后每块都会命中排版缓存 ——
   损伤报得再准也没用，画面停在旧列宽上。
2. **损伤里要有"容器自己的记录变了"这一条**。损伤定位按哈希下降，过去只在"两边都不含段落
   标记"的叶子上记一笔。容器改了自身属性时孩子哈希全相同，下降会在没有一处记账的情况下
   结束，于是报"没有损伤"。现在先比自身哈希（`hashSelf`，种类 + 隐藏 + 载荷，不含孩子）：
   变了就把它覆盖的块整段算损伤。

两条判据各自可证伪，都实测过：去掉块哈希里的容器栈 → "表内五块的哈希全变"红；
去掉自身哈希那一条 → "改列宽的损伤是整张表"红。

范围按容器层级落，不是一律"整张表"：改列宽影响整张表（每格的可用宽度都变），改某一行的
行高只影响那一行（三块）。判据分别钉在 `[1,6)` 与 `[1,4)`。

载荷没有做成"表格里再套行/格"：三种节点各带自己的记录（`TableSpec` / `RowSpec` /
`CellSpec`），种类到载荷的对应是一张查表。多一层包装只会让哈希与落盘都再分一次支。

投影与编译的等价判据扩到表格：同一份表分别经 `makeTableTree` 与 `makeTableDoc` 构造，
`BlockSpec` 逐字段相同（格路径里的表格句柄归一后）、`LayoutTable` 逐字段相同（列宽、行高
规则、每格的块区间）。网格推导抽成 `buildGridFromSpans`（模型层与投影层共用一份规则），
长度与对齐的映射并进 `format_map` —— 这两处原本各有一份，接表格时正好合掉。

★ 一处只有"格内编辑"才会暴露的错：`locate` 里 `off` 是"段内已累积的码点数"，对行内容器
（控件）成立，对块级容器（表格、行、格）不成立 —— 格里的段落是另一段，`off` 该从 0 起。
第一版按行内容器处理，第二格里的落点永远偏出两格文字。现已按 `isBlockContainer` 分开：
块级容器只认"这一段在它里面"，没有"在该段 cp 处进入它"这种落点。

### 10.6 原子、域与迁移路径：一条算法，两个模型

图片与公式进载荷时，真正的问题不是"多两支 variant"，而是**盒子几何算几遍**。它要按
"给了绝对宽 / 只给一边 / 两边都没给但给了像素 / 两边都没给且没像素"四条岔路走，其中两条
还要按原图比例推另一边。两条路各写一份，第一次在某个岔路上分叉时，表现是"同一份文档在
投影里比编译里高出一截"——画面上看不出来，只有逐字段比较才抓得住。

所以抽成 `src/core/doc/atom_map.*`：

- `atomContentHash`：图片看资源标识、公式看表达式与后端。尺寸不在里面 —— 尺寸改了行盒几何
  自己会变，它管的是几何看不见的那一类（换了一张同样大的图）。
- `resolveAtomBox`：输入是一份与模型无关的 `AtomGeometry`（宽高、像素、DPI、表达式码点数），
  输出盒子的磅值与两个"作者给的是相对长度"的标记。**诊断归调用方记**：几何只有一份，日志
  各记各的节点号，句子共用 `atomRelativeDiag`。
- 盒子在落段时才算：公式的默认框按段落字号估，而字号是段落属性，走到原子那一刻还看不到它。
  两条路都是先记"这里有一枚原子"，落段时补齐 —— 投影为此维护一份 `(对象下标, 输入)` 的
  待定表。

域进载荷只多一件事：`FieldSpec::cache` 是求值结果，**不进内容哈希**。把派生值算进内容哈希，
"同一份文档求值前后"就会得到两个哈希，撤销回到旧修订时对不上，而内容一个字都没改。它照样
落盘（重新打开时先显示已有的值），往返判据因此对域另做一份逐字段比对 —— 哈希在这个字段上
是刻意失明的。

迁移路径是 `rev::fromTree(const NodeTree&, Doc*, std::string*)`：节点号原样带过去（身份跨
模型同源），载荷按种类一一对应，`hidden` 与分配器水位一起带。**表示不了的形状直接拒绝并说明
原因**，不做"能搬多少搬多少"：搬一半的结果是一份看起来完整的修订，而调用方没有别的办法知道
它不是同一份文档。本切片拒绝多节（节的记录还没进载荷）。

判据（`rev_layer` [15]–[17]，141 → 194）都是用 `fromTree` 搭的桥：

- 原子的四种盒子形状逐一对值（150×75 pt、只给宽的 30 pt、只给高按 2:1 推成 40 pt、相对宽度
  折算并记诊断），并与编译产物逐字段相同；
- 换一张同样大的图（资源标识变、尺寸不变）只动那一块的哈希；
- 只改域的缓存值，全文哈希与块哈希一个都不变；
- 六条原子记录逐字段落盘往返（图片 4 / 公式 1 / 域 1）；
- 嵌套表格：两张结构表、格路径两层、块区间按嵌套算；改内层列宽只损伤内层两块，改外层列宽
  损伤整张外表格 —— 两种范围由容器层级定，不是一律整表；
- 跨段控件：一对边界落在两块上，两块的文字各自算进自己的段，控件跨度跨两块；呈现态隐藏后
  它的段落标记也一起走，两段并成一段。

一条自证的判据：`fromTree` 的等价判据能红。把投影层原子盒子的宽高对调，[15] 的"每一块与
编译产物逐字段相同"与三条盒子值断言同时红；而 `blockDiff` 当时只报"只有 owner 不同" ——
判据的报错信息本身也是判据的一部分，已补上宽高、原子种类与内容指纹四项。
