# 代码审查与架构评估

> 审查对象：HEditor 全仓（`src/` `demo/` `tests/` `web/` 与两份设计文档）。
> 审查角度：文档模型设计、代码实现质量、模块拆分、数据一致性与不同步风险、底层架构合理性。
> 方法：静态阅读 + 结构体尺寸实测（MSVC x64 / C++20）+ 与四个成熟编辑器的公开架构资料比对。
> 本文只记录审查结论与建议，不改动任何代码。
>
> 结论摘要：**模型层的设计水准明显高于同类自研项目**（可逆步骤、不变量含反向判据、
> 作者意图/运行时状态分离、区间端点外扩，这几条与 ProseMirror / CKEditor 5 的主流做法同向）。
> 问题集中在三处：**坐标系有三套**、**`Node` 是"所有种类载荷并集"的胖结构体（实测 1496 字节）**、
> **模型层与引擎层之间没有接缝（ControlApi / 序列化 / 撤销都没接到引擎，宿主也拿不到文档）**。
> 数据不同步风险的最主要来源不是编辑器内部，而是"同一份文档在进程里有三份表示、且只有一份能被写出去"。

## 二、总体结论

**做对了的部分**（值得保留，不要在后继重构中丢掉）：

1. **文档模型与排版引擎解耦，只有一处接缝**（`compile.cpp`）。这是全仓最有价值的架构决定：
   模型换过一轮、控件从"区间标注"换成"跨度容器"，引擎的整形/断行/分页/增量一行没改。
2. **可逆步骤 + 位置映射 + `assoc`**。形状与 ProseMirror 的 `Step` / `StepMap` / `Mapping`
   同构，与 CKEditor 5 的"所有结构改动都走 operation，一批 operation 是一个撤销单位"同向。
3. **不变量检查器要求"判据必须含反向一半"**（构造反例必须报出对应规则）。
   这一条比多数开源编辑器项目做得严格 —— 它把"永远全绿"这种伪成功在结构上排除了。
4. **作者意图落盘 / 运行时状态不落盘**这条判据统一了 `hidden`、`placeholder`、`validationState`
   等一批字段的归属，省掉了逐个争论。
5. **区间端点落在不可半分单位内部时向外扩到整块边界**，从而"复制出来的片段永远良构"。
   ProseMirror 走的是"拆开节点再取 slice"，本项目不能拆（拆了容器边界不成对）所以改成外扩，
   理由记录充分。

**主要问题**（按影响排序）：

| 编号 | 问题 | 影响 |
|---|---|---|
| P1 | 同一份文档在进程里有三份表示（宿主块流、引擎树、引擎块流），且没有"把树拿出来/写出去"的入口 | 无法持久化；宿主重建走有损路径；"底稿过期"是结构性问题而非偶发缺陷 |
| P2 | `ControlApi` / 序列化 / 撤销 / 值回填都只连到模型层，**没有连到引擎** | 表单回填（产品核心需求）在 wasm 上不可达；批量设值不会触发重排 |
| P3 | `Node` 是所有种类载荷的并集，实测 1496 字节/节点，且逐节点堆分配 | 内存与缓存局部性代价，与 Lexical"每类节点只带自己字段"相反 |
| P4 | 坐标系三套（`Pos` / `FlowPos` / 引擎 `(段, 码点偏移) + 侧别`） | 被自身文档称作"唯一的结构性风险"；`TRAPS.md` 里"光标与边界"一节整节都在描述它的后果 |
| P5 | 每次按键整篇重编译 + 块流整份拷贝 + 派生索引整体重建 | 增量排版的投资被上游全量开销稀释；是当前最可能的性能瓶颈 |
| P6 | 双路并存（`setBlocks` 旧路 / `setDocument` 树路）渗透进引擎内部（`blocks_` 与 `blocks_full_` 语义随模式变、`controls_` 权威或派生随模式变） | 读代码时必须先判模式；新加一处分叉就是一个静默不一致（★ 2026-10-13 **已消除**：旧路径退役，树是唯一入口） |

## 三、文档模型设计评估

### 3.1 与成熟项目的对照

| 维度 | 本项目 | ProseMirror | CKEditor 5 | Lexical | CodeMirror 6 |
|---|---|---|---|---|---|
| 文档真相 | 可变的树 + 一批派生缓存 | 不可变 `doc`，位置是整数 | 可变 model + view 双向转换 | 不可变 `EditorState`（树+选区） | 不可变 `EditorState`（rope+选区） |
| 选区归属 | 会话状态，不进文档 ✔ | 在 `EditorState` ✔ | 在 document 上 | 在 `EditorState` ✔ | 在 `EditorState` ✔ |
| 位置模型 | `Pos{节点,槽位}` + 流位置 + 引擎坐标（三套） | 单套整数位置，`ResolvedPos` 解析出路径 | 单套位置（path + offset） | `(nodeKey, offset)` | 单套整数偏移 |
| 编辑单位 | `Step` + 逆操作 + `mapPos(assoc)` | `Step` + `StepMap` + `Mapping` | operation + batch | update + node key 失效 | `ChangeSet` / `ChangeDesc` |
| 字符样式 | 三态 `CharFormat` 挂在 run 节点上 | marks 区间 | **文本属性**（不是元素） | 节点字段 | 不适用 |
| 节点载荷 | 所有种类字段的并集（1496 B） | `type` + 小 `attrs` | 元素属性 + 文本属性分离 | 每个子类只带自己的字段 | 不适用 |

对照结论：**"选区不进文档""步骤可逆""一批一个撤销单位"三条与主流一致且实现正确；
位置模型与节点载荷这两条偏离主流**，而它们恰好是本项目缺陷密度的两个中心。

### 3.2 P4：坐标系三套

同一份文档上有三套坐标：

1. `Pos{container, offset}`（`flow.h`）—— 节点级；
2. `FlowPos`（整数，深度优先展开）—— 段级；
3. 引擎的 `(para, cp_offset)` + `caret_side_` —— 光标与排版级。

文档自己写"两套坐标必须双向互逆，这是本方案唯一的结构性风险"（模型文档第四节）。
`memory/TRAPS.md` 的"光标与边界"一节（第 23、24 条）整节都在描述第三套坐标与第二套的换算
在边界上的后果：方向键一次跨一枚簇、点击量到的是侧别、`setCaretRaw` 必须清侧别、
侧别要在重排之后写。

**成熟项目怎么避免**：ProseMirror 只有一个位置空间（文档里的整数），"在哪个节点内、
第几个孩子"由 `doc.resolve(pos)` 现算，因此不存在"两套坐标互逆"这个问题域；
CKEditor 5 的位置同样是单套 path + offset。

**建议（不必推翻现有设计）**：明确"唯一权威坐标"这一条纪律并写进编译器/类型层面 ——
把 `FlowPos` 做成不可从 `int` 隐式构造的强类型（`struct FlowPos{int v;}`），
把引擎坐标的入口收敛到 `FlowPos` 上（现在是双向的 `flowPosAt` / `flowToTextPos`）。
目的不是省代码，而是让"拿 `int` 直接当另一套坐标用"变成编译错误而不是运行期落偏一个字。
这属于"消除一整类缺陷"的抽象，符合 AGENTS.md 里"稳定一条边界"才引入抽象的口径。

### 3.3 P3：`Node` 是并集结构体

`node.h` 的 `Node` 把 `para` / `marks` / `control` / `cell` / `table` / `field` / `section`
全部内联，注释理由是"编译要按流顺序取它，而流顺序就是树的顺序"。这条理由成立，
但代价实测如下（MSVC x64）：

- `Node` = **1496 字节**；
- 其中只对极少数节点有意义的部分：`control` 560 + `section` 472 + `para` 160
  + `field` 72 + `table` 56 + `cell` 8 ≈ **1328 字节，占 89%**；
- 真正每个节点都用的部分（`id`/`kind`/`parent`/`children`/`text`/`hidden`）
  只有约 100 字节。

`NodeTree` 用 `std::vector<std::unique_ptr<Node>>` 持节点，所以每个节点是一次独立的
堆分配：1000 个节点的文档光节点头就是约 1.5 MB 外加约 1000 次分配与对应指针追逐。
`TextRun` 均摊只承载十几个码点。

**成熟项目怎么避免**：Lexical 把每种节点做成 `TextNode` / `ParagraphNode` / `LinkNode`
各自的子类，字段只带自己的；CKEditor 5 明确把字符样式做成**文本属性而不是元素**，
官方理由就写着"这样显著降低模型算法的复杂度"。

**建议**：按"节点种类"分槽，而不是全并集。三种可选形态，代价递增：

1. 最小改动：把 `control` / `section` / `table` / `field` 改成
   `std::unique_ptr<...>`，只在对应种类上分配（`TextRun` 立刻从 1496 降到约 300 字节）；
2. 中期：`Node` 只留公共头 + 一个 `std::variant<std::monostate, ParaPayload, ControlPayload, …>`；
3. 若将来要跑大文档（几万节点），再考虑把 `TextRun` 的文本改成 rope/slice 引用。

第 1 条与现有"编译按流顺序取字段"的用法完全兼容（把 `n.control.x` 改成 `n.control->x`），
是性价比最高的一档。

### 3.4 P3b：`ParaFormatPatch::operator==` 被静默删除

`WritingMode` 没有 `operator==`，于是 `std::optional<WritingMode>` 的默认相等被隐式删除，
`ParaFormatPatch` 的 `operator== = default` 随之被删除，进而 `StyleDef::operator==` 也被删除。
`TRAPS.md` 第 6 条已记录过这个坑，但仍值得指出：**现在这三处比较算子处于"写了但不可用"
的状态**，任何将来调用都是编译错误（MSVC 静默、clang 告警），排查成本高。
建议给 `WritingMode` 补一个显式的 `operator==`（三个分量逐字段比），
而不是让每个含它的结构各自回避。

## 四、模块拆分评估

### 4.1 现状

目录划分本身是合理的，与路线图 4.7 的约定一致：
`core/doc`（模型）、`core/layout`（排版）、`core/render`（光栅）、`core/text`（整形）、
`core/engine`（调度与门面）、`core/utils`（纯工具）。

问题在"文件内部"与"双路并存"两处。

### 4.2 `EditorEngine` 仍是一个巨型类

`engine.h` 里公开方法 **136 个**、私有成员 **约 86 个**，`engine.cpp` 1780 行，
另有 `engine_layout.cpp` 556、`engine_paint.cpp` 511、`engine_audit.cpp` 252、
`engine_diag.cpp` 188 —— 已经做过"只拆文件不拆类"的一轮（路线图 4.7 有记录）。

86 个私有成员里，**至少有 15 个是同一份文档的派生缓存**：

```
blocks_  blocks_full_  control_node_ids_  owner_index_  flow_  block_flow_
block_flow_span_  block_src_  layout_  shaping_cache_  controls_  undo_
page_fp_new_  page_fp_in_base_  layout_dirty_from_  para_count_changed_  ...
```

这属于 AGENTS.md 说的"已经没法一眼说出这个文件负责什么"。
路线图把拆类的时机定为"接口的输入形状定下来之后"，这个判断是对的；
建议先把"派生状态"整块提取成一个 `DerivedDocument`（树 → 块流 / 流索引 / 控件集合 /
来源身份一次算完，只读），引擎只持有它 + 排版结果 + 光栅账。这样：

- 每一处"重建派生量"只剩一个入口（现在是 `rebuildFromTree` + `exportControlsFromBlocks`
  + `syncInlineObjects` 三处，且有明确的次序依赖）；
- `objectsFor` / `block_flow_` / `block_src_` 这类"随模式变语义"的成员被收进一个对象，
  调用方不再需要先判 `tree_valid_`。

### 4.3 双路并存渗透到成员语义

> ★ 2026-10-13 **本节结论已消除**（保留原文作为快照）：旧路径退役后引擎只剩树一条路，
> `tree_valid_` 换成 `loaded_`（只区分"装载过没有"），`blocks_full_` 只有"未筛选的原件"一种角色。
> 退役过程见 `memory/MIGRATION.md` "旧路径退役"一节。

现在同一个成员有两种相反的角色：

| 成员 | `setBlocks` 旧路 | `setDocument` 树路 |
|---|---|---|
| `blocks_` | 调用方拼好的输入，权威 | 编译产物，且与 `blocks_full_` **内容相同**（整份拷贝） |
| `blocks_full_` | 空（`objectsFor` 要绕开它） | 未筛选的原件 |
| `controls_` | 权威（宿主给的） | 派生（从产物边界导出） |
| `owner_index_` | 空 → owner 即下标 | 有 → owner 是节点 id |
| `undo_` | 空 | 有 |

这套"按模式切换语义"的写法在每一处访问点上都要正确判断，`objectsFor` 与 `policyAt` 是
两个收口点，但收口是纪律而非结构。建议在 `DerivedDocument` 落地时顺手把旧路标记为
`IsLegacySource` 的一个显式状态（而不是散落的 `tree_valid_` 判断），
并按路线图尽快收掉旧路剩下的两个调用方（`addControl` 的跨段分支与单测的手工对照）。

### 4.4 测试是两个巨型翻译单元

`edit_test.cpp` 6242 行（6 个顶层函数，其余全在 `main` 里顺序断言）、
`model_test.cpp` 5969 行（89 个函数，但仍是同一个 TU）。
这与 AGENTS.md"不要出现巨长的文件"直接冲突，实际代价：

- 单 TU 无法并行、编译时间长；
- 一个断言失败后面全部不跑（崩溃时更甚，已用 `_IONBF` 缓解）；
- 几百项断言放在一个 `main` 里，定位靠阅读而非测试名。

建议按"节"拆成多个 TU + 一个注册表（路线图阶段 8 已经写了"测试骨架换成可注册可分片"），
先做机械拆分即可，断言一条不改。

### 4.5 宿主门面是"每个入口手写一次"

`wasm_main.cpp` 864 行、56 个导出、全局可变状态（`g_engine` / `g_blocks` / `g_fields` / `g_cfg`），
每个函数自己拼 JSON 字符串（`statsJson` / `editStatsJson` / `controlsJson` / `caretReport` …）。
路线图阶段 8 要的是"版本化 API / JSON 协议"的门面层，现在还没建。
这直接导致第五节 R1/R2 两个风险 —— 门面不是"薄转发"，而是"缺了一层"。

## 五、数据一致性与不同步风险清单

按严重程度排序。每条给出：现象、根因、影响、建议。

### R1（高）同一份文档有三份表示，且没有出口

```
宿主 (web/app.js + wasm_main.cpp)      g_blocks：块流副本，有损（不含 runs 的切分方式与 objects）
引擎 tree_：模型的唯一权威实例（setDocument 时 assignFrom 深拷贝）
引擎 blocks_ / blocks_full_：上一步的编译产物
```

- **没有"把树拿出来"的入口**：`wasm_main.cpp` 导出列表里没有 `documentTree`
  （C++ 侧有 `EditorEngine::documentTree()`，但没导出），于是宿主不可能持有模型树。
- **没有序列化入口**：`serializeDocument` / `deserializeDocument` 也没导出。
  即"保存 / 打开文档"这条产品必需链路在交付物（wasm）上**不可达**，
  1.10 判据全绿但只在 native 单测里跑。
- 宿主重建走 `rebuildDocument()` → `setDocument(demoTree(g_blocks, g_fields))`，
  而 `demoTree` 只读文本与块级字段，`runs` / `objects` 靠重新编译再生。
  这就是 `TRAPS.md` 第 21 条"宿主的底稿会过期"的**结构成因**：
  宿主手里必然是装载时那一份，只有靠 `syncBlocksFromEngine()` 手工刷新才不变旧。

**影响**：文档无法持久化；宿主侧任何"改完再重建"都可能把用户改动倒回去；
模型层的完整能力（样式、控件记录、节、修订）在宿主侧全部丢失。

**建议**：按路线图的层序，把"宿主门面 + 序列化"提到功能开发之前做完。
最小可用的形状是三条：`saveDocument() → string`、`loadDocument(string)`、
`documentJson()`（只读视图）。有了它，宿主就可以只持字符串 / JSON，不再持有第二份内存表示，
R1 与 R2 一起消失。

### R2（高）模型 API 与引擎之间没有接缝

实测 `ControlApi` 的构造只接 `NodeTree& / UndoStack& / ControlIndex&`，
全仓除测试与 `ChangeGate` 外无调用者；它**不持引擎引用、不触发重编译、不触发重排**。
`evaluateFields`、`RevisionLog`、`ControlIndex` 同样是"模型层自足、未接引擎"。

后果：

- `setValues` / `setValuesByKey`（回填，病历表单的核心动作）走完之后，
  引擎的 `blocks_` 仍是旧的 —— 除非调用方再调一次 `setDocument` 整篇重装。
- `1.5` 的判据"设 1000 个字段与设 1 个字段耗时同一量级"目前只证明了模型层，
  没有覆盖"改完之后上屏一次"这半段。
- `ControlSet controls_`（引擎侧区间控件）与 `ControlIndex`（模型侧 id/key 索引）
  是被同一份文档驱动的**两套控件表**，彼此不认识；隐藏控件在两者里的口径还相反
  （引擎在呈现态把它从流里摘除 → 导出时不出现；模型 `ControlIndex` 保留它，
  因为 `getValue` 对隐藏控件仍然有效）。两个口径各自都对，但没有一处契约写明它们的差异。

**建议**：把"改模型 → 重编译 → 标脏 → 重排 → 上屏"做成模型层与引擎之间**唯一的一条提交路径**，
让 `ControlApi` 的 `flush()` 与引擎的 `commitOnTree()` 汇到同一个函数
（现在 `UndoStack::commit` 由引擎的 `commitOnTree` 调用，而 `ControlApi` 自己直接调 `undo_.commit`）。
同时把"隐藏控件在两张表里的口径差异"写进模型文档，作为契约而不是待查项。

### R3（中）派生缓存的重建是"三次调用 + 次序依赖"

`rebuildFromTree()` 末尾 `exportControlsFromBlocks()`，而 `syncInlineObjects()`
在 `relayout()` 之前另外更新对象表；`markLayoutDirtyForBrackets()` / `markAllLayoutDirty()`
由若干入口分别调用。次序错了不会报错，只会"光标落偏一个字"（源码注释自己写了这句）。
这是典型的"派生状态分散在类里"的代价，解决方案见 4.2 的 `DerivedDocument`。

### R4（中）每次按键整篇重编译

`commitOnTree()` → `rebuildFromTree()`，而后者：

1. `compileDocument(tree_, …)` 走**整棵树**（含三层样式解析）；
2. `flow_.emplace(tree_, vis)` 全树重建流索引；
3. `blocks_ = blocks_full_`（**整份拷贝**：每块的 `cp_text` / `runs` / `objects` 都复制一遍）；
4. `exportControlsFromBlocks()` 扫全部块 + `controls_.normalize()` 排序。

也就是说：**排版侧精心做的增量（页指纹 + 段级续排 + 后缀复用），
被上游"每次编辑全量重编译 + 全量重建索引"抵消了一部分**。
文档记录的"敲一个字 1.96 ms，其中排版 0.16 ms"说明当时的瓶颈在别处（上屏），
但这条路径是随文档长度线性增长的，200 段场景下它会逐渐变成主要成本。

**建议**：先量化（在 `edit_test` 现有 24 段/200 段场景上分别量 `rebuildFromTree` 的耗时占比），
再决定是否做"编译产物的增量维护"。若要做，切入点很自然：`BlockSource` 已经给出每块的来源身份，
增删落在某一子树内时，只需重编那一段并平移后缀的 `block_flow_`（与排版的后缀复用同构）。

### R5（中）封装泄漏：`Node` 字段全公开 + 引擎暴露可变控件集合

- `NodeTree::find()` 返回非 const `Node*`，全仓 69 处 `Node* n = tree.find(...)`；
  其中 `steps.cpp` 直接写 `tree.find(x)->marks = …`。这是设计选择（"字段公开，封装留在树那层"），
  但它意味着任何调用方都能改结构相关字段而不通知派生索引 —— `hidden` 改一下就不改流位置了。
- `EditorEngine::controls()` 返回非 const `ControlSet&`，在树路下它是派生量：
  外部一改，下次 `rebuildFromTree` 就被覆盖（静默）。建议对树路只暴露 const 视图。

### R6（低）序列化缺口与"能存住"的承诺

`serialize.cpp` 覆盖了节点、节、页眉页脚片段、分配器水位；**没有**样式表（`StyleSheet`）、
资源表、修订日志。文档已把这三项列为待落地（"它们还没挂到 Document 上"），
但要注意第十节"完整保留、按需理解"这条承诺目前的兑现方式是"节点属性袋"——
而样式表是**顶层对象**，不在属性袋能覆盖的范围内。若 1.10 的往返判据只跑"节点内容"，
"打开再保存不损坏文档"这条对带样式的文档尚不成立。

### R7（低）光标侧别的状态冗余

`caret_side_` + `caret_side_at_` 这一对是"位置没变就认存着的侧别"的缓存，
`TRAPS.md` 第 23 条列了它的四个坑（含"位置变过又变回来会骗过位置相等这一条"）。
缓存是必要的（侧别无法从偏移唯一恢复），但可以把不变式收紧成一条可断言的规则：
`setCaretRaw` 是唯一的清除点，且 `caret_side_at_ == caret_` 之外一律视为失效。
建议把它写进 `checkInvariants` 或一条专门的单测，避免将来新增入口时漏清。

## 六、底层架构评估

### 6.1 分层与依赖方向

八层划分（文本/光栅/排版/模型/命令/模式/序列化/门面）方向正确，
依赖是单向的（`engine → doc → utils`，`doc → layout` 仅经 `compile.cpp` 一处）。
`utils` 里没有领域语义，`writing_mode.h` 放在 `text/` 而非 `utils/`，符合约定。

一个值得指出的反向依赖：`compile.h`（模型层）include `core/layout/layout.h`（排版层），
即"模型层唯一 include 引擎类型的地方"。这条边界被明确记录为唯一接缝，
**建议把它固化成编译期约束**（例如给 `layout.h` 里的 `BlockSpec` 加一个
"只许 compile.cpp 使用"的注释 + 头依赖守卫脚本里加一条检查），
否则后来人很容易在 `doc` 里顺手再 include 一次，接缝就从一个变成多个。

### 6.2 增量排版的可证伪判据

`auditFrame`（逐像素）与 `auditLayout`（逐字段）这两条"与全量一致"的判据，
以及"关掉字形缓存后逐字节等价"的开关，是本仓工程质量最高的部分，
也是路线图 2.4 里"参照项目没有而我们有的资产"。这部分不要动。

一个缺口：这两条判据覆盖的是**排版与光栅**，而 R4 指出的"编译 + 派生索引重建"没有对应判据
（没有"增量编译产物 == 全量编译产物"的对照，因为现在根本没有增量编译）。
若做 R4 的优化，判据应与 `auditLayout` 同形：增量产物的逐字段快照必须与整篇重编相同。

### 6.3 光栅双实现

`bitmap.cpp`（自写，native）+ `bitmap_skia.cpp`（wasm）双实现、以 Skia 为准，
这条纪律与"native 是第二把尺子"的定位一致，是合理的取舍。没有发现反向改 Skia 的地方。

## 七、更优实现方式汇总（供后续排期）

| # | 现状 | 建议改法 | 依据（成熟项目做法） |
|---|---|---|---|
| 1 | 三套坐标互逆 | 单一权威坐标 + 强类型包裹（`FlowPos` 不从 `int` 隐式构造），解析式取另一视图 | ProseMirror 只有一套整数位置，`resolve(pos)` 现算节点与偏移；CKEditor 5 位置是 path + offset |
| 2 | `Node` 是并集（1496 B） | 先把大载荷改成 `unique_ptr` 按需分配；再考虑 variant | Lexical 每类节点只带自己的字段；CKEditor 5 明确把字符样式做成文本属性而非元素 |
| 3 | 每次编辑全量重编译 | 有了 `BlockSource` 之后做段级增量编译，判据 = 增量产物与全量逐字段一致 | CodeMirror 6 的 rope 结构共享；Lexical 的双缓冲 + dirty 追踪只重算脏子树 |
| 4 | 门下无门面（宿主拿不到文档） | 先建门面三条：save / load / documentJson；宿主只持字符串 | Lexical `editorState.toJSON()` / `parseEditorState()`；ProseMirror `doc.toJSON()` / `Node.fromJSON()` |
| 5 | 模型 API 未接引擎 | `ControlApi::flush` 与 `Engine::commitOnTree` 汇到同一条提交路径 | CKEditor 5 的 `writer` 只在 `change()` 里改模型，改动自动 propagate 到 view；Lexical 的 update 批次统一提交 |
| 6 | 状态（含选区、撤销、控件表）散在引擎里 | 收成 `DerivedDocument`（只读派生）+ 一个显式的 State 对象 | CodeMirror 6 的 `EditorState` + `StateField`；Lexical 的 `EditorState` 双缓冲 |
| 7 | 测试两个巨型 TU | 按节拆 TU + 注册表（声明式断言表） | 主流编辑器项目的测试都是按模块分文件的 |
| 8 | 双路并存渗透成员语义 | 用显式状态（`SourceKind`）替代散落的 `tree_valid_` 判断，并尽快收掉旧路 | 无直接对照，属于降低自身复杂度的重构（★ 2026-10-13 **已做**：旧路退役，`tree_valid_` → `loaded_`） |

其中 **1、4、5 三条**是"能消除一整类缺陷"的改动（分别消除边界类缺陷、文档无法持久化、
模型与视图不同步），优先级最高；2、6 是一次结构性重构，应在阶段 1 的旧路收尾后做；
3 在量出数字之后再决定。

## 八、结论

- **设计文档的质量高于实现与集成的完成度。** 模型文档把每个取舍的理由与代价都写了
  （含"不可构造的两条不变量要标出来"这种很少见的自觉），这是本仓最大的资产。
- **风险不在编辑器内部的一致性，而在"边界"上**：进程里有三份文档表示、
  模型层与引擎层之间缺一条提交路径、门面缺一层、序列化没接到交付物。
  这三件事互相放大 —— 宿主不得不持有有损副本，正是因为没有出口。
- **实现的"最佳"程度在模型层很高（步骤/不变量/判据），在数据结构层面偏低（并集节点、
  三套坐标、派生状态散落）**。两者并不冲突：前者是纪律问题、后者是形状问题，
  形状问题可以在不推翻设计的前提下逐步收敛。
- 建议的推进次序：**先把门面与序列化接通（4、5 两条），再收旧路与派生状态（6、8），
  最后按量出来的数字决定是否做增量编译（3）**。`Node` 的瘦身（2）可以随时穿插，
  它与其它改动无耦合。
