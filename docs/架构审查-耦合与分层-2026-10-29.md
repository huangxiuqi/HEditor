## 1. 结论

主线架构与业界做法一致：不可变修订 + 步骤事务 + 单一数据流 + 一份绘制实现。这部分不用动。

## 2. 实测依赖图

目录级 include 边（`src/core/*` 之间，不含第三方头）：

```
doc    -> utils, text(writing_mode), layout(compile_result)
layout -> utils, text, doc
render -> utils, text, engine(page_recorder)
text   -> utils, doc(doc/utf8.h)
engine -> 全部
```

三处反向边，三个环：

- `doc <-> layout`：`compile_result.h:11` 引 `layout.h`（为了 BlockSpec），`layout.h` 又引 doc 的格式类型。
- `text <-> doc`：`text/fallback.cpp:5`、`text/shaper.cpp:8` 引 `doc/utf8.h`（一个 UTF-8 叶子工具放错了目录）；反方向是 `doc/para_format.h` / `doc/section_spec.h` 引 `text/writing_mode.h`。
- `render <-> engine`：`render/page_recorder.h:9` 引 `engine/page_scene.h`；而 `page_scene.h:16` 引 `engine/render_input.h`，`render_input.h:23-25` 又引了三个 engine 头。

正确的层序应该是：

```
utils -> text -> doc -> layout -> compile -> render(低) -> engine
```

其中 `render(低)` 指 bitmap / page_sink / page_scene 的纯数据与光栅部分；`buildPageScene` 这类吃 RenderInput 的函数属于 engine。

## 3. 业界对照

| 项目 | 做法 | 对本项目 |
| --- | --- | --- |
| ProseMirror | model / state+transform / view 三层；所有更新经 dispatch -> transaction -> 新 state；节点是不可变值、结构共享 | 本项目的 Doc + Step + commitSteps 已经是这个模型。差别在"单一更新入口"宿主侧没守住：页度量、配置各有多条写路径，违反的正是这条原则 |
| CodeMirror 6 | 包级拆 state / view / commands；functional core + imperative shell；state 只读 | 支持"按层拆"的方向。但它的 state/view 是包依赖，不是 C++ 的链接依赖；拆目标只能兜住符号级越界，兜不住纯头文件越界（见 L5） |
| CKEditor 5 | editing engine（model + view + conversion）与 UI 库分成两组包；命令与插件标准化 | 对应本项目的 doc/compile/layout/engine 与两个宿主。它的 conversion 是独立一层，这正好说明本项目的 compile/project 不该住在 doc/ 里（L2） |
| OOXML（Word） | 页面设置在文档里（`w:sectPr` 的 `w:pgSz` / `w:pgMar`），按节存 | 页度量必须以文档为真源，引擎配置只能是派生缓存。这是 S1 的依据 |
| Figma 式边界（代码里已引用） | 跨边界只传大块位图 | 已经是本项目做法，保留 |
| tldraw / Excalidraw | 场景图与渲染器分离，脏矩形重绘 | 本项目的 PageScene + 记录/重放已经是这个形状；只是 PageScene 放在 engine/ 里，位置不对（L1 的延伸） |

不引用具体版本号，只取结构与职责划分，避免把"某个库某年这么写"当成论据。

## 4. 任务清单

### L 系列：分层与循环依赖

#### L1 render -> engine 反向依赖

- 位置：`src/core/render/page_recorder.h:9`
- 现象：`page_recorder.h` 引 `engine/page_scene.h`；engine 侧又引 `render/{bitmap,page_sink}`。目录级成环。
- 是否真问题：是。环使目标拆分不可能；而且它说明"render 是底层"这个直觉只对一半——`page_recorder` 实际是引擎侧的胶水。
- 改法：把 `render/page_recorder.{h,cpp}` 移到 `engine/`。它只被 `engine_paint.cpp` 使用，语义是"引擎把自己的绘制调用记成场景"。
- 影响面：`engine_paint.cpp` 的 include；`CMakeLists.txt:212` 的源路径；`page_recorder.cpp` 自身 include。无 API 变化。
- 验收：`grep -rn '#include "core/engine' src/core/render` 为空；native 与 wasm 全量判据；`stress` 的帧指纹不变。
- 风险：低。纯移动。

后续（可选）：把 `PageScene` 的数据部分与 `rasterPageScene` 移到 `render/`，`buildPageScene` / `diffPageScene` 留在 engine（它们吃 RenderInput）。这一步会牵动 `render_input.h` 的三个 engine 依赖，收益不如 L1，排在 L1 之后单独评估。

#### L2 doc -> layout 反向依赖

- 位置：`src/core/doc/compile_result.h:11`
- 现象：模型层为了 `BlockSpec` 引排版层的总头 `layout.h`；`doc/project.h` 顺带也认识排版类型。
- 是否真问题：是。这是"编译层住在 doc 目录里"的直接后果（见第 3 节 CKEditor 对照）。
- 改法：新建 `src/core/compile/`，把 `compile_result.h`、`project.{h,cpp}`、`atom_map.{h,cpp}`、`format_map.{h,cpp}` 移过去。新层依赖 doc + layout，engine 依赖它。
- 影响面：源文件 7 个；include 更新约 10 处（`format_map.h`、`project.h`、`edit_command.h`、`engine.h`、`projection_service.h`、`document_session.h`、`structure_index.h`、`project.cpp`、`engine.cpp`，外加 `tests/doc_test.cpp`、`tests/edit_test.cpp`）；`CMakeLists.txt` 的源列表。
- 验收：`grep -rn '#include "core/layout' src/core/doc` 为空；`ctest --preset native` 全绿；`doc_test` 的投影/损伤用例不变。
- 风险：中。移动面大但语义不变；`project.h` 被 4 个 engine 头与 `engine.cpp` 包含，注意不要顺手改内容。

#### L3 text -> doc 反向依赖

- 位置：`src/core/text/fallback.cpp:5`、`src/core/text/shaper.cpp:8`
- 现象：底层 text 引 `doc/utf8.h`。该头只提供 `utf8ToCodepoints` / `codepointsToUtf8`，与 `utils/utf8.h` 的 `decodeUtf8` / `appendUtf8` 是同一个解码器的两半。
- 是否真问题：是（层次倒置，虽然只是两个叶子函数）。
- 改法：把三个函数并进 `utils/utf8.h`（或 `utils/utf8.cpp`），删 `doc/utf8.{h,cpp}`。函数名与命名空间不变。
- 影响面：9 个 include 点（doc 的 4 个 cpp、`doc/textbuf.h`、`layout/layout.h`、text 的 2 个 cpp、`doc/utf8.cpp` 自身）；CMake 源列表删一行。
- 验收：`grep -rn 'doc/utf8.h' src` 为空；`doc_test` 的 UTF-8 往返用例绿。
- 风险：低。

#### L4 doc -> text（writing_mode.h）

- 位置：`doc/para_format.h:23`、`doc/section_spec.h:21`
- 现象：`WritingMode` 是一个无依赖的枚举包装，放在 text/ 里，于是 doc 依赖 text。
- 是否真问题：边界上算，危害小。它与 L3 的 `text -> doc` 边构成一个二级环；L3 做完之后这条就只剩向下的一条边。
- 改法：`writing_mode.h` 移到 `utils/`。10 个 include 点跟着改。
- 验收：`grep -rn 'core/text/writing_mode.h' src` 为空。
- 风险：低。优先级排在 L1~L3 之后。

#### L5 分层闸：脚本先，目标拆分后

- 现状：`CMakeLists.txt` 只有一个 `heditor_core`，`target_include_directories` 用一个 `src/` 根，`#include "core/..."` 的写法下任何层都能看到任何层。
- 是否真问题：是"没有机械保证"，不是缺陷。
- 改法（推荐先做）：`scripts/check_layers.mjs`，解析 `#include "core/<layer>/..."`，按一张允许边表判定，违规打文件与行号，进 `npm run check`。三条反向边进 allowlist 并写原因，L1~L3 做完后 allowlist 清空；`doc -> text`（writing_mode）由允许边表直接放行，它是叶子值类型，不构成环。
- 目标拆分的现实边界：在现有 include 风格下，CMake 只能做到链接期兜底（用了未链接层的符号会链接失败），纯头文件依赖（类型、inline）照样编得过。所以脚本是主闸，目标是次闸。真要拆，顺序是 utils -> text -> doc -> layout -> compile -> render -> engine，`heditor_core` 拆成 6 个静态库，tests/wasm/native 分别链接。
- 影响面：脚本（新增）；`web/package.json` 的 check 链；拆目标时 `CMakeLists.txt` 与各 target 的链接行。
- 验收：故意在 doc 里加一句 `#include "core/layout/layout.h"`，check 必须红。
- 风险：低（脚本）；中（拆目标）。

### S 系列：状态真源

#### S1 页度量有三份真源（缺陷）

- 位置：`doc/section_spec.h:57`（文档存的纸张）、`engine/engine.cpp:249 adoptPageFromDocument`（装载时采用）、`wasm/wasm_main.cpp:346 setPageMetrics`（宿主影子）、`web/src/editor.ts` 的 `config.page`（前端影子）。
- 现象与链路：
  - 文档里的纸张只在装载时被采用一次（`engine.cpp` 的 `installDocument` 调 `adoptPageFromDocument`）。
  - wasm 的 `g_cfg.page` 只在 `setPageMetrics` 时写；其余 setter 走 `applyConfig()` 把整份 `g_cfg` 推回引擎（`wasm_main.cpp:43`），`EditorEngine::setConfig` 判出页度量变化后按旧纸整篇重排。
  - 触发：打开一份带纸张的文档 -> 改缩放（`api.ts` 的 `density` -> `setZoom` -> `applyConfig`）-> 纸张回退成宿主记的那张。
  - 反向也没有出口：命令表里 `pageSetup` 只有写，没有读，所以 `editor.config().page` 永远不刷新；打开 A5 文档后面板显示 A4，提交时把 A4 写回文档。
  - 撤销是一条独立缺陷：`setSectionPaper` 是步骤（`edit_command.cpp:3476`），undo 只恢复文档，不重新采用页度量，于是屏幕按新纸、文档按旧纸。
- 是否真问题：是（静态链路闭合；复现待运行，见第 8 节）。三处写入、零处回读。
- 改法（三步，可分开提交）：
  - S1a 引擎：把 `adoptPageFromDocument` 改成"提交后同步"——在 `commitSteps`、`undo`、`redo` 收尾处比较文档第一节的 paper/margins 与 `cfg_.page`，不同才采用并重排。比较成本是几个浮点，不必缓存。
  - S1b wasm：删掉 `g_cfg` 这份长期影子。每个 setter 以 `EngineConfig c = g_engine.config();` 起手，只改自己那一项再 `setConfig(c)`。`caret_width_pt` 的手工回写（`wasm_main.cpp:407`）随之消失。
  - S1c 前端：加一条读命令（名字不能叫 `pageSetup`，与写命令重名会被 `idl_check` 拒；建议 `pageMetricsJson`），`open` / `undo` / `redo` 之后刷新 `config.page`。读的值按 `PageMargins{top,right,bottom,left}` 出，不要按 `SectionMargins` 的 top/bottom/left/right 顺序直接摆（`engine.cpp:463` 有注释）。
- 影响面：engine 的提交/撤销路径（只在纸张真的变了才多一次重排）；wasm 的 9 个 setter 与两个读回函数；`api.ts` 的 COMMANDS + READ 表 + wasm 导出；`editor.ts` 的 `syncConfigFromEngine`；判据 `edit_test [98]`、`props`、`saveload`。
- 验收（新判据，三条）：
  - 打开 200x300 的文档，改缩放，页宽仍是 200。
  - 改页面设置后撤销，版面与面板读数一起回退。
  - 打开文档后 `describePageSetup()` 报的是文档那张纸。
- 风险：中。undo 路径加一次比较要避免"每次撤销都整篇重排"；只在纸张变化时重排。

#### S2 wasm 侧配置影子（缺陷的一半）

- 位置：`wasm/wasm_main.cpp:33 g_cfg`，12 个字段、9 个 setter 调 `applyConfig()`。
- 现象：引擎夹取过的值（`setConfig` 里的 density 上下限、caret 最小宽度）不回写影子；已经有 `caret_width_pt` 手工回写作为补丁。
- 是否真问题：是，但 S1b 一并解决。
- 改法：见 S1b。删 `g_cfg` 之后，`caretStyleJson` / `selectionStyleJson` / `undoLimit` 三个读回改成读 `g_engine.config()`（它们本来就有这个入口，`engine.h:120`）。
- 影响面：12 个字段的读写点；无 API 变化。
- 验收：改缩放后再改撤销上限，缩放不回退（一条判据）。
- 风险：低。

#### S3 前端配置影子（契约所限，保留 + 补同步）

- 位置：`web/src/editor.ts:1692 syncConfigFromEngine`，`config.page`。
- 现象：`config()` 是同步读，必须有一份本地值；当前只在诊断装载时同步，open/undo 不同步。注释自己写了失败模式："不同步 -> 下一次 configure 按过期差集算成空操作"。
- 是否真问题：是，但不是"删掉影子"能解决的——同步读的契约要求它存在。
- 改法：把同步点补齐（open、undo、redo、applyPageSetupForm、诊断装载），值来自 S1c 的读命令；`configure` 的差集仍以影子为基准。
- 影响面：`editor.ts` 的 5 个入口；`props` 判据。
- 验收：打开 A5 文档后改任意一项配置，纸张不被改写。
- 风险：低。注意 open 是 async，同步读发生在 await 之后才安全。

#### S4 跨语言常量手抄

- 是否真问题：是。`editor.ts:231` 的注释已经写明"两边不一致会平白挪一次页面"。
