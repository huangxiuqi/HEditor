# 依赖与工具链管理

> 结论摘要：**源码依赖走 git submodule，Skia 走脚本化归档，本工程不用包管理器。**
>
> - **HarfBuzz → submodule**，gitlink 钉在上游 tag `14.6.0` 指向的 commit
>   `c7a7457b`，稀疏检出只留 `src/` 与根文件（工作区 108 MB 里的 92 MB 是上游测试数据）。
> - **nlohmann/json → 脚本化取回**（单头文件、MIT、tag `v3.12.0`、校验 SHA-256），
>   见第二节末尾：头文件库没有构建系统也没有编译宏，走 submodule 只有成本没有收益。
> - **不用 vcpkg 或任何包管理器**：它只服务"本机专用、有稳定成品件"这一类依赖，
>   而这一类现在是**空集**；真正在用的依赖分别命中 submodule 与脚本化归档。
>   判断标准与重新引入的条件见第六节。
> - **Skia 与 emsdk / gn / ninja 不属于"依赖"**，继续走 `.toolchain` 下的脚本化获取；
>   但 Skia 目前取的是 `refs/heads/main`，**这份源码本身还没有钉 commit**，见第五节。
> - **web（wasm）是主线**，native 退为单测与审计的宿主。这不是一句定位，它会改变
>   "判据该落在哪一侧"，见第七节。

## 二、判断标准：一个依赖该走哪条路

依次问四个问题，第一个"是"决定归路：

| 问题 | 判定 | 归路 |
|---|---|---|
| 参与 wasm 构建吗？ | 是 | **源码依赖**（submodule）。vcpkg 的 emscripten 三元组是社区级支持，且不能保证 native 与 wasm 用同一份源码、同一组宏 |
| 需要我们一起改编译宏、裁剪尺寸吗？ | 是 | **源码依赖**。宏参与公共头的类型定义，契约必须摆在明处（`HEDITOR_USE_SKIA` 那段注释就是这种契约） |
| 自带非 CMake 构建系统（gn / meson / 自带依赖同步器）吗？ | 是 | 脚本化归档 + 钉 commit。submodule 管不住它的依赖同步器，vcpkg 没有对应的构建配方 |
| 以上都不是（只在本机、有稳定成品件、有包管理配方）吗？ | 是 | **包管理器（vcpkg）** |

按这条标准过一遍：HarfBuzz 命中前两条（两边共用、要关 `HB_NO_MT`）；
Skia 命中第三条；FreeType 现在三条都不命中——**它压根不该在库里**；
最后一档**目前是空集**，所以仓库里不放包管理器的清单文件（见第六节）。

**头文件库是这套标准的第四种情形，走脚本化取回。** 判据是"有没有构建系统"：
没有构建系统、没有编译宏、只有一份（或几份）源文件时，submodule 提供的那些好处
（钉 commit、稀疏检出裁掉测试数据、跟着父仓库的提交一起走）全都不起作用，
而它的代价照付（要人跑 git 写入、update 会把 HEAD 静默拉回、多一层目录与
`.gitmodules` 条目）。这类依赖按"钉 tag + 校验哈希 + 入库"处理：
`third_party/nlohmann/` 就是这么来的，`scripts/deps_init.ps1` 第 5 节负责取回与校验，
校验不通过就报错退出，不静默换版本。它与 Skia 归路的差别只在取回方式
（单文件 HTTPS 下载对 tar 归档），钉版本与校验这两件事一样。

第四档还带一个附加条件，这也是它在本工程几乎不可能命中的原因：本工程要求 native 与
wasm 用**同一份源码、同一组宏**，"两边一致"本身就是正确性判据。一个依赖只要参与
wasm 构建，就只能走第一档的源码依赖；而包管理器给的是按平台各自构建的成品件，
两组二进制无法保证行为一致。于是这一档只剩"只服务 native、且不参与任何输出比对"
的依赖，例如纯本机的测试或分析工具。

**否决的替代方案，以及为什么：**

- **FetchContent / CPM**：配置期下载，把"构建"与"网络可达"绑在一起，
  离线环境与可审计性都变差，而且版本钉在 CMake 文件里、与 git 历史对不上号。
- **emscripten ports（`-sUSE_HARFBUZZ=1`）**：只服务 wasm 一侧，
  会直接打破"native 与 wasm 共用同一份 HarfBuzz 源码与宏"这个前提——
  两套 HarfBuzz 意味着断行结果可能不一致，而"与全量一致"是本项目的核心判据。
- **系统包管理器**：Windows 上没有可用的上游包源，不谈。

## 三、HarfBuzz 走 submodule：已验证是直接替换

换成 git 检出会不会需要额外的生成步骤？这是 submodule 方案最大的不确定点，已核实：

- 上游 tag `14.6.0` 的 `src/hb-version.h` **是入库文件**（blob
  `8b7864cce9cd1c7c8faeb334f6086b5fdeae19f1`，即 LF 内容 2597 字节、`md5 671d707a`）：
  `src/meson.build` 虽然会从 `hb-version.h.in` 生成它，但仓库里已经带了一份。
  我们直接编译 `harfbuzz.cc`、不跑 meson，所以**移植后不需要任何生成步骤**。
- **迁移前后是同一份源码，这条是实测的**：`diff -rq --strip-trailing-cr` 比对
  `third_party/harfbuzz-14.6.0/src` 与 `third_party/harfbuzz/src` 输出为空。
  不加 `--strip-trailing-cr` 会看到 575 处"差异"，全是行尾 —— 本机 `core.autocrlf=true`，
  git 检出写出的是 CRLF。由此得一条纪律：**不要拿工作区文件的 md5 与 git 里的内容比**
  （`hb-version.h` 工作区 2692 字节、blob 2597 字节，差的 95 字节就是行数），
  要比就比 blob 标识（`git rev-parse HEAD:<path>`）。
- **tag 与主分支尖端不是同一份源码**：主分支尖端（`fd0c6c9a`，2026-10-10）比
  tag `14.6.0`（`c7a7457b`，2026-10-05）新五天，`src/` 下差 41 个文件、+539/−2442 行；
  差异包含 subset 与内部测试，也包含 `hb-ot-layout-gsubgpos.hh` 和 GPOS 的
  `PairPosFormat*.hh`、`ValueFormat.hh`——那正是 kerning 走的路径。
  也就是说"取到哪一份"会影响排版结果，必须钉死，不能让它跟着默认分支漂。
- `harfbuzz.cc` 的 69 条 include 全在 `src/` 内，`src/` 自成闭包。
- 版本表达方式随之改变：**目录名里的版本号作废，版本等于 gitlink 里的 commit**。
  这里要说清 tag 与 commit 的关系，否则容易以为"钉 tag"和"钉 commit"是两件事：
  gitlink 只能存裸 SHA，**存不下 tag 名**，所以 submodule 钉住的从来就是 commit；
  tag `14.6.0` 只是这个 commit 的可读名字，脚本拿它当入口（决定拉哪个 ref），
  拿解析出的 commit 当断言。能把名字也记进仓库的只有 `.gitmodules` 的 `branch` 字段
  （本仓库写的是 `branch = 14.6.0`）：它只被 `git submodule update --remote` 使用，
  普通的 `update` 一律按 gitlink 里的 commit 检出，所以它只是个标签，
  不影响"钉死"这个性质。
  升级 HarfBuzz 就是"改 gitlink（tag 名与 commit 一起改）+ 提交一条"，
  不再是"删目录、下压缩包、解压"。

迁移期两套路径并存，不要求一次切换到位：`CMakeLists.txt` 优先取
`third_party/harfbuzz`（submodule 路径），不存在时回退 `third_party/harfbuzz-14.6.0`
（旧的版本号目录），配置时打印实际用的是哪一份。

具体命令在 `scripts/deps_init.ps1` 里：`--depth 1` 浅克隆、钉 tag、稀疏检出
（只留 `src/` 与根文件）、按哨兵文件与 md5 校验结果。脚本要执行 git 写入命令，
所以**必须由人运行**（本仓库硬性约束：禁止智能体执行 git 写入）。

两个已经踩到的坑，脚本已按下面的做法实现：

- **浅取 tag 之后不能再用 tag 名字去检出。** `git fetch --depth 1 origin refs/tags/<tag>`
  只把结果写进 `FETCH_HEAD`，**不会**在本地建出 `refs/tags/<tag>` 引用（显式 refspec
  不触发 tag 自动跟随）。此时 `git checkout refs/tags/<tag>` 直接失败，而脚本在失败处
  中断，后面的稀疏检出就不会执行——一次失败同时留下"版本没钉（HEAD 停在默认分支尖端）"
  与"工作区没裁剪（109 MB）"两个症状，看起来像两个 bug，其实是一个。
  正确做法是从 `FETCH_HEAD^{commit}` 解析出 commit 再检出，并且把这个 commit 作为常量
  写进脚本、在末尾断言 `rev-parse HEAD` 等于它。
- **钉完必须提交那条 gitlink。** `git submodule update` 会把子模块的 HEAD 拉回父仓库
  索引里记录的那个 commit。只改工作区不提交，下一次 update 就把 tag 覆盖回默认分支尖端，
  而且是静默的。

## 四、FreeType 现在就不该在库里

21 MB，零引用。native 侧用自写后端 `bitmap.cpp`，wasm 侧用 Skia，
而 Skia 自己那份 FreeType 在它的 `third_party/externals` 里，只服务 Skia。

所以处理方式是**什么都不做**：不加 submodule、不进 vcpkg、也不急着删。
将来 native 侧真要用到它（比如做 hinting 开关或对照度量），它属于源码依赖，
按第三节同样的做法加 submodule — 但那时要注意"我们自己的 FreeType"与
"Skia 内部的 FreeType"是两份，别把两者的字形度量混着比。

## 五、Skia 为什么不进前两条路

三条理由，每条都是实测过的：

- **不是 CMake 工程**：它用 gn 生成 ninja，构建入口与我们这套 CMake 无关；
  vcpkg 没有官方 skia port，也没有办法据此产出 wasm 版静态库。
- **自带依赖同步器**：`third_party/externals` 在源码包里是空目录，
  六个依赖按它 `DEPS` 里钉的 commit 各自取。submodule 管不了这一层。
- **编译期契约必须可见**：`CMakeLists.txt` 里那一组 `SK_*` 宏（现在是六条）必须与
  Skia 自己编译时逐条对齐，漏一条不会报错、只会让两边对同一个结构体有两种理解。
  包管理器恰恰会把这类开关藏起来。
  ★ 这份清单**不是固定的**：开 wasm SIMD 时会少掉 `SKVX_DISABLE_SIMD`（那是上游
  wasm 工具链的默认，见 `scripts/build_skia_wasm.ps1` 顶部坑 ⑤），同时主程序的
  **编译与链接**都要补 `-msimd128`。三处成对：缺 `-msimd128` 则 SIMD 静默无效，
  只改库不改主程序则 ODR 违规。

所以它继续走脚本化归档，但**现状有一个缺口要补**：脚本取的是
`https://codeload.github.com/google/skia/tar.gz/refs/heads/main` —— 分支，不是 commit。
换成 commit 只需把 `refs/heads/main` 换成具体 SHA，两种写法都可行：

```
https://codeload.github.com/google/skia/tar.gz/<sha>                    # 与现在同源，换掉分支名
https://skia.googlesource.com/skia/+archive/<sha>.tar.gz                # 与 externals 同一套只读归档接口
```

取 SHA：`git ls-remote https://github.com/google/skia main`（只读命令，人可跑）。
这件事**留到下一次重建 Skia 时做**，不要在没验证的情况下改——本机 `.toolchain/skia`
已经解压好了，改了 URL 不影响现有构建，但新机器会拿到另一棵树，而重建一份 Skia
要跑几百个编译步骤。

## 六、为什么不用包管理器

结论：仓库里不放 `vcpkg.json`，构建侧也不提供任何包管理器开关。按第二节的标准倒推
就能得到结论——包管理器只对应第四档，而第四档是空集，为它长期维护一份清单、一个开关、
一条判据是空转，而且会给人"这里有成品库在用"的错觉。

支撑这个结论的是两条事实，都不是"wasm 是主线"这句话本身：

- **主线上唯一有分量的候选永远不可能走包管理器。** HarfBuzz 必须与 wasm 共用同一份源码
  与同一组宏，所以它只能走源码依赖。哪怕将来 native 反过来成为主线，这个约束也不变——
  也就是说"哪边是主线"其实不改变这条判断，它只改变了第七节说的判据分布。
- **native 侧现在没有任何成品库可装。** native 的光栅后端是自写的 `bitmap.cpp`，
  三个依赖（HarfBuzz、Skia、FreeType）没有一个落在第四档。

**重新引入的条件**：出现一个只服务 native、不参与任何输出比对的依赖，并且在 Windows 上
从源码构建它的代价明显高于装成品件（zlib、libpng、ICU 这类就属于这种）。真到那一步，
下面几条经验仍然适用，先记在这里：

- **只服务 native。** 构建脚本不向 wasm 传任何包管理器的工具链。
  判据是 wasm 的 `CMakeCache.txt` 里不出现 `VCPKG_` 前缀变量。
- **依赖必须可选。** 在 `CMakeLists.txt` 里用 `find_package(<pkg> CONFIG QUIET)`
  加一个 `HEDITOR_WITH_<PKG>` 选项，缺了不影响 wasm 与 native 的默认配置。
  理由同上：wasm 侧永远拿不到它。
- **钉注册表快照。** 清单里要写 `builtin-baseline`（包管理器仓库的 commit），
  它决定"同一个 port 名解析到哪个版本"；不写就跟着本机 HEAD 走，换台机器版本会漂。
  这与第三节 HarfBuzz 钉 commit 是同一个诉求，只是表达方式不同。
- **三元组选 `x64-windows-static-md`**（静态库 + 动态 CRT）。它与 CMake 默认的 `/MD`
  一致，不会撞 LNK2038 运行库不匹配，也不用把 DLL 复制到运行目录。
- **包管理器本体与 port 构建由人在终端执行**，不要在这个沙箱里跑：本机的 vcvars 链路
  对 `reg.exe` 有限制，port 编译会以看不懂的方式失败。建议开二进制缓存
  （`VCPKG_DEFAULT_BINARY_CACHE`），否则换个构建目录就重编一遍 port。
- **许可证同步。** 加任何一个这样的依赖，都要同时更新
  `docs/THIRD_PARTY_NOTICES.md` 与 `licenses/`。本项目是"静态链接进闭源产品"
  这条线，授权从第一天就要能逐条回答，不能等到发版。

## 七、web 是主线，判据要跟着挪

"主线是 wasm"这条定位，真正的影响不只在依赖，更在**哪一侧的判据算数**：

- native 的光栅后端是自写的 `bitmap.cpp`，wasm 用的是 Skia。两者对同一条排版结果
  **不可能逐像素一致**——抗锯齿、字形栅格化、亚像素定位的实现各不相同。
  所以 `auditFrame` 在 native 上证明的是"排版与光栅逻辑自洽"，
  不能证明"线上看到的就是这样"。
- 判据分层要把归属写清楚：**与全量比对的排版判据（`auditLayout`）两侧都算数**，
  因为排版不依赖光栅后端；**整帧像素判据只在同一后端内部有效**，
  跨后端比较必须落到浏览器探针（`scripts/verify_web.ps1`）那一侧。
- 单测仍然走 native 的理由也在这里：它快、可调试，且排版逻辑与线上同源。
  但"改完只跑 native 单测"不够——凡触及上屏的改动都要再跑一次浏览器探针。
- native 的定位与边界（为什么保留、什么条件下才该砍掉）见
  `docs/正式化架构与迁移路线.md` 4.6。

```powershell
powershell -ExecutionPolicy Bypass -File scripts\deps_init.ps1
```

它做四件事：`git submodule add --depth 1` 到 `third_party/harfbuzz`；
按 ref 取 tag `14.6.0`、从 `FETCH_HEAD` 解析 commit 并检出；
`sparse-checkout set --cone src` 裁掉 92 MB 的上游测试；校验 HEAD 与版本头 md5。
跑完后**由你提交** `.gitmodules` 与那条 gitlink，否则 `git submodule update` 会静默
把 HEAD 拉回主分支尖端。之后再各跑一次 `cmake --workflow --preset native-local` 与
`cmake --workflow --preset wasm`。

## 九、判据（可证伪）

- 跑完 `deps_init.ps1` 后：`git -C third_party/harfbuzz rev-parse HEAD` 等于
  `c7a7457b7385f33178e8cf87615ca077a810bbe7`；`git -C third_party/harfbuzz status
  --porcelain` 输出为空（工作区与 HEAD 一致）；`test/` 不存在；目录体积约 10 MB。
  脚本自己不通过就退出非零。本地实测的落地结果：HEAD `c7a7457b`、体积 **9.1 MB**、
  工作区干净、`src/` 是唯一残留的顶层目录。
- **钉对版本就不改变任何输出**：取到的是与迁移前同一份源码，所以 native 单测
  （364 项与 55 项）与浏览器探针的整帧判据应当全绿。若 `auditFrame` 出现像素差异，
  先查 `rev-parse HEAD`——多半是取到的不是同一份源码，而不是"排版变了"。
- 仓库里不再有包管理器痕迹：根目录没有 `vcpkg.json`，`CMakePresets.json` 里没有任何
  vcpkg 相关开关，`build/wasm/CMakeCache.txt` 里没有 `VCPKG_` 前缀变量。
- 跨后端的像素判据只在浏览器探针一侧算数（第七节）：native 的 `auditFrame` 全绿
  不能替代 `scripts/verify_web.ps1` 全绿。
- **单头文件依赖按哈希钉住**：`third_party/nlohmann/single_include/nlohmann/json.hpp` 的
  SHA-256 是 `aaf127c0…de63`，与 `scripts/deps_init.ps1` 里记的常量一致；
  不一致时脚本报错退出而不是覆盖。`CMakeLists.txt` 在缺文件时直接配置失败并指回本文件，
  不会带着一个缺依赖的配置往下走。
- **换 HarfBuzz 源码（改 submodule 的 commit、或改它自己的头）之后，`heditor_harfbuzz`
  的 obj 必须重编。** 这条由 `/showIncludes` 那条通道记着：`harfbuzz.cc` 把 69 个 `.cc`
  与 289 个 `.hh` 全聚合进来，它们都是被 include 的文件，通道认得出。
  自查手法：推一下某个 HarfBuzz 头的 mtime 再构建，看聚合 TU 有没有重编；
  平时也可以用 `ninja -C build/native -t deps` 反查它的依赖条数（不该是 0）。
  ★ 历史：这条曾经是断的 —— 早先那份 `heditor_track_header_deps` 只 glob `.h/.hpp`，
  `.hh` 与 `.cc` 都没进依赖图，换版本会静默复用旧对象、编出来的是上一份源码。
  后来用 `OBJECT_DEPENDS` 兜住，而 2026-10-13 那个粗粒度余量**整体撤掉**了
  （改一个 core 头要重编 37 个 TU，而实测真正需要的只有 9 个），现在只靠真通道。
  ★ 这条通道的前提是**配置与构建用同一个控制台代码页**：前缀是本地化的（"注意: 包含文件: "），
  936 与 65001 两档都能工作，但两档不一致时一条依赖都不记 —— 而且**不报错**。
  所以别在构建脚本里擅自切代码页；排查手法见 `.workbuddy/memory/ENV.md`。
