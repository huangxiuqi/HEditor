# 正式化架构与迁移路线：富文本 + 表单 + 三模式

> 结论摘要：**在原地做，但第一刀要切在文档模型这一层，而且要连"一块文本 + 一组字体参数"
> 这个假设一起换掉。**
> 新需求（富文本、图片、公式、表格、表单控件、三模式切换）全部落在**文档模型及它以上**的层，
> 一处也没落在排版引擎上；而引擎那套东西（整形、光栅、增量排版、以及配套的
> "与全量一致"判据）是这份仓库里最贵、也最难重新长回来的资产。所以重开项目解决不了
> 主要矛盾，只会净亏。
>
> 参照项目 `D:\Develop\DCWriterLite` 的授权是 **GPLv3**（见第二节）：
> 它的**代码**不能进入闭源产品，但它的**架构选择与功能清单**可以参考。
> 事实上它的架构（元素树 + 命令层 + 撤销 + 三视图模式）与本方案的结论同向，
> 可以当成"这条路别人已经走过"的现成证据，而不必当成代码来源。
>
> **与 `docs/文档模型设计.md` 的分工：** 本文管分层、路线与选型取舍（为什么这么做、
> 先做什么）；数据结构与语义（节点类型、位置、控件、域、表格、单位、序列化形状）
> 以那份文档为准，两份冲突时以它为准。本文第五节阶段 0 与 1 的细化也在它那里。

## 一、需求与现状的差距

现状盘点：`src/core` 共约 3.4 千行（实测 3379 行；另有 `src/wasm` 748 行与 `src/app` 407 行），
对外只有"编辑模式 / 表单模式 / 只读模式"三档开关（`EditMode`）与一套区间式控件
（正在按方案 A 改造），没有撤销、没有选区、没有序列化。

| 需求 | 现状 | 差距性质 |
|---|---|---|
| 文本样式按 run（粗斜体、字号、颜色、字体） | 引擎输入有字符格式 run（`FormatRun`）、排版按它切、行度量按行算；模型层的 `CharFormat` 与三层解析已接进编译 | 接缝已通；粗体、斜体、下划线引擎还不认（编译记诊断）；`line_factor` 与段后距仍是块级 |
| 图片（内联原子元素，可拖拽改尺寸） | 无 | 新增元素类型 + 排版原语 |
| 公式 | 无 | 新增元素类型（渲染可先做占位，后接排版后端） |
| 表格（合并单元格、行高列宽） | 无 | 新增容器元素 + 一套独立排版 |
| 表单控件（文本框、单选、复选、下拉） | 有区间式控件模型 | 改造为容器元素（方案 A 的自然延伸） |
| 编辑 / 表单 / 只读 三模式 | `EditMode` 三档 + `edit_capability` 落点判定已就位 | 骨架可用，行为需要补齐 |
| 撤销 / 重做 | 无（全程 0 处命中） | 新增命令层 |
| 选区 / 剪贴板 | 无 | 新增 |
| 文档保存 / 打开 | 无 | 新增序列化层 |
| 多文档 / 版本化对外 API | 单例引擎 + 手拼 JSON 字符串 | 新增门面层 |

一句话：**引擎层不用重写；文档模型要换；模型以上全部要新建。**
前两轮说的"方案 A 把控件边界做成流位置"，正是这个换模型动作的第一刀，
只是当时的范围划窄了——它同时也是"元素树"的地基。

## 二、DCWriterLite 的定位：可借鉴什么，不能借鉴什么

### 2.1 授权

`LICENSE` 是 **GNU GPL v3**，强 copyleft：只要把它的代码（哪怕片段）并进我们的项目再分发，
整个作品都必须按 GPLv3 开源。闭源商用产品做不到这一点。
作者另有商业版 `DCWriter`（收费），**若确实需要它的代码，正规途径是买商业授权**。

需要分清的两件事：

- **表达**（.cs 源文件、注释、命名）受版权保护，不能复制；
- **思想、架构、算法、功能清单**不受版权保护，照着思路自己实现是干净的。

所以它可以当**参照与需求清单**用，不能当**代码来源**用。

### 2.2 技术栈

它是 .NET 9 / Blazor WebAssembly / C# + Canvas/SVG；我们是 C++ / 自建 WASM / 手写 JS。
代码层面本来就无法直接复用，能迁移的只有架构决策。

### 2.3 它的开源版清单可以直接当验收表

元素类型（`Source/DCSoft.Writer.Core/Dom/`）：文本、图片、输入域（容器）、
复选框 / 单选按钮、表格（行 / 列 / 单元格）、段落标记、换行、分页、页码、
文档节、子文档、条码、图表、媒体、控件宿主。
视图模式（商业版）：**表单视图**（操作只许落在输入域内，域外不可选中）、
**阅读视图**（只读但可选中复制）、**长文档视图**（不分页连续编辑）。
其中表单视图的"域外不可选中"我们**部分不照搬**，关键是把两个轴分开：
**光标落点**限制在可编辑控件内（这一点与它一致），**选区不限制**
（Shift 扩展、拖拽、全选都能跨出控件）。它连选区一起禁，是因为它的用途之一是防复制；
我们没有这个需求，反倒要能核对上文。详见 4.3 与模型文档第七节。
另有撤销/重做、复制粘贴、标尺、段落样式、权限管控、数据源绑定、Excel 语法的数值公式。

对照它，可以确认三件事：我们要的三模式是**同一个控件上的策略差异**，不是三套控件；
表单控件必须是**容器**（输入域里能放段落，所以参考项目里 `DomInputFieldElement`
继承 `DomContainerElement`）；命令层与撤销层是**并列的两层**，不是塞进控件里。

### 2.4 它没有而我们有的

- **增量排版 + 可证伪判据**（`auditFrame` 逐像素、`auditLayout` 逐字段、
  单测 `[16]` 用第二个引擎从零重排的整帧对照）。它的公开文档没提这套东西。
- **书写模式是一等公民**：横排 / 竖排 / 侧倒蒙文共用一套贪心断行。
- 光栅层"关掉字形缓存后逐字节等价"的断言。

结论：**它的架构值得抄思路，它的代码不能抄；我们的引擎比它更讲究，不该丢。**

## 三、目标分层

自下而上八层。标注含义：保留 = 一层不动；扩展 = 只加不改；换 = 整层替换；新 = 新建。

```
8  宿主门面          版本化 API / JSON 协议 / 演示数据搬出 src/         新
7  序列化            DOM 树 <-> JSON（含包容器与压缩，见 4.5）          新
6  视图与模式        EditMode 三档 + 策略裁剪 + 选区呈现                扩展
5  命令层            EditCommand / Undo / Redo / 剪贴板 / 选区          新
4  文档模型          容器元素树 + 元素流 + run 级样式                   换
3  排版              断行 / 书写模式 / 分页 / 增量续排 / 后缀复用        扩展
2  光栅              位图 / 页指纹 / 增量上屏                           扩展
1  文本与字体        HarfBuzz 整形 / 字体回退链 / 度量                   保留
```

第 1、2 层完全不动。第 3 层要新增一类输入：**内联原子元素**（图片、公式、控件占位）
作为"不可断的盒子"参与断行；分页与增量续排的机制不变。
第 4 层是本次改造的主体。

## 四、关键设计决策

### 4.1 文档模型：元素流 + 容器元素

```
Document
  └─ Body                          流；段落是流里的范围，不是节点
       ├─ TextRun("患者主诉：")      叶子，带样式
       ├─ ContentControl [id=3]     容器：自带开闭两个边界元素
       │    └─ TextRun("反复")
       ├─ ParagraphMark             段落结束标记：段落属性的唯一宿主
       ├─ Image {ref,w,h}           原子（不可断的行内盒子）
       ├─ Formula {src}             原子
       └─ Table                     容器：行 / 单元格，单元格内又是流
```

要素：每个元素自己管四件事——**子元素、属性、命中/绘制委托、序列化**；
样式挂在元素上（run 级），继承由树决定（这正是 `BlockSpec` 缺的那一层）。

**没有"块级容器 / 行内容器"这个二分**（这一条是后来修正的，依据见模型设计第三节）：
容器之间的差别只有"接受哪些元素类型"与"跨度是否跨过段落标记"。
段落也不是节点，而是同一容器内两个 `ParagraphMark` 之间的范围，段落属性挂在标记上；
落盘时段落不单独写，它是派生量。于是"主诉：\[____\]"（不跨标记）与
"一栏里多段"（跨标记）是同一机制的两个取值，不需要两个类型，
也不需要"行内升级为块级"的提升规则。

这同时把方案 A 收进来了：**控件是一个容器元素，它的两个边界就是它在流里的开闭标记**
（结构形态上它属于容器型；另一种是"内部没有可寻址位置"的原子型，今天没有实例 ——
见模型文档第七节"控件分三层"）。
并且 `InputField` 这个名字已换成 `ContentControl`（与 OOXML 的 `w:sdt` 同义）。
不再需要"从裸区间反推嵌套"：方案 A 里要删的那批东西
（`withBracketSlots` 三分桶、`inlineOffsetFor` 短路、`innermostAt`、`normalize()`、
`adjustControlsOn*` 四个函数）在这个模型里没有存在的必要。

### 4.2 光标是容器加偏移，不是整数

节点级位置是 `Pos = { container: NodeId, offset: int }`：容器里 `offset` 是子元素槽位序号，
文本节点里是码点下标。这是 ProseMirror / Slate / Lexical 与 OOXML 的共同做法，
也是上一轮文档 `docs/控件边界诊断与方案.md` 第四节给出的结论。

要点：**边界是流里的真实元素**，所以"在 `[` 与 `]` 之间"天然是一个合法位置，
删空的控件也仍有两个互不相等的槽位。另有一套索引**流位置**（深度优先展开后的元素序号）：
段落序号、脏段标记与引擎接口都定义在它上面，它不是"等价但更快的视图"，而是第二套索引。
约定是节点级 API 与内部位置用 `Pos`，段级与引擎级用流位置，换算必须双向互逆。
细节见模型设计第四节。

**引擎侧的光标只有一个数：段内流位置 `caret_rel_`。** 边界是流里的真实元素，所以同一个段内
码点偏移上可能压着好几枚括号："控件之前 / 进入控件 / 内容末尾 / 控件之后"是互不相同的插入点 ——
它们只在流位置上才是互不相邻的整数。`rel` 就是"数格子"（文本字与边界括号各占一位），
`(段, 码点偏移)` 与侧别都是它的派生量：

    offset = cpOffsetInBlock(para, rel)           // 对外接口照旧说这个
    side   = rel - offset - 排在它前面的边界数     // 光标几何与命中测试说这个

派生量不可能与它不同步，所以"陈旧侧别复活"这一类 bug 从结构上不存在（此前那对
`caret_side_` / `caret_side_at_` 需要失效标记兜，正是因为这个）。

| rel 落点 | 位置 |
|---|---|
| 本偏移上所有括号之前 | 侧别 0 |
| 第 k 枚括号之后（0 < k < 括号数） | 方向键逐格走、点击落在两枚之间 |
| 本偏移上所有括号之后 | ＝紧随其后那个字的位置，字段内容起点 |

三条纪律：**方向键一次跨一枚簇**（括号也占一格，所以共享边界 `][` 要按两下）；
**点击量到的是侧别**（`hitTestPt` 交出去的 `side` 是落点的完整身份，`field` 只是它的投影，
给界面显示用）；**编辑落点一律走 `setCaretAtFlow` / `setCaretRel`**，只有"宿主按 (段, 偏移)
程序化定位"与 Home/End 才走 `defaultSideAt` 那条投影约定。

**为什么"一到控件就问题多"：光标以前只存在"文本坐标"里，而那个坐标不含括号。** 模型里括号是
流里的普通元素（每个边界各占一个流位置），所以"一个字符一个字符地移动"本来就是在流位置上
加减一 —— 根本不需要认识括号。但引擎的光标存的是 `(段, 段内码点偏移)`：每次要拿它去问
"这是流里的哪一个位置"，都得**猜**。猜的入口有四处：方向键移动、点击落点、删除区间、
编辑之后的落点。每猜错一次就冒一个只在边界上出现的症状（跳一格 / 点不进去 / 字进错字段），
于是修一处冒一处。

收口只有一条：**位置与侧别由操作算出来的流位置给出，不猜。**

| 入口 | 流位置从哪来 |
|---|---|
| 方向键 | `rel ± 1`（括号也占一位，所以"一次一格"是字面意思） |
| 点击 | 命中测试量到的侧别，与偏移合成 rel |
| 删除 | 区间 = 这段文本码点自己占的那一段（`textSpanAt`），落点 = 区间起点 |
| 插入 | 落点 = 插入区间的终点（事务里已经算好） |
| 分段 / 合并 | 新段落标记之后那一位 / 被删掉那枚标记的位置 |
| Tab | `tabFrom` 给出的目标 |
| 撤销 / 重做 | 撤销栈给出的恢复位置 |

只剩两类入口没有流位置可给：宿主按 `(段, 偏移)` 程序化定位（`setCaret`）与 Home/End 按行盒
端点定位。它们走 `projectCaret` —— 用 `defaultSideAt`（"最内层含端点"）投影一次，
那是**从文本坐标投影到流位置的唯一约定**。

★ **rel 相对"边界表"而存在，所以表在变的那一刻不能读它。** 三条实测教训：
① 曾经 `syncInlineObjects` 里"清表"必须排在"问聚焦字段"之后 —— 名单靠光标位置定，而光标位置
是拿对象表解释出来的，先清表再问会让聚焦字段当场换人（**现结构性消除**：`syncInlineObjects`
只重写显示副本 `blocks_`，解释 rel 读的是编译产物那一份，引擎碰不着它）；
② 宿主整批换控件曾经是"清空 + N×`addControl`"两步（现已合成 `setFormControls` 一次调用）：
中间态里一枚括号都没有，侧别那一刻没有对应物，引擎自己搬必然抹成 0（实测 7/2 变 7/0，接着
打字进了左边字段）—— 当时的补救是宿主在整批开始前把 `(偏移, 侧别)` 记下来、整批做完再摆回去。
★ 教训留着：**只要"读侧别"与"改边界"分处两次调用之间，就一定会踩这一格**；合成一次调用才是
根治，宿主那几十行补救也一并删了；
③ 持树那条路（`objectsFor` → 编译产物）用的是**全部边界**（不区分显示与否），所以 rel 不受
"显示哪些括号"影响；旧 `setBlocks` 路径只有显示表，rel 会随显示档漂 —— 这是退役那条路的
又一条理由。

### 4.3 三模式是一套能力 + 策略裁剪

不写三套代码。同一个文档模型，`EditMode` 决定"光标能落在哪、哪些命令可用"：

| 模式 | 光标落点 | 编辑 | 说明 |
|---|---|---|---|
| 编辑模式 | 全部 | 全部 | 现状（`EditMode::Document`） |
| 表单模式 | **全部（与编辑模式相同）** | 只有在可编辑控件内插入/删除 | 光标位置不受控件约束，受约束的只有编辑能力（`canInsert` / `canErase`）；**选区三种模式都不受限**（可选中复制）。早期草案写成"只落可编辑控件内"，实测会得到"字段外的正文连点都点不进去"这类与编辑边界无关的怪现象，已改回 |
| 只读模式 | 全部 | 一律拒绝 | 打印预览同此路径 |

表单模式的落点/选区口径、以及"可编辑集合取交集"（只读控件里嵌可编辑控件时内层仍不可编辑）
写在模型文档第七节与第二节；`w:group` 那种"内层覆盖外层"的例外我们不需要。
Tab 的分工（编辑模式是制表符、表单模式在控件间切换、只读模式放行、表单模式不提供插制表符的
默认键位）、结构操作默认关闭（内容可编辑但控件不可删）、越界交互只走宿主回调不在编辑器内提示、
以及"默认键位必须避开浏览器保留键（`Tab` 家族带修饰键拿不到事件）"，也都在那一节。

**这个思路已经落地**：`edit_capability` 的 `canEditAt` / `canEditRange` 就是它
（判定的输入是树 + 流位置 + 侧别，不再是"控件下标 + preferred"那套区间算术 —— 那一版
`EditPolicy` 已随旧装载路径一起退役）。两条轴也分开了：**"这个位置能不能当落点"是独立
判定**，不要混进"能不能编辑"里。

### 4.4 命令层是差量与撤销的唯一入口

所有编辑都走 `EditCommand`：命令自己负责"文档改了、控件跟着走、撤销记录的什么"。
上一轮诊断出的那类缺陷（三个编辑入口各自手工维护控件区间、漏调一个就脱节）
在命令层里结构性地消失。

**先做命令层再做富文本**：风格切换、插入图片、插入表格都只是新的命令，
不必再碰引擎。

### 4.5 序列化：JSON 做语法，包做容器，压缩做体积

**结论：JSON 能满足全部功能需求，选定 JSON。但体积的大头不在"XML 还是 JSON"。**

实测 23 份真实病历模板（`scripts/probe_serialization_size.py`，样本取自参照项目的
`wwwroot/demoDocuments`，合计 13.84 MB）：

| 口径 | 字节 | 占原始 |
|---|---|---|
| XML 原始 | 13,835,860 | 100.0% |
| 其中 文字 | 829,811 | 6.0% |
| 其中 属性值 | 736,483 | 5.3% |
| 其中 标签间缩进与换行 | 7,584,303 | 54.8% |
| 其中 空元素（93,160 个） | 1,954,659 | 14.1% |
| JSON 完整键名 | 9,956,253 | 72.0% |
| JSON 紧凑（键名与标签名走符号表） | 3,122,346 | 22.6% |
| gzip(XML 原样) | 468,773 | 3.4% |
| gzip(JSON 紧凑) | 342,210 | 2.5% |

三个结论：

**一、88.7% 不是内容。** 缩进与换行一项就占 54.8%，纯空白、零信息；空元素占 14.1%，
是"每个元素把默认属性照写一遍"的产物（`<Attributes />`、`<Expressions />`、
`<ScriptItems />`、`AutoFixTextMode=None`、`<XElements xsi:nil="true"/>`）。
这两项与语法无关，换成 JSON 一样会犯。

**二、换 JSON 省的是语法那一份。** 完整键名只有 72%，因为参照项目的写法本身已经很紧凑
（所有元素都叫 `<Element>`，类型放在 `xsi:type` 属性里，标签名恒定）。
把标签名与属性名收进符号表、每个名字只出现一次，才降到 22.6%——这是 JSON 的真正优势。

**三、压缩之后差距缩到 1.37 倍。** gzip(XML 原样) 0.47 MB 对 gzip(紧凑 JSON) 0.34 MB。
"XML 体积太大"这个感受在**未压缩的中间态**下成立；一旦落到传输与存储，体积主要由压缩决定。

所以决定体积的是三条与语法无关的措施：

- 缩进只用于人工调试输出，落盘一律无空白（这一条单独就是 55%）。
- **默认值不写**，只序列化与默认不同的属性（XML 与 JSON 都要做）。
- **二进制资源外置**：图片不要 base64 塞进文档（base64 膨胀 33%），走包里的二进制条目，
  文档只存 ID。这批样例里没有图片，所以图上没体现；真实病历一旦有检查报告、心电图，
  图片会成为绝对大头。对标 OOXML 把图片放在 `word/media/*` 的做法。

这正是 OOXML 的选择：它不靠 XML 语法省体积，靠的是 ZIP 包 + 压缩 + 二进制资源分 part 存放。

JSON 与 XML 的实际得失：

| 维度 | JSON | XML |
|---|---|---|
| 未压缩体积 | 好（键名只出现一次） | 差 |
| 压缩后体积 | 略好（1.37 倍） | 可接受 |
| 前端（JS）读写 | 原生 | 需要解析器 |
| WASM（C++）读写 | 自己实现，注意浮点往返 | 可用 pugixml 之类 |
| 调试可读、版本管理 diff | 好 | 好 |
| 模式校验 | JSON Schema 生态弱于 XSD | XSD 成熟 |
| 与外部标准互换 | 弱 | 强：HL7 CDA、卫生信息共享文档、医保接口规范基本是 XML |

最后一行是 XML 唯一有实质优势的地方，但**那是边界适配器的事，不是内部存储格式的事**：
内部用 JSON，需要对接外部系统时写一个 XML 导入导出适配器即可。

实现时要定死两条：

- **浮点按十进制字符串写**，不依赖默认浮点格式化，否则 `parse(print(doc)) == doc`
  这条判据会失败（坐标、字号、行高都要过）。
- **增量保存**：嵌套树不友好（改一处要重写整个文件），而增量是本项目的特色。
  建议编码成扁平形式——元素表 + 样式表 + 父子索引数组，只存非默认值。
  既更小（没有嵌套括号），也更适合差量落盘。二进制编码的取舍见 4.5.1。

### 4.5.1 要不要自定义二进制格式

**结论：不要。** 实测（`scripts/probe_encoding_formats.py`，同一批 23 份样本，
payload 统一抽取为元素类型、属性、文字、子节点个数，各编码信息量相同）：

| 编码 | 未压缩 | 占原始 | gzip | lzma |
|---|---|---|---|---|
| XML 原始 | 13,835,860 | 100.0% | 468,773 | 339,188 |
| XML 去空白 | 6,251,557 | 45.2% | 383,996 | 317,516 |
| JSON 完整键名 | 11,727,748 | 84.8% | 429,331 | 329,552 |
| JSON 紧凑（符号表） | 3,518,152 | 25.4% | 353,943 | 305,288 |
| 自定义二进制（LEB128 + 符号表） | 2,565,915 | 18.5% | 346,565 | 303,636 |

自定义二进制在**未压缩**时比紧凑 JSON 小 27%，**压缩后只小 2%（gzip）到 1%（lzma）**。
而且这还是理论上最紧凑的自研编码：变长整数、符号表、无对齐、无版本头、无区段表、无校验码。
真实实现补齐这四样之后，未压缩体积会向紧凑 JSON 靠拢。

原因是紧凑 JSON 已经把键名收进符号表，剩下的差异只有引号、逗号、括号与数值的十进制写法。
这些字节**低熵且高度可预测**，压缩算法本来就近乎免费地吃掉。压缩越强差距越小：
gzip 下二进制领先 2%，lzma 下只剩 1%。二进制省掉的是"语法字节"，不是"信息"。

二进制的真正价值不在这里，而在**解析速度、随机访问与原地更新**（零拷贝、mmap、
FlatBuffers / Cap'n Proto 那一类）。这三条在本项目都不成立：文档量级是几百 KB 到几 MB，
元素表在内存里毫秒级建好，解析根本不是瓶颈；编辑走增量，也不需要每次全量序列化。

代价却是实打实的：无可读性（出问题只能 hexdump）、无 git diff、跨版本加字段要处理前向兼容、
端序与对齐各是一类 bug，而且 WASM 与 JS 两端要各写一遍编解码器——这是最容易出现
"同一份文件两端解读不一致"的地方。

分档建议：

- 本期：JSON（扁平元素表）+ 压缩容器。压缩不只是省空间，IO 少意味着加载更快。
- 真要二进制：用 **CBOR 或 MessagePack**，不要自研。它们与 JSON 同构、可无损转回 JSON 打印、
  两端都有成熟库，能拿到解析速度而保留可调试性。
- 只有出现可测量的瓶颈（单文档超过几十 MB、或高频全量同步）才考虑
  FlatBuffers / Cap'n Proto 这类需要 schema 编译的方案。

### 4.6 双宿主与验证面：native 留在哪一侧

**定位**：wasm 是交付物，native 不是。native 存在的理由是当**验证宿主**——它承担
522 项断言（`heditor_edit_tests` 467 项、`heditor_tests` 55 项），而且不需要浏览器。

**为什么不是"砍掉就完事"，三个数字说话：**

- **两边的断言是分层关系，不是重复。** C++ 侧的 522 项里有大量循环采样式的地毯覆盖
  （光标命中测试就是"横扫 x ∈ [118.3, 220.5]，采样 205 点"这种形状），在原地跑是毫秒级，
  逐条走调试协议问会慢几个数量级。浏览器探针 `edit_probe.mjs` 有 192 个断言点，
  管的是真实指针事件、宿主按键处理、画布上屏，以及真正的 Skia 光栅；
  native 管算法级的穷举与几何。
- **核心判据已经两边都有。** `auditLayout` 与 `auditFrame` 已通过 wasm 导出，
  并已在 `edit_probe.mjs`、`stress_probe.mjs`、`web/app.js` 里被调用。
  所以"与全量一致"这些可证伪判据**不依赖 native**；native 提供的是更快的迭代与
  可调试性（断点、栈、性能剖析），不是判据本身。
- **native 是第二把尺子。** `HEDITOR_USE_SKIA` 只在 wasm 有效，native 一律走自写
  `bitmap.cpp`。两个独立光栅实现互为对照；砍掉 native 就只剩 Skia 一个实现，
  没有东西能独立地证明"这一帧是对的"。

> ★ 2026-10-19 追记：上面"第二把尺子"那条**已撤回**。native 现在链接 x64 版 Skia
> （`scripts/build_skia_native.ps1`），两侧共用 `bitmap_skia.cpp`，`bitmap.cpp` 已删除。
> 理由是跨后端像素比较本来就没有判据效力（见 `docs/依赖与工具链管理.md` 第七节），
> 而"两套光栅器都对"这件事没有可证伪的形式；合成一套之后 native 单测跑的就是线上实现。
> 逐像素判据仍然只在同一构建内算数，跨构建比较走浏览器探针。

**边界（要收窄的部分）：**

- native 只做验证宿主：**新功能不得只在 native 上实现**，否则它从宿主变成了第二个产品。
- 光栅只有一个实现（`bitmap_skia.cpp`），两侧都链接它。再引入第二个后端不在
  "减少重复"的例外之内 —— 它带不来判据，只会带回来两套需要同步的像素账。
- 内存布局类诊断（`heditor_abi_probe` 打印 `sizeof` 与 `EditStats` 字段偏移）天然属于 native，
  不在 wasm 上复刻。

**什么条件下才该砍掉 native**：native 工具链的维护成本持续高于它的收益
（换台机器就构建不起来、或 CI 上跑不了）。那时把像素与几何断言整体搬到
"wasm + node"——测试代码本身不依赖浏览器（`tests/*.cpp` 里只有一处提到 Skia，
且只是注释），所以这条路技术上可行。代价是丢掉 522 项断言的现成覆盖与独立光栅对照，
并接受每次迭代都要重编 wasm。这是一次有真实代价的取舍，不是顺手的清理。

### 4.6.1 Web 侧的两套宿主：in-thread 做行为法器，Worker 做产品主线

上面那笔账（谁是交付物、谁是验证宿主）在 Web 侧还有一个同构的版本。引擎只有一份 wasm，
但**宿主有两套**：

| | 单线程宿主 | Worker 宿主 |
| --- | --- | --- |
| 文件 | `web/index.html` + `web/app.js` | `web/worker.html` + `web/worker_host.js` + `web/engine_worker.js` |
| 引擎住在哪 | 主线程内 | Dedicated Worker |
| 门面 | 同步取值器 | 一律异步 + 镜像热读 |
| 画布 | 宿主自持 `<canvas>` | `transferControlToOffscreen` 交给 Worker |
| 规模 | 80 KB / 1704 行 | 48 KB + 32 KB / 1021 + 707 行 |

**共的是什么（这是"共存"能成立的前提）**：

- **对外同一个门面名**：两个宿主都把 `window.__heditor` 指向自己（`app.js:1181`、
  `worker_host.js:1016`，后者那句注释的原文就是"同名：两个宿主对外是同一个门面形状"）。
- **同一份 wasm 产物、同一套探针**。`edit_probe` / `stress_probe` / `web_probe` 三套在两边
  都能跑全绿（`worker_probe` 测的就是传输层，只在 Worker 侧有），这才是"行为等价"的**证据**；
  这件事读代码断言不了。
- **同一批判据口径**：`present()` 的收尾账、`stats` / `editStats` 两本账、`retarget` 的滞回。

**验收（同一份探针文件，两宿主各跑一遍）**：

| 探针 | 管什么 | 单线程宿主 | Worker 宿主 |
| --- | --- | --- | --- |
| `edit_probe.mjs` | 编辑语义、命令、光标、控件、撤销 | 279 项 / 0 红 | 279 项 / 0 红 |
| `worker_probe.mjs` | 传输层本身（消息配对、镜像、脏页重贴） | 不适用 | 63 项 / 0 红 |
| `stress_probe.mjs` | 随机点击后"两宿主同点同结果"的活体对照 | 69 次点击 / 0 不一致 | 69 次点击 / 0 不一致 |
| `web_probe.mjs` | 排版账（页数 / 字形 / 字体 run / 缺字）与逐场景截图 | 6 场景，结构列一致 | 6 场景，结构列一致 |

探针在增长，项数以 2026-10-15 那一轮为准。`stress_probe` 的"0 不一致"另配了反向一半
（`out/_livecheck.mjs` 验"点了确实有反应"）—— 否则"没反应"同样满足 0 不一致。

**形状缺口是量出来的，不是推断的**。`Object.getOwnPropertyNames(window.__heditor)` 在两
宿主上分别是 **79** 与 **93**，同名 76 个。差异三处：

- Worker 独有 17 个，都是宿主专有：`quiesce` / `rendered` / `mirror` / `ask` / `ink` /
  `setScroll` / `syncScroll` / `zoomTo` / `geom` / `heapMB` / `info` / `readyWallMs` /
  `engineStats` / `engineEditStats` / `pageCanvasCount` / `pageCanvasEls` / `pageCanvasList`。
- Worker 缺 3 个。`env` 与 `bracketScope` 是 `app.js` 自己的取值器被带进了门面，
  **没有任何探针碰过它们**（探针里出现的同名项是 `selfCheck()` 与表单装载结果的字段，
  不是门面成员）；`pageCanvases` 是真的形状差异 —— 画布所有权已经交给 Worker，
  它对外报的是 `pageCanvasEls` / `pageCanvasList` / `pageCanvasCount`。
- **一个测量陷阱**：`Object.keys(window.__heditor)` 在单线程宿主上给出 79，在 Worker 宿主上
  只给 66。原因是 Worker 侧有 27 个成员由 `Object.defineProperty` 定义，没给 `enumerable`
  就默认**不可枚举**，而这 27 个恰好是 `stats` / `editStats` / `text` / `controls` /
  `caretReport` / `viewport` 这些热读。按 `Object.keys` 数会得到"少了 13 个"的错误结论。

**为什么一套都不能砍**：

- **`app.js` 是行为法器。** 砍掉它就没有东西能独立证明异步改造"语义没变" ——
  同一份探针在两边全绿，正是"`await` 对普通值是恒等"这条论证的力量来源。它同时是异步宿主
  出问题时的同步对照组：同一份探针挪过去跑一遍，立刻能排除"是不是镜像时序造成的"。
- **Worker 那条是产品必需，不是可选项。** 要支持**第三方 iframe 嵌入**，OPFS 只能走 Worker
  那条：`FileSystemSyncAccessHandle` 只在 Dedicated Worker 里存在；另一条路（`-pthread` +
  SAB）要跨源隔离，而 COOP/COEP 下第三方 iframe 拿到隔离的前提是整条父链都隔离，
  走不通（`Document-Isolation-Policy` 只在 Chrome 137+ 有，Firefox / Safari 未支持）。
- **滚动成本的解法只在 Worker 那条上**：一页一张画布 + OffscreenCanvas 是"滚动由合成器搬、
  不让引擎搬"的前提。

**纪律（与 4.6 对 native 那条同构）**：**新功能不得只在 Worker 宿主上实现**。两边各实现
一遍，就是把 `app.js` 从"法器"变成第二个产品 —— 那是退化成两套产品的第一条缝。

**收口路径不是"永久维护两份"，而是"一个门面 + 两种传输"**：

1. **先定政策**：`worker_host.js` 是产品主线；`app.js` **冻结为行为法器** —— 不再加新功能，
   只保证探针继续全绿。不定这条，两份实现会漂移成两个产品。
2. **再加工厂**：`createEditor(container, { transport: 'in-thread' | 'worker' })`，两个实现
   同一份接口，多出来的只是一个传输层。今天两边是手抄两份同名成员（80 KB + 48 KB），
   上面那 3 个缺口与 27 个不可枚举，正是"手抄"留下的缝。
3. **退役只在触发条件下发生**：当新功能被迫在两边各实现一遍、或单线程那条开始拦路时，
   把它降成"只跑探针的 oracle"，乃至删除。现在它的收益（独立对照 + 同步调试）大于成本。

收口的具体形态、命令表缺口（实测 24 条）与四步迁移判据，见
`docs/一个引擎API与两种传输.md`。那一份给的是"一个 engine API + 一个宿主主体 +
两个传输实现"，并明确保留了 in-thread 的同步读作为对照物。

### 4.6.2 宿主工厂与错误降级：一个容器一份实例，失败必须看得见

4.6.1 收口路径的第 2 步（"再加工厂"）已经落地了一半，这里记下落地后的形状与剩下的差距。

**工厂形态**（两个入口，不是一个 `transport` 选项）：

| 入口 | 文件 | 谁来调 |
| --- | --- | --- |
| `window.createEditor(container, opts)` | `web/app.js` | 单线程实例 |
| `window.createWorkerEditor(container, opts)` | `web/worker_host.js` | Worker 实例 |

自动启动的口径：两个文件末尾都判 `window.__heditorAutoBoot !== false && document.getElementById('stage')`，
成立就把容器取成 `document.body` 起一个实例（Worker 侧同时挂 `__wheditor` 与 `__heditor`）。
**多实例页面必须在加载这两个文件之前写 `window.__heditorAutoBoot = false`** —— 演示页里
`#stage` 一定存在，这个判断挡不住多实例页面。

`opts` 只有两项：`chrome`（默认 `true`，是否接管工具条元素；给 `false` 就只接编辑器本体：
舞台 / 页容器 / 输入层）与容器本身。

**多实例能成立的三条前提**：

- **元素查找限定在容器内，再回落到整页**：`root.querySelector('#' + id) || document.getElementById(id)`。
  回落是给演示页用的（工具条在容器外）；容器内查找是多实例用的。所以
  `#stage` / `#pages` / `#ime` / `#bar` / `#scenario` / `#zoom` / `#status` 在同页重复出现是
  **有意的**，不是标记写错。
- **容器必须 `position: relative`**：错误横幅是绝对定位的，落在自己那一块里。多实例页面上
  "是哪一个实例坏了"能不能分清，就取决于这一条。
- **两个宿主文件各自包一层 IIFE**：同页同时加载 `app.js` 与 `worker_host.js` 时，顶层
  `const FONTS` / `DPR` 重名会让**整份**脚本以 `SyntaxError: Identifier 'FONTS' has already
  been declared` 拒绝执行 —— 症状是后加载的那个工厂是 `undefined`，而不是某一处行为不对。

**标记契约在两处不同（写宿主页时必须知道）**：

- **输入层的挂法**：单线程那侧把滚动位移**加在**坐标上，输入层必须在滚动容器**内部**；Worker 那侧把
  滚动位移**减去**，输入层必须是滚动容器的**兄弟覆盖层**。
- **画布水平居中是谁的责任**：单线程宿主的画布在 `#pages` 里绝对定位、`left: 0`，**居中要由宿主页的 CSS
  给**（`#stage { display: flex; justify-content: center }` + `#pages { flex: none }`，`web/index.html`
  就是这么写的）；Worker 宿主**自己算画布左边距**，它的画布全是绝对定位，页面给的居中样式落不到它们身上。
  给 in-thread 宿主写宿主页时漏掉这一条，症状是"页面贴在左边"。

**错误降级（`web/host_error.js`，两宿主共用）**，两档，判据是"引擎还能不能用"：

| 档 | 触发 | 界面 | 之后的行为 |
| --- | --- | --- | --- |
| `fatal` | Worker 脚本自身出错；`where` 以 `boot` 开头（取不到胶水、实例化抛异常、首帧排版失败）；宿主处理引擎状态时抛异常 | 常驻横幅 `role="alert"`，带 detail / hint / 重试按钮；容器加 `data-host-fatal="1"` | `dead = true`：命令不再发出，挂起调用当场 reject（写明"命令 X 未发送"），`quiesce()` 直接返回真 |
| `warn` | 某一条命令 / 查询 / 视图操作失败 | 自动消失的提示条 `role="status"`，同类 800 ms 内合并，最多 4 条堆叠，6 秒后消失 | 记账后继续；`dead` 保持假 |

界面元素一律带 `data-host-error="fatal|warn"`，`hostErrors` 句柄暴露 `entries` / `counts` /
`fatalActive` / `bannerText` / `bannerDetail` / `toastTexts` / `element` —— 这些是给探针取证的，
不是给人看的。`dead` 之后 `quiesce()` 直接返回真，是因为屏障自己抛异常会把真正的失败原因
盖在下面。

**验收**：

| 探针 | 管什么 | 结果 |
| --- | --- | --- |
| `scripts/error_probe.mjs` | 两档降级 + "失败之后编辑器仍可用"的反向一半 | 单线程 19 项 / 0 红，Worker 19 项 / 0 红 |
| `scripts/multi_probe.mjs` | 同页三实例（A、B 单线程 + C Worker）的独立性、隔离性、可拆性 | 30 项 / 0 红 |
| `web/multi.html` | 三实例的活体页面（也是手工调试入口） | 三份都起、无横幅、无页面异常 |

`multi_probe` 的"可拆性"那一组是这一层最值钱的判据：`dispose(A)` 之后 A 不再报告内容、
自己的画布从文档里摘掉、自己的错误界面也抹掉，而 B 照常能编辑且记得自己的缩放、C 照常可用。
只验"能开三个"不构成证据 —— 共享了状态的实现同样能开三个。

**与收口路径第 2 步还差什么**：现在是两个函数名（`createEditor` / `createWorkerEditor`），
不是文档里写的单一 `createEditor(container, { transport })`。不合并的理由是合并会引进一层
转发，而两边的差异远不止一个传输层（元素查找、输入层挂法、呈现路径全不同）；**要合并的
是门面形状，不是宿主实现**，而门面形状已经对齐（4.6.1 那张缺口表就是对齐的度量）。这一步
留给"门面契约固化"那一轮一并处理。

### 4.7 源码组织：先拆文件，后拆类

`src/core/engine/engine.cpp` 一度是 2295 行、承载 120 个方法的单一实现文件。已经处理过一轮，
但方式值得写下来 —— 因为它**只拆文件、不拆类**，而这一步与后面的拆类是两件事。

**已经做的（机械搬迁）**：按职责把实现分到五个文件（排版调度、呈现、审计判据、诊断、门面），
`EditorEngine` 仍是同一个类 —— 成员函数在哪个 .cpp 里定义不改变类的结构。
跨文件共用的三个自由函数（`Clock` / `msSince` / `quantPt`）提到 `core/utils/`，
公共头里的 `EngineConfig` 与 `EngineStats` / `EditStats` 各自独立成头。
判据是"数字一条不变"：522 项断言、逐像素帧审计、探针断言点全部照旧。

**为什么只拆文件、不拆类**：那 120 个方法里，编辑操作、光标、控件合计 847 行
**即将被替换或重写** —— 编辑操作要变成命令层（阶段 2）、控件要换成 `ContentControl`、
光标要跟着流位置一起改。现在为它们设计接口，而接口的输入（文档模型与排版结果的形状）
本身还在换，等于**为一份马上要改的东西定边界**。这类边界比不拆更糟：它看起来有条线，
实际上拦不住任何改动，还会让后来者以为那里是稳定的。

**保留的那部分暂时不适合拆类，原因是依赖面**：`presentInternal` 直接读十个以上的私有成员
（底图、帧、排版结果、统计、字形缓存）。要把它做成独立的渲染器，得先定义"绘制需要哪些输入"，
而这份输入的形状由**排版结果的形状**决定 —— 那正是阶段 1（文档模型替换）与阶段 4
（行内原子）要改的。顺序只能是先定形状、再切依赖。

**正式拆分的时机与目标**，每一步的前置条件都是"接口的输入已经定下来"：

| 做完哪一步 | 拆什么 | 拆成什么 | 状态 |
| --- | --- | --- | --- |
| 阶段 1 文档模型替换 | 编辑操作、缩进 | 命令层 `EditCommand`（见 4.4） | **已落地**（2026-10-18） |
| 阶段 1 | 光标、命中测试 | 选区与位置解析（`CaretResolver`） | **已落地**（2026-10-18） |
| 阶段 4 行内原子 | 绘制 | 渲染器 + 一份"绘制输入"结构（排版结果形状定了） | 等阶段 4 |
| 阶段 5 表格 | 控件查询 | 控件索引（`ContentControl` 定了之后） | 等阶段 5 |
| 阶段 6 序列化 | 引擎门面 | 宿主门面只做转发与版本化 | 等阶段 6 |

**完成判据可证伪**：`EditorEngine` 的每个公开方法都只剩一到三行、把调用转给真正的实现类；
出现"在门面里算东西"就是没拆干净。

**已落地的一刀：行内原子（阶段 4）。** 图片与公式在流里各占一个位置、各是一个不可断的盒子。

- **模型层**：`ImageSpec`（资源标识、原始像素宽高、DPI、显示尺寸 `Length`、定位与环绕两个
  枚举）与 `FormulaSpec`（表达式、排版后端、显示尺寸），挂在 `Node` 上，只对各自的种类
  有意义。不变量加一条"结构.原子的尺寸可定"：图片不能既没有正的原始像素、又没有非自动的
  显示尺寸 —— 那时排版给不出宽度，只能凭空猜。序列化与 `NodeSpec`（撤销要搬子树）同步补上。
- **编译层**：`Image` / `Formula` 各产一枚 `InlineObject`（`kind = Atom`），盒子的宽高在这里
  定死（EMU → 磅的唯一一次换算）：优先用作者给的绝对显示尺寸，只给一边时按原始宽高比推
  另一边，两边都没有时按像素与 DPI 折算。公式两边都缺时按表达式估一个框 —— **估的是框，
  不是公式的排版结果**。
- **排版层**：原子用它自己的盒宽（不再按括号字形算），`break_after` 为真（它与一个全角字
  同价）；盒高进行度量，行高取"字号 x 行距"与盒高的大者 —— 行距是正文行的排版倍数，不是
  盒子的属性，一张 200 磅高的图不该被撑到 320 磅。竖排与空段落两条分支同样处理。
- **引擎层**：`BracketCounts` 按"开括号 / 非开括号"分桶（原子记进后者），于是
  `closes + opens` 恒等于这一处压着的对象总数，侧别上界与"跨过这一处所有对象"的偏移都
  不必再单独记一个总数；**原子不被"显示哪些括号"的名单筛掉**（它是内容，与光标状态无关），
  后缀复用也不把它当成"端点会动的占位"（它的锚点是段内码点、几何是自己的宽高）。
- **绘制**：底图里画**显式占位框**（边框 + 极浅底色 + 框里写资源标识 / 表达式，放不下就
  截断）。不做伪渲染：把表达式按普通文字画出来会得到错误的字距与上下标，比一个明确的框
  更危险。行指纹混进原子的种类与内容指纹 —— 几何看不见的那类变化（换了一张同样大的图）
  靠它才重画。

**判据**：`shaping_test [8]`（+9 项）管排版那一半 —— 宽度真进了行宽、高度真进了行盒（各有
反向一半）、窄行里原子整枚换行、超宽原子独占一行且不产生空行、空对象表与加原子之前逐字段
相同；`edit_test [44]`（+15 项）管引擎那一半 —— 原子进块流、后缀里带原子照常复用、
`auditLayout` 与 `auditCompile` 全 0；浏览器 `out/_atom.mjs` 管绘制那一半 —— 底图里真的
出现了那个边框色与底色（换到无原子场景必须回到 0）。**注入旧行为当场红**：忽略盒高红 3 条、
忽略盒宽红 4 条。

**已落地的一刀：表格（阶段 5）。** 表格是第一个容器元素，它不是"多一种行内对象"，而是
"块流里多一层归属"。六层各自的落点：

- **模型层**：`CellSpan` 就地扩成 `CellSpec`（跨度 + `v_align`），新增 `RowSpec` 挂在
  `TableRow` 上（允许跨页断行、标题行、行前强制分页、行高三档），`TableSpec` 补宽度与对齐、
  **删掉 `header_rows`**。标题行因此是逐行开关，几个标题行降为派生量 `headerRowCount`，
  并新增不变量"标题行必须是从第 0 行起的连续前缀"——逐行开关允许标出坏形状，只有前缀有意义。
- **编译层**：表格走扁平化 —— 格里的内容照常编成段落，每块带一条 `cell_path`（外层到内层，
  嵌套表格就是路径更长一条），单元格是段落边界（进格前先落当前段）。产物另附 `LayoutTable`
  （网格尺寸由跨度推、行属性、列宽、每格的块区间）。**表格不再记"尚未进入编译"的诊断。**
- **排版层**：格矩形定行内起点与可用宽度，断行、行高、行盒放置全部复用同一条代码路径 ——
  只有 `cur_cx` / `cur_cw` 是变量。行高在行末结算（`内容高 + 上下内边距` 与显式行高取大）。
  跨页按行记录的开关分两档：允许断行的按行盒切片（切点落在行与行之间），不允许的整行挪到
  下一页；整行换页时这一行已写下的行盒与字形一起平移。
- **引擎层**：`tables_` 随编译产物落地并传给排版；**有表格时不做任何增量**（续排与后缀复用
  都假定"排版状态只有页号、块轴位置、行数三个标量"，表格还有"第几行第几格"）。块起点的
  递推要多一步：上一块标记之后与本块第一个内容元素之间可能夹着格边界，取两者的较大值。
- **绘制**：底图里按每个格自己的外框画线（合并格内部因此不会多出线），跨页片段的切口那条边
  按 `cont_top` / `cont_bottom` 跳过 —— 看起来是裁开的，不是被分出一条线。
- **光标与命中**：行盒坐标就是页面坐标，格与格之间只是空隙 —— 光标、命中测试、选区都沿用
  既有实现，没有为表格开特例。

**判据**：`model_test` +33 项（属性默认值、标题行前缀正反两半、序列化往返、编译产物的路径
与结构表、嵌套表格、表格夹在段落中间）；`shaping_test [9]` +28 项（2x2 的列位置、格内断行、
行高三种规则、显式列宽、表宽百分比与居中、跨页切片的正反两档、不传结构表时的反向一半）；
`edit_test [45]` +17 项（装载、路径、格内编辑、增量被禁、撤销）。**注入旧行为当场红**：
标题行前缀不变量失效红 1 条、序列化丢 `is_header` 红 2 条、格内不落段红 5 条、格内用页宽
红 2 条、禁掉行拆分红 1 条、块起点递推退回旧口径红 1 条。

**这一刀明确不做**：`TableStyle`（边框、底纹、单元格边距仍走引擎配置常数）；标题行重复
（模型与编译已就位，重复显示要在产物里复制行片段，而"命中重复副本落到哪里"这条规则还没定，
设计文档第九节已标为未定）；竖排文档里的表格按整页宽排（不做静默的错误格布局）；
`setTableRows` / 行标识 / 行模板这一半动态表格。

**没做的、以及为什么**：图片的字节与公式的排版后端都不在本期。前者要等二进制资源外置
（阶段 6 的包容器），后者是另一件工程 —— 所以两者都画占位框，框里写清它是什么。定位方式
与环绕方式只留了枚举：浮动的断行核心是"每行可用宽度随浮动框变化"，与现有"左右边界是常数"
的假设冲突（第十一节末尾）。

**落地后修掉的两个缺陷**（都由演示页暴露，见 TRAPS 89 / 91）：

- **绘制侧把"不是闭括号"当成了"开括号"**。`drawControlMarks` 的
  `open = (bracket_side != Close)` 在只有两个枚举值时是对的，而原子占位簇的
  `bracket_side` 是 None ⇒ 每枚原子左边长出一枚开括号。改成正向判据 `== Open` 并显式
  挡掉 None；`LineCluster::bracket_side` 的注释也跟着改（原文反向读就是"占位一定是括号"）。
- **`demoTree` 没按锚点切文本**。段落没有 runs 时"取 run 边界"把整段取成一个窗口，
  于是原子全被推到段尾。判据：`edit_test [44]` 量 `demoTree → compile` 之后的 cp，
  `out/_atom.mjs` 量槽表里的 cp。
- **原子删不掉**。删除是一条白名单：产步骤的只有文本与段落标记两条，而原子占流位置却不产
  步骤 —— 选区里只要有一枚原子，`eraseFlowSteps` 的安全阀（覆盖长度必须等于区间长度）就把
  整条编辑拒掉；单键那一路走的是文本坐标，而原子没有码点，连"删它"都说不出来。现在模型层有
  按流位置寻址的 `makeRemoveAtom`，命令层有"原子那一条"（选区）与 `eraseAtomBeside`
  （退格 / 前删紧邻的那一枚）。
- **行高把行距吃掉了**。原先写的是 `max(字号 x 行距, 盒高)` —— 盒子撑高的是内容，而行距是
  段落属性，两者该相加：正解是 `max(行距, 内容高 + 行距 - 文本高)`。只取大者时带原子那一
  行的下一行会贴着盒底排（实测两行行盒重叠 4 磅，视觉上就是"那一行的行距没了"）。竖排的
  列宽同一条规则。判据：`shaping_test [8]` 与纯文本对照段比"行间空隙"，`out/_atom.mjs`
  在敲字折行之后量"相邻行盒不重叠"。

**已落地的第二刀：命令层（`src/core/engine/edit_command.h` / `edit_command.cpp`）。** 拿走的六族：

- **插入** —— `insertCodepoints` / `insertCodepoint` / `insertTextUtf8` / `typeTextUtf8`（含
  "选区非空 ⇒ 替换选中内容"与"沿用落点左侧的字符格式"）；
- **删除** —— `backspace` / `deleteForward` / `eraseOnTree`（含控件边界上的四条规则
  `bracketBackspace` / `bracketDeleteForward` 与 `controlFlowSpan` 一族）；
- **跨段** —— `splitParagraph` / `mergeParagraphInto` / `mergeWithPreviousParagraph` /
  `mergeWithNextParagraph`；
- **缩进** —— `indent` / `outdent`；
- **结构操作** —— `removeControl` / `setControlProp`；
- **选区删除的公共前缀** —— `planEraseSelection` / `commitErase` / `replaceSelectionWithText` /
  `eraseFlowSteps`，以及落点判定 `policyAt` / `policyErase` 与 `marksAtFlow`。

**没拿走的、以及为什么**：

- **编译产物的重建**：命令只把事务交出去（`EditHost::commitEdit`），重建与标脏归引擎 ——
  那是"树 → 块流 / 流索引 / 控件集合"的活，与"这次编辑该发哪些步骤"不是一件事。
- **`loaded_`**：`removeControl` / `setControlProp` 的"装载过没有"留在门面。命令层只管
  "编辑怎么做"，"有没有可编辑的东西"是引擎的装载状态。
- **`markAllLayoutDirty`（hidden 改了呈现态流结构）**：由 `setControlProp` 的返回值
  （`PropResult::Structural`）带出去，引擎据此标脏 —— 命令层不碰排版。
- **`setControlPropAndRender` 的"幂等就别重排"**：同样靠 `PropResult::Unchanged` 表达，
  于是引擎不必再自己去读一遍旧值（原来那个匿名命名空间里的 `readPropValue` 因此只在命令层
  留一份）。
- **排版、绘制、帧与窗口、控件查询与光标移动**：与编辑无关。

**输入与出口是两个接口**（`EditView` / `EditHost`）：命令层不持引擎指针。`EditView` 存的是
容器地址（与 `PositionView` 同一套办法），`EditorEngine` 私有继承 `EditHost` —— 事务出口是
一次虚调用，不是 `std::function`（编辑是每次按键都要走的一步）。
★ 一个连带的搬迁：`ParaDelta` 原先嵌在 `EditorEngine` 里，命令层要构造它就得把它提到
`edit_command.h`（命令层不该反过来 include 引擎头）。

**判据**：三套 native 断言一条不改、全绿（`heditor_tests` 104、`heditor_edit_tests` 1129、
`heditor_model_tests` 809），浏览器串行探针全绿。`engine.cpp` 2178 → 1373 行，
`edit_command.cpp` 881 + `edit_command.h` 370。

**已落地的一刀：选区与位置解析（`src/core/engine/caret.h` / `caret.cpp`）。** 拿走的四样：

- **位置代数** —— 流位置与文本坐标的互换、侧别与归属提示、括号统计、簇吸附；
- **选区与光标状态** —— 两端、行别、上下键的列位、光标条宽度，外加 `setCaret*` 一族；
- **行盒几何与命中** —— 行盒查找、光标矩形（页面磅）、选区矩形（页面磅）、按页二分；
- **光标移动** —— 方向键、行首行尾、文档首末、上下键。

**没拿走的、以及为什么**（边界要写下来，不然它会自己长回去）：

- **帧像素与帧槽偏移**（`caretRectPx` / `selectionRectsPx*` / `selectionRectsVisible`）：
  那是呈现侧的窗口换算，解析器只到"页面磅"为止。
- **`hitTestPt` 留在引擎**：它要 `cfg_.zoom`、`pagePxHeight()`、`pageGapPx()` 与连页标志 ——
  页像素步距是"宿主把页摆在哪"的约定，不是位置解析的输入。行内那一半（`hitTestInLine`）
  已经拿走了，所以留在这里的只剩"像素点 → 哪一行"的呈现侧换算。
- **重排触发**：聚焦档下"显示哪些括号"由光标位置决定，移动光标可能换占位集合 ⇒ 要重排，
  而 rel 与簇吸附都按排版结果算。所以移动族的公开入口在引擎侧是 4~6 行：记计划 id →
  调解析器 → 按需重排 →（行首行尾还要）按新簇表再投影一次。解析器自己只算位置，不触发重排。
- **编辑落笔、编译重建、绘制、审计**：与位置解析无关。

**输入是一份只读视图**（`PositionView`）：段文本与两张对象表、块起点与跨度、流索引、控件集合
与节点 id、id→下标表、排版结果。解析器不持引擎指针 —— 多要一样就得改这个结构，依赖面在
编译期看得见。视图只存这些容器的**地址**，而它们都是引擎成员、不换对象，所以摆一次就够
（`init` / `setDocument` / `rebuildFromTree` / `relayout` 各摆一次是保守做法）。
★ 一个必须记住的坑：流索引是"重建时 emplace 进去"的，所以视图要持 `std::optional` 的地址
而不是它内容的地址 —— 持内容地址会在第一次重建时拿到空指针，并且一直空下去。

**判据**：三套 native 断言一条不改、全绿（`heditor_tests` 104、`heditor_edit_tests` 1129、
`heditor_model_tests` 809），浏览器串行探针全绿。这是"只搬不改"的那一类拆分，所以判据就是
"数字一条不变"。`engine.cpp` 从 2903 行降到 2201 行，`caret.cpp` 877 行 + `caret.h` 369 行。

**目录约定**：`src/core/` 下的子目录对应实现层（`text` / `render` / `layout` / `doc` /
`engine`），`utils` 放跨层共用的纯工具与基础类型（无领域语义：哈希混合、UTF-8 解码、
计时、长度量化）。有领域语义的头不放 utils —— 书写模式（`InlineAxis` / `BlockFlow` /
`TextOrientation`）因此归 `text/`。缺的三层（命令层、序列化、宿主门面）**不预先建空目录**：
空目录不承载任何约束，只会让人以为那里已经有东西。

### 4.8 呈现的粒度：帧是视口窗口，画布是一页一张

**问题**：帧缓冲原来等于"整篇一张位图"。200 段（16 页）在 1.5 倍缩放下是 893 × 20523 =
18.3 Mpx，3000 段（64 页）是 893 × 82155 = 73 Mpx —— 后者光引擎自己那两张位图
（`base_` + `bitmap_`）就要 587 MB wasm 堆，而且帧高远超 GPU 纹理上限 16384。

**判据是量出来的，不是推出来的**（`scripts/diag_perf.mjs`）：同一串敲字，把画布
`visibility:hidden` 再跑一遍 —— 引擎侧与 `putImageData` 完全没变，只有浏览器不再合成它。
18.3 Mpx 时帧间隔 **33.3 ms → 16.7 ms（差整整一个 vsync）**；1.13 Mpx 时差 **0.0 ms**。
这一笔**不在任何引擎计时里，也不在 `putImageData` 里**（后者是惰性的：拿 73 Mpx 与
1.13 Mpx 的画布贴同样一小块，都返回 0.000 ms），只能这样做对照才看得见。

**做法**（引擎侧只是加法，默认行为逐字节不变）：

- `EditorEngine::setViewportAnchor(first, count)`：`repaint()` 只呈现
  `[first, first+count)` 这几页。`count <= 0` 表示整篇，即原来的行为 ——
  单测与既有探针因此一行都不用改。
- `dirtyPages()`：本轮写过哪几页（绝对页号）。口径与原来那份上屏 bbox 完全一致
  （同一批矩形算出来的），但比"脏页数"更准 —— 光标与表单标记画在帧上、不进底图，
  它们所在的那一页同样要重贴，而页指纹里没有这两样。
- `EditStats::window_pages` / `window_first_page` 与 `total_pages` 分开：
  `total_pages` 是**文档**页数（"脏页 / 总页"的分母必须是整篇，否则恒等于 1），
  帧里那几页看 `window_pages`。
- 宿主（`web/app.js`）：`#stage` 是滚动容器，`#pages` 撑出全文高度，窗口内每页一张
  `<canvas>` 绝对定位。上屏用 `putImageData` 的源矩形切片
  （`putImageData(img, 0, 0, 0, k*step, pw, ph)`），零拷贝。

**窗口怎么定**：可见页 ∪ 光标页，封顶 `MAX_WINDOW` 页，并且**带滞回** ——
现有窗口只要还盖得住就不动它。没有滞回的话，光标一路往下打字、可见页一格一格地换，
每换一格就整帧重建一次（一页约 13 ms），手感是"每隔十几个字卡一下"。
换文档之前必须先把锚点摆到开头（`presetWindowForLoad`）：顺序反了的话第一次重排
会按上一篇文档留下的锚点栅格化，随后再挪一次窗口重排，"装载花了多少"被后一次覆盖掉。

**效果**：扫 zoom（1.0 / 1.5 / 2.0 / 2.5 / 3.0，帧 1.01 → 9.10 Mpx）实测，帧间隔
**不再随画布面积走**，只由单拍操作耗时决定；合成那一笔在 4 档上都是 0.0 ms。
3000 段（116 页）的帧从 73 Mpx 降到 3 页 / 3.4 Mpx。

**另一半（已做）**：单拍操作里还有 13~20 ms，其中**字形光栅占 7~13 ms** ——
wasm 走 Skia，整页约 1000 个字形每帧从头画一遍，**改一行与改一页同价**。
按"页指纹 → 行指纹"的同一套路子把它收到行粒度：行指纹（含行盒几何、簇表、这一行的字形）
与页指纹在同一次遍历里算出来，增量分支据此找出**连续的一段差异行**，只重画那一条带，
帧也只贴这条带。带边界取**与相邻行盒的中线**（不是行自己的 ascent/descent ——
个别字形的墨迹会探出去），且取新旧两版里更靠外的那个；页边框每次补画
（带底色的填充会擦掉它一条，实测差的正是 `2×(893+1263)-4 = 4308` 像素）。
竖排页退回整页重画（行盒的块轴在竖排下是横轴，行带会变成竖条）。

**两刀合起来**：200 段 / 16 页 / 1.5 倍下，单拍操作 **21.2 → 5.0 ms**，
**帧间隔 33.3 → 16.7 ms（30 拍 0 慢帧）** —— 持续按键与退格不再卡。

**第三笔：整窗重画一次太贵**（回车那一格）。行带之后剩下的怪兽是"行数一变，
编辑点以下每一行都要重新定位"⇒ 整窗的页内容跟着移位 ⇒ 整窗重画。此时花钱的不是
"该不该重画"（确实该），而是**重画一次太贵**：光栅器的入口是**一个字形一次调用**
（Skia 侧每次都要新建 SkPaint、装配一遍字形运行、算一遍包围盒），一页约 700 个字形的
固定开销就是整窗重画里几十毫秒的来源。收口在 `Bitmap::drawGlyphs`：同一字体 / 颜色 / 朝向攒成
一段，一次交出去（`drawGlyph` 退化成 count=1 的壳 —— 两条入口只能有一条实现）；
包围盒也改用批量重载一次取完。宿主侧配套**画布池**（换窗口时复用页画布，省掉
重新分配 backing store 的那 1.2~2.7 ms/张）。

结果：回车 **48.7 → 22.9 ms**（paint 40.7 → 13.6）、装载 200 段 **190 → 100~105 ms**、
快速滚动帧间隔 **p50 50 → 16.7 ms**（慢帧 10/12 → 4/12）。

**第四笔：段数变化也走后缀复用**（2026-10-14）。回车/退格合并一个字都没改内容，
只是段边界挪了 —— 原来 `relayout` 里有一道门禁止后缀复用（判据"第 from+1 段开始时的状态
与上一轮相同"，而段号一变"第 from+1 段"已经不是同一段）。判据本身没错，错在只认那一种情形。
打开之后：脏区在新旧两版里各占几段由"段落数的变化只可能来自插入或删除一枚段落标记"这条
规则给出（窄的那一侧恒为一段），段表按增量挪槽位、行盒与字形的段号跟着整体平移。
10000 段实测 **361.7 → 66.8 ms**（排版 330 → 10.4 ms）。

**第五笔：页指纹从 O(文档) 变 O(1)**（2026-10-14）。上一笔之后剩下的最大一笔是页指纹：
它要判断"这一页的画面还对不对"，而在**后缀整体平移**那一级，后缀在的每一页内容都跟着挪了 ——
这个答案在进那里之前就已经确定，可原来还是把整条后缀的字形逐页哈希了一遍
（2000 段 21.1 ms、10000 段 33.9 ms，比排版本身贵一个数量级，而"回车/合并/敲到换行"每一下都付）。
收口在 `markPagesChangedFrom()`：只标脏、不算哈希（标脏值的高位是保留的哨兵位，
真指纹一律清掉它 ⇒ 标脏值与真指纹编码上不相交；低位按底图那一版翻一下 ⇒ 连续两次标脏
不会读成"没变"）。续排路径（没有后缀可复用，例如在文档末尾敲字）也从"整篇重算"
改成按"脏段新旧两版更靠前的那一页"框范围。顺带把 `EditStats::total_ms` 的口径补齐
（它原来不含 pageFp：面板显示"合计 18 ms"而操作实际 39 ms）。

效果：2000 段回车·中段 **66.0 → 34.4 ms**（pageFp **21.1 → 0.0**）、回车·末段 21.4 → 14.8、
末段敲字（3000 段）14.4 → 6.4。★ pageFp 现在**与文档规模无关**（10000 段也是 0.0），
剩下的 paint 在 2000 / 10000 段完全相同（21.6 ms）—— 它只由窗口那 2 页决定。

**还剩的一条**（不在同一条线上）：
**行级位图平移** —— 页边界是整数像素，窗口平移好办；但回车那种页内整体下移是小数像素，
平移与从零重画的抗锯齿会差一堆像素，而"增量帧 == 从零重画的帧"是硬判据。
解锁前提是让字形的纵向位置落在整数设备像素上。它换来的是"回车再快一档"：
现在回车 34.4 ms 里 paint 占 24.5，全是"窗口那 2 页整页重画"（改一行与改一页同价），
而这 2 页的内容其实只是**整体下移**。


## 五、迁移路线

每一步都要求**可独立验证**，且不改变对外行为，直到该步自己的判据转绿。

**落在文档模型上的各步，其细化与判据以 `docs/文档模型设计.md` 第十五节为准**：
那里的 0.1–1.10 把阶段 0 与后续阶段里属于文档模型的部分拆成可单独转绿的小步
（它的 1.7 表格对应本表阶段 5、1.10 序列化对应阶段 6）。**它的 0.x / 1.x 是本表阶段号
之下的第二套编号，不要与本表的 0–8 混用**；本文只保留粒度与先后。

| 阶段 | 做什么 | 判据 |
|---|---|---|
| 0 | 元素流进段落容器（方案 A 第 1、2 步）：标记先不参与长度账 | 现有单测全绿、帧与全量一致 |
| 1 | 文档模型升为元素流：`BlockSpec` 变成"元素流 + 段落标记 + run 级样式"，`cp_text` 降为派生视图 | 同上，另加"排版输入与旧路径逐字段一致"。**已落地**：六刀（字符格式 run、三层解析进 run、行度量按行与按列、行内对象进块流、控件边界由编译层产出、引擎持树吃编译产物）、第七刀 A/B/C（段落身份与流位置桥接、编辑改在树上落笔、策略改走 `edit_capability`）、演示页切到树上、旧装载路径整个退役、`cp_text` 降为派生视图（引擎侧不再有写入口，只由 `compile.cpp` 从树产出）。见本表后说明 |
| 2 | 命令层：把已有编辑动作（插入/删除/分段/合并）改建为 `EditCommand` | 撤销 N 次回到原状态、帧一致 |
| 3 | 选区 + 剪贴板（选区本身是会话状态、不进文档模型；进模型的是端点形状、位置映射与区间原语） | 选区端点用流位置、带方向；跨段选择往返不变；复制片段始终良构（控件边界成对）；撤销恢复到编辑前选区 |
| 4 | 内联原子元素：图片、公式（公式渲染成**显式占位框**，不做伪渲染） | 断行处不可分割；增量与全量一致。**已落地**（2026-10-18），见本表后说明 |
| 5 | 容器元素：表格 | 单元格内独立排版；跨页行为与全量一致。**已落地**（2026-10-19），见本表后说明 |
| 6 | 序列化：DOM <-> JSON（扁平元素表 + 样式表），二进制资源走包 | `parse(print(doc)) == doc`；落盘无空白、不写默认值 |
| 7 | 三模式行为补齐：表单模式的 Tab 遍历、只读继承、控件聚焦 | 策略单测 + 浏览器探针 |
| 8 | 门面版本化、演示数据搬出 `src/`、测试骨架换成可注册可分片 | 断言一条不改，只换驱动 |

阶段 0 与 1 是地基，不能跳。反过来先做壳（如图片、表格）会白做——
元素的语义刚换过，壳上的差量与序列化都得跟着重写。

**阶段 1 的拆法与进度。** 第一刀（2026-10-12）落在引擎输入：加字符格式 run
（`FormatRun` = 码点区间 + 已解析的字体、字号、颜色、语言、回退链）。排版先按格式 run 切、
再在每段内按字体回退切 —— 两把尺子求交，整形段的边界是两者边界的并集。
两条等价判据：`runs` 为空与显式一个 run 产出同一帧；一个 run 切成 N 个属性相同的 run
产出同一帧（后一条是 ECMA-376 的 w:r 一节给的）。三条反向判据：块级字号与 run 不同时
行宽跟随 run（证伪"还在读块级字段"）、只改 run 字号必须让整形缓存未命中、run 序列必须
恰好铺满段落文本（无空洞、无重叠、不越界）。

★ 第一刀刻意不做的两件事，都写在判据旁边以免被当成已完成：
其一，**行度量仍是块级字段**（`size_pt`、`line_factor`、`space_after_pt`）——一行里字号
不同时，字形与推进按 run 算，行盒高度与基线仍按段级算；`LineBox::size_pt` 当时是个标量，
要容纳行内混排字号得先改它（第三刀改了，见下）。其二，**`cp_text` 仍是文本的唯一存储**
（run 只存区间与属性）。

**第二刀（同日）把接缝接通了**：编译层（`compile.cpp`）现在按三层解析把字符格式写进 run，
那条"文本的字符格式尚未进入编译"的诊断删掉了。做法与三条硬约定：
文本段要**缓存到段落结束才解析** —— 三层解析得先知道本段的段落样式，而段落样式挂在**结束**
这一段的那枚段落标记上，走到文本节点时还看不到它；段落样式链的字符部分一段解析一次
（`paragraphRunBase` + `resolveRunFormatFrom` 把原来的一体式解析拆成两段），否则同一段里
十个文本节点会把"未知段落样式"重复报十遍；run 以**段落默认字符格式**（就是刚解析出来的那组
块级字段）为底、解析结果盖在上面，于是没有字符格式的文本其 run 恒等于它，加 run 之前的行为
逐字段不变。相邻且格式相同的文本段并成一个 run（不并也对，等价判据证明过切分不改产出，
但并起来让 runs 不随模型里节点的切分方式变化）。粗体、斜体、下划线在引擎输入里还没有字段，
**设了就记诊断**而不是静默丢；显式设成 false 不报（那就是引擎的默认行为）。

★ 这一刀之后 `cp_text` 的写入口还在（引擎的编辑操作直接改它），所以"降为派生视图"仍未完成：
要封掉它得让编辑操作改 run，那是后面某一刀的事（第四刀走的是行内对象那条线，见下）。

**第三刀（同日）把行度量按行算。** 上一刀之后混合字号的字形已经按各自的 run 整形，但行盒高度、
基线、行高还是块级那套 —— 24 磅的 run 装在 12 磅的行盒里，大字会溢出到相邻行上。现在横排
**按行取本行所有 run 的最大 ascent / descent / 字号**（`LineBox::size_pt` 因此不再是"块的字号"，
而是"这一行的字号"）；竖排**按列取本列所有 run 的最大字号 / ascent / descent** —— 列宽 = 该列
字号 × 行距，于是混排字号下小字列不再白占大字列的宽度，与 CSS 竖排同一条（列宽就是该列的行高）。
列位因此由前缀和推进而不是乘法：中日从右边缘往左推、蒙文从左边缘往右推，两侧各记一个"下一列的
边缘"；"本列放不下就换带"这一步只能放在这一列的内容定下来之后（列宽是逐列算出来的），而列长与
列宽无关，所以换带之后同一段内容仍然装得下，不必重取。

★ 逐列变宽的前置条件曾经写成"要连列序与页内列数一起重算"，落地时发现没有循环依赖：列长（一列
装多少）与列宽无关，先取内容、再算宽度、再落列位即可。`LineBox` 的字段形状不变（`size_pt` /
`block_lo_pt` / `block_hi_pt` 本来就能表达"这一列自己的范围"），所以引擎侧与绘制侧一处都不用改。
判据在 `tests/shaping_test.cpp` [7]：八列各一个字符、字号 24 与 12 交替，逐列断言"字号 = 本列
最大字号"、"列宽 = 字号 × 行距"、"不越出内容框"、"同页两两不重叠"、"列号小的更靠右"，另加
"大字列真的比小字列宽"这一条对照（取整段最大字号时两者相等，注入旧行为当场两红）与反向一半
（整段一个字号 ⇒ 所有列宽相等，与逐列算之前逐字段相同）。

★ `line_factor` 与段后距**按段落、不按 run**，这是定下来的口径而不是缺口：模型层把它们放在
`ParaFormat`（`para_format.h`），OOXML 的 `w:spacing` 同样是段落属性（`w:pPr` 里），Word 的
行距与段后距也只在段落上设。所以引擎输入里它们留在 `BlockSpec` 的块级字段，不进 `FormatRun`。

★ 这一刀连着抓出两个真 bug，都是"上一刀留下的、只有混合字号才会露出来"的那一类：
其一，引擎侧的增量重排（`engine_layout.cpp` 的 `shiftSuffixBlockAxis`）按块级字号推进后缀的页高，
与排版层不再一致 ⇒ 编辑前一段之后后缀的页号会错位；其二，排版层自己用**基线**累加来推进行
（`baseline += line_h`），而基线 = 行顶 + 本行 ascent —— 混排字号时上一行的 ascent 会串到下一行，
翻页之后落点就错。改成推进**行顶**，并且把"本行放不下"的判定挪到本行度量已知之后（上一行结束时
还不知道下一行多高，拿上一行的高度估会漏判）。判据是一条端到端的：编辑含混合字号文档的前一段，
断言增量分页与整篇重排逐字段一致（`auditLayoutJson` 的 diff 必须为 0）—— 它在修好之前报 10 处。

★ 一个必须先修的构建系统缺口：`heditor_demo` 原先漏挂 `heditor_track_header_deps`，
而 `demo_documents.cpp` 直接构造 `BlockSpec`。改 `layout.h` 的字段就是改它的类布局，
漏挂的后果不是编译错误，而是"静态库的 .obj 用旧布局、测试的 .obj 用新布局"混链 ——
症状是析构时随机段错误，而所有断言都打印 PASS。已补上，并把 `heditor_demo` 的 obj
加进 `scripts/verify_header_deps.ps1` 的期望表（那个脚本自己也在这次被修好了：
它找的是引擎拆目录之前的旧路径，一上来就 throw，所以早就失效了）。
（★ 2026-10-13 追记：那个 `OBJECT_DEPENDS` 余量后来**整体撤掉**了 —— 改一个 core 头要重编
37 个 TU、实测 ~380 s，而从 `ninja -t deps` 反查真实依赖只有 9 个。细粒度依赖交回
`/showIncludes` 轨道本来就是准的：改 `engine.h` 之后重编的恰好是 include 它的那 9 个 obj，

**第四刀（同日）把行内对象写进块流。** 前三刀都在"文字怎么排"，这一刀改的是"段落里除了文字
还有什么"：控件边界从排版接口的一个参数，搬进块流本身 —— `BlockSpec::objects`（`InlineObject` =
锚点码点 + 种类 + 不透明 owner + 只读位）。排版层的签名因此收窄成
`layoutDocument(lib, blocks, page)` / `layoutDocumentRange(lib, blocks, page, from, to, ...)`，
不再收 `ControlSet`，也不再收"要显示括号的那张名单"。这是**方案一（元素流）在引擎输入侧的落点**：
段的行内序列不再只有文本，而是"对象与文本按码点位置交错"，两者共用一套坐标，于是断行、光标、
命中测试、增量都不需要第二套坐标。

产生端暂时还是引擎：`EditorEngine::syncInlineObjects()` 在每次 `relayout()` 之前把"要显示括号的
字段边界"写成对象表（只有引擎认识编辑模式与 `form_brackets`，也就知道哪些字段显示括号）。
**同一处边界上多枚括号的先后（闭的按 depth 降序、空字段成对居中、开的按 depth 升序）从
`layout.cpp` 原封搬到引擎** —— 排序只有这一处，排版层只按数组顺序做一次线性归并，
**不做第二次排序**。这条契约有反向判据：把表倒过来，占位簇的顺序跟着倒。

判据四层：其一，不变量 `objectsOrdered`（cp 非降且不越段长；逆序与越界各报各的位置），
顺序一坏括号层级就画错而画面仍然"有括号"；其二，表为空 == 与"没有表单"同一份几何，
反向那半是"表里加一项，末字右移量必须恰好等于行盒多出来的宽度"；其三，产生端的口径 ——
Focused 档表里只留聚焦字段的两项、文档模式表为空（"不画却还占宽度"是最坏的形态）；
其四，排版层自足 —— 直接调 `layoutDocument`（完全不经引擎）也能插出占位簇，
且 `bracket_side` / `owner_control` / `read_only` 逐项到位。

★ 越界锚点的处理：排版层假定表已合序且锚点不越段长，但真越界时旧实现的线性扫描会把它夹到
段尾、重写成归并循环后则会静默丢掉 —— 丢一枚括号 = 凭空少画一层，比错位更难发现。现在显式
保留"收尾再排一次、夹到段尾"这一步。

★ 这一刀不碰的：控件的**三层缺口**仍在（`compile.cpp` 的 `supported` 不含内容控件，
引擎侧仍跑 `setControls(std::vector<Control>)` 与六处 `adjustControlsOn*`）；产生端仍是引擎
而不是编译层 —— 产出端那一半紧接着由下一刀补上，引擎侧那两处到第五刀末仍未动。
（★ 这两处已在**第七刀 D 段**随旧装载路径一并退役，见本节末的退役清单。）

**第五刀（同日）把产出端搬到编译层。** 第四刀造出了"块流里能放非文字元素"的位置，
往那个位置写东西的还是引擎（`syncInlineObjects()` 从旧的 `ControlSet` 现算）。这一刀把产出端
搬进 `compile.cpp`：`ContentControl` 不再是"尚未进入编译的元素"，而是**边界进内容**的容器 ——
进入它写一枚 `ControlStart`、离开时写一枚 `ControlEnd`，锚点是那一刻"当前段已累积的码点数"。

三条随之而来的结论：

其一，**跨段控件不需要特殊规则**。锚点按"当前段"算，于是控件从哪一段开始、在哪一段结束，
边界就落在哪两段的对象表上，规则只有一条。段落标记落在控件内部时，闭边界自然落到下一段 ——
那两条 0.4 判据现在验的就是它（两段文本各带一枚边界）。

其二，**排序规则消失了**。次序是遍历的自然产物：同一处边界上"到此结束"的闭括号先出现
（离开得早），"从此开始"的开括号后出现（进入得晚），空控件自己的一对紧挨着。第四刀在引擎侧
写的那套 bucket/key/tie 排序因此只剩"尚未迁移的旧路径"在用，编译层这边一个排序函数都不需要。

其三，**owner 是控件的节点 id，不是序号**。序号会在插入一个控件之后整体平移，而命中测试拿到
的句柄要活过重排；节点 id 是身份，不随编辑漂移。

判据（model_test 763 → 784，一节八组）：锚点等于内容的首尾；相邻两控件在共享边界上是
[前一个的闭, 后一个的开]（即 `][`）；空控件的一对锚在同一处、开在前 —— 且"只攒下边界、
既没文本也没标记"的文书照样落一段（少了这条，那对括号连产物都进不去）；三层嵌套的六项边界
用栈验严格配对、owner 由外到内逐层收窄；只读控件的两枚括号都带 `read_only`；隐藏控件在编辑态
照常产边界、呈现态整棵摘除；图片在控件内部仍记自己的诊断；反面是"没有控件的文档一段都不产对象"。

★ 顺带推翻的两条旧判据：`compile.cpp` 原先对内容控件记一条"尚未进入编译的元素"，model_test
里两条 0.4 判据钉的正是那个诊断（"控件本身未编译"、"图片与控件各记一条"）。这一刀把前者改成
"控件已进编译 + 边界落在两段上"、后者收窄成"只剩图片一条" —— 判据跟着实现一起翻面，
旧结论不能留着当"仍然成立"。

**第六刀（同日）让引擎持树：块流第一次由文档模型编译产出。** 前五刀改的是引擎输入的
"形状"，这一刀改的是**来源** —— `EditorEngine::setDocument(tree, sheet)` 让引擎持有模型树，
`blocks_` 变成 `compileDocument` 的产物，控件集合也从产物的边界里导出来
（`exportControlsFromBlocks`：按 owner 配对两枚边界，得到控件的 (起, 止) 区间与只读位；
业务标识与种类从节点记录取，标签刻意不填 —— 第七节里标签是内容，旧表示的 label 是
调用方自填的显示名，产物里没有对应物）。

三条随之而来的分工变化：

其一，**"产边界"与"决定显示哪些"分开了**。编译对所有内容控件都产边界，`syncInlineObjects()`
在持树时退化成一次过滤：按要显示括号的名单筛一遍，且只改对象表、不整段拷回（编辑路径暂时
仍直接改块流）。这正是第五刀末尾预告的那个退化。

其二，**句柄口径要翻译一次**。编译给的 owner 是控件的节点 id（第五刀的决定：序号会在插入
之后整体平移），而对外（宿主、探针、既有判据）的口径一直是控件下标 —— `controlIndexOfOwner`
在命中测试那一处翻译，两端各用各的口径而不互相污染。

其三，**隐藏控件的可见性随模式重编译**。口径与编译同一处取值：文档模式是设计态（隐藏的照常
参与流，否则作者没法选中它改回来），表单与只读是呈现态（整棵摘除、不占流位置）。所以
`setEditMode` 落在持树这条路上时必须重编译并整篇标脏 —— 摘除/放回发生在文档任何位置，
脏区不是一个后缀。

★ 这一刀**不碰编辑**：树上编辑（改树生成步骤、走事务、撤销）是下一刀，在此之前，引擎一旦
真的要在文档上落笔就**摘掉"树是真相"这个标记**（`leaveTreeModeForEdit`），诚实地退回块流
路径 —— 不假装 `blocks_` 还是树的产物。不这样做的话，产物里的 owner 是节点 id 而控件集合
已是旧路径的，命中测试会一律判不出"点到的括号是谁的"。退回时 run 表一并拉回旧口径
（旧路径只有"整段一个 run"这一种形态，而编译产物带着按字符格式切开的序列；编辑只改
`cp_text`、不动 run 区间，留着就是"run 铺不满文本"），**丢没丢东西由 `droppedCharFormats()`
报出来**，不静默。所以 web 演示页照旧走 `setBlocks`，行为与这一刀之前逐字节相同。

判据（edit_test 一节十二组）：两条路逐项一致（文本、按 `effectiveRuns` 比的 run、对象表的
锚点与只读位、控件区间与业务标识），且**帧逐字节相同** —— 形状替换最典型的错法是"排版多算
了一处"，只比数据字段抓不到；句柄口径反过来验一次（同一个点在两条路上落在同一偏移，归属都是
下标 0）；业务类型与业务标识从节点来（number → 数值字段）；可见性随模式变（呈现态下隐藏控件
整棵摘除，剩 5 个码点、边界也没了；设计态 7 个码点、两枚边界都在）；反向是"树里改一个字，
重编译之后与手工改块流逐字节相同"，证伪"持树只是把首次编译的结果存了一份"；有损降级的信号
也要真的亮（给首段挂 14 磅字符格式，退回时 `droppedCharFormats()` 为真）；最后一条钉住这一刀
的边界 —— 落笔之后 `hasDocumentTree()` 变假，且退回之后的帧与旧路径逐字节相同。

**第七刀把编辑搬回树上**，分三段走：A 段搭桥、B 段改落笔、C 段换策略。让一整个"编辑路径迁移"
一次落地会有两个问题：中间态没有任何东西可判（改完才第一次知道对不对），以及三件事的
证伪方式完全不同（坐标换算 / 产出等价 / 策略语义），混在一起会互相掩盖。

**A 段（段落身份与流位置桥接）已落地。** 它是 B 段的地基：引擎对外一直说 (段, 段内码点偏移)，
模型层说流位置，而两者之间隔着**控件边界**（开闭括号各占一位）与**节边界**（起止各占一位）——
段的码点里没有它们，靠算式互换必然分叉。所以换算只认一个权威：编译给出的来源身份加
`FlowIndex`。

- `CompileResult` 多了 `sources`，每块一条 `BlockSource{first, mark}`：`first` 是**本块吃到的第一个
  在流里占位的元素**（文本节点 / 控件节点 / 空段时它自己的结束标记），`mark` 是它的结束标记
  （`kInvalidNodeId` 表示末尾那段还没被标记结束）。记**节点 id** 而不是流位置，是因为编译这一层
  不认识 `FlowIndex`，让两边各算一遍，分叉是迟早的事。
- 引擎据此建 `block_flow_`（每块内容起点，取自 `intervalOf(first)`）与 `block_flow_span_`
  （文本码点数 + 边界数），两者与流索引**一起**在 `rebuildFromTree()` 里重建 —— 分两次建就会出现
  "块按新树、流位置按旧树"的错配，而那种错配只表现为光标落偏一个字，很难查。
- 对外是两个互逆入口：`flowPosAt(段, 码点偏移, 归属提示)` 与 `flowToTextPos(流位置)`。

★ 两条语义要点。其一，**同一处边界上"控件之前 / 进入控件"是两个流位置**（流那侧早就这么划，
见 flow.h），光凭码点偏移分不出侧别 —— 无提示时取最外侧，提示指到该控件时贴内侧（开括号落在
它之后，闭括号自己的位置就是"内容末尾"，不跳到括号之后）。其二，**不持树时桥不存在**：旧
`setBlocks` 路径的块流是调用方拼好的，没有对应的树，两个入口分别返回 -1 与 false —— 不猜一个
位置出来。

判据（edit_test [26] 一节五组）：块起点与模型侧独立算出的流位置逐项一致；两段起点之差恰为
首段内容位数加段落标记一位；压在开括号上的归属分侧、闭括号即内容末尾、段末正落在标记那一位；
**正向换出去再反向换回来逐项相同**；落在段间的位置归到相邻段端点；不持树时桥消失。这一节
不碰编辑路径，行为与第六刀之后逐字段相同。

**B 段（编辑改在树上落笔）已落地。** 判据口径一句话：树上编辑与旧路径**逐字段逐字节相同**、
增量页数不退化、撤销往返回帧。引擎侧持一枚 `UndoStack`（`setDocument` 时按树建，`setBlocks` /
`setControls` 时丢弃），五个内容级编辑入口（插入、退格、前删、拆分、合并）与缩进全部改成**先建步骤、
再经 `commitOnTree` 提交**：commit 应用并规范化 → `rebuildFromTree()` 重编译 → 只标脏受影响的那一段。
重编译不是可选项 —— `blocks_`、流索引、块-流映射、来源身份、控件集合全是树的派生量，少建任何一个就
"块按新树、位置按旧树"，而那种错配只表现为光标落偏一个字。段数变了才置 `para_count_changed_` 禁
后缀复用。撤销与重做按事务逆序应用逆操作，commit 后重编译并**整篇标脏**（撤销的脏区不可定位：事务
可能跨段），光标按事务记的编辑前选区经桥换回 `TextPos` 恢复，置 `frame_needs_full_refresh_`。

三条落笔时的语义要点：

- **字符格式要继承**：新字沿用**落点左侧文本节点**的 `marks` 与 `styleRef`（`marksAtFlow`），
  否则在粗体字中间敲字会得到不粗的字。
- **段落格式归属要显式搬**：段落属性挂在**结束标记**上。回车在光标处插新标记 ⇒ 新标记结束的是
  **前半段**，"拆出的后半段不该跟着强制分页"这条约定得落到**原标记**上；合并是删前一段的结束标记
  ⇒ 留下来的标记是**后一段**的，"保留前段格式"须显式搬到后段标记上。两者都只改标记数据、不改流
  结构，新增步骤 `SetParaMarkFormat` 承载，位置映射为恒等。
- **末尾段没有结束标记**：合并进末段时删掉前段标记后，合并段将按默认格式编译 ⇒ 须在末尾补插一枚
  标记带上被删标记的格式，且坐标要按"删完之后"给（`mapPos(rm.step, end_before, Assoc::After)`）。

★ 这一段暴露的第一个真地雷是**结构口径与编辑口径的分叉**：`makeDeleteRange` 走 `normalizeRange`，
端点落在不可半分单位（控件 / 表格 / 链接）**内部**时会向外扩到**单位边界** —— 于是"删控件里的一个
字"被理解成"覆盖控件节点本身"，步骤构造直接失败。编辑要删的是**码点**，须按文本节点切分，所以另立
`makeDeleteTextSteps`（按文本节点分组、从后往前发步）。同一棵树上两个"取区间"的入口各管各的口径，
不合并。

判据（edit_test [27] 一节五组）：装载逐字段一致；控件内退格（只摘掉那一个文本节点，控件与括号不动，
区间 `1,1-1,2`）；分段（`ab|cd|efgh|ij`，`page_break_before` 留在前半段的原标记上）；合并（含并进
末尾段：`abcdefgh|ij`、`abcdefghij` 仍 20 磅、区间 `0,5-0,7`）；24 段多页文档敲字增量不退化 —— 6 页、
脏页数 `1 / 1`（两路逐值相同且 ≤ 总页数 / 4）加撤销回帧。另有往返与护栏几条：撤销之后重做栈有货、
树还在；撤销把那一笔收回去按**码点**比（不按字节）；`SetParaMarkFormat` 的往返与守卫（原值不符拒绝
且文档未改、目标非标记拒绝、位置映射恒等）。

**C 段（策略改走 `edit_capability`）已落地。** 口径一句话：持树路径的编辑判定与旧路径**同一份
结论**，而持树这条路上不再问旧 `EditPolicy`。引擎里只留一个分叉点 —— `policyAt(TextPos, 归属提示)`
与 `policyErase(TextPos, TextPos)`：持树就先过桥把落点换成 `FlowPos`，再问模型层
`canEditAt` / `canEditRange`；不持树才问 `EditPolicy::canInsert` / `canErase`。六个编辑入口
（插入、退格、前删、分段、合并、反缩进）全部改调这两个入口，判定结论因此可以逐位对照。

三条实现要点：

- **安全阀要镜像**：表单模式下"一个可编辑控件都没有"的文档，旧路 `EditPolicy` 会退化成文档模式
  （编辑一律放行），而不是什么都不让改。持树路若不带这条，同一份文档换条路装载行为就变了 ——
  所以 `formDegraded()` 与 `hasEditableControl()` 由两条路共用一个判据。
- **归属提示两条路都要留**：共享边界上"前一个控件的末尾"与"这个控件的开头"是**同一个码点偏移**，
  点击带来的侧别不能丢。无提示且持树时才回落成"**最内层含端点**的控件" —— 不回落的话桥会取最外侧
  （读成"在控件之前"），光标停在字段起点时编辑随即被拒，表象是"光标停住了、字却打不进去"。
- **Tab 要带归属**：新增引擎入口 `tabCaret` 走模型层 `tabFrom`（**到最后一个可编辑控件就放行，
  不绕回**；文档 / 只读模式不消费 Tab，裸 Tab 留给缩进）。`TabStop` 增 `owner`（`NodeId`）——
  落点是控件的内容起点，共享边界上调用方重推归属会推成前一个控件，表象是"Tab 跳过去却打不进字"。
  web 端已加 `tabCaret` 包装，默认键位不绑它。

★ 这一段的第一条硬边界是：**光标位置不受控件约束**（字段外、只读字段里都能停，方向键能走出字段 /
跨过只读字段），受约束的只有**编辑**与一次 Tab 跳到哪。C 段只换编辑判定，不碰光标移动 —— 第一轮
照"编辑与移动一起受限"写，27 条判据当场红（`edit_test` [7] / [18] 早就钉着"字段外可停"），全部回滚。

判据（edit_test [28] 一节四组）：落点 0..9 的允许位两条路**逐位一致**（实测 `0000011100`）、被拒
次数相同（7 / 7）；带点击归属 `setCaretAt(0,4,1)` 两路都放行、可编辑控件长成 `[4,8)`；安全阀
（只有只读控件时表单退化，控件外也能打字）；Tab 落点偏移 `4`、`caretFieldHint()==1`、跳过去后字
真的进那个控件、在最后一个可编辑控件上再按返回 false、文档 / 只读模式不消费。model_test
`checkTabStops` 补 `owner` 两条（两个不同控件各带自己的身份、放行时为空）。

**演示页切到树上（已落地）。** web 演示页从"拼块流"（`setBlocks` + `setControls`）改走
`setDocument`：场景文书由 `demo/demo_documents.cpp` 的 `demoTree(blocks, fields)` 建成模型树 ——
块级字段逐项搬到段落结束标记的段落格式上、字段区间换成内容控件。控件从此长在树上、编辑也落在
树上，与单测里那条路是同一份代码。

三条与老路径对齐的次序规则（都写在"谁当下一枚、谁进内层"上）：

- **块级字段逐字段搬**，不"只搬与默认不同的那些"：少搬一个就会静默换成默认值。
- **空字段不参与嵌套**：它的开闭两枚落在同一列，老路径把它那一对排在"到此为止"的闭括号之后、
  后一个字段的开括号之前 —— 只有与包住它的字段**并列**，才画得出同一个次序（`][][]`）。
- **归属提示要过 `slotOwnerOf`**：占位簇上记的是产生端的句柄（持树时是控件节点 id），而光标
  侧别、命中测试与宿主报的都是下标 —— 差这一道翻译，共享边界上就是"括号排对了、光标却画到
  另一侧"。

★ 顺带修掉三处真缺陷，都是"只有把演示页切过去才会露出来"的那一类：

1. **删区间没带归属**：`policyErase` 求端点流位置时没给提示，桥取的是最外侧（控件**外**）⇒
   "把字段最后一个字退掉、把字段删空"被判成越出控件而拒掉，表象是"删到只剩一个字就删不动了"。
2. **光标侧别比错了句柄空间**：`caretRectFor` 拿控件下标去和占位簇的 `owner_control` 比，
   持树时一次都比不中 ⇒ 共享边界上光标画到另一侧。
3. **宿主的底稿会过期**：树上编辑之后宿主手里那份块流还是装载时那一份，紧接着"改控件再重建"
   会把用户改过的内容整个倒回装载时的样子（光标归零、字打不进任何字段）。

判据：`edit_test` [29] 十组 —— 两条路的帧逐字节相同（4 页演示文书 + 嵌套/相邻/只读表单）、
零宽与完全重合的字段只建出三枚控件、把字段删空能删得动、偏移 7 上的括号次序 `][][]` 且归属
`0 1 1 2 2`、零宽字段上打字放行、占位簇句柄往返。浏览器探针 192 项全绿，其中**用户报的三条
边界现象各自都有专门的断言**（点三层各自的第一个字归属 0/1/2；删空之后光标仍停在那个零宽字段上、
字进它自己；删空的内层仍画成一对相邻的 `[]` 且嵌在中层的边界之内），三条全部通过。

★ **括号边界上的两个位置（点选侧别）**。同一处边界上"控件之前"与"进入控件"是两个流位置
（flow.h），而占位括号把这两个位置画在同一个 x 附近 —— 只按"码点偏移 + 归属"渲染的话，
"字与开括号之间""闭括号与字之间"这两段永远落不进光标：点下去光标被贴回括号内侧。修法是让
括号占位簇的**势力范围按左右半边分**（与真实字簇同一条中点规则）：左半边是"括号之前"、
右半边是"括号之后"，命中测试在需要时给出"贴外侧"这个归属（`LineBox::kInlineOffsetOuter`，
与控件下标并列的一个哨兵），渲染侧 `LineBox::outerOffsetAt` 把外侧位置落在**所有闭括号之后、
所有开括号之前**。默认（无归属，例如键盘移动）仍取内侧 —— 字段起点画在开括号之内。

判据：`edit_test` [29](g)（外侧落在括号左缘、内侧落在它之后那个字，两侧差一个括号槽宽；
`hitTestPt` 在括号的左半边 / 右半边分别给出"贴外侧"）+ 浏览器探针 [14.7]（点开括号左半边 →
光标画在括号之前；点闭括号右半边 → 画在括号之后）。

★ **旧装载路径已整个退役**。删掉的东西与它们各自的替身：

| 删掉的 | 替身 | 为什么能删 |
|---|---|---|
| `EditorEngine::setBlocks`（宿主递块流） | `setDocument`（树是唯一入口） | 块流的唯一产处是编译层；递进来的块流没有树、没有流位置、没有事务 |
| `setControls` / `clearControls`（宿主递区间） | 重新装载一棵树 | 控件是编译产物的派生结果，换字段名单就是换树 |
| `tree_valid_` 与 27 处分叉 | 无（只剩一条路） | 分叉的每一处都是"树有/没有"两种语义 |
| `owner_index_` 的"空即下标"回落 | 恒在的节点 id → 下标映射 | owner 现在一律是节点 id |
| `objectsFor` 的双路分支 | 只读 `blocks_full_` | 对象表只有编译产物这一处 |
| `syncInlineObjects` 的"自己产边界"分支 | 只筛显示名单 | 产边界归编译层（排序是遍历的自然产物） |
| `EditPolicy`（`edit_policy.h/.cpp`） | `edit_capability` + 引擎一个 `EditMode` 字段 | 落点判定改说流位置与侧别，不再需要"控件下标 + preferred"那套 |
| 四个 `adjustControlsOn*`（区间伸缩） | 无 | 手工维护区间要求"每次内容改动"与"每次端点适配"永远配对，漏一处就静默错位；边界由编译从树产出之后这件事不存在了 |

`ControlSet` 留着，但地位变了：它不再是"由调用方给、由引擎就地维护"的权威，而是**编译产物的
一种扁平投影**（导出给宿主与几何用），只读。编辑入口一律只在树上落笔（事务 + `UndoStack`），
`blocks_` 与它上面的对象表每轮由新树重编出来。

判据：编辑侧 706 项 / 模型侧 803 项 / 整形 55 项全绿；浏览器探针 202 项全绿。

## 六、代价与风险

- **两套索引**：流位置与码点偏移并存。必须约定唯一口径——对外一律说流位置。
  这是本方案唯一的结构性风险（上一轮文档已标出）。
- **元数据规模**：参照项目 `Dom` 一层六万行；我们的目标不是对齐它的体量，
  而是保持"元素自带四件事"的一致性。可以只实现需要的元素类型。
- **单测改写**：现有用例里有一批编码的是被替换掉的启发式，必须一起重写，
  否则回归无从判断。这是实际工作量的大头。
- **公式渲染**需要一个排版后端（MathML 或自绘排版），可作为独立模块后接，
  先用占位盒不影响主链路。占位盒必须是**显式可见**的"暂不支持"呈现
  （渲染成占位框并记诊断），不要把它接到一条看起来正常的空渲染路径上。

## 七、待确认

1. **起手式（唯一阻塞开工的一项，其余三项都可后置）**：按第五节从阶段 0 开始动手，
   还是先把第四节的设计决策写成更细的接口草案
   （元素基类与命令基类的签名）再动手？
2. **公式的深度**：本期只要"能插入、能显示、能存"，还是要"可编辑、可参与计算"？
   后者需要独立的后端选型，建议排在阶段 6 之后。
3. **表格的优先度**：病历表单大量用表格排版，是否把它从阶段 5 提前到阶段 3 之后？
   提前会增加地基未稳时的返工风险。
4. **外部互换的接口**：是否需要与院内 HIS / 区域平台或医保接口对接（这些基本走 XML）？
   需要的话，XML 导入导出适配器要单独排期，但它不影响内部选 JSON 这个决定。
5. **Web 侧两套宿主何时收口**（见 4.6.1、4.6.2）：**已部分落地** —— `app.js` 已冻结为行为法器
   （多实例与错误降级这两轮都按这个纪律做：两边各实现一遍），两个工厂
   （`createEditor` / `createWorkerEditor`）也已落地。**剩下的那一问还在**：要不要把两个入口合并成
   文档里写的单一 `createEditor(container, { transport })`。合并要动的是两边手抄的同名成员
   （76 个），四套探针已经能当它的回归网（`edit_probe` / `stress_probe` / `web_probe` /
   `multi_probe`），但收益是把"两个入口"减成一个，成本是引进一层转发 —— 建议等门面契约固化
   那一轮再定，那一轮本来就要逐条对形状。
