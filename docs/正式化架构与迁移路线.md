# 正式化架构与迁移路线：富文本 + 表单 + 三模式

> 结论摘要：**在原地做，但第一刀要切在文档模型这一层，而且要连"一块文本 + 一组字体参数"
> 这个假设一起换掉。**
> 新需求（富文本、图片、公式、表格、表单控件、三模式切换）全部落在**文档模型及它以上**的层，
> 一处也没落在排版引擎上；而引擎那套东西（整形、光栅、增量排版、以及配套的
> "与全量一致"判据）是这份仓库里最贵、也最难重新长回来的资产。所以重开项目解决不了
> 主要矛盾，只会净亏。
>
> 参照项目 `D:\Develop\DCWriterLite` 的授权是 **GPLv3**（见第二节）：
> 它的**代码**不能进入闭源产品，但它的**架构选择与功能清单**可以参考。
> 事实上它的架构（元素树 + 命令层 + 撤销 + 三视图模式）与本方案的结论同向，
> 可以当成"这条路别人已经走过"的现成证据，而不必当成代码来源。
>
> **与 `docs/文档模型设计.md` 的分工：** 本文管分层、路线与选型取舍（为什么这么做、
> 先做什么）；数据结构与语义（节点类型、位置、控件、域、表格、单位、序列化形状）
> 以那份文档为准，两份冲突时以它为准。本文第五节阶段 0 与 1 的细化也在它那里。

## 一、需求与现状的差距

现状盘点：`src/core` 共约 3.4 千行（实测 3379 行；另有 `src/wasm` 748 行与 `src/app` 407 行），
对外只有"编辑模式 / 表单模式 / 只读模式"三档开关（`EditMode`）与一套区间式控件
（正在按方案 A 改造），没有撤销、没有选区、没有序列化。

| 需求 | 现状 | 差距性质 |
|---|---|---|
| 文本样式按 run（粗斜体、字号、颜色、字体） | `BlockSpec` 是扁平块：整段一份字体参数 | 模型缺失：样式要下沉到元素 |
| 图片（内联原子元素，可拖拽改尺寸） | 无 | 新增元素类型 + 排版原语 |
| 公式 | 无 | 新增元素类型（渲染可先做占位，后接排版后端） |
| 表格（合并单元格、行高列宽） | 无 | 新增容器元素 + 一套独立排版 |
| 表单控件（文本框、单选、复选、下拉） | 有区间式控件模型 | 改造为容器元素（方案 A 的自然延伸） |
| 编辑 / 表单 / 只读 三模式 | `EditMode` 三档 + `EditPolicy` 判定已就位 | 骨架可用，行为需要补齐 |
| 撤销 / 重做 | 无（全程 0 处命中） | 新增命令层 |
| 选区 / 剪贴板 | 无 | 新增 |
| 文档保存 / 打开 | 无 | 新增序列化层 |
| 多文档 / 版本化对外 API | 单例引擎 + 手拼 JSON 字符串 | 新增门面层 |

一句话：**引擎层不用重写；文档模型要换；模型以上全部要新建。**
前两轮说的"方案 A 把控件边界做成流位置"，正是这个换模型动作的第一刀，
只是当时的范围划窄了——它同时也是"元素树"的地基。

## 二、DCWriterLite 的定位：可借鉴什么，不能借鉴什么

### 2.1 授权

`LICENSE` 是 **GNU GPL v3**，强 copyleft：只要把它的代码（哪怕片段）并进我们的项目再分发，
整个作品都必须按 GPLv3 开源。闭源商用产品做不到这一点。
作者另有商业版 `DCWriter`（收费），**若确实需要它的代码，正规途径是买商业授权**。

需要分清的两件事：

- **表达**（.cs 源文件、注释、命名）受版权保护，不能复制；
- **思想、架构、算法、功能清单**不受版权保护，照着思路自己实现是干净的。

所以它可以当**参照与需求清单**用，不能当**代码来源**用。

### 2.2 技术栈

它是 .NET 9 / Blazor WebAssembly / C# + Canvas/SVG；我们是 C++ / 自建 WASM / 手写 JS。
代码层面本来就无法直接复用，能迁移的只有架构决策。

### 2.3 它的开源版清单可以直接当验收表

元素类型（`Source/DCSoft.Writer.Core/Dom/`）：文本、图片、输入域（容器）、
复选框 / 单选按钮、表格（行 / 列 / 单元格）、段落标记、换行、分页、页码、
文档节、子文档、条码、图表、媒体、控件宿主。
视图模式（商业版）：**表单视图**（操作只许落在输入域内，域外不可选中）、
**阅读视图**（只读但可选中复制）、**长文档视图**（不分页连续编辑）。
其中表单视图的"域外不可选中"我们**部分不照搬**，关键是把两个轴分开：
**光标落点**限制在可编辑控件内（这一点与它一致），**选区不限制**
（Shift 扩展、拖拽、全选都能跨出控件）。它连选区一起禁，是因为它的用途之一是防复制；
我们没有这个需求，反倒要能核对上文。详见 4.3 与模型文档第七节。
另有撤销/重做、复制粘贴、标尺、段落样式、权限管控、数据源绑定、Excel 语法的数值公式。

对照它，可以确认三件事：我们要的三模式是**同一个控件上的策略差异**，不是三套控件；
表单控件必须是**容器**（输入域里能放段落，所以参考项目里 `DomInputFieldElement`
继承 `DomContainerElement`）；命令层与撤销层是**并列的两层**，不是塞进控件里。

### 2.4 它没有而我们有的

- **增量排版 + 可证伪判据**（`auditFrame` 逐像素、`auditLayout` 逐字段、
  单测 `[16]` 用第二个引擎从零重排的整帧对照）。它的公开文档没提这套东西。
- **书写模式是一等公民**：横排 / 竖排 / 侧倒蒙文共用一套贪心断行。
- 光栅层"关掉字形缓存后逐字节等价"的断言。

结论：**它的架构值得抄思路，它的代码不能抄；我们的引擎比它更讲究，不该丢。**

## 三、目标分层

自下而上八层。标注含义：保留 = 一层不动；扩展 = 只加不改；换 = 整层替换；新 = 新建。

```
8  宿主门面          版本化 API / JSON 协议 / 演示数据搬出 src/         新
7  序列化            DOM 树 <-> JSON（含包容器与压缩，见 4.5）          新
6  视图与模式        EditMode 三档 + 策略裁剪 + 选区呈现                扩展
5  命令层            EditCommand / Undo / Redo / 剪贴板 / 选区          新
4  文档模型          容器元素树 + 元素流 + run 级样式                   换
3  排版              断行 / 书写模式 / 分页 / 增量续排 / 后缀复用        扩展
2  光栅              位图 / 页指纹 / 增量上屏                           扩展
1  文本与字体        HarfBuzz 整形 / 字体回退链 / 度量                   保留
```

第 1、2 层完全不动。第 3 层要新增一类输入：**内联原子元素**（图片、公式、控件占位）
作为"不可断的盒子"参与断行；分页与增量续排的机制不变。
第 4 层是本次改造的主体。

## 四、关键设计决策

### 4.1 文档模型：元素流 + 容器元素

```
Document
  └─ Body                          流；段落是流里的范围，不是节点
       ├─ TextRun("患者主诉：")      叶子，带样式
       ├─ ContentControl [id=3]     容器：自带开闭两个边界元素
       │    └─ TextRun("反复")
       ├─ ParagraphMark             段落结束标记：段落属性的唯一宿主
       ├─ Image {ref,w,h}           原子（不可断的行内盒子）
       ├─ Formula {src}             原子
       └─ Table                     容器：行 / 单元格，单元格内又是流
```

要素：每个元素自己管四件事——**子元素、属性、命中/绘制委托、序列化**；
样式挂在元素上（run 级），继承由树决定（这正是 `BlockSpec` 缺的那一层）。

**没有"块级容器 / 行内容器"这个二分**（这一条是后来修正的，依据见模型设计第三节）：
容器之间的差别只有"接受哪些元素类型"与"跨度是否跨过段落标记"。
段落也不是节点，而是同一容器内两个 `ParagraphMark` 之间的范围，段落属性挂在标记上；
落盘时段落不单独写，它是派生量。于是"主诉：\[____\]"（不跨标记）与
"一栏里多段"（跨标记）是同一机制的两个取值，不需要两个类型，
也不需要"行内升级为块级"的提升规则。

这同时把方案 A 收进来了：**控件是一个容器元素，它的两个边界就是它在流里的开闭标记**
（结构形态上它属于容器型；另一种是"内部没有可寻址位置"的原子型，今天没有实例 ——
见模型文档第七节"控件分三层"）。
并且 `InputField` 这个名字已换成 `ContentControl`（与 OOXML 的 `w:sdt` 同义）。
不再需要"从裸区间反推嵌套"：方案 A 里要删的那批东西
（`withBracketSlots` 三分桶、`inlineOffsetFor` 短路、`innermostAt`、`normalize()`、
`adjustControlsOn*` 四个函数）在这个模型里没有存在的必要。

### 4.2 光标是容器加偏移，不是整数

节点级位置是 `Pos = { container: NodeId, offset: int }`：容器里 `offset` 是子元素槽位序号，
文本节点里是码点下标。这是 ProseMirror / Slate / Lexical 与 OOXML 的共同做法，
也是上一轮文档 `docs/控件边界诊断与方案.md` 第四节给出的结论。

要点：**边界是流里的真实元素**，所以"在 `[` 与 `]` 之间"天然是一个合法位置，
删空的控件也仍有两个互不相等的槽位。另有一套索引**流位置**（深度优先展开后的元素序号）：
段落序号、脏段标记与引擎接口都定义在它上面，它不是"等价但更快的视图"，而是第二套索引。
约定是节点级 API 与内部位置用 `Pos`，段级与引擎级用流位置，换算必须双向互逆。
细节见模型设计第四节。

### 4.3 三模式是一套能力 + 策略裁剪

不写三套代码。同一个文档模型，`EditMode` 决定"光标能落在哪、哪些命令可用"：

| 模式 | 光标落点 | 编辑 | 说明 |
|---|---|---|---|
| 编辑模式 | 全部 | 全部 | 现状（`EditMode::Document`） |
| 表单模式 | 只落可编辑控件内 | 只有在可编辑控件内插入/删除 | **选区三种模式都不受限**（可选中复制）；被裁的是落点与编辑能力（`canInsert` / `canErase`），不是选区范围 |
| 只读模式 | 全部 | 一律拒绝 | 打印预览同此路径 |

表单模式的落点/选区口径、以及"可编辑集合取交集"（只读控件里嵌可编辑控件时内层仍不可编辑）
写在模型文档第七节与第二节；`w:group` 那种"内层覆盖外层"的例外我们不需要。
Tab 的分工（编辑模式是制表符、表单模式在控件间切换、只读模式放行、表单模式不提供插制表符的
默认键位）、结构操作默认关闭（内容可编辑但控件不可删）、越界交互只走宿主回调不在编辑器内提示、
以及"默认键位必须避开浏览器保留键（`Tab` 家族带修饰键拿不到事件）"，也都在那一节。

现有的 `EditPolicy::canInsert / canErase / canSplit / canMerge` 就是这个思路的雏形，
扩展它即可，不要另立一套；**此外还要一条独立的"这个位置能不能当落点"判定**，
它与编辑能力是两个轴，不要混进 `canInsert` 里。

### 4.4 命令层是差量与撤销的唯一入口

所有编辑都走 `EditCommand`：命令自己负责"文档改了、控件跟着走、撤销记录的什么"。
上一轮诊断出的那类缺陷（三个编辑入口各自手工维护控件区间、漏调一个就脱节）
在命令层里结构性地消失。

**先做命令层再做富文本**：风格切换、插入图片、插入表格都只是新的命令，
不必再碰引擎。

### 4.5 序列化：JSON 做语法，包做容器，压缩做体积

**结论：JSON 能满足全部功能需求，选定 JSON。但体积的大头不在"XML 还是 JSON"。**

实测 23 份真实病历模板（`scripts/probe_serialization_size.py`，样本取自参照项目的
`wwwroot/demoDocuments`，合计 13.84 MB）：

| 口径 | 字节 | 占原始 |
|---|---|---|
| XML 原始 | 13,835,860 | 100.0% |
| 其中 文字 | 829,811 | 6.0% |
| 其中 属性值 | 736,483 | 5.3% |
| 其中 标签间缩进与换行 | 7,584,303 | 54.8% |
| 其中 空元素（93,160 个） | 1,954,659 | 14.1% |
| JSON 完整键名 | 9,956,253 | 72.0% |
| JSON 紧凑（键名与标签名走符号表） | 3,122,346 | 22.6% |
| gzip(XML 原样) | 468,773 | 3.4% |
| gzip(JSON 紧凑) | 342,210 | 2.5% |

三个结论：

**一、88.7% 不是内容。** 缩进与换行一项就占 54.8%，纯空白、零信息；空元素占 14.1%，
是"每个元素把默认属性照写一遍"的产物（`<Attributes />`、`<Expressions />`、
`<ScriptItems />`、`AutoFixTextMode=None`、`<XElements xsi:nil="true"/>`）。
这两项与语法无关，换成 JSON 一样会犯。

**二、换 JSON 省的是语法那一份。** 完整键名只有 72%，因为参照项目的写法本身已经很紧凑
（所有元素都叫 `<Element>`，类型放在 `xsi:type` 属性里，标签名恒定）。
把标签名与属性名收进符号表、每个名字只出现一次，才降到 22.6%——这是 JSON 的真正优势。

**三、压缩之后差距缩到 1.37 倍。** gzip(XML 原样) 0.47 MB 对 gzip(紧凑 JSON) 0.34 MB。
"XML 体积太大"这个感受在**未压缩的中间态**下成立；一旦落到传输与存储，体积主要由压缩决定。

所以决定体积的是三条与语法无关的措施：

- 缩进只用于人工调试输出，落盘一律无空白（这一条单独就是 55%）。
- **默认值不写**，只序列化与默认不同的属性（XML 与 JSON 都要做）。
- **二进制资源外置**：图片不要 base64 塞进文档（base64 膨胀 33%），走包里的二进制条目，
  文档只存 ID。这批样例里没有图片，所以图上没体现；真实病历一旦有检查报告、心电图，
  图片会成为绝对大头。对标 OOXML 把图片放在 `word/media/*` 的做法。

这正是 OOXML 的选择：它不靠 XML 语法省体积，靠的是 ZIP 包 + 压缩 + 二进制资源分 part 存放。

JSON 与 XML 的实际得失：

| 维度 | JSON | XML |
|---|---|---|
| 未压缩体积 | 好（键名只出现一次） | 差 |
| 压缩后体积 | 略好（1.37 倍） | 可接受 |
| 前端（JS）读写 | 原生 | 需要解析器 |
| WASM（C++）读写 | 自己实现，注意浮点往返 | 可用 pugixml 之类 |
| 调试可读、版本管理 diff | 好 | 好 |
| 模式校验 | JSON Schema 生态弱于 XSD | XSD 成熟 |
| 与外部标准互换 | 弱 | 强：HL7 CDA、卫生信息共享文档、医保接口规范基本是 XML |

最后一行是 XML 唯一有实质优势的地方，但**那是边界适配器的事，不是内部存储格式的事**：
内部用 JSON，需要对接外部系统时写一个 XML 导入导出适配器即可。

实现时要定死两条：

- **浮点按十进制字符串写**，不依赖默认浮点格式化，否则 `parse(print(doc)) == doc`
  这条判据会失败（坐标、字号、行高都要过）。
- **增量保存**：嵌套树不友好（改一处要重写整个文件），而增量是本项目的特色。
  建议编码成扁平形式——元素表 + 样式表 + 父子索引数组，只存非默认值。
  既更小（没有嵌套括号），也更适合差量落盘。二进制编码的取舍见 4.5.1。

### 4.5.1 要不要自定义二进制格式

**结论：不要。** 实测（`scripts/probe_encoding_formats.py`，同一批 23 份样本，
payload 统一抽取为元素类型、属性、文字、子节点个数，各编码信息量相同）：

| 编码 | 未压缩 | 占原始 | gzip | lzma |
|---|---|---|---|---|
| XML 原始 | 13,835,860 | 100.0% | 468,773 | 339,188 |
| XML 去空白 | 6,251,557 | 45.2% | 383,996 | 317,516 |
| JSON 完整键名 | 11,727,748 | 84.8% | 429,331 | 329,552 |
| JSON 紧凑（符号表） | 3,518,152 | 25.4% | 353,943 | 305,288 |
| 自定义二进制（LEB128 + 符号表） | 2,565,915 | 18.5% | 346,565 | 303,636 |

自定义二进制在**未压缩**时比紧凑 JSON 小 27%，**压缩后只小 2%（gzip）到 1%（lzma）**。
而且这还是理论上最紧凑的自研编码：变长整数、符号表、无对齐、无版本头、无区段表、无校验码。
真实实现补齐这四样之后，未压缩体积会向紧凑 JSON 靠拢。

原因是紧凑 JSON 已经把键名收进符号表，剩下的差异只有引号、逗号、括号与数值的十进制写法。
这些字节**低熵且高度可预测**，压缩算法本来就近乎免费地吃掉。压缩越强差距越小：
gzip 下二进制领先 2%，lzma 下只剩 1%。二进制省掉的是"语法字节"，不是"信息"。

二进制的真正价值不在这里，而在**解析速度、随机访问与原地更新**（零拷贝、mmap、
FlatBuffers / Cap'n Proto 那一类）。这三条在本项目都不成立：文档量级是几百 KB 到几 MB，
元素表在内存里毫秒级建好，解析根本不是瓶颈；编辑走增量，也不需要每次全量序列化。

代价却是实打实的：无可读性（出问题只能 hexdump）、无 git diff、跨版本加字段要处理前向兼容、
端序与对齐各是一类 bug，而且 WASM 与 JS 两端要各写一遍编解码器——这是最容易出现
"同一份文件两端解读不一致"的地方。

分档建议：

- 本期：JSON（扁平元素表）+ 压缩容器。压缩不只是省空间，IO 少意味着加载更快。
- 真要二进制：用 **CBOR 或 MessagePack**，不要自研。它们与 JSON 同构、可无损转回 JSON 打印、
  两端都有成熟库，能拿到解析速度而保留可调试性。
- 只有出现可测量的瓶颈（单文档超过几十 MB、或高频全量同步）才考虑
  FlatBuffers / Cap'n Proto 这类需要 schema 编译的方案。

### 4.6 双宿主与验证面：native 留在哪一侧

**定位**：wasm 是交付物，native 不是。native 存在的理由是当**验证宿主**——它承担
522 项断言（`heditor_edit_tests` 467 项、`heditor_tests` 55 项），而且不需要浏览器。

**为什么不是"砍掉就完事"，三个数字说话：**

- **两边的断言是分层关系，不是重复。** C++ 侧的 522 项里有大量循环采样式的地毯覆盖
  （光标命中测试就是"横扫 x ∈ [118.3, 220.5]，采样 205 点"这种形状），在原地跑是毫秒级，
  逐条走调试协议问会慢几个数量级。浏览器探针 `edit_probe.mjs` 有 192 个断言点，
  管的是真实指针事件、宿主按键处理、画布上屏，以及真正的 Skia 光栅；
  native 管算法级的穷举与几何。
- **核心判据已经两边都有。** `auditLayout` 与 `auditFrame` 已通过 wasm 导出，
  并已在 `edit_probe.mjs`、`stress_probe.mjs`、`web/app.js` 里被调用。
  所以"与全量一致"这些可证伪判据**不依赖 native**；native 提供的是更快的迭代与
  可调试性（断点、栈、性能剖析），不是判据本身。
- **native 是第二把尺子。** `HEDITOR_USE_SKIA` 只在 wasm 有效，native 一律走自写
  `bitmap.cpp`。两个独立光栅实现互为对照；砍掉 native 就只剩 Skia 一个实现，
  没有东西能独立地证明"这一帧是对的"。

**边界（要收窄的部分）：**

- native 只做验证宿主：**新功能不得只在 native 上实现**，否则它从宿主变成了第二个产品。
- 光栅层的双实现（`bitmap.cpp` 与 `bitmap_skia.cpp`）是本工程唯一被认可的重复实现，
  正当性就是上面第三条。两者不一致时以 **Skia（线上那份）为准**，
  `bitmap.cpp` 的差异记为待查项，不要反向改 Skia 去迁就。
- 内存布局类诊断（`heditor_abi_probe` 打印 `sizeof` 与 `EditStats` 字段偏移）天然属于 native，
  不在 wasm 上复刻。

**什么条件下才该砍掉 native**：native 工具链的维护成本持续高于它的收益
（换台机器就构建不起来、或 CI 上跑不了）。那时把像素与几何断言整体搬到
"wasm + node"——测试代码本身不依赖浏览器（`tests/*.cpp` 里只有一处提到 Skia，
且只是注释），所以这条路技术上可行。代价是丢掉 522 项断言的现成覆盖与独立光栅对照，
并接受每次迭代都要重编 wasm。这是一次有真实代价的取舍，不是顺手的清理。

### 4.7 源码组织：先拆文件，后拆类

`src/core/engine/engine.cpp` 一度是 2295 行、承载 120 个方法的单一实现文件。已经处理过一轮，
但方式值得写下来 —— 因为它**只拆文件、不拆类**，而这一步与后面的拆类是两件事。

**已经做的（机械搬迁）**：按职责把实现分到五个文件（排版调度、呈现、审计判据、诊断、门面），
`EditorEngine` 仍是同一个类 —— 成员函数在哪个 .cpp 里定义不改变类的结构。
跨文件共用的三个自由函数（`Clock` / `msSince` / `quantPt`）提到 `core/utils/`，
公共头里的 `EngineConfig` 与 `EngineStats` / `EditStats` 各自独立成头。
判据是"数字一条不变"：522 项断言、逐像素帧审计、探针断言点全部照旧。

**为什么只拆文件、不拆类**：那 120 个方法里，编辑操作、光标、控件合计 847 行
**即将被替换或重写** —— 编辑操作要变成命令层（阶段 2）、控件要换成 `ContentControl`、
光标要跟着流位置一起改。现在为它们设计接口，而接口的输入（文档模型与排版结果的形状）
本身还在换，等于**为一份马上要改的东西定边界**。这类边界比不拆更糟：它看起来有条线，
实际上拦不住任何改动，还会让后来者以为那里是稳定的。

**保留的那部分暂时不适合拆类，原因是依赖面**：`presentInternal` 直接读十个以上的私有成员
（底图、帧、排版结果、统计、字形缓存）。要把它做成独立的渲染器，得先定义"绘制需要哪些输入"，
而这份输入的形状由**排版结果的形状**决定 —— 那正是阶段 1（文档模型替换）与阶段 4
（行内原子）要改的。顺序只能是先定形状、再切依赖。

**正式拆分的时机与目标**，每一步的前置条件都是"接口的输入已经定下来"：

| 做完哪一步 | 拆什么 | 拆成什么 |
| --- | --- | --- |
| 阶段 1 文档模型替换 | 编辑操作、缩进 | 命令层 `EditCommand`（见 4.4） |
| 阶段 1 | 光标、命中测试 | 选区与位置解析（流位置定了才有稳定接口） |
| 阶段 4 行内原子 | 绘制 | 渲染器 + 一份"绘制输入"结构（排版结果形状定了） |
| 阶段 5 表格 | 控件查询 | 控件索引（`ContentControl` 定了之后） |
| 阶段 6 序列化 | 引擎门面 | 宿主门面只做转发与版本化 |

**完成判据可证伪**：`EditorEngine` 的每个公开方法都只剩一到三行、把调用转给真正的实现类；
出现"在门面里算东西"就是没拆干净。

**目录约定**：`src/core/` 下的子目录对应实现层（`text` / `render` / `layout` / `doc` /
`engine`），`utils` 放跨层共用的纯工具与基础类型（无领域语义：哈希混合、UTF-8 解码、
计时、长度量化）。有领域语义的头不放 utils —— 书写模式（`InlineAxis` / `BlockFlow` /
`TextOrientation`）因此归 `text/`。缺的三层（命令层、序列化、宿主门面）**不预先建空目录**：
空目录不承载任何约束，只会让人以为那里已经有东西。

## 五、迁移路线

每一步都要求**可独立验证**，且不改变对外行为，直到该步自己的判据转绿。

**落在文档模型上的各步，其细化与判据以 `docs/文档模型设计.md` 第十五节为准**：
那里的 0.1–1.10 把阶段 0 与后续阶段里属于文档模型的部分拆成可单独转绿的小步
（它的 1.7 表格对应本表阶段 5、1.10 序列化对应阶段 6）。**它的 0.x / 1.x 是本表阶段号
之下的第二套编号，不要与本表的 0–8 混用**；本文只保留粒度与先后。

| 阶段 | 做什么 | 判据 |
|---|---|---|
| 0 | 元素流进段落容器（方案 A 第 1、2 步）：标记先不参与长度账 | 现有单测全绿、帧与全量一致 |
| 1 | 文档模型升为元素流：`BlockSpec` 变成"元素流 + 段落标记 + run 级样式"，`cp_text` 降为派生视图 | 同上，另加"排版输入与旧路径逐字段一致" |
| 2 | 命令层：把已有编辑动作（插入/删除/分段/合并）改建为 `EditCommand` | 撤销 N 次回到原状态、帧一致 |
| 3 | 选区 + 剪贴板（选区本身是会话状态、不进文档模型；进模型的是端点形状、位置映射与区间原语） | 选区端点用流位置、带方向；跨段选择往返不变；复制片段始终良构（控件边界成对）；撤销恢复到编辑前选区 |
| 4 | 内联原子元素：图片、公式（公式渲染成**显式占位框**，不做伪渲染） | 断行处不可分割；增量与全量一致 |
| 5 | 容器元素：表格 | 单元格内独立排版；跨页行为与全量一致 |
| 6 | 序列化：DOM <-> JSON（扁平元素表 + 样式表），二进制资源走包 | `parse(print(doc)) == doc`；落盘无空白、不写默认值 |
| 7 | 三模式行为补齐：表单模式的 Tab 遍历、只读继承、控件聚焦 | 策略单测 + 浏览器探针 |
| 8 | 门面版本化、演示数据搬出 `src/`、测试骨架换成可注册可分片 | 断言一条不改，只换驱动 |

阶段 0 与 1 是地基，不能跳。反过来先做壳（如图片、表格）会白做——
元素的语义刚换过，壳上的差量与序列化都得跟着重写。

与这张阶段表并行、且不阻塞它的是**依赖与工具链**这条工程化线：源码依赖走 git submodule
（HarfBuzz 的 gitlink 钉在上游 tag 14.6.0 指向的 commit）、Skia 与 emsdk 走脚本化归档
（Skia 的 commit 尚待钉住）、**不使用包管理器**（唯一适用它的依赖面目前是空集）。
web（wasm）是主线，native 退为单测与审计宿主，这对判据落在哪一侧有影响。
它不动文档模型，可以随时穿插进行，清单与判据见 `docs/依赖与工具链管理.md`。

## 六、代价与风险

- **两套索引**：流位置与码点偏移并存。必须约定唯一口径——对外一律说流位置。
  这是本方案唯一的结构性风险（上一轮文档已标出）。
- **元数据规模**：参照项目 `Dom` 一层六万行；我们的目标不是对齐它的体量，
  而是保持"元素自带四件事"的一致性。可以只实现需要的元素类型。
- **单测改写**：现有用例里有一批编码的是被替换掉的启发式，必须一起重写，
  否则回归无从判断。这是实际工作量的大头。
- **公式渲染**需要一个排版后端（MathML 或自绘排版），可作为独立模块后接，
  先用占位盒不影响主链路。占位盒必须是**显式可见**的"暂不支持"呈现
  （渲染成占位框并记诊断），不要把它接到一条看起来正常的空渲染路径上。

## 七、待确认

1. **起手式（唯一阻塞开工的一项，其余三项都可后置）**：按第五节从阶段 0 开始动手，
   还是先把第四节的设计决策写成更细的接口草案
   （元素基类与命令基类的签名）再动手？
2. **公式的深度**：本期只要"能插入、能显示、能存"，还是要"可编辑、可参与计算"？
   后者需要独立的后端选型，建议排在阶段 6 之后。
3. **表格的优先度**：病历表单大量用表格排版，是否把它从阶段 5 提前到阶段 3 之后？
   提前会增加地基未稳时的返工风险。
4. **外部互换的接口**：是否需要与院内 HIS / 区域平台或医保接口对接（这些基本走 XML）？
   需要的话，XML 导入导出适配器要单独排期，但它不影响内部选 JSON 这个决定。
