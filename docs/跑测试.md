# 跑测试：哪些是真的在等，哪些只是起停

一轮完整验证（native 四套 + wasm 构建 + 十份浏览器探针）原来要四分多钟，其中**一半以上不是
在跑断言**，而是在起服务、起浏览器、装字体、等进程退出。这一页记三件事：时间花在哪、
已经省掉了什么、哪些省钱的路子试过但不成立。

数字取自 2026-10-21 深夜，同一台机器（8 逻辑核）。机器有负载时单节耗时会有 ±20% 的抖动，
所以下面的数看量级不看末位。

## 一、native：`edit_and_caret` 一家独大

`ctest --preset native` 串行 56 s：

| 套件 | 时间 | 断言 |
| --- | --- | --- |
| `shaping_and_layout` | 2.2 s | 150 |
| `edit_and_caret` | **52.9 s** | 1529 |
| `doc_model` | 0.4 s | 845 |
| `rev_layer` | 0.3 s | 314 |

所以 `-j4` 只能省 3 s —— 四个套件里三个加起来不到 3 s。要看的是 `edit_and_caret` 内部：

| 节 | 时间 | 内容 |
| --- | --- | --- |
| [15] | 8.5 s | 增量排版：200 段的复用与摘要 |
| [29] | 3.8 s | 演示页装载：源块流 → 树 → 编译回来逐字段相同 |
| [23] | 3.6 s | 字符格式 run |
| [17] | 3.3 s | 跨段编辑（回车 / 合并） |

前四节占 19 s，其余 57 节分摊剩下的 23 s。另有约 4 s 是 71 处 `EditorEngine::init` ——
每次装载三张字体，中文字体 16.9 MB，实测单次 56 ms。

**一个口径**：上面是"冷启动跑完整个套件"的分节耗时。单独跑某一节时，那一节要自己承担
字形光栅与字体解析的冷启动，会比表里的数大。

## 二、web：一条命令，服务与浏览器只起一次

`verify_web.ps1` 那一套已经删掉。它每被调用一次都要：起静态服务（等端口）、起无头 Chrome
（等调试端口）、`Page.navigate` 与 boot（1~3 s）、收进程树 —— 短探针的九成时间花在这上面，
而它一条断言都不跑。现在这些都归 Playwright 管：`webServer` 起服务、`channel: chrome` 复用
已装浏览器、每条 test 一个干净 context、退出自己收。

`npm test` 一次跑十份 spec，实测 3~4 分钟；产物在 `out/web/pw-runs/<轮次>/`
（失败截图、trace、明细附件），报告在 `out/web/pw-report/`，机器可读的结果在
`out/web/pw-results.json`。

`edit` 那份独占 2.5 分钟上下（367 条、36 节、615 次页面求值），其它八份加起来不到 1 分钟。
并行度是 2：每个 worker 各自编译一份 wasm、各自解析中文字体，开满核并不更快。


## 三、想改哪节就只跑哪节

`edit_and_caret` 每一节前面都有一道 `runSection(N)` 开关：

```bash
HEDITOR_TEST_ONLY="15,29" ./build/native/heditor_edit_tests.exe
```

不设变量 = 全跑（与没有这个开关时逐条相同，整跑仍是 1529 条）。改一行代码时先只跑相关那几节，
一秒出结果，最后再整跑一次 —— 这是日常最省时间的一件事，比任何并行都直接。

## 四、试过但不成立：分片并行

把 61 节按 `n % 4` 分给四个进程：

| 跑法 | 墙钟 |
| --- | --- |
| 整跑（单进程） | 50~59 s |
| bash 直接并行四片 | 39 s |
| 起四个进程（带输出重定向）并行四片 | 54 s |

四片并行只快 20%，因为单节是内存与光栅的重活，几个进程互相抢带宽；而且它多一层要维护的
假设（"节与节之间没有隐含依赖"，以及每片要各自付一次字体装载）。**没有采用**，代码里只留
了 `HEDITOR_TEST_ONLY`。

## 五、还没做、但算得出来的两笔

1. **字体字节跨引擎共享**：71 次 `init` × 56 ms ≈ 4 s。`FontFace::loadFromFile` 每次都把
   16.9 MB 读进自己的 `data_`，而同一轮里这些字节完全一样。`addFaceFromMemory` 已经有了，
   缺的是"一份字节按路径共享"的那层缓存（`data_` 要能指向共享块）。
2. **`[15]` 的 8.5 s**：还没拆开看。它是 200 段文档上的一串编辑 + 摘要比对，先把每段的
   耗时打出来再说，不猜。

## 六、十份 spec 与两条硬规则

`cd web && npm test` 走 Vite 源码直连，改一行就能测。判据、视口、浏览器与验收时完全一致，
换口径不改判据。

| 命令 | 服务 | 页面 | 需要先构建什么 |
| --- | --- | --- | --- |
| `npm test` | Vite 开发服务器（5173，已在跑就复用） | 源码 | 只有 Worker 壳（`pretest` 自动做，约 0.5 s） |
| `npm run test:dist` | `scripts/dev_server.py`（8781） | `web/dist-app/` | `pretest:dist` 先跑 `build:app` |
| `npm run test:report` | — | — | 打开 `out/web/pw-report` |

| spec | 条数 | 看什么 |
| --- | --- | --- |
| `demo` | 23 | 公开面只有公开面，六组行为按契约工作 |
| `multi` | 11 | 同页两个实例互不干扰，拆一个另一个照常 |
| `saveload` | 11 | 存盘往返：正文、帧指纹、页数回到存盘那一刻 |
| `input` | 25 | 真实键鼠与输入法（轨迹留档见附件） |
| `diag` | 39 | 诊断面每个成员都接通（装载、相位、页画布、多页点击、闪烁） |
| `error` | 19 | 正常态无错误界面、单次失败降级、致命失败给横幅 |
| `stress` | 69 步 | 点击与按键之后引擎帧与画布始终一致（差分审计） |
| `edit` | 367 | 键盘、增量、码点与字素簇、输入法、控件边界、长文档后缀 |
| `clipboard` | 11 | 复制粘贴的保真（文字、段落、控件）、外部纯文本、撤销、跨实例、键盘路径 |
| `format` | 6 | 字符格式落到标记上、幂等不占撤销栈、字号与行距对页数的影响 |

输入探针每步写一条轨迹，失败时作为附件留档 —— 判据仍是一次性求值，轨迹只用来复盘。

两条硬规则写在 `web/tests/support/check.ts` 与 `docs/web测试工程化评估-Playwright.md`：

断言一次性求值，禁 `expect.poll` 与 locator 断言 —— 引擎状态判据必须"调用返回后立刻读"，
自动重试会把同步性回归改成绿。像素账以旧探针的值为基线，视口 / DPR / 浏览器版本任何一项
都不能动；所以浏览器用 `channel: 'chrome'` 复用已装那一份，不下载 Chromium。

反证做过两次：把 `editor.ts` 里的缩放上限从 2.25 临时改成 2.5，`demo` 立刻红两条；
把 `edit` 的滚动等待去掉，`stress` 与 `edit` 的平移复用判据在机器有负载时红。

迁移里遇到两处需要交代的差异：

`stress` 的帧差有一处恰好等于光标矩形（2x28 px，56 px）。成因是光标从不可见转为可见
（按键会重置闪烁相位）时，增量帧与整帧重画差出一个光标 —— 内容层完全一致。判据对"帧差
只落在光标矩形上"补一次 `present` 再问一遍；补完仍差就照算不一致，不因为能被修好就放松。

逐页滚动的 8 拍原先只等两帧。Worker 传输下这一拍要跨线程往返，机器有负载时读到的还是
换窗前的账，于是"平移复用"那条会偶发红。改成与跳页同一个口径（安静 180 ms 再对齐），
等的是滚动停下来，不是等断言成立。

## 七、临时诊断：用 Playwright 现写，用完即删

旧的十八份 `scripts/diag_*.mjs` 与 `scripts/cdp.mjs` 已删（2026-10-22）。它们不是工具，
每次都是"为某一个现象写的取证脚本"：等 `window.__heditor` 出现、用 CDP 逐步派事件、把中间
读数打出来。而那个门面名已经不存在了 —— 现在页面运行时 `window.__heditor` 是 `undefined`
（`demo.spec` 里有一条判据专门钉这一点），所以它们全部是等满 60 秒超时的死代码，唯一的消费者
是彼此（`cdp.mjs` 只被这十八份引用）。它们的结论都还在 `.workbuddy/memory/` 的每日日志里。

要再临时诊断，直接写一份 spec，跑完删：

```ts
// web/tests/specs/tmp.spec.ts —— 用完即删，不要提交
import { test } from '../support/probe';

test('复现：删空三连字段之后打字进了哪个字段', async ({ open }) => {
  const p = await open('index.html', { query: { debug: '1' } });
  const r = await p.read(`
    await D.setFormControls([...]);
    return { controls: D.controls(), caret: CARET() };`);
  console.log(JSON.stringify(r, null, 2));
});
```

`read()` 与 `ev()` 的分工：`read` 在前面拼一段读数前言（`H` / `D` 两个别名，加 `CARET` /
`SEL` / `FRAME` / `ZOOM` / `TYPE` / `MOVE` / `LOAD` 这些测试动作，见
`web/tests/support/readings.ts`），要求页面带 `debug=1`；`ev` 不拼，用在没有诊断面的页面上
（`demo` 的公开面判据就是这一类）。要读 `editStats` / `selfCheck` 这类诊断面成员就用 `read`。

比旧脚本省掉的全是场地费：静态服务、Chrome 生命周期、CDP 连接、console 收集。`open` 已经
等过 boot，`p.ev` 是异步 IIFE（可以写 `await`），`p.shot('名字')` 落一张截图，
失败自动带 trace。

`p.ev` 是唯一要注意的地方：它不接受"等一会儿再看"的写法。想量"若干拍之后"的状态，就在
页面里 `await` 那个拍（`flush()` / `quiesce()`），不要在外面 sleep —— 那是把同步性判据
换成时序运气。

三条旧惯例仍然成立：先做最小复现、跑一次对照（"改回去还在不在"）、用完即删。
留在 `scripts/` 下的取证脚本没人跑得起来，这一批十八份就是前例。
