# 跑测试：哪些是真的在等，哪些只是起停

一轮完整验证（native 四套 + wasm 构建 + 十份浏览器探针）原来要四分多钟，其中**一半以上不是
在跑断言**，而是在起服务、起浏览器、装字体、等进程退出。这一页记三件事：时间花在哪、
已经省掉了什么、哪些省钱的路子试过但不成立。

数字取自 2026-10-21 深夜，同一台机器（8 逻辑核）。机器有负载时单节耗时会有 ±20% 的抖动，
所以下面的数看量级不看末位。

## 一、native：`edit_and_caret` 一家独大

`ctest --preset native` 串行 56 s：

| 套件 | 时间 | 断言 |
| --- | --- | --- |
| `shaping_and_layout` | 2.2 s | 150 |
| `edit_and_caret` | **52.9 s** | 1529 |
| `doc_model` | 0.4 s | 845 |
| `rev_layer` | 0.3 s | 314 |

所以 `-j4` 只能省 3 s —— 四个套件里三个加起来不到 3 s。要看的是 `edit_and_caret` 内部：

| 节 | 时间 | 内容 |
| --- | --- | --- |
| [15] | 8.5 s | 增量排版：200 段的复用与摘要 |
| [29] | 3.8 s | 演示页装载：源块流 → 树 → 编译回来逐字段相同 |
| [23] | 3.6 s | 字符格式 run |
| [17] | 3.3 s | 跨段编辑（回车 / 合并） |

前四节占 19 s，其余 57 节分摊剩下的 23 s。另有约 4 s 是 71 处 `EditorEngine::init` ——
每次装载三张字体，中文字体 16.9 MB，实测单次 56 ms。

**一个口径**：上面是"冷启动跑完整个套件"的分节耗时。单独跑某一节时，那一节要自己承担
字形光栅与字体解析的冷启动，会比表里的数大。

## 二、web：每起一轮要 8~10 s，而它一条断言都不跑

`verify_web.ps1` 每被调用一次就：起静态服务（等端口）、起无头 Chrome（等调试端口）、
探针里 `Page.navigate` 与 boot（1~3 s）、收进程树。`web_probe` 只有 6 条断言却要 10 s ——
九成是这套起停。

**改法：一条命令跑一串探针**，服务与浏览器只起一次。每条后面可以带 `@页面`：

```powershell
$list = "scripts/edit_probe.mjs@index.html,scripts/edit_probe.mjs@worker.html," +
        "scripts/worker_probe.mjs@worker.html,scripts/multi_probe.mjs@multi.html," +
        "scripts/saveload_probe.mjs@index.html,scripts/saveload_probe.mjs@worker.html," +
        "scripts/error_probe.mjs@index.html,scripts/error_probe.mjs@worker.html," +
        "scripts/stress_probe.mjs@index.html,scripts/web_probe.mjs@index.html," +
        "scripts/demo_probe.mjs@demo.html"
powershell -ExecutionPolicy Bypass -File scripts\verify_web.ps1 -Probe $list
```

实测十一份探针 **120 s** 左右（原先是逐次调用，约 205 s）。每份最后一行打印自己的退出码与耗时，
结尾有一张汇总表；任何一份非 0，整条命令的非 0。

`demo_probe` 只测 inline；worker 那条要单独跑（`verify_web.ps1` 只拼 `?wasm=...`，带不了
`transport` 参数），共用同一个浏览器：

```bash
node scripts/demo_probe.mjs   --port 9333 --transport worker
node scripts/input_probe.mjs  --port 9333 --transport worker
```

`input_probe`（25 项）发的是**真实键盘 / 鼠标 / 合成事件**，不调 API —— 它照的是
"输入层真的接上了没有"，API 面全绿时它仍可能红（实际红过两次：拖选坐标少除密度、
Worker 传输把 `hit` 吞成 null）。两条传输各跑一遍，最后一行的 `TRAIL` 应当逐位相同。

配套的一条纪律：**探针不许在批量模式下自己 `Browser.close`**。它们原来结尾都关浏览器，
于是批量跑只能跑第一个，第二个报"连不上 Chrome 调试端口 9222"。现在看
`HEDITOR_KEEP_BROWSER`（由 `verify_web.ps1` 在批量时置上），收浏览器统一交给脚本里那个
按 profile 杀进程树的 `finally`。

## 三、想改哪节就只跑哪节

`edit_and_caret` 每一节前面都有一道 `runSection(N)` 开关：

```bash
HEDITOR_TEST_ONLY="15,29" ./build/native/heditor_edit_tests.exe
```

不设变量 = 全跑（与没有这个开关时逐条相同，整跑仍是 1529 条）。改一行代码时先只跑相关那几节，
一秒出结果，最后再整跑一次 —— 这是日常最省时间的一件事，比任何并行都直接。

## 四、试过但不成立：分片并行

把 61 节按 `n % 4` 分给四个进程：

| 跑法 | 墙钟 |
| --- | --- |
| 整跑（单进程） | 50~59 s |
| bash 直接并行四片 | 39 s |
| 起四个进程（带输出重定向）并行四片 | 54 s |

四片并行只快 20%，因为单节是内存与光栅的重活，几个进程互相抢带宽；而且它多一层要维护的
假设（"节与节之间没有隐含依赖"，以及每片要各自付一次字体装载）。**没有采用**，代码里只留
了 `HEDITOR_TEST_ONLY`。

## 五、还没做、但算得出来的两笔

1. **字体字节跨引擎共享**：71 次 `init` × 56 ms ≈ 4 s。`FontFace::loadFromFile` 每次都把
   16.9 MB 读进自己的 `data_`，而同一轮里这些字节完全一样。`addFaceFromMemory` 已经有了，
   缺的是"一份字节按路径共享"的那层缓存（`data_` 要能指向共享块）。
2. **`[15]` 的 8.5 s**：还没拆开看。它是 200 段文档上的一串编辑 + 摘要比对，先把每段的
   耗时打出来再说，不猜。
