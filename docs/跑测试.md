# 跑测试：哪些是真的在等，哪些只是起停

一轮完整验证（native 四套 + wasm 构建 + 二十五份浏览器判据）原来要四分多钟，其中一半以上不是
在跑断言，而是在起服务、起浏览器、装字体、等进程退出。这一页记四件事：时间花在哪、
已经省掉了什么、性能判据为什么单独跑、哪些省钱的路子试过但不成立。

数字取自 2026-10-25 深夜，同一台机器（4 物理核 / 8 逻辑核 / 16 GB）。机器有负载时单节耗时
会有 ±20% 的抖动，所以下面的数看量级不看末位。

## 一、native：一份二进制，四片并行

`ctest --preset native` 跑九个用例：`edit_and_caret` 的四片、`shaping_and_layout`、
`doc_model`、`rev_layer`、`features`，外加性能那一片 `edit_perf`。预设里 `execution.jobs=4`，
墙钟 60~66 s（改动前串行 169 s；机器有负载时偏大）。

| 用例 | 时间 |
| --- | --- |
| `edit_and_caret_0..3`（四片） | 40.9 / 41.1 / 40.0 / 40.7 s（另一轮 44~45 s） |
| `shaping_and_layout` | 5.2~6.4 s |
| `doc_model` / `rev_layer` | 0.6 / 0.9 s |
| `features` | 1.1~1.6 s（双击选词、三击选段、水印、列宽行高、格线命中、拖拽移动、图片环绕） |

分片由二进制自己算：`tests/edit_test.cpp` 顶部有一张分节表（id、是否性能节、权重），
`HEDITOR_TEST_SHARD="i/4"` 时按权重从大到小贪心装进当前最轻的一片。四片实测差不到 3%。

权重的一个单位约合 250 ms，用 `HEDITOR_TEST_TIMES=1` 跑一遍就能重新量出来，别靠猜。

为什么不是"一节一个 ctest 用例"：每个进程有 2.5 s 固定开销（三张字体 + 共享前言那一次
整页呈现），75 节就是 187 s，比整跑还贵。分片是"每进程付一次固定开销"能接受的最小粒度。

## 二、性能判据单独跑

只有六条判据在比耗时，其余"写入量 / 重排段数 / 脏页数"都是结构量，机器再慢也不会翻。

- native 第 78 节：尾部敲字对全量、中部敲字对全量、后缀平移对续排。三条比值，前两条各测
  5 次取中位数，第三条各测 3 次取最小值。
- web `tests/perf/edit-perf.spec.ts`：增量对全量、增量对审计里的全量、页指纹对整篇。

跑法：

```bash
ctest --preset native-perf         # RUN_SERIAL，约 6 s
cd web && npm run test:perf        # 源码直连，单 worker 独占
cd web && npm run test:dist:perf   # 构建产物，先跑过一次 test:dist
```

为什么单独：这些判据比的是"省了多少"，同机上的其它 test 会把分子顶上去。实测四 worker 跑
全量时，`fonts` 的"注册字体不改画面"红过一次（帧指纹变了）—— 那一类假红正是这里要躲的。

## 三、web：trace 默认关，四 worker

| 口径 | 墙钟 | 全部用例耗时之和 |
| --- | --- | --- |
| 2 worker，trace 开（改动前） | 114 s | 298 s |
| 4 worker，trace 开 | 108 s | 298 s |
| 4 worker，trace 关 | 61 s | 180 s |
| 4 worker，trace 关，编辑面拆成七份 | 59 s | 172 s |

`trace: 'retain-on-failure'` 给每个 test 持续截图并抓 DOM 快照，全部用例的耗时之和因此
多出 118 s（最长那份从 45 s 涨到 86 s）。默认改成关，失败仍有截图、报错与附件；要回放就
`HEDITOR_TEST_TRACE=1` 重跑那一条。

并行度 4 是上限：六 worker 更慢（除 edit 那批 66 s → 72 s），而且当场把 `fonts` 的一条判据
顶红。每个 test 的装载固定开销 0.49~0.66 s（4 MB wasm 编译 + 17 MB 中文字体解析），
59 个 test 就是三十多秒 —— 这是并行省不掉的那部分。

编辑面那份 226 KB、367 条的单个 test 按域拆成七份（`edit-core` / `edit-form` /
`edit-boundary` / `edit-sweep` / `edit-longdoc` / `edit-fonts` / `edit-selection`）：
最长的一份从 45 s 降到 16 s，失败时报告直接指到域，不用在一个上千行的日志里找。

## 四、想改哪节就只跑哪节

native 的四个开关（都在 `tests/edit_test.cpp` 顶部实现）：

| 变量 | 作用 |
| --- | --- |
| `HEDITOR_TEST_ONLY="15,29"` | 只跑点名的几节（性能节也可以点名） |
| `HEDITOR_TEST_SHARD="1/4"` | 只跑第 1 片（0 起） |
| `HEDITOR_TEST_PERF=1` | 只跑性能节 |
| `HEDITOR_TEST_TIMES=1` | 收尾打印每节耗时，填权重要它 |

web 侧按文件跑：`cd web && npx playwright test tests/specs/edit-form.spec.ts`。
改一行代码时先只跑相关那几节或那一份，几秒出结果，最后再整跑一次 —— 这是日常最省时间的
一件事，比任何并行都直接。

## 五、试过但不成立

- 按节号取模分片：节号与体量相关（表格那几节都靠后、都重），实测最大片是最小片的两倍。
  改成按权重贪心之后四片差不到 3%。
- 一节一个 ctest 用例：每进程 2.5 s 固定开销，75 节 187 s。
- 六 worker：见上一节。
- 分片的前提是"节之间没有隐含依赖"。这一条原来不成立：有一处裸块（表格后空段落那三条）
  和共享前言不受 `runSection` 守卫，任何子集都会带上它们 —— 四片跑出 1778 条、整跑 1766 条
  就是这个差。现在两处都补了守卫，收尾还有一条对账判据（分节表与代码必须一一对应，
  新加的节忘了登记会当场红）。

## 六、还没做、但算得出来的两笔

1. **字体字节跨引擎共享**：每次 `EditorEngine::init` 都把 16.9 MB 中文字体读进自己的
   `data_`，而同一轮里这些字节完全一样。`addFaceFromMemory` 已经有了，缺的是"一份字节按
   路径共享"的那层缓存（`data_` 要能指向共享块）。
2. **页面复用**：每个 test 一次装载 0.5 s，worker 级复用能省三十多秒。但判据都假设
   "一个 test 一个干净页面"，改动面比收益大，暂时不做。

`edit` 那七份合起来 382 条，与拆分前逐条对应：判据名一条不改，只换了文件与用例边界。

spec 文件按功能域建，不按交付批次建：一份对应一个域，域内用 `describe` 分节。
新功能往所属域里加用例，修缺陷也往引入它的那个域里加一条钉住该缺陷的判据。
按"这一轮新增"或"这一轮修复"建文件，等于给每个批次开一个抽屉：同一个模块保证什么
要跨几份文件拼，而且旧抽屉不再增补，最后没人知道某条保证还在不在。

输入探针每步写一条轨迹，失败时作为附件留档 —— 判据仍是一次性求值，轨迹只用来复盘。

三条硬规则写在 `web/tests/support/check.ts` 与 `docs/web测试工程化评估-Playwright.md`：

断言一次性求值，禁 `expect.poll` 与 locator 断言 —— 引擎状态判据必须"调用返回后立刻读"，
自动重试会把同步性回归改成绿。像素账以旧探针的值为基线，视口 / DPR / 浏览器版本任何一项
都不能动；所以浏览器用 `channel: 'chrome'` 复用已装那一份，不下载 Chromium。

**常用操作要有全景判据**（`smoke.spec`）：工具栏每个按钮、公开面每个方法都走一遍并逐条判
效果。单点判据只钉"某条路对不对"，而"点下去没反应""返回 true 但画面没变"这类问题恰恰
漏在缝里 —— 别等用户点出来才补一条。引擎侧那半边靠两份自审（`diag.auditCompile()` 与
`diag.auditLayout()` 的 `diff` 必须为 0）：它们当场回答"增量产物还是不是全量的那份"。

反证做过两次：把 `editor.ts` 里的缩放上限从 2.25 临时改成 2.5，`demo` 立刻红两条；
把 `edit` 的滚动等待去掉，`stress` 与 `edit` 的平移复用判据在机器有负载时红。

迁移里遇到两处需要交代的差异：

`stress` 的帧差有一处恰好等于光标矩形（2x28 px，56 px）。成因是光标从不可见转为可见
（按键会重置闪烁相位）时，增量帧与整帧重画差出一个光标 —— 内容层完全一致。判据对"帧差
只落在光标矩形上"补一次 `present` 再问一遍；补完仍差就照算不一致，不因为能被修好就放松。

逐页滚动的 8 拍原先只等两帧。Worker 传输下这一拍要跨线程往返，机器有负载时读到的还是
换窗前的账，于是"平移复用"那条会偶发红。改成与跳页同一个口径（安静 180 ms 再对齐），
等的是滚动停下来，不是等断言成立。

## 八、临时诊断：用 Playwright 现写，用完即删

旧的十八份 `scripts/diag_*.mjs` 与 `scripts/cdp.mjs` 已删（2026-10-22）。它们不是工具，
每次都是"为某一个现象写的取证脚本"：等 `window.__heditor` 出现、用 CDP 逐步派事件、把中间
读数打出来。而那个门面名已经不存在了 —— 现在页面运行时 `window.__heditor` 是 `undefined`
（`demo.spec` 里有一条判据专门钉这一点），所以它们全部是等满 60 秒超时的死代码，唯一的消费者
是彼此（`cdp.mjs` 只被这十八份引用）。它们的结论都还在 `.workbuddy/memory/` 的每日日志里。

要再临时诊断，直接写一份 spec，跑完删：

```ts
// web/tests/specs/tmp.spec.ts —— 用完即删，不要提交
import { test } from '../support/probe';

test('复现：删空三连字段之后打字进了哪个字段', async ({ open }) => {
  const p = await open('index.html', { query: { debug: '1' } });
  const r = await p.read(`
    await D.setFormControls([...]);
    return { controls: D.controls(), caret: CARET() };`);
  console.log(JSON.stringify(r, null, 2));
});
```

`read()` 与 `ev()` 的分工：`read` 在前面拼一段读数前言（`H` / `D` 两个别名，加 `CARET` /
`SEL` / `FRAME` / `ZOOM` / `TYPE` / `MOVE` / `LOAD` 这些测试动作，见
`web/tests/support/readings.ts`），要求页面带 `debug=1`；`ev` 不拼，用在没有诊断面的页面上
（`demo` 的公开面判据就是这一类）。要读 `editStats` / `selfCheck` 这类诊断面成员就用 `read`。

比旧脚本省掉的全是场地费：静态服务、Chrome 生命周期、CDP 连接、console 收集。`open` 已经
等过 boot，`p.ev` 是异步 IIFE（可以写 `await`），`p.shot('名字')` 落一张截图，
失败自动带截图与报错。

`p.ev` 是唯一要注意的地方：它不接受"等一会儿再看"的写法。想量"若干拍之后"的状态，就在
页面里 `await` 那个拍（`flush()` / `quiesce()`），不要在外面 sleep —— 那是把同步性判据
换成时序运气。

三条旧惯例仍然成立：先做最小复现、跑一次对照（"改回去还在不在"）、用完即删。
留在 `scripts/` 下的取证脚本没人跑得起来，这一批十八份就是前例。
