# 实现与设计复核（2026-10-20）：哪里跑偏、哪里是设计时没想到

方法：把 `docs/重构方案-2026-10-19.md` 的 D1–D6、`docs/架构复核-2026-10-19.md` 的 P1–P8、
`docs/正式化架构与迁移路线.md` 的阶段表当作"设计"，逐条到代码里找落点。找不到落点的分三类：

- **跑偏**：设计写明了、实现没做，日志里也没有记成欠账；
- **欠账/延期**：设计或日志里记了"还没做"，这里只复核它是否仍然成立；
- **设计缺口**：设计当时没想到，落地时才暴露，只能妥协或补结构。

标注"实测"的都有可复现的最小形状（第十节）；标注"未实测"的只有代码路径，别当成结论用。

---

## 零、一句话

**换掉了数据源，没有换掉形状。**

修订层是真的：引擎只持 `rev::Session`，编辑只产 `Step`，撤销就是拿回旧修订，投影带哈希记忆化、
块流由调用方持有并原地 splice。这些都不是装饰，代码路径上确实只有一条。

但 D3 说的"七个并行数组收成一份快照"没有发生 —— 那七个数组一个没少，位置索引仍由三段事后递推
补出来。更要紧的是这次复核实测到**两个同根的正确性缺陷**：流位置与块数都是"随编辑模式变"的量，
而携带它们的两个类型（`Step`、`BlockDamage`）都没有带上"按哪个可见性算的"。一个让字打错位置，
一个让块被搬重。

补丁的数量少了，补丁的**形态**还在。原因不是懒，是那个缺口一直没被写成一条不变量：
"任何一个跨层传递的坐标，必须自带它的口径（可见性 / 侧别 / 哪一侧的块序）"。

## 二、跑偏：数据源换了，形状没换

### 2.1 D3 说"七个数组不存在了"，它们一个没少

`重构方案` 第 87–89 行：

> `project` = 今天的编译 + 流索引 + 控件导出，**一次遍历同时产出**：块、对象表、格表、控件表、
> 位置索引。没有 `blocks_` / `blocks_full_` / `flow_` / `block_flow_` / `block_src_` /
> `control_node_ids_` / `owner_index_` 七份东西。

现状（`engine.h`）：

| 成员 | 行 | 现状 |
| --- | --- | --- |
| `blocks_` | 1250 | 在（Focused 档的筛过副本） |
| `blocks_full_` | 1277 | 在（原件） |
| `flow_` | 1304 | 在（`optional<rev::FlowIndex>`） |
| `block_flow_` | 1309 | 在（每块起点，事后递推） |
| `block_flow_span_` | 1314 | 在（每块位数，事后递推） |
| `block_src_` | 1319 | 在（从 `proj_hist_.keys` 循环抄一遍） |
| `control_node_ids_` / `owner_index_` | 1290 / 1295 | 在（从块流再导出一次） |
| `tables_` | 1286 | 在 |
| `proj_hist_` | 1264 | 新增（上一轮身份账，32 B/块） |

D3 的"一份 `Projection`"只做到了一半：产物里确实有 `keys` / `controls` / `tables`，但引擎没有
"只持一份快照"，而是把它们再拆回自己的成员。成员数因此与复核时持平（复核记 61 个，现在仍在
60 上下），"引擎不再有 60 个成员"这一句没有兑现。

**这不是纯粹的洁癖问题**：拆回成员意味着每一份都要有一次填装，而填装分散在三个函数里
（`rebuildFromTree` 填 keys/tables → `finishRebuildFromTree` 填 flow/block_flow/block_src →
`exportControlsFromBlocks` 填 controls/owner_index）。每加一种产物，就要在三个地方各加一段，
这正是复核 1.2 那五个"回头重建"点的形状。

### 2.2 位置索引没有随投影产出，两处 `max` 的化石还在

D3 明确把"位置索引"列进投影的同一次遍历。现状：

- `project` 的产物里没有任何流位置字段（`project.h:98-123`）；
- 引擎在 `finishRebuildFromTree`（`engine.cpp:236-311`）里重新走一遍流索引，再按段落标记递推
  `block_flow_` / `block_flow_span_`，其中：

```cpp
// engine.cpp:283-286
if (!block_src_.empty() && i < block_src_.size() &&
    flow_->intervalOf(block_src_[i].first, &first_lo, nullptr) && first_lo > start) {
    start = first_lo;      // ← 「取较大值」：第二次事故的化石
}
```

以及标记查不到时的兜底：

```cpp
// engine.cpp:297-300
block_flow_span_[i] =
    static_cast<int>(blocks_full_[i].cp_text.size() + blocks_full_[i].objects.size());
```

这两处正是 `架构复核` 2.2 诊断过的东西："编译层本来就在按流顺序走同一棵树，在同一个遍历里记
一个位置计数器就能直接给出每块的流起点与跨度，不需要事后拿节点 id 去查区间、再和递推值打架。"
重构把"编译层"换成了"投影层"，投影也确实按流顺序走，但**位置没有在那一刻被记下来** —— 于是
同一段补丁以原样留在了引擎里。

为什么当时没做：`ProjectedBlock` 只有 `spec/source/hash` 三个字段，`BlockSpec` 不接收流位置，
`Walker::flush` 手里也没有"当前流位"这个变量（它只数了 `cpCount()`）。要补，得让 Walker 在
`walk` 里维护一个 `flow_cursor_`（它走过的每个节点恰好就是 `FlowIndex::measure` 数的那些位），
`flush` 时把 `[start, end)` 写进 `ProjectedBlock`。这是一次小改，但会动 `project` 的产物形状，
所以与 2.1 是同一件事。

### 2.3 `ParaDelta` 成了空壳

`EditHost::commitSteps(steps, dirty_para, ParaDelta delta, before, after)`（`edit_command.h:70`），
引擎第一行就是 `(void)delta;`（`engine.cpp:438`）。而命令层仍有 8 处按形状构造它：

```cpp
commit(std::move(steps), p.para, ParaDelta{true, p.para, 1})   // 分段
commit(std::move(steps), dirty, structural ? ParaDelta{true} : ParaDelta{})  // 改控件属性
```

`ParaDelta` 的三个字段（`changed/at/inserted`）在重构方案里被判了死刑（P2："不需要 `ParaDelta`、
不需要 13 个 reject 码"），现在它既不读也不删，变成"第二种损伤表达"的化石。危害不是性能，是
**下一个人会以为它有用**：改分段逻辑时顺手把 `inserted` 填对，然后发现没有任何效果。

### 2.4 `Projection.controls` 算完就扔，控件导出仍全表重做

投影每次都为每个控件产出一条 `ControlSpan`（`project.cpp:373-392`），但引擎一次都没读它
（grep `res.controls` 为 0）。引擎用自己的 `exportControlsFromBlocks`（`engine.cpp:329-388`）
从 `blocks_full_` 重新扫一遍对象表，再对每个控件 `rev::findNode`（线性，`engine.cpp:375`）
取业务标识。

于是"控件表有两份"这件事在复核 1.3 里被记过一次，重构之后仍然是两份 —— 只是第二份从
"模型层的 `ControlIndex`"换成了"投影算完丢掉、引擎再算一遍"。判据也还停在"成对计数"
（`engine_audit.cpp:267`），没有验证两份的区间一致。

顺带一个量：`findNode` 是线性扫描，表单文档 1000 个控件 × 4000 个节点 ≈ 每次按键 4×10⁶ 次
指针追逐（估算，未采样）。这一项没有出现在任何性能账里。

### 2.5 撤销：投影增量了，排版仍整篇

`undo()` 先算 `damage` 并走增量投影（`engine.cpp:470-471`），紧接着
`markAllLayoutDirty()`（`engine.cpp:473`），重做同（`engine.cpp:489`）。

`重构方案` 10.13 记过这一笔（"撤销 整篇（`markAllLayoutDirty`）"），10.14 说"撤销的 damage
与那次编辑相同，所以接上之后撤销也一并回到同价"——**只接了投影那一半，排版那一半没接**。
今天撤销仍然比一次编辑贵，而 D1 的卖点恰恰是"撤销与那次编辑同价"。

排版侧能不能接：`markLayoutDirty(dirty_para)` 需要"最靠前的脏段"，而批步骤可能跨段。现在
`EditCommand` 每条路径都知道 `dirty_para`，`undo` 却没存它。补法是让 `SelectionRecord` 旁边
再记一个 `dirty_para`（或直接记 `damage` 的块区间经 `block_src_` 反查段号），撤销时用它代替
`markAllLayoutDirty`。属于欠账，不是缺口。

## 三、设计缺口（实测，两条同根）：可见性是坐标的隐藏参数

### 3.1 步骤的流位置按 Display 算，`rev::applySteps` 按 Design 解释 —— 字打错位置

代码路径：

1. 引擎的 `flow_` 按 `flowVisibility()` 建：文档模式 `Design`，表单/只读 `Display`
   （`engine.cpp:204-208`、`engine.cpp:240`）；
2. 命令层用这个索引造步骤：`at_flow = pos().flowPosAtSide(para, at, side)`（`edit_command.cpp:254`、
   `601`），`Step::at` 是一个裸 `FlowPos`；
3. `rev::applySteps` 收到它，但内部每一处 `FlowIndex` 都写死 `FlowVisibility::Design`
   （`rev/steps.cpp:143`、`194`、`283`、`390`、`439`）。

所以只要有一个隐藏控件（表单模式才摘除），隐藏子树之前/之后的所有流位置就差一个
"隐藏子树的流位数"。

**实测**（临时探针，已撤）：`AABB` 中间插一个隐藏控件 `XX`，呈现态下"AA 之后"是位置 2；
在该位置插 `Z`：

```
display size=7  design size=11
after insert at display-flow 2: text=AZAXXBB
```

期望 `AAZXXBB`（Z 落在 `AA` 与控件之间），实际 `AZAXXBB`（Z 落进 `AA` 中间）。偏移量就是隐藏子树的那一段
（控件两枚边界 + 两个字），所以落点从"控件之前"退到了 `AA` 中间。

危害：表单模式（产品主线）+ 任一隐藏字段，之后的所有编辑都落在错的位置；偏移量足够大时会
落进别的字段（编辑被策略拒绝，表现为"点进去打不了字"），偏移量小时静默改错文本。

### 3.2 `damage` 的块数不带可见性 —— 块被搬重

`damage(before, after)` 的坐标来自 `Node::paras`（`project.cpp:657-689`），而 `paras` 数的是
**所有**段落标记，不分可见性；投影按 `Display` 跳过隐藏子树（`project.cpp:320`）。两个"块数"
因此不是同一个数。

**实测**（临时探针，已撤）：`AABB` 里插控件 `XXYY`，在控件内部（偏移 4）分段，再把控件隐藏。
此时：

```
display blocks=1  design blocks=2  damage.after_blocks=2  lo=0 hi=1
after incremental project: before=1 after=2 reused=0
```

引擎那一拍是 `before_blocks = blocks_->size()`（Display 的 1），`after_blocks = 2`，于是
`shift = +1`，旧区间右端算成 `max(0, hi - shift) = 0` —— **一块都不删**，再把 1 块插进去，
块流变成 2 块，而正确的全量是 1 块。旧内容的块留在原地，表现为**段落重复**。

现有的安全网（`project.cpp:63-75` 的 `fresh.size() != hi - lo`）抓不到它：它校验的是"区间长度
与物化块数相等"（1 == 1），而错的是**总数**。TRAPS 121 记的"两侧块数不同要补 shift"在这里
反过来咬了一口 —— shift 本身算错了。

同一条缺陷也在撤销路径上（`undo/redo` 同样用 `damage(before, after)` 配 Display 的块流），
所以"编辑一次再撤销"可能变成"重复一段再少一段"。

### 3.3 为什么设计没兜住

`重构方案` 405 行其实写下了关键一句：

> `hidden` 放在节点上而不是载荷里 —— 它对任何节点都成立，且**呈现态下它决定的是位置空间**，
> 所以进哈希。

"决定位置空间"这句话是对的，但只落到了哈希（`hidden` 进 `hashSelf`），没有落到**坐标类型**上。
D2 说"位置只有一种：流位置"，这句话在"同一个可见性之下"成立；跨模式传递时，流位置是一个
二元组（位置，可见性），而 `Step::at` 与 `BlockDamage` 都只带了前者。

这不是"实现没按设计做"，是设计本身漏了一个参数：它把"模式"当成了引擎的外部状态，忘了它会
改变坐标的含义。同类的东西在项目里已经有过一次（TRAPS 81 的 `optional` 地址、TRAPS 114 的
根节点漏压栈），形状都是"某个上下文没有随坐标一起传下去"。

### 3.4 修法与判据

**步骤侧**（3.1）：给 `applySteps` 加一个 `FlowVisibility` 参数，`steps.cpp` 里五处 `FlowIndex`
全用它；`Session::applySteps` 透传；引擎传 `flowVisibility()`。`Session::apply(const Edit&)`
不受影响 —— 它用 `(para, cp)`，那个坐标与可见性无关（`paraTexts` 也不过滤），这也是为什么
两条入口里只有 `Step` 这一条出了事。

**损伤侧**（3.2）：`damage(before, after, vis)`，并把"该可见性下这棵子树有几个段落标记"变成
节点上的第二个顺序统计量（`paras_display = hidden ? 0 : Σ 孩子`，不进哈希）。`endsOpen` 也要
按 vis 判（末尾是隐藏控件时，Design 是"开放段"、Display 不是）。

**判据**（每条都要能红）：

1. 表单模式 + 隐藏控件（控件内含段落标记）+ 在它之后插字：文本与全量投影逐字段相同；
2. 同上 + 退格 / 分段 / 合并 各一条；
3. 同上 + 编辑后撤销：块数与全量相同（防 3.2 的重复段）；
4. `damage(before, after, Display).after_blocks == project(..., Display).keys.size()`，四种形状
   （文本 / 控件 / 控件内分段 / 表格）；
5. 反向一半：没有隐藏控件时，加 vis 参数前后逐字节不变（`rev_test` 现有 278 条全绿）。

## 四、设计缺口（结构代价，不是 bug）

### 4.1 `NodeId` 水位让"按 id 下表"的结构随会话变长

`rev::FlowIndex` 的注释与实现都按"节点号 ≈ 节点数"设计：

```cpp
// flow.cpp:25-28
const size_t slots = static_cast<size_t>(doc.next_id) + 1;
by_id_.assign(slots, nullptr);
first_.assign(slots, -1);
span_.assign(slots, 0);
```

但不可变树每次编辑都分配新 id（切 run 一次 1~2 个），`next_id` 是**累积**的，活节点数不是。
2000 段文档编辑 1 万次之后 `next_id` 约 3 万，这三个数组合计约 0.5 MB，而且每次构造都要
`assign`（分配 + 清零）。一次按键要构造几次：`slotAtFlow` 一次、`insertRunAt` 可能再一次、
`finishRebuildFromTree` 一次 —— 3 次上下。

这是设计时没算到的：D1 说"节点号跨修订稳定"，这是对的；但"按节点号直接下标"隐含了
"id 空间有界"，而不可变树的 id 空间随编辑次数单调增长。短会话看不出来，长会话里它是
一条只随时间变差的曲线（正是最难复现的那类）。

改法：位置表按"活节点重新编号"建（遍历时给每个节点一个紧凑下标），或者换开放寻址哈希。
前者与 2.2 的"投影时顺带产出位置索引"是同一件事 —— 一次遍历里既数流位又发紧凑号。

判据：编辑 5000 次后重建一次 `FlowIndex`，分配字节数与文档规模同阶（不随 `next_id` 线性）。

### 4.2 一次编辑仍是 O(文档)，不是 O(路径)

D1 的"2000 段敲一个字，新分配十来个节点"只对**树**成立。一次按键的完整路径上还有：

- `slotAtFlow` 构造全篇 `FlowIndex`（`steps.cpp:143`），切 run 时再来一次（`166`）；
- `pathTo` 从根做一次全树 DFS（`steps.cpp:23-31`），每个原语至少一次；
- `findNode` 线性扫描（`rev.cpp`），每步数次；
- `normalize()` 全树走一遍，每个容器分配一个 `kids` 向量（`steps.cpp:617-658`）。

所以拿到的是"常数更小"，不是"最坏情况消失"（第九节的目标）。`重构方案` 9.4 那条"每次按键堆
分配 ≤ 100 次"按结构现在不可能成立（未实测次数，但 2000 段至少一次 2000 元素的 `kids` 向量）。

这一条不必马上改：投影与排版已经是增量，编辑这一层的 O(n) 在当前规模下是 3 ms 里的小头。
但要写进文档，别让人以为 D1 的局部性已经拿到 —— 否则下一次有人按"O(1) 编辑"去做缓存或并发，
会得到错误的结论。

### 4.3 选区快照栈与撤销栈的裁剪不同步

- `recordSelection` 自己按 `undoLimit()` 裁 `sel_history_`（`engine.cpp:453-464`）；
- `setConfig` 改上限时只 `session_->setLimit(undoLimit())`（`engine.cpp:151`），不碰
  `sel_history_`。

运行中把上限从 10 调到 2：撤销栈剩 2 份，选区栈还有 10 份；再撤两次，`sel_pos_` 指到第 8 份，
恢复的是早就被丢掉的那一步的选区。症状是"撤销内容对了、光标跳到一个无关的位置"，不会崩。

另有一处 0 的语义分叉：`setDocument` 用 `cfg_.undo_limit` 直接建会话（`engine.cpp:184`），
而 `undoLimit()` 才把 0 翻成"不限"（`engine.cpp:434`）。于是"先设 0 再装载"= 没有历史，
"先装载再设 0" = 不限历史 —— 同一个配置值，两种行为，取决于调用顺序。

改法：把选区快照并进 `Session`（两栈同进同出），或至少让 `setLimit` 同时裁剪两处，并让
`setDocument` 走 `undoLimit()`。

### 4.4 Focused 档：光标与排版读的不是同一份对象表（未实测）

`CaretResolver::objectsFor` 恒读 `blocks_full_`（`caret.cpp:88-92`），而 Focused 档排版吃的是
筛过的 `blocks_`。光标的侧别由 `bracketCountsAt` 数**全部**边界得出（`caret.cpp:111-118`），
落到行盒时 `offsetAtSide` 又把 side 夹到"本偏移上实际显示的占位簇数"
（`layout.h:701-717`）。两个数不一致时，光标会贴到该偏移的最后一个占位簇之后。

未实测（要引擎 + 字体），复现配方：Focused 档，一段里两个相邻空控件，光标移进第二个控件，
比较 `caretRectPt().x` 与 `controlRects(1)` 的左缘。如果两者差一个括号宽，就是这个问题。
它与 3.1/3.2 同族：**两个读者对"同一份对象表"的理解不同**。

"换就整个换掉"执行到引擎为止。`src/core/doc` 仍是 11,459 行，其中约 2,000 行是**与引擎无关的

建议：在四个文件顶部写死"只作参照，不得新增功能"；`control_api`/`validation` 产品无出口，
可以考虑直接删（连带 `model_test` 里那几十条），把"设值"作为一组命令补进 rev 侧，再接一个
引擎出口 —— 那本来就是 P8 的第二件。

## 十一、结论

1. **主干没跑偏**：修订是唯一真值、写入口唯一、撤销=旧值、投影增量、差分判据都在。这些不是
   文档上的说法，是代码路径上只有一条。
2. **形状没换完**：D3 的"一份快照"没做到，七个数组一个没少，位置索引仍在投影之外由三段递推
   补出来，`ParaDelta` 与 `Projection.controls` 是两处算完不用/不读的化石。
3. **两处真缺陷同根**：可见性没有随坐标传下去。一个让表单模式的字打错位置，一个让块被搬重
   （段落重复）。这是"设计时没想到"，不是"实现没按设计"，所以修法要动类型而不是加判断。
4. **路线层面**：把 P8 推到最后是可以辩护的，但"文档存不下来"这条产品缺口到今天还在；它是
   现在最便宜的一刀。
