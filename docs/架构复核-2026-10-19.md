# 架构复核：数据流、重复状态与已经积起来的补丁

复核日期 2026-10-19。范围是整个交付链路（模型 → 编译 → 排版 → 帧 → 宿主），不是某一刀。
方法：读头文件里的契约与实现里的分支，不看单条缺陷；凡是"同一件事在两处各写一遍"的地方，
顺着写入口反查有几个写点。本文只写结论与证据，不复述既有评审（`docs/代码审查与架构评估.md`）
里已经解决的部分。

> ★ 同日夜间追记：本文写完到落地之间有两项改动 —— 自写扫描线光栅器删除（两侧共用 Skia）、
> 两套宿主合并（命令表、输入层、缩放换算各收成一份）。受影响的小节已就地改正并标注：
> 1.3（页几何、窗口上限、槽数）、2.5（宿主）、P7（宿主门面）、五.3、六.4、七 的最后一条。

## 零、一句话结论

主干是单向的（树 → 产物 → 排版 → 帧），这一点守住了。**但增量是横向同步出来的，不是纵向传下去的**
—— 编辑改了哪一块，这件事在每一步都被"重新猜一遍"而不是"带下去"，于是每一层都长出了自己的
判据、自己的失效标记、自己的审计。重复状态不是当年的三份文档了，剩下的是**三份文本、五个选区字段、
八本呈现账**，以及五个"回头重建"的岔口。补丁不是乱打的，它们形状一致：**缺一个显式的"变更"对象**。

## 一、数据流的实况

### 1.1 主干（这一段是干净的）

```
NodeTree ──compileDocument──▶ blocks/tables ──layout──▶ LayoutResult ──paint──▶ base_ ──▶ bitmap_ ──▶ 画布
   ▲                                                                                        │
   └──────────────── EditCommand ── Transaction ── commitEdit ◀──────────────────────────────┘
```

编译只读树、产物是快照、排版只吃块流、绘制只吃排版结果 —— 这四条契约在头文件里写死了，
实现里也守住了（`compile.h`、`layout.h` 顶部）。这是本仓最值钱的部分，不要动。

### 1.2 主干之外的五个"回头重建"点

| # | 重建的东西 | 谁在重建 | 为什么必须重建 | 代价 |
| --- | --- | --- | --- | --- |
| 1 | 每块的流起点 `block_flow_` / 跨度 | `finishRebuildFromTree`（engine.cpp:306-382） | 编译只给节点身份（`BlockSource`），不给流位置 | 全表重算，且有两处 `max(递推值, 区间起点)` 的补丁 |
| 2 | 脏到哪一段 | `ParaDelta`（三个字段）+ 13 个 reject 码（engine.cpp:392-465） | 步骤里不记"改了哪几块"，只能从树的形状反推 | 形状不认识就整树重编；新增内容类型（表格）时只能"一律不做增量" |
| 3 | 撤销/重做影响哪一段 | `undo()`：`rebuildFromTree()` + `markAllLayoutDirty()`（engine.cpp:616-643） | 事务只还原文档，不还原"改了哪儿" | 长文档里 Ctrl+Z 是整篇重编 + 整篇重排，比打字贵一个数量级 |
| 4 | 控件区间 | `exportControlsFromBlocks`（engine.cpp:483-549） | 控件是产物的投影 | 每次重建全表导出 + `normalize()` |
| 5 | 宿主手里的文档 | `g_blocks` + `syncBlocksFromEngine()`（wasm_main.cpp:148/325/853） | 没有"把树拿出来"的出口 | 改一次字段名单就从块流重建整棵树；重建是**有损**的（见 P8） |

这五处是同一件事的五种写法：**改动的影响面在产生它的那一刻是已知的，却没有被带下去**。

### 1.3 同一份数据的副本清单

| 数据 | 几份 | 位置 | 判断 |
| --- | --- | --- | --- |
| 文档文本 | **3**（wasm 演示装载时 4） | `tree_` 的文本节点、`blocks_full_[].cp_text`、`blocks_[].cp_text`、`g_blocks` | 后两份是整份深拷贝，每次按键重做一遍（engine.cpp:377） |
| 块流对象表 | 2 | `blocks_`（按聚焦筛过）、`blocks_full_`（原件） | 只有 `objects` 一个字段不同，却把整份 `BlockSpec` 拷了一遍；侧别在 full 里数、绘制在筛过的占位里夹，两套口径靠一次 clamp 对齐（刻意的不对称，但没有断言守着） |
| 表格的"格 ↔ 块" | 2 | 块的 `cell_path`、`LayoutCell::first_block/block_count` | 编译同一次遍历产出，但两个写入口，于是需要 `auditTables` 永久对账 |
| 光标/选区 | **5** 个字段 | `sel_`、`sel_cell_`、`cell_lo_/hi_`、`cell_blocks_`、`cell_mask_`、`cell_caret_`（caret.h:464-499） | 只有 `sel_` 与 `cell_blocks_` 是输入，其余四项都能现算 |
| 控件表 | 2 | 引擎 `ControlSet`（按段/偏移）、模型 `ControlIndex`（按 id/key） | 两个口径都对，但没有一处契约说明差异；`ControlApi` 还没接到引擎（见 P8） |
| 页几何 | 3（合并前 4） | 引擎 `cfg_.page`、`web/app.js` 与 `web/engine_api.js` 各一份 A4 常量，`kZoomBase = 4/3` 在 `engine_api.js` 的常量与 `host_core.createZoom` 的默认值里各一份 | 宿主合并去掉一份，仍是"改一处要记得改两处"；`app.js` 调 `createZoom` 时还把 4/3 写了第三遍 |
| 窗口上限 | 2 | `engine_api.js:161-172` 读 `mod.pagePx*`，`app.js:395-406` 读 `api.read('pagePx*')` | 三个常量同值、公式逐字相同，只差"页面度量从哪读"；两边注释都写着"同一口径" |
| 槽数 | 3 | 引擎 `frame_slot_count_`、`engine_api` 的 `syncFrameSlots`、宿主 `slotCanvases.length`，外加 `geom` 里的 `frameSlots/slots` 两个同值字段 | 注释已经写明"必须相等"—— 靠注释维持的相等就是将来的一次错位 |
| "画面上现在是什么" | **8** 本账 | `base_valid_`、`slot_page_`、`page_fp_*_`、`line_fp_*_`、`line_lo/hi_in_base_`、`mark_sig_prev_`、`*_prev_` 三个矩形表、`frame_needs_full_refresh_` | 每本账一个失效点，漏一个就是"画面没更新"或"残留" |

### 1.4 两处"回头路"与一处可写派生量

主干之外还有三条绕过提交路径的口子，它们不属于增量，属于**写入口不唯一**：

1. `ControlApi` 直接往 `UndoStack` 提交（control_api.cpp 的 `flush`），不经过
   `EditHost::commitEdit` —— 设值成功、树变了、引擎一无所知；全仓除 `validation.cpp` 与测试外无调用者。
2. 宿主侧的 `g_blocks` 走 `setDocument` 整份换树（wasm_main.cpp:287-315），绕过事务与撤销栈：
   重建之后撤销栈被整个丢掉（engine.cpp:182-185），用户之前的撤销记录一起没了。
3. `EditorEngine::controls()` 返回可写的 `ControlSet&`（engine.h:429）。它现在是编译产物的投影，
   外部改一下，下一次 `rebuildFromTree` 就被覆盖 —— 静默。树路应该只暴露 const。

只要这三条还在，"数据流单向"就只是主干的性质，不是整个系统的性质。

## 二、补丁的形状：六类，一个根因

### 2.1 增量重建：用"形状启发式"代替"变更"

- `ParaDelta{changed, at, inserted}` 只能表达"某段之后插入/删除了整段"；
- `rebuildAfterSplit` 为了找到新插入的那枚段落标记，**在容器里往回扫**，再用区间是否相接来确认
  （engine.cpp:415-445）；
- 13 个 `reject(code)` 是 13 种"这个形状我接不住"；
- `commitEdit` 按 `delta.changed` 三分支，删除整段（`inserted < 0`）没有局部路径；
- 撤销连 `ParaDelta` 都没有，直接整篇。

还有一条更贵的：**后缀复用对带控件的文档实际失效**。`trySuffixReuse` 从脏区之后扫一遍，
只要后缀里有一段带非原子行内对象就返回 `None`（engine_layout.cpp:461-473）—— 而表单文档里
括号对象几乎每段都有。于是"在长表单文档的中段打字"退化成"从脏段重排到末尾"，不是整篇，
但也随文档长度线性涨。这条没量过，建议在动手 P2 之前先量一次：它是 P2 最直接的一份收益证据。

这是典型的"重新推导变更"。步骤在 `applyStep` 的那一刻**知道**自己插了哪枚标记、删了哪几个节点 ——
`InsertNode` 甚至已经把 `detached` 的 id 存下来了（steps.h:122-127），`InsertParaMark` 却什么也不记。
信息在产生点被丢掉，下一层只好猜。

### 2.2 坐标：用"事后递推"代替"当场计数"

`block_flow_` 的递推里有两处 `max`：

- 表格的格边界夹在"上一条递推值"与"本块 first 的区间起点"之间（engine.cpp:347-356）；
- 控件从中间切开时，`first` 是控件节点、起点偏前，要取递推值。

两处注释都在解释"为什么这里要取较大值"。这不是算法，这是两次事故的化石。编译层本来就在
按流顺序走同一棵树，**在同一个遍历里记一个位置计数器**就能直接给出每块的流起点与跨度，
不需要事后拿节点 id 去查区间、再和递推值打架。

### 2.3 选区：一个概念，五个字段，三个谓词

| 谓词 | 为真的条件 | 谁会读错 |
| --- | --- | --- |
| `hasSelection()` | `sel_` 非空 | 空格整格选中时为假（内容是 0 长），于是 `planEraseSelection` 直接返回（edit_command.cpp:698） |
| `selectionIsCell()` | `sel_cell_ && (sel_ 非空 \|\| cell_blocks_ 非空)` | 与上一个不是粗细两档，是真假表 |
| `hasCellRange()` | `sel_cell_ && cell_blocks_ 非空` | 全选为假、整格为真 |

三个谓词各自都说得清，合起来没人能一遍读对。`cell_lo_/hi_` 是 `cell_blocks_` 的 min/max，
`cell_mask_` 是它合并后的区间表，`cell_caret_` 是焦点格的末尾 —— 三个派生量都存着，
于是每个写入口都要记得 `clearCellRange()`（现在有 5 处）。

### 2.4 呈现：一本账一个失效点

`presentInternal` 单函数 **742 行**（engine_paint.cpp:216-957），读 41 个私有成员（台账 10-19 统计）。
它同时在管五件事：窗口/槽、页指纹差分、行带差分、底图重画、覆盖层擦与画。每一件事都有自己的
"变了没有"判据，而判据之间没有共同的时间基准。

### 2.5 宿主：三处写法收成两处，剩下一处在 C++ 侧

写完本文当晚两套宿主合并了：命令表与状态归属进 `web/engine_api.js`（1135 行），
输入层与缩放换算进 `web/host_core.js`（315 行），`app.js` 里 `mod.` 字面量归零。
原来"同一份协议知识三处写法"（命令表、直调点、宿主门面）现在只剩两处：

- **JS 侧**：一张命令表（`engine_api.js` 的 `WRITE` / `READ`）同时服务两个宿主，
  `PRESENT_ALWAYS` 也从"每个宿主手抄一份"变成一处（engine_api.js:259）。
  漏一条的症状还是"帧画好了、画布还是旧的"（台账记过量到 557 ms），但漏的机会少了。
- **C++ 侧**：wasm 导出的函数名与 JSON 字段仍是手写的，与命令表没有对上号的判据，
  漏一个只在跑探针时暴露 —— 这是 P7 剩下的那一半。
- `mirror` 的 `m.x || mirror.x` 兜底还在（worker_host.js:791-801），"这一拍没有这个字段"
  与"值是空的"仍然分不开，旧值会留着。

同名函数从 11 个降到 8 个，剩下的是 `frameSlotOf`、`setStatus`、`positionIme`、
`syncPageCanvases` 这类依赖本侧 DOM 的，以及窗口与滚动那一层 —— 按
`docs/一个引擎API与两种传输.md` 第 5 节，那是两套所有权模型，不是重复。

### 2.6 文档债：注释跟着方法走了，注释没走

`engine.h` 1546 行、约 143 个公开方法、61 个数据成员，其中 **24 处块注释后面没有声明**
（现在落在 916-1029 一段连续 22 处，外加 1077 与 1388；行号会随文件变动，形状是"块注释结束
之后紧跟另一段块注释"，用脚本按这个形状找，别按行号找），都是方法搬进 `CaretResolver`
之后留下的原文；另有 2 处注释被粘在声明行尾（`redoAndRender();` 在 541 行、
`caretRectPx() const;` 在 1025 行）。这不是排版问题：读这 160 行会得到"`flowForRel`、`textSpanAt`、`hintFromCrossSegment`
都是引擎的私有方法"这个错误结论，而它们其实在 `caret.h`。`caret.h` 205 行起还留着一组成员声明顶格写在类中间（同样是搬代码留下的）。

## 三、更好的形状：四条结构性改法

### P1 把派生量收成一份不可变快照

```cpp
struct CompiledDocument {                 // 一次编译的完整产物，构造完只读
    std::vector<BlockSpec> blocks;        // objects 是未筛的原件
    std::vector<FlowPos> block_lo;        // 编译时按同一遍历记下的流起点
    std::vector<int> block_len;
    std::vector<BlockSource> src;
    std::vector<LayoutTable> tables;
    ControlSet controls;
    ...
};
std::shared_ptr<const CompiledDocument> doc_;   // 重建 = 造一个新的再换指针
```

- 一次替换 `blocks_ / blocks_full_ / tables_ / flow_ / block_flow_ / block_flow_span_ /
  block_src_ / controls_ / control_node_ids_ / owner_index_` 十个成员；
- `refreshViews()` 的五处调用退化成"把指针交给视图"，`std::optional` 取地址的坑与
  "重建之后要再摆一次视图"这条纪律一起消失；
- `blocks_` 与 `blocks_full_` 合并成"一份文本 + 一份按名单筛出来的对象视图"，
  每次按键的整份深拷贝消失（engine.cpp:377）；
- `block_lo/len` 由编译在遍历时直接给出（见 2.2），删掉那两处 `max` 与整段递推。

改法与现有分层完全兼容：`PositionView` / `EditView` 的字段一个不减，只是从"指向十个成员的地址"
变成"指向一个快照"。

### P2 让事务带一份"损伤报告"

```cpp
struct Damage {
    int block_lo = 0, block_hi = 0;   // 受影响的块区间（含端点）
    int para_delta = 0;               // 段数变化
    bool touched_table = false;
    FlowPos flow_lo = 0, flow_hi = 0; // 流区间（位置映射与光标复位用）
};
```

- `applyStep` 在改树的那一刻就知道插/删了哪些节点（`InsertParaMark` 加一个 `NodeId created`
  即可），事务把每步的损伤并起来；
- 引擎不再需要 `ParaDelta`、不再需要往回扫新标记、不需要 13 个 reject 码；
- **逆步骤天然带着同一份损伤**，于是 `undo()` 可以只重建那几块、只重排那几段 —— 撤销从
  "整篇"变成"与刚才那一下同价"；
- 表格的"一律不做增量"可以收紧成"只有 `touched_table` 时退回全量"，而不是看文档里有没有表。

### P3 把续排状态补全，而不是给表格开后门

现在 `ReflowState` 只有三个标量（layout.h:689），于是表格的"第几行第几格第几页"续不上，
两条判据直接短路（engine_layout.cpp:339-342）。补成闭合记录：

```cpp
struct ReflowState {
    int page; float cursor_y; int line_total;
    TableCursor table;   // {index, row, cell, page, y}；不在表里时为 none
    WritingMode wm;      // 竖排的列状态
};
```

"从第 k 段续排 == 整篇重排"就成了对任意文档都成立的性质，`auditLayout` 也才真正覆盖表格。
在那之前，`can_resume` 里的每个 `&&` 都是一条"这条路我不敢走"的注释。

### P4（更远，方向先定）对外坐标该是流位置，"段 + 偏移"只是一个视图

引擎内部早就是 `Range{anchor, focus}` 的流位置了，但对外仍然是 `(段, 码点偏移)`。这个坐标表达不了
引擎自己知道的三件事，于是它们被拆成四个出参挂在命中测试上：

```cpp
bool hitTestPt(float x, float y, TextPos* out, int* owner, int* side, int* line_aff, int* cell_para);
```

一个坐标需要四个附加字段才无歧义，说明它不是坐标，是一个有损投影。宿主拿到这五样之后又要
原样送回 `setCaretAtSideLine` / `selectCellAtPara`，一来一回就是 1.2 与 1.3 那两节的
"重建"来源之一。改成对外只认 `FlowPos`（加行别），`(段, 偏移, 侧别)` 降级为探针与面板用的
只读视图，命中测试就只剩一个返回值。blast radius 大（两宿主 + 全部探针），所以放在最后做，
但方向要现在定下来：**新增接口一律收 `FlowPos`，不再加 `(para, offset, side)` 三件套**。

## 四、四条可以并行做的（P5-P7 是清理，P8 是接缝）

### P5 选区收成一条记录

```cpp
struct Selection {
    enum class Kind { Text, Cell } kind = Kind::Text;
    Range text;                        // 用户落下的两端（原 rawSelection）
    std::vector<CellBlocks> cells;     // 整格时才有
    FlowPos caret = -1;                // 整格时的插入点
};
```

流包络、掩码、焦点格末尾全部现算（或作为私有缓存，只有一个写入口）。三个谓词塌成一个 `kind`。
这一条消掉"反向拖选长不回来"与"空格选不中"背后的状态机，因为那类缺陷的根都是
"改 A 忘了清 B"。

### P6 呈现改用版本号，不用八本账

```cpp
uint64_t content_ver;   // 每次 relayout 自增（或按页的版本）
uint64_t overlay_ver;   // 光标/选区/标记变化自增
uint64_t window_ver;    // 窗口或槽数变化自增
```

底图第 p 页有效 ⟺ `base_page_ver[p] == content_ver`；帧需要重组 ⟺ `overlay_ver` 变了。
指纹只留"页内哪几行"这一级。同时把 `presentInternal` 拆成
`reconcilePages` / `reconcileBands` / `paintOverlays` / `accountBlit` 四段 —— 742 行不是问题，
问题是四套失效规则挤在一个函数里，改一条必须读懂另外三条。

### P7 宿主门面从"一张表"生成（合并之后只剩一半）

目标不变：把每个能力的 `{名字, 读/写/视口, 是否自呈现, 参数, 返回}` 写成一张声明表，
宿主门面的 `CMD`/`ASK`、worker 的 op 表、`PRESENT_ALWAYS` 全部由它生成；
再加一条判据：wasm 导出的每个函数名都必须出现在表里（漏一个当场红）。

2026-10-19 的合并已经做掉了这条的 JS 那一半 —— 命令表、输入层、缩放、`PRESENT_ALWAYS`
各只有一份，新增引擎能力只动一处。**剩下的是 C++ 侧与几处常量**：

- wasm 导出与命令表没有对上号的判据；漏一个症状是"某条命令只在 worker 宿主上静默不生效"；
- `maxWindowPages` 两份（`engine_api.js:165` / `app.js:399`），公式逐字相同，只差读数方式；
- A4 常量两份、`kZoomBase` 两份（`engine_api.js` 的常量与 `host_core` 的默认值），
  `app.js` 调 `createZoom` 时把 4/3 又写了一遍；
- 槽数三处（引擎 `frame_slot_count_`、`syncFrameSlots`、`slotCanvases.length`）。

最小改法：`maxWindowPages` 收成一个接受"页面度量从哪读"的函数（两处差别只有这个），
其余几项进一个 `web/geometry.js`，槽数只保留"宿主建了几个、随 pageCanvas 报给引擎"一个来源。

顺带把 wasm 门面的 JSON 收敛成一层：`wasm_main.cpp` 里 104 处字段名靠字面量拼进 JSON
（`controlsJson` / `linesJson` / `selectionReport` / `hitTest` …），每个入口各拼一次、
各转义一次，协议没有一处集中的定义。用一个小的 DTO + 一个 JSON 写出器，
协议就只有一处定义 —— 这也是 P6 那张表能成立的前提。

### P8 补上产品接缝（不是复杂度问题，是能不能用）

- `serializeDocument` / `deserializeDocument` 只在 `tests/model_test.cpp` 里被调用，wasm 一次也没导出；
- `ControlApi`（取值/设值/批量/属性）只被 `validation.cpp` 与测试使用，**没有引擎出口** ——
  设 1000 个字段之后不会重编译、不会重排、不会上屏；
- 引擎没有"新增控件"的入口（`addControl` 不存在），于是改字段名单只能整棵树重建
  （`setFormControls` → `syncBlocksFromEngine` → `demoTree`）；
- `demoTree` 只还原控件记录的 key / controlType / readonly 三项（demo_documents.cpp:306-308），
  `required`、`structureLock`、属性值、`styleRef`、字符格式的 language 与回退链都不在转换里
  —— **改一次字段名单，这些静默回到默认值**。

对一个表单编辑器，这四项合起来意味着：文档存不下来、字段建不出来、值回填不上去。
它比前面所有复杂度问题都更该先做。

## 五、明确不要动的

1. 编译只读树、产物快照、`BlockSource` 单向换算 —— 这是"单向"的骨架。
2. `auditFrame` / `auditBase` / `auditLayout` / `auditGlyphPages` / `auditCompile` 五条自审。
   它们是增量系统的判据，不是补丁；但要注意 P3 之前 `auditLayout` 对表格是盲的。
3. 两个宿主仍并存，但**引擎访问面与输入层已经只有一份**（2026-10-19 合并：`engine_api.js`
   与 `host_core.js`）。`app.js` 剩下的价值是"同步宿主"这个对照物 —— 调用即生效、随后能
   同步读值，探针的同步假设靠它站住。再往下合只剩画布与窗口所有权那一层，那是产品决策
   （见 `docs/一个引擎API与两种传输.md` 第 5、7 节），不是清理。
4. `CaretResolver` / `EditCommand` 的边界划法（只吃视图、不持引擎）—— 方向是对的，
   剩下的问题是视图要手工摆（P1 解决）。

## 六、建议顺序

1. **P8 的最小三件**：导出 save/load、`ControlApi` 接一个 `EditHost` 出口、加 `addControl`。
   做完之后 `g_blocks` 与 `syncBlocksFromEngine` 可以整段删除，重建文档这条路不再需要。
2. **P2**：事务带损伤报告。它同时消掉 `ParaDelta`、13 个 reject、撤销的整篇重排 —— 收益最大。
3. **P1**：快照化。在 P2 之后做，因为快照的形状由"损伤报告要重建哪几块"决定。
4. **P5 / P6 / P7**：三件互不依赖的清理，可并行（P7 的 JS 那一半已随宿主合并落地，
   只剩 C++ 侧与几处常量）。
5. **P3**：表格续排。等前面稳定了再做，它是纯算法收益，没有正确性前置。

每步的验收沿用现有纪律：先有判据再改，判据必须含反向一半；增量路径的判据一律"与全量逐字段一致"
（`auditCompile` / `auditLayout` 已经是这个形状），新增的损伤报告要能被注入错误（把 `block_hi` 减一）
并当场红。

## 七、没有量的（留给下一轮）

- `Node` 仍是所有种类载荷的并集（10-13 实测 1496 字节），本轮没有重新测量；它影响内存与缓存局部性，
  不影响正确性，优先级低于上面七条。
- `undo` 的实际耗时、`rebuild_copy_ms` 的实际占比只有字段没有采样 —— 建议在 P2 之前先量一次，
  给"撤销有多慢"一个数。
- 两宿主的窗口/几何逻辑是否等价，仍然没有判据 —— 合并之后 `engine_api.js` 与 `app.js`
  各留一份窗口计算（公式相同、读数方式不同），一个 `api.read` 写错就静默错位。
  补一条跨宿主对照探针（同一份脚本跑两个宿主，比 `geom` 与窗口区间）成本很低。
