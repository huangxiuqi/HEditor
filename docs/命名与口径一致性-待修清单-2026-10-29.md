# 命名与口径一致性：待修清单（2026-10-29）

这份清单是一次 C++ 侧与 TS 侧对照审查的产出，只收两类问题：同一概念有多份实现、
同一件事在两侧叫不同名字。行数与性能不在范围内。

与 `重构收口方案-单实现-2026-10-28.md` 的关系：那份方案已落地 T0–T4、T6、T7，T8 于
2026-10-29 落地，只剩 T5（部分完成）。本清单是它「同一概念多份记录」的剩余面（控件、
像素单位、纸张、配置命名），**不改动 T5 的结论与顺序**，编号用 N 前缀避免冲突。

每条的判据都要求一正一反：反向是把两份实现中的一份改坏，对应判据必须变红。
只有正向判据的修复不算完成 —— 那证明的是「新的能用」，不是「旧的已经不在」。

**总原则：不做兼容（2026-10-29 确定）。** 仓库里没有需要读的旧文档，落盘格式可以直接改；
公共面 `PUBLIC_MEMBERS` 的使用者只有 `web/app` 与判据，没有外部调用方，别名可以删。
因此本清单里凡是可以走「加迁移函数 / 留旧字段 / 保旧别名 / 加版本号」的地方，一律不采用，
按「删干净 + 改调用点」处理。

**本清单做下来没有任何一处需要 rebaseline**：N5 删掉规格名之后文档内容哈希确实变了，但全仓
没有判据钉住它的绝对值 —— `edit_test` 里那几个常数是 `LayoutDigest`（行盒、字形坐标、页数），
与内容哈希无关。

### N1 `selection().rects` 的单位与注释相反，判据看不见（**已完成**）

**现状**

- C++ `selectionReport()`（`wasm_main.cpp:871`）取 `selectionRectsVisible()`，输出字段名是
  `r_pt`，单位磅。
- `editor.ts:687` 取 `devicePixelRatio`，`:692-694` 把每个矩形的 `x/y/w/h` 除以 dpr 之后
  交给公共面。
- `web/tests/specs/table.spec.ts:8` 的头注释断言「`selection().rects` 是磅」。
- 判据跑在 `deviceScaleFactor: 1`（`tests/support/config.ts:74`），除法是恒等，所以这条
  错在 129 条用例里一次都看不见。

除以 dpr 之后的量既不是磅，也不是 CSS 像素（磅到 CSS 像素要乘 density/dpr，缺 4/3）。
同一条公共面上 `caret().rect` 来自 `caretRectPx`（磅乘 density，**不除 dpr**），
两个字段两种单位，`types.ts` 里 `Caret.rect`、`Selection.rects`、`Rect` 都没标单位。

**实际做法（与初稿不同）**

没有统一到 CSS 像素，改为让 `rects` 回到磅：引擎给的本来就是磅，透传即可，判断依据是
「两种单位回答的不是同一个问题」—— 选区矩形是被选中的版面区域，光标矩形是位图上光标条的
位置（后者带"至少一个设备像素"这个光栅约束，换成磅就丢了它）。

- `editor.ts` 的 `selectionOf` 去掉 `/ dpr`，注释写明"引擎给的是磅，直接透传"。
- `types.ts`：`Rect` 的类型注释改为"单位由持有它的字段决定"，`Caret.rect` 标设备像素，
  `Selection.rects` 标磅。

**判据（`edit-selection.spec.ts`，新分节「DPR=2：选区矩形的单位不随屏幕变」）**

- 正向：`test.use({ deviceScaleFactor: 2 })`，`caret().rect.h` 必须等于
  `rects[0].h × density`（容差 1 像素，因为 `caretRectPx` 是 ceil 且保底 1 像素）。
  实测 `caret.h=47`、`rects.h=17.38`、`density=2.667`。
- 反向：把 `selectionOf` 改回除 dpr，实测报 `caret.h=47，rects.h×密度=23.18`，判据红。
- 另一条附带结论：探针的 `SEL()` 读的是 `diag.selectionRaw()`（引擎原样），**绕开了公共面
  那次折算** —— 所以既有判据从来没覆盖到这条路径，新判据只能用 `H.selection()`。

**代价**：`web/src/editor.ts` 一处、`types.ts` 三处注释、`edit-selection.spec.ts` 新增一节。

### N2 `Selection.cells` 是恒 null 的契约（**已完成**）

**现状**

`types.ts` 声明 `cells: { rows, cols } | null`，注释写「单元格选区时给出格区间」。
全仓只有 `editor.ts` 的 `selectionOf` 一处赋值，写死 `cells: null`。引擎侧数据是齐的
（`syncCellSelection`、`cellFlowRangeAt`、`TableState` 里都有格区间）。

这是一条恒为空的分支：调用方按类型写 `if (sel.cells)` 永远不会进。

**实际做法**

接上，值取整格选区的原值而不是从块区间反算：

- `CellRange` 在 `CaretResolver::setCellRange` 里存下来（`cell_range_`，随 `clearCellRange`
  复位），新增 `cellRange()` 读数，`EditorEngine` 转发一层。这是「用户选了什么」的唯一原值，
  块区间与流包络都是它的投影。
- `selectionReport` 增加 `cells`（表、行列范围、焦点格），文字选区写 null。
  `gen_payloads.py` 的 `KIND_OVERRIDES` 补一条：这个键的第三支写出的是字符串 `null`，
  按默认规则会被判成 num。
- `types.ts` 的 `Selection.cells` 改为 `{ table, rows, cols, focus }`；`editor.ts` 原样转发。

**判据（`table.spec.ts`「整格拖选：插入点钉在焦点那一格的末尾」）**

- 正向：2x2 拖选之后 `H.selection().cells` 的 rows / cols 各是 `[0,1]`，跨度与
  `tableState().selRows` / `selCols` 相同；`focus` 与 `tableState().cellRow` / `cellCol`
  （光标所在格）逐字段相同 —— 两条读数各自算，互为交叉验证。
- 反向：`H.select()` 造一个文字选区，`cells` 必须为 null。

### N3 磅 → 像素的换算在 C++ 有两份，保底规则不同（**已完成**）

**现状**

| 位置 | 取整 | 宽高保底 |
| --- | --- | --- |
| `engine.cpp:1000 caretRectPx` | `floor(x)` / `ceil(w)` | `max(1.0f, …)` |
| `engine.cpp:1043 selectionRectsPxIn` | 同上 | `w<=0\|\|h<=0` 丢弃 |

同一句「乘 `cfg_.zoom`」，一处保证「至少画得出一个像素」，另一处保证「画不出就不画」。
后者丢掉空行插入点是刻意的（注释说明了），前者保底 1 像素也是刻意的 ——
但两条规则写在两个函数里，谁都没引用谁。

**做法**

抽一个 `Rect ptToPx(const Rect&, float density, bool keep_min_px)`，两个调用点各传一个
布尔。`keep_min_px=false` 时返回 bool 表示「可画」。不要抽成两个函数（那只是把两份搬到
一起），也不要抽成一个不带参数的函数（保底语义确实不同）。

**判据**

- 正向：空行（只有段落标记）上 `caretRectPx` 宽高为 1，`selectionRectsPx` 为空数组，
  两者都不变。
- 反向：把 `ptToPx` 的 `keep_min_px` 在 `caretRectPx` 处传 false，`view` 域
  「0.8 倍压到单倍的八成」必须红。

**实际做法**

- 抽出 `ptToPx(const Rect&, float density, bool keep_min_px, Rect* out)`，放进 `engine.cpp`
  的匿名命名空间；两个调用点各传自己的保底语义（光标 true、选区 false）。
- 顺带删掉 `EditorEngine::ptToPx(float)`：它与新函数同名且零调用。留着会让成员名遮蔽自由
  函数 —— 成员函数体里不加限定就调不到新的那份，编译报「参数个数不符」。
- 像素那两条没有独立判据：`caretRectPx` / `selectionRectsPx` 都在 private 区，native 判据
  够不着，wasm 侧也没有逐次查询入口（光标像素随 editStats 一起回）。它们由
  `edit-selection` 的 DPR=2 用例间接钉住（`caret().rect.h == ceil(rects[0].h × density)`）。
  「宽高保底一个像素」这一半没有判据，只由 `view` 域的行距用例间接覆盖 —— 这是本节留下的
  缺口，要补得先把像素面开到判据够得着的地方。

**代价**：`engine.cpp` 净 −8 行，`engine.h` −6 行（删死成员）。

### N4 「最内层控件」有三份实现、两套裁决（**已完成**）

**现状**

| 实现 | 位置 | 输入 | 裁决规则 |
| --- | --- | --- | --- |
| `ControlSet::innermostAt` | `control.cpp:102` | `TextPos` | 比 `depth`，同深度取**下标小者** |
| `innermostControlAtFlow` | `control_spans.h:80` | `FlowPos` | 起点最大者，同起点取**跨度短者** |
| `ControlIndex::innermost` | `control_spans.h:222` | `FlowPos` | 注释声明「规则与 innermostControlAtFlow 相同」 |

三处注释互相指认对方为权威：`control.h:158` 说「查询的口径统一走 innermostAt」，
`control_spans.h:222` 说「规则与 innermostControlAtFlow 相同」。`caret.cpp:147` 用
`include_end=true`，`engine.cpp:1695`（`controlAtPt`）用 `false` —— 同一个函数两个口径，
差别在「空控件的两个括号之间算不算在控件里」。

T5 已完成的那一半是「位置入口收成一处」，没收的是这三份查询。

**做法**

1. `ControlIndex::innermost` 成为唯一实现，`ControlSet::innermostAt` 改成
   「TextPos → flow（走 `flowPosAtSide` 的唯一换算）→ 查索引」，不再自己遍历区间树。
2. `include_end` 显式化：改名两个入口 `innermostContentAt` / `innermostInsertAt`，
   把「空控件算不算命中」写到名字上，而不是靠一个布尔默认值。
3. `innermostControlAtFlow`（线性版）只保留给「索引未建」的路径，并在注释里写明它只在
   `ControlIndex::empty()` 时被调用（`edit_command.cpp:309` 已经是这个用法）。

**判据**

- 正向：嵌套控件（外层可编辑、内层只读）里敲字与点选，归属与 `focusedControlIndex()`
  逐项相同；空控件两侧的落点归属与改前相同。
- 反向：把 `ControlIndex` 的排序里 `content_hi` 降序改成升序，嵌套三层的归属用例必须红；
  改前先确认它现在为绿，否则这条反向臂无效。
- 反向：把 `controlAtPt` 的 `include_end=false` 改成 `true`，「点在空控件括号内侧」用例必须红。

**实际做法（上面第 1 条不做，理由见下）**

第 1 条按代码事实不成立：`ControlSet` 是文字位置面（段号 + 段内码点偏移），`ControlIndex`
是流位置面，方向不可逆 —— `caret.cpp` 的 `defaultSideAt` 注释已经写明理由（同一个文字偏移
上压着好几个插入点，「这个偏移归谁」正是要先回答的问题；拿流位置反推会跳过字段边界）。
两份坐标面都保留，收敛的是裁决规则的描述与调用点的名字。

- `include_end` 显式化：`ControlSet::innermostAt(pos, bool)` 拆成 `innermostContentAt` 与
  `innermostInsertAt` 两个入口，共用的实现转私有。两个生产调用点按语义各选一个
  （`caret.cpp` 要插入面、`controlAtPt` 要内容面），判据 3 处跟着改名。
- 线性版与索引版的注释写清谁是索引路径、谁是索引未建（或建出来为空）时的路径。
- `control.h` 的类注释原来写「查询的口径统一走 innermostAt」，改成「两个入口 + 两份坐标面
  不能互相替代」。

**反向臂（实测，与清单给的那条不同）**

清单那条（把 `ControlIndex` 排序里 `content_hi` 降序改升序）无效：`content_lo` 严格递增
（每个控件的开括号各占一格），同起点不可能出现，那个排序键是死代码 —— 改了全量仍绿。
有效的是拆 parent 链：`e.parent = stack.back()` 改成 `-1` 之后 `edit_and_caret_2` 红 7 项
断言，恢复后绿。

**代价**：`control.h` / `control.cpp` 净 +12 行（两个入口 + 私有实现），调用点 5 处改名。

### N5 纸张规格两套模型，其中一套零调用（**已完成**）

**现状**

| | TS | C++ |
| --- | --- | --- |
| 枚举 | `PaperSize` 8 项，含 **A3**（`types.ts:178`） | `PaperName` 6 项，**无 A3**（`section_spec.h:28`） |
| 尺寸表 | `PAPER_PT`（磅，`types.ts:184`） | `builtinSizePt`（磅，`section_spec.cpp:15`，已与 TS 同值） |
| 派生 | `paperSizePt()` 横排对调 | `paperSize()` 横排对调（零调用） |

`paperSize()` 全仓**零调用点**。`section_spec.h:25` 与 `:68` 写「尺寸由名称与方向推出来
（见 paperSize）」，而 `wasm_main.cpp:344` 的 `setPageMetrics` 注释写「纸张规格不在这里认，
抄进引擎就是第二个真相」—— 两份注释互相否定。

通道现状：TS 的 `page.paper` 只影响它自己算出的宽高；`pageSetup` 命令只发 4 个数
（`api.ts:1257`），不发规格名；文档落盘却要写 `SectionSpec.paper.name`
（`record_json.cpp:898`），于是永远写默认 A4。选 A3 能画出 A3 的页，规格存不下来。

**做法（A：引擎只认宽高，规格不进文档）**

**前提：不做兼容。仓库里没有需要读的旧文档，旧 JSON 里的 `name` 键直接忽略。**

`paperSize()` 是唯一一条"按名字算尺寸"的路径，且零调用。整条删掉：

- 删 `Paper` 的 `name` 字段、`PaperName` 枚举、`paperNameName` / `paperNameFromName`、
  `builtinSizeMm`、`paperSize()`、`PaperSizeEmu`。
- 写入端（`record_json.cpp:896-903`）不再写 `name`，只写 `w` / `h` / `orient`。
- 读取端（`record_json.cpp:996`）删掉 `readEnum(p, "name", …)` 那一行。字段不认识就不读，
  不需要迁移函数，也不需要 `legacyPaperSizeMm`。
- `Paper` 的默认值必须换成绝对长度，否则删了 `name` 之后默认节没有页宽页高。
  **纸表已经按磅给了（见下面「已统一」一节），所以这里直接写
  `Length::abs(ptToEmu(595.276))` / `Length::abs(ptToEmu(841.89))`**，与纸表同一串字面量，
  不要再出现毫米制的 7,560,000。
- `section_spec.h:25` 与 `:68` 的注释要改（现在写「尺寸由名称与方向推出来」，改成反的）。
- `document.cpp:155-166 hashSectionSpec` 去掉 `sec.paper.name` 那一项。

**已统一（2026-10-29 先做掉了这一步）**

纸表原来按毫米存（A4 = 210×297mm），而 `PageMetrics`（`layout.h:92`）与宿主那侧都按磅。
换算回 EMU 两边差 5 个（7,560,000 对 7,560,005），量级是 0.0004 磅 —— 看不出来，
只会在某一行刚好压线时让分页多出一行。

现在 `section_spec.cpp` 的 `builtinSizePt` 直接按磅给，六种纸的数值与 `PAPER_PT`
逐位相同（A4 595.276×841.89、A5 419.528×595.276、B5 498.898×708.661、Letter 612×792、
Legal 612×1008），`paperSize()` 用 `ptToEmu` 换算。三处（本表、`PageMetrics` 默认值、
宿主规格表）因此是同一串字面量。

钉住它的判据在 `doc_test.cpp` 的 [26] 节：`paperSize(Paper{})` 与
`ptToEmu(PageMetrics::A4().width_pt)` 逐值相等。反向是把纸表的 A4 改回 `210.0`（毫米口径），
实测报 `7559999 / 10692003`，断言变红。

所以 N5 落地时不必再处理这处差异，也不再需要"将来接桥前先统一"这个待办。

**A2 可选：`Paper` 改名 `PageSize`**

删完之后结构体只剩宽高与方向，改名是可读性收益，可以不做。

TS 侧不动：`PAPER_PT` / `paperSizePt()` 保留为唯一的规格表。删完之后 C++ 侧不再有任何东西
跟它们抢，TS 的 `PaperSize` 想加 A3 之外多少种都只影响它自己算出来的宽高。

**判据**

- 正向：选 A3（C++ 枚举里不存在）设页面 → 保存 → 重开，页宽高与保存前逐磅相同。
  这条用例本身就是"规格名不进文档"的正面证据。
- 正向：新建文档（默认节）的页宽高是 A4，且 `serialize` 出来的 JSON 里没有 `section` 段
  （全默认不写，这条保证默认值真的等于 A4，而不是"写了一份 A4 出去"）。
- 正向：设成 A3 之后，JSON 的 `section.paper` 里只有 `w` / `h`，**没有** `name` 键。
- 反向：把写入端恢复成写 `name`，上一条「`section.paper` 里没有 name 键」必须红。
- 反向：把 `Paper` 的默认宽高改回零，默认文档的分页页数必须变（零宽页装不下一行）。

**代价**：净删约 120 行（`section_spec.h` / `.cpp` / `record_json.cpp` / `document.cpp`），
外加两处哈希常数 rebaseline。

**必须声明的 rebaseline**：`hashSectionSpec` 少了一个字节，所有文档的内容哈希都会变，
`edit_test.cpp:8470`（`0x65cf7bda39ea3a62`）与 `:8548`（`0x088f6c06542fa222`）两个常数要改。
这不是布局结果变了，是哈希的输入集合变了 —— 提交说明里要写清这一句，否则下一个读到
这两个数字的人会以为排版行为被改动了。不要用「留一个常量字节占位」的办法保住旧哈希，
那是给删除留后门。若 `doc_test` 另有整份 JSON 快照，一并 rebaseline。

**实际做法**

一次删完，没有迁移函数、没有版本号：

- `section_spec.h`：删 `PaperName`、`paperNameName`、`paperNameFromName`、`Paper.name`、
  `PaperSizeEmu`、`paperSize()`；`Paper` 只剩 `orient` / `width` / `height`，默认值
  `Length::abs(ptToEmu(595.276))` / `Length::abs(ptToEmu(841.89))`（与 `PageMetrics::A4`
  同一串字面量）。文件头与结构体注释改成「只存宽高与方向，规格名是宿主的概念」。
- `section_spec.cpp`：删匿名命名空间里的纸表（`PtSize` / `builtinSizePt`）、两个名称互转
  函数、`paperSize()`。文件里不再有毫米或磅的纸表。
- `record_json.cpp`：写端不再写 `"name"`，读端删掉 `readEnum(p, "name", …)`；旧 JSON 里
  的 `name` 键落在白名单之外，自然被忽略。
- `document.cpp`：`hashSectionSpec` 少了一个 `u8`。

**判据（实测）**

`doc_test` 的 [26] 节：默认节的宽高与 `PageMetrics::A4` 同源；全默认的节不写 `paper` 段；
A3 宽高落盘之后 `section.paper` 里只有 `w` / `h`、没有 `name`；序列化再读回逐磅相同。

**清单原来那条 rebaseline 不成立**：`edit_test` 里 `0x65cf7bda39ea3a62` /

### N8 「光标有没有移动」两处判据（**已完成**）

**现状**

| 位置 | 判据 | 用途 |
| --- | --- | --- |
| `dom.ts:652`（旧） | para:offset:side:lineAff:page:visible（六项） | 决定发不发 `caret` 事件 |
| `dom.ts:705`（旧） | para / offset / page（三项） | 决定滚不滚视口 |

同一文件两种判据。三项那一处缺 `side` 与 `lineAff`：软换行处从「上一行行尾」跳到
「下一行行首」时位置三元组完全相同，视口不滚。清单原判断是「这里缺两项」；实测下来
软换行处的 `caretLineAff` 确实会在 0 与 1 之间变、而几何（`caret().rect.y`）不变 ——
差别只在「宿主知不知道落点换了」，不在「画面动不动」。

**实际做法**

拆成两个函数，字段表只有一份：

- `caretRelocated(a, b)`：段、偏移、侧别、行别、页（五项），回答「位置挪了没有」。
- `caretMoved(a, b)`：`caretRelocated` 或相位不同（六项），回答「身份换了没有」。

两处各取所需：`finish()` 用它决定发不发 `caret` 事件（相位翻转也要发）；`afterEdit()`
用它决定滚不滚视口（只要位移，相位翻转不该拽视口）。`finish` 的比较对象是
`lastCaretState`，`afterEdit` 的是 `lastState` —— 两者的「上一次」不是同一拍，
这一点写进了注释，否则后来人会以为是同一个变量。

清单原写的「滚动那一处再叠一层『是否同页同行』」按代码事实改成「叠一层：排除相位」。
同页同行不是判据：同一页同一行里的横向移动也要滚（横向不滚是 reveal 的事，不是前提）。

**判据（实测）**

- `[24]` 软换行处的两个插入点：`caretLineAff` 从 1 变 0、段号偏移页全相同，
  `caret` 事件必须发。反向实测：把 `caretLineAff` 从 `caretRelocated` 去掉，事件数 0，红。
- `[25]` 闪烁相位翻转：光标放在末段、视口滚回顶部，等一次 530 ms 翻转 ——
  事件要发、`scrollTop` 不许动。反向实测：把相位项从 `caretMoved` 去掉，事件数 0，红。
- 两条都在 `edit-selection.spec.ts`。`[24]` 的落点用 `setCaret(pos, {side, line})`：
  行别只在给了侧别时才下发，无侧别的分支是 plain 落点，不看行别 —— 清单没提这一点，
  第一版判据就是因为只传 `line` 而拿到两个相同的插入点。

**代价**：`dom.ts` 净 +26 行（两个函数加注释），删掉一个字符串键的拼装。

### N9 换行有两种语义：粘贴断段，插入当码点（**已完成**）

**现状**

TS 侧 `editor.ts:773` 的 `paragraphs()` 是
`String(link.read('textAll')).split('\n')` —— 段数由 JS 数分隔符得出，不是引擎给的。
它依赖两个前提：`documentTextAll`（`wasm_main.cpp:2179`）用 `\n` 连接块，
且**块文本里永远不含 U+000A**。

第二个前提没有任何东西保证，因为换行在引擎里有两条不同的路：

| 路径 | 遇到 `\n` 怎么做 |
| --- | --- |
| `pastePlainText`（`engine.cpp:396-414`） | 换成 `NodeKind::ParagraphMark`，**断段** |
| `insertCodepoints`（`edit_command.cpp:233-295`） | 原样进 `InsertText` 步骤，**当普通码点** |

`insertCodepoints` 全程没有 0x0A / 0x0D 的判断，`filterTypedText` 只按控件类型过滤数字与
日期。于是 `insertText(0, 0, "甲\n乙")` 或 `type("甲\n乙")`（两条都是公开 API）会让块 0
的文本变成 `甲\n乙`。

后果是一个文档两个段数：

```
引擎 blocks().size() == 1
paragraph(0)        == "甲\n乙"
paragraphs()        == ["甲", "乙"]   // 2 项
paragraphs().length == 2              // 与块数不符
```

`paragraph(i)` 走 `documentText(i)`（按块号取），`paragraphs()[i]` 走 split —— 两条公开
方法对同一份文档给出不同的段号空间。这是 N9 的实质，与"分隔符选得好不好"无关。

`loadTextDocument`（`wasm_main.cpp:1826-1830`）自己也按 `\n` 拆段，所以测试文档那条路
是安全的。风险只在 `insertText` / `type` 这两条吃字符串的入口。

**做法（统一到"换行即断段"，一份实现三处共用）**

不要在 `insertCodepoints` 里做——它是"在一段内插码点"的底层，中途断段会让一次提交变成
多次，撤销栈跟着变。改在 `EditorEngine` 这一层分派：

1. 抽 `nodesFromPlainText(const std::string&, std::vector<NodeSpec>*)`，
   就是现在 `pastePlainText` 里那段（含 CRLF 合并、空行保留）。`pastePlainText` 改成调它。
2. `insertTextUtf8` / `typeTextUtf8` 检测到 `\n` / `\r` 时走同一条：构造
   `TextRun + ParagraphMark + TextRun` 一次 `pasteNodes`，落点用最后一段的末尾。
   一次事务，仍然一步撤销。
3. 不含换行时走原来的 `insertCodepoints`，路径不变、性能不变。

顺带把「块文本不含 U+000A」变成可证伪的契约：`documentTextAll` 拼装时若某块文本含 `\n`
直接返回空串并记一条 `blocked_edits`（与"拒绝时文档不动"同一口径），而不是把歧义拼进去。

**判据**

- 正向：`type("甲\n乙")` 之后块数为 2、`paragraph(0) == "甲"`、
  `paragraph(1) == "乙"`、`paragraphs().length` 与块数相同；一次撤销回到 1 段。
- 正向（回归）：`paste()` 走片段路、`pasteText()` 走纯文本路，两者对同一段含换行文本
  产出相同的块数与段落文本。
- 反向：把 `nodesFromPlainText` 的 `ParagraphMark` 分支去掉（`flush()` 后不 push 标记），
  上面正向用例必须红 —— 此时 `paragraphs()` 仍会报 2 而块数是 1，两条断言同时失败。
- 反向：把 `documentTextAll` 的换行检查去掉并让某块含 `\n`，新加的契约断言必须红。

**代价**：`engine.cpp` 净删约 20 行（`pastePlainText` 的循环搬进共用函数），
`edit_command.cpp` 加一个分派；三处调用点。**改 `documentTextAll` 不改载荷**，
所以三份生成产物不用重生成。

**为什么不改载荷**：把 `documentTextAll` 改成返回数组只是让 JS 不再猜分隔符，
引擎里"换行有时断段、有时是码点"这个矛盾还在 —— 用户敲一个含换行的字符串，
`paragraph(0)` 依然会返回带换行的文本。改载荷治的是症状。

**实际做法**

- `nodesFromPlainText` 放在 `core/doc/subtree.h`（与 `makeEmptyTableSpec` 同一族：都不依赖
  引擎的纯值构造），`hasLineBreak` 与它同处。`pastePlainText` 改成一行调用。
- `EditCommand::insertTextUtf8` / `typeTextUtf8` 在含换行时分派：前者落点由参数给定，
  走新增的 `insertNodesAt`（不动选区 —— 程序化插入的坐标是按调用时的文档算的）；
  后者落点就是光标，走 `pasteNodes`（先删选区，与打字替换选中内容同口径）。
  落点正好是光标且有选区时，`insertTextUtf8` 也走 `pasteNodes`。
- `pasteNodes` 的下半段抽成 `insertNodesAtFlow(at, erase, before, nodes)`，两个入口共用。
- 换行不进段文本改成入口拒绝，而不是读的时候降级：`insertCodepoints` 见到
  U+000A / U+000D 整批拒绝并记一笔 blocked_edits。原先打算在 `documentTextAll` 里检测并
  返回空串 —— 那更糟：空串与「真空白文档」同形，宿主会把整篇当空的。不变量应该钉在入口，
  不在读的时候兜。

**判据（实测）**

- `edit_test` 新增 `[95]`：插入折成两段、前后段文本、一步撤销回一段、粘贴与打字同构、
  码点入口拒绝 U+000A 且文档不动。16 项断言。
- `clipboard.spec` 新增一条：`type('甲\n乙')` 之后 `paragraph(i)` 与 `paragraphs()[i]`
  说同一件事、一步撤销回一段、`insertText` 走同一条路。
- 反向臂两条，都实测会红：拆掉 `nodesFromPlainText` 的段落标记分支 → `[95]` 红 4 项，
  web 那条报 `["头甲乙"]`（正是修前的症状：换行被当普通码点）；去掉码点入口的换行拒绝
  → `[95]` 红 3 项。

**代价**：`engine.cpp` 净删约 30 行，`edit_command.cpp` 加两个分派与一个共用函数，
载荷没改（三份生成产物不用重生成）。

### N14 判据自带一份密度常量（**已完成**）

**现状**

`web/tests/support/edit-helpers.ts:11` 是 `export const ZOOM = 1.5;` —— 这是"密度"的第三个
副本，与实现里的 `createZoom` 无关，永远不会随实现变。

它只在一条路径上恰好成立：`LOAD.reset(6, ZOOM)` 把 1.5 当作密度**主动设进引擎**，所以走
`reset` 的那些 spec 对得上。而 `LOAD.form(0)`（`loadFormSample`）不设密度，引擎保持 boot
时的 1.333（`config.zoom=1 × 4/3 × dpr=1`），`edit-form` 里几处 `× 1.5` 的竖带窗口就整体
偏右 11%，括号一个都框不住。

实测（`edit-form` 的 `#0` 字段，控件左缘 132.93 磅、帧宽 794）：

| 系数 | 竖带 `[cx-10, cx-1]` | 命中亮蓝像素 |
| --- | --- | --- |
| 1.5 | `[184, 198]` | 0 |
| 1.333 | `[164, 176]` | 42 |

**做法**

`bandAt`、空字段的括号统计、"相邻字段共享边界"的窗口与扩容点击位置，四处都改成在页面内
读 `ZOOM()`（PRELUDE 里那个按 `config.zoom × 4/3 × dpr` 现算的函数）。

**判据**

- 正向：`edit-form` 全绿（1 passed）。
- 反向：把任一处改回 `1.5`，`#0 左缘` 立刻回到 0 px，那五条断言全红。

**为什么单独记一条**：这不是"实现有 bug"，是判据里又长出一份与实现无关的常量。它和
N6 / N7 是同一类问题（密度有多个副本），只是副本长在测试里 —— 生产代码改了，判据不会
跟着改，于是判据从"钉住行为"变成"钉住某个历史时刻的场地配置"。
