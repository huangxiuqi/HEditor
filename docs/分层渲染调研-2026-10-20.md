# 分层渲染调研（2026-10-20）

> 问题：为什么有的框架能开很多层却不怎么费资源？我们这套引擎（CPU Skia → wasm → RGBA 位图
> → 宿主 `putImageData`）该怎么分层？
>
> 结论先行：**层的开销不取决于"几层"，取决于每层占多少像素、多久重画一次。**
> 别人能有几十层，是因为那些层里绝大多数是**显示列表**或**稀疏 DOM**，不是几十张全幅位图。
> 一旦一层是一张整幅位图，它就按 `宽 × 高 × 4 × dpr²` 收费，跟里面画了多少东西无关。

---

## 一、四种层，四种成本

| 形态 | 层里存什么 | 成本 | 典型例子 |
| --- | --- | --- | --- |
| 全幅像素层 | 一块 `W × H` 的位图 | `W×H×4×dpr²` 字节，**与内容多少无关** | Chromium 合成层、一张 canvas |
| 稀疏像素层 | 只在有内容的地方有像素 | 有内容的面积 | 光标覆盖层、批注层 |
| 显示列表 | 绘制命令（矢量） | 每命令几十字节；重放成本 ∝ 命令数 | Flutter 的 `Layer`、Figma 的场景图 |
| 稀疏 DOM | 只在有内容的地方有节点 | 每节点一次 style/layout | pdf.js 的文字层、批注层 |

数量级对比：1920×1080 的一张全幅位图是 **8.3 MB**；同样"一层"如果只是 100 条绘制命令，
是 **4 KB** 量级。差两千倍。所以"几十层不费资源"的真正含义是"那几十层不是几十张全幅位图"。

## 二、几个案例（各自解决了什么）

### 2.1 pdf.js：一页一组，四种形态各司其职

每页固定叠四层：canvas（视觉内容）+ text layer（透明 span，只覆盖文字）+ annotation layer
（HTML 元素，只覆盖有批注的地方）+ XFA 层。层序由 `LAYERS_ORDER` 管。

关键点不是"层多"，而是**每层只在自己有内容的地方存在**：文字层是几千个 span，不是一张
794×1123 的位图；批注层只有几个元素。选择、复制、搜索、表单全部走 DOM，浏览器原生处理。

来源：<https://deepwiki.com/mozilla/pdf.js/1.1-three-layer-architecture>、
<https://blog.mozilla.org/attack-and-defense/2021/10/14/implementing-form-filling-and-accessibility-in-the-firefox-pdf-viewer/>

### 2.2 Excalidraw：两张叠放的 canvas，按"变化频率"切

静态层画所有图形，只在场景变更时重画；交互层画选中框、协作光标、吸附线，每帧重画。
两张 canvas 在 DOM 里上下叠放，静态层不参与每帧。另外每个元素还有自己的离屏 canvas 缓存
（`generateElementCanvas`），重复绘制时直接 `drawImage`。

这是最贴近我们的一张参考：**同一份内容里，按"多久变一次"切成两层**。

来源：<https://deepwiki.com/excalidraw/excalidraw/5-rendering-system>

### 2.3 tldraw 5.0：反向证据——层太多时并成一层

5.0 之前，选中框、控制柄这些瞬态 UI 是"每个一个 React SVG"；5.0 改成**全部画进一张
HTML canvas**（Overlays Utils）。官方说法是"渲染得更高效"。

方向很重要：它不是从一张 canvas 拆成很多层，而是从很多元素并成一张。**元素级分层是有上限的。**

来源：<https://tldraw.dev/blog/tldraw-sdk-5-0>

### 2.4 Flutter：层是显示列表，不是像素

`RepaintBoundary` 创建的是一个**独立的 display list**，不是一个像素缓冲。父子树重画时，
边界内的 display list 可以原样复用；子树重画时，边界外不用重录。

光栅缓存（raster cache）是**额外**的一步，而且官方明确说滥用会更差：父子总是一起重画时，
这个边界纯属浪费（`debugSymmetricPaintCount` 就是量这个的）。

所以 Flutter 的"很多层"便宜，是因为层里是命令；真要缓存像素，它自己也要算账。

来源：<https://api.flutter.dev/flutter/widgets/RepaintBoundary-class.html>、
<https://api.flutter.dev/flutter/rendering/RenderRepaintBoundary-class.html>

### 2.5 Figma：一张 canvas + 瓦片，成本 ∝ 屏幕像素

一个 canvas，自己实现渲染器，按 256px 瓦片缓存；平移只重贴缓存瓦片 + 画新进视口的条带；
缩放先复用旧瓦片再后台换清晰的。成本随"屏幕上有多少像素"走，不随"文档里有多少对象"走。

这是"单层 + 瓦片"的极端：**层数为 1，靠损伤粒度（瓦片）拿回增量。**

来源：<https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/>、
<https://kaelan.fyi/research/figma-architecture/>

### 2.6 PSPDFKit / Nutrient：把取舍做成开关

默认把批注**烘进页图**：省内存，但改一个批注要重画整页，选中批注还得先把它从页图里抠掉。
"overlay mode"把每个批注放进独立的 View：选中即时、更新快，但内存升高，官方建议只在
高端设备上全开。

这段最值得记：**同一家厂商，同一份内容，两种分层方式，按设备能力选。**没有绝对更优。

来源：<https://pspdfkit.com/guides/android/annotations/annotation-overlay-mode/>

### 2.7 Chromium：层的经济学

- 每个合成层背后是一张纹理，成本 `W×H×4×dpr²`；全屏层在 3× 手机上就是好几 MB。
- 层的默认策略是**合并**，只有"直接合成理由"（3D 变换、`will-change`、动画、canvas、
  重叠）才拆；重叠还会引发"层爆炸"，所以 Blink 有 layer squashing 把重叠的一批压成一张。
- Chrome DevTools 团队自己说过：**多个 canvas 比一个更大的 canvas 更贵**，哪怕那个
  canvas 更大。

来源：<https://www.chromium.org/developers/design-documents/gpu-accelerated-compositing-in-chrome/>、
<https://developer.chrome.com/blog/performance-insights>、
<https://sujeet.pro/articles/browser-runtime-internals/critical-rendering-path/crp-layerize>

### 2.8 putImageData 的账

`putImageData` 是 CPU → GPU 的上传，成本与**上传面积**成正比；脏矩形参数是 API 层唯一
可控的优化。`willReadFrequently` 会把背衬放到 CPU 内存，读变快、画变慢，是个取舍。

同一条约束也解释了为什么"层"能省钱：**省的不是层，是每次上传/重画的面积。**

来源：<https://stackoverflow.com/questions/3952856/why-is-putimagedata-so-slow>、
<https://bugs.webkit.org/show_bug.cgi?id=65207>

## 三、五条可迁移的规则

1. **同频同层**：变化频率相同的东西放一层，不同频的拆开。拆开的收益 = 高频那部分不再
   拖着低频那部分重画；代价 = 多一层的内存与合成。
2. **面积按内容分配**：能稀疏就稀疏。光标层只有光标那一块，不是一整页。
3. **能命令就命令**：装饰性、结构化的东西（选择、链接、批注锚点）优先 DOM/矢量，
   它们只在有内容处收费；像素留给真正贵的东西（字形、图片）。
4. **层必须活在滚动内容里**：层若固定在视口上，滚动时要么每帧重画，要么和内容错位。
   Excalidraw/pdf.js 的层都在滚动内容里，滚动是纯合成。
5. **层数要能被观测**：DevTools 的 Layers 面板、我们自己的 `EditStats`。没有计数就没有
   层爆炸的判据。

## 四、本引擎的现状（实测）

### 4.1 现在有几张全幅位图

- `base_`（窗口底图）+ `bitmap_`（帧）：两张窗口大小的位图。5 页窗口、测试页 893×1263，
  一张约 **22.5 MB**（893×1263×5×4），两张 45 MB。A4@96dpi（794×1123）一张 17.8 MB。
- 5A 之后每页还有一张 `PageBitmap`：一页 4.5 MB（893×1263），窗口内 5 页 22.5 MB。

### 4.2 一次光标移动，实际传了多少像素

宿主 `blitPage` 是**整页上传**（`putImageData(img, 0, 0)`，源是整页）：

```
光标右移一次 → dirtyPages = [光标所在页] → 上传 893 × 1263 = 1.13 Mpx
```

而光标本身只有 `2 × 20` 像素量级。**上传面积比必要面积大四个数量级。**
连页模式更重：`blitPageContinuous` 每拍把所有可见页重贴一遍（一屏五页约 1.1 ms）。

这是目前最大的一笔浪费，比"层不够多"严重得多。

### 4.3 覆盖层的擦除方式

`presentInternal` 里，光标/选区/表单标记画在帧上，擦除靠 `copyRectFrom(base_, r)` 从底图
拷回来；选区混色还要靠 `sel_paint` 保证"整块重铺再混一次"，否则光标每闪一次选区就深一层
（代码里那段注释写得很清楚）。这套机制能工作，但它把"瞬态"和"内容"绑在了同一张位图上：
瞬态一变，就得从内容位图往回拷。

## 五、三个方案

### A. 每页一张稀疏透明覆盖层

内容层与覆盖层各一张 canvas，覆盖层只给"当前有标记的页"分配（光标在 1 页、选区在几页）。

- 内存：每张有标记的页 +4.5 MB（dpr2 时 +18 MB），通常 1–3 页。
- 上传：矩形级，光标一次约 40 px。
- 滚动：两张 canvas 都在滚动内容里，纯合成、不重画。
- 判据：`selfCheck`（画布 == 引擎像素）要改成"内容层 + 覆盖层合成后再比"；
  浏览器合成的 alpha 取整与 Skia 可能差 1 LSB，像素判据要留容差。
- 风险：多一层 DOM/合成层；两层的对齐（分数 DPR、亚像素滚动）是新的错位来源。

### B. 单层 + 矩形合成（推荐）

一张页画布。引擎按矩形把"内容 + 瞬态"合成成最终像素，宿主按矩形上传。

- 内存：0 额外全幅位图（一份矩形大小的合成暂存）。
- 上传：矩形级，与 A 相同。
- 滚动：一张 canvas 在滚动内容里，天然跟随。
- 判据：`selfCheck` 语义不变（画布 == 引擎给的像素），像素逐字节一致，
  现有 365×2 条探针不用改判据形状。
- 代价：内容 canvas 会被光标"弄脏"，浏览器要为那一小块重新上传纹理。
  这点成本与 A 把像素传到覆盖层是同一量级。
- 风险：全页重贴（滚回来、改配置）时要把瞬态重新合成一遍，需要"呈现版本"或
  按需合成；这是实现细节，不是架构风险。

### C. DOM 覆盖层

光标是一个 div（CSS 闪烁），选区是 N 个 div，表单标记是边框。

- 内存：~0；闪烁零 JS、零光栅；滚动原生。
- 风险：几百个标记就要几百个节点；像素判据读不到 DOM，365×2 条里凡是对着画布找光标/
  选区的断言都要改成读 DOM 或截图；视觉要与 Skia 逐像素对齐（线宽、取整）。
- 适合：链接热区、批注、协作者光标这类"结构性、可交互"的装饰，不适合高频几何量大的东西。

| | A 稀疏覆盖层 | B 单层矩形合成 | C DOM 覆盖层 |
| --- | --- | --- | --- |
| 额外像素内存 | 1–3 页 | 0 | 0 |
| 一次光标移动上传 | ~40 px | ~40 px | 0 |
| 滚动 | 纯合成 | 纯合成 | 纯合成 |
| 像素判据 | 要改 selfCheck，容差 1 LSB | **不变** | 要改判据形状 |
| 内容层是否被弄脏 | 否 | 是（小块） | 否 |
| 实现改动 | 中（新位图 + 合成） | 中（矩形合成 + 呈现版本） | 大（判据面） |

## 六、建议

**逻辑分五层，物理只留一层（每页一张画布）。**

| 逻辑层 | 内容 | 变化频率 | 物理位置 |
| --- | --- | --- | --- |
| L-1 水印 | 页底色 + 水印（文字/平铺/图片） | 设置时（极少） | **一张共享的页大小位图**，作为页光栅的底 |
| L0 内容 | 页边框、格线、字形、原子框 | 编辑时（带级） | 页画布 |
| L1 装饰 | 搜索高亮、批注锚点、拼写波浪线 | 查找/批注时 | 合成进 L0 的矩形（暂不单独建层） |
| L2 瞬态 | 选区、光标、表单标记 | 每次按键 / 530ms | 合成进 L0 的矩形 |
| L3 宿主 | IME textarea、无障碍、工具栏 | 各自 | DOM（已有） |

水印看起来像"最底下一层"，但它**不该是第二张画布**。原因：内容位图不透明（页底色 + 字），
要让下面的水印透出来，内容层必须带 alpha —— 字形抗锯齿混的是水印色还是透明、`selfCheck`
的语义、"内容层 == 文档的纯函数"这条不变量全要改。而静态水印只要**一张共享位图做光栅底**
就能拿到同样的画面：页光栅的起点从 `fillRect(页底色)` 换成 `blitFrom(水印位图)`，每页多一次
与原来同面积的 memcpy，水印本身只光栅一次。真正的第二张底层只在"水印动态变化（每页不同 /
随时间变）"或"必须盖在文字之上"时才成立。

具体三条：

1. **上屏从"整页"改成"矩形列表"**。这是最便宜、收益最大的一刀，与选 A/B/C 无关。
   5B 的接口就应该是 `pageDirtyRects(page) -> [{x,y,w,h}]`，不是单矩形 bbox、
   更不是整页。光标一次从 1.13 Mpx 降到几十像素；打字从整页降到行带（排版已经有
   `band_y0/band_y1`）。
2. **瞬态不进内容位图，但要经过内容位图合成**：合成在引擎里做（B），保证逐字节一致，
   不让浏览器合成器参与像素账。
3. **装饰层先不单独建**。等搜索/批注真的出现、且"改高亮会重光栅整页"成为实测瓶颈时，
   再按 A 的形状加一张稀疏层——那时它已经有独立的更新频率，符合"同频同层"。

### 什么时候才真的需要第二张像素层

- 页上有**昂贵且几乎不变的图片内容**（扫描件底图、签名图）：拆成背景层，打字不重画它。
  注意水印不走这条路——它是文本/平铺图案时，共享位图足够，见上。
- **批注/评论**独立更新：与 PSPDFKit 的 overlay mode 同一个理由。
- **协同光标**：数量多、频率高、面积小，DOM 或独立小 canvas 都行。
- **GPU 化之后**：层变成纹理/瓦片，成本模型换一套，那时再按 Figma 的瓦片思路重排。

现在这几条都还不成立：内容是纯文字 + 表格线，重光栅一页 8–9 ms，且已经是带级增量。
